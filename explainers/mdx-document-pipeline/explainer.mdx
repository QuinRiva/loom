# How an `.mdx` file becomes a rendered, annotated, lint-gated document

An `.mdx` plan, recap or explainer is a markdown file that may use **33 block tags** and nothing else. When the file panel opens one, it goes through **five stages**: the panel **reads** it, a Web Worker **compiles** it while a guard throws out anything executable, the main thread **runs** the result against a closed list of block components, the rendered DOM is **stamped** so every block and sentence has an address, and the annotation layer turns a reader's gesture on that output into a **review comment** the agent receives on the next turn. The lint script runs stages 2 and 3 off-app, plus a static render, so an author sees a broken document before the reader does.

The sentence to carry: **security is decided at compile time in the worker — before any code exists — and at run time by the closed registry; the lint gate reuses both; annotation lives entirely in the rendered DOM and never touches the file.**

One thing to know before reading on: there is one known gap in the guard, stated in §2.2 without a recommendation, because a decision on it is pending.

## 2. How it works, following one file

### 2.1 Read — the panel hands the source to the MDX renderer

**Input:** a path ending in `.mdx` opened in the file panel. **What happens:** the panel always routes it to the MDX renderer wrapped in the annotation layer (`FilePreviewPanel.tsx` → `MdxPlanAnnotationLayer` → `MdxPlanRenderer`). It never falls back to the plain-markdown viewer, because that viewer shows every block tag as literal escaped text and would present a healthy document as broken. The read budget is **8 MiB**, the server's ceiling for plan previews; the lint warns above 6 MB. **Output:** the source string, unchanged, plus the document's directory so an `<Image src>` can resolve relative to the file.

The frontmatter is the first thing the next stage sees. `remark-frontmatter` parses the leading YAML block into an inert `yaml` node that MDX never renders — so the `reader:` brief at the top of this document, and a signing manifest, sit in the file without appearing on screen. Without that plugin the three dashes would render as a horizontal rule and the YAML as body text above the title.

### 2.2 Compile — a worker runs the guard and stamps heading ids

**Input:** the source string. **What happens:** `planCompileClient.ts` posts it to one shared Web Worker (`compileWorker.ts`), created on first use and kept for the page's life; where there is no `Worker` (server-side render, tests) the same compile runs on the calling thread with the same plugins. The worker calls `@mdx-js/mdx`'s `compile` with the plugin set in `mdxCompileOptions.ts` — frontmatter, GitHub-flavoured markdown, the two guard passes, and heading anchors. **Output:** a JavaScript function-body **string** plus a map of heading slug → source byte range. Nothing has executed; the string is inert until stage 3.

The guard is three layers, in this order:

<Columns>
  <Column>
    <Card heading="Reject" badge="THROWS" tone="risk">
      `import`/`export`, a `{expression}` in the body, a `{...spread}` attribute, or an attribute expression that is not a literal — a string, number, boolean, array or object, or a template literal with no `${}`. Any of these aborts the whole compile; the reader sees an error card instead of the document.
    </Card>
  </Column>
  <Column>
    <Card heading="Rewrite" badge="ERROR CARD" tone="warning">
      A capitalised tag not in the 33-tag list becomes `UnknownPlanBlock` with the original name as its `tag` attribute; its attributes and children are dropped. One typo degrades one block, instead of hitting MDX's missing-component throw and killing the page.
    </Card>
  </Column>
  <Column>
    <Card heading="Left alone" badge="KNOWN GAP" tone="neutral">
      Lowercase tags are not inspected. MDX treats them as HTML elements and React renders them. A document containing `<iframe src="https://example.com">` renders a live iframe, and the lint gate reports `OK — no findings`. A decision on closing this is pending.
    </Card>
  </Column>
</Columns>

Why the attribute rule is load-bearing: `code={"…"}` compiles to a JavaScript expression in the output module, and the body-node walk never visits it. The literal-only check is what stops `code={fetch("/api/secrets")}` from running at render. Here is what the two rejecting paths say, verbatim, for a document that writes `Cost is {1 + 1} dollars.` and the `fetch` attribute:

### 2.3 Run — the main thread instantiates it against the closed registry

**Input:** the function-body string. **What happens:** `runPlanModule` calls MDX's `run`, which uses the `Function` constructor — so the render needs `unsafe-eval`. The web app sets no CSP on its own page today, so the guard plus the registry are what bound what that eval can reach; the desktop shell does set one (`apps/desktop/src/electron/ElectronProtocol.ts`), and its `script-src` allows only `'wasm-unsafe-eval'` — whether documents run there was not checked for this explainer. The resulting `MDXContent` component is rendered with `components={PLAN_BLOCK_COMPONENTS}`: the 33 registry entries, an `img` override so markdown images resolve like `<Image>`, a `pre` override so fenced code gets syntax highlighting, and the `UnknownPlanBlock` card. **Output:** React elements inside one error boundary keyed on the source, so a corrected file re-renders fresh.

Each registry component does the same three things (`makeBlockComponent` in `registry.tsx`): parse the props with the block's zod schema, on failure render an error card carrying `data-plan-block-error`, on success call the block's `Read` with the clean data. The prose between a block's tags reaches `Read` as `children` only for blocks that declare it (`Callout`, `Card`, `Details`, `Columns`, `TabsBlock`, `Endpoint` and the canvas containers); a self-closing block gets none. An authored `id` becomes the block's `data-plan-block-id`; without one, stage 4 assigns one.

What the schema says when a prop is wrong — this is the message the error card shows for `<Callout tone="loud">`, and the lint quotes the same text:

### 2.4 Stamp — ids, bleed and the outline, after mount

**Input:** the rendered DOM under one `data-plan-root` container. **What happens:** three passes in `MdxPlanRenderer.tsx` run after each render.

- `assignBlockIds` walks the root's direct children — headings, paragraphs and blocks alike — and any nested element carrying `data-plan-block-type` (a block inside `Columns`, a tab, a card), giving each without an authored id a `plan-block-N` from one document-wide counter. The walk is deterministic, so the same DOM yields the same ids and a persisted comment still finds its block after a re-render.
- `stampBleedingBlocks` marks the **top-level** blocks allowed to escape the prose column with `data-plan-bleed`: `hug` for code, diffs, tables, file trees, JSON, Mermaid and `Columns` (take the width the content wants, up to a budget); `stretch` for canvases and iframes (take the budget). Prose-bearing blocks — callouts, cards, checklists, details, question forms — deliberately stay at the readable measure, and nothing nested inside a container bleeds.
- `readOutline` collects the top-level `h2` elements; a document with **four or more** gets a sticky row of section chips above the page, outside the root so it takes no block id and adds no text to the annotation search space.

**Output:** for the example file, four top-level nodes with ids `plan-block-0` to `plan-block-3`, and this markup (classes trimmed):

### 2.5 Annotate and decide — a gesture becomes a review comment

**Input:** one of three gestures on the stamped DOM — a text selection, a hover-and-click on a block's comment affordance, or a click in a `<QuestionForm>` option or a `<ReviewChoice>` verdict. **What happens:** all three converge on the same object, a review comment of kind `mdx-anchor` added to the **viewing thread's composer draft**. It shows as a removable chip; on send it is serialised into the user turn as a `<review_comment>` element carrying the anchor as JSON, the reviewer's words, and the quoted passage in a fence. Nothing is written to the file, which is why a document in another worktree can still be annotated from here. **Output:** the agent's next turn opens with the comments, each one locatable.

The anchoring engine (`annotation/anchoring.ts`) decides how a comment finds its place again after a re-render:

Flattening is the detail that makes text anchors readable: the document's text nodes are joined with a newline at every block boundary (paragraph, list item, table cell, heading), so a quote across two cells reads as two lines rather than `budget120`, and the same function is used to capture and to re-find. On every layout change each pending comment is re-resolved; one whose quote is gone degrades to a **detached** card, and one inside a closed `<Details>` or hidden tab becomes a **collapsed** badge on the disclosure's summary that opens it on navigate.

Selecting the words `kills the whole document` in the example file produces exactly this anchor (the section id is the heading's block id, and the context after runs into the next block's figcaption because of the newline rule):

Answers and verdicts ride the same channel with one twist: their comment ids are deterministic — `mdx-question:<file>:<questionId>` and `mdx-review:<file>:<itemId>` — so re-answering **upserts** rather than duplicates, and the comment's presence _is_ the state: removing the chip un-answers the question. The structured selection (which options, which verdict, the note) lives in a local draft store because the comment's prose is not losslessly parseable back. The "N of M decided" pill counts `<ReviewChoice` occurrences in the source against review comments present. The comment text the agent reads is one line, for example `Review A-1 → accept — "keep the gate"`.

### 2.6 The lint gate — stages 2 and 3, off-app, plus a static render

**Input:** `node apps/web/scripts/lint-plan.mjs <file> [--out render.html]`. **What happens:** two stages against the renderer's real module graph, loaded through Vite with a jsdom for the DOM globals.

1. **Lint** (`planLint.ts`): the size budget; a parse with the same remark set; a _warning_ when the `reader:` brief is missing; then AST rules — unknown tag with a did-you-mean, attribute resolution, each block's zod schema, unknown props (warning: zod strips them silently), slot nesting (`Tab` in `TabsBlock`, `Column` in `Columns`, canvas children), duplicate `id`s, duplicate `ReviewChoice` item ids, every question `refs[].anchor` against the heading slugs, `Diagram` edge endpoints, `Json` and `OpenApi` parse, `Mermaid` through the real Mermaid parser, ragged `Table` rows, and a dry run of the wireframe sanitiser reporting what it would strip. If no error was found it runs the **same compile** as the worker (`compilePlanMdx`) as the authoritative gate.
2. **Render**: only a lint-clean document reaches it. `renderToStaticMarkup` through the real registry with `<Details>` forced open; it scans the HTML for `data-plan-block-error` cards (a prop failure lint could not see, such as prose children), `<Image>` files missing on disk, and rendered-text defects — literal `\u2014` escapes and latin-1 mojibake — and prints the block types that mounted.

**Output:** `file:line:col severity: message` lines; exit 0 means the document renders in-app. `--out` writes the same markup as a standalone dark page with the app's stylesheet inlined. For the deliberately broken file from §2.2 with the `tone="loud"` callout added:

### 2.7 The escape hatches — where author HTML is allowed, and what guards each

Three blocks accept raw HTML from the author. The guard in §2.2 passes that HTML through unread — it is a string attribute, which is data — so each surface has its own boundary:

The wireframe surface sanitises _because_ it injects into the live DOM, which is what gives it the same geometry model as prose for annotation. `HtmlBlock` is same-origin so the host can read into it and pin a comment to one card; that is safe only because nothing in it can execute, so the remaining risk — the frame's own requests being credentialed — is closed by the CSP and the navigation guards. Mermaid output gets a light second pass over the SVG, but Mermaid's own strict mode is the real boundary there.

## 3. What this means for you

If the decision in front of you is which blocks to add, this is where a new block plugs in and what it gets for free:

- **One registry entry, one tag name, one zod schema** (`registry.tsx`, `planBlockTags.ts`, a file under `blocks/`). The tag list is a React-free copy of the registry because the worker cannot import components; a test asserts the two sets match. The generated `block-schema.md` the skills read comes from these schemas.
- **Free from stage 4 and 5:** a `data-plan-block-id`, the per-block comment affordance, whole-block anchoring, and lint's prop validation and unknown-prop warning.
- **Two opt-in decisions per block:** whether it bleeds past the prose column (`BLEED_MODE_BY_BLOCK_TYPE` in `MdxPlanRenderer.tsx` — a block not listed stays at the measure), and whether text inside it is quotable (`OPAQUE_BLOCK_TYPES` in `anchoring.ts` — listed blocks always anchor whole; everything else lets a reader highlight a phrase inside it). An inline device like a status pill inside a sentence would be a `mdxJsxTextElement`, which the registry already resolves, and a text anchor inside it works unchanged.
- **What is unaffected by any new block:** the guard, the worker, the composer channel, the lint script's two stages. A block that only renders and validates needs no change outside its own file and the two registries.
- **What to watch:** the lowercase-tag gap in §2.2; `unsafe-eval` at stage 3 if the web app ever sets a CSP, and the desktop shell's CSP, which already omits it; a Mermaid of more than about ten nodes stops reading, and it draws only in-app.

## 4. Open edges

- **The lowercase-tag gap** is stated in §2.2 as it stands; which way to close it, or whether to, is the pending decision and is not argued here.
- **Not covered:** the canvas `DesignBoard` with its connectors and free-floating notes (anchor kind `canvas`, resolved through a board-to-pixel transform the canvas renderer owns); `<Image>` signing through the thread's asset URL; the project's reference-link rules that linkify prose after the guards; the question-form section peek beyond the fact that it compiles a section slice through the same worker and renders it outside the plan root so it cannot disturb existing anchors.
- **A fact that is a reading of comments, not of behaviour I exercised:** that the annotation layer re-resolves on _every_ layout change is what the layer's header comment and the resize observer wiring say; I did not measure it. Everything quoted in §2 — the error messages, the compiled output, the rendered markup, the anchor JSON, the lint lines — was produced by running the real code on the example file.
