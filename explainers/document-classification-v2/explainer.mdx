# Document Classification v2 — How It Works

Your v1 system answers _"what type is this file?"_ — flat per-document labels, per company, via a LangGraph of prompt/invoke/parse nodes. That leaves downstream consumers (extraction, audit) to _guess_ at everything relational: which documents together form one legal instrument, which lease was superseded by which deed, which referenced side-deed was never supplied, whether "Oldco Pty Ltd" and "Newco Group" are the same landlord across time.

v2 answers _"what is the legal-instrument graph of this tenancy?"_. Per tenant it emits a typed **entity graph**: entities (instruments, with embedded sub-documents nested inside them), relationship edges between them, dated lifecycle events, documents concluded to be **missing**, explicitly **waived** expectations, and party substitutions — all validated against a 314-type taxonomy, with an LLM self-repair loop enforcing the taxonomy's obligations.

<Callout tone="success">
  **The core inversion:** v1 asked the model to label files and trusted the answer. v2 asks the
  model to assert a graph, then *machine-checks the graph against the taxonomy's declared
  obligations* and makes the model repair specific, named violations. Correctness is enforced by
  validators, not hoped for in prompts.
</Callout>

## 1. The 30-second shape

_Vocabulary gap — the HTML shows this as six boxes in a left-to-right row joined by arrows, each with a bold name and a muted one-line description inside the box; `Mermaid` is the closest native form, but with the descriptions inside the nodes the six-wide chain scales down to ~7px text in the reading column, so the boxes carry the names only and the descriptions follow as a list._

<Mermaid
  caption="The six pieces, in the order data flows through them"
  source={
    'flowchart LR\n  pfc["PFC output"] --> bucketer["Bucketer"] --> worker["Worker × N in parallel"] --> assembler["Assembler"] --> stage2["Stage 2"] --> reads["Two reads"]\n'
  }
/>

- **PFC output** — files grouped by tenant_id + building files (upstream, unchanged)
- **Bucketer** — one EntityBucket per tenant + one `__building__` bucket
- **Worker × N in parallel** — 3 LLM calls per bucket: phase 1, phase 2, adjudication
- **Assembler** — `corpus_classification.json`
- **Stage 2** — building→tenant matcher + party reconciler (2 more LLM calls, corpus-wide)
- **Two reads** — **native:** data extraction reads `corpus_classification.json` directly · **legacy:** converter also emits `aggregated_classification.json` for the not-yet-migrated readers

**Cost envelope:** per tenant, 1 phase-1 call + one phase-2 call per parent with a non-empty containment closure + an adjudication that is often free (no LLM call if the graph validates), then 2 per corpus; cached, bounded repair (max 7 validation attempts per call). **No LangGraph** — plain `asyncio.gather` with a semaphore (50 buckets).

## 2. Pipeline walkthrough

_Vocabulary gap — the HTML shows this as six numbered stage cards stacked with ▼ arrows between them, each title carrying a DETERMINISTIC (green) or LLM ×N (purple) chip; a stack of `Card`s with a `badge` and a `tone` per kind is the closest native form — the step numbers move into the heading text and the arrows are lost._

<Card heading="1 · Bucketer — bucketer.py" badge="DETERMINISTIC" tone="success">
  The **only** module that speaks PFC's vocabulary (`tenant_files`, `building_files`). Emits one
  `EntityBucket` per tenant, keyed by the production-stable `tenant_id` (dbt id or md5 fallback),
  slugged to a `bucket_id` used for cache keys and filenames. Building files are **partitioned, not
  duplicated**: a file PFC marked building-level is removed from every tenant bucket and placed in a
  single `__building__` bucket, which is classified through the same machinery (this fixed
  cross-building adjudication failures). A tenant whose *every* file turned out building-scoped is
  **dropped** — the one legitimate absence downstream joins must tolerate, and the reason extraction
  makes the identical cut on the file map before joining. Bucket-id collisions raise rather than
  silently shadowing a tenant; `unresolved_files` (tenant-scoped but unidentified) are deferred with
  a warning, not classified.
</Card>

<Card heading="2 · Orchestrator — orchestrator.py" badge="DETERMINISTIC" tone="success">
  Loads the taxonomy into a filtered Pydantic view, sets up the cache and Langfuse tracing, then
  dispatches one worker per bucket via `asyncio.gather` bounded by a semaphore
  (`MAX_PARALLEL_BUCKETS`). **Tenant-level failure is strict; corpus-level is not fail-fast** —
  complete buckets are written, failed buckets get debug sidecars under `_debug/failed_tenants/` and
  a `FailedEntityBucket` record in metadata, and a rerun replays cached successes.
</Card>

<Card heading="3 · Worker — worker.py (the heart; see next section)" badge="LLM ×3" tone="accent">
  Classifies one bucket end-to-end: phase 1 (standalone instruments), phase 2 (embedded
  sub-documents per parent), then a single adjudication of the assembled graph against the **full**
  taxonomy. Programmatically stamps `tenant_id` / `tenant_name` from the batch key after the LLM
  turns *and* on every cache hit (a cached artefact may predate the field or have been produced
  under a different tenant_id — tenant_id is not part of the cache key). Both fields are `DERIVED —
  do not populate` in the schema: tenant identity is an upstream fact (PE-1369) the model can never
  influence.
</Card>

<Card heading="4 · Assembler — assembler.py" badge="DETERMINISTIC" tone="success">
  Pure function: wraps the per-bucket results in a metadata envelope (taxonomy provenance,
  completeness status, failed buckets) → `corpus_classification.json`. Buckets sorted by
  `tenant_id`, `__building__` last.
</Card>

<Card
  heading="5 · Stage 2 reconciliation — building_tenant_matcher.py + party_reconciler.py"
  badge="LLM ×2"
  tone="accent"
>
  Two corpus-wide passes that **self-gate on a complete corpus** (a half-seen corpus must not
  testify about links or succession). Each is deterministic candidate generation + ONE bounded LLM
  adjudication + a typed validated store. Details below.
</Card>

<Card heading="6 · Legacy converter — legacy_output.py" badge="DETERMINISTIC" tone="success">
  Written alongside `corpus_classification.json` on every run. Maps the entity graph down to the v1
  `aggregated_classification.json` contract so the readers that have *not* migrated
  (Exlake/DataNexus ingest, the tenant audit's classification context) are untouched by the swap.
  The one judgement call — `active` *recomputed* from dated lifecycle events at an `as_at` date (v2
  deleted the point-in-time boolean) — now lives in `liveness.py`, shared with the native extraction
  read so the two cannot drift.
</Card>

## 3. The three-call architecture (per bucket)

The key architectural invariant, worth internalising because most design questions trace back to it:

<Callout tone="info">
  **Slices shape prompts; obligations are adjudicated once, against everything.** Each pass sees a
  *narrowed taxonomy slice* (fewer candidate types → less run-to-run variance), but the slice only
  shapes the prompt. No obligation checking happens per pass. The concatenated graph is validated
  ONCE against the FULL taxonomy — so a narrowed menu can never truncate a necessity challenge, and
  a role can never end up both edged and waived.
</Callout>

_Vocabulary gap — the HTML shows the three calls as a three-column panel grid, each with a heading and a muted "Schema · slice" line; `Columns` of three `Card`s with the schema and slice as `meta` chips is the closest native form — three columns in the ~850px reading column are narrow._

<Columns>
  <Column>
    <Card heading="Call 1 — Phase 1: standalone" tone="accent" meta={["Schema: StandalonePass", "slice: the 181 standalone types"]}>
      Classifies top-level instruments only. Because this is the **only pass that reads every document in full**, it owns three bucket-wide obligations:

      - **Document accounting** — every input filename appears exactly once: on an entity's `source_documents` or in `unclassified_documents` with a reason.
      - **Content-first missing-document scan** — the pipeline's *primary* missing-doc signal: verbatim quotes of in-content references to absent documents.
      - **Party-substitution scan** — in-document succession assertions ("the Lessor's interest was assigned to…").
    </Card>

  </Column>
  <Column>
    <Card heading="Call 2 — Phase 2: embedded" tone="accent" meta={["Schema: GraphFragment", "slice: parent type + containment closure", "one call per parent"]}>
      For each standalone entity with a non-empty containment closure, extracts the sub-documents *within* it (clauses, schedules, embedded guarantees) against only the parent type + what may transitively nest inside it. The parent is passed as **read-only context** — never re-emitted. Child entity ids are prefixed (`parent__child`) at assembly so siblings under different parents can't collide.
    </Card>
  </Column>
  <Column>
    <Card heading="Call 3 — Adjudication" tone="accent" meta={["Schema: EntityBucketClassification", "FULL taxonomy", "often zero LLM calls"]}>
      The passes are concatenated and validated. **If validation passes, no LLM call happens at all.** On failure, ONE stitcher `aupdate` repair session runs: the model sees the whole graph plus every violation class at once and patches it. This is where taxonomy-expectation missing documents and waivers get added — and where phase-1 content findings are protected from being dropped (see below).
    </Card>
  </Column>
</Columns>

### Prompt construction — `prompts.py` + templates

- **Three honest system prompts** (phase1 / phase2 / adjudication), not one template with a retracted scope note. Each tells the model its place in the three-call architecture so its output composes with the others.
- **Schema-first principle**: field-level instructions live in Pydantic `Field(description=...)` strings, not in the templates. The four LLM-visible channels (class docstrings, field descriptions, validator error strings, Jinja templates) may only use _invented_ examples — evaluation-corpus content can never leak into the prompt.
- **Taxonomy as compact JSON** in the system prompt, with uniform empty-elision (nulls never serialised). One deliberate omission: `document_scope` stays off the classification prompt — it is Stage-2-only metadata.
- **Prompt-cache lever**: types are emitted standalone-first, so phase 1's taxonomy block is a byte-for-byte _prefix_ of the adjudication prompt and the provider's implicit prefix cache carries across passes.
- **The when-gate rule** (v2.26): a target's `applicability_condition` is a factual trigger — if the condition is unmet, the role is _waived_, not "missing". This is what lets a government tenant correctly waive commercial-only expectations while a commercial tenant emits them.

## 5. Validation & the repair loop

The schema hierarchy separates what one pass extracts from what the whole graph must satisfy:

<Code
  language="text"
  caption="The schema hierarchy, and which validators run at each level"
  code={
    "GraphFragment                    structural only: entity-id uniqueness, referential integrity\n  └─ StandalonePass              + bucket header, unclassified_documents, document accounting\n       └─ EntityBucketClassification   + the whole-graph validators (adjudication only):\n            • taxonomy integrity        every type_id / role_id / target drawn from the taxonomy\n            • necessity challenge       every `required` role resolved via an explicit channel\n            • lifecycle challenge       co-existing same-family instruments chained or waived\n            • no-edge∧waive guard      a role cannot be both satisfied and waived\n            • content-survival arm      phase-1 missing docs cannot be silently dropped\n"
  }
/>

<Callout tone="info">
  **Everything at once, in one error.** `_validate_against_taxonomy` aggregates all violation
  classes into ONE raised error (integrity + necessity + lifecycle + dropped-content, as markdown
  sections). Historically these were sequential validators; Pydantic stops at the first failure, so
  the model never saw necessity errors until integrity cleared — producing "class ping-pong" that
  burned the repair budget. One combined error lets one repair plan address everything.
</Callout>

### How a repair turn actually works (stitcher 0.0.16)

_Vocabulary gap — the HTML shows the repair turn as three boxes in a left-to-right row joined by arrows; `Mermaid` is the closest native form — the inline code in the patch-op shape is lost in the label._

<Mermaid
  caption="One repair turn: validate → patch prompt → apply + revalidate, looping until clean or 7 attempts"
  source={
    'flowchart LR\n  v["1. Validate<br/>Pydantic raises the combined markdown error"]\n  p["2. Patch prompt<br/>model sees its previous JSON + the current errors,<br/>replies with JSON-Patch ops {op, path, value}"]\n  a["3. Apply + revalidate<br/>patch applied to the dict, validated again;<br/>loop until clean or 7 attempts"]\n  v --> p --> a\n'
  }
/>

- **Native since 0.0.16** (upstreamed from the pipeline, subclass deleted): shape-informed apply-failure feedback (on a bad JSON-Pointer the model is shown the _actual current value_ at the failing path), a separate inner apply-retry budget (3) so mechanical pointer errors never burn semantic attempts, repeated-error rollup (explanation once + a path list), and `initial_error` seeding via the `aupdate` kwarg.
- **No validation state in the system channel.** The adjudication `SystemMessage` carries durable task guidance only; the initial error seeds turn 1's patch prompt and is replaced by the real current error each turn — a pinned error would go stale and mislead later turns.
- **Content-first findings are load-bearing.** The repair regenerates the whole document, so it could silently drop a phase-1 `referenced_in_content` entry while adding a taxonomy expectation. The pre-repair entries are threaded into validation context as `preserved_content_missing_docs` (keyed on verbatim `reference_text`, as a multiset) and the survival arm fails any repair that loses one.
- **Shape-coaching** (v2.27): the terminal failure shapes seen in benchmarks — bare strings in `unmet_roles`, bare items in `lifecycle_events` — get recovery-first error messages that show the exact accepted object shape, so one repair turn fixes them.
- **Affirmed emptiness**: at fresh-generation boundaries, an omitted or null scope list is rejected ("emit `[]`") — "scanned, none found" stays distinct from "never considered", with no sentinel strings on the wire.

## 6. Corpus-level reconciliation (Stage 2)

Both stages share one shape — **deterministic, unit-tested candidate generation → ONE bounded LLM adjudication → typed validated store** — and both run only on a _complete_ corpus (enforced twice: in code and by the store validator).

_Vocabulary gap — the HTML shows the two reconcilers as side-by-side panels with a muted file-name line under each heading; `Columns` of two `Card`s with the file names as `meta` chips is the closest native form._

<Columns>
  <Column>
    <Card
      heading="Building→tenant matcher"
      tone="neutral"
      meta={["building_tenant_matcher.py", "relational_eligibility.py"]}
    >
      Links relational building-level documents (a per-shop floor plan) to the tenant lease(s) they
      concern, and reattributes PFC misfiles. The over-linking guard is **type + asset-class aware**
      eligibility: a thermographic survey is relational in retail but whole-building in office —
      only `(type, asset_class)` pairs with an explicit spec are ever candidates. The LLM judges
      only the semantic step (premises correspondence: "Shop 248" ≈ "T248"). Output:
      `building_tenant_links` + `unresolved_building_docs`.
    </Card>
  </Column>
  <Column>
    <Card heading="Party-identity reconciler" tone="neutral" meta={["party_reconciler.py"]}>
      Links (never merges) party surface forms across buckets on exactly **three evidence bases**:
      explicit substitution text (up to high confidence), a shared ABN/ACN (up to high), or a
      synchronised role-transition corroborated across ≥2 independent tenancies (capped at medium).
      The discipline is **structural, not prompt hope**: name similarity and world knowledge
      generate nothing because no basis in the enum fits them, and the verdict×basis compatibility
      table is code-enforced at build and re-checked at rest. Output: `party_identity_links` +
      `unreconciled_party_groups`.
    </Card>
  </Column>
</Columns>

<Callout tone="info">
  **The `reconciliation_ran` marker.** An empty store with `reconciliation_ran=true` means
  "genuinely nothing to link"; with `false` it means "never ran" — the distinction a completeness
  gate needs, since both stages self-gate and silently produce nothing on a partial corpus. (The dev
  line's `splice.py`, which re-runs one flaked bucket and must therefore clear the stores plus this
  marker, was deferred off the rollout train and is **not** in the shipped tree: production handles
  a flaked bucket by rerun-with-cache.)
</Callout>

## 7. Downstream: one native reader, one legacy shim

The rollout no longer has a single downstream path. Since `ee207aae1` (2026-07-30) **data extraction reads the v2 artefact natively**; the legacy converter continues to serve the readers that have not migrated.

<Columns>
  <Column>
    <Card heading="Extraction — data_extraction/classification_view.py" badge="NATIVE" tone="info">
      Owns the *entire* v2 read: Pydantic-validates `corpus_classification.json`, computes
      per-entity activeness at the run date, and projects one `TenantClassificationView` per tenant

## 8. Caching, retries, failure containment

_Vocabulary gap — the HTML shows these as a three-column panel grid; `Columns` of three `Card`s is the closest native form — three columns in the reading column are narrow._

<Columns>
  <Column>
    <Card heading="Cache — runtime/cache.py" tone="neutral">
      Per-bucket `FileBatchCache`. The key is the invalidation contract:

      - `PROMPT_VERSION` bump → everything misses
      - taxonomy file hash change → everything misses
      - one bucket's documents change → only that bucket misses
      - code-only changes → hits

      `PROMPT_VERSION` (now v2.27.0) is bumped whenever *any LLM-visible byte* changes; `PIPELINE_VERSION` (now v2.4.0) is the second axis, recording code releases that deliberately do *not* invalidate the cache. `config.py` carries a running changelog of every bump on both axes and every deliberate non-bump. Production runs from scratch: Exlake's `--reset` / `--force-cache-rebuild` are accepted as aliases that disable caching, exactly as `--no-cache` does. Fan-out is `MAX_PARALLEL_BUCKETS = 50`.
    </Card>

  </Column>
  <Column>
    <Card heading="Two retry layers" tone="neutral">
      - **Inside stitcher**: up to 7 validation attempts per call (semantic repair), with an inner 3-try apply budget for mechanical patch failures.
      - **Outside** (`runtime/retry.py`): transport-level retry for provider errors (deadline, empty response, max-tokens), wrapping the whole attempt.
    </Card>
  </Column>
  <Column>
    <Card heading="Failure containment" tone="neutral">
      A bucket that exhausts everything raises `BucketClassificationError` carrying the stage, attempt count, the assembled graph and the final validation error — written as a debug sidecar. The corpus completes partial; completeness metadata gates Stage 2; a rerun replays cached successes and retries only the failure.
    </Card>
  </Column>
</Columns>

**Tracing:** every LLM call is a single named Langfuse generation span (`docclass.phase1` / `phase2` / `adjudicate` / `patch`), tagged by corpus, tenant and phase — one trace per corpus run.

## 11. Q&A crib sheet — likely questions, defensible answers

_Vocabulary gap — the HTML shows these as collapsible question panels, the first one open; `Details` is the native equivalent._

<Details summary='"How do you stop the LLM inventing document types or relationships?"' open>
  Taxonomy integrity is a validator, not a request: every `type_id`, `role_id` and edge target must
  exist in the taxonomy or validation fails and the model must repair. A genuinely novel
  relationship has one legal escape hatch — an emergent-role *object* with declared fields — so
  nothing degrades into free text. Judged result across all gold corpora: zero hallucinated
  findings.
</Details>

<Details summary={'"What happens when a required document just isn\'t there?"'}>
  The necessity challenge forces every `required` role into exactly one explicit channel: an edge
  (it's present), a `missing_documents` entry with an `unmet_roles` claim (it's absent but evidenced
  or expected), or a `waived_expectations` entry (it genuinely doesn't apply, with reasoning — e.g.
  an applicability condition that isn't triggered). Silence is not an option; the validator rejects
  an unresolved required role and the repair loop makes the model choose a channel.
</Details>

<Details summary='"Why three LLM calls instead of one big one?"'>
  Variance and honesty. One call against 314 types produced unstable classifications; narrowing each
  pass's menu (standalone slice, then parent+closure) reduces run-to-run variance. But narrowing
  prompts is dangerous if it also narrows *checking* — so obligations are deliberately adjudicated
  once against the full taxonomy, where the slices can't hide anything. The third call frequently
  costs nothing: if the assembled graph validates, no adjudication LLM call is made.
</Details>

<Details summary='"How does the repair loop work, and how do you know it terminates?"'>
  Failed validation → the model gets its previous JSON plus a combined markdown error naming every
  violation → it replies with JSON-Patch operations → apply, revalidate, repeat. Bounded at 7
  validation attempts; mechanical patch-apply failures get their own inner 3-try budget with
  shape-informed feedback (the model is shown the actual value at the failing pointer), so pointer
  typos can't burn semantic attempts. Total LLM calls ≤ 7×3 per extraction. All of this now lives
  natively in stitcher 0.0.16.
</Details>

<Details summary={'"Is it deterministic? What\'s actually cached?"'}>
  LLM outputs are not deterministic; the architecture contains the variance (narrow slices, single
  adjudication, validators as hard rails) and the evaluation is judged semantically against gold
  rather than byte-compared. Caching is per bucket, keyed on prompt version + taxonomy hash +
  domain-context hash + the bucket's documents (contents, not just paths) — so a rerun replays every
  unchanged bucket byte-identically and re-runs only what changed. Production runs from scratch:
  Exlake passes `--reset --force-cache-rebuild`, accepted as aliases of `--no-cache`.
</Details>

<Details summary='"How can you swap this in without breaking consumers?"'>
  Two answers, because the answer changed. For consumers that have *not* migrated, the converter
  emits the exact legacy `aggregated_classification.json` contract alongside the new artefact — same
  shape, same fields, `active` recomputed from lifecycle events at the run date — so they never
  learn the classifier changed. Data extraction, the biggest consumer, was then migrated properly:
  it reads `corpus_classification.json` directly, with no compat shim and no dual-shape detection,
  and every contract corruption stops the run loudly. The Exlake cutover itself was a one-line
  command-token flip (now landed) whose revert is the rollback; both classifiers remain deployed in
  the same image.
</Details>

<Details summary='"What stops the party reconciler merging two companies that just have similar names?"'>
  Structure, not prompting. Links are generated only from three closed evidence bases — explicit
  substitution text, shared ABN/ACN, or a synchronised role-transition corroborated across ≥2
  independent tenancies — and the verdict×basis compatibility table is enforced in code at store
  build and re-checked at rest. Name similarity has no basis in the enum, so a confident merge on
  names alone is structurally impossible. And it links; it never merges records.
</Details>

<Details summary='"How is this evaluated?"'>
  Benchmark-first: judged gold corpora over 5 real buildings, semantic LLM judging (never string
  matching), frozen evidence directories per prompt version under
  `/home/Carl/data/lease_extraction/_eval_*`. Current anchor: v2.27 gate at 131/133 pooled vs
  129/133 baseline, zero hallucinations, plus a targeted repair-path re-gate for the stitcher 0.0.16
  migration. Unit tests exist only for at-rest contract corruption and rare-LLM-shape determinism —
  correctness claims rest on the judged benchmarks. Since the gate, the rollout added platform-scale
  validation on `develop`: a 13-tenant building (040049) run end-to-end on the native path with a
  fix-isolating baseline diff over 364 fields, an over-firing control building (002338), and a
  5-building v2-vs-v1 regression batch where every consistency-eval gate passed (llm_variance
  1.8–10.2% against a 15% threshold). Those are rollout evidence, not a re-run of the judged gate.
</Details>

<Details summary='"What are the known weak points?"'>
  Honest list: (1) one adjudication bucket still converges at exactly the 7-attempt ceiling on the
  densest corpus — zero headroom, a watch item; (2) two known-flaky role-selection/landlord-identity
  items (NEURO-E9, CORP-A1) that predate the current version; (3) `unresolved_files` from PFC are
  deferred, not classified; (4) mega-tenants past the 1M-token context (~1 in 500) fail loudly per
  bucket rather than being split; (5) taxonomy prompt-copy and validator must move in lockstep —
  drift between them creates unwinnable repair loops, so taxonomy syncs are atomic PRs; (6)
  **doc-type vocabulary coupling downstream** — v2 emits `lease_agreement` while
  `models/data_schema.json`'s `authoritative_source_document_type` vocabulary is still v1
  (`commercial_lease_agreement`). Harmless where the mapping is semantic (the LLM bridges the
  names), but `data_extraction/processor.py:650` (`_build_entity_document_type_map`) is the one
  place a doc-type string is a literal set-membership key: inert at the default
  `--doc-selection=all-documents`, live under the `active-only` / `active-plus-recent-inactive-tail`
  token-limit escape hatches.
</Details>
