# Upstream has no "keep it off the phone" list: the phone is a remote, and gaps are bugs

T3 Code's maintainers have written down one hard limit on mobile: **the phone is a remote and never runs the agents**. Everything else points the other way. They sell the app as "pretty much the full power of the desktop app". Their contributor rules call a feature missing from one client a defect. In practice a mobile gap gets filed as a bug ("expected: same as web") and fixed within weeks.

So most of what feels constrained on your phone is not a decision upstream made. It is one of three things:

- Loom's own features that were never ported (covered in the earlier explainer).
- Upstream features that shipped on web first and haven't reached mobile yet.
- Interactions that need a mouse or keyboard and have no touch version yet.

**Stated** below means a maintainer wrote or said it, quoted with its source. **Inferred** means I read it from what is present and absent in the code and docs. Theo's spoken remarks come from a transcript or a third-party summary of his streams, and each is marked as one or the other.

## 1. The phone is a remote for a machine that does the work

**What it is.** The phone never hosts T3 Code or runs an agent. It pairs with a server on another machine and drives it. That machine also holds the provider logins and command-line tools.

**What it explains.** Why the install guide says to set up the computer first and to sign providers in "in the web or desktop app", and why the FAQ's answer to "my provider is missing" is "(Not your phone. The computer.)". <Sidenote>Upstream `docs/user/install.md` (Mobile app, Providers) and `docs/user/faq.md`. The phone can now sign some providers in under Settings → Providers, so even this has softened.</Sidenote>

**Justification (stated).** The FAQ: "The phone is a remote. Your computer does the work and needs to stay on." <Sidenote>`docs/user/faq.md`, "How do I use T3 Code on my phone?" on [GitHub](https://github.com/pingdotgg/t3code/blob/main/docs/user/faq.md).</Sidenote> Theo gave the reason in May, before the native app existed: "the problem we're trying to solve with remote control is what happens when I shut my laptop and an agent is running. I want to open and see the result. I don't want it to get stopped." He framed the alternative, a terminal over SSH on a phone, as the thing to beat: no worktrees without hand-written git, no image pasting. <Sidenote>Theo, "How I code with AI changed a lot", 27 May 2026, [transcript](https://rosetta.to/u/t3dotgg/how-i-code-with-ai-changed-a-lot).</Sidenote> That is why the phone app has a terminal, worktrees and image attachments rather than a slimmed-down chat.

## 2. Parity is the default, and a gap is a bug

**What it is.** A feature on web is expected on mobile too. When it's missing, that is treated as a defect, not a product choice.

**Example.** On the phone, a thread waiting on background work showed only "Waiting on 4 monitors"; tapping did nothing. A user filed it as "web lists each item"; a core contributor's fix added a sheet listing each item and a Stop button. <Sidenote>Issue [#21342](https://github.com/pingdotgg/t3code/issues/21342), fixed by [#21395](https://github.com/pingdotgg/t3code/pull/21395) ("fix(mobile): expose background work and thread status actions").</Sidenote> The same batch includes "fix(mobile): bring model controls in line with web" and "show plans and fold settled progress notes" (the phone had been showing proposed plans as raw JSON). <Sidenote>[#21406](https://github.com/pingdotgg/t3code/pull/21406), [#21393](https://github.com/pingdotgg/t3code/pull/21393). Bug reports use an "Area: apps/mobile" field and typically state "Expected: the same as web", for example [#15380](https://github.com/pingdotgg/t3code/issues/15380).</Sidenote>

**Justification (stated).**

## 3. Web ships first; the phone first gets what lets you answer an agent

**What it is.** New features are built on web and reach mobile later, sometimes days later, sometimes about two months. When a feature arrives on the phone in part, the part that arrives first is the one that stops an agent waiting on you.

**Example.** Side chats (ask a side question without derailing a running thread) shipped on web on 31 Oct. Its PR says: "Mobile: the parent's thread screen lists its side chats, so you can answer their approvals from a phone. Starting one is web and desktop only for now." Starting one from the phone followed five days later. <Sidenote>[#26901](https://github.com/pingdotgg/t3code/pull/26901), then "feat(mobile): start side chats with /side" [#31709](https://github.com/pingdotgg/t3code/pull/31709).</Sidenote> The same ordering shows elsewhere: alerts go out when an agent finishes, fails, needs approval or asks for input, and approvals, questions (with attachments), secret requests and guest messages can all be answered from the phone. <Sidenote>Upstream `docs/user/mobile-notifications.md`, `question-attachments.md`, `secrets.md`, `guest-links.md`.</Sidenote>

**Two more lags, both since closed.** Linking a pull request to a thread shipped on web on 24 Aug and reached mobile on 18 Oct; the user guide still says it is web and desktop only, so the docs lag the code. <Sidenote>[#8160](https://github.com/pingdotgg/t3code/pull/8160) (web), [#20394](https://github.com/pingdotgg/t3code/pull/20394) (mobile); `docs/user/source-control.md` still reads "Linking and unlinking are available in the web and desktop clients."</Sidenote> At the store launch, Theo said subagent views were not built yet; the phone now has an Agents view. <Sidenote>Third-party summary of the launch stream, ["Big launch today"](https://www.youtube.com/watch?v=x_xJMlt_2Hc); current state in `docs/user/thread-sidebar.md`.</Sidenote>

**Justification.** The "for now" is **stated**. The reason for building web first is not stated anywhere I found. The obvious reading (**inferred**) is cost: web and desktop are one codebase, the phone is a second one, and the maintainers try features on web where they work all day.

## 4. Mouse and keyboard interactions get a touch version, or wait for one

**What it is.** Where web relies on right-click, hover, drag, a modifier key or a keyboard shortcut, the phone gets a touch equivalent. Where nobody has designed one, the feature is missing. Nobody upstream states this as a rule; it is the pattern in their own user guide.

The citation PR is the clearest case: it says mobile "renders sent quotes as readable blockquotes with the comment below; it doesn't create citations", and gives no reason. <Sidenote>[#9146](https://github.com/pingdotgg/t3code/pull/9146). **Not every gap is a touch problem.** **Edit from here** (rewind the conversation to an earlier message) is a button under a message, which works on touch. Its absence looks like unfinished work, not a decision.

## 5. A native app, plus what only a phone can do

**What it is.** Upstream chose a native app over the mobile web page it already had, and it uses the phone's own facilities rather than imitating web.

**Justification (partly stated).** In May, Theo: "We do have mobile web, and it works better than I would have expected. Julius is cooking a React Native app now." <Sidenote>Same May transcript as section 1.</Sidenote> The app has its own native terminal and diff renderer, and per platform look: "Mobile has its own themes and text, code, and terminal preferences. It does not follow environment themes or defaults," with Material You on Android. <Sidenote>Upstream `docs/user/appearance.md`; native terminal and diff surfaces arrived in the first mobile PR, [#2013](https://github.com/pingdotgg/t3code/pull/2013).</Sidenote> Why native beats a web page is not argued at length anywhere. Theo's demo post for the native build stressed "Running on awful 15mbps WiFi" and "Working in hell threads with 0 latency", which suggests responsiveness on poor connections is the point (**inferred**, from a post seen only via a [mirror site](https://www.24vids.com/video/real-world-demo-of-the-new-t3-code-mobile-build-running-on-awful-15mbps-wifi-p-tw-2085608364223172903)).

**Layout follows the window, not the device.** One app serves phones, foldables, tablets and resizable iPad windows. Under 600 points wide, the list is the root and pages push over it. Between 600 and 720, the list floats over the page. From 720 up, the list sits beside the page, with an optional third column. "A feature screen never asks which platform or window width it is on." <Sidenote>Upstream `docs/internals/mobile-layout.md`, added 3 Nov 2026. Theo reportedly uses a Samsung Z Fold unfolded for T3 Code (third-party summary of ["So my workflow has changed a lot"](https://finance.biggo.com/podcast/edd2a2fc77a07445)).</Sidenote> So on your Fold, folded is the phone layout, and unfolded should be wide enough for the side-by-side one (my estimate from the screen's size, not measured). Nothing is hidden because the screen is small; it is arranged differently.

**What the phone has that web doesn't.** This shows what upstream thinks the phone is for: being pulled back in when an agent needs you, and capturing things while away from the desk.

## 6. What upstream hasn't said

- **No list of features ruled out for mobile**, apart from running agents. I checked the user and internals docs, the contributor rules, the mobile PRs and the store copy.
- **A few settings stay on web with no reason given**: adding custom models, setting model prices, machine load balancing ("Mobile keeps its manual environment selection"), and turning on webhook signature checks ("mobile keeps an existing signature check but can't turn one on"). <Sidenote>Upstream `docs/user/composer.md`, `usage.md`, `remote-access.md`, `project-settings.md`.</Sidenote> They are all one-off setup you'd do at a desk, which is a plausible reason, but it is **inferred**. Provider sign-in was in the same bucket and has since come to mobile, so treat these as not yet ported rather than ruled out.
- **Find within an open thread, Edit from here, the Commits view in the diff pane, and the local servers list** are web-only with no stated reason and no touch obstacle. They read as unfinished.

## 7. What carries over to Loom's own features

Context for a later decision, not a recommendation:

- **The remote principle cuts against Loom today.** The phone is for being called back when an agent needs you. Loom's Needs-you and Accept? flags never push, so the phone misses the one job upstream built it for.
- **Answer-first ordering fits Loom well.** Following upstream, the first Loom pieces to bring across are the ones that unblock an agent (answering a carried-past question, accepting a child, clearing a flag), before the panels for building a workstream (goal editing, the graph).
- **"A gap is a bug" is already Loom's rule on paper.** Loom's `AGENTS.md` lists mobile under Hit every surface, and Loom's web-only features break it. Either the rule gets a Loom exception or the gap is debt.
- **Comments on plan documents hit the same wall as citations.** They depend on selecting text, which upstream hasn't solved on touch either. Expect that one to be hardest.
- **Every Loom change to the mobile app has to be re-merged at each upstream pull.** Upstream changed the mobile app 137 times in the eight days after Loom's last merge, so each Loom hunk there is likely to collide again.

## 8. Open edges

- **Spoken sources are second-hand.** The May quotes are from a caption transcript. The launch-stream and Z Fold remarks come from third-party summaries, not a transcript I checked.
- **Your build lags upstream.** Loom last merged upstream on 1 Nov. The three-way layout (list floats at medium widths, third panel becomes a sheet) landed upstream on 3 Nov, so your Fold shows the older two-step split for now. <Sidenote>Loom's `apps/mobile/src/lib/layout.ts` splits at 720 points wide and 600 tall; upstream's adds the 600–720 medium class.</Sidenote>
- **Upstream's docs trail the code.** The pull-request-linking line is stale, and other "web and desktop only" lines may be too. The code is the safer guide.
