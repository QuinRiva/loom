# Upstream's orchestration toolkit beside Loom's tools — coexistence verdicts

<Callout tone="decision">
**What is being decided.** Pull 9 adopts upstream's Orchestration V2 as Loom's substrate. Upstream ships 41 agent-facing orchestration tools across five MCP toolkits (`OrchestratorToolkit` 15, `ThreadToolkit` 17, `t3_thread_launch`, `PullRequestsToolkit` 5, `WorktreeToolkit` 3), plus six project-administration tools in `ProjectToolkit` that are judged as one group; Loom ships 23 of its own. The pull-9 strategy plan proposes withholding upstream's whole set so a model sees one delegation model per prompt. This document compares the two sets by the *move an agent is making*, gives one verdict card per upstream tool with the concrete failure if a model had both, and recommends what the plan should say instead.

## 1. The two models, side by side

Upstream's toolkit follows from one sentence (05 §1.1): *an agent is a thread mid-turn; while its turn is live it may start other agents, talk to any thread, and change threads that run within its own permissions; results come back as a pointer to read, not pushed text; the app owns workspaces, queues, schedules and durable records.* Everything a Loom reader needs to know about its lifecycle is in 05 §1.9's 21 checkable sentences. The ones that matter for coexistence:

- A delegated task exists only inside the parent's live turn (`parent_not_active`, L1). The child receives the parent-written task text, as a Loom child receives its brief (L2); it runs in the parent's checkout (L3), which matches where Carl wants Loom's children to run.
- Its result is published **once** — the child's most recently finished run at the moment the child first goes quiet (not "the first run"; L5, 05 §1.10 claim 2) — and never reopens (L6). The parent learns of it through a generic pointer message telling it to call `task_status` (L8); reading the result mid-turn cancels the queued wake (L12).
- Waiting is a first-class move: `delegate_task mode=wait` and `t3_thread_wait` poll until terminal or timeout (L10).
- Any thread in the environment can be read; writing to another thread needs the caller mid-turn and the target within the caller's permission modes (L14, L15 — widened by #15219 after the inventory's snapshot).
- Interrupting a thread **holds its queue** until a client issues `queue.resume`, which no agent tool can do (L17). Interrupting a parent means none of its delegated tasks will ever wake it (L11).
- Thread-toolkit decider refusals reach the agent as the opaque "The operation could not be completed." (05 §2.2).
- Tools are listed to every credential; capabilities are enforced only at call time (L20).

Loom's model (02, "What Loom is actually for"): a child is a **durable, inspectable thread** with its own role, model and transcript; work starts only when its dependencies are `done` and its brief is present (lane release is a third hold that Carl is minded to retire); plan, runtime and "needs a human" are three axes of which agents may write only plan intent and agent-raised attention; a human hold actually holds; review runs as a gated coder–reviewer loop in the control plane; results come back as a **report file plus a routed outcome** through one terminal call; the orchestrator is woken by the dispatcher with digests rather than polling; information moves cheapest first — report, graph, frozen-fork consult, and only then raw history; and the tool surface is lean per role with dormant families one `enable_toolset` away.

Where the two agree is the substrate: a child is a real app thread a human can open; parentage is recorded; a child starts from a brief, not a transcript; launching into a prepared workspace is a server workflow. Where they disagree is every tool that *moves* a thread through its life — and that is what the next two sections sort out.

### 3.1 `OrchestratorToolkit` (15)

<Card id="tool-orchestrator-capabilities" heading="orchestrator_capabilities" tone="warning" badge="REDUNDANT" meta={["Orchestrator", "read", "dormant + denied"]}>
Lists every provider instance and model with option descriptors, `canRunChildTask` and `maxBatchThreads` (05 §2.1). Loom's model selection is deliberately shape-based: a parent passes `taskShape`, `modelPreset` or nothing, the server resolves against the operator's capability matrix and headroom, and `workstream_list` omits the raw catalogue because "on deployments with large catalogues it dwarfs the graph itself" (`apps/server/src/mcp/WorkstreamSpawnHttp.ts:3446–3452`; 02 §H). Without `delegate_task`, `create_threads` and `t3_thread_configure` it has no consumer.

**If a model had both:** it would read model ids here and pass them as `modelSelection` to `workstream_spawn`, bypassing `taskShape`, the `sensitive: security` exclusion and the usage-headroom buckets Loom resolves at spawn (02 §H). Nothing breaks in the control plane; the capability matrix is simply sidestepped.

</Card>

<Card id="tool-delegate-task" heading="delegate_task" tone="risk" badge="CONTRADICTORY" meta={["Orchestrator", "the core collision", "dormant + denied"]}>
Starts a child owned by the calling thread, from inside the caller's live turn only (`parent_not_active`, `OrchestratorMcpService.ts:1504–1519`), in the parent's checkout (`Orchestrator.ts:6398–6412`, L3 — where Carl wants Loom's children too), from a parent-written task text plus a one-sentence role prefix (L2 — the same brief-not-transcript start a Loom child gets), and publishing one result — the child's latest finished run at first quiescence — exactly once (`SubagentProjection.ts:243–254`, `Orchestrator.ts:8946–8954`, L5–L6). The parent is woken with "Use task_status with taskId … to read the result" (`Orchestrator.ts:509–514`, L8). Loom's `workstream_spawn` creates a thread the dispatcher starts when its dependencies are `done` and its brief is present, with optional gate and dependency edges, `consult_thread`/`forkFrom` for context, and a report-plus-outcome hand-back (02 §A, §D).

**If a model had both.** Two outcomes, depending on how pull 9 maps V2 lineage onto Loom's `parentThreadId` (plan Area A adopts V2 `lineage` as the parentage record):

- *Lineage mapped.* The delegated child appears in Loom's graph with `parentThreadId` set and no Loom fields, so it takes `loomThreadDefaults.planLane: "in_progress"` (`packages/contracts/src/orchestration.loom.ts:600–611`). It never calls `workstream_submit`, so its lane never leaves `in_progress`. Consequences in today's rails: once its run ends the idle "forgot to finish" backstop classifies it `idle` (`apps/server/src/orchestration/Layers/WorkstreamDispatcher.ts:1279–1312`) and raises `needs_guidance` after the grace window (`:2539–2591`) — a human flag on a child that is, by upstream's model, complete; the parent's auto-settle is blocked forever by a non-terminal descendant (`apps/server/src/orchestration/decider.ts:877–892`); a parent cancel cascades into it; and the parent is woken twice for the same event — once by upstream's `task_status` pointer and once by Loom's rails.
- *Lineage not mapped.* The child is invisible to `workstream_list` (which reads Loom's graph, `WorkstreamSpawnHttp.ts:1999–2004, 3429`), has no plan lane, cannot be gated or depended on, writes no report file, and its completion reaches the parent only as a `task_status` pointer rather than a report path in a digest.

In both cases the model's own instructions pull the other way: `delegate_task`'s description and the shared instructions say to prefer native subagents for same-provider work and to re-run `delegate_task` per review round (`orchestrator/tools.ts:59–70`; `T3OrchestrationInstructions.ts`), where Loom's review is a gated loop in the graph.

With `delegate_task` withheld there is nothing to read. Loom's equivalent is the report path in `workstream_list` and the dispatcher's digest.

<Card id="tool-task-cancel" heading="task_cancel" tone="risk" badge="CONTRADICTORY" meta={["Orchestrator", "holds the child's queue", "dormant + denied"]}>
Interrupts the child's newest active run and disposes the parent wake; no cascade to the child's own children (05 §1.3 "Cancellation"). <Card id="tool-schedule-task" heading="schedule_task" tone="risk" badge="CONTRADICTORY (delivery)" meta={["Orchestrator", "capability Loom lacks", "decision 1: wrap the unbound form"]}>
A persisted recurring prompt. **Bound** (the default in the caller's project) it sends the prompt into this thread with `mode: "queue"` on every fire (`ScheduledTaskService.ts:538–553`, L18); **unbound** it launches a fresh top-level thread per run, over MCP always in a new worktree from `main` fetched from origin (`OrchestratorMcpService.ts:196–203`). In Loom only `workstream_stop` on a *direct child* may do that, and the idle backstop catches a forgotten resume. (`auto` on a Pi target is a steer, not a restart — `PiAdapterV2.ts:144` declares `supportsActiveSteering: true`.)

- A send to a scaffolded, not-yet-started node is `message.dispatch` on an idle thread. Loom's first-turn dependency gate lives in a `thread.turn.start` hunk today (`apps/server/src/orchestration/decider.ts:1908–1929`; lane release and brief presence are dispatcher conditions a direct send never consults) and must move to the `message.dispatch` hunk cluster (plan Area C); until then this starts a node before its dependencies finish.

- No cap, no framing, no terminal-target refusal: the collision the notify rail was designed to avoid (02 §F `notify_thread`).

The plan's Area F describes `t3_thread_send` as "never aborts a turn"; `restart` does.

### A semantic worth adopting: quiescence as completion

<Card id="semantic-quiescence" heading="Adopt upstream's quiescence-as-completion into Loom's idle rail" tone="success" badge="ADOPT SEMANTIC" meta={["Loom rail change, not a tool exposure", "Area C/D", "recommended with a yield route"]}>
Upstream publishes a delegated child's result the moment the child thread first goes quiet — no active run, no live sub-children, no pending deliveries — from the latest finished run's last assistant message (`SubagentProjection.ts:210–255`; 05 L5). Loom children sometimes finish their work and forget `workstream_submit`; today the only rail is the idle "forgot to finish" backstop, which waits out a grace window and raises `needs_guidance` (`WorkstreamDispatcher.ts:1279–1312`, `:2539–2591`), pulling a human in for a child that may simply have stopped one call short. Carl wants the upstream semantic considered: *a child idle with no submit and no open user question → synthesise its report from its last assistant message and route a distinguishable outcome.*

**Recommended shape.** Keep the existing detection (idle, no stored attention, lane in progress, activity-freshness grace window — all already in `classifyChildWake` and the idle rail) and add upstream's two quiescence conditions that Loom's rail does not check: no non-terminal children of its own, and no open user-input request (the awaiting-input wake already covers the latter). At that point, instead of raising `needs_guidance`: write the child's last assistant message to its report file with a synthesised header saying so, record `thread.work.submit` on the child's behalf with the reserved outcome **`quiescent`**, and let `routeWorkSubmit` route it as an *unmatched* outcome — i.e. **yield to the parent with the report**, never `done`. The parent then sees a distinguishable card ("went quiet; report synthesised from its last message") and decides: accept as done, re-prompt, or cancel.

**Trade-offs, stated plainly:**

- *False completion while a child merely paused.* A child that ended a turn to wait for a steer, or stopped on a provider error that recovery will resume, or was stopped by the orchestrator (`workstream_stop`) looks idle. The grace window and freshness check already exist for exactly this; `workstream_stop` leaves a `server:` interrupt the rail can recognise; an exhaustion-stalled turn carries `lastErrorClass: quota_exhausted` (02 §C.3). Routing to **yield rather than done** is what makes a residual false positive cheap: the parent reads one card and re-prompts, and dependents are not released on a guess. This is also why `done` is the wrong token — Loom's rule that "no outcome can ever silently become done" (02 §D) would otherwise be broken by the very mechanism meant to help.
- *A human may be talking to the child.* Carl's guard: unlike upstream subagents, Loom children are real threads he opens and talks to. A child that answers his question and stops is not finished, and the parent should not be told for a good while — he may be reading for ten minutes. The rail must therefore key its grace window on **who started the child's last turn**: a turn started by a human send (the message's `createdBy` is the user) gets a long window or none; a turn started by the kickoff brief, a `workstream_prompt`, or a control notice gets the short one. Loom's messages already carry origin, so the two cases are distinguishable today; the classification is "quiescent after agent/control-plane input" versus "responded to a human", and only the former synthesises.
- *Which outcome token.* `quiescent` (reserved alongside `done` and `needs_human`), so digests, the verdict chip and the parent's decision menu can name it. It must not be a gate verdict.
- *Interaction with gates.* A gate member that goes quiet must never auto-resolve: a reviewer's synthesised "verdict" is not a verdict, and a coder's synthesised submit during `pendingRework` would be read as its rework hand-back. Rule: for a thread that is a member of an unresolved gate (`isMemberOfUnresolvedGate`, 02 §D), `quiescent` routes to yield as well — the orchestrator re-drives or dissolves the gate, as the orchestrator doctrine already says.
- *Last message as report.* Upstream's choice of the latest assistant message is right because it is usually the model's own summary; when it is not ("I'll now run the tests…"), the synthesised header makes that obvious to the parent.
- *Cost.* A dispatcher-rail change plus one reserved token in `workstreamGraph.ts`; no new tool, no upstream code. It supersedes the idle backstop's `needs_guidance` raise rather than adding to it.
