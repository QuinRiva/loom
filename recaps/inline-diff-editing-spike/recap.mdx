# Typing in the right-hand side works: build it, in the "click to type, Escape to finish" form

**Recommendation: go.** In a throwaway prototype on the real app, you click any word in the right-hand side, type, and the file saves as it does from today's editor. The highlights follow your typing, and comments and the author card still work. Typing is **as smooth as today's editor up to about 3,400 lines**. The library hides the green word marks on the new side while you type. So typing starts on a click and ends on Escape: you read with the word marks, and they come back, recomputed, when you stop.

**Why option 3 over option 1.** Your use is "read what the agent wrote, fix the wording". Option 1 removes the hunt for your place. But it still swaps the comparison out when you start typing, so you reword without the original beside you. Option 3 keeps the original on the left and shows your wording against it as you go. The prototype shows it is buildable on the diff library the app already uses, as smooth as the editor on ordinary files. Option 1 is still worth doing, because large files and Earlier comparisons keep using Edit.

**Why not the editor with change marks.** It is cheaper than option 3 and robust, but it shows only *where* the agent changed things, not what the text said before. For prompt wording the before is what you are judging.

## 4. Measurements

Each run typed 84 characters at about 16 a second into a changed line, twice per file and view. A slow frame took over 50 ms, a visible stutter at 60 frames a second. "Blocked" is the total time the page could not respond. These ran on a development build in a headless browser on the VM, so absolute numbers are pessimistic. Compare the two views on the same file, not the rows.

**One trap a build must avoid.** The first wiring updated the app's copy of the file on every keystroke, which re-drew the whole Files panel. On the 769-line file that cost 25 slow frames, a one-second freeze and 801 ms blocked over the same 84 keystrokes. Waiting for a pause in typing before updating that copy brought it to parity. The slowness was the app's wiring, not the diff library.

## 5. What a build involves

Starting from the prototype (about 200 lines, two commits on this branch), a real build is these pieces. Rough total: **three to four agent-days** including review.

<Table
  columns={["Piece", "Why", "Size"]}
  rows={[
    ["Click to start typing, Escape or click-away to finish", "Keeps the word marks while reading; already working in the prototype", "small"],
    ["Typing only when the right-hand side is the file", "Changes (branch), Uncommitted and Since your message; not Earlier, not a Sources filter that hides some edits", "small"],
    ["One source of truth for the file", "So an agent's write and your typing reconcile without typing switching off (the trap found in the spike)", "medium"],
    ["Recount the changes after typing", "The 'n of m' counter and the change bar on the right go stale while you type", "small"],
    ["Comments keep their line", "The reference sent to the agent must follow the line, as the editor already does", "medium"],
    ["Edit keeps your place (option 1)", "Large files and Earlier comparisons still go through Edit", "half a day"],
    ["Live checks on a real thread, remote", "Verify over the tailnet and with an agent writing mid-edit", "half a day"]
  ]}
/>

**Risks.** The diff library's editing is new surface, and the app would depend on more of it. The installed version (1.6.1, with a local patch) is already a step past the one this spike was briefed on. The library drops the new side's word marks during typing; click to type works around that rather than fixing it. Large files remain the weak spot.

**What it gives up.** Typing in Earlier comparisons and in files over about 5,000 lines; both keep Edit. Word marks on the new side while you type.

## 6. How to try it

The prototype is on branch `t3/spike-inline-diff-editing`. Open a thread whose agent changed files, then **Files** in the right panel, and pick a file marked **M**. Click any text in the right-hand side and type; Escape or click elsewhere to finish. It saves to the real file, as Edit does. To compare with today's read-only view, run `localStorage.setItem("loom.spike.inlineEdit", "off")` in the browser console and reload.
