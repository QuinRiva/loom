# Query threads: built, verified live, ready to ship

**You can now select a passage of a plan or recap, press Query, and chat with a read-only fork of the thread that wrote it, in the main window, without that thread spending a turn.** Twelve commits on `t3/side-questions-on-plans-recaps` (77 files, +3,829 / −276), every one behind a review gate, and three live browser passes against a real pi author: 29 of 29 end-to-end assertions pass. Your three decisions hold on screen: pressing Query sends the question as the fork's first turn; Promote leaves the query thread open so one pass can promote several exchanges; and the fork comes from the thread that **signed** the document, not the thread you happen to be viewing it from.

**What you are deciding:** ship it (PR from the branch, merge via `pnpm ship`) or hold it. Three items departed from the plan during the build and are explained in §3; none change the design you approved. Four small things are deliberately left open (§4); none block shipping. ## 2. How it works, in two lines

A query thread is a Loom root with role `document-query`, forked from the author's pi session exactly as a `/handoff` drafter is, with no goal and no parent, so it is outside every join barrier, rollup and attention cascade. The author is the thread whose pi session signed the document (`manager_sessions` in the frontmatter or the HTML manifest: the newest `plan`/`architecture`/`intent`/`manager` entry, else the newest entry, mapped to its thread through the provider-thread projection); an unsigned document falls back to the viewing thread, and the sidecar records which (`authorSource`). It replays the author's launch identity verbatim (so its first turn re-reads the author's context at prompt-cache price) and is held read-only by three things: a pi hook that refuses `edit` and `write`, a read-only MCP credential, and a per-role allow-list of workstream tools (`consult_thread` in, `spawn`/`submit`/`prompt` out). One query thread serves one revision (SHA-256 of the file) of one document. Promote is an event on the query thread; the author's client seeds it once into the composer as an ordinary review chip, and you send it with the rest of your review.

## 4. Still open, none blocking

- **A double Promote records two chips.** The tool has no idempotency key; a transport retry or a model calling twice would seed two chips. Not observed in either live run; recovery is deleting one.
- **No consult edge to a root author.** When the author is a root, a consult from the query thread shows its card but draws no edge; that is the graph's existing rule for consults to roots, not new to this work.
- **Annotation card clipped by the file tree.** With the file-tree pane open beside the viewer, the Comment and Query cards both run under it. Pre-existing in the shared annotation layer.
- **Mobile has no Query button.** Query threads are ordinary threads, so chatting in one works on mobile; the affordance and pins are web and desktop only, as the plan deferred.
