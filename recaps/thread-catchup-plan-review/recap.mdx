<Card
  heading="M1 · The plan misses a second independent silent connect-gap"
  tone="risk"
  badge="MUST-FIX"
  meta={["correctness", "silent event loss", "recovery may require cache reset"]}
>
  The plan says to sample the projection cursor after an “eager live attach”, but the thread path does not currently perform one. It builds `streamDomainEvents` lazily and forks its consumer; `forkScoped` returns without establishing that the PubSub subscription as a stated invariant. An event committed after the sampled cursor but before the child fibre subscribes is in neither replay nor the live buffer. A later delivered event can then advance the persisted cursor past the missed event — the same permanent-cache failure class under review.

The shell hardening already replaced this shape with `yield* orchestrationEngine.subscribeDomainEvents`. The thread plan must explicitly require the same API before any cursor/snapshot read, rather than relying on the current queue comments. It also needs a gated connect-gap test that publishes immediately after handler entry, before releasing the cursor/snapshot read; the existing 25 ms sleep test at `/home/Carl/.t3/cockpit/worktrees/loom/t3code-d0e78679/apps/server/src/server.test.ts:5848-5912` gives the fork time to attach and does not exercise the race.

<Card
  heading="M4 · Truncation does not advance the thread cursor beyond omitted events"
  tone="risk"
  badge="MUST-FIX"
  meta={["diagnostic accuracy", "cache remains valid"]}
>
  The plan imports the shell incident's “gap sealing” mechanism into thread detail, but the reducer advances `lastSequence` only for events actually delivered to this thread. Because the store returns an ordered global prefix, any omitted target-thread event has a higher sequence than every delivered target-thread event. A truncated prefix therefore leaves a valid historical state and a cursor before the omission; it cannot advance beyond it.

For the reported zero-delivery case, reconnects are still permanently stuck because the unchanged cursor repeatedly scans the same irrelevant 1,000-row window. If a truncated window contains some target events, subsequent reconnects can crawl forward from the last delivered target event. Correct §1.3 and retain the no-schema-bump conclusion.

## Required validation adjustments

- Direct lane test: >1,000 persisted rows and `readEvents(0, Number.MAX_SAFE_INTEGER)` returns all — valid and fails today.
- Incident test: >1,000 unrelated rows **before** the target rows — required correction from M2.
- Overflow boundary: `cap + 1` matching detail rows snapshots; exactly `cap` replays; unrelated same-stream rows follow the explicit cap semantics chosen in M3.
- Client-ahead case: snapshot replacement — valid.
- Per-stream equivalence: compare after the same detail predicate — required correction from M3.
- Seam test: acquire `subscribeDomainEvents`, hold the cursor/snapshot read on a deferred, publish, release, then assert replay/snapshot → marker (when requested) → buffered event with no loss — required addition from M1.
- Marker tests: requested exactly once between initial leg and live leg; unrequested absent — valid.
- Projector >1,000 behind: valid; a cheaper unit test can additionally assert `bootstrapProjector` supplies the explicit unbounded limit.
