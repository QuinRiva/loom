# Why one evaluation document cost $35

An audit of workstream thread `0f89eaa5` ("Usage UI: baseline, evaluation, way forward"), which spent **$35.02 across 180 turns in 48 minutes** to produce a ~25 KB evaluation document. You asked whether the agent struggled, and if so what the root cause was.

  **How to review this.** Nine changes are proposed below, each with a measured or modelled saving and a named owner. Each carries an Accept / Reject / Discuss control; **silence defaults to the stated recommendation**, so you only need to touch the ones you disagree with. The two genuinely balanced calls are in the question form at the bottom. Nothing here has been implemented — this document is the decision gate.
</Callout>

## The verdict on your hypothesis

Your guess was **half right, and the wrong half is the more useful one**.

It did not struggle with its objective. It understood what it owed from its first turn, never revised the deliverable's shape, never discovered late that it had built the wrong thing, and produced the entire analytical argument once — in a single block of thinking at turn 105 — which survives essentially unchanged into the shipped document. There is no objective confusion and no meaningful scope drift.

What it struggled with was **producing and then looking at the artefact**. Two gaps in our own tooling, both invisible from its brief: the MDX recap format has no way to embed a screenshot, and there is no way to view a rendered MDX document short of booting the whole app and driving a browser through a file tree. The work that *looks* expensive — booting two instances and capturing ten UI surfaces — was 28% of the spend and largely honest. The single most expensive phase was **looking at a document it had already written and already lint-verified: $11.04, 31.5%**.

And the cost driver is not what any of us assumed. I opened this investigation telling you screenshots were 84% of the transcript bytes and implying they were the problem. **They were 7.3% of the money.** Anthropic bills images by pixel area after downscaling, not by payload size — a 2.6 MB screenshot and an 894 KB screenshot both cost about 2,900 tokens. The money went somewhere else entirely.

Two framing facts. **78.4% of the bill ($27.47) is cache-read** — the price of re-reading the context 180 times — and caching was already working near-perfectly: 98.4% of the 55.8M billed input tokens were cache hits, so uncached this thread would have cost roughly $281. There is no caching lever left. The only levers are **fewer tokens resident** and **fewer turns carrying them**.

That is why the cost curve steepens so sharply. Per-turn cost rose 4× over the thread — from $0.098 to $0.409 — not because the later work was harder, but because every later turn re-read a bigger context. The last 46 turns were 26% of the turns and **44% of the money**.

## The $5.16 mouse click

One event deserves its own account, because the causal chain crosses three components and explains most of the others.

At turn 157 the agent clicked `recap.mdx` in the app's file tree to look at its own document. The click returned an accessibility snapshot of the page **including the file's entire raw source**: 323,140 characters, of which 95.9% were base64 image data the agent had itself inlined into the document. That is 299,180 tokens — **38% of the final context** — arriving in one tool result and then re-read for 22 further turns.

The chain runs backwards like this: the MDX renderer has no image block and resolves relative paths against the app origin, so the recap skill's self-containment rule forced the agent to base64-inline its screenshots, which produced a 663 KB document, which the file viewer painted into the DOM unvirtualised, which put all of it in the accessibility tree, which one click then pulled into the model's context.

The part that makes this a tooling failure rather than a judgement failure is that **the agent saw it coming and could not act**. Twice it explicitly resolved to stop pulling in snapshots:

<Details summary="The agent's own words, from the transcript">
  Turn 25, after an 18 KB hover result: *"I should avoid full snapshots going forward since they're too large, sticking with screenshots and evaluate calls instead."*

  Turn 36: *"These snapshots are too large, so I'll skip that approach and instead wait briefly"* — it then called `browser_wait_for`, a **sleep**, which returned 24,352 characters of page dump anyway.

  Every browser action tool attaches a full accessibility tree unconditionally, and the injected browser rules tell the agent *"Action tools already include a snapshot in their response — do not call `browser_snapshot` again afterwards."* Correct advice for the current behaviour; exactly backwards for cost.

  Its successful workaround is the proof a terse default is viable: it switched to `browser_evaluate` returning the inner text of the element it cared about — **604 characters average across 19 calls, $0.34 total**. It captured the entire meter popover, the key evidence of the whole deliverable, in one 604-character call. That is one-thirtieth the cost of the snapshot carrying the same information.
</Details>

## What a well-run version would have cost

Modelled with a replay simulator over the measured per-turn token increments; it reproduces the actual thread to within 1.6% (biased low), so these savings are slightly conservative. Turn-count judgements carry roughly ±25%.

**A well-run version of this thread costs $11–13** (point estimate $12.50, range $9–16). The overspend is about **2.8×**, and roughly half of the avoidable half is a tooling default the agent could not opt out of. Note that the disciplined single thread and the split-into-children structure land in the same place — once interaction results are terse, the residual is the irreducible real work. Given this brief, about $12 is the floor; below that you are cutting evidence.

One tempting conclusion to resist: **the expensive verification phase was not waste.** It caught a real defect — Python's `json.dumps` was emitting literal `\u2014` escapes into all twelve image captions, which the linter passes clean because it is cosmetic rather than structural. That check should be made cheap, not deleted.

<Card
  id="c1"
  heading="1 · Terse-by-default browser interaction results"
  tone="risk"
  badge="Biggest lever"
  meta={["pi-browser extension", "$11.04 (32%)", "measured + simulated"]}
>
  Every browser action — click, wait, hover, navigate — returns the full accessibility tree of the page. A `browser_wait_for(time: 8)`, which is literally a sleep, returns an 8,700-token page dump. On the usage page that tree includes the entire sidebar thread list, every table row and every button label, none of which the caller asked for.

  Return URL, title, and a *diff* of the accessibility tree against the last snapshot; keep the full tree available through the existing `browser_snapshot` for when it is actually wanted. This inverts the current injected rule telling agents not to call `browser_snapshot` after an action.

  The capability cost is real but small and bounded: the agent loses the free "what does the page look like now" after every click, so expect a handful of explicit snapshot calls back — around five full snapshots here, about $1.50, making the net saving ≈$9.50. The evidence it survives is that this agent already routed around snapshots using `browser_evaluate` at 604 characters per call and lost nothing.

  <Details summary="Where the code is — this is ours, not a vendor's">
    I checked, because it determines whether this is actionable at all. The browser tools are not in loom and not in the pi npm package; they are a **local extension we own** at `/home/Carl/.pi/agent/extensions/pi-browser/`, 2,465 lines of TypeScript. Better still, snapshot attachment runs through a single choke point — `setIncludeSnapshot()` on the `BrowserToolResult` builder in `src/response.ts`. This is a small, targeted change, not a fork of somebody else's tool.
  </Details>

<Card
  id="c2"
  heading="2 · Clamp any single accessibility text node"
  tone="risk"
  badge="Zero capability cost"
  meta={["pi-browser extension", "$5.16 (15%) here, unbounded elsewhere"]}
>
  The runaway click was one enormous text node: a 663 KB file rendered into a single DOM element. A per-node character clamp — say 2 KB, replaced with a marker naming how many characters were elided — would have caught it with **no capability loss whatsoever**. No agent can use 300,000 tokens of base64.

  Worth taking even if change #1 is accepted, and worth taking *especially* if it is rejected: it is the cheap safety net against the unbounded tail, where change #1 addresses the routine bulk.

<Card
  id="c3"
  heading="3 · Give the MDX renderer an image block"
  tone="warning"
  badge="Root cause"
  meta={["loom / apps/web", "~$1.5 direct, plus the cascade"]}
>
  There is no `<Image>` block, and relative paths resolve against the app origin rather than the worktree — so a document cannot reference a screenshot on disk. The agent spent nine turns reading renderer source to establish this, because no document states it, and **its brief asserted the opposite**: *"a static PNG mock in the recap's asset dir is fine too."* That is false for this renderer.

  Everything downstream flowed from the workaround: base64 data-URIs inside `<Design>` frames, a bespoke 203-line build script written twice, a two-file deliverable, a PIL re-encoding pipeline, an undocumented 200,000-character cap discovered only by lint failure, and the caption-escaping bug that drove part of the $11 verification phase. It also produced the 663 KB document behind the $5.16 click.

  An `<Image src caption>` block resolving worktree-relative paths deletes that entire workaround class from every future screenshot-led recap. Failing that, at minimum document the data-URI pattern and its cap in the block vocabulary, and correct the brief template's false claim.

</Card>

<Card

>
  This is the one that cost $11.04. The agent had linted clean, then tried to *look* at its document — which the quality bar it was given explicitly requires. It first hunted for the cheap path and **found that it already exists and is thrown away**: `lint-plan.mjs` renders the document to 707,465 bytes of HTML on every run and prints only a byte count, and its entire CLI is `const file = process.argv[2];`. It wanted exactly an `--out` flag, found the code, and was stopped by its brief's instruction not to modify product code. So it booted a third dev server and clicked through a file tree instead.

  Two changes: add `--out <file.html>` writing the rendered markup with the stylesheet linked, and add an assertion for literal `\uXXXX` escapes and similar mojibake in rendered text — which is precisely the defect the $11 browser pass caught. Then amend the skill's "open the document and check it" instruction to name that command as the supported way to do it.

  This does not replace a human-eye check for layout, which is exactly why that check belongs in a cheap disposable child (change #6).

  Every thread's system prompt carries a snapshot of the parent's entire task tree — here 16,652 characters, about 6,400 tokens, describing 90 tasks of which exactly one was this agent's, re-read 180 times. ## Things I looked at and am recommending against

<Details summary="Four rejected levers, and why the evidence does not support them">
  **Evicting stale images from context.** The ceiling is $2.55 and realistically about $1.50, for real machinery and a real loss — the agent legitimately compares old against new screenshots across turns. Fix the payload at source instead.

  **Using the cheap /preview component harness instead of the full dev-verify path.** It could not have produced this evidence: the brief required a *booted retired release* and *live poller quota against real accounts*, and fixtures supply neither. Change #4 is the cheap substitute for the part that was substitutable.

  **"The agent used too many turns."** 180 turns at the thread's *early* cost rate would have been $17.60, not $35. Turn count is a second-order multiplier on the first-order problem, which is tokens resident per turn.

  **The agent's own small tool misuse.** Three sequential `sed -n` reads instead of one file read, an unbounded process listing returning 92,026 lines, four Playwright selector collisions. All cheap, and all already covered by existing standing rules. Adding guidance for these would cost more prompt than it saves — which is the same trap as the system-prompt campaign above.
</Details>

<Details summary="And one thing the thread did that was not in its brief and was worth every turn">
  While cleaning up, it noticed the disk was nearly full and traced it to `/tmp/pi-am.log` at **259 GB and growing**, on a disk with 23 GB free, written by the `@blackbelt-technology/pi-anthropic-messages` extension. That is the only scope expansion in the thread, about five turns.

  I have verified the current state: the log is now a symlink to `/dev/null` and there is 281 GB free. Already dealt with — noted here only so the audit is complete.
</Details>
