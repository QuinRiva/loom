# The workstream that deadlocked on an edge nobody drew

A five-thread workstream sat stuck for **43 minutes** after one child finished, and nobody was told. The child's branch never merged, three downstream threads sat "ready" with nothing able to start, and the only sign was the sidebar badge *Deadlocked · no path forward*. The cause was **one dependency edge the graph had but never wrote down**: a thread under review only merges when its reviewer signs off, so anything waiting on that merge is also waiting on the reviewer — and here the reviewer was, three hops later, waiting on it. A cycle of four edges, of which the cycle checker could see three.

Roles rather than thread ids throughout. The five children were a **researcher**, a **writer** (a skill-author, working in its own branch), a **coder** (its own branch), a **script reviewer** gating the coder, and a **skill reviewer** gating the writer.

## 2. Why it deadlocked

Three rules of the control plane as it then stood, each true on its own, combined into a cycle:

<Columns columns={3}>
  <Card eyebrow="Rule 1" heading="A dependent of a child with its own branch waits for the merge, not just for `done`.">
    The coder's start was refused with exactly this:

    > dependency 'the writer' is done, but its fan-in has not completed (fanInState: none)
  </Card>
  <Card eyebrow="Rule 2" heading="A child under review merges exactly once, when its reviewer resolves the gate.">
    Until then the merge step skips it silently — no event, no notice — because a rework round could reopen it.
  </Card>
  <Card eyebrow="Rule 3" heading="The cycle check only follows the edges written in `blockedBy`.">
    Rule 2 makes a dependent wait on a reviewer; nothing records that edge, so the checker cannot see it.
  </Card>
</Columns>

The scaffolded graph, with that edge drawn in. An arrow A → B means A waits on B; follow the arrows from the coder and you return to the coder: *coder → writer's merge → skill reviewer → script reviewer → coder*.

**Why the issue blamed the wrong thing.** The issue was filed suspecting the scaffold launch path, because two later children created one at a time merged cleanly. The difference was graph shape, not launch path:

<Columns>
  <Card tone="risk" heading="The scaffolded graph" badges={[{ "label": "deadlocked", "tone": "risk" }]}>
    The reviewer waits on a sibling that waits on the thread under review.

    <Code code={"skill reviewer → script reviewer → coder\ncoder → writer's merge → skill reviewer"} />
  </Card>
  <Card tone="success" heading="The two later spawns" badges={[{ "label": "merged in 2 s", "tone": "success" }]}>
    Each reviewer waits *only* on its own coder, so the gate resolves the moment the coder submits.

    <Code code={"reviewer → coder\ncoder's merge → reviewer → resolves at once"} />
  </Card>
</Columns>

A single-spawn call would have accepted the deadlocked shape too — both paths used the same checker over the same edges.

**The guidance that would have prevented it.** The orchestrator role already said: *wire everything downstream on the reviewer (or on both), never on the coder alone*. The coder was wired on the writer alone. Nothing enforced the rule, and this is the one shape where breaking it deadlocks rather than merely risking a stale dependent.

## 3. The fix that shipped

PR #288, merged 27 September. Four changes:

<Columns columns={2}>
  <Card id="fix-edge" heading="Draw the missing edge, so the cycle check rejects the shape" tone="success" badge="primary" meta={["spawn", "scaffold", "set-dependencies", "late gate"]}>
    Whenever a thread is wired on a child under review in its own branch, the reviewer is added to that thread's `blockedBy` explicitly, with a warning saying why. The ordinary cycle check then sees the whole cycle and rejects it with a message that names the implicit edge and says what to do instead:

    > The edge coder → skill reviewer is implicit: coder depends on writer, whose branch fans in only once its gate reviewer skill reviewer resolves the review, so coder waits on skill reviewer either way — while skill reviewer waits (through the rest of the cycle) on coder. Wire the dependent on the reviewer.

    The earlier investigation had proposed teaching the checker about the edge without writing it; the shipped version writes it, which also makes the dependency visible on the board.
  </Card>
  <Card id="fix-notice" heading="Tell the orchestrator when its workstream is deadlocked" tone="success" badge="backstop" meta={["server-side", "once per entry into the state"]}>
    The sidebar's deadlock predicate (every unfinished child is released, unstarted and waiting on another stuck sibling) moved into shared code, and the dispatcher now wakes the orchestrator once per episode with each stuck child, what it waits on, and the ways out.

    The investigation had called this "more machinery than the defect needs"; it shipped anyway, and §4 is why that was the right call.
  </Card>
  <Card id="fix-reply" heading="Stop the submit reply lying" tone="success" badge="honesty" meta={["one string"]}>
    "Work submitted … (dependents released)" was a fixed string. The writer saw it twice — once on its first submit, once after the orchestrator reopened and resubmitted it hoping to re-trigger the merge — and both times its dependents were not released.

    The reply now says *dependents are NOT released yet: they wait for your branch to fan in, which happens only once reviewer X resolves its review gate*.
  </Card>
  <Card id="fix-flag" heading="Clear the stale flag a cancel leaves on its dependents" tone="success" badge="recovery" meta={["raise kept", "clear added", "wake copy fixed"]}>
    Cancelling a thread flags any unstarted dependent `needs_guidance`, correctly — a cancelled dependency never releases. But re-pointing that dependent onto live threads did not clear the flag, and the wake told the orchestrator *a human is in the loop — plan around the pause*, when the control plane had raised it and the right move was to re-plan the graph.

    The fix clears the flag when a re-point leaves no cancelled dependency, and gives that wake its own wording.
  </Card>
</Columns>

## 4. What is still in place today

Pull 9 (merged 7 October) re-platformed loom's orchestration onto upstream's V2 engine and, by a decision you made for that pull, dropped per-child worktree isolation. The pull-9 strategy plan records it as: *"Shared checkout is the default and the only mode in pull 9 (about 2,400 lines not ported); isolation returns later as an opt-in only if wanted."* With no per-child branch there is no merge step, so rule 1 above is gone and the invisible edge cannot exist. <Callout tone="warning" title="The one thing to act on">
  The stale-flag fix was lost in the re-platform without anyone deciding to drop it. The flag does not block the thread from starting (a kickoff ignores attention and clears it), so the cost is the same as before the fix: a misleading `needs_guidance` on the board and a wake that steers the orchestrator away from re-planning its own graph — exactly what prolonged this incident by several minutes.
</Callout>

Deriving the clear from the same state — an unstarted node carrying `needs_guidance` whose current `blockedBy` names no cancelled sibling — is the mirror rule in the same place, and the wake copy from PR #288 ("the control plane flagged it for that reason — no human raised it; re-point its dependencies, revive the cancelled thread, or cancel this node too") is in git history. Rejecting means accepting the pre-fix behaviour as the permanent one.

  <Card id="d-optin-note" heading="Tie the missing-edge guard to any future isolation opt-in" tone="info" badge="recommended" meta={["a note, not code", "strategy plan's opt-in row"]}>

The guard is in git history; the risk is that the opt-in is ported without it, since the pull-9 log records only that it was deleted, not that it is a precondition of isolation. Record that precondition on the opt-in row of the pull-9 strategy plan (or wherever the opt-in is next sized). Rejecting means relying on the deadlock notice alone if isolation comes back.
