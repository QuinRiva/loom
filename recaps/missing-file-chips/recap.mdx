# False "missing?" file chips: root cause and fix

<Callout tone="decision">

## Root cause

This is a **regression from 21 Sep 2026**, caused by two commits that each seemed safe on their own:

1. `645c8ae988` moved ChatMarkdown back onto upstream v0.0.43 and re-attached loom's existence check as a wrapper around the chip renderer (`useVerifiedFileLinkChip`). The wrapper is **optimistic**. Every inline-code span that resolves is drawn as a chip straight away, and it flips to **"missing?"** when the stat reports that the file is gone. Before this commit, loom was **pessimistic** about inline code. An unverified span stayed as plain code and became a chip only when a stat confirmed the file. A bare name was also tried against the worktree root and then against every directory mentioned in the same message (`collectMessageDirectoryBases`, `selectChipBinding`). The re-home deleted all of that logic.
2. `19c964965b` ("bare-filename inline-code chips resolve again") sent separator-less spans like `prices.json` straight to the resolver. Its comment justifies this with _"loom renders a chip only once the server confirms the file exists"_. After commit 1, that premise was no longer true.

As a result, every bare filename is joined onto the **thread worktree root** (`markdownCwd = gitCwd`) and stat'd there. When the file is not at the root, the chip shows **missing?**. This happens for **96% of bare filenames** in the sample.

## The concrete case (thread cd2f3f37)

Entry 126 of the session reads: _Now_ `` `prices.json` `` _, converted to net USD from the export…_. It is a **bare inline-code basename**, with no link and no path. Every bash call in that session runs `cd /home/Carl/.t3/cockpit/worktrees/lease-extraction/t3code-c9847a68/data-pipeline-jobs/lease-extraction && …`. pi's bash tool does not keep the working directory between calls, so the agent repeats the `cd` each time. The agent wrote the file in the **same message** by its absolute path, `…/data-pipeline-jobs/lease-extraction/gold_set/eval/prices.json`. So the file existed, and the agent knew the full path. The chip still resolved to `<worktree>/prices.json`. Resolving against the agent's `cd` directory would **not** have found it either, because the file sits two levels lower, in `gold_set/eval/`. A lookup by basename across the worktree index finds exactly one match. The same thread also shows the second failure class: `` `src/models/chain_models.py:61` `` is relative to the `cd` directory, not to the worktree root.

## How common it is

**Method.** I scanned assistant text in every loom session jsonl (sessions whose cwd is under `~/.t3/cockpit/worktrees`) modified since 21 Sep. That is 203 sessions whose worktree still exists; sessions in deleted worktrees were excluded. The scan re-implements loom's inline-code gate: absolute paths with an OS root, `~/`, `./`, `../`, or a known file extension, with non-path characters and hostnames excluded. It also scans explicit markdown links. Each hit is resolved against the session cwd and stat'd **now**. Missing hits are then classified by checking the session's `cd` targets, `git ls-files -co --exclude-standard` in the worktree, and absolute paths that appear anywhere in the session.

**Result.** 1,153 chip-eligible references, of which **610 (53%) render "missing?" today**. 148 of the 203 sessions have at least one.

<Callout tone="warning">
  **Caveats.** Existence was checked now, not when each message was rendered, so some "really gone"
  absolute paths existed at the time. The gate is an approximation; it errs slightly broad. `git
  ls-files` leaves out gitignored files, so the "not in the worktree" count includes real files in
  `workbench/` and `.artifacts/`. **The conclusion does not depend on these details:** about 91% of
  false "missing?" chips are *unanchored* references (bare or relative) that are joined onto the
  worktree root, and only about 8% point at a file that has really gone.
</Callout>

## Fix options

<Card id="fix-1" heading="Fix 1: never show 'missing?' for an unanchored guess" tone="success" badge="RECOMMENDED · fix now" meta={["client only", "no new RPC", "removes ~91% of false chips"]}>
Put the pessimistic polarity back for **unanchored** inline-code spans: bare names, and relative paths without `./`, `../` or `~/`. Such a span becomes a chip only when a stat confirms a **file**; otherwise it stays as plain code. This is exactly what `useVerifiedScannedPath` / `useScannedPathTargets` already do for prose and fenced code. **Anchored** references (absolute paths, `~/`, `./`, `../`, explicit markdown links) stay optimistic, so a file the agent named precisely and that then moved still shows **missing?**, which is useful. The change is a branch in the `code` renderer, or in `VerifiedFileChip` keyed on the span's shape, plus correcting the false comment in `markdown-links.ts:113-118`. Cost: none. The same batched stat already runs.

<Card id="fix-2" heading="Fix 2: resolve bare names against more than the root (follow-up)" tone="info" badge="follow-up" meta={["server + contract", "bounded", "rescues roughly 35–45% of bare names as live chips"]}>
Fix 1 makes the false chips disappear. Fix 2 turns them into **working** chips. Options, cheapest first:

- **(a) Directories mentioned in the same message.** Restore the deleted `collectMessageDirectoryBases` / `selectChipBinding` (from `645c8ae988^`). It is purely syntactic, costs N extra stat entries, and needs no server change. It would not have rescued `prices.json`, because that message names no directory.
- **(b) Exact-basename lookup in the worktree index.** Bind to the match only when it is **unique**. The server already keeps a per-worktree `WorkspaceSearchIndex` (fff, capped at 25k entries, 15-minute idle TTL) for @-mentions, so the lookup is an index query, not a filesystem walk. It would rescue about 144 unique matches plus most of the 68 cd-relative cases, and it would have fixed `prices.json`. It needs a new RPC, or a `cwd` plus bare-name mode on `statPaths` in `packages/contracts`. Ambiguous matches (49) stay as plain code.
- **(c) The agent's recorded tool cwd.** Low value: pi's bash does not keep a working directory, and the per-call `cd` exists only inside command strings. Not recommended.

<Card id="fix-3" heading="Fix 3: agent-side guidance" tone="neutral" badge="small, complementary" meta={["premise correction", "guidance alone cannot fix it"]}>
**The brief's premise is off:** `~/.pi/agent/AGENTS.md` does **not** ask for absolute paths. The rule exists only as the memory fact `file_references_inline_code`, and the injected memory block is truncated. Compliance is partial: about 40% of file references in the sample are bare names. One line in loom's system-prompt addendum ("write file references as inline code with the full absolute path") would raise the share of working chips. It cannot be the fix on its own, though: models drift, and the renderer must not show a false "missing?" for any input.
