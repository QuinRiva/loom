### D1: Pi text generation blames `--no-extensions`, which Loom does not pass

`packages/provider-pi/src/server/textGeneration.ts:62-80`. Upstream's new `set_model` error handler rewrites a Pi rejection into "Pi rejected model 'X': … If the model comes from a Pi extension or package, text generation cannot use it because it runs Pi with --no-extensions. Pick a built-in Pi model or one defined in Pi's models.json." Loom's hunk at `:41-45` sets `disableExtensions: false` precisely so the extension-registered cliproxy provider works, and Loom's `textGenerationModelSelection` defaults to `PI_DEFAULT_MODEL` (`packages/contracts/src/settings.ts:1238`), so `set_model` runs on every Loom text-generation call. **Consequence:** when the hub or the cliproxy extension is down and Pi cannot resolve the model, a commit-message, PR-content or branch-name generation fails with advice that is false on Loom: it tells Carl to pick a built-in model because of a flag Loom never passes, steering him away from the real cause (the extension or hub). Rare (only on a `set_model` failure) but misleading when it happens. **Fix:** a marked `// loom:` edit keeping upstream's mapping but dropping the `--no-extensions` sentences, e.g. `` `Pi rejected model '${modelSelection.model}': ${error.detail ?? "unknown error"}.` ``, and the upstream comment at `:68`. Product string, not model-read text.

### D1: first-start seeding reads `~/.t3`, which no Loom host has (fix before S4)

`scripts/dev-runner.ts:640` takes the seed source as `path.join(HomeDirectory, ".t3", "userdata", "statev2.sqlite")`, upstream's line verbatim. On Carl's host and on the cockpit VM the live install is `$T3CODE_HOME` = `~/.t3/cockpit`. On this host `~/.t3/userdata/` holds no `statev2.sqlite` (only a 0-byte `state.sqlite`), so `exists(source)` is false. DL-1500 corrected where the seed goes (the port-scoped `<worktree>/.t3/dev-instances/<port>`) but not where it comes from. The step is therefore a silent no-op: it logs nothing, and the dev server starts on an empty database.

- **Who and how often:** every agent or developer who runs a plain `vp run dev` in a fresh Loom worktree, i.e. every new worktree's first dev start.
- **Consequence:** `AGENTS.md:128`, ported this pull (DL-1416), says "The first `vp run dev` in a worktree does this for you when its database is missing". An agent trusts that line and verifies UI against an empty app ("An empty database is a bad test"). The documented manual fallback misses too (N1).
- **S4:** unaffected if it follows `docs/dev-site-testing.md`. That recipe seeds with `dev:seed --home-dir <scratch>` before starting. The home then lies outside the worktree's `.t3`, so first-start seeding never runs.
- **Fix:** take the source from the ambient install, as `migrate-dev-db` already does (`apps/server/scripts/migrate-dev-db.ts:462–466`): `hostEnvironment.T3CODE_HOME?.trim() || ~/.t3`, passed into `prepareFirstStart` behind `// loom:`. Read it from `HostProcess.Environment` in `runDevRunnerWithInput`, not from `env`: the dev env's `T3CODE_HOME` is the dev home itself. Point the dev-runner test's source at a stubbed `T3CODE_HOME`, and update the `--seed` flag description (l.1012, "from ~/.t3") to match. With the fix, a home seeded by `vp run dev` makes a later `vp run dev:seed` on that same home refuse ("already exists"); the dev-site recipe's order already avoids that.

### D2: the ported setup-marker rule contradicts Loom's setup signal

`AGENTS.md:116` (DL-1416) says: "While `.t3/setup-running` names a live PID, wait … With no marker at all, setup never ran here, so run `vp i` yourself." Only `scripts/setup-worktree.ts`, the `t3.json` action, writes those markers. The cockpit's `loom` project instead runs its own `runOnWorktreeCreate` script, `bash scripts/bootstrap-worktree.sh`, per `projection_projects.scripts_json` on the live DB. That script writes no marker. This worktree has no `.t3/` directory at all, while `$(git rev-parse --git-dir)/t3code-setup-state.json` reads `"status": "ready", "scriptId": "bootstrap-worktree"`.

- **Consequence:** on every Loom worktree an agent following `AGENTS.md` finds no marker and runs `vp i` at once, even while bootstrap's `pnpm install` is still running. That is the race the rule exists to prevent. It also contradicts the instruction every Loom agent carries in its addendum: on `pending`, "re-check rather than running installs yourself".
- **Fix:** replace l.116 with Loom's signal. Setup state is `$(git rev-parse --git-dir)/t3code-setup-state.json` (`ready` / `pending` / `failed` with `detail` / absent), written by the server's setup runner (`ProjectSetupScriptRunner.loom.ts`) whichever script the project runs. Correct l.115's "from the t3.json setup script", a pre-pull Loom line, in the same edit. `AGENTS.md` is allow-listed as Loom-owned prose, so no marker is needed.
