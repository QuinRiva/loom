**DL-99 batch-path verification.**

- **Who takes the lock.** Four call sites take it:
  - `getStatus` (cache miss only), `refreshStatus` and `refreshPullRequestStatus` each take one cwd's lock and never take a second while holding it.
  - The poller takes every subscriber cwd's lock through `withRemoteWriteLocks`, deduplicated and acquired in sorted order (`reduceRight`, so the smallest key is outermost).
- **No deadlock.** No path holds two locks in an inconsistent order, so the wait-for graph is acyclic.
- **No re-entry.** `refreshStatus` already holds its cwd's lock and calls `refreshRepositoryRemoteStatus` directly, not through the lock helper. Nothing inside that batch takes a broadcaster lock: `maybeAutoPull`, `refreshLocalStatusCore` and `updateCached*` are all lock-free. `GitWorkflowService` cannot call back into the broadcaster without a layer cycle.
- **Race closed.** The poller's read and cache write sit inside the locks, so a poll that started before a turn-end refresh can no longer land after it. Upstream's two race tests exercise this path and pass.
- **Behaviour change.** A batch holds every subscribed sibling's lock for the whole repository fetch: the 5 s await, the `gh pr list`, and any auto-pull. An explicit refresh, PR refresh or cold `getStatus` on a sibling worktree now waits for the whole batch instead of only its own cwd.
