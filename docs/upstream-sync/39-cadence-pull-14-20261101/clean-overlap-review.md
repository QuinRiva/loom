### B1 (loom behaviour changed): an untrusted-folder warning on the first turn of every Pi process in Loom-project worktrees

**Who sees it, how often.** Upstream #27539 adds a `before_agent_start` handler to the T3 bridge extension (`packages/provider-pi/src/server/mcpExtensionSource.ts:276-290`) that posts a `warning` notice ("Pi did not load project settings, extensions, skills, prompts, MCP servers or system prompt files for … because the folder is not trusted …") on the first turn of each Pi process whose cwd Pi does not trust. Pi 1.3.0 counts a folder as needing trust when it, or an ancestor, holds `.agents/skills` (or `.pi/` protected resources), and in RPC mode it resolves an unrecorded folder to untrusted. Every Loom checkout carries `.agents/skills/` (`contribution-triage`, `test-t3-app`, `test-t3-mobile`), and `~/.pi/agent/trust.json` has only `/home/Carl/loom` for this repo: no entry covers `~/.t3/cockpit/worktrees/loom/*` (this worktree included). So every thread in the Loom project shows the yellow notice on its first turn, and again after each Pi process restart (Stop, idle release, server restart), because the check is per extension instance. Other projects' cockpit worktrees mostly have trust entries and stay quiet.

**What changes.** Only the notice: Pi already skipped those repo skills in cockpit sessions before the merge (agents read `.agents/skills/test-t3-app/SKILL.md` by path, as `AGENTS.md` says). The notice is truthful, but on Loom threads it is noise Carl will see daily. It is not in the model's context.

**Decision for the orchestrator/Carl (no code change proposed by this review):** (a) accept the notice; (b) add one `trust.json` entry for `/home/Carl/.t3/cockpit/worktrees/loom` (Pi's trust store resolves the nearest ancestor entry), which also starts loading those three upstream skills into every Loom thread's skill list; (c) a Loom hunk to suppress the notice for cockpit worktrees. `--no-approve` in the launch args is not a fix: it would also switch off resources in the folders Carl has trusted. S4 should expect the notice on a Loom-project thread.

### Also-read items

**X1. Stop and Force stop (#27252) against Pi's `interruptTurn`.**
`ProviderTurnControlService.interrupt` always calls the adapter with `requestRuntimeRestart: true` (unchanged from before the merge), wrapped by `ProviderSessionManager`'s 15 s `timeoutOrElse` (`apps/server/src/orchestration-v2/ProviderSessionManager.ts:1901-1918`). Only that timeout raises `ProviderAdapterInterruptTimeoutError`, which `EffectWorker` turns into `thread.interrupt.unresponsive` and the web into Force stop. Pi's path (`packages/provider-pi/src/server/adapter.ts:2849-2890`) takes the restart branch: `clear_queue` (2 s cap, failure ignored), `abort` (2 s cap, ignored), then under `sessionEventPermit` a tree-ref capture (2 s per listing, at most two) and `connection.terminate`, which sends SIGTERM and always sleeps `TERMINATION_GRACE` (1 s) before a SIGKILL check (`packages/provider-pi/src/server/rpc.ts:175-184`). A healthy turn therefore confirms in about 1 to 1.5 s (the RPCs answer in milliseconds; the fixed 1 s grace dominates), and the bounded worst case is about 9 s plus the permit wait, inside 15 s. Force stop appears only if an event handler holds the permit for long, for example `finalizeTurn` racing the stop on a wedged Pi (its own tree-ref read has the 15 s default timeout); that is the case Force stop exists for. Then `ProviderTurnControlService` polls up to 2 s for the projection to leave `running`; Pi's transport-close handler finalises the turn as `interrupted`. Expectation for S4: Stop on a Pi root completes in about 1 to 3 s with no Force stop.
`workstream_stop` (`apps/server/src/mcp/toolkits/workstream/handlers/stop.ts`) dispatches the same `run.interrupt` (with `holdQueue`) and is not itself a cascade. The cancel cascade (`workstream_set_outcome cancelled`) reaches each descendant through `redrive.ts`'s `outcomeSet` and `Orchestrator.loom.ts:1276-1300`, which calls the nested `dispatchRunInterrupt`; both produce the same `provider-turn.interrupt` effect, so both sit on the same timeout and Force stop path, and an unresponsive child would show Force stop. Pi launches through `agentScope.wrap`, so Force stop's process-scope kill reaches it.

**X2. Latent gap, not a DEFECT today: Loom's `openTools` drops upstream's `parentToolCallId`.**
Loom's `openTools` map (`adapter.ts:1040-1047`) stores `{ toolName, result }` and `finalizeTurn` ends still-open calls with a synthesised event that has no `parentToolCallId` (`adapter.ts:1581-1592`). Nothing in Carl's Pi setup calls `ctx.executeTool` today (no codemode package in `~/.pi/agent/settings.json`), so no one hits it; if codemode is adopted, the fix is one field: store `parentToolCallId` in the `openTools` entry and pass it on the synthesised event.

**X4. `VcsStatusBroadcaster.ts` (DL-1614, DL-1655, DL-1656, DL-1691): two refreshes on one repository.**
Read at the tip. The poller takes every enabled cwd's remote-write lock in sorted order (`withRemoteWriteLocks`, lines 291-297) before `refreshRepositoryRemoteStatus`; an explicit `refreshStatus` takes only its own cwd's lock and runs the batch for `[cwd]`; `getStatus` and `refreshPullRequestStatus` take one lock each; `updateCachedRemoteStatus`, `maybeAutoPull` and `refreshLocalStatusCore` take no remote lock, so nothing re-enters a held lock and the sorted multi-lock cannot deadlock against single-lock holders. A poller tick and an explicit refresh of the same cwd therefore serialise. A branch switch mid-batch is caught by `updateCachedRemoteStatus`'s branch check after `refreshLocalStatusCore`, and `refreshLocalStatus` wakes the poller on a real branch change. A cwd added to `initialPending` during a tick loops again immediately; a pending cwd with no cached local status is cleared by an empty successful pass, so no hot loop. The one concurrency left is two explicit refreshes of two different worktrees of one repository running two fetches at once, which upstream's per-cwd design also allows: pre-existing, not a race the merge introduced. `_demandCwd` stays unused by design (DL-1614).

**D1 (medium). A finished Loom root no longer auto-settles at its outcome.**
`apps/server/src/orchestration-v2/ThreadSettlementService.ts:383-394`. Upstream #27897 added a pre-check that calls `resolveAutoSettlementAt` for every candidate and calls `settleThread` only when that returns a time. **D2 (low). A steer the restart cut is lost when the restart continuation has to be retried.**
`apps/server/src/orchestration-v2/RestartContinuation.ts:303-311` with `apps/server/src/orchestration-v2/Orchestrator.ts:2337-2360` (upstream's new `retryContinuationStart`) and `apps/server/src/loom/recovery/loomRecoveryPolicy.ts:176-207`.
