### Defects

None. Nothing in this slice is broken, lost or duplicated at HEAD.

### Loom behaviour changed

- **B1: the finished-work trigger now honours the per-thread auto-settle switch.** Loom's `settleFinishedRoots` (`ThreadSettlementReactor.ts:366-371`) gates on `isAutoSettlementCandidate`, which now returns false while `autoSettleDisabledAt` is set. A finished root whose user turned auto-settle off stays in the inbox. This looks like the intended composition (PR-5: "the switch is a user opt-out"). The decider would refuse anyway (`decider.ts:862`). Carl should be aware of it, but nothing needs to change.
- **B2: turning auto-settle back on does not wake the finished-work trigger.** Neither upstream's `processEvent` nor loom's handles `thread.auto-settle-set`. Upstream recovers through its 1-minute inactivity sweep. Loom's finished-root rule runs only on a terminal `plan-lane-set` or on a session going quiet, never on the periodic sweep or at startup. So a done/cancelled root re-enabled by the user stays unsettled until one of those events, or until the inactivity window passes. The same gap already exists for unpin and unsnooze; the switch adds another instance.
  - Proposed fix (one marked hunk in `ThreadSettlementReactor.ts` `processEvent`):
    `case "thread.auto-settle-set": return event.payload.autoSettleDisabledAt === null ? finishedWorkWorker.enqueue() : Effect.void; // loom: re-enabling lets a finished root settle`
  - Carl's call whether it is worth it.

### Loom behaviour changed (for Carl)

- **B1 — cmd+k "Restart agent session" (`921cb3c8bc`) is offered on every open thread, Pi included.** What it does:
  1. Dispatches `threadEnvironment.stopSession`, but only when `session.status !== "stopped"`.
  2. Shows a toast: "Your next message starts a fresh session".
  3. Calls `serverEnvironment.refreshProviders({ instanceId, cwd, fresh: true })`.

  For Pi, step 3 does almost nothing. The fresh scan only drops other instances' snapshots for that cwd: `PiDriver` has no `snapshotForCwd`, so `ProviderRegistry.refreshWorkspaceSnapshot` returns early (`ProviderRegistry.ts` ~L888) and never runs the machine-snapshot refresh.

  **Effect:** after a restart, new pi extensions, prompt templates and skills load in the next pi process. However, the composer's slash/skill menu (fed by `enrichPiSnapshot`) is not refreshed by this action.
