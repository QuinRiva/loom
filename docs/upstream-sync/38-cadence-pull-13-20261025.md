### 4.3 Can the two indexes coexist?

Yes, measured on the schema and on the cockpit data:

- **Different objects.** Upstream: `orchestration_v2_message_search` + three
  triggers named `orchestration_v2_message_search_*`. Loom: `loom_thread_search`,
  `loom_thread_embeddings` + fifteen `loom_ts_*` triggers (three of them on the
  same messages table). Names never collide; both sets fire on a message
  insert/update/delete. Neither trigger set reads the other's table, so
  **neither breaks a write**. The extra cost per finished message is one
  trigram tokenisation of its text (streaming rows are skipped by both).
- **Both keyed on rowids of TEXT-primary-key tables**, so both are invalidated
  by anything that renumbers rowids: VACUUM (`t3 doctor --fix`) and the
  dev-database copy. Upstream rebuilds its index in both places; Loom rebuilds
  only in `migrate-dev-db` and in 1062. §4.4.
- **`migrate-dev-db` rebuilds both** once the union in §4.2 is taken
  (upstream's `rebuildMessageSearch` and Loom's `rebuildThreadSearchIndex`
  after the copy).
- **069 on the cockpit:** 31,749 messages / 21.8 MB of text to tokenise at the
  first boot, inside the migration transaction: seconds, not minutes (S3 times
  it on the `VACUUM INTO` copy). The index exists afterwards whether or not it
  is read.
- **1062 already ran** on the cockpit (ledgers 64 / 1062); it does nothing
  again.

### 4.4 Findings that hold under every option

- **Loom's index silently breaks after `t3 doctor --fix`.** The cockpit has
  `auto_vacuum = 0` and an 11.75 GB file, so pull 12's deploy step 1
  ("compact offline first") was not run; the next time anyone runs
  `t3 doctor --fix`, VACUUM renumbers the rowids `loom_thread_search` encodes
  and every content hit is credited to the wrong thread, with no error. S2a
  adds `yield* rebuildThreadSearchIndex; // loom:` beside upstream's
  `rebuildMessageSearch(sql)` in `DatabaseMaintenance.ts` (one marked line;
  the rebuild is already exported for `migrate-dev-db`). Pre-ruled (§8.2).
- **Upstream's search hides every Loom child.** Upstream's eligible set and
  index predicate exclude `lineage.relationshipToParent = 'subagent'`, which is
  how every `workstream_spawn` child is created. Any resolution that uses
  upstream's rows for Loom's surfaces loses the children, the briefs, the
  reports, goals and tasks, and the archived roots that #436 was built to find.
- **`t3_thread_search` is withheld from Loom roles** (`families.ts`,
  by construction from the thread toolkit's exports), so its new shape changes
  nothing an agent in Loom sees; it must still compile, which pins the service
  shape to upstream's.
- **`searchOlderSettled` is a #24723 dependency, not a search feature.** It
  exists so a client that received a shell without older settled threads can
  still get their rows when a search hits them. Loom's search returns settled
  roots like any other; the client needs the rows, so whichever index serves
  `search`, this operation must exist and `searchThreadsWithOlderSettledRows`
  must be the ws handler.

### 5.2 Rule T, test prune

For a conflict hunk in a test file where upstream's side is empty or smaller
and Loom's side holds test code:

1. **No `loom:` line in Loom's side → take upstream's deletion.** These are
   upstream's own tests that git kept on Loom's side only because Loom edited
   something nearby (`GitManager.test.ts` 121 lines, `ProviderSessionManager.test.ts`
   80, `terminal/Manager.test.ts` 479, `VcsStatusBroadcaster.test.ts` 96,
   `WorkspaceFileSystem.test.ts` 75, `composerContextRecords.test.ts` 49/96/87,
   `modelSelection.test.ts` 55, `keybindings.test.ts` 7, `CommandPalette.logic.test.ts`
   18, `CodexProvider.test.ts` 10).
2. **A `loom:` line that marks a Loom fixture adjustment** (a field added so an
   upstream assertion still passes under Loom's defaults; a Loom service stub
   so an upstream layer builds) **goes with the upstream test it fed**: deleted
   with it.
3. **A `loom:` line that marks a Loom assertion is kept only if it guards a
   Loom behaviour nothing else tests.** Behaviours such as (examples, not a
   closed set; DL-1410 lists the further keeps S1 found): hosted
   refusals and the thread-less-scope refusal; the withheld-tool list; the
   Pi-only registry and pi-enabled-by-default; Loom's settings defaults
   (`contextWindowMeterEnabled`, `autoResumeLimitedThreads`, allow-list fields);
   the V1 import boundary; the foreign-home guard; the two-ledger migrator;
   workstream fields on shells; the repository status batch (DL-1221,
   `VcsStatusBroadcaster.test.ts`); verified chips and scanned paths; the
   annotation surviving unmount; the thread-search index; agent-created
   messages in the minimap; the question age; the trailing-window subtree
   activity. A kept Loom test moves into a **Loom-only file** (`<name>.loom.test.ts`
   beside the upstream file, as pull 12's browser re-homings did) when the
   upstream file around it is otherwise gone or thinned to nothing, so the next
   prune cannot delete it again. It stays in place, marked, when the upstream
   file keeps its structure.
4. **A kept test must compile against upstream's exports.** The `lost-ours`
   names (§5.4) were de-exported because their only tests are gone; a kept Loom
   test that imports one re-exports it with a marked line rather than restoring
   the deleted upstream test.
5. **New test lint rules apply to what is kept** (§6.9): a re-homed browser
   test uses `apps/web/test/render.tsx` with `using`/`await using`, no
   `beforeEach`, no module-level screens.

`client-runtime/state/shell.ts`, `threadFamilies.ts`, `olderSettledThreads.ts`):
a client that advertises `shellThreadFamilies` (and `shellOlderSettled`) gets a
shell without (1) subagent-lineage threads that are not live, where live means
`activityRunStatus`, a live `status`, a `pendingRuntimeRequest` or background
tasks (`isLiveSubagentShell`), unless they are the parent of a kept child; and
(2) top-level threads with `settledOverride = "settled"` older than the 25th
newest settled one, unless pinned, snoozed or an ancestor of a kept child.
Omitted rows are read on demand (`getThreadFamily` when a thread's family is
needed, `getOlderSettledThreads` as the user pages the sidebar's shelf, and the
search returns rows for older settled hits). On the cockpit this drops 415 of
440 settled roots and most of the 4,703 children from the cold shell: the 93%
upstream measured.

What is joined is fine: every path reads through the Orchestrator's joined
`readShellSnapshot` (§6.1), so a paged-in root carries `workstream`. What is
**not** fine is the liveness test: Loom's child threads finish their turn and
then hold a stored flag (`needs_guidance`, `awaiting_acceptance`,
`awaiting_orchestrator`, `error`, and the derived `brief-needed`), and Loom's
`rollup.ts` computes the root's badge, `loomAttentionOf` and the goal chips from
the descendants' `workstream.attention` on the client. A flagged child is idle
by upstream's test, so after a cold connect the root shows no Loom badge until
something loads its family. DL-1312 (a persisted question after a restart) was
the one-restart version of this; this is every cold connect.

**Fix (pre-ruled, §8.2):** a Loom predicate `keepsLoomChildInColdShell(thread, roots)`
in `loom/projection/loomShellJoin.ts`, true when **either** (i) the child's
root is unarchived and not settled, **or** (ii) `thread.workstream?.attention`
is non-empty, or the thread's outcome is null and its status is `failed` (S2a
checks `rollup.ts`'s reason list so nothing the rollup reads is omitted). It is
called with one marked `||` in `omitIdleSubagentShells` and one in
`omitOlderSettledShells`. The join runs before the filter, so the field is
there. Gate 2a verifies; S4 proves it with a child that submitted
`needs_guidance` before a fresh browser connects, and with an active root whose
finished children are counted on its sidebar badge before the root is opened.

_Orchestrator's review amendment (DL-1404):_ clause (i) was added after S0.
The rollup badge on a sidebar row shows plan counts (`N done`, `N blocked`)
over every descendant, not only the flagged ones, so a flagged-only predicate
leaves an unopened active root under-counting after a cold connect until
`useThreadFamily` loads its family. Keeping every child of a live root costs
**238 of the cockpit's 4,713 children** (92 unsettled, unarchived roots), so
upstream's saving on the 4,475 children of settled or archived roots stands;
those roots load their family when opened, as upstream intends.

### 6.3 Guest sharing (#24104): a new principal that cannot reach Loom

A guest redeems a signed link into a cookie scoped to one share
(`apps/server/src/guest/http.ts`: redeem, submit, stream, session, render, item,
command-output, attachment routes under `GUEST_ROUTE_PREFIX`; `GuestShareService.ts`
verifies tokens against the thread's `guestShare` record). The guest holds **no
auth session, no scope, no ws connection and no MCP credential**: the only
authenticated ws method is the owner's `guestShare.create` (`AuthAccessWriteScope`,
`clientRpcPermissions.ts` hunk 2, union with Loom's hub-login scopes). A guest
message waits in `thread.guestShare.messages` until the owner approves it, then
dispatches as `message.dispatch { guestMessageId }`; `ThreadMessageIntake.ts`
attaches the guest's files. The feature is behind `guestSharingEnabled`
(default `false`, Settings → Beta). Loom's tools and ws methods are therefore
unreachable to a guest by construction, not by a check; nothing to prove beyond
`registration.test.ts`'s thread-less-scope refusal, which still holds. Gate 2a
reads `GuestShareDecider.ts` once for the lineage walks (a guest share on a Loom
root is just a share).

## 7. Upstream change digest and per-zone resolution doctrine

Doctrine §4.3 (`05-strategy.md`): where upstream now expresses the same
functionality, upstream's mechanism is the baseline and Loom's variant is
deleted. Otherwise upstream wins verbatim and Loom's seam is re-applied behind
`// loom:`.

### 7.1 Five mechanical rules

- **Rule A: comment-adjacent (86 markers).** Upstream's side is empty or
  comment-only; Loom's side is a `// loom:` hunk or a Loom comment next to a
  comment #21514 deleted. Keep Loom's side, drop upstream's. Do not restore a
  pruned upstream comment; where Loom's side is only a narration comment with
  no marker and no code, take upstream's deletion (DL-1206's practice: keep
