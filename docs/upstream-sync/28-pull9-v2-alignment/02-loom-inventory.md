## 0. How to read this

### Coupling classes (as used throughout)

- **self-contained** — Loom owns the module; it talks to the engine only through
  a narrow seam (`OrchestrationEngineService.dispatch` / `streamDomainEvents`,
  `ProjectionSnapshotQuery` read methods, the command-receipt repository, the
  provider-launch parameters).
- **hunk-in-engine** — Loom logic interleaved into a V1 decider / projector /
  reactor / engine case (usually `// loom:`-marked), changing what an upstream
  command or flow does.
- **substrate** — Loom changes V1's own invariants: new command/event types or
  aggregate kinds, new read-model fields every consumer must carry, new
  command-boundary rules, settlement-policy changes, activity-payload projection.

Most capabilities are a **pair**: a self-contained module that implements the
behaviour, sitting on substrate that makes the behaviour expressible. Each row
names both where they differ.

### Premises in the brief that the evidence corrects

1. **Plan lanes are six, not five.** `yielded` (control-plane-only, from a
   submit's routing decision) sits between `in_progress` and `done`
   (`packages/contracts/src/orchestration.loom.ts:116`).
2. **Attention has a third, derived-only kind beyond the two agent-raised
   reasons**: `error` (stored, server-only), `awaiting_approval` /
   `awaiting_input` (derived from open requests, unioned in at the read
   boundary), and a **derived "brief-needed" parent attention** computed in
   `ProjectionSnapshotQuery` and never stored
   (`plans/2026-07-31-workstream-condition-registry.md` §2).
3. **`RuntimeInstructions.ts` carries no Loom hunks** (`git diff c14f6015bf HEAD`
   is empty for it). The work-model addendum is a constant in the Pi driver
   (`apps/server/src/provider/Drivers/PiDriver.ts:164`), prepended only when the
   thread has a workstream MCP session.
4. **`consult_manager` and `sign_document` are not Loom code.** They are pi-craft
   extensions (the `authored-document` / `seek-manager-guidance` skills); Loom
   only names them in role tool profiles (`roles/orchestrator.md`,
   `roles/coder.md`). Loom's own consult primitive is `consult_thread`.
5. **Restart turn continuation is upstream's, not Loom's.** Loom's own
   continuation was deleted when upstream's `reconcileProviderSessions` (#9167)
   arrived (`plans/2026-07-16-restart-turn-continuation.md`, "superseded");
   Loom keeps marked hunks in that path.
6. **The Pi driver is where several orchestration capabilities physically
   live** (work-model prompt, tool-extension loading, `T3_*` env, native fork,
   launch-identity capture, the ask broker). `PiDriver.ts` is a Loom-added file
   (2 959 lines) relative to `c14f6015bf`. Those pieces are inventoried here;
   the driver's runtime internals are the sibling thread's.
7. **Pull 8 is not an ancestor of this `HEAD`** in this checkout's refs
   (`origin/t3code/upstream-sync-20261004`). The brief states it does not change
   orchestration shape; nothing here depends on it.

**One structural fact governs the whole inventory.** The July seam campaign

files — fork contracts into `orchestration.loom.ts`, 17 decider cases into

cases modified in place because "they change what upstream commands mean"
(campaign §B.4). So Loom is **self-contained by file, substrate by contract**:
easy to carry across a V1 merge, not separable from V1's command/event model.

## A. Thread graph & delegation

**Intent.** A child is a real, durable, addressable thread — not an in-turn
subagent — so a human can open and talk to it, and so delegation survives
restarts (`.plans/workflow-subagent-sessions-research.md` §1: "the tool-call
subagent and the spawn-a-session subagent are different primitives"). The graph
starts work only when **both** start-gates clear — dependencies `done` and plan
lane released — so a whole DAG can be laid out and reviewed "before any tokens
are spent" (`.plans/workstream-state-model-design.md` §3). Writers get their own
worktree so "a thread's diffs mean what this thread changed", revert cannot
destroy a sibling's work, and "a dependent child starts from a tree that already
contains its dependency's merged output" (`plans/workstream-worktree-isolation/plan.mdx`,
objective).

## B. Agent tool surface & transport

**Intent.** Tool metadata is **data**, so it type-checks and is testable; the
pi-side code is a dumb "POST-and-print" shim and **the server render is the
single source of truth** (`providerToolExtension.ts` header;
`mcp/workstreamRender.ts` header). The prose itself is treated as a distributed
prompt read at different decision moments (`docs/architecture/tool-def-authoring.md`).
A leaf runs with a deliberately lean surface and escalates on demand: the
child-prompt-dedup plan measured a leaf researcher at 101 selected tools / 59 KB
prompt and set the target at ~27 tools / ~45–47 KB (`plans/child-prompt-dedup/plan.mdx`).

### B.3 Dormant tool families and role profiles

`roleOverlay.ts` auto-unions `LEAF_CORE_PROVIDER_TOOLS` (9) + `enable_toolset`

### B.4 Non-Pi providers

Today **no non-Pi provider gets any of these tools**:

- the capability `workstream` is requested only by the Pi driver (`PiDriver.ts:2229`);
- the tools are delivered as a pi extension `.mjs`, loaded via pi `--extension`
  only when a workstream MCP session exists (`PiDriver.ts:~2405`);
- they are **not** registered as MCP tools — upstream's `McpHttpServer` serves
  only the `preview`, `device` and `pullRequests` toolkits (`mcp/toolkits/`);
- the work-model addendum is prepended by the Pi driver, not by
  `RuntimeInstructions.ts`;
- role tool profiling, `enable_toolset`, `forkFrom`, `thread_fork`,
  `consult_thread` (pi `--fork`), launch-identity replay and the ask broker are
  pi-specific mechanisms.

What _is_ provider-neutral: the routes are plain JSON POSTs authenticated by
the upstream MCP bearer, and every response carries server-rendered text, so the
handler layer does not care which agent called it.

**What a port needs (B):** a per-thread credential carrying caller identity; a
way to put ~24 tools in front of the agent (pi extension today; an MCP toolkit
would serve other agents); for profiling, a provider that supports
selection-not-allowlist tool activation.

## C. Lifecycle & state model

**Intent.** "Status describes the plan; runtime is the truth." One writable
enum conflated plan intent, runtime and "needs a human", and agents misused it;
the fix is **three independent axes**, of which agents may only write plan and
agent-raised attention, and the system exclusively owns `in_progress`, `error`
and the derived reasons (`.plans/workstream-state-model-design.md` §1–§2, §8).
The governing invariant is **no silent halt**: a node that is not executing,
will not be auto-resumed, and is not plan-terminal must carry a raised attention
flag (§4). Completion is otherwise cooperative self-report, so the control plane
must notice dead, stalled or spinning agents "instead of letting it silently pin
its dependents/parent forever" (`.plans/phase-d-liveness-design.md`).

## E. Goals & task tree

## What Loom is actually for

Loom's thesis is that delegated agent work should be a **durable, inspectable
organisation of threads**, not a function call. A plain subagent runs inside one
parent turn, returns a summary, and vanishes; a Loom child is a real thread with
its own transcript, worktree, role and model, which a human can open and talk to
at any time, which survives server restarts and provider failures, and whose
place in the plan is recorded rather than inferred
(`.plans/workflow-subagent-sessions-research.md` §1). The goal and its task tree
sit above the threads as the north star and the shared, glanceable record of
what is done and what remains, so that the human — and any fresh session picking
the work up — can re-orient without reading transcripts.

The model guarantees outcomes a subagent model cannot. **Work starts only when
it should**: a graph can be laid out, reviewed and released before a token is
spent, and dependents start from a tree that already contains their
dependencies' merged output. **Work cannot silently stop**: plan, runtime and
"needs a human" are separate axes; agents can only write intent; the control
plane owns `in_progress` and `error`; every not-running, not-auto-resumed,
non-terminal node must carry a flag; and dead, stalled, spinning, wedged or
quota-stalled threads are detected and resumed or surfaced, with exactly-once,
restart-safe delivery. **Review is part of the graph, not of the orchestrator's
attention**: a gated coder–reviewer loop runs to resolution under control-plane
routing, round-capped, with escalation — never silent completion — as the
default for anything unexpected. **A human hold actually holds**: acceptance and
guidance flags gate dependents, and questions are shaped for a reader who has
seen none of the thread.

Underneath, the product is also a context economy. Each thread receives only
what binds for it — a delta brief, its role's doctrine, its branch of the task
tree, a lean tool surface with dormant families one call away — and information
moves between threads cheapest first: report, graph, frozen-fork consult, and
only then the raw session. Shared-prefix forks make parallel lenses on one large
corpus comparable and cache-cheap. The orchestrator is woken once per meaningful
event, with digests rather than per-event noise. That is the difference the
intent record keeps returning to: the system, not the agent's goodwill, keeps a
many-thread effort coherent, attributable and recoverable.
