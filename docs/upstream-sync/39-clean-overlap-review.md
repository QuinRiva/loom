### DEFECTs

**D1 (medium). A finished Loom root no longer auto-settles at its outcome.**
`apps/server/src/orchestration-v2/ThreadSettlementService.ts:383-394`. Upstream #27897 added a pre-check that calls `resolveAutoSettlementAt` for every candidate and calls `settleThread` only when that returns a time. Loom's finished-root rule is an argument to that function (`loomFinishedRootAt`, the early return at l.222), and the new call site does not pass it, so for a Loom root with an outcome but recent activity the pre-check returns `null` and `settleThread` (which does pass it, l.354) never runs. The thread then goes to the branch lookup, which settles it at its outcome only if it has a branch and the host finds a pull request for it (`wouldSettle`, l.469). Who hits it: every finished workstream whose root has no PR (research, reviews, planning roots, and any root on a branch never pushed). What Carl sees: those roots stay in the active sidebar after `done` until the inactivity rule settles them (5 days on the cockpit's `sidebarAutoSettleAfterDays`), instead of dropping to settled as soon as they finish; their unsettled root also keeps `inLiveLoomGoal` and `keepsLoomChildInColdShell`'s live-root clause true, so the cold shell keeps their whole family. Auto-settle is the only path that settles a Loom root on outcome (no Loom code dispatches `thread.settle`), and the only Loom test (`Orchestrator.loom.attention.test.ts`) checks `loomSettleBlockers`, not the sweep. Documented rule: doc 37 S10 and `plans/upstream-pull9-phase2-substrate/plan.mdx` ("a root with a terminal outcome settles at its outcome time"). **Fix:** add `loomFinishedRootAt: loomSettlement.get(thread.id)?.finishedRootAt ?? null, // loom:` to the pre-check call at l.387–393, as at the other two sites.

**D2 (low). A steer the restart cut is lost when the restart continuation has to be retried.**
`apps/server/src/orchestration-v2/RestartContinuation.ts:303-311` with `apps/server/src/orchestration-v2/Orchestrator.ts:2337-2360` (upstream's new `retryContinuationStart`) and `apps/server/src/loom/recovery/loomRecoveryPolicy.ts:176-207`. Loom's DL-690 carries a stashed steer (accepted by the cut turn's pi, never delivered) in the continuation prompt via `withStashedSteer(threadId, sourceRunId, …)`, which matches only `stash.runId === sourceRunId`; at startup `redeliverStashedSteers` runs that continuation and then clears the stash. Upstream now retries a continuation that failed before its prompt was taken ("under load a resumed provider can time out", 60 s then 180 s), dispatching `provider-runtime.continue` with the **failed continuation** as `sourceRunId`. The retry builds a fresh prompt: the stash is cleared and would not match the new source anyway, and the failed run's message, which held the steer, never reached pi. Who hits it: a thread that had a steer in flight when the server restarted and whose pi then timed out taking the first continuation, which is the deploy-restart case with many threads resuming at once. What it costs: the instruction (often Carl's, or an orchestrator's correction) silently never arrives; the agent resumes without it. Rare. **Fix:** in the marked hunk, when `continuationFailedBeforePrompt(source, projection.providerTurns)`, carry the redelivered-steer block from `sourceMessage.text` (the failed continuation's own message, already read at l.291) onto the new text; `withStashedSteer` stays for the first continuation.

### Brief questions

**Q1. Can the SQL superset and `keepsLoomEntryInColdShell` disagree with `keepsLoomChildInColdShell` and drop a thread the old path kept? No.** `keepsLoomChildInColdShell` keeps a Loom thread for (a) an unarchived, unsettled root (via `lineage.rootThreadId`, only when `workstream.parentThreadId !== null`), (b) stored attention, or (c) no outcome plus a classed failure or an un-started unheld child. The SQL `keep` (`json_array_length(w.attention) > 0 OR w.outcome IS NULL`) is a superset of (b) and (c), read from the same column `selectWorkstreams` decodes into `workstream.attention`/`outcome`. (a) matters only in `omitIdleSubagentShellsWith` (the older-settled call passes an empty map), and the index's subagent branch checks the same root in `unsettledIds`, which, like the decoded `roots`, contains only unarchived rows (the index is `archivedAt IS NULL`). The decoded `roots` map is now only the selected shells, but an unsettled top-level root is never trimmed by the index (it is not older-settled), so the root (a) needs is always decoded. `inLiveLoomGoal`'s live set is built from non-subagent unsettled rows; every such row is selected, so the index's set and the decoded set are equal. Facts (`subagentParentIds`, `olderSettledBeforeMs`) come from the index on both sides. A row with no sidecar row computes `keep` true in SQL but gets no `workstream` field (`loom_row = 0`), so it is ignored, as S3 measured. The sidecar join itself runs after the read transaction (`Orchestrator.readShellSnapshot`), as on `origin/main`; a sidecar write between the two is corrected by the next delta.
On deltas: every `thread.updated` the server sends is built from `getThreadShell`/`readShellSnapshot`, both wrapped by `joinLoomThreadShell`/`joinLoomShellFields` (`Orchestrator.ts:14208-14223`), and `skipUnchangedThreadShells` compares with the contract schema, which includes `workstream`. The client's batched `applyShellStreamEvents` upserts the whole row and DL-1613 applies goal items before the batch, so no path delivers a kept thread without its sidecar fields (client files are 2c/2d's to confirm in full).

**Q2. #27221 `releaseUnattendedHolds` (`Orchestrator.ts:2367`).** It runs only when a run **completes** (`handleRunUpdate`), only for the newest run, and not when that run had a Stop (`run_interrupt_request`); it releases held queued runs whose message is not a person's (`createdBy !== "user"` or a scheduled task). What changes for Loom:
- Restart recovery (`ProviderRuntimeRecoveryService.ts:356`) holds every queued run; Loom's `releaseHeldQueues` resumes a live Loom thread's held control wake at startup, and deliberately leaves it held when a human is owed an action or the thread has an outcome (`isContinued` false: "their message is the release"). Since a message to an idle thread starts a run even while older runs are held, the next Loom notice to such a thread runs, and when that run completes the older held wake is now released and delivered after it, without the human. The agent is already taking turns on that thread, so the human-owed state does not change; the older wake simply arrives after the newer one. Benign.
- `workstream_stop` (`handlers/stop.ts`, `holdQueue: true`) then `workstream_prompt`: when the resume run completes, the messages held by the stop are released. Before, they waited for a person's client message. This matches the stop's own text ("paused … resume it with workstream_prompt").
- No steer is redirected: released runs start as their own queued runs after the completed one; stashed-steer redelivery is a separate rail (D2 is the only steer gap found). `bg_wait` completions are buffered provider notifications, which already bypass holds (`wakeSkipsHold`, recovery's `bufferedMessageIds`), so they arrive no earlier than before. DL-1463 is about a person's mid-turn composer message (steer by default); #27221 never touches `createdBy: "user"` runs, so it does not interact. No fix.

**Q3. Side chats beside Loom's overlay.** No confusion either way. A side chat is `relationshipToParent: "fork"` with `lineage.sideChat: true` and never gets a sidecar row (rows come only from `thread.workstream-created` and `thread.goal-set`), so `joinLoomShellFields` attaches nothing and no Loom predicate reads `sideChat`; a Loom child is `subagent` lineage without `sideChat`, and Loom's own forks pass no `sideChat` to `ThreadForkService.plan`. `requireWorkstreamCaller` keys on the credential's `workstream` capability and thread, which a side chat's pi has like any thread (pre-existing for every thread kind). **Consequence the runbook does not state (§8.1 row 1):** upstream refuses a side chat whose source is a subagent (`ThreadForkService.ts`, "A subagent cannot start a side chat."), and the web disables `/side`, `/btw` and **+ → Side chat** with "Subagent threads cannot start side chats." (`ChatView.tsx:2816-2841`). Every Loom child is `subagent` lineage, so side chats are available only on roots. Whether Loom children should get side chats is a product question for Carl, not a merge defect; if yes, the server refusal and `isSubagentThread` need a marked Loom exemption (DL-1510's "a Loom child is not upstream's delegated subagent").

**Q4. Linked environments (§5.2): confirmed.** A linked OAuth caller is built in `apps/server/src/auth/McpOAuth.ts:585-601` with `thread: undefined` and `capabilities: orchestration, worktree, pull-requests`; `requireWorkstreamCaller` refuses it on the missing `workstream` capability before the thread check. `RemoteDelegation.ts`'s `followScope` is a thread scope with `orchestration` only, so it is refused too. `ProviderSessionManager.ts`'s Loom clause (`filterOrElse` + `Option.getOrThrow`, l.472-482) is equivalent to `origin/main`'s `flatMap` form: the predicate guarantees `loomStore` is `Some` before `getOrThrow`, and a failed read still yields `subagent: false`. #16695's `linkOrigin` is stamped on threads, not on credentials, so these lines do not read it. Hardening note (not a defect; the beta is off and the cockpit has one environment): a thread a fenced link starts here runs pi with Loom's `workstream` capability, and Loom's tools bypass `McpToolAccess`'s `assertSameLink`/`assertNotLinked`, so its agent could `workstream_spawn` children that carry no `linkOrigin` and so escape the fence. If the beta is ever turned on, have `requireWorkstreamCaller` refuse a caller whose thread has a fencing `linkOrigin`, or withhold `workstream` from such a thread's credential.

**Q5. Interrupt-timeout path (§6.1).** Loom's stops dispatch upstream's `run.interrupt` (`workstream_stop` with `holdQueue: true`, the cancel cascade with `holdQueue: false` and its dispatch-time `catchIf`); the timeout lives in the effect worker (`EffectWorker.ts`, `ProviderTurnControlService.ts`), after dispatch, so neither Loom call site sees a new error. If pi never confirms, the run stays open with `thread.interrupt.unresponsive` and the UI offers Force stop; an agent caller has no Force stop. Before #27252 such an interrupt hung with no way out, so this is not worse. Whether pi confirms in time is Gate 2b's `adapter.ts` read and S4's journey.
