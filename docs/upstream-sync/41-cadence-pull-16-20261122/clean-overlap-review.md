### Seams that needed thought

**Loom's chat file-chip lookup against upstream's idle index rule (#38585): the one DEFECT.** Upstream now drops a workspace's file index at the next `refresh` unless something searched it in the last 15 minutes. Every upstream reader of the index records its use with `markSearched` (`WorkspaceEntries.ts` l.327, l.421, l.601), and `refresh` (l.219 to 224) invalidates any index key that has no recent record. Loom's `locateFiles` (l.664 to 677), which resolves bare file names in chat (`` `foo.ts` ``) to file chips, reads the same `paths` index but never records its use. `refresh` runs at every run finalisation (`RunFinalizationService.ts` l.182) and after every file save (`WorkspaceFileSystem.ts` l.942). So in any thread where nobody typed an @-mention in the last 15 minutes, which is most Loom threads, each agent turn drops the index, and the next chip lookup for that thread rebuilds it from scratch: an fff scan of the worktree, a `git ls-files --ignored` read and a new file watcher. Who sees it: Carl, viewing any thread whose replies mention bare file names. What he sees: those names turn into chips a second or two later than before after each turn, on a large worktree; nothing resolves wrongly, because the rebuild waits for the scan. What it costs the machine: one full index build per turn per viewed thread instead of an incremental refresh. **Fix (one marked line):** in `locateFiles`, name the key and record the use before the lookup, as `search` does: `const indexKey = WorkspaceSearchIndex.workspaceSearchIndexKey(normalizedCwd, "paths");` then `markSearched(indexKey, yield* Clock.currentTimeMillis); // loom: a chip lookup is a use, like search`, and pass `indexKey` to `workspaceSearchIndexes.get`. No test is needed beyond the existing `locateFiles` case; the rule is upstream's and the fix makes Loom a party to it.

**Start-of-run baseline and upstream's checkpoint rework (§6.6, DL-2104).** Loom's P3-17 capture still sits ahead of upstream's reuse check in `captureScopeBaseline`, and DL-2104's departure from B.8 is right: moving it after the timeout check would also put it after `if (exists) return`, so it would never run in the one case it exists for (upstream reusing the previous run's checkpoint, which in a shared checkout holds siblings' edits). The block now honours upstream's skip after two timeouts, runs under the baseline budget through `captureWorkspaceCheckpoint(…, true)` and passes `excludePaths`. Its own timeout counts towards upstream's skip, and a baseline capture never marks the folder as timed out (`noteCapture(cwd, !baseline)`), so it cannot make another thread's end-of-turn capture skip itself through `timedOutWhileWaiting`. On the diff side `diffBaseRef` still prefers the Loom baseline only for Loom threads and only when the ref exists. Multi-repository scopes go through `noteRepositoryBaseline` and `captureHeadCheckpoint` and get no Loom baseline, which matches the §8.1 ruling (left reachable and unsupported). `CheckpointStore.ts` now guards all four mutating operations, `captureHeadCheckpoint` included (DL-2105); a refused head capture surfaces as `VcsUnsupportedOperationError`, which `captureSummarized` already maps to `missing` and `captureRepository` ignores, so a copied database simply records no snapshot.

**The batched remote status beside #40153's shared git reads (`GitManager.ts`).** `remoteResultFromDetails` is still upstream's tail verbatim, and both the per-cwd path and Loom's `readRemoteStatuses` go through it. #40153's shared-read scope (`prLookupGitReads`) is opened inside the `prLookupCache` lookup itself (`withActivePrLookupGitReads`), not in `remoteStatus`, so Loom's batch gets the same saving on its PR lookups without any change.
