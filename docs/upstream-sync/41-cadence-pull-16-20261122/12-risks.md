## 12. Risks

| Risk | Owner | Mitigation |
| --- | --- | --- |
| A new upstream tool, or `pull_request_merge` itself, reaches Loom agents because a list in `families.ts` was fixed the quick way (classify the toolkit under a capability) | S2a, Gate 2 | §4.2 names the exact lists; `families.test.ts` is rewritten to the pinned nine and the eleven withheld toolkits; S4 reads a new root's tool list (§10 `tools`) |
| Loom's shipper children lose `watch_pull_request` because the DL-471 exemption stays in the dead hunk | S1 lane 1, Gate 1 | §4.4 gives the line and its new home; Gate 1 reads `PullRequestWatchService.ts`; S2a's service test; S4's shipper journey |
| Upstream prompt text reaches pi (the PR-linking block, or orchestration instructions with it) because hunk 7 looks like a plain upstream insertion | S1 lane 2, Gate 1 | §4.3; the new assertion on the prompt-sections path, which today's test does not cover |
| Seven writers on one uncommitted merge: a tree-writing git command, or two threads in one file | S1 lead | §7.2: only the lead writes the index; zones are disjoint by file; lanes copy finished files to `.artifacts/pull16-s1/resolved/`; `git checkout -m -- <path>` re-creates a lost file's markers; the sequenced order of §2.1 is the fallback |
| A lane keeps Loom's side of an `o` hunk that is an upstream deletion, or takes a `B` hunk that declares something twice | S1 lanes, Gate 1 | §7.1 names the cases; every zone file flags them per hunk; the lead's typecheck observation shows duplicates at once |
| The root disk fills. `/` is at 97 to 98 % and its free space moved between 53 GB and 32 GB within one hour during S0 (other threads' worktrees and installs; 133 worktrees live under `~/.t3/cockpit/worktrees/loom`). S1's first `vp i` adds new package versions to the shared pnpm store on `/`; S3 deletes and re-installs every `node_modules`, builds, and needs a database copy | S1 lead, S3 | Before each install: `df -h / /mnt/fast`; **stop and tell the orchestrator if `/` has under 15 GB free** (clearing other threads' worktrees is Carl's call, not a session's). The `VACUUM INTO` copy (about 4.7 GB, 5.0 GB after migrating) and S4's copy go under `/mnt/fast/pull16/` (116 GB free), never `/` or `/tmp` (which is on `/`), and are deleted when the session ends. The S1 lead removes the trial worktree. Nobody runs `pnpm store prune`: the store is shared by every worktree |
| First boot exceeds the deploy's 240 s start timeout (28 migrations with passes over a 2 GB table) and the deploy puts itself back | S3, deploy | S3 measures boot-to-listen on the cockpit copy, warm and (if it can) cold; a number over about 150 s is reported to the orchestrator before the ship, with the option of raising `startTimeoutSeconds` for this one deploy |
| The lint rule's exclusion block misses a Loom-only file, or a wrap changes a string a Loom test asserts | S2b | The count must be 0 on Loom-only files after the block (`vp check`); English is the source text, so tests asserting English keep passing if the English inside `gt()` is unchanged |
| The markdown ports are skipped or half done and chat silently loses ticket links and bare path links | S2b, Gate 2 | §10 `markdown`; the new `wordsHast` unit test; S4 checks one reference link live (the harness cannot) |
| Inline diff editing regresses on `@pierre/diffs` 1.7 (the first keystroke jumps) | S2b, S4 | Loom's hunk goes into the 1.7 patch; S4's seven-step journey (§9) |
| Carl's saved right-panel layout breaks (a saved side-chat tab the build cannot render) | S1 lane 5, S2b | Version 17 (§6.9); S2b loads a saved v16 state |
| The meter's re-home is larger than sized, or Carl rules to take upstream's deletion after S2b built it | S2b | S1 starts on "keep", the cheaper side to reverse (a deletion); S2b does the meter last in its list, after the rulings are in |
| Loom's `reportedError`, the resume sanitiser or the text-generation probe is resolved the obvious way and breaks pi turns or moves titles off the hub | S1 lane 2, Gate 1 | §6.3's six traps are on Gate 1's list; S2a's suites; S4's pi journeys and the Settings picker check |
| The CLI path applies a Loom migration behind a running server | S1 lane 1, Gate 1 | `Sqlite.ts`: both setup paths and the pending test (§5.5); S2a's test |
| Node 26.13.1 changes behaviour beyond the one SQLite pattern | S3 | S3 runs every suite on it; `n 26.12.1` reverses it in one command |
| The launcher switch 3 → 4 fails on the real pairing (old launcher, new runner), which no test covers | S3, deploy | The failure mode is the automatic put-back; S3 tries one cross-version seam run; the deploy watches the switch |
| The APK build fails on the new native modules | deploy | Watch `build.log` and the six post-build checks; the old APK keeps working against the new server |
| `origin/main` moves before or during S1 (Loom PRs in flight) | S1 lead | Before opening: merge it in first. After opening: hold; a catch-up merge after S1's commit (DL-2430+) |
| Upstream moves about 240 commits a day, so the next pull grows by a pull-15's worth every three days this one takes | orchestrator | Parallel lanes; no scope added to this pull; follow-ups stay follow-ups (§8.3) |
| A decision row is ruled differently after the session that depends on it has run | orchestrator | §8.1's last column prices each reversal; the three with real cost are the meter, the translation rule and the tool lists, all cheap in the recommended direction |
