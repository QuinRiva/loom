## 4. The orchestration overlap — upstream's subagent model vs Loom's workstream

Carl expected "a big conflict with the new orchestrator approach". This
section is the file-level answer. Upstream's model: a parent thread calls
`delegate_task`, which creates an **`app_owned` subagent record** on the parent
(`OrchestrationV2Subagent`, `origin: "app_owned"`) and a child thread whose runs
carry `delegatedTaskId`. Everything upstream built since the base — question
routing, wake-ups, stop propagation, worktree isolation, background tool
access — is keyed on that record. Loom's model: `workstream_spawn` dispatches
Loom's own `thread.spawn` (`Orchestrator.loom.ts` line 1095), which emits
`thread.created` + `thread.workstream-created` and **never a subagent record**;
the child carries `lineage.parentThreadId` and `relationshipToParent: "subagent"`
but no `delegatedTaskId`. Lineage is shared; task records are not. That one
fact decides most of the table.
