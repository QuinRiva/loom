## 2026-09-25 — heap-retention researcher (loom thread, worktree t3code-9bf25c2c): refinements to the queue-backlog root cause

Measured on a VACUUM copy of the cockpit DB (release 20260925-020235-9ad7082, no agents, foreign-home guard on) plus the live `--trace-gc` journal. Read-only; no code changed.

1. **The ~2.3 GB main-isolate baseline is not backlog.** It exists with zero agents: the copy settles at 2.1–2.3 GB live 30 s after boot and stays flat for 15 min idle. The live cockpit shows the same (2.30–2.38 GB about 90 s after every boot). So the ingestion backlog only has about 1.7 GB of headroom before the ~4.4 GB limit. Removing the baseline roughly doubles the time to OOM, independently of the queue fix.
2. **What holds the baseline:** the rows loaded by the boot-time full `getSnapshot()`, which includes every thread's activities, messages and checkpoints. It is called by `ProviderRuntimeIngestion.reconcileInterruptedToolActivitiesOnStartup`. Allocation sampling puts about 1.45 GB in `Schema.parseJson` (row JSON decode) and about 0.6 GB in node:sqlite row objects. On a copy trimmed to 1/20 of the activities and messages, the baseline fell to about 0.4 GB, so it scales with activity + message volume. That set is 458k activities (970 MB of `payload_json`) plus 210k messages.
   The retainer path (heap snapshot dominator tree): Effect `Cache` entries (`VcsDriverRegistry.detectionCache`, `GitVcsDriverCore.defaultBranchCache`, `providerContextCache`, …) keep their lookup `FiberImpl` after it exits. In effect rc.115, `fiber.cache.stackFrame` (the `Effect.fn` `callError` → CallSiteInfo closure context) and `fiber.cache.span` are not cleared on exit. They pin the calling request's locals: `activityRows`, `messageRows`, `threadRows`, `checkpointRows`, and whole `snapshot` objects.
3. **A second 2.3–2.4 GB regression, in the sqlite worker isolate. It is separate from the main heap and not the OOM isolate, but it adds to RSS (7 GB).** The `SqliteWorker` `prepareCache` entry → lookup fiber → `fiber.cache.span` (NativeSpan of the RpcServer request) → `status.exit.args` holds the full result-row array of the first query that prepared each cached statement. That was 219 of 239 MB on the trim copy and about 2.4 GB on the full copy.
   Journal evidence that this is a pull-7 regression: the pre-pull-7 release 5c350f7 (effect beta.103) ran the worker at a steady **15 MB**. Every release from 576d1e8 on (effect rc.115) runs it at **2.29–2.44 GB**. Over the same boundary, the main baseline rose from about 1.8 GB to about 2.35 GB. Pre-pull-7 main also climbed (1.8 → 3.4 GB over 35 h) but never crashed.
4. **Growth without agents:** light synthetic load (1 thread-detail GET/s, turn-start/meta dispatches every 3–5 s, all provider side effects refused) grew main from 2.3 to about 3.0 GB post-GC in about 5 min on the full copy, and from 0.4 to 0.8 GB on the trim copy. So churn-driven growth also exists outside the ingestion queue, with no pi RPC traffic at all. I did not attribute it: re-scoped before the growth snapshot.
5. **Span/trace buffering:** there is no span-exporter or trace-file buffer among the top dominators. Spans retain memory only incidentally, as described above: an ended NativeSpan keeps its `Exit` value and is reachable from a cached fiber's `cache`.
