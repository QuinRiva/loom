# Hand agents the report path, and stop pointing them at the graph

**Why.** Reports as the hand-off medium work: **62%** of child reports are read by another thread, a parent reads within **1.4 minutes** (median), and after **1,541** reads there was **one** consult of the author and under **3%** went on to open the author's session. Finding them is the failure: **240 of the 353** list calls that led to a report read already held the author's id, and **199 of 243** reviewer calls are a gated reviewer at turn five or earlier looking up the one path its kickoff id implies. The path is deterministic and no prompt states the rule, so agents never derive it.

**What ships.** Deliver the report path wherever a thread id is delivered (gate kickoff, dependent child's kickoff, one derivation line in every identity clause). Delete the sentences that tell agents to call `workstream_list` and make its description say what it shows. Make `workstream_list` lean by default (a measured **60%** smaller on the 266 real outputs), with `detail: "full"` restoring purposes, anchors and session paths, and drop the spawn catalogue from it entirely. Replace the 400-character wake excerpt with a **required response block** every report carries and every notice relays verbatim. Let the liveness sweep resume a **root** after a provider error, as it does a child since PR #415. Of the audit's **$437 per 30 days, $171 was overnight watchdogs**, a symptom of stall risk that the root resume addresses and that is not counted here; of the **$266 that remains, about $200 goes**, for under $10 of added prompt per 30 days. No new tool.

### 3.4 Remove the spawn catalogue from `workstream_list`

Carl asked why it is in the list at all. It landed there in July (`plans/2026-07-13-capability-based-model-selection.md`, line 319) because the pi bridge was then post-and-print and `workstream_list` was the one text surface a parent saw. That constraint is gone, and the audit shows the cost: 32 calls, $14, printed for every caller including leaves that cannot spawn, and 27 of the 32 used nothing from it. It goes, from the renderer and from `handlers/list.ts` (`spawnCatalogue` is no longer read there).

Its two consumers are served elsewhere. **An orchestrator checking preset names:** `resolveSpawnModelSelection` in `apps/server/src/mcp/toolkits/workstream/modelSelection.ts` already rejects an unknown `modelPreset` with `Unknown modelPreset "x". Available presets: a, b, c.`; nothing was spawned, so a wrong guess is a free lookup. **The platform-update `[INVALID]` check** (`docs/operations/platform-update.md` around lines 291 and 418, and the pi-craft `platform-update` skill out of repo) read the list for presets whose instance or model is not in the catalogue. That marker moves onto the same rejection echo: `resolveSpawnModelSelection` has `input.presets` and `input.catalogue` in scope, and `validateModelSelection(preset, catalogue)` is the pure check `spawnCatalogue` already runs per preset, so the message becomes `Available presets: a, b [INVALID: model "…" is unknown for instance "…"], c.` with no extra reads. The runbook step becomes "spawn with a bogus preset name and read the echo"; the negative-control logic is unchanged. The `taskShape` and profile lists are not needed by either consumer; `spawnCatalogue` and `TASK_SHAPE_HINTS` are deleted if nothing else imports them.

**Test.** `resolveSpawnModelSelection` with an unknown preset and one invalid configured preset returns the names with the `[INVALID: …]` marker on the invalid one.

### 3.5 A required response block replaces the 400-character excerpt

Every notice that relays a report (digest, yield, attention wake, both gate legs) carries the first 400 characters, which 99.5% of reports overrun, and 25% of parent actions happen on that cut alone. Carl's direction: the report carries a tagged response block the author writes as the concise answer, the control plane parses it and relays it verbatim, and the full report stays on disk for the detail.

**The tag.** HTML comment delimiters, `<!-- response -->` and `<!-- /response -->`, around ordinary markdown at the top of the report. Chosen over a `<response>` element because comments are invisible in every markdown renderer the report meets (the file preview, the digest card's `markdown(item.excerpt)`, GitHub) without a sanitiser rule, cannot collide with prose that mentions a tag in backticks, and parse with one regex. The block's content is markdown, so a heading or a short list inside it renders as such.

**Parsing and relay.** One function, `reportResponse(markdown)` in `apps/server/src/loom/workstream/report.ts`, returns `{ text, source: "block" | "head" }`: the first block's inner text trimmed, else the head of the report cut at the legacy limit. `formatReportExcerpt` and `boundedExcerpt` in `apps/server/src/loom/orchestration/dispatcher/wakes.ts` call it: a block is relayed verbatim with no truncation marker; a head fallback keeps today's cut and its `_[excerpt truncated — …]_` line. The duplicate pair in `apps/server/src/mcp/toolkits/workstream/render.ts` (`REPORT_EXCERPT_LIMIT`, its own `boundedExcerpt` and `formatReportExcerpt`) is deleted and its importers re-pointed at `wakes.ts`; `rails.ts` line 362 cuts a relayed human message, not a report: it keeps a plain 400-character head cut of its own instead of calling the report-parsing `boundedExcerpt`. `WAKE_REPORT_EXCERPT_LIMIT` is renamed `LEGACY_REPORT_HEAD_LIMIT`, stays 400, and applies only to reports with no block: the synthesised "went quiet" reports (which have no author to write one) and reports written before this ships. A block longer than a generous bound (4,000 characters) is cut at the bound with a marker; the constant's comment says it is a guard against a report that wrapped itself in the tag, not a target length. No fixed length is a design parameter.

**Enforcement.** `handlers/submit.ts` refuses a report without a block before writing anything, beside its other input checks: `Report has no response block. Put a concise summary of your hand-back (the gist of the answer and what the receiver must act on; the full answer stays below it) between <!-- response --> and <!-- /response --> at the top of the markdown and submit again.` A block with no text counts as none. Gate round reports are submits too, so they carry one.

**Guidance** (instruction text, tier 2). `workstream_submit`'s `markdown` description in `defs.ts` gains: `Open with a <!-- response --> … <!-- /response --> block: a concise summary of your hand-back, giving the gist of the answer and anything the receiver must act on. Every notice carries the block verbatim to whoever receives your work. The full report below it may be as long as the work needs and is read from the file on demand; when the answer itself is long, the block summarises it rather than containing it.` The kickoff wrapper in `prose.ts` changes "Write the report as a concise handoff for your parent orchestrator, not a transcript dump: lead with" to "Write the report as a concise handoff for your parent orchestrator, not a transcript dump, opening with the response block its markdown description asks for: lead with". Role lines that already say what the report leads with are reworded to say the response block holds it: `roles/researcher.md` line 37 becomes "Your `mcp__t3-code__workstream_submit` response block gives the answer; the evidence follows it in the report.", and `roles/planner.md` line 42's first sentence becomes "Your `mcp__t3-code__workstream_submit` response block gives the plan's location and its key decisions." No role gains a new rule.

**Test.** `reportResponse` on a report with a block, without one, with two (first wins), with the block inside a code fence (still matched: the guard cut covers the pathological case), and over the bound. Submit refuses a blockless report with the message above and writes nothing. A digest for a child with a block relays it verbatim with no truncation marker; for a synthesised report, the head cut.

**Measurement.** From the first week of reports after release, extend `reportsizes.py` to print the response-block length distribution (expected: median well under 1,000 characters; a p90 past 2,500 means the guidance is read as "put the report in the block") and the share of reports falling back to the head (expected: only synthesised ones after the first day).

### 3.6 The liveness sweep resumes a root after a provider error

What the watchdog threads were for, in Carl's words: "a simple backup mechanism to ensure that a large graph didn't stall on large overnight work. If loom was robust, and never stalled, they would never be needed." For a **child** the rails now cover every condition those briefs polled: a run that dies on a provider error gets one steered resume naming the error (`apps/server/src/loom/orchestration/liveness/errorResume.ts`, PR #415, commit `fbf0225d5c`), then an `error` flag to the parent on repeat; a frozen turn gets a nudge, then `error`; a quiet child is yielded with a synthesised report; a usage limit is parked and rerouted; a wedged child is flagged; a stuck graph raises a deadlock notice. The gap: `WorkstreamLivenessSweep.ts` skips every row with `parentThreadId === null`, so a **root or orchestrator whose own turn dies on a provider error is resumed by nothing**, and its children's wakes queue until a human writes to it. That is the stall an overnight graph would most likely take now, and the one a watchdog child could catch.

This is about provider failures that end the run (a dropped stream, an "unexpected EOF", a 5xx): the run's status is `failed` with a `lastErrorClass` other than `usage_limit`. A malformed tool call is not one; pi returns that as a tool error inside the turn and the model carries on.

**The change.** In the sweep loop, a root (`parentThreadId === null`, in `listActiveWorkstreams` because every root that has delegated has a loom row) is judged on the failure path only: `resumeAfterError` sends the same one steered resume under the same `errorResumeCommandId(threadId, runId)` with the same `errorResumeText`, and `awaitsErrorResume` already refuses a second one per failure episode. On `failureCap` consecutive failed sweeps `markDead` raises `error` on the root itself; the attention rail skips rows with no parent, so no notice is composed, and the flag shows on the root's card and in the inbox as any `error` flag does (the web's `workstreamPresentation.ts` already maps it). Stall nudges (State C), spinning and slow-tool advisories stay sub-thread only: the first because a root's long human-facing turns are not a child's, the others because they are digest items and a root has no digest. The quiescence rail keeps excluding roots (`quiescence.ts` line 67): a root ends turns without submitting by design. Usage limits on roots are already the reroute sweep's.

**Root-specific checks the coder makes.** `controlMessage` with `tier: "steered"` lands on a root the same way (it is the same thread kind); `submitSupersedesFailure` is false for a root (no `lastOutcome`), which is correct; a root never delegated has no row and is not covered, which is correct since it has no graph to stall; the resume must not fire while the human is mid-conversation, which `awaitsErrorResume`'s "no run after the failed one" clause already guarantees.

**Test.** In `liveness.test.ts`: a root with a failed latest run gets one `error-resume` control message; the same root on the next sweep gets none; after `failureCap` failed sweeps it carries the `error` flag; a child's behaviour is unchanged. A `failed` root with a later queued run gets nothing.
