# Pull 9 Phase 4 — import Loom's history into V2 and stand up a QA world

Loom is a Pi-first fork of `pingdotgg/t3code` whose product is an orchestration layer — goals, a shared task tree, a workstream graph of durable threads with roles, briefs, dependencies, review gates, attention flags and reports. The signed strategy (`plans/upstream-pull9-strategy/plan.mdx`) re-platforms that layer onto upstream's Orchestration V2; Phase 2 (`plans/upstream-pull9-phase2-substrate/plan.mdx`) defines the sidecar table it lives in; Phases 1–3 leave a branch where Loom works on V2 against an **empty** workstream layer. **Phase 4 brings Carl's history across** — the workstream fields of his threads, each thread's binding to its existing pi session, and the lineage that keeps children out of the sidebar — and stands up a **QA instance** he can test for days without touching production. Carl's scope: *work through to phase 4 including data import, but not deletions and cut-over*; *run this without overwriting the local DB … ensure that we can still roll back to this version of Loom*.

**Done** means: the importer in this plan runs at the first V2 boot of a copied database and is idempotent on every later boot; the fixture test in *Gates* passes; a QA home built by the procedure below runs the pull-9 build against a relocated copy of production inside a sandboxed systemd unit — the guard off because every recorded path is the QA home's own, and production, the release store and production's pi sessions unwritable from inside the unit; an imported orchestrator and an imported child each remember their transcript when continued, in a QA working directory; the first dispatcher pass after import sends no kickoff and no digest; `vp run typecheck` and `vp check` are green; and `docs/upstream-sync/30-pull9-phase4-qa-guide.md` exists for Carl to walk. Nothing in Phase 4 deletes V1 code, merges to `main`, or deploys.

## Three facts that change the procedure

<Callout tone="risk">
**1. Production does not live at `~/.t3/userdata`.** The cockpit unit runs with `T3CODE_HOME=/home/Carl/.t3/cockpit` (`~/loom-releases/RUNBOOK.md`, `systemctl --user cat loom-cockpit`); the live database is `~/.t3/cockpit/userdata/state.sqlite` (6.1 GB plus WAL), and `~/.t3/userdata/state.sqlite` is **0 bytes**. Every snapshot in this plan reads the cockpit home. The hard rule is restated accordingly: **nothing in Phase 4 writes to `~/.t3/cockpit`, `~/.t3/userdata` or `~/loom-releases`** — the cockpit home is the one that matters, and the Phase 4 worktree itself sits under `~/.t3/cockpit/worktrees/`, which is the one place inside that home Phase 4 legitimately writes (its own checkout).

**2. A raw copy of production cannot drive an agent.** Loom's foreign-home guard (`apps/server/src/workspace/foreignHomeGuard.loom.ts`, carried into pull 9 as DL-81) engages whenever a database records worktree paths and none sits inside the running home's `worktrees/` directory — which is every `VACUUM INTO` copy of the cockpit — and an engaged guard refuses provider session open, worktree create, checkpoint capture and setup scripts. `docs/dev-site-testing.md` says it outright: a copy-DB instance "is deliberately incapable of" driving an agent, and the Phase 1 runbook split its smoke into a read-only copy (A) and an agent-driving empty home (B) for exactly this reason. The strategy's Phase 4 gate — *continue an imported orchestrator and an imported child and confirm each remembers* — therefore cannot run on a raw copy. And even with the guard forced off it must not: pi's RPC `switch_session` resumes **into the session's recorded working directory** (`agent-session-runtime.js`: `createRuntime({ cwd: sessionManager.getCwd() })`) unless the adapter passes a `cwdOverride`, so an imported thread continued on a raw copy would run its tools in production's live worktree and append to the very session file production's pull-8 server is driving. The resolution is a **relocated QA world** (§2): the copy is rewritten before its first V2 boot so that every recorded path — project roots, worktrees, report and brief files, pi session files — lives under the QA home, and the importer binds sessions through a parameterised root. The strategy's author (consulted, medium confidence) endorsed this with three conditions, all adopted: the relocation is a QA-only script the cut-over runbook names as **must not run**; session files are byte copies, never hard links; and the gate checks *before* the first boot that every recorded path column is under the QA home (an allow-list, not a search for the cockpit prefix), so an unrelocated copy fails loudly. The guard itself is not a check: it switches off as soon as one recorded path is inside the QA home. Relocation only aims the QA world at its own copies; what stops a QA agent that follows a production path quoted in an old transcript is the **sandbox**: the QA server runs in a systemd user unit with `PrivateUsers=yes`, production's home, the release store, the shared `.git` and production's pi sessions read-only, and git, `gh`, SSH and Slack credentials and the user bus inaccessible (§2 *The sandbox*).

**3. `planned` is not "never started" in V1 data.** V1 roots created through `goal_handoff` or `thread_fork` are born `planned`, and a turn start deliberately leaves `planned` untouched ("it is a deliberate hold" — `apps/server/src/orchestration/decider.ts:2171`), so a root can carry hundreds of turns at `plan_lane = 'planned'`. Mapping `planned → held: true` unqualified would hold most of Carl's goal-handoff roots forever (an imported root has `kickoffAt`, so the human-release rule never fires). The six-lane mapping below qualifies `planned` by whether the thread has ever had a turn.
</Callout>

## 1. The importer

### Where it runs, and when

`LoomV1WorkstreamImporter.reconcile` is a **startup phase**, not a migration and not a CLI: it needs `EventSinkV2` (the lineage and binding are V2 events) and `LoomStoreV2`, which exist only in the running layer, and it must run **after** upstream's `reconcileShells` (every V1 thread then has a V2 `thread.created`, including the parents the lineage re-emit points at) and **before** `providerRuntimeRecovery.recover` and the Loom reactors (so the dispatcher's first pass sees complete sidecars). Upstream sequences those as `runOrderedV2StartupPhases({ importLegacyShells, recover, … })` in `serverRuntimeStartup.ts`; the Loom hunk is one marked line that pipes the import phase on:

```ts
// apps/server/src/serverRuntimeStartup.ts — inside runOrderedV2StartupPhases({...})
importLegacyShells: runStartupPhase(
  "orchestration-v2.legacy-v1.import-shells",
  legacyV1ThreadImporter.reconcileShells.pipe(
    Effect.tap(/* upstream's log */),
    Effect.andThen(loomV1WorkstreamImporter.reconcile), // loom: workstream sidecar, lineage, session binding
  ),
),
```

It runs on **every** boot and is idempotent: its pending query is `projection_threads` rows that upstream has imported (`orchestration_v2_legacy_imports`) and that have no row in Loom's own ledger `loom_legacy_imports`. On a fresh install both are empty; after cut-over the ledger covers every V1 row, so the phase costs one indexed query. It records that it ran, per thread, in the ledger (§1 *The ledger*). **Re-running** is deleting ledger rows with the server stopped: `DELETE FROM loom_legacy_imports WHERE thread_id = ?` re-processes one thread; deleting all rows re-processes everything — safe, because the sidecar insert is `ON CONFLICT DO NOTHING`, the lineage re-emit is skipped when the V2 row already carries `subagent` lineage, and the binding is skipped when the thread already has a provider thread with a strong `nativeThreadRef`. There is no retry loop for missing session files: a file that appears later is re-bound by deleting that thread's ledger row.

One parameter, read from the environment because a startup phase has no argv, and it is **pi's own variable**: `PI_CODING_AGENT_SESSION_DIR` (pi's `ENV_SESSION_DIR`, `dist/config.js`), which tells every pi process the server spawns where to create, fork and look up sessions. When it is unset the importer indexes pi's default root `~/.pi/agent/sessions` (slug directories, depth 2) — the cut-over value; when it is set, as the QA unit sets it, the importer indexes that directory (pi writes it flat when the variable is set — `SessionManager.create(cwd, sessionDir)` uses the directory as given) and every session QA creates or forks lands there too. One variable, read by both pi and the importer, so the bindings and the new sessions can never name different roots. The importer logs the root it indexed in its summary line, and `verify.sql` F asserts every bound path is under it.  Path rebasing of reports, briefs and worktrees is **not** an importer concern: the QA relocation rewrites the V1 copy before boot (§2), and at cut-over the paths are already right.

### The thread re-emit: lineage, and the provider fix

Upstream's importer writes every imported thread with `lineage: { parentThreadId: null, relationshipToParent: null, rootThreadId: threadId }` (`legacy/LegacyV1ThreadImporter.ts`, `importedThread`), so an imported Loom child would surface as a top-level sidebar thread and receive thread notifications. Lineage lives only in `orchestration_v2_projection_threads.payload_json`, and every upstream thread mutation is a full-row `thread.metadata-updated` — so the importer reads the current V2 row and re-emits it with lineage set, exactly as upstream's own metadata-repair path does. The same event carries the **provider fix** (below) when it is needed, so a root on upstream's codex fallback gets its re-emit too; a thread needing neither is not re-emitted. The binding event is written **after** the re-emit in the same transaction, so the projector's `activeProviderThreadId` write is the last word on the row:

**Provider fix.** Upstream's `modelSelectionFor` falls back to `{ instanceId: "codex", model: DEFAULT_MODEL }` when a V1 row has no decodable `model_selection_json`. A Loom thread with a pi session on disk is a pi thread whatever its row says, so when the binding finds a session and `current.providerInstanceId` is not the pi instance, the thread re-emit (previous section — issued for roots too, not only for lineage) sets `providerInstanceId` and `modelSelection` to the pi instance (model: the row's model if it had one, else Loom's default pi model), and the binding written after it uses that instance id. **Missing session.** No binding, ledger `session: missing`; the thread's first continuation gets upstream's designed fallback — a fresh pi session with a 32,000-character transcript handoff — and the `missing` list is part of the pre-boot report, because in production that list should be near-empty (every Loom thread was launched with `--session-id`), and a long list means the sessions root is wrong.

**Resume failure is silent — the gate reads the log.** If `switch_session` fails, `ProviderTurnStartService` logs `Provider resume failed; attempting a fresh native session` and continues with a `full_thread_summary` handoff — amnesia with a warning nobody reads. The remember-check (§6) therefore also asserts that line appears zero times for imported threads.

### No legacy handoff for a bound thread — one upstream hunk

Upstream prepares a legacy-import handoff on an imported thread's first run whenever `historyOrigin === "v1_import"`, the thread has no completed run and its imported transcript items exist (`shouldPrepareLegacyImportHandoff`, `Orchestrator.ts`, called from the immediate-start path at `:5076`; the queued-start path in `startNextQueuedRun` already keys its legacy handoff on `needsFullContext`, i.e. on the native ref being null). The immediate path never looks at the native ref. For a bound Loom thread that means the resumed pi session — which already holds the whole conversation — receives a `Context handoff (legacy_import)` block plus up to 32,000 characters of its own transcript prefixed to Carl's first message, permanently, in every imported thread. The pure helper gains one argument:

```ts
// apps/server/src/orchestration-v2/Orchestrator.ts — marked hunk
export function shouldPrepareLegacyImportHandoff(input: {
  readonly hasCompletedRun: boolean;
  readonly historyOrigin: OrchestrationV2AppThread["historyOrigin"];
  readonly legacyImportItemCount: number;
  readonly hasStrongNativeRef: boolean; // loom: a thread bound to its native session already has its history
}): boolean {
  return input.historyOrigin === "v1_import" && !input.hasCompletedRun &&
    input.legacyImportItemCount > 0 && !input.hasStrongNativeRef;
}
// the one call site (immediate start): hasStrongNativeRef: activeProviderThread?.nativeThreadRef?.strength === "strong"
// the queued-start path needs no change: it already gates on needsFullContext (nativeThreadRef === null)
```

`historyOrigin` stays `v1_import` (it is what makes the imported transcript count as pre-run history for fork boundaries, item windows and the awareness relay). Unbound threads keep upstream's handoff by construction. Upstream's own `AgentSessionImporter` path has the same redundancy, so this hunk is a candidate to upstream.
