Build the brief's read-only Tasks tab as **two coder pieces in sequence and one delivery step**. Everything the tab draws already reaches the phone. Goals and their task trees arrive on the connection that feeds the Home list, and so does an agent's tick, within the same second. The work is reading that data and drawing it. All of it lands in Loom-owned mobile files, apart from **one edited hunk in one upstream source file** and one export line.

## 3. What the tab shows: the row rules

The tab is a flat list of rows computed from the goal's tree. One pure function decides the rows; the components only draw them. This is the part worth getting exactly right, because a mistake here hides work that is left.

```text

caption   ○ Production GraphtusEnricher, built in small PRs Carl wa…
task      ▾ First chunk: Stage 1 document typing from the doc tree…        5/20

task        ▾ Phase 1: basic typing from each document's summary…          3/10
```

This is the real 31-task goal from the brief's pictures, on To do, as the function below orders it. The two thread rows have their state set, as in the mockup.

### The rules

1. **Order is the tree's own**: depth first, siblings in their stored order. That is the walk web's `TaskTree` does, so All lists every task in web's order.
2. **A lone top-level task that has sub-tasks is a caption**: one line, with its ring or tick, and its sub-tasks start at depth 0. Any other goal starts at depth 0 with its top-level tasks.
3. **On To do, a run of finished siblings is one row.** A task is _finished_ when it is ticked, every task beneath it is ticked, and no thread on it or beneath it is still live. The row reads `N finished`, where N counts every task in those subtrees. A run that is a single task with no sub-tasks shows that task's text on one muted line.
4. **A ticked task that is not finished stays an ordinary row**, ticked and muted, with its count; its finished sub-tasks fold as in rule 3.
5. **A run opens in place.** Tapped, its row stays as a heading with the chevron down, followed by its tasks as All would show them. Tapped again, it closes.
6. **On All there are no runs.** Every task is a row. Finished ones are ticked and muted, not struck through.
7. **A task with sub-tasks** is bold, cut at two lines, and carries `done/total` over the tasks beneath it, itself excluded. Tapping the left of the row, where the chevron sits, folds its subtree to that one row on either filter.
8. **A task without sub-tasks** is cut at three lines. Tapping any task's text shows it in full; tapping again cuts it.
9. **Under a task, its owning threads.** Each live thread is a two-line row: title and age or flag, then role and state, the same words the Graph's row uses. Then the finished ones. Exactly one, with no live thread beside it, is one muted line reading `title · role` that opens it. Otherwise the line reads `N threads finished` and opens in place to those lines.
10. **One task can be marked** (`THIS THREAD'S TASK`, tinted). Unfolded, it is the task of the thread open on the right. On the cover screen, it is the task you arrived at from a thread's header line.
11. **Indent is 15 dp a level, every level.** The deepest real tree is 9 levels, 7 indent steps once its lone top task is a caption, which leaves about 250 dp for text at 412 dp.

A thread is _live_ when it has no outcome yet or carries a flag: `node.outcome === null || node.reasons.length > 0`. A task's owning threads are the non-archived threads the phone holds whose `workstream.goalId` is this goal and whose `workstream.anchorTaskId` is the task, oldest first. That is web's rule, moved to the shared package in §5.

Above the rows, as the list's header, come the needs-you cards and then the goal block. The goal block is the goal's title, its objective cut at two lines until tapped, a progress bar with `9/31 done · 22 to go`, and the To do / All switch with its counts. To do is `total − done` and All is `total`, from the same `countGoalTasks` web's badge uses.

### The contract

```ts
// apps/mobile/src/features/workstream/goalTaskRows.loom.ts
export type TaskFilter = "todo" | "all";

export type GoalTaskRow =
  | { kind: "caption"; key: string; taskId: string; text: string; done: boolean }
  | { kind: "task"; key: string; taskId: string; depth: number; text: string; done: boolean;
      count: { done: number; total: number } | null;      // null without sub-tasks
      folded: boolean; fullText: boolean; marked: boolean }
  | { kind: "run"; key: string; depth: number; label: string; open: boolean }
  | { kind: "thread"; key: string; threadId: ThreadId; depth: number; quiet: boolean }
  | { kind: "threads"; key: string; depth: number; count: number; open: boolean };

export function goalTaskRows(input: {
  tasks: ReadonlyArray<LoomGoalTask>;
  filter: TaskFilter;
  /** What the person opened or folded: "fold:<taskId>", "run:<first taskId>", "text:<taskId>", "threads:<taskId>". */
  toggled: ReadonlySet<string>;
  threadsByTask: ReadonlyMap<string, ReadonlyArray<{ id: ThreadId; live: boolean }>>;
  markedTaskId: string | null;
}): ReadonlyArray<GoalTaskRow>;

/** `toggled` without the folds that hide `taskId`, so a jump to it lands on a visible row. */
export function unfoldTo(tasks: ReadonlyArray<LoomGoalTask>, taskId: string,
  toggled: ReadonlySet<string>): ReadonlySet<string>;
```

Keys are the task id, `run:` plus the run's first task id, and `thread:` plus the thread id, so a row keeps its identity when a neighbour is ticked. The function reads structure only. What a thread row says (step, age, flag) is read from the thread at render, so a running step ticking over never re-runs it.

<Details summary="The reference: rules 1 to 4 and 6 as 30 lines of Python, for the coder to check the TypeScript's row counts against">

Save as `task_rows.py`, run anywhere on the cockpit VM with one or more goal ids. It opens the live database read-only. It ignores owning threads, folds and opened runs, so it gives the task-row counts in the table above.

```python
import collections, os, sqlite3, sys
con = sqlite3.connect(f"file:{os.path.expanduser('~')}/.t3/cockpit/userdata/statev2.sqlite?mode=ro", uri=True)

def load(goal_id):
    rows = con.execute("""select task_id, parent_task_id, text, done from loom_goal_tasks
        where goal_id = ? and deleted_at is null order by position""", (goal_id,)).fetchall()
    ids, kids = {r[0] for r in rows}, collections.defaultdict(list)
    for r in rows: kids[r[1] if r[1] in ids else None].append(r)
    build = lambda r: dict(id=r[0], text=r[2], done=bool(r[3]), kids=[build(k) for k in kids[r[0]]])
    return [build(r) for r in kids[None]]

def size(task): return 1 + sum(size(k) for k in task["kids"])
def finished(task): return task["done"] and all(finished(k) for k in task["kids"])

def rows(tasks, todo, depth=0, top=True):
    if top and len(tasks) == 1 and tasks[0]["kids"]:          # rule 2: a lone top-level task is a caption
        return [("caption", 0, tasks[0]["text"])] + rows(tasks[0]["kids"], todo, 0, False)
    out, i = [], 0
    while i < len(tasks):
        task = tasks[i]
        if todo and finished(task):                             # rule 3: a run of finished siblings is one row
            j = i
            while j < len(tasks) and finished(tasks[j]): j += 1
            n = sum(size(t) for t in tasks[i:j])
            out.append(("run", depth, task["text"] if n == 1 else f"{n} finished")); i = j
            continue
        out.append(("task", depth, task["text"]))               # rule 4: ticked but not finished stays a row
        out += rows(task["kids"], todo, depth + 1, False)
        i += 1
    return out

for goal_id in sys.argv[1:]:
    tasks, title = load(goal_id), con.execute("select title from loom_goals where goal_id = ?", (goal_id,)).fetchone()[0]
    todo, everything = rows(tasks, True), rows(tasks, False)
    print(f"{title}: To do {len(todo)} rows ({sum(r[0] == 'run' for r in todo)} runs) | All {len(everything)} rows")
```

## 4. What the phone reads, live updates, and what it costs

**One source, already there.** The phone's connection is the shared one in `packages/client-runtime/src/state/shell.ts`, which asks every Loom server for goals. The snapshot it holds has a `goals` array beside `threads`. When any goal changes, the server sends the whole goal as a `goal.updated` item, and `applyLoomGoalItem` replaces it in that array. <Sidenote>`packages/client-runtime/src/state/shellGoals.loom.ts`; the server side is `LoomGoalBroadcast`, published to by the agents' task tools in `apps/server/src/mcp/toolkits/workstream/handlers/shared.ts` and by web's edits in `apps/server/src/loom/wsMethods.ts`.</Sidenote> The phone receives and stores all of this today and draws none of it.

**Live updates need no wiring.** An agent's tick is published after its write and reaches every connected client on that same connection. The tab reads an atom derived from the snapshot, so the row turns to a tick and the counts move when the item lands. The tunnel and the relay carry the same socket as the tailnet. So the brief's "the same holds over the tunnel" is the claim that the Home list updates over the tunnel, which it does today. Only a phone off the home network can confirm it on screen.

**The 435-task goal.** Three things keep it smooth, and one is unchanged by this build:

- The list is a `LegendList`, the virtualised list the Graph and the Home list use. It mounts the rows on screen and a margin, whether the goal has 9 tasks or 435. Rows give it their kind through `getItemType`, so it recycles like with like.
- The row rules are one walk of the tree. On the 435-task goal the Python reference takes 0.5 ms; piece 1 times the TypeScript the same way (§7). They run on a change to the goal or a tap, never on scroll.
- A tick repaints the changed rows only. Every `goal.updated` carries the whole goal with new object identities, so rows are compared by value, not identity.
- Unchanged: each tick of that goal arrives as the whole goal, about 0.2 MB. The phone already receives and decodes it today whether or not the tab is open.

**A goal the phone does not hold.** `createLoomGoalAtoms` already answers this. Its `goalAtom` returns the goal from the snapshot, else asks once with `loom.goal.get` and caches the answer. A later change arrives on the stream and joins the snapshot. The tab and the header button use `goalAtom`. The Home row uses only what the snapshot holds, as §2 argues.

**Owning threads the phone does not hold.** The 435-task goal's 408 threads sit under 30 top-level threads. The tab shows the owning threads of the workstream it is opened on (loaded while the screen is open, §2) and of every other unsettled one. Threads under other finished workstreams of the same goal are absent. Web's panel has the same limit.

## 5. Shared logic: what moves
