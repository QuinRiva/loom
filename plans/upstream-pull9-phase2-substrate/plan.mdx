# Pull 9 Phase 2 — Loom's substrate on upstream's Orchestration V2

Loom is a Pi-first fork of `pingdotgg/t3code` whose product is an orchestration layer — goals, a shared task tree, a workstream graph of durable threads with roles, briefs, dependencies, review gates, attention flags, liveness and reports. Upstream's Orchestration V2 deleted the V1 engine that layer sat on, and the signed strategy (`plans/upstream-pull9-strategy/plan.mdx`, revision 3) decided to re-platform: `upstream/main` becomes the base and Loom's layer is re-expressed on it. Phase 1 (the mechanical merge, running in parallel) leaves V2 Loom booting with the workstream layer absent. **Phase 2 builds the seams that layer attaches to**: the sidecar contract beside upstream's closed unions, a Loom decider arm redesigned for V2's per-thread lock, the two dispatch/receipt-core hunks, the Loom projector and sidecar tables, the goal tables, the `1046+` migrations, and the substrate half of quiescence-as-completion. Phase 3's four tracks (MCP toolkit, dispatcher and rails, driver economics, web re-hang) consume what this plan delivers; Phase 4 imports Loom's historical data into the tables it defines.

**Done** means: the files below exist on the integration branch; `vp run typecheck` and `vp check` are green; the seven tests in *Verification* pass against V2's real orchestrator, event sink and SQL projection (no mocked engine); every hunk in an upstream file carries a `// loom:` marker and appears in the amended hunk inventory; and a Phase 3 coder can wire a tool handler or a dispatcher rail to the arm, the store and the shell join without making a design decision this plan left open.

Three facts about V2 decide the design, and each is checked against code rather than docs:

1. **One closed command/event union, one decider, one receipt per command id.** `OrchestrationV2DomainEvent` is a `Schema.Union` decoded straight from `orchestration_events.payload_json` (`persistence/Layers/OrchestrationEventStore.ts`, `decodeV2EventJson`), so a Loom event can only live in V2's log if it is a member of that union. `dispatchWithReceiptEffect` (`Orchestrator.ts:9690`) rejects any command producing no events and receipts every rejection; a repeated command id then returns `OrchestratorCommandPreviouslyRejectedError` forever.
2. **Per-thread lock, one projection per command.** `dispatchWithReceipt` runs under `threadDispatch.withLock(commandThreadId(command))` (`Orchestrator.ts:9878`); the keyed executor is neither re-entrant nor deadlock-aware; upstream nests into another thread only when it has just created it (`dispatchDelegatedTaskRequest` writes child events under the parent lock) and otherwise takes locks *sequentially, never nested* (`handleTerminalRun`, `:9883`).
3. **Delivery modes are fixed and a notification is only legal on `queue_after_active`.** `message.dispatch` offers `defer_start | steer_active | restart_active | queue_after_active | start_immediately` (`orchestrationV2.ts:2735`); a `notification` on anything but a server/provider-created `queue_after_active` is a receipted rejection (`Orchestrator.ts:4517–4528`); queuing happens only when a blocking run exists (`shouldQueue`, `:4696`); the delegated-completion block converts a queued wake to a steer when the target is `running` with a running provider turn on a session that supports active steering without interrupting tools (`:4570–4605`).

## 2. The decider arm — `Orchestrator.loom.ts`

### The rule

The arm **writes only to the commanded thread and to threads it creates in the same command**. Every effect on another thread is recorded as a decision event on the commanded thread and turned into a separate, idempotent, episode-keyed per-thread command by the re-drive planner (§4), which the dispatcher runs on every pass. Nesting into upstream's own dispatchers is allowed when the nested command targets the *same* thread (`dispatchMessage`, `dispatchRunInterrupt`) or a thread the arm is creating (`thread.created`). The arm never takes a second lock.

`loomTurnStartRules`, in order, for a thread with a sidecar:

1. **Reject permanently** when `workstream.deletedAt !== null` or `archivedAt !== null` — a message to a dead target fails once (its sender gets the error; a re-drive planner never produces one, §4).
2. **First-turn dependency gate.** If `parentThreadId !== null && kickoffAt === null && !dependenciesSatisfied(node, siblings)` → `OrchestratorDispatchError` naming the unsatisfied dependency (`describeUnsatisfiedDependency`). Applies to every path including a human send from the composer; the dispatcher's kickoff passes by construction.
3. **Held release by a human.** If `held && kickoffAt === null && command.createdBy === "user"` → emit `thread.held-set false` (acting on a held node is the release). A control-plane message to a held node (`loom.origin` set) is refused — the dispatcher never sends one, and a stale one must not start a held node.
4. **Attention clear.** If `command.createdBy === "user" || command.loom?.origin !== undefined`, and the stored attention set is non-empty → emit `thread.attention-cleared` (all). Upstream's own notification-source dispatches (PR-watch wake, a schedule fire) have neither and leave attention alone — a shipper's `awaiting_acceptance` survives a failing-check wake. A steer runs this too, on the *target* only: a child's yield steered into its parent clears nothing on the child.
5. **Kickoff stamp.** If `kickoffAt === null` → emit `thread.kickoff-recorded { kickoffAt: now, messageId, origin: command.loom?.origin ?? (command.createdBy === "user" ? "user" : "other") }`. The first turn by anyone is the start; the promotion rule then never fires for this thread again.
6. **Supersede** (slot reserved; implemented in Phase 3a with `runtime-request.create`): a `createdBy: user` message while a Loom-marked `user_input` request is pending resolves it as the tool result and withholds the turn start.

`LoomDispatchDeferredError` is a `Schema.TaggedError` (`commandId`, `commandType`, `threadId`, `reason`) exported from `Orchestrator.loom.ts` and added to the `OrchestratorV2Error` union with one marked member. It is raised **only** when the same command can succeed later without anyone changing the target:

1. `start_if_idle` against a target with a blocking run (it goes idle).
2. A Loom gate leg (`thread.gate.rework` / `thread.gate.reverify`) whose nested `message.dispatch` would be queued behind a blocking run while the target has a pending merge-back transfer (`pendingMergeBackTransfersForThread(projection).length > 0`) — upstream rejects queued dispatch in that state ("queued merge-back consumption is not implemented yet"); the arm pre-checks and defers instead.

Everything permanently unsatisfiable is a receipted rejection that fails once: an archived or deleted target, a stale `routeEventId`, a cancelled thread, a dependency gate. ### The shell join

`joinLoomShellFields(loomStore)(snapshot)` attaches `workstream` to each shell for which a row exists; threads without one carry no key. Two marked hunks in `Orchestrator.ts`'s service record wrap `getShellSnapshot` and `getThreadShell` so every consumer — ws, MCP, settlement, PR services — reads the joined shape. ### Goals: tables, idempotency, broadcast

Goals and tasks are **plain tables written by the Phase 3a tool handlers** through `LoomStoreV2.goals` / `.tasks`. Idempotency needs no ledger: ids are derived from the command id the MCP layer already stabilises per `clientRequestId` (`goalId = GoalId.make("goal:" + hash(commandId))`, `taskId` likewise), and every write is an upsert, so a retried `goal_task_add` lands on the same `task_id` and `goal_tasks_rewrite` is idempotent by construction (the submitted list *is* the tree). The 300-character register cap, round-trip identity and anchor scoping stay in the ported `goalTaskTree.ts` / `goalTaskMarkdown.ts` / `goalTaskAnchor.loom.ts` (3a brings them out of quarantine; their logic is engine-free).

Broadcast: `LoomGoalBroadcast` is a `PubSub<LoomGoalShellStreamItem>`; a handler publishes `goal.updated` / `goal.removed` after its write, and a small reactor on `streamDomainEvents` publishes after a projector-folded cascade (`thread.archived | unarchived | metadata-updated` on a thread whose sidecar names a goal). Each item carries `sequence` = `applicationEvents.latestApplicationSequence` at publish, so the client's cursor logic keys it like any other shell item. Because these items sit outside V2's event sequence, a client resuming from a cursor cannot catch up on goals from the cursor alone: `loadSnapshot` in `ws.ts` includes `goals` (one marked hunk) and Loom's connect-gap-aware subscriptions (3d) refetch the snapshot on reconnect. Contract hunks: two members on `OrchestrationV2ShellStreamItem`, `goals: Schema.optional(Schema.Array(LoomGoalShell))` on `OrchestrationV2ShellSnapshot`.

### The re-drive planner

Multi-thread effects become per-thread commands. `apps/server/src/loom/orchestration/redrive.ts`:

```ts
/** One episode-keyed command per affected thread. Pure over a graph snapshot. */
export const planReDrive = (rows: ReadonlyArray<LoomThreadWorkstream>): ReadonlyArray<OrchestrationV2ServerCommand> => [
  // cancel cascade: root cancelled → every live descendant with outcome null
  ...rows.filter((r) => r.outcome === "cancelled").flatMap((root) =>
    descendants(rows, root.threadId).filter((d) => d.outcome === null && d.deletedAt === null)
      .map((d) => outcomeSet(d.threadId, "cancelled", `server:loom:cascade-cancel:${root.outcomeEventId}:${d.threadId}`))),
  // wedged dependents: a live, unstarted node blocked on a cancelled same-parent sibling
  ...rows.filter((r) => r.outcome === null && r.kickoffAt === null && !r.attention.includes("needs_guidance"))
    .filter((r) => r.blockedBy.some((id) => cancelledSibling(rows, r, id)))
    .map((r) => attentionRaise(r.threadId, "needs_guidance", `server:loom:wedged:${cancelledDepEventId}:${r.threadId}`)),
  // archive / delete cascades keyed on the root's stamp; unarchive keyed on its event id
  ...rows.filter((r) => r.archivedAt !== null).flatMap((root) => descendants(rows, root.threadId)
    .filter((d) => d.archivedAt === null).map((d) => upstreamArchive(d.threadId, `server:loom:cascade-archive:${root.threadId}:${root.archivedAt}:${d.threadId}`))),
  ...rows.filter((r) => r.unarchivedEventId !== null && r.archivedAt === null).flatMap((root) => descendants(rows, root.threadId)
    .filter((d) => d.archivedAt !== null).map((d) => upstreamUnarchive(d.threadId, `server:loom:cascade-unarchive:${root.unarchivedEventId}:${d.threadId}`))),
  ...rows.filter((r) => r.deletedAt !== null).flatMap((root) => descendants(rows, root.threadId)
    .filter((d) => d.deletedAt === null).map((d) => upstreamDelete(d.threadId, `server:loom:cascade-delete:${root.threadId}:${root.deletedAt}:${d.threadId}`))),
  // goal attach down: a child with no goal whose parent has one
  ...rows.filter((r) => r.goalId === null && parentOf(rows, r)?.goalId).map((r) => goalSet(r.threadId, parentOf(rows, r)!.goalId, `server:loom:goal-attach:${r.threadId}:${parentOf(rows, r)!.goalId}`)),
  // gate legs from the latest route on a source (loop → rework on the target; loop-back → reverify on the source; resolve → resolve on the counterpart)
  ...rows.filter((r) => r.lastRoute !== null).map((r) => gateLegFor(r, rows)),
];
```

`runReDrivePass(orchestrator, commandReceipts, loomStore)` reads `listActiveWorkstreams()` (plus archived rows for the cascades), plans, skips any command whose id already has a receipt (`commandReceipts.getByCommandId`), dispatches the rest **sequentially** (one lock at a time, never nested), and classifies results: accepted → done; `LoomDispatchDeferredError` → leave for the next pass; any other error → log at warning with the episode key (the episode is receipted dead; Phase 3b's advisory rail surfaces it). The gate-leg text and `controlPayload` come from a `composeGateLeg` the dispatcher owns in 3b; Phase 2 ships it with a minimal fixed template so the test can run, marked for 3b to replace.

`LoomReDriveReactor` subscribes to `streamDomainEvents`, debounces on `thread.outcome-set | thread.route-taken | thread.archived | thread.unarchived | thread.deleted | thread.goal-set`, runs the pass, and runs once at startup. Phase 3b folds it into the dispatcher's pass (first rails, before promotion) and owns the periodic tick; until then the reactor is what keeps cascades and gates moving in the Phase 2 smoke.

The window the strategy accepted is visible here: between a reviewer's `route-taken` and the coder's `gate-rework-accepted` the board reads the coder as done for one pass; dependents cannot start in that window because `isMemberOfUnresolvedGate` (the reviewer is non-terminal and carries the loop route) already holds them, and the promotion predicate excludes gate members.

## 6. Quiescence as completion — the substrate half

The semantic: a started child that goes quiet without `workstream_submit` is treated as having yielded, not as owing a human. Phase 2 provides the state and the predicate; Phase 3b's rail writes the report and dispatches the synthesised submit.

- **The event and the state.** The dispatcher dispatches `thread.work.submit { threadId, reportPath, outcome: "quiescent" }` with a `server:loom:quiescent:<threadId>:<lastRunId>` id. The arm accepts `quiescent` only on `server:` ids, records `thread.outcome-recorded { outcome: "quiescent", decision: "yield", synthesised: true }` and raises `awaiting_orchestrator`. `routeWorkSubmit` returns `yield` for it before the rework interception (§2), so a gate member that goes quiet also yields and never resolves or loops its gate. Spawn and scaffold refuse `quiescent` in any route's `on` list.
- **The hook.** V2 run completion as projected: Phase 3b subscribes to `run.updated` with a terminal status on `streamDomainEvents` and re-evaluates on the periodic tick; it never listens to the adapter's `agent_settled`.
- **The predicate** (`apps/server/src/loom/orchestration/quiescence.ts`):

```ts
export const quiescenceCandidate = (input: {
  readonly shell: OrchestrationV2ThreadShell;        // joined: shell.workstream present
  readonly runs: ReadonlyArray<OrchestrationV2Run>;   // getThreadRecords(threadId, ["runs"]) for the few pre-filtered candidates
  readonly latestUserMessage: Pick<OrchestrationV2ConversationMessage, "createdBy" | "loom" | "createdAt"> | null;
  readonly children: ReadonlyArray<LoomThreadWorkstream>;
  readonly now: DateTime.Utc;
  readonly grace: { readonly controlStartedMs: number; readonly humanStartedMs: number | null }; // null = never for human-started turns
}): boolean => {
  const ws = input.shell.workstream;
  if (ws === undefined || ws.parentThreadId === null || ws.kickoffAt === null || ws.outcome !== null) return false;
  if (ws.attention.length > 0 || input.shell.pendingRuntimeRequest !== null) return false;
  if (input.shell.activityRunStatus !== null || input.runs.some((run) => run.status === "queued")) return false; // includes a held queue
  if (input.children.some((child) => child.outcome === null && child.deletedAt === null && child.archivedAt === null)) return false;
  const lastRun = latestUnheldRun(input.runs);
  if (lastRun?.completedAt == null) return false;
  const humanStarted = input.latestUserMessage?.createdBy === "user";
  const graceMs = humanStarted ? input.grace.humanStartedMs : input.grace.controlStartedMs;
  return graceMs !== null && DateTime.toEpochMillis(input.now) - DateTime.toEpochMillis(lastRun.completedAt) >= graceMs;
};
```

"Who started the last turn" is the latest user-role message's `createdBy` (a Loom control message is `agent`; the composer is `user`), cross-checked against the shell's `latestUserAuthoredMessageAt`. The grace values are settings owned by 3b; the defaults travel from the V1 idle backstop.
