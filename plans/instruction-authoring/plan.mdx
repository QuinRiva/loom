# The rules we have are as strong as anyone's; what we lack is a separate judge and a number

**Recommendation: rebuild `skill-authoring` as the one skill that fires before creating or editing a skill or an AGENTS.md, and make every such edit pass an independent reviewer with a veto and a before/after word count.** The survey of 17 sources (Anthropic's `skill-creator`, the agentskills.io guide, Lauren Tan's `pstack` at Cursor, Matt Pocock, Vercel, HumanLayer, Codex, Grok Build, and the 2026 research that still applies) found no wording rule we lack. Our line-earning test, drop-if-derivable rule and whole-file review are at least as strict as theirs. What they have and we do not is structural: the drafter never judges its own addition, the size change is visible at edit time, the skill that carries the rules fires on the edit, and skill firing is measured rather than assumed.

Today's failure fits exactly. The Vertex thread had the skill available and the rule in front of it; it drafted and judged in one act, nothing counted the words, and no skill fired on "edit AGENTS.md" because ours triggers on writing a skill.

**What you get:** an agent asked to add a fact to AGENTS.md produces a PR whose description shows `+N/−M words`, whose addition a separate reviewer has tested against the whole file's purpose with the power to reject it, and whose drafting followed a skill that loaded because the file was being edited. Skills that never fire become visible from session logs instead of from your frustration.

**The bets:** that a reviewer briefed to veto will actually reject (pstack's data says it does when the rejection reasons are fixed and named), and that one pointer line in AGENTS.md is enough to make the skill load (Vercel: 44% to 95%+).

**Cost:** one pi-craft goal (planner-preset author plus reviewer, about half a day of agent time), one loom commit, one researcher query. The trigger-eval runner is deferred until the telemetry says which skills need it.

Scope: pi-craft's `skill-authoring` and `lesson-triage` skills, two lines in the global AGENTS.md, one loom overlay bullet. Not in scope: a trigger-eval harness for pi (deferred, see §5), any change to loom's tool descriptions. Done means the rebuilt skill ships in a pi-craft PR you merge, the loom bullet ships on `t3/prompt-review-restores`, and the Vertex-thread scenario re-run cold produces a reviewed, counted addition. The open decisions are in the form at the end; the one that is genuinely yours is whether our "negative constraints only" rule still holds (§4).

## 1. Why the existing rules did not bind

Three things were true at once in the Vertex thread, and each is a gap the survey names:

- **Drafting and judging were one act.** The thread wrote the section, then assessed it against the file only when you challenged it. Every rigorous source separates the two: pstack's `/reflect` has a synthesiser that rejects proposals with fixed reasons ("already covered", "changes no decision"); Anthropic's `/revise-claude-md` and HumanLayer's `improve-claude-md` run as a distinct pass; and our own loom review gate exists for code but was not applied to instruction text.
- **Nothing was counted.** pstack ships PRs that only delete text and report token counts; Claude Code warns past about 200 lines; Codex truncates at 32 KiB. We have a whole-file review rule but no number the drafter sees.
- **The skill did not fire.** `skill-authoring` triggers on creating a skill; the task was editing AGENTS.md. Vercel measured this failure directly in January: a skill never invoked in 56% of cases scored the same as no docs; one line in AGENTS.md saying to use it raised invocation to 95% or more. Pocock's `writing-for-agents` is the only surveyed skill whose trigger is simply "modifying AGENTS.md".

<Callout tone="info" title="What the survey did not find">
  No source has a wording rule ours lacks. The line-earning test ("a line stays only if the model would get something wrong without it"), the guard-first routing in `lesson-triage`, the drop-if-derivable rule and the complete-review-per-PR rule are as strict as anything at Anthropic, Cursor or Vercel. The survey file with every quote, date and model generation is at `.artifacts/skill-authoring-survey.md`.
</Callout>

## 2. The rebuilt skill

One skill, still named `skill-authoring` so nothing that points at it breaks, with its trigger widened and its body reorganised around the edit rather than the blank page.

**Trigger (the whole header):** before creating or editing any skill, or editing any AGENTS.md or CLAUDE.md, including a one-line addition; and when a skill exists but is not being loaded.

**Body, what it keeps:** where a skill lives per repo and how it deploys; the frontmatter pi drops; what a description must say (the complete trigger, nothing else); what a body line must earn.

## 3. The loom side

One bullet in `roles/orchestrator.md` already says text models read is authored by the orchestrator or on the planner preset. It gains the other half: "and reviewed by a gate briefed to veto: the four rejection reasons, the file's purpose, the word count." This is a sentence, on the restores branch, and it is what would have put a reviewer between the Vertex thread's draft and its PR. The `workstream-review-gate` skill in loom's `skills/` gets a short section for instruction-text reviews with that brief as a template, so an orchestrator does not write it from memory.

## 4. The decision that is yours: does "negative constraints only" still hold?

Our rule rests on the pi-craft option-b ablation (Opus 4.7 and GPT-5.5, May 2026, one run per cell on one task) and *Guardrails Beat Guidance* (Opus 4.6, April 2026). Three newer sources disagree with it as a general rule: Anthropic's Claude 5 guidance (July 2026) replaced "give Claude rules" with "let Claude use judgement"; pstack PR #633 (October 2026, 180 blinded runs on Opus 5.5, GPT-5.6 and Gemini 4) found an old ban made models delete a contract test in six of six runs; Pocock argues a prohibition makes the banned behaviour more salient.

They reconcile: a narrow tripwire on an action agents were actually observed taking, with its reason, still earns its tokens; a general prohibition misfires. That is also what the option-b trial actually tested, since its negative rules were specific. The proposal is to rewrite the rule as the reconciliation rather than re-run the ablation now; the ablation can be re-run on the current tier if you want the number first.

## 5. Measurement, in two steps

**Now, cheap:** a researcher queries loom's session logs for which skill files were ever read (a `read` call on a `SKILL.md` path), per skill, over the last 30 days, against the list of skills declared in those sessions' prompts. This is Claude Code's `/skill-doctor` done by hand once. It tells us which skills never fire before we build anything to fix firing.

**Deferred:** the trigger-eval loop everyone serious runs (about 20 realistic queries, half near-misses that should not fire, three runs each, a 60/40 train/held-out split, up to five rewrites, winner on the held-out score) needs a pi runner that detects the SKILL.md read. `llm-instruction-change` already has the statistics. Build it only for the skills the telemetry shows are not firing; a skill that fires has no use for it.

## 6. Verification

The smoke is the failure itself, re-run cold: a fresh thread is given the Vertex brief again (add "Gemini is callable through Vertex" and "ask before working around a missing tool" to the global AGENTS.md) with the rebuilt skill in place. Pass means: the skill loaded (visible in the session log as a read of its SKILL.md), the PR description carries +N/−M words, a separate reviewer thread recorded a verdict with at least one line tested against the four reasons, and the resulting addition is no longer than the version you accepted today after challenging it. The pi-craft PR also carries the skill's own before/after word count, and the frontmatter loads in pi's banner.
