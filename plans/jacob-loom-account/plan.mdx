### 3.1 Layering: how pi composes several packages, and the sync timer

pi loads the `packages` list in `~/.pi/agent/settings.json` in the order written, global packages before project ones, de-duplicating by canonical path (`dist/core/resource-loader.js`, `mergePaths`, in the pinned pi 1.3.0 under the release's `node_modules`). Two rules decide what happens when two packages carry the same name:

- **Skills: the first one loaded wins by name.** `loadSkills` (`dist/core/skills.js:316-410`) fills a map by skill name; a later skill with the same name is dropped and a `collision` diagnostic names winner and loser. Load order is `~/.pi/agent/skills/` first, then the project's `.pi/skills/`, then each package's skills in list order.
- **Extensions all load, and a tool or command name goes to its first registrant.** `getAllRegisteredTools` (`dist/core/extensions/runner.js:411`) keeps the first extension that registered a name and the loader reports the conflict as an error diagnostic; both extensions stay loaded for everything else they do.

So "later adds, earlier overrides". Jacob chose add-only: his list is your list verbatim (`../../pi-craft`, the npm and git packages, the two forks) with `../../jacob-pi-loom` **last**, and his skills, tools and prompts carry a `jacob-` prefix ("i'd probably rename my skill to be 'jacob' specific to ensure no collisions"). A pi-craft change he wants to try is a branch in `~/pi-craft`, not a shadowing copy. If he ever needs to override a pi-craft name on his side, moving his package first does it, and the collision diagnostic in `/skills` names the loser.

Read it left to right. The export never opens your database read-write (`file:…?mode=ro`, as the dev slicer does) and never changes a row. ### 5.2 `export` (as Carl)

`node ~/loom-releases/current/apps/server/dist/bin.mjs loom-migrate export --root <id> [--root …] --out /srv/loom-handoff/<batch>` (`t3` is on neither user's PATH; `t3 loom-migrate` below is shorthand for that invocation from the user's own release path):

1. **Select** the family of each root (every thread whose `lineage.rootThreadId` is the root), plus the `continues_thread_id` and `fork_from_thread_id` chain so a goal-continue chain moves as a unit (the three Mirvac threads in §6 are one chain), plus the goals those threads reference and their tasks. Print the set and stop unless `--yes`.
2. **Refuse a tree that is not quiesced**: any run in `queued|preparing|starting|running|waiting`, any node not terminal, a pending `runtime_requests` row, a nonterminal background turn item, an outbox row `pending|running`, a `pending-steering/<id>.json`. The operator stops the turn in the UI first. `--root` in the dev slicer bypasses this check on purpose; here it is mandatory.
3. **Carry uncommitted work.** For each thread whose `worktreePath` is dirty (`GIT_OPTIONAL_LOCKS=0 git status --porcelain`, so the check itself never rewrites an index), and only after the quiescence check has passed, the tool runs `git -C <worktree> add -A && git -C <worktree> commit --no-verify -m "loom-migrate WIP: <thread id> <timestamp>"` on the thread's own branch: untracked files included, `.gitignore` respected, hooks skipped. The manifest records the pre-commit `status --porcelain` output and the WIP commit SHA per thread. This is the one write the export makes inside your repos, on the thread's branch only, and it is exactly what the thread's next turn would have done; a worktree whose branch is checked out elsewhere, or that is mid-rebase or mid-merge, makes the export stop and name it.
4. **Slice**, inside the same read transaction as the quiescence check (`BEGIN` on the read-only attach, check, then copy, then `COMMIT`), so a turn that starts between the two is never half captured: every table with a `thread_id` column filtered to the set, `orchestration_events` by aggregate, goals and tasks by id, consults, peer messages and context transfers where either end is in the set, into a fresh `slice.sqlite` created with the source schema. Ids and paths untouched.
5. **Files**: reports, briefs, round and quiescent reports by stem glob; `pending-steering`; attachments by every id referenced from messages, turn items and tool-output images (not by prefix); each thread's pi session jsonl from `provider_threads.payload.nativeThreadRef.nativeId`. Copied under `files/` with their relative paths.
6. **Git**: for each project in the set, `git bundle create <project>.bundle` with every `refs/t3/orchestration-v2/checkpoints/<scope>/*`, `refs/t3/loom-baseline/<scope>/*` (computed with `loomBaselineRef`) and `refs/t3/loom-review/*` ref named in the slice, plus each thread's work branch at its post-WIP tip. The bundle is how the branch reaches his clone: `import` fetches it in step 7, no GitHub round trip, no push of a WIP commit to `origin`, and the checkpoint refs travel in the same file (pushing the branch to origin and fetching was the alternative; it leaves WIP commits on the shared remote and still needs a bundle for the refs). Your project repos are `/home/Carl/loom/.git` and `/home/Carl/fathom-platform/.git` (the lease-extraction root is itself a worktree of the latter).
7. **Manifest**: per thread, row counts per table, max event `sequence`, file paths with SHA-256, ref names with their SHA, project id with its workspace root, worktree path and branch. Then `sudo chown -R jacob:jacob` the batch. The export's only writes are the WIP commits of step 3 (on thread branches, in your repos) and the batch directory; your database is opened read-only throughout.

### 5.3 `import` (as jacob, server and refresh timer stopped)

`systemctl --user stop loom-refresh.timer loom-cockpit.service`, then `T3CODE_HOME=/home/jacob/.t3/cockpit node ~/loom/release-current/apps/server/dist/bin.mjs loom-migrate import --batch /srv/loom-handoff/<batch> --project <carlRoot>=<jacobRoot> …`, then `systemctl --user start loom-cockpit.service loom-refresh.timer`. The timer is stopped because `loom-refresh.sh` runs every 60 seconds and restarts his server whenever a release becomes current, whether or not it was running; you promote about daily, so an import that overlaps a promote would otherwise boot his server onto a half-written database. The tool runs from his pinned `~/loom/release-current`, not `/srv/loom/releases/current`, which can flip mid-batch; the pinned release is the one his database's migration ledger matches. The destination home is `T3CODE_HOME`; the session directory and the project clones come from `--sessions-dir` (default `~/.pi/agent/sessions`) and the `--project` map, so the dry run in §5.5 can point all three at scratch locations.

1. **Guards**: `ensureNotInUse` on his database (the dev slicer's pid and `BEGIN IMMEDIATE` check); the two migration ledgers (`effect_sql_migrations`, `loom_sql_migrations`) must be identical, which the shared release makes true; every project in the manifest must map to a live row in his `projection_projects`; every thread, goal, task and attachment id must be absent on his side (or, with `--replace`, present and unchanged since its last import: see below); every goal slug must be free in its target project. Any failure aborts before a write.
2. **Snapshot before any write**: `VACUUM INTO <batch>/pre-import-<timestamp>.sqlite` of his database, `quick_check`ed, the same way his nightly backup is taken. It stays in the batch directory beside the export bundle, so an import that goes wrong is undone by stopping the server and copying the snapshot back; the procedure for that is one line in the runbook. Files written under `userdata/` and the sessions directory by a failed import are only ever additions, listed in `import-manifest.json`, and are removed by `import --rollback <batch>`.
3. **All database writes in one transaction** (`BEGIN IMMEDIATE` … `COMMIT`): a bad `json_set`, a full disk or a killed shell leaves his database exactly as the snapshot has it. Files and git refs are written after the commit, and `verify` (§5.4) is what proves they all landed.
4. **Rewrite** while inserting, with the map below, in both the column and the JSON payload (`json_set` on the known keys, never a blind `replace` across text).
5. **Append** events in source `sequence` order with new sequence numbers; renumber `peer_messages.seq` likewise; set `projection_metadata.last_sequence`.
6. **Files** copied into his `userdata/` and `<sessions-dir>/--<new cwd encoded>--/` (he runs the command, so ownership is his; mode 600 on sessions, which the resume sanitiser rewrites in place). Launch identity files are **not** copied: the next launch composes one under his paths.
7. **Git**: `git fetch <bundle> 'refs/t3/*:refs/t3/*'` and the work branches into the clone named by the `--project` map. The worktree directory itself is not created; the server recreates it from the branch at the next turn under `<T3CODE_HOME>/worktrees/`, so the remapped path must sit there.
8. **Search**: `rebuildThreadSearchIndex`. Embeddings re-sweep on boot.
9. Write `import-manifest.json` with the same counts and hashes measured on his side.

**Re-importing a tree** (`import --replace`), for when `export --check` finds that a thread kept moving on your instance after export and it was exported again: allowed only when every row count of his existing copy still matches the previous `import-manifest.json`, that is, nobody has touched the tree on his side. The tool then deletes his copy of that tree's rows and files inside the same transaction as the fresh insert, after the snapshot in step 2. If his copy has changed, the tool stops and names the thread; the two copies have diverged and merging them is a human decision, not a tool's.

### 5.4 `verify`, then archive, then a confirmed delete after 30 days

`t3 loom-migrate verify --batch …` runs on his side after `import` and compares `manifest.json` with `import-manifest.json`: every per-thread, per-table count equal; every file present with the same hash and readable by jacob; every ref present in his clone with the same SHA; every session path in `provider_threads` pointing at an existing file. It prints one line per thread and a non-zero exit on any difference. Then the operator smoke test, which is the only proof that the agent's memory survived, because a missing session file resumes silently as an empty one: start his server, open one migrated thread per project, send "where were we?", and the answer refers to the thread's actual work.

Only then does archive happen, and only by you, in the UI, so it goes through `thread.archived` events like any archive and can be undone the same way (Loom cascades archive to the tree's descendants, `apps/server/src/loom/orchestration/redrive.ts:181-194`). Before you do, `export --check` re-reads each thread's max event `sequence` on your instance and warns if it moved since export (someone kept working on the source copy); a moved thread is exported again and brought over with `import --replace` (§5.3), not archived stale.

**Delete after 30 days, confirmed by a human every time.** Your answer: "archive now, delete from your instance after 30 days if he has not come back for it". The mechanism, per batch:

1. When you archive the batch's roots, you create one **scheduled task** (Settings → Scheduled tasks; one-shot, 30 days out, posting into the thread that ran the migration, so it dies with that thread) whose prompt names the batch directory. Loom has no agent-reachable delete, so the task's agent prepares the decision and you make it.
2. When it fires, the agent reads `<batch>/manifest.json` for the root ids, checks **his** copies read-only (`sudo $(which sqlite3) "file:/home/jacob/.t3/cockpit/userdata/statev2.sqlite?mode=ro"`: each root present, `deleted_at` null, its max event `sequence` at or past the import's), checks the roots are still archived and untouched on yours (`export --check`), and asks you with one question listing the roots and both findings. If a root is missing or unhealthy on his side, it asks you to hold and notifies Jacob through the Slack bridge; nothing is deleted.
3. On your "yes", **you delete each root in the sidebar**. `thread.delete` is a soft delete (`thread.deleted` event, `deleted_at` on the row; `packages/contracts/src/orchestrationV2.ts:2807`): Loom cascades it to every descendant (`redrive.ts:209-220`), the tree leaves every view and the search index, its worktrees are removed only if "Delete worktrees with deleted threads" is on in project settings, and scheduled tasks posting into it are deleted with it. Rows, report and brief files, session files and checkpoint refs are **not** purged by a delete (checkpoint refs have their own retention sweep); they are invisible, not gone.
4. The agent then records the deletion in `<batch>/manifest.json` (`deletion: { confirmedBy, at, roots }`) and the task is done. Never automatic: a task that fires with nobody answering does nothing.

After the delete, the last copies on your side are the **batch directory** `/srv/loom-handoff/<batch>/` (the export bundle: `slice.sqlite`, files, git bundles, manifest; and his `pre-import-<ts>.sqlite` snapshot), owned by jacob after the export's `chown`, on this host's disk and in nobody's backup. Its retention is yours; the recommendation is to keep it until the delete has happened and his nightly backup has run at least once since the import, then remove it by hand.
