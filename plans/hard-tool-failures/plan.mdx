## 2. `edit` escapes: decode in a pi-craft extension

**What happens.** Claude models sometimes emit the six characters `\u2014` in a tool argument where they mean `—`. pi parses the JSON correctly (a model-emitted `\\u2014` decodes to the literal text), cliproxy passes `partial_json` through untouched, and pi's `edit` does exactly what it is asked. In the root thread that edited `docs/operations/shipping.md` on 3 Oct, turn 143's argument bytes were `disappears \u2014 it`, the file's were `disappears — it`; the edit succeeded and wrote the escape into the doc. The next turn the same model emitted a raw `—` in a `bash` call to `sed` it back.

**Why it is worse than counted.** The audit counted the failed edits (oldText escaped, file has the character — ~42% of edit failures). It excluded code files from the silent half. Including them, **~200 successful edits a month** wrote a literal escape into a file, nearly all in comments and prose strings. And it compounds: after a session's first escaped call, the rate jumps from ~15% to 41–57%, because the model's own history primes it. In 29 of 34 "successful" escaped-oldText edits, the only reason the oldText matched was that the same session had already corrupted the file.

**Where it lives.** A global pi extension in `pi-craft` (`plugins/pi-craft/extensions/edit-unicode-escapes.ts` plus one `package.json` line). pi-craft is loaded by every pi process on this machine — terminal pi and every loom thread — and survives pi upgrades because it uses only the documented `tool_call`/`tool_result` hooks. Rejected: a loom pi patch (re-derived at every pi bump, far too heavy for 50 lines) and loom's own extension (misses terminal pi). The right end state is an upstream PR to pi's `edit-diff.js`, which already absorbs model quirks in this tool; delete the extension when that lands.

<Callout tone="decision" title="The decode rule">
  Per edit item, decode only escapes for code points ≥ U+0080 not preceded by a backslash. Decode **both** `oldText` and `newText` when either: **(a)** the raw `oldText` is not in the file but the decoded one is — Claude Code's rule, which catches the failures; or **(b)** the file contains no literal escapes of its own — which catches the silent newText corruption that (a) misses because its oldText matched fine. Then append one line to the result: *"Note: decoded literal \uXXXX escapes in N edit(s) into the characters they name (e.g. —). Write such characters directly."* `write` stays verbatim — it is the escape hatch for deliberately writing a literal escape — and only gains a warning on `.md`/`.mdx`/`.txt`.
</Callout>

## 4. `workstream_prompt`: amend a waiting child's brief

**What happens.** `workstream_prompt` to a child that has a brief but is still waiting on a dependency composes the brief plus the message and tries to *start the child now*. The orchestrator's first-turn dependency gate refuses: `Thread … cannot start: dependency '…' is not done yet.` The tool description says the message is "appended to that brief"; neither the V1 nor the V2 code ever did that. The V2 port kept V1's behaviour and the existing test asserts the refusal on purpose. Every refused message since 10 Oct was an addendum or correction ("Correction to the brief above: 18 trials, not 27"), never an attempt to start early.

**Why it matters more than $23 of recovery turns.** Since 13 Oct, 13 of 15 refusals were followed by the orchestrator doing `cat >> …/userdata/workstream-briefs/<id>.md` or a python rewrite — writing into the live cockpit's state directory, outside the control plane, with no event and no "has it started yet" check. It works only because the dispatcher reads the brief file at launch. The other two re-sent whole 10–20k-character briefs.

<Callout tone="decision" title="The fix">
  In `apps/server/src/mcp/toolkits/workstream/handlers/prompt.ts`, inside the unstarted-child branch: if the child has an unsatisfied dependency (`describeUnsatisfiedDependency`, the same check as the gate), append the message to the brief file under a separator, re-record the path with `thread.kickoff-brief.set` — which the orchestrator already refuses if the child has meanwhile started — and return *"Added your message to the brief of … It has not started (dependency … is not done yet); it reads the brief with your addition as its first turn once it launches."* The unblocked-unstarted path (compose and start) stays as is. No contract, schema, orchestrator or store change.
</Callout>

Edge cases: several amendments append in order; a later `workstream_brief` overwrites the whole file, amendments included (correct, and the description will say so). The amendment can race the launch only when the orchestrator marks the dependency done in the same tool batch; the window is the same one `workstream_brief` already has, and the worst outcome is the child seeing the addendum twice. The focused test flips the existing "a blocked one is refused" case to "a blocked one is amended" and asserts the file contents, `kickoffAt` still null, no message sent.

I author the tool text (`prose.ts:85`, `defs.ts:229-230`, the separator heading and the success string) — text models read is not a coder's to write.

Rejected: only improving the error ("call `workstream_brief` with the full revised brief") — pushes orchestrators to re-send 20k characters, and they would keep hand-editing because it is cheaper. Making *every* unstarted prompt an append and deleting the compose-and-start path is the cleanest end state but turns the race's worst case into a silent loss; worth doing only with a brief revision checked at kickoff, which is more machinery than this earns.

## 5. `pkill`: take the pattern out of argv

**What happens.** pi runs every bash call as `/bin/bash -c "<the whole command>"` (`bash.js:63-65`), and Carl's `shellCommandPrefix` makes every script compound, so bash never execs away. `pgrep -f X` / `pkill -f X` match on `/proc/<pid>/cmdline`, which now always contains `X` — procps 3.3.17 excludes only its own PID. So:

<Steps>
  <Step at="kill forms" tone="risk" title="`pkill -f X; echo done` kills the tool shell." badge="29 in 30 d" aside="`echo done` never runs; exit 143. The target usually dies too.">
    Lease-extraction researcher, turn 82: `pkill -f "node srv.js" ; echo done` → `(no output) Command exited with code 143`. One session took three turns to discover the `[c]onsist_t0` bracket trick.
  </Step>
  <Step at="wait loops" tone="risk" title="`while pgrep -f X; do sleep 30; done` never ends." badge="4 timeouts, ~1.7 h" aside="The jobs had finished in ~6 min. One agent wrote the diagnosis into its own RUNBOOK.">
    The audit filed these under slow calls, not here. Same cause.
  </Step>
  <Step at="liveness" tone="warning" title="`pgrep -f X && echo running` is always true." aside="Unmeasured; a finished pipeline looks alive.">
    `pgrep -af X` listings always include the shell.
  </Step>
</Steps>

The audit's "kills the agent" is wrong in detail: pi's own argv is just `pi`; what dies is the tool shell. Loom's `AGENTS.md` rule gives the wrong reason ("your own agent process has this worktree's path in its argv") — and loom agents trip too.

<Callout tone="decision" title="The fix">
  A ~15-line loom extension part (`loomExtensionParts/pgrepSelfMatch.ts`, registered after the search guard) hooks `tool_call`: when a bash command mentions `pgrep` or `pkill` (~7 a day across all threads), rewrite it to `eval "$(printf %s <base64> | base64 -d)"`. The pattern is then in no process's argv, so all three forms behave as the agent meant. Nothing is blocked, the agent is taught nothing, and because the hook mutates a `structuredClone` after `tool_execution_start`, the transcript and UI still show the original command. Covered: every loom thread in every repo (fathom, pi-fathom, slack-bridge, loom), since the generated extension is loaded by every loom-launched pi. Not covered: terminal pi, which does not appear in the audit.
</Callout>

Verified locally with `pgrep` only (no kill): the plain form self-matches and a wait loop spins; the encoded form returns rc=1 and the loop exits. `eval` of the whole script behaves like `-c` — same exit status, `set -e`, traps, heredocs, incremental parsing; the one visible difference is `bash: eval: line 2:` in syntax errors. Commands over 64 KiB are left alone to stay under `MAX_ARG_STRLEN`. The try/catch means an analyser bug degrades to "no fix", never to blocked tools. A focused test loads the part and runs the rewritten command through a real `bash -c`.

Rejected: blocking `pkill -f` with a teaching message (the audit's idea) — treats the kill form only, costs a turn per block, and agents already know the bracket trick (37 uses) and still slip; PATH shims for `pgrep`/`pkill` (must re-implement `-n`/`-o`/`-c` after filtering); moving the rule to global `AGENTS.md` (loom's rule exists and loom agents still trip). The principled long-term fix is upstream: pi's bash tool should not put the command in argv. Worth an issue, not needed now. Also fix the wrong sentence in loom `AGENTS.md:162` and `docs/dev-site-testing.md:171` while there; keep the rule, since killing *another thread's* server by a loose pattern is still a hazard.
