# Ask the coder that wrote a line, from the diff you are reviewing

**Goal.** "I may want to ask questions about why a line or a function was
written in a certain way. But the most meaningful way to ask that is to ask
that of the coder subthread that wrote that line." While reviewing a branch's
changes, see which thread wrote each part and go to that thread to ask,
without losing your place in the diff.

**You'll know it works when.**

- You open the Diff panel on a branch several threads worked on. Each block
  of changed lines carries the name of the thread that wrote it and its
  commit. A row at the top lists those threads, and clicking one narrows the
  diff to that thread's changes.
- You select lines and a card names the thread, the commit and its message.
  Where a later thread rewrote the lines (a reviewer's fix, say), the card
  offers the earlier author too.
- You press Open thread and land in the coder's own conversation at the
  turn that made the commit. The same diff is reopened beside it: the same
  file, the same comparison and the same selected lines. You ask the coder
  there.
- One click returns you to the thread you were reviewing in, with the diff
  as you left it.

Those four pass in the Diff panel. After trying it you said: "it seems it
was only built for *just* the diff view - which is the view that I rarely
use for reviewing diffs". So the same holds in the view you do review in, a
changed file opened whole from the Files list:

- Its changed lines carry their author thread's colour, and the file's
  header names the threads that wrote them.
- Selecting lines opens the same card.
- Open thread lands in the coder's conversation at the turn that made the
  commit, with the same file open beside it at the same lines. One click
  returns you to the file as you left it.

Those pass too. Having used Open thread you said: "I'd like to build the
rest of the phases that we paused (with the query fork)". So, in both views:

- You press Query author on the card and type a question. A read-only copy
  of that coder answers from its own transcript in the main window. The
  file or diff beside it is as you left it: the same file, the same
  comparison and the same selected lines.
- The lines you asked about keep a marker saying a question was asked
  there, in the whole-file view and in the Diff panel.
- You press Promote on an answer, and a comment about those lines is
  waiting in the real coder's composer for you to send.
- One click returns you from the copy to the thread you were reviewing in.

After using it you selected a line the branch had not changed and asked:
"Did you fail to add the new ask stuff to the view I actually use?" The
card had only said the line did not change. So, in both views:

- Query author is offered on any line a thread wrote on this branch,
  whichever comparison the view is on, and the "?" mark shows in both.
- On a line no thread on this branch wrote, Query author is offered to the
  threads that changed this file on the branch. Its copy says the lines are
  not its own, and answers from what it knows of them and what their
  history shows, without passing a guess off as the original author's
  reason.

**It must not.**

- Name a thread that did not write the lines. No author shown beats a guess.
- Spend a turn of the coder's thread, or change anything in it, when you
  Query.
- Make the diff slower to open or scroll, on this machine or over the relay.

**Approaches in play.**

- Finding the author with git blame on the changed lines, then the
  `Loom-Thread` line agents add to every commit. Wins if the lines you review
  are committed, which they are by the time you compare against
  `origin/main`. Every agent commit that is not a merge carries it (583 of
  583 since it began on 13 Oct), and every thread they name still exists. Blame takes
  17 ms on the largest file of the latest merged branch and runs after the
  diff is drawn. _Chosen._
- Finding the author of uncommitted lines from the snapshot Loom takes at the
  end of each turn. Wins if you often review before coders commit. Not in
  the first cut.
- Dropped: recording every edit an agent makes with its line range. It is a
  second record of authorship that drifts as lines move.
- Asking through Open thread: you go to the live coder, and the diff
  follows the main window there. _Chosen._ Your question and its answer
  become part of that coder's conversation.
- Asking through Query author: a read-only copy of the coder answers, so
  its thread is untouched. _Chosen, alongside Open thread._ It costs more
  than everything above put together (a database migration, new event
  types, model-read text to evaluate). A coder that finished a while ago is
  read in full, at the uncached price, for your first question to its copy;
  later questions to that copy are cheap. `plans/code-query/plan.mdx` holds
  its plan; `plans/diff-author-query/plan.mdx` built everything above it.

**Decided.** "Yep looks good" to the mockup, which fixed three things.

- Authorship is shown per block of changed lines, not per line.
- On the cost of Query author: "I didn't anticipate the huge increase in
  cost for querying the author", and "I'm less convinced about the value of
  querying the author, unlike plans", because with code "I often anticipate
  changes much more directly". So: "let's just try slices 1 and 2 and see if
  that works. Then we can always come back and build the remaining ones
  after we deploy slices 1 and 2 if I see value in that." After deploying
  them: "I'd like to build the rest of the phases that we paused (with the
  query fork)". The card offers Query author beside Open thread.
- Lines not yet committed show as uncommitted, with no author.
- Asked whether his second view, "the last hunk of work that was done",
  needs anything new: "No, those two cover it; build nothing more for it".
  The two are the Diff panel's existing "Since your message" view and this
  brief's filter that narrows the diff to one thread's changes.
- Asked whether authors should also show in "Since your message", the view
  the panel opens on: "Show authors in both views". That is the live "Since
  your message" view and the whole-branch view ("Changes", which already
  compares against `origin/main` without you picking a base). Earlier "Since
  your message" intervals show no authors.
- _Assumed:_ authorship is on by default, with a toggle that is remembered.
  Redirect if you would rather switch it on yourself.
- _Assumed:_ a commit made outside a Loom thread (yours, or upstream's)
  shows its git author and offers no thread to open. So does a commit one
  thread amended after another made it (4 of 583): the card names both and
  opens neither.
- _Assumed:_ a block that only removes lines shows as removed, with no
  author, because blame names who wrote a line, not who deleted one. That is
  24 of 564 blocks (4%) across the last ten merged branches, about two a
  branch. Redirect if you want the thread that deleted them named.
- _Assumed:_ clicking a thread in the top row narrows the list to the files
  it changed and dims the other threads' lines in them; it does not cut
  those lines out. Redirect if you want them hidden.
- _Assumed:_ the earlier author appears on the card, not on the hunk's own
  row as the mockup's "after Deploy server" note drew it. Redirect if you
  want it on the row.
- Asked what should happen on a line the branch did not change, from four
  options: "Let me ask this branch's coders about any line". The option
  read: on an unchanged line, offer Query author to the threads that
  changed this file, for questions like why they left it alone; the copy
  would be answering about code it did not write.
- On naming the author of lines from before the branch, and reaching the
  threads behind them: "whilst "nice" to be able to see who wrote any line,
  it's be way to cluttered in the current display, and link out to old
  closed threads to directly ask them questions when they don't have the
  context of the current goal, wouldn't be very useful." So on such a line
  the card offers this branch's coders and says nothing of who first wrote
  it.
- _Assumed:_ the marker on asked-about lines is a mark in the line-number
  gutter. Selecting marked lines lists the questions on the card, each with
  a way to its answer. Redirect if you want the question shown beside the
  lines, as the mockup's "1 question" pill drew it.
- _Assumed:_ a copy answers on the model its coder ran on, since no other
  model can reuse what the coder already read. Redirect if a cheaper model's
  answer would do.
- _Assumed:_ once you send a promoted comment and the coder acts on it, your
  next question to that coder starts a fresh copy. The earlier copy is
  archived and every marker from it goes, in every file. Redirect if markers
  should outlast the copy.
- _Assumed:_ in the whole-file view, authors show when it is comparing
  against the whole branch or the live "Since your message", as in the Diff
  panel, and not for an earlier interval. The Files list itself is
  unchanged. Redirect if you want the thread filter there too.
- _Assumed:_ web and desktop first. Redirect if you review diffs on your
  phone.

**Not doing.** Authorship on GitHub's pull request page. Authors for
uncommitted lines. Mobile. A view that steps through the branch one commit
at a time. Showing who wrote lines from before the branch, or opening or
asking the threads behind them. Having a copy consult such a thread: "The
one consideration, which goes beyond the scope of this goal, works be the
possibility of using consult thread."

**Still unknown.**

- Does a copy of a coder whose long session was summarised part-way still
  give the real reason for its early lines, or a plausible reconstruction?
  The copy is told to say when it is reconstructing and to read its own
  transcript first. Asking about the early lines of a long-running coder in
  the first live pass settles whether that is enough. If it is not, the card
  warns when the coder was summarised after it wrote the lines, and whether
  a warning is enough comes back to you. So far it has been asked only of a
  stand-in: a short Sonnet session, compacted twice, whose copy searched its
  own transcript and quoted the original instruction word for word. A test
  instance cannot run your real coders, so the answer for one of those waits
  for your first use after deploy.
