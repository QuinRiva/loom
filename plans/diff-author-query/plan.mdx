# Ask the thread that wrote a line, from the branch diff

**Build it in five slices on two things Loom already has.** Git blame, stopped at the branch's merge base, names the commit behind every changed line, and every agent commit names its thread. So the server can say which thread wrote each block of the whole-branch diff without recording anything new. The read-only query thread built for plans and recaps answers questions about code under its existing role.

The reviewer sees a coloured edge and a thread chip on each block. Selecting lines opens a card naming the thread and commit. From the card he asks a read-only copy of that thread (Query author) or goes to the live thread at the turn that made the commit (Open thread). Either way the Diff panel beside the new conversation is the one he left, and one click returns him.

The plan makes **three bets**. Authorship is computed by the server in **one background request after the diff is drawn**, never on the diff's own path. A code query is **the existing query thread role with a second subject record**, so its read-only posture is inherited, not rebuilt. The diff follows the main window by **pointing the destination thread's Diff panel at the reviewing thread's state**, not by copying it.

The whole-branch view of the Diff panel, same file both sides. After, a row under the toolbar lists the threads that wrote the surviving changes, and each is a filter. Every changed line carries its thread's colour on its left edge. The row above each hunk names the thread and commit. Thread names and code are invented, as in the mockup the owner approved; the layout is his.

**In scope.** Web and desktop, the Diff panel's whole-branch view, pi-backed author threads. **Not built**, per the brief: authorship on GitHub's pull request page, authors for uncommitted lines, mobile, a per-commit stepping view, anything new for the "Since your message" view. **Done means** every check in the brief passes in a live pass on a dev instance against a real pi author, and its three must-not lines hold (§8 maps each).

## 1. One review, start to finish

Four words are used with one meaning throughout. A **block** is a run of consecutive changed lines that one thread wrote. The **author thread** is the thread a block's commit names. The **reviewing thread** is the thread whose Diff panel the reviewer is looking at. A **query thread** is the read-only, visible fork of an author that already exists for documents. <Sidenote>`docs/internals/glossary.md`, Loom side threads.</Sidenote>

<Steps>
  <Step at="open" title="The reviewer opens the whole-branch diff." badge="slice 1">
    The panel draws exactly as today. Once its file list has loaded, one extra request, `loom.review.authorship`, asks the server who wrote the changed lines. When it answers, edges, hunk chips and the "Written by" row appear; no row changes height. Clicking a thread in the row narrows the file list to files holding that thread's lines and dims the other threads' lines.
  </Step>
  <Step at="select" title="He selects lines; a card names the thread and commit." badge="slice 2">
    The card is the panel's existing comment card with a header: thread chip, role, when it last ran, the commit's short id and subject. A second request, `loom.review.lineHistory`, lists earlier commits on the branch that touched the same lines. Where an earlier one belongs to a different thread, the card offers that thread too. Three actions: Query author, Comment, Open thread.
  </Step>
  <Step at="open thread" title="Open thread lands on the live author at the commit's turn." badge="slice 2">
    The main window moves to the author thread and scrolls to the moment the commit was authored. The Diff panel beside it shows the reviewing thread's diff: same comparison, same file, same selected lines. A "Back to review" button sits in the thread header.
  </Step>
  <Step at="query" title="Query author forks the author and sends the question." badge="slices 3 and 4">
    One RPC, `loom.codeQuery`, checks the commit and reads its thread. It forks that thread into a query thread, or reuses the live one, and sends the question as the reviewer's own message with the selected lines attached. The main window moves there; the diff follows as above. The author thread spends no turn and gains nothing. The asked lines carry a pin row in the diff, in every thread that shows that diff.
  </Step>
  <Step at="promote" title="Promote leaves a comment about those lines in the author's composer." badge="slice 5">
    The existing Promote button and tool. The query thread writes one comment; it appears in the live author's composer as an ordinary diff line comment for the reviewer to send.
  </Step>
  <Step at="back" title="One click returns to the reviewing thread." dashed>
    Its own Diff panel state was never written, so the comparison, folds and thread filter are as left; the file and selected lines are restored from a per-thread focus record.
  </Step>
</Steps>

## 3. Authorship: how a line gets its thread

<Callout tone="decision" title="Blame the working tree down to the merge base, then read the commit's trailer; one request per diff">
  For each file the branch changed, the server runs `git blame --incremental ^<mergeBase> -- <path>` on the working-tree copy. Lines older than the merge base come back marked `boundary` and are dropped. Lines not yet committed come back with the zero commit id and are reported as uncommitted. Every other group of lines names a commit on the branch. One `git log <mergeBase>..HEAD` reads each commit's subject, git author, author date and `Loom-Thread` trailers. The trailer is written by the git shim in `apps/server/src/loom/workstream/agentGitIdentity.ts`. The reply is run-length encoded, so a branch of 161 blocks is a few kilobytes.
</Callout>

The client draws from it, the server applies it again when a question is asked (§7), and the tests cover it once.

**Bounds.** At most 400 files, four blames at a time, 5 s per file, 8 s in all; past either, `incomplete` is true and the unreached files carry no entry. A normal branch needs a fraction of that (the largest of the ten took 1.7 s serially). The client keys the query on the branch-range source's `diffHash`, so it re-asks only when the diff's content changed, not on every refresh tick.

**Earlier authors.** `loom.review.lineHistory` takes `{ threadId, baseRef, path, startLine, endLine }` and returns the branch commits that touched those lines, newest first, in the same commit and thread shapes, from `git log -L<start>,<end>:<path> -s <mergeBase>..HEAD` (64 ms measured). It returns no commits when the file differs from `HEAD`, because the line numbers would not match; the card then offers no earlier author. It is asked when a card opens, never at diff open.

**Deferred: who removed a line.** `git blame --reverse <mergeBase>..HEAD` gives the last commit in which an old line existed; on a branch without merges the next commit touching the file removed it. Exact, two more git calls per block, and not needed for 96% of blocks, so it waits for the owner to miss it.

## 6. The diff follows, and returns

<Callout tone="decision" title="Point the destination's Diff panel at the reviewing thread; write nothing into the destination's own diff state">

## 9. The live pass, and the summarised coder

The end-to-end journey, run at slice 4 and again after slice 5, on a dev instance with a real pi author on its cheapest model. The fixture is a small branch in a scratch worktree: one coder thread makes two commits, a second thread rewrites three of its lines in a third commit, and one line is left uncommitted.

1. Open the Diff panel, pick Changes. Two thread chips and "uncommitted" in the row; edges match `git blame`; the rewritten lines wear the second thread's colour.
2. Select the rewritten lines. The card names the second thread and its commit, and offers the first as earlier.
3. Query author on a block of the first thread; ask why. The main window is the query thread with the lines as a chip and an answer; the panel shows the same base, file and selection; the lines carry a pin row.
4. Ask it to change a line: it refuses and names the author as the writer. Ask it to commit a one-line fix from the shell: it declines, and `git status` and `git log` are unchanged. Open the author thread: no new message, no new run.
5. Back to review: the panel is as left, pin included. Select other lines by the same thread and Query again: no new thread.
6. Promote the first answer; open the author: one chip on those lines in its composer.
7. Open thread from another card: the timeline is at the commit's turn, the diff beside it; Back returns.

**The summarised coder.** In the same pass, on a copy of the cockpit database, pick a coder thread whose pi session holds a `compaction` entry later than one of its own commits (the session file records them; `apps/server/src/loom/context-viz/piSessionContext.ts` already reads that entry). Query the lines of that commit and compare the answer with what the thread wrote in the turn that made it. First confirm the fork's `$PI_SESSION_FILE` holds the author's turns from before the summary; if it does not, the overlay sentence that points there is replaced with a consult of the live author.

## 10. Risks, and where the code differed from the brief's leads

<Callout tone="risk" title="What could go wrong">
  - **Stamping the viewer** (§4). The only part resting on a library's behaviour rather than its API. Proved first; fallback named.
  - **The first question to a cold author costs a full read of its context.** A coder that finished days ago has no warm prompt cache, so its query thread's first turn reads the whole context at the uncached price. Later questions in that thread, within the cache window, are cheap. Nothing in the brief bounds cost; the owner is told (below).
  - **A very large branch.** An upstream sync changes tens of thousands of files. The bounds return a partial answer and the row says so; such a branch has few agent lines anyway.
  - **A query thread can still write through bash.** The guard refuses pi's `edit` and `write`. A `sed -i` or `git commit` in a shell is stopped only by the overlay's instruction, as for document queries today. It matters more here, because the fork is a coder sitting in the worktree under review. The paragraph under this box says why the plan adds no filter.
  - **Pins and line numbers.** A pin is tied to a commit and a line range, and hides once those lines change hands. It is a marker for the review in progress, not a durable annotation.
  - **Earlier authors on a dirty file.** Not offered when the file differs from `HEAD` (§3).
  - **An old query thread's shell.** Shell snapshots omit settled roots beyond the newest 25, so pins of long-finished query threads can disappear, as document pins do today.
</Callout>

**Why no bash filter.** A commit made by a query thread would carry its own trailer and show as its own block, so it would be visible, not misattributed. Matching shell commands is leaky, and the real fix is a read-only sandbox for the fork, which is its own piece of work and serves document queries equally. Slice 4's live pass asks the fork to commit as well as to edit, so a model that ignores the instruction is seen before the owner uses it.

**Where the code said otherwise, or more.**

- The lead said the diff "does not follow by itself" and suggested carrying state. The panel is also remounted per thread and takes its worktree from the thread, so a copy would be wrong whenever the author's worktree differs; §6 follows by reference instead.
- The lead asked whether Promote can reuse the diff line comment shape. It can: a promoted code comment is an ordinary `line` review comment, and `DiffCommentAnnotation` already has the secondary-action, label and placeholder props the card needs. The promote tool's own description is written for documents and is reworded (§7).
- The lead counted 193 of 193 commits over 14 days. Over the trailer's whole life it is 583 of 583 non-merge commits, but 4 carry two different threads (an amend adds the amender's trailer), which the lead did not anticipate and §3 handles.
- "There is no blame anywhere in the app" holds for the app; `scripts/loom-evals/gate_escapes.py` already pairs `git blame` with the `Loom-Thread` trailer for an eval, the same technique.
- The whole-branch diff is the working tree against the merge base, not `HEAD` against it, so it already contains uncommitted and untracked changes. That is why "uncommitted" is a real state in the first cut and not an edge case.
- A side-thread class exists (`SIDE_THREAD_ROLES`, `plans/side-thread-class/plan.mdx`) that places query threads in the sidebar, graph and thread tabs by role; it is a further reason for one role in §7.

**Earlier plans checked.** No plan is superseded.

- `plans/change-review/plan.mdx` (done) removed the per-coder scope and deferred "a per-file chip naming the coder". This plan delivers that by blame, adopts its seam rule, and replaces none of its decisions.
- `plans/plan-query-threads/plan.mdx` (done) and `recaps/query-threads/recap.mdx` define the query thread. This plan widens what its role means and changes nothing for documents beyond rewording five strings.
- `plans/promotion-link-back/intent.mdx` (done) added the promotion receipt row, which slice 5 extends to code.
- `plans/document-comments-to-author/intent.mdx` (draft) concerns document links and does not overlap.

**Recorded in the brief as Assumed, for the owner to redirect.**

- A block that only removes lines shows no author.
- A commit two threads amended names neither.
- Authors show in the whole-branch view, which he reaches by picking Changes when the panel opens on "Since your message".
- The thread filter narrows the file list and dims other threads' lines; it does not cut their hunks out.
- The mockup's "after ‹thread›" note on a hunk's row is not drawn. The earlier author is on the card, where the brief's check puts it, because finding it needs a history walk per hunk.

## As built

Slices 1 and 2 were built and reviewed on 17 Nov 2026 and ship in one pull request. Where the build departs from the sections above:

- **Slices 3 to 5 were not built.** After the plan was approved the owner deferred Query author, its line markers and Promote: "let's just try slices 1 and 2 and see if that works. Then we can always come back and build the remaining ones after we deploy slices 1 and 2 if I see value in that." So the card offers Open thread only, no Query author button is drawn, and `AnnotatableCodeView.tsx` gained one optional prop, not three. §7 and the slice 3 to 5 cards stand as the design for that later work.
- **Authors also show in the live "Since your message" view**, which the plan left out. The owner chose "Show authors in both views" once it was clear the panel opens on that view. The server reply still covers the whole branch; the client cuts it to the lines the interval's patch adds, so a thread is not named on lines changed before the message. Earlier intervals show no authors.
- **`baseRef: null` means the automatic base**, resolved by the server through the same driver call as the diff, so the live view can ask for authors without a branch source of its own. The wire shape is unchanged.
- **Authorship is asked once the diff's first patches have arrived**, not on the viewer's first render, which raced the patch reads and slowed loads over the shared link. The query is keyed on the diff's content hash and the workspace mutation id, and an answer is drawn only on the content it was asked for, so a refresh never paints an old answer on lines that moved.
- **Blame runs on git's background lane**, so it never takes a permit the diff's own reads use.
- **The edge recolours the viewer's existing added-line bar** instead of adding a second edge, which sat under that bar and could not be seen. Removed lines get no edge; the hunk label still names the authors.
- **Each author row on the card has its own Open thread button.** With Query author gone, the plan's single action row and its "subject" chosen by clicking an earlier row would only have added a state to manage.
- **A card with no comment typed gives way to a new selection.** Selecting lines opens the card at once, and upstream disables selection while a draft exists, so without this a second selection would need a Close first.
- **`reviewFollowStore.removeThread` was not kept.** The plan asked for it for parity; nothing calls it.
- **`authorOf` stayed in `packages/shared`** as planned, although the server check that was to share it belongs to slice 3.
- **Slice 2 ran after slice 1's review, alone.** The parallel run with slice 3 never arose.
