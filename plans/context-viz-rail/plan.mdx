# The rail becomes the scrollbar: a token-space track at the right edge, three marked lines upstream, the drag measured first

Rebuild `Rail.tsx` as the timeline's scrollbar: an **8 px track at the right edge, full height, on fine pointers only**, coloured by the whole session's context window in tokens as the rail is today, with a **thumb that is the rows now in view, mapped into token space**. **Wheel** over it scrolls the timeline, forwarded as the minimap forwards. **Drag** scrolls through tokens: once per frame the row holding the token under the pointer is placed at the pointer's own height in the viewport, so the pointer stays on the thumb while a folded 300K turn flies past. **Click** lands on the row through today's `jumpToItem`, unfolds a folded turn, or, in the veil over turns not loaded yet, pages back through the conversation jump the Workstream surfaces already use. **Hover** names the item, as today. The native scrollbar goes by **one marked CSS rule** on an attribute the host sets, and the prose does not move because the timeline's padding already subtracts the measured gutter. The upstream cost is **three marked lines in `MessagesTimeline.tsx`**: an import, one guard, one call publishing the visible row range `refreshMinimap` already computes. The one bet the code cannot settle is whether `scrollToIndex` once per frame keeps up on the 58-turn thread, so **the drag is built first and measured** (§3); if it fights, the drag becomes land-on-release, and the brief's unknown is settled either way.

## 1. The token-space map

**Reused.** `railLayout` in `Rail.tsx` already filters the report to `inWindow && tokens > 0`, lays the items in session order, and keeps `span`, a map from item id to its `[start, end)` in tokens from the top, plus the merged `segments` with their `start`. `TimelineFigures` (in `timelineFigures.ts`) already carries `rowKeyOfItem` (item id to the row key its row is found under: a tool's `nativeId`, `user:<messageId>` for a prompt) and `runOfItem`; `rowKeys(row)` and `rowIndexOf(rows, rowKey)` already turn a row key into a row index with a per-rows cache. The join (`figures.join`) carries `byNativeId`, `byUserMessageId`, `argsOfTool` and `runs.get(runId).items`. Nothing new is computed on the server and nothing new crosses the socket.

**Added.** Two directions on top of that, both pure, in a new `railLayout.ts` beside `Rail.tsx` (the layout and `segmentTitle` move there from `Rail.tsx`):

**The thumb.** Its top is the smallest `start` and its bottom the largest `end` over the rows `visibleRows.start … visibleRows.end` that have a span, written as `top: start/total × 100%` and `height: max(4px, (end − start)/total × 100%)`, the formula today's outline uses. When no row in the range has a span (the viewport shows only the history control, or only the footer), **the thumb is not rewritten** and stays where it was. The thumb is today's outline (`ring-1 ring-foreground/70 ring-inset`) with a `bg-foreground/10` fill so it reads as something to grab; no transition on it. The whole 8 px width is grabbable: the track takes the pointer, not the thumb (§2), so the thumb needs no hit area of its own.

**The veil.** Loaded turns are a suffix of the session (history pages in from the end, ten human turns at a time), so the veil is one rectangle: from the first item that is not fixed overhead (`CATEGORY_OF[kind] !== "fixed"`) to the first item whose run has a row. A run has a row when a `turn-fold`, `attempt-fold`, `message` (`message.runId`) or `work-toggle` row names it; `loadedRuns(rows)` is one pass over the rows cached per rows array, like `rowIndexOf`. The veil is `bg-background/60`, `pointer-events-none`, `aria-hidden`, recomputed at render when `rows` change. The fixed overhead at the top (system prompt sections, tool schemas, compaction base) is not veiled: it has no row anywhere, so "not loaded yet" would be a lie; §2 says where a click on it goes.

**Where an item lands.** `jumpToItem(key, itemId)` today scrolls to the row, or unfolds a folded turn and finishes the jump when the host next publishes rows that hold it, or returns silently. It gains a return value, the landing it found, so the rail can take the fourth case itself:

<Code
  filename="apps/web/src/loom/context-viz/timeline/timelineFigures.ts"
  language="ts"
  code={"export type ItemLanding = \"row\" | \"folded\" | \"fixed\" | \"unloaded\";\n\n/** Where an item's row is: in the loaded rows, inside a folded loaded turn, nowhere\n *  because it is fixed overhead, or in a turn history has not paged in yet. */\nexport function landingOf(key: string, itemId: string): ItemLanding;\n\n/** As today, and returns the landing it acted on; \"unloaded\" means it did nothing. */\nexport function jumpToItem(key: string, itemId: string, unfold = true): ItemLanding;\n\n/** listRef.scrollToIndex({ index, animated: false, viewPosition }), reading the latest rows. */\nexport function scrollToRow(key: string, index: number, viewPosition: number): void;\n"}

`landingOf` tests in order: `rowIndexOf(nav.rows, rowKeyOfItem.get(id)) ≥ 0` is `"row"`; a collapsed `turn-fold` or `attempt-fold` row with `runOfItem.get(id)` is `"folded"`; `CATEGORY_OF[kind] === "fixed"` is `"fixed"`; else `"unloaded"`. It reads `navigation.get(key).rows`, the rows the host last published, as `jumpToItem` does, so a drag during streaming sees the rows the list has.

## 2. The four inputs: wheel, drag, click, hover

<Callout tone="decision" title="Drag semantics: the row holding the token under the pointer sits at the pointer's fraction of the viewport">
  `scrollToRow(index, f)` with `viewPosition: f`, not a grab offset. A native thumb keeps its height during a drag so a grab offset keeps the pointer on it; this thumb's height is the tokens of whatever rows are in view and changes every frame, so a grab offset in tokens would put the pointer outside the thumb the moment a folded turn scrolls in. With `viewPosition: f` the row holding token `t` is at height `f` of the viewport, so `t` is inside the visible range and therefore inside the thumb, by construction, on every frame.
</Callout>

A scroll commanded while the agent is streaming is the one place the follow-release ordering could bite: the conversation jump calls `onManualNavigation()` and waits two frames before scrolling because "the timeline must have re-rendered without pinning to the end, or it snaps straight back". The Heaviest menu's `jumpToItem` does neither and has not been reported to snap. If a drag during a running turn snaps back on the dev instance, the fix is one more marked line, `onManualNavigation: navigateTimeline` on the `sharedState` literal in `MessagesTimeline.tsx` (and its field on `TimelineRowSharedState`), called once at pointer down; the coder adds it only if the snap is seen and says so.

## 3. The drag is step one, and it is measured

The brief's unknown: "Does `scrollToIndex` once per frame during a thumb drag keep up on the 58-turn thread with a tool group expanded, or does the list fight the drag?" This plan does not spike it beforehand; it builds the live drag as the primary design, in the order §8 gives, and measures it before the rest of the rail is built, because the fallback changes one handler.

**The measurement.** Dev-verify recipe, dev database seeded with `vp run migrate-dev-db --root 50aa9c55-75dc-4d6a-b059-365a95393600` (Carl's "Context Usage Breakdown Visualisation" thread, 33 runs in the projection, 58 turns in its session). ## 4. Hiding the native scrollbar

**Reused.** `--app-scrollbar-width: 6px` and the global `::-webkit-scrollbar` rules in `apps/web/src/index.css`; the scroller's `scrollbar-gutter-both` class (`scrollbar-gutter: stable both-edges`, 6 px reserved on each edge); `ChatCanvas.tsx` measuring `(offsetWidth − clientWidth) / 2` into `--chat-timeline-gutter` from a ResizeObserver on the scroller; the rule `[data-chat-canvas] .messages-timeline-scroll` whose `padding-inline-*` is `3rem + inset − gutter`.

**Added.** One rule in the fork-only region of `index.css` (between the `/* loom: from here … */` and `/* loom: end of fork-only UI */` markers), on an attribute the host sets on the scroller:

<Code
  filename="apps/web/src/index.css"
  language="css"
  code={"/* loom: context-viz rail: while the token-space scrollbar is mounted the native one goes, on fine\n   pointers only; the gutter it reserved collapses with it and the lane's padding grows by the same\n   6 px (the padding subtracts --chat-timeline-gutter), so the prose does not move. */\n@media (pointer: fine) {\n  .messages-timeline-scroll[data-context-scrollbar] {\n    scrollbar-width: none;\n  }\n  .messages-timeline-scroll[data-context-scrollbar]::-webkit-scrollbar {\n    display: none;\n  }\n}\n"}
/>

Both declarations, because they cover different engines: `scrollbar-width: none` is Firefox 64+, Chromium 121+ (the desktop app's Electron 44 is well past that, so it takes this one; Chromium then ignores `::-webkit-scrollbar` on that element, which is fine since both hide) and Safari 18.2+; `::-webkit-scrollbar { display: none }` covers older Safari. On macOS, where the native scrollbar is already an overlay with no gutter, the rule changes nothing visible and the track sits where the overlay would; the brief's "not checked on a Mac" carries forward.

**Why the lane does not shift.** With `scrollbar-width: none`, `scrollbar-gutter` reserves nothing, so `clientWidth` grows by 12 px. The ResizeObserver in `ChatCanvas.tsx` observes the scroller's content box and fires; `timelineGutter` becomes 0; the padding rule's `− var(--chat-timeline-gutter)` term goes from −6 px to 0 on both sides. Content left edge before: 6 px gutter + (48 px + inset − 6 px) padding; after: 0 + (48 px + inset). Same number. The one cost is a frame between the attribute landing and the measurement landing, in which the prose sits 6 px left; it happens once per mount and once per switch flip, not on scroll.

**The attribute.** Set in `TimelineHostOn` (switch on, thread known), not in `TimelineFiguresHost` (report loaded), so a thread opened with the switch on hides the native scrollbar on the list's own first frame rather than when the report arrives: a `useLayoutEffect` keyed on `figureKey` that writes `scrollNode.dataset.contextScrollbar = ""` and deletes it on cleanup (`// oxlint-disable-next-line t3code/no-unreasoned-state-sync -- hides the native scrollbar of the list the rail replaces; the scroller is LegendList's element, not React-owned here`). The figures effect in `TimelineFiguresHost` re-asserts it when missing, `if (!("contextScrollbar" in node.dataset))`, which costs one property check per publish and covers a list remount without a thread change. The track renders empty (the `bg-muted/40` strip, no segments) until the report arrives, so the edge does not pop.

## 6. Timeline off, width, touch, keyboard

**Timeline off is today exactly.** `TimelineHost` returns `null` before reading any store; the attribute is never set, so the CSS rule never matches, the native scrollbar and both 6 px gutters are back, `--chat-timeline-gutter` measures 6 px, the minimap is untouched (the guard change in §5 is behaviour-identical). The check, in the console on the dev instance with the switch off, then on: `getComputedStyle(document.querySelector('.messages-timeline-scroll')).scrollbarWidth` reads `auto` then `none`; `offsetWidth − clientWidth` on that element reads 12 then 0; `getComputedStyle(document.querySelector('[data-chat-canvas]')).getPropertyValue('--chat-timeline-gutter')` reads `6px` then `0px`; and `document.querySelector('[data-timeline-root]').getBoundingClientRect().left` reads the same number both times. Screenshots of both.

**Width.** The `@container/context-rail` and `@min-[1100px]/context-rail:flex` classes go: the track is the scrollbar and is on at every width. Nothing replaces the rule; the only width-dependent thing is the label, which opens leftward at every width (§2). With the right panel open the track sits at the chat column's right edge, against the panel, where the native scrollbar sits today.

**Touch.** The track root is `hidden [@media(pointer:fine)]:block`, the minimap's own variant, and the CSS rule is under `@media (pointer: fine)`, so on a coarse pointer the rail is absent and the native scrollbar and touch scrolling are untouched.

**Keyboard and accessibility.** The custom scrollbar is a pointer affordance, like the native one: not focusable, no key handling, and keyboard scrolling of the timeline (`timelineViewport.ts` hears PageUp, PageDown, Home, End and the arrows app-wide) is untouched. The track keeps today's `role="group"` and `aria-label` (`Context window, 1.1M in session order`); the segments become `aria-hidden` spans rather than buttons, and the thumb and veil are `aria-hidden`. This removes today's several hundred tab stops (one `<button>` per segment), which no keyboard user was going to tab through to reach a tool result; the Heaviest menu and the Context tab remain the keyboard routes to an item.
