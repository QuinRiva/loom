# Binding sub-threads to a branch of the goal task tree — options

The goal task tree is the human's glanceable record of a goal: what is done, what is outstanding, where each thread is up to. It is also, today, an undifferentiated broadcast: every child thread receives the **whole** tree as a spawn-time prompt snapshot, and every task mutation echoes the **whole** tree back into the conversation. On a mature goal that is mostly ticked history, both channels ship almost nothing the child needs. This document lays out four genuinely distinct designs for scoping what a sub-thread sees and touches — from a pure rendering change to a real thread↔branch binding — costs each one on both token channels against a realistic ~90-item tree, and recommends one.

**Done means:** Carl picks an option (or the recommended composition) and resolves the decision points in the bottom form; the choice then becomes an implementation plan. This document changes no code.

<Callout tone="decision">
Two constraints are treated as fixed throughout, plus one this document adds. (1) **The human's tree must not get worse** — every design is judged first on the glanceable shared artefact. (2) **Round-trip identity holds per scope**: any view that can legally feed `goal_tasks_rewrite` must reproduce, verbatim, a tree the rewrite parser accepts as a no-op (`apps/server/src/orchestration/goalTaskMarkdown.ts`, header contract). From these two follows the **rewrite-source invariant** this document adds: a scoped or elided rendering must either be complete within its declared scope, or be mechanically unusable as a rewrite submission — never a plausible-looking partial tree whose resubmission silently deletes what was elided.
</Callout>

The two channels obey the same rule of thumb — **≈$0.09 per 1k tokens made resident in a long (~180-turn) thread** — so the design question is the same for both: how many of those tokens carry information *this* thread acts on. But the channels are not symmetric in purpose. The prefix snapshot is orientation, injected whether or not the thread ever touches the tree. The echo exists **because agents were managing a tree blind**: before the whole-tree echo shipped, mutations returned only `"Added task <id>"` and agents accreted 50-item flat messes without ever seeing them (`plans/goal-task-tree-redesign/plan.mdx`, evidence section). Carl's framing for this document: the axis is **awareness versus bloat**, not "echo or not" — every option below must say what keeps the agent genuinely aware of the tree state it is responsible for, and what that costs per call. Regressing to a blind confirmation line is off the table.

## What exists today (verified in code)

- **No thread↔task link exists anywhere.** `OrchestrationGoalTask` (`packages/contracts/src/orchestration.loom.ts:225-269`) carries id, goalId, parentTaskId, text, done, position, timestamps, children — nothing else. The thread record (`LoomThreadFields`, same file, ~line 375ff) carries `goalId` but no task id; the spawn/scaffold request shapes (`apps/server/src/mcp/WorkstreamSpawnHttp.ts:97-129`) have no task parameter (`taskShape` there is a model-selection hint, unrelated). A child inherits its parent's `goalId` wholesale at spawn (`apps/server/src/orchestration/decider.loom.ts:1583`). A child identifies "its own task" only through brief prose — the orchestrator pastes the id into the brief, or nothing. The retro's recommendation R7 ("inject the agent's own task plus its immediate parent") therefore **presupposes a link that does not exist**; it is not implementable as stated.
- **Injection is once, at session spawn.** `buildGoalSystemPrompt` (`apps/server/src/orchestration/Layers/ProviderCommandReactor.ts` ~line 688) appends `activeGoalContextInstruction` (same file, line 223) to the pi system prompt: goal header, objective, the full tree via `renderGoalTaskTree`, then a static write-discipline paragraph (~1.5 KB in the child variant) carrying the register rules and the AIT-101 worked example — the same example that also ships in the 300-character cap error (`goalTaskMarkdown.ts`). The child variant frames the tree as "background, NOT your task" and points at `goal_task_list` for the live tree. A `forkFrom` child replays its **source's** captured launch identity, so a fork's injected snapshot is the source's; only live tool calls see current state.
- **One rendering, three surfaces.** `renderGoalTaskTree` (`apps/server/src/orchestration/goalTaskRender.ts`) is the single home of the `- [x] text (id)` shape, shared by the injection, `goal_task_list`, and the `t3 goal show` CLI. Full 36-character uuids account for roughly a fifth of the rendered bytes.
- **Every mutation echoes the whole tree** via `echoTree` (`apps/server/src/mcp/GoalTaskHttp.ts:74-80`) — a deliberate design ("the agent sees the shape it is accreting at the moment it mutates").
- **Structure is already ownership-gated.** `goal_tasks_rewrite` is rejected for any thread with a `parentThreadId` (`GoalTaskHttp.ts`, rewrite handler), with the check living at the HTTP edge because commands carry no thread identity — the precedent for where any branch-scoping check must live. Children keep `goal_task_add` and `goal_task_update` (855 of 1,029 historic updates were children marking tasks done).
- **The rewrite parser is strict about ids.** A trailing `(token)` is an id only if it names a task of this goal; an unknown uuid-shaped token is a 400 (stale read); a non-id token is task text; an unparseable line fails the whole submission (`goalTaskMarkdown.ts:70-150`). This strictness is what makes elision markers in scoped renderings mechanically self-defending (used below).
- **Prior art sets the frame.** The tree redesign explicitly deferred "thread↔task assignment links" ("defer until the rewrite loop proves out" — it has now run for weeks); the content contract owns register and the 300-char cap (grandfathered on retained text); the child-prompt-dedup plan left the tree snapshot untrimmed as a named loose end and made all four goal-task tools leaf-core (`apps/server/src/mcp/toolPaths.ts:67-77`).
- **Human surfaces:** `GoalTasksPanel.tsx` renders the tree read-only; `GoalThreadsSection` lists the goal's threads, but nothing connects a task to the thread working it. `t3 goal show` renders the same markdown.

## Option A — Prune the views (state-scoped rendering, no binding)

No data-model change; the tree is re-rendered by *state* for token-sensitive surfaces. A fully-done subtree collapses to its root line plus a count marker; open tasks and their ancestors render in full.

**1. Binding.** None. "Own task" remains brief prose; a child with no node is simply a child whose brief has no task id — exactly today.

**2. Injection.** Both child and root variants use the pruned rendering. Against the reference tree:

The static guidance is unchanged apart from one added sentence: *"Done work is elided above ('N done tasks elided'); `goal_task_list` reads the complete live tree."* Every snapshot keeps the refresh pointer, per Carl's rule that a snapshot is only justified alongside the instruction to re-read live.

**3. Tool semantics and echo.** Tools behave exactly as today; only renderings change. `goal_task_list` stays **complete** — it is the sole rewrite source (rewrite-source invariant). All three mutation echoes switch to the pruned rendering, for every thread. **Awareness:** the agent sees the entire open plan — every phase, every unticked item, correct nesting — on every mutation; what it loses is re-reading finished history, which is precisely the ~5.6k tokens per call that carry no decisions. **Cost per call: ≈2.1k tokens (from 7.7k)** on the reference tree. The elision markers are the safety mechanism: `— 12 done tasks elided` makes the marker part of the task text if resubmitted (and the line would rename the task), while a wholesale paste of the pruned echo into `goal_tasks_rewrite` deletes elided tasks only if the agent also strips the markers — the existing "rewrite from a fresh `goal_task_list` read" guideline plus a one-line note in the echo footer covers the residual risk. Weakness: pruning scales with the done ratio — a young goal (mostly open) barely shrinks, and an old goal's 14 open items still include every phase unrelated to this child.

**4. Out-of-branch discovered work.** Unchanged: `goal_task_add` anywhere, nested under the phase it belongs to; the pruned echo still shows the placement in context.

**5. Human surfaces.** Untouched — the panel and CLI keep the full tree.

**6. Contracts/migration.** None. A render helper (`renderOpenGoalTaskTree`) beside `renderGoalTaskTree`, plus call-site switches in `ProviderCommandReactor.ts` and `GoalTaskHttp.ts`.

**7. Token model.** Prefix 6.4k → ≈2.1k (≈$0.40 saved per long thread); echo 7.7k → ≈2.1k (≈$0.50 saved per call made early). Capability lost: ambient sense of completed momentum (partially preserved by the counts).

**8. Size.** ~0.5–1 coder-day.

## Option B — Anchor tasks (a real thread↔branch binding)

A thread may be **anchored** to one task of its goal at spawn. The anchor's subtree is "its branch": the branch is what gets injected, what tools read and echo by default, and what the thread may restructure. Everything else in the goal shrinks to a one-line pulse.

**1. Binding.** `workstream_spawn` and each `workstream_scaffold` node gain an optional `anchorTaskId`. Validated at the HTTP edge (the established home for thread-identity checks): it must be a live task of the parent's goal, and — when the spawning thread is itself anchored — a descendant of (or equal to) the spawner's own anchor, so a nested orchestrator can only delegate within the branch it owns. Stored as a decode-defaulted nullable field on the `thread.created` payload and `LoomThreadFields`/shell (the standard additive pattern — historic events replay untouched). Omitted ⇒ **unbound**, which stays a first-class state: reviewers, researchers-against-a-brief, and gate threads mostly should not have nodes. A `forkFrom` child inherits its source's anchor (the fork diverges on the same work; tools resolve the anchor live from the thread record, so scoping is correct even though the fork's replayed prompt shows the source's snapshot). If the anchor task is later deleted (a root rewrite omits it), the thread degrades to unbound at read time — no event, no dangling failure. Auto-creating a node from the child's title/purpose is **rejected**: the tree's shape should follow the plan, not the org chart, and half of all children legitimately have no node. The orchestrator that wants a node adds it (`goal_task_add`, id in the echo) and passes the id — two calls, no new surface.

**2. Injection.** The bound-child variant becomes spine + branch + pulse, and the static guidance shrinks to a branch-framed third of today's (register clause kept as one line; the worked example drops from the child variant — the 300-char cap error already re-teaches it at the moment of violation; the root variant keeps it):

**Awareness:** a bound child is *never* blind about anything it can write to — its whole branch arrives on every mutation, and round-trip identity holds within the scope (the branch view resubmitted to branch rewrite is a no-op). What it gives up is line-level sight of sibling branches, which it cannot write to anyway (update is branch-restricted) and can read in one deliberate `scope "tree"` call. Branch scoping is thus itself the echo lever: the echo shrinks not by hiding state but because the thread's writable world is genuinely smaller. Unbound children (no branch to scope to) get Option A's pruned open-tree echo (~2.1k) — they can add anywhere, so they see the open plan everywhere.

**5. Human surfaces.** This is where the binding pays the human back: thread shells carry `anchorTaskId`, so `GoalTasksPanel` can chip anchored task rows with the working thread (role glyph + title, click to open) — task→thread navigation, the affordance the panel has never had. `workstream_list` prints each child's anchor line, so an orchestrator re-orients without a tree read. **6. **8. Size.** ~2–3 coder-days (the largest single item is branch-scoped rewrite; without it, ~2).

## Option C — Pull, don't push (no injected tree)

Delete the tree from the prompt entirely; the tools are the only tree surface.

**1. Binding.** None. The **brief contract** gains a line: a brief that assigns a tree task must name its id (today this is folk practice; here it becomes the only mechanism).

**2. Injection.** Goal header + objective + ~4 lines of guidance (~0.15k tokens): the tree exists, read it with `goal_task_list` when you orient and before you write, mark your task done, record discovered work under the phase it belongs to.

**3. Tool semantics and echo.** Tools unchanged. Because there is no ambient snapshot, the echo becomes the *sole* awareness channel and must not be gutted: mutations echo Option A's pruned open-tree (~2.1k), and `goal_task_list` stays complete. **Awareness:** entirely behavioural — and this is the option's honest weakness. Carl's own observation is that `goal_task_list` "wasn't being called very often": the retro child went 180 turns without one. An agent that never orients writes its adds against a guessed shape, and a child whose brief omits the task id cannot even mark it done. C converts a guaranteed cheap signal into a bet the measured behaviour already contradicts.

**4. Out-of-branch.** Unchanged mechanically; every placement now costs a prior list call (or lands top-level, the degradation the redesign fought).

**5. Human surfaces.** Untouched. **6. Contracts.** None — deletion plus prose. **7. Token model.** Prefix ≈0.15k; echo ≈2.1k; cheapest prefix of all options, echo cost equal to A. **8. Size.** ~0.5 day.

## Option D — Staged sub-trees (fold into the shared tree on submit)

Presupposes B's anchor. The child's branch becomes a **staging area**: its writes exist in the goal store flagged `staged`, invisible (or dimmed) in the shared panel and in other threads' views, and fold into the live tree when the child submits.

**1. Binding.** As Option B. **2. Injection.** Spine + anchor + pulse (the branch typically starts empty; ≈0.3k). **3. Tools/echo.** All child writes are staged; echo = own staged branch + pulse (≈0.3–1k) — awareness of its own work is complete by construction, awareness of the shared tree is the pulse. `workstream_submit`'s reactor flips the staged subtree live (cancel discards it). **4. Out-of-branch.** Everything stages under the anchor with the discovery phrased in the text; the orchestrator re-homes at fold-in — the most literal reading of the AIT framing ("that task is the orchestrator's"), at the price of the discovery being invisible until submit. **5. Human surfaces.** The panel needs a staged rendering (dimmed subtree per working thread) — and this is where D fails the first constraint: the human's glanceable "where is this thread up to" goes *dark* for exactly the long-running children who most need glancing at. Live progress visibility is the tree's point. **6. Contracts.** A `staged` flag on tasks, a fold event, submit/cancel reactor changes, panel rendering — real surface. **7. Token model.** Cheapest echoes of any option; prefix like B. **8. Size.** ~3–5 days.

## Recommendation: Option B, composed with A's rendering for the unscoped cases

<Callout tone="decision">
Adopt the **anchor binding** (B), using A's **open-tree rendering** wherever no branch scope exists — unbound children's echoes, and the root's injection — and C's near-empty injection *only* for the degenerate case of a goal with no tasks. Specifically: optional `anchorTaskId` at spawn/scaffold (explicit only, no auto-created nodes); bound-child injection = spine + branch + pulse; unbound-child injection = top-level overview + counts; bound-child echo = **branch + pulse** (rendered above); unbound-child echo = open-tree; root injection = open-tree, root echo and `goal_task_list` complete; branch-scoped rewrite for bound children; `goal_task_add` legal anywhere with a placement echo; `goal_task_update` branch-restricted for bound threads; the child guidance paragraph shrinks to the branch-framed third, dropping the worked example (the cap error keeps it).
</Callout>

Reasoning. B is the only option that makes "the agent knows what it owns" **mechanical** rather than prose — which is simultaneously the token fix (the writable world is smaller, so both channels shrink to it honestly, not by hiding shared state), the awareness fix (complete-within-scope on every mutation, satisfying the redesign's never-blind requirement at a tenth of the cost), the answer to the retro's two concrete findings (the no-task child gets a purpose-built overview; "own task" stops depending on brief discipline), and the only option that *improves* the human's tree, via task→thread navigation. It is also the smallest model that makes the behaviour unsurprising: one nullable field, scope resolution at the same edge that already owns thread-identity checks, orchestration and the decider untouched in their pure form. A alone leaves every child carrying all nine phases forever; C bets against measured behaviour; D hides in-flight work from the human. The redesign's rationale for deferring the binding — "until the rewrite loop proves out" — has been met.

On the two sub-decisions inside B: **branch rewrite for bound children** should be allowed. The blanket child block existed to protect the shared shape from any child; anchoring is a *principled narrowing* of the same rule — the root owns the tree's shape, a bound thread owns its branch's interior. Without it, a bound child-orchestrator decomposing its branch is back to the 79-event rebuild dance the redesign was built to kill. And **out-of-branch adds stay open** (with the placement echo) because live shared visibility of discovered work is the tree's job; the orchestrator re-homes at the next seam, exactly as it re-shapes anything else.

### Worked example: the AIT-ticket flow under the recommendation

The scenario Carl posed: a sub-thread discovers unrelated broken behaviour; a ticket should be written, likely by a fresh thread — but *creating that thread* is the orchestrator's task, not the discoverer's.

1. **Discovery.** The Phase-6-anchored coder above hits a pre-existing projection bug unrelated to its branch. It calls `goal_task_add` with text `"File an AIT ticket for the stale usage-projection rows (found during the thread-screen work)"` and, having the phase lines from its pulse-side `scope "tree"` read (or defaulting under its own anchor when unsure), targets Phase 7. The echo costs it ≈0.8k tokens: the added line with its spine, its own branch, the pulse.
2. **Shared visibility, immediately.** The task is live in `GoalTasksPanel` and in the root's next echo/list — the human and the orchestrator see the discovery hours before the child submits. Nothing about the child says the work is *its own*: it has no anchor there, `goal_task_update` on that task would be refused to it, and its guidance says discovered work is recorded, not adopted.
3. **Report.** The child's `workstream_submit` report names the finding and the task id — the report explains, the tree records.
4. **Ownership transfer is a binding, not prose.** The orchestrator, at the next seam, re-homes the task if the child's placement was wrong (one `goal_tasks_rewrite`) and spawns the ticket-writer with `anchorTaskId` = that task. The panel chip on the task row flips to the new thread. The ticket thread is injected with exactly that one-line branch plus the pulse (≈0.3k), writes the ticket, ticks its anchor, submits.

Every hand-off in the walkthrough is visible in the shared tree at the moment it happens, and at no point does any thread carry the 82 ticked tasks of Phases 1–5.

## Risks

- **Anchor drift.** A root rewrite can delete or move a thread's anchor mid-flight. Degrade-to-unbound at read time is the chosen behaviour; the thread's next echo switches shape (branch → open-tree), which is noticeable but not harmful. Accepted for a prototype.
- **Pruned-echo misuse as rewrite input** (root only, since children's rewrite is branch-scoped). The elision markers make a verbatim paste fail loudly; an agent that strips them can still delete elided tasks. Mitigated by the existing "rewrite from a fresh read" guideline plus an echo footer line; residual risk accepted. If it bites, the fallback is making the root's echo complete again — a one-line revert.
- **Behavioural bet on the pulse.** The claim that a one-line pulse preserves enough ambient awareness is untested. The fallback is graduated: swap the pulse for the top-level overview lines (≈+0.4k per echo) without touching the model.
- **Two children on one branch.** Nothing prevents anchoring two threads to the same task (forks do it by design). The panel chip shows both; the branch guard means they can race on done-marks exactly as siblings race today. Accepted.

## Resolved decisions (2026-09-23, Carl: "Proceed")

All seven questions below are resolved to the recommended option; these resolutions are binding on implementation:

1. **Design:** Option B composed with A — anchor binding, open-tree rendering for unscoped cases.

5. **Out-of-branch work:** `goal_task_add` legal anywhere with the placement echo; orchestrator re-homes.
6. **Root surfaces:** open-tree injection and open-tree echo; `goal_task_list` stays complete.
7. **Short ids:** deferred.
