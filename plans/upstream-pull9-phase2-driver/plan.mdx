## 1. pi 1.0.2 with both patches, and the bundled binary

### What the bump actually changes

Measured against the pristine 1.0.2 tarball (`npm pack @earendil-works/pi-coding-agent@1.0.2`, extracted under the worktree's `.artifacts/pi-1.0.2/`), so the coder knows what will and will not drift:

- **Patch 0002 is still needed and applies at zero offset.** `dist/core/auth-storage.js` writes `auth.json` with plain `writeFileSync` on both `withLock` (line 66) and `withLockAsync` (line 140); no `renameSync` anywhere in the file. The bundle's two call sites `…(this.authPath,next,AUTH_FILE_WRITE_OPTIONS)` are in `dist/bundle/chunks/chunk-PDFMCAOZ.js` (count 2, as the applier expects).
- **Patch 0001 is still needed.** `dist/cli/args.js` has no `--cwd`; the headless `--session` path still welds the runtime to the header cwd. The readable diff needs re-deriving: hunk 1 of `args.js` fails only because its context line `result.models = args[++i].split(",")…` became a four-line chain in 1.0.2; `args.d.ts` applies clean; `args.js` hunk 2 applies at a three-line offset and the `main.js` hunks apply (two of them at a six-line offset). All **eight** 0001 anchors of the current `patch-bundle.mjs` match exactly once in `chunk-ZSBPJAJ2.js` (and 0002's one anchor matches its two call sites in `chunk-PDFMCAOZ.js`; `patch-bundle.mjs` run on a copy of the pristine tarball reports `0002 … patched (1 edits)`, `0001 … patched (8 edits)`), and `resolvePath` is imported unaliased there, so the existing bundle edits carry over unchanged.
- **The RPC `switch_session` path is where the extension goes.** `dist/core/agent-session-runtime.js` `switchSession(sessionPath, options)` already accepts `options.cwdOverride` and hands it to `SessionManager.open(sessionPath, undefined, options?.cwdOverride)`, then builds the runtime with `cwd: sessionManager.getCwd()` — so **tools run in the session's recorded cwd** unless the override is given — and `assertSessionCwdExists` throws when that cwd is gone. Only the RPC command handler never passes it: `dist/modes/rpc/rpc-mode.js` `case "switch_session"` calls `runtimeHost.switchSession(command.sessionPath)`. The minified form `case"switch_session":{let result=await runtimeHost.switchSession(command.sessionPath);` occurs exactly once, in the same chunk as `main()`. The RPC loop already turns a thrown error into an error response (`output(error(command.id, command.type, message))`), so validation can simply throw.
- Dependencies: the six `@earendil-works/*` packages move `^0.99.2 → ^1.0.2`; one new transitive (`brace-expansion@5`, MIT). No new `@earendil-works/*` package, so `third-party-licenses.config.json` needs no new override — the README's manifest check still runs.
- pi 1.0.2's `runMigrations` touches only legacy layouts (`oauth.json`, `apiKeys` in settings, commands → prompts, keybindings, tools → bin) and skips when `auth.json` exists, so running the bundled 1.0.2 against the shared `~/.pi/agent` does not rewrite what the global 0.99.2 reads. The smoke still records before/after hashes of `~/.pi/agent/settings.json` and `auth.json` (read-only observation) because Phase 4's precondition asks for the evidence.

`resolveBundledPiCliPath()` is the quarantined function verbatim (`import.meta.resolve` of the package, walk up to the manifest, take `bin.pi` — `dist/bundle/cli.js`). The resolved path is spawned **directly**: the file is executable with a `#!/usr/bin/env node` shebang, `node` is on `PATH` wherever `pi` itself would have been (the cockpit unit puts `~/.n/bin` on `PATH`; the dev runner inherits the shell), and `PiRpc.makePiRpcConnection` → `resolveSpawnCommand` passes a POSIX command through unchanged. **`pi update --self` needs no disabling.** Upstream's `resolvePackageManagedProviderMaintenance` (`apps/server/src/provider/providerMaintenance.ts`) returns the **manual-only** capabilities for any binary whose real path contains `/node_modules/` unless a package manager is proven to own it (vp, bun, pnpm-global, yarn-global, volta, npm `lib/node_modules`, Homebrew); the bundled path `…/node_modules/.pnpm/@earendil-works+pi-coding-agent@1.0.2_patch_hash=…/node_modules/@earendil-works/pi-coding-agent/dist/bundle/cli.js` matches none of the proofs (`npmGlobalPrefixFromCommandPath` requires `/lib/node_modules/<pkg>/` with no earlier `/node_modules/`; `isPnpmGlobalCommandPath` matches only pnpm's global store paths). One test pins this (`providerMaintenance.loom.test.ts`). The "Update available: Pi 1.0.3" advisory will keep appearing while the bundled pin lags npm; it is informational and `enableProviderUpdateChecks` turns it off — not this item's concern.

## 3. `costUsd` on the terminal `tokenUsage`

Upstream's `OrchestrationV2ProviderTurnTokenUsage` (`packages/contracts/src/orchestrationV2.ts`) carries `usedTokens`, `maxTokens`, `inputTokens`, `cachedInputTokens`, `outputTokens`, `reasoningOutputTokens`, `updatedAt` — no cost. `PiAdapterV2.finalizeTurn` fills it from `get_session_stats` (`tokenUsageFromStats`); pi's `SessionStats` has `cost: number`, but that figure is the **whole session's** cumulative cost, as are its `tokens.*` totals. This plan keeps that semantics — **per turn, pi-priced**:

- Contract (marked): `costUsd: Schema.optional(Schema.Number)` on `OrchestrationV2ProviderTurnTokenUsage`, doc comment *"loom: USD for this provider turn, summed from pi's per-message usage.cost.total; never computed by T3"*. ## 5. Two doctrine checks — verdicts and their smallest hunks

### 5a. Area H — does the "Pi default" sentinel land a new thread on `PI_DEFAULT_MODEL`?

**How a new Pi thread gets its model today.** `PiProvider.ts` builds the model list as `[PI_DEFAULT_MODEL sentinel {slug: "default", name: "Pi default"}, …discovered]` with no `isDefault` on any entry (`piModelsFromSettings`, `parseDiscoveredModels`). The web picks a new thread's model with `models.find(isDefault && !isCustom) ?? models.find(!isCustom) ?? …` (`apps/web/src/providerModels.ts` `getDefaultServerModel`, `providerInstances.ts`, `modelSelection.ts`), so with nothing flagged the **sentinel** is chosen; the adapter then skips `set_model` (`PI_INHERIT_MODEL_SLUG`) and pi runs whatever `~/.pi/agent/settings.json` names.

**The fact that decides it.** Carl's pi settings name `defaultProvider: cliproxy`, `defaultModel: claude-fable-5-1`; Loom's `PI_DEFAULT_MODEL` is `cliproxy/claude-opus-5-5`. They differ **by design**: the platform-update skill maintains "global pi `defaultModel`" and "loom `PI_DEFAULT_MODEL`" as two separate default surfaces in its `targets.yaml`. So the sentinel lands a new Loom thread on Fable, not on the model Carl chose for Loom — the functionality is **not** satisfied — and it also records the run's `modelSelection.model` as the opaque `"default"`, which Phase 3c's cost-by-model, spawn headroom and reroute cannot key on.

**Verdict: hunk.** One marked line in `parseDiscoveredModels` (`PiProvider.ts`): `...(slug === LOOM_PI_DEFAULT_MODEL ? { isDefault: true } : {})`, plus one marked import `PI_DEFAULT_MODEL as LOOM_PI_DEFAULT_MODEL` from `@t3tools/contracts` — `PiProvider.ts` already declares a local `PI_DEFAULT_MODEL`, which is the sentinel `ServerProviderModel` object (`slug: "default"`), so the bare name compares a string to that object and never matches. The sentinel stays in the list (upstream's mechanism is not deleted; a user can still pick "Pi default"); `DEFAULT_MODEL_BY_PROVIDER[pi]`, the auto-bootstrap selection (DL-85) and text generation already name `PI_DEFAULT_MODEL`. If the cliproxy extension is absent and `PI_DEFAULT_MODEL` is not discovered, the fallback is the first non-custom model — the sentinel — which is the right degradation. Recorded evidence, both in the smoke below: stock (session 1 tree) — a new thread with no pick reports `modelSelection.model = "default"` on its first run; with the hunk (session 2) — `cliproxy/claude-opus-5-5`.

### 5b. Area L / DL-74 — does V2 prune a deleted thread's provider-session binding?

## 6. Stuck-launch verification — two modes, recorded verdicts

V1 had `stuckLaunchRecovery.ts` (a CAS repair) and `thread.turn-start.fail` for two failures: (a) pi hangs at spawn so the run sits in `starting` with no turn; (b) the `provider-turn.start` effect fails before any turn so the pending-turn row holds the idle gate forever. **No repair is ported.** The output is one verdict per mode, with evidence, that Phase 4 uses to delete or keep those modules and that 3b reads before deciding whether its liveness sweep needs a starting-run rule (P3-10).

**What V2 already does, so the coder knows what to look for.** The effect worker (`EffectWorker.ts`) retries a failed `provider-turn.start` with backoff `min(30 s, 100 ms × 2^(attempt−1))` up to `maxAttempts = 5`, then fails the outbox row. `ProviderTurnStartService.start` receives `willRetry` and, on the **last** attempt, `settleStartFailure` writes the run `failed` with an `error` turn item ("instead of leaving it `starting` after the effect gives up") for a session-open failure or a provider-thread-load failure. A `failed` run is not a blocking run (`isBlockingRun` = preparing | starting | running | waiting), so Loom's `start_if_idle` sees the thread idle. A hung pi is caught by `PiRpc` request timeouts: `get_state` in `registerThread` has 15 s (`PI_REQUEST_TIMEOUT_MS`); only lifecycle requests (`switch_session`, `new_session`, 60 s) terminate the process on timeout. Nothing in `ProviderTurnStartService` releases a session after a start failure, so a hung pi process may stay cached in `ProviderSessionManager` until its idle release (30 min). The verdict must therefore distinguish *the run recovers* from *the thread is usable again*.

<Callout tone="risk">
**Risks.** (1) *A regenerated patch that applies to `dist/` but not the bundle passes typecheck and fails at runtime* — the contract test drives the bundle and is the gate; never trust `apply.sh --check` on the global install as evidence for the bundled copy. (2) *The sibling-worktree trap* — a worktree that merged the bump commit without running `vp i` still resolves 0.99.2 and every probe passes anyway; assert the resolved version first (README). (3) *`cwdOverride` on an unpatched bundle degrades silently* to today's behaviour (pi ignores the field); only the contract test notices. (4) *Replay fixtures match outbound frames on the union of keys* — a future Pi fixture with a `switch_session` frame needs `cwdOverride: "<any>"`, or it fails for the right reason. (5) *Phase 2 substrate coders are editing `runtimeLayer.ts` concurrently* (the `storesLayer` line); this item's line is in `providerSessionManagerProvided`, so the merge is trivial but must be re-checked at rebase. (6) *The smoke runs the bundled 1.0.2 against the shared `~/.pi/agent`* — settings and auth are read-only by construction; the smoke's pi sessions are new files under pi's default session dir, `~/.pi/agent/sessions/<cwd-slug>/` for the scratch repo cwd, as every pi run writes them; F2's hashes are the evidence that settings and auth were not rewritten, and the scratch repo's session directory may be left for the reviewer. (7) *Stuck-launch mode (a) leaves a hung wrapper process* cached in `ProviderSessionManager` until idle release; kill it only by the PID read from `/proc`, after the observation, never by pattern.
