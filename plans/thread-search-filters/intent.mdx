# Thread search you can widen or narrow, with sub-threads as results you can open

**Goal.** "I think we need to consider how search is designed - because I can imagine I'd want to be able to have filters (include vs exclude children for example)." Make search something you steer. A few visible switches say where it looks: sub-threads, archived, one project. With none touched it reads what you ruled on 26 Oct, minus the padding it lists today when nothing matches. **Switching sub-threads on has to list the sub-thread itself and open it.** A switch that only reads their text, which is what the October toggle would have been, changes almost nothing.

<Callout tone="decision" title="What that means for your idea" focus>
  Filters are worth having, but "include children" as a reading switch is the weak version. Most of what a sub-thread did is already found through its report. What is missing is seeing which sub-thread it was and landing in it. So this brief asks for three switches, sub-thread rows you can open, and a default that stops padding. Five questions at the end; a bare "go" takes the recommended answers.
</Callout>

The Today column comes from `thread_search`, the search tool agents use, run on the cockpit on 23 Nov, and from the code each screen runs. I did not drive your browser or phone.

**You'll know it works when.**

- You touch no switch, and Cmd+K, the sidebar search and the phone's thread search find what they find today. That is a top-level thread's own messages, purpose and goal, and every sub-thread's report, with archived threads included and marked.
- You switch **Sub-threads** on and type `Word to PDF without malforming`: the sub-thread is listed under its top-level thread, and choosing it opens the sub-thread. Switch it off and the row is gone.
- You switch **Archived** off and the archived rows leave. You pick one project in Cmd+K and get a full list from that project, not what is left of thirty rows chosen across every project.
- You choose a result whose excerpt says "Report:" and land in the sub-thread that wrote it.
- You type words from a plan you read and the thread that wrote it is listed; choosing it opens the plan.
- You type `xylophone marmalade wombat` and see "No threads found". A paraphrase still works: `how do I stop the model picker showing duplicate names` still lists "This model picker is awful…" near the top.
- You type `CI` and get message matches.
- What is switched on shows beside the search box on every screen, and one action puts it back to the default.
- An agent's `thread_search` takes the same narrowing as parameters.
- **Must not:**
  - change which threads you find with no switch touched, beyond the padding going and plans arriving;
  - take longer to show results than today, or send more over the socket than the thirty rows a search returns now; <Sidenote>Six agent searches traced on the cockpit, 23 Nov. Three run alone took 0.44 to 0.52 s; three sent together each waited the 2 s limit and came back with word matches only.</Sidenote>
  - leave a switch on out of sight, so a later search silently misses things;
  - go back over old threads to re-read them.

- **Chips under the search box.** Wins if you want to see and flip a switch at a glance, on a phone as well. Costs one row of height. The words you type stay plain, which matters because they also drive title matching and highlighting.
- **Typed in the query.** Wins if you never want to leave the keyboard, and it is the same on every screen. Loses on a phone keyboard and has to be remembered. It could come later as shorthand that flips the chips.
- **A filter button with a menu.** Wins if a chip row crowds the phone. Loses because what is on hides behind a count.
- **Sub-thread rows.** One row per matching sub-thread under its top-level thread. Wins if you are after one particular sub-thread. _My pick._ Or one row per top-level thread naming its best sub-thread. Wins if several rows per workstream is the clutter you ruled out on 1 Oct. You try both.
- **Stopping the padding.** Drop results matched by meaning that are not close enough, with the cut-off set on the 57 test searches. Or keep them in their own "Related" group under the word matches. A spike decides.
- **Speed.** Show word matches at once and let rows matched by meaning join without moving the rows already shown. Wins if rows hold still; otherwise both arrive together as today.
- Dropped: wiring the October toggle as ruled, where sub-threads' text is read and only top-level threads are listed. It changed 1 first place in 57. <Sidenote>Pull 13 decision log, ranker test of 26 Oct. Every answer in that set is a top-level thread, so it understates the case.</Sidenote>
- Dropped: upstream's own search. Pull 16 re-checked it: it reads the messages of about 650 active top-level threads and nothing archived, no sub-thread and no report.

**Decided.** Your words, oldest first; the newest governs, and the first question asks where sub-threads now stand.

- 1 Oct, on sub-threads as results: "I can't imagine that I would *ever* want to find a sub-thread this way … enabling sub-threads to appear in the result is just going to clutter the result with things I'm not looking for."
- 26 Oct, on what you look for: "if I'm looking for something it's almost certainly something I've seen before: a root message or a report/plan I've read". The record of that ruling puts sub-thread content behind an "include sub-threads" toggle; that phrase is the runbook's, not yours.
- 26 Oct, on agents: "it's possible that when an agent uses the tool, it may get value from finding/searching sub-threads".
- 26 Oct, on ranking: "Loom hybrid, as it stands".
- 23 Nov: "all the stuff here that's trying to support "old" threads, or backport stuff to threads I'm never going to touch, is safe to drop".
- _Assumed:_ that last line covers documents too, so plans written before this ships are not gone back for. Redirect if wrong.
- _Assumed:_ the agents' search keeps reading sub-threads by default and gains the same switches as parameters, since it already has the project and archived ones. Redirect if wrong.
- _Assumed:_ a switch lasts while the search box is in use and returns to the default when you clear or close it, so a forgotten one never hides results. The sidebar's project picker keeps its own memory, as today.
- _Assumed:_ the short-word fix is folded in, as you allowed; it is one condition.
- _Assumed:_ nothing is built before upstream pull 16 merges. It rewrites the same Cmd+K, sidebar and phone files, and removes nothing this brief relies on.

**Not doing.** Changing how results are ranked, apart from that cut-off. Re-reading or back-filling old threads. Searching tool calls, command output or an agent's messages other than its last of each turn. The find box inside a thread. The title-only pickers (Link to thread on a pull request, a scheduled task's destination, `!` in the composer). A settings page for any of it.

**Still unknown.**

- How often search fails you, and on which kind of miss. Nothing counts searches. Counting them for two weeks after the first cut settles it: what was typed, on which screen, which switches were on, whether a result was opened.
- Whether switching sub-threads on puts the right sub-thread first. All 57 October test searches have a top-level thread as their answer; a dozen written from words that live only inside sub-threads settle it.
- How the server learns a plan exists. Documents are files in a project folder, signed with the session that wrote them, and nothing tells the server when one is written. A spike chooses between reading it when it is signed, when a thread links it, or by looking in `plans/`, `recaps/` and `explainers/`.
- Where the cut-off for matches by meaning sits. There is none today; the 57 test searches plus a handful of nonsense ones set it.
- Why three searches sent together each waited 2 s and came back without their matches by meaning. A timing run against Vertex settles whether it was a cold connection or a limit on parallel calls.
- Whether a chip row fits the phone's search field without pushing the first result off screen. Agents cannot run the phone app on this machine, so that check is yours.
