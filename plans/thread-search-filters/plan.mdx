# Thread search with three switches: sub-thread rows inside the thirty, a measured cut-off, one PR

Build the approved brief as **one PR in four layers**. The server's existing search gains three things. A result can carry up to **three sub-thread rows** under its top-level thread. The project filter applies **before** the cut to thirty rows. A result matched only by meaning is listed only when it is **close enough**. One shared filter state then drives a chip row in Cmd+K, the sidebar box and the phone's search, and the agents' `thread_search` gains one parameter. Nothing is migrated, re-indexed or re-ranked.

## 1. The four layers

A _top-level thread_ is one with no parent; a _sub-thread_ is any thread spawned under one. Search today returns one row per top-level thread, chosen by combining two rankings. A _word match_ means every word of the query appears in one piece of indexed text. A _match by meaning_ means the query's embedding is near the top-level thread's embedding, which Vertex computes on the cockpit. This plan does not change how the two are combined.

## 2. The result on the wire

This is the part contracts, both clients and the agent tool read, so it is settled first.

<Callout tone="decision" title="Sub-thread rows are nested inside their top-level row, and count against the thirty">
  A result stays one object per top-level thread, exactly as today. When the request asks for sub-thread rows, that object also carries `subThreads`: the sub-threads of that workstream with a word match of their own, best first, three at most. `subThreadsOmitted` says how many were held back. The server stops adding results when top-level rows plus sub-thread rows reach the limit, so a search never sends more than thirty rows.
</Callout>

  </Card>

    Each row would be the thread it opens, which reads simply. But `threadId` means "the top-level thread" in every client today. Grouping rows back under their parent would become each client's job, and the top-level thread's title, project and dates would repeat on every row.
  </Card>
</Columns>

**Which sub-threads qualify.** A sub-thread gets a row when one of its own pieces of text holds every word of the query, the last word as a prefix. Its pieces are its title, purpose, brief, messages and report. That is the rule a top-level thread's word match already follows. Matches by meaning produce top-level rows only, because the embedding is one vector per top-level thread. The Archived switch looks at the top-level thread: a workstream is in or out as a whole.

**The top-level row when sub-thread rows are present.** Its fields keep today's meaning, the best hit in scope, which under `scope: "all"` is often a sub-thread's text and so repeats the first sub-thread row. Clients draw the top-level row's own excerpt only when `matchedThreadId` is null, and otherwise show it as a heading over its sub-thread rows. Choosing the heading opens the top-level thread.

**Why three.** Two probes ran read-only against the live index on 24 Nov, using the search's own SQL with its grouping changed from per top-level thread to per thread.

**What "omitted" means.** The count comes from the same 1,000 best pieces of text the search reads today, so for a very broad query it is a floor. The clients word it "+N more sub-threads".

**Unfolding.** Choosing "+N more sub-threads" sends the same query with `rootThreadId`. The server answers with that one workstream and up to 29 sub-thread rows, skipping the embedding call, so it returns in word-match time. On the client it is a second call of the existing search hook with that one field added, and its rows replace the three in place. The number three is the constant `SUB_THREAD_ROWS` in `ThreadSearch.loom.ts`.

## 3. The cut-off for matches by meaning

Today the embedding side returns its 50 nearest top-level threads with no threshold, so a query with no word match anywhere still fills the list.

<Callout tone="decision" title="Listed by meaning alone: similarity of at least 0.62, and at least 0.06 above that query's average">
  A thread with no word match is listed only when both hold. _Similarity_ is the cosine between the query's vector and the thread's. The _average_ is the mean similarity of that query to every stored thread vector, taken before any filter. Threads with a word match are never cut, and the order of what remains is today's order with the cut rows removed. The rule and its two numbers are set per embedding model, in one table.
</Callout>

The two parts catch different failures. Gibberish sits unusually close to everything, so its nearest threads clear an absolute bar while standing barely above their own average. A real but off-topic query is far from everything, so one thread can stand well clear of the average while still low in absolute terms.

The chosen rule is the strictest one measured that loses no expected thread from the first ten. That is what the brief's must-not asks: the threads you find with no switch touched do not change, beyond the padding going. Each stricter rule buys a cleaner nonsense result at the price of a real thread.

**What it does not settle.** The figures are on today's whole corpus, which has grown from 781 top-level threads on 26 Oct to 1,030. The harness's pass marks use the frozen October corpus, so 22 and 40 are baselines for comparison, not its headline numbers. The two numbers were fitted on these 80 searches for one model, `vertex/gemini-embedding-001`. Any other embedding provider gets no cut-off until someone measures it, and behaves as today. Sixteen nonsense queries is a small set; two of them still list one or two rows, both arguably related ("Garbled response query" for gibberish).

**Dropped: a separate "Related" group.** The brief's alternative kept meaning-only rows under their own heading. Its check needs "No threads found" for a nonsense search, which needs a cut-off either way, and with one in place a second heading changes nothing about what is listed.

**Where it goes.** `ThreadEmbedder.nearest` already scores every vector; it additionally returns which of its 50 pass the rule for the active model (all of them when the model has no entry). `rank` in `ThreadSearch.loom.ts` votes exactly as today, then drops a thread that has neither a full word match nor a pass. The harness gains the nonsense set and prints both columns above, so the next model change has numbers to set.

**What a chip row costs.** Cmd+K's result area is 329 px tall at 1440 by 900 and shows about five rows; a chip row takes roughly one of them. **The project switch is fixed at the source.** Clients already put `projectIds` in the request, but only when asking for older settled threads, and the server strips it before the message search runs. **Short words.** Three places refuse to send a search with no word of three letters: `searchMessages` in `packages/client-runtime/src/state/threadSearch.ts` and `canSearch` in each app's `state/queries.ts`. The rule suits upstream's own index, which Loom does not use. Each becomes one marked line calling a Loom predicate that passes any query of two or more characters, the contract's minimum. A one- or two-letter word is matched whole, never as a prefix. The server already does that, because expanding so short a prefix is slow.

## 6. Speed

<Callout tone="decision" title="Results arrive together, as today; a switch flipped on an unchanged query answers in word-match time">
  The embedder keeps the last few dozen query vectors in memory. Flipping a chip re-sends the same words with a different filter, so it reuses the vector and skips the 0.45 s Vertex call. A fresh query costs what it costs today.
</Callout>

**Why not word matches first.** The brief's version has rows matched by meaning "join without moving the rows already shown". They would then have to sit below the word matches, which is a different order from the combined ranking Carl ruled stays as it is. It also means two responses per search: up to sixty rows over the socket, or a new protocol for sending only the difference. And the part that feels instant already is. Title matches are ranked on the client and appear with each keystroke; only "In messages" waits.

**What the build is held to.** The harness prints wall-time percentiles for the search; run on the same database copy before and after, the median and 90th percentile may not rise by more than a tenth. On the cockpit the word-match step measured 49 ms at the median and 108 ms at the 90th percentile over 67 searches. With sub-thread grouping it measured the same within a millisecond. Four agent searches traced on 24 Nov took 447 to 604 ms end to end.

**The 2-second searches were not reproduced.** The brief records three searches sent together that each waited the 2 s limit and came back with word matches only. That batch was also the first search after a long idle, so "together" and "first" were never separated.

What is left is a transient: a slow answer from Vertex, a busy server, or a rate-limit reply. The Vertex adapter retries a rate-limit reply after a full second, which cannot finish inside the limit. Today a timeout logs nothing, which is why nobody could say. The build adds one warning per outage when the limit fires, with the elapsed time. The cause stays unknown until it recurs with that line in the log.

## 7. The agents' tool

`thread_search` gains `includeSubThreads` (default true, as the brief assumes; false reads top-level threads' own text and every report only), beside `projectId` and `includeArchived`, which it already has. Its handler maps false to `scope: "roots"`. It does not send `subThreadRows`, so `limit` still counts top-level threads and its output is unchanged, line for line.

A new parameter is model-facing text. The coder loads the `llm-instruction-change` skill, where a new field counts as a rule change, and follows `evals/README.md`. That means running the `mcp-tool-use` cases that involve `thread_search` on the old and new definitions before the PR merges. The parameter's description says what to pass and what an omitted value does. The tool's main description is not reworded.

## 10. Where this tightens the brief, risks, and what is carried forward

**Tightened, not reopened.**

- **One project in Cmd+K** is the project of the thread you have open, the reading the brief's own picture ("This project") gives. Any other project is the sidebar's picker.
- **"Opens that sub-thread at its report"** is built as the sub-thread with its report document open in the right panel on web and desktop. On the phone it opens the sub-thread.
- **The nonsense check** passes with any three words no thread holds, for the reason above.
- **Thirty rows includes sub-thread rows.** With Sub-threads on and a broad query that is about eight top-level threads a search. It follows from the brief's must-not; the lever, if it feels thin in use, is the number three.
- **A sub-thread row needs a word match.** A top-level thread found only by meaning shows no sub-thread rows.

**Risks.**

- **The cut-off is fitted to one model and 80 searches.** It lives in one table keyed by model, the harness prints what a refit needs, and a model with no entry behaves as today.
- **Upstream files.** `Sidebar.tsx`, the three `CommandPalette*` files and four phone files are rewritten by upstream at most pulls. Logic stays in Loom files and the shared state; what lands in upstream files is state, one mount line and a map over rows, each marked.
- **Find in a sub-thread opened cold.** Find at a message works today for a top-level thread already in the client's list. For a sub-thread whose rows arrive after navigation it relies on the find store's existing wait for the timeline. The live pass checks one. The fallback is to open without find, as archived threads do.
- **Helper threads under Archived.** Document-query threads ("Query: recap.mdx") are archived by Loom itself and turn up often among matches by meaning. With Archived on they are listed, as the brief reads. One condition removes them if Carl finds them noise.
- **Without embeddings.** When the embedding call times out, or no provider is set, search lists partial word matches as it does today. A nonsense search can then show a row for one matching word.
