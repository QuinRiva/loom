# Pull 9 Phase 3 — Loom's layer on V2, in four parallel tracks

Loom is a Pi-first fork of `pingdotgg/t3code` whose product is an orchestration layer: goals, a shared task tree, and a workstream graph of durable threads with roles, briefs, dependencies, review gates, attention flags, liveness and reports. The signed strategy (`plans/upstream-pull9-strategy/plan.mdx`, revision 3) re-platforms that layer onto upstream's Orchestration V2. Phase 1 (the mechanical merge) leaves V2 Loom booting with the workstream layer absent; Phase 2 (`plans/upstream-pull9-phase2-substrate/plan.mdx`) builds the substrate it attaches to — the sidecar contract, the decider arm under per-thread locking, the dispatch modes, `LoomStoreV2`, the re-drive planner, migrations 1046–1048, the quiescence predicate. **Phase 3 is everything that makes the layer work end to end on that substrate**, built as four tracks by parallel coders under one Phase 3 orchestrator: **3a** the agent tool surface and every text that names a tool; **3b** the control plane; **3c** the Pi adapter's economics; **3d** the web. The tracks meet at an integration reviewer and a real Pi workstream smoke test.

This document is one plan with a shared front section and four track sections. **The front section is the integration contract**: every interface two tracks share, who owns it, its shape, which track lands it first and what the other stubs until then — so the four coders can build without re-deciding anything. **Done** for Phase 3 means: the integration smoke scenario below passes on a copied database with the dev-verify recipe; `vp check` and `vp run typecheck` are green on the integration branch; every hunk in an upstream file carries a `// loom:` marker and appears in the amended hunk inventory; the name sweep's gate passes; and the Phase 4 obligations at the end are met.

### Capabilities and the withhold

Two marked hunks and one literal. `McpInvocationContext.ALL_MCP_CAPABILITIES` gains `"workstream"`. `McpSessionRegistry.issue` stops force-adding `orchestration`, `worktree` and `pull-requests` and issues exactly `request.capabilities` (plus `preview` when browser tools are allowed and the request names nothing). `ProviderSessionManager.prepareMcpSession` builds `["workstream", "pull-requests"]` (+ `preview`, `device` per settings). ### `forkFrom` children — the session fork

`forkFrom` keeps V1's meaning: it names an **active sibling** (the reader in acknowledge-then-fork), and the spawn handler / `thread.spawn` implicitly appends the source to the child's `blockedBy` — so the fork does not start until the source is `done`, exactly as today (`WorkstreamSpawnHttp.ts:1296–1330`). Reader and forks are spawned together; nothing about the source is checked at spawn beyond "a live sibling". Phase 2's `thread.spawn` nests `thread.created` with `subagent` lineage and `forkedFrom: null` (its D7) and never calls `thread.fork`; the open-session field carries no fork member (P3-23). The native session fork therefore comes from the mechanism upstream already resolves at a thread's first run — **a pending `fork` context transfer targeting the child** — written **at promotion**, when the source has finished:

- **A new Loom command, `thread.fork.prepare`** (contract delta in 3a-0; arm case in `Orchestrator.loom.ts`; `threadId` = the child, so it writes only to the commanded thread). It reads the source's projection (`runs`, `providerThreads`); takes the source's latest provider-finished run as the canonical `latest_stable` `sourcePoint`; **refuses** (receipted, permanent) when the source's provider thread has no strong `nativeThreadRef` — today's "refuse loudly when no identity record exists" — or when the child already has a pending or consumed fork transfer; **defers** with `LoomDispatchDeferredError` when the source's latest run is still blocking (`preparing | starting | running | waiting`); otherwise emits `context-transfer.created` on the child in exactly the shape `ThreadForkService.plan` builds (`ThreadForkService.ts:116–136`): `type: "fork"`, `sourceThreadId`, `targetThreadId: child`, `sourcePoint`, `basePoint: null`, `sourceProviderInstanceId` = the run's, `status: "pending"`, `error: null`. This is the third legitimate `LoomDispatchDeferredError` site (Phase 2's D15 listed two); it satisfies the confinement rule — the same command succeeds later without anyone changing the target.
- **Promotion (3b) issues it before the kickoff.** When `isEligibleToStart` holds for a child whose sidecar has `forkFromThreadId` (its dependencies are done, so the source is done), the dispatcher first dispatches `thread.fork.prepare` with the deterministic id `server:loom:fork-prepare:<childId>`; a deferral leaves the child for the next pass; a rejection is surfaced to the parent as a dead-episode digest item; on success (or an existing receipt) the kickoff follows in the same pass. At the kickoff's run start, `pendingForkTransferForThread` (`Orchestrator.ts:632–641`, lineage-agnostic) finds the transfer and `decideForkExecution` / `ensureNativeFork` run the adapter's `forkThread` (a throwaway `pi --fork <source file>` in the child's cwd, registering the new file as the child's `nativeThreadRef`).
- **Lineage.** `thread.created` keeps `subagent` lineage and `forkedFrom: null` — `forkedFrom` is read by `appOwnedSubagentParentThreadId` and the Lineage panel's provenance, not by the fork resolution; the panel shows the fork edge from the transfer (3d confirms it renders; if not, nothing is lost but a badge). No chain resolution: a `forkFrom` of a `forkFrom` child forks that child's final session, as V1 did.
- **Cache prefix.** The composer replays the source's identity (prompt, skills, extensions, model, tool profile) and the fork carries the source's final transcript, so the first request's prefix is byte-identical across every fork of one source — the property acknowledge-then-fork exists for.

### Wake tiers, ids and modes

### The quiescence rail

Candidates come from Phase 2's `quiescenceCandidate` over the joined shell, the thread's runs and messages, its children, and two settings (`loom.quiescenceGraceMs`, default 600,000; `loom.quiescenceHumanGraceMs`, default null = never for a human-started turn) under `packages/contracts/src/settings.loom.ts`. > The control plane wrote this file from its last assistant message after <grace> of silence
> and yielded it to the parent. Nothing below was written as a hand-back.

then dispatch `thread.work.submit { reportPath, outcome: "quiescent" }`. ### Liveness

`classifyLiveness` and the stall ladder port unchanged in logic. Inputs under V2: *dead* = the thread's provider session has read `error` for `failureCap` consecutive sweeps (shell `lastErrorClass` non-null and the latest run `failed`, excluding `usage_limit` which belongs to 3c); *waiting* = `shell.pendingRuntimeRequest` is one of the approval kinds (`command`, `file-read`, `file-change`, `mcp-elicitation`, `permission`, `dynamic_tool_call`, `auth_refresh` — there is no kind named `approval`; `user_input` is a question and is not exempt, as today); *stall* = `activityRunStatus` running, no in-flight tool, heartbeat frozen past `staleActivityWindowMs` (10 min), after the 2-minute startup grace; *spinning* (State D) = heartbeat advancing, work-product fingerprint over the last N tool items flat for `noProgressWindowMs`. **The heartbeat advances on `turn-item.updated` for the thread**, which is how a tool call that prints periodically (today's heartbeat pattern — a `sleep 60 && echo` loop, or a long test run) stays alive: each output chunk is a turn-item update, and `hasInFlightTool` suppresses State C entirely while the tool runs. A stall nudge is one steered control message per frozen episode; escalation raises `error` with a `server:` id and wakes the parent through the attention rail. State D stays behind its one boolean.

### Park-and-resume on upstream's mechanism

Upstream already has what Carl asked for in the common case: a run that fails with `class: "usage_limit"` and a `resetAt` arms `thread.limitRecovery`; `UsageLimitRecoveryWorker` dispatches a resume when the window passes if `autoResumeLimitedThreads` is on (`UsageLimitRecoveryWorker.ts:12–71`); the web shows `UsageLimitRecoveryBanner`. Loom's V1 adapter did the same with its own sweep. Under the doctrine, upstream's is the baseline: the adapter hunk's job is to make pi's quota errors *look like* a `usage_limit` failure with a reset time, which pi's error text often lacks — so `classifyPiFailure` fills `resetAt` from Loom's `ProviderHealthRegistry` account window (the pollers Phase 1 kept) or a `Retry-After`. Loom's build defaults `autoResumeLimitedThreads` to `true`. What Loom still owns because upstream cannot do it: the **cross-vendor reroute** (a healthy fallback of another vendor before the window resets), the **move back** once the intended account is healthy and the thread is idle, and the rare **no-reset-time** resume off the registry's mark. All three live in `RerouteSweep.ts`. The resume message is a Loom control message (`origin: control_notice`, `queue_after_active` — the target is idle), never `createdBy: user`, so no hold is erased; seam 14 protects holds from upstream's own `limit-resume` message as well.

**Re-anchored on `agent_settled`.** V1 classified errors in its `agent_end` handler mid-turn-loop. Under V2 the classification happens where upstream already builds `turn.failure` (`PiAdapterV2.ts:1611–1620` and the `extension_error` path) and the failure is emitted at `finalizeTurn` on `agent_settled`. Nothing else of V1's turn loop comes across: no T3-level retry tier (`piTurnRetryPolicy.ts` stays quarantined — pi's own `retry.*` settings and the proxy's rotation stand in), no backend fallback mid-turn, no pause.

## Phase 4 obligations

What the importer and the QA instance will need from Phase 3, stated so Phase 4's planner can rely on it.

- **Report paths.** `<serverConfig.workstreamReportsDir>/<threadId>.md`, `.round-<n>.md` for gate rounds, `.quiescent-<runId>.md` for synthesised reports; `reportPath` on the sidecar is the latest. The importer copies V1 `report_path` as is (same directory).
- **Attention reasons** are exactly Phase 2's four stored values; `awaiting_orchestrator` is added for a V1 `yielded` lane. Nothing in Phase 3 adds a stored reason.
- **Lineage re-emit.** Phase 2 §5 requires the importer to re-emit each child's thread row with `subagent` lineage; Phase 3's web filters and rollups read `lineage.parentThreadId`, so an imported child without it would surface as a root. Phase 4 must do this before the board is trusted.
- **Episode columns stay null** on imported rows (Phase 2); the dispatcher's digest and yield rails key on `lastOutcome.eventId` / `outcomeEventId` and so stay silent for history. The first pass after import must send no kickoff: every imported thread with a transcript carries `kickoffAt`.
- **Usage ledger** rows travel by the 1049 rename; no import step. `loom_thread_reroute` starts empty.
- **`loom.humanAuthored` on imported messages.** V2's importer copies messages without Loom fields, so an imported root a human had been talking to would read as not human-engaged and its idle children's quiescence would use the control grace. The Loom importer stamps `loom.humanAuthored: true` onto every imported user-role message whose V1 `origin` was `human` (the copied `projection_thread_messages.origin` column), by re-emitting `message.updated` with the full payload.
- **Session binding** (`importedNativeThread` with the `*_<threadId>.jsonl` path) is what `consult_thread`, the sanitiser and the stall context resolve through; the Phase 4 remember-check covers it.
- **The subscribe flag.** The QA web client passes `loom: true`; a store mobile app pointed at the QA instance must show threads without errors — that is the mobile check for pull 9.
- **The name sweep** must have run before QA, so that imported live orchestrators (whose system prompts were composed with bare names) are re-launched with the new addendum on their first continuation; their in-transcript bare names are history and harmless.
- **Stored `thinkingLevel` selections.** 3a's `modelSelection.ts` emits upstream's `thinking` option id for new selections; imported threads carry V1's `thinkingLevel` in their `modelSelection.options`, and the importer maps it to `thinking` (ladder values clamp to pi's per-model set) — a data step on upstream's projection rows that belongs to the importer, not a 1001+ migration.
- **Settings** the QA instance needs on: `continueThreadsAfterServerUpdate` (Phase 2 default), `autoResumeLimitedThreads` (3c default), the quiescence grace defaults.

**Risks.** (1) *The driver work item.* It is the Phase 2 orchestrator's; if it slips, 3c waits and 3a's composer lands behind a default layer — the smoke cannot run until both exist, and nothing in Phase 3 may absorb it without a new ruling.
