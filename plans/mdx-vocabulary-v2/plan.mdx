## 2. The shared palette and two helpers

Three things every package depends on, landed first by package A.

**One tone palette.** `Card`'s six categorical tones are the palette for every new surface — `Badge`, `Stats`, `Steps`, `Table` rows and cells, `Mermaid` node classes — exported from a new `apps/web/src/components/files/mdx-plan/tones.ts` as the zod enum `toneSchema`, the `Tone` type, and a `BadgeSpec` shape (`string | { label, tone? }`) that `Card.badges`, `Step.badge`, `Stats` items and `Table` cells all reuse, so "a badge" is written the same way everywhere. `Callout` keeps its own five status tones (`info | decision | risk | warning | success`); they are a wire contract used by every existing document and they mean status, not category.

**CSS variables, not Tailwind classes, for the new surfaces.** `index.css` gains `--plan-tone-<name>` and `--plan-tone-<name>-soft` for the six tones under `:root` and `.dark`, derived from the colours `Card` already uses (blue, emerald, amber, red, violet, and the muted grey). The new blocks style with plain classes (`.plan-badge--risk { color: var(--plan-tone-risk); background: var(--plan-tone-risk-soft) }`), which is what lets the same variables reach Mermaid's SVG `<style>` and the `HtmlBlock` iframe (§3.6, §3.9) — a Tailwind class cannot cross either boundary. `Card` keeps its Tailwind maps; nothing existing is restyled.

**An inline-markdown helper.** `apps/web/src/components/files/mdx-plan/inlineMarkdown.tsx` exports `InlineMarkdown({ text })`: one module-level `unified().use(remarkParse).use(remarkGfm)` processor parses the string, and the component renders the first paragraph's inline children — text, `strong`, `emphasis`, `inlineCode`, `delete`, `link`, `break` — as React, memoised on the string. Anything else (an `html` node, an image, a second paragraph) renders as its text. No HTML, no JSX, no second markdown library: it reuses the parser the linter already imports. `Table` cells, `Stats` details and `Step` asides are the string props that become inline markdown.

<Callout tone="info">
  **Why a cell string cannot hold a Badge tag.** A string attribute is never parsed as MDX, so `"<Badge>lost</Badge>"` inside `rows` would render as literal text. That is why the string props that want a pill take a `badge` field beside the markdown instead, and why `Badge` as an inline *tag* is for prose: sentences, list items, `Callout` and `Card` bodies, `Step` bodies.
</Callout>

## 3. The contracts

Each block: the props with their zod shape, how it renders, what lint says, the vocabulary entry, and the doctrine line that tells an author when to reach for it. Existing props are unchanged unless named.

### 3.1 `Badge` — an inline pill

The one device every HTML page leans on hardest. An `mdxJsxTextElement`: it lives inside a paragraph, a list item, a heading, a `Card` or `Callout` body. The label is the prose between the tags.

```ts
// blocks/badge.tsx
const badgeSchema = z.object({ tone: toneSchema.optional() });
mdx: { tag: "Badge", passChildren: true }
```

- **Renders** `<span class="plan-badge plan-badge--{tone}">` — mono, 0.6875rem, weight 600, uppercase via `text-transform`, letter-spacing 0.06em, `padding: 0.1em 0.55em`, `border-radius: 999px`, `white-space: nowrap`, `vertical-align: middle`. The tone colours come from the variables in §2; default `neutral`. It carries **no** `data-plan-block-type` and no block id: it is text, so the annotation layer treats a selection through it as prose and `assignBlockIds` never stamps it. A `Badge` written alone on a line parses as a flow element and takes a top-level block id like any paragraph would — harmless, and the vocabulary says to put it in a sentence.
- **Lint.** None beyond the registry checks. (A tone outside the enum is already a schema error.)
- **Vocabulary entry.** *`<Badge tone>` — an inline pill for a state, class or verdict inside a sentence, list item, table cell object or card body: `<Badge tone="risk">lost</Badge>`. Six tones; the text names the meaning, the colour makes it scannable. For a pill in a `Table` cell or a `Card` header use the `badge` fields there — a string attribute is never parsed for tags.*
- **Doctrine line** (§3 of `document-quality.md`, the "judgement rides the block" bullet): *a state or verdict that recurs through the document — `in place`, `moot`, `lost`; `OURS`, `THEIRS` — is a `<Badge>` the first time and every time, so the reader learns the colour once and finds every occurrence by eye.*

### 3.2 `Card` — eyebrow and multi-tone badges

Two optional props on the existing block.

```ts
eyebrow: z.string().trim().max(40).optional(),
badges: z.array(badgeSpecSchema).max(6).optional(),   // string | { label, tone? }
```

- **Renders.** `eyebrow` sits above the heading as a mono uppercase line (0.6875rem, letter-spacing 0.1em) in the card's tone text colour — for a `neutral` card the `accent` tone, which is what gives the HTML's gold `RULE 1` its lift. `badges` render after the existing `badge` in the header row; a string entry takes the card's tone, an object its own. `badge` stays as the one-pill shorthand.
- **Lint.** None new. The generated `block-schema.md` needs `blockSchemaDoc.ts` to render a union of object alternatives (today `typeLabel` prints `string | object` with no sub-shape); package A adds that so `badges`, and later `Table` cells, document themselves.
- **Vocabulary entry addition.** *`eyebrow` is the small line above the heading — `RULE 1`, `OPTION B`, `STAGE 3` — for a numbered or classified series of cards. `badges` is a list of pills with their own tones when the card's single `badge` is not enough: `badges={[{ "label": "deterministic", "tone": "success" }, "x3 calls"]}`.*

### 3.3 `Columns` — cards as direct children

The explainer skill already prescribes `<Columns>` of `<Card>`s (goal task 8db9454f), and the CSS grid already lays any direct child out as a cell; only the lint rule `EXPECTED_CHILDREN.Columns = ["Column"]` says otherwise. One optional prop and a lint relaxation:

```ts
columns: z.number().int().min(2).max(6).optional(),   // the most columns to lay out
```

- **Renders.** `.plan-columns` keeps `repeat(auto-fit, minmax(min(240px, 100%), 1fr))`; with `columns={n}` the min track becomes `max(240px, calc((100% - (n - 1) * gap) / n))`, so the grid never shows more than *n* across and still collapses on a narrow panel. Direct block children lose their `my-4` inside the grid (`.plan-columns > [data-plan-block-type] { margin-block: 0 }`), so a card row has no vertical slop.
- **Lint.** `EXPECTED_CHILDREN.Columns` becomes: a direct child is either a `Column` or any registered block; warn only when the two are mixed in one `Columns` (a labelled slot beside a bare card renders at different heights). `REQUIRED_PARENT.Column` is unchanged.
- **Vocabulary entry addition.** *A `<Columns>` of `<Card>`s needs no `<Column>` wrappers: cards are columns. Use `<Column label>` when a side needs a label or holds several blocks. `columns={3}` caps the row at three across.*

### 3.4 `Stats` — the number strip

```ts
const statSchema = z.object({
  value: z.string().trim().min(1).max(24),
  label: z.string().trim().min(1).max(80),
  detail: z.string().trim().max(300).optional(),      // inline markdown
  tone: toneSchema.optional(),
  badge: badgeSpecSchema.optional(),
});
const statsSchema = z.object({ items: z.array(statSchema).min(1).max(8) });
```

- **Renders** `<div data-plan-block-type="stats" class="plan-stats">` of tiles: `value` at 2rem, weight 700, `tabular-nums`, in the tone colour (`neutral` → foreground); `label` mono uppercase 0.6875rem muted; `detail` 0.8125rem muted through `InlineMarkdown`; `badge` after the detail. Grid `repeat(auto-fit, minmax(min(11rem, 100%), 1fr))`, gap 0.875rem; each tile `bg-card`, 1px border, radius 0.625rem. **Bleed mode `stretch`** in `BLEED_MODE_BY_BLOCK_TYPE` — a strip of short tiles has no useful max-content, so it takes the budget outright and the tiles share it; that is what makes four tiles sit on one line in the panel. Each tile's text is distinctive, so a text-quote annotation pins to one tile.
- **Lint.** None new; `max(8)` is the schema's own guard (nine tiles wrap into two uneven rows).
- **Vocabulary entry.** *`<Stats items>` — the numbers the answer rests on, as large tiles under the lede: `{ value, label, detail?, tone?, badge? }`. Three to six tiles; `value` is the headline figure (`43 min`, `3 of 4`), `label` names it, `detail` is the one line that makes it mean something.*
- **Doctrine line** (§2, the first screen): *when the answer has numbers — a count, a duration, a share — the lede states them and a `<Stats>` strip right under it shows them, one tile per number, toned by what the number means.*

### 3.5 `Steps` / `Step` — the rail

A container and a slot, on the `Columns`/`Column` pattern: each step's body is MDX prose (so inline `Badge`, code and lists all work), the chrome is props.

```ts
// Steps: no props (container, passChildren)
const stepSchema = z.object({
  at: z.string().trim().max(40).optional(),            // the left column: a time, a number, a stage name; never wraps
  title: z.string().trim().max(200).optional(),        // the bold first line of the body
  tone: toneSchema.optional(),                         // colours the marker and the `at` label; default info
  dashed: z.boolean().optional(),                      // hollow dashed marker: nothing happened, dropped, ghost
  badge: badgeSpecSchema.optional(),                   // first line of the aside; a string takes the step's tone
  aside: z.string().trim().max(400).optional(),        // inline markdown under the badge
});
```

- **Renders** `<section data-plan-block-type="steps" class="plan-steps">` with a 2px rail (`::before`, `var(--border)`) and one `<div class="plan-step">` per child. The container is the grid and each step is `display: contents`, so the `at` column lines up down the whole rail: `grid-template-columns: minmax(5.5rem, max-content) minmax(0, 1fr)`, and `.plan-steps:has(.plan-step-aside)` adds a third track `minmax(0, 15rem)` — a container cannot read its children's props (they arrive as React nodes), and `:has()` needs no introspection; a steps block with no asides stays two-column. The marker is a 12px circle on the rail: ring in the tone colour by default, filled when `tone` is `risk` or `warning` (the HTML fills the bad moment), dashed ring when `dashed`. `at` is mono 0.75rem muted with `white-space: nowrap` — the wrapping of *12:36 → 13:16* was half of why the table did not read as a timeline. When every step omits `at`, the marker carries the step number instead. `title` renders bold as the body's first line; the body is `prose-plan` at 0.9375rem. Not bled: a prose-bearing block keeps the measure, as `Card` does; three columns inside the measure give the body ~28rem, the HTML's own proportion.
- **Lint.** `REQUIRED_PARENT.Step = ["Steps"]`, `EXPECTED_CHILDREN.Steps = ["Step"]` — the same two tables `Column` and `Tab` use.
- **Vocabulary entry.** *`<Steps>` of `<Step at title tone dashed badge aside>` — moments or stages in order on a rail: a timeline when `at` is a time, a ladder when it is a stage, numbered when it is omitted. The body between the tags is the detail; `aside` is the right-hand column for what someone saw or what it cost.*
- **Doctrine line** (§4 table, new row): *A sequence in time or in stages — a timeline, a ladder of options, a pipeline's steps: `<Steps>`, one `<Step>` per moment, tone on the ones that went wrong.* And one sentence beside it: *a table of times is not a timeline; a reader scans a rail, not a column of wrapped timestamps.*
- **Deferred:** `orientation="horizontal"` (the left-to-right pipeline the document-classification port wants three times). The vertical rail is the acceptance test; the horizontal form's hard part is what six stages do at the reading measure, which needs a document in hand to tune. Bottom form.

### 3.6 `Table` — markdown cells, badges, tones, alignment

```ts
const cellSchema = z.union([
  z.string(),                                            // inline markdown
  z.object({
    md: z.string().optional(),                           // inline markdown
    badge: badgeSpecSchema.optional(),                   // a pill before the text; a string takes the cell's tone, else neutral
    tone: toneSchema.optional(),                         // tints this cell
  }),
]);
const rowSchema = z.union([
  z.array(cellSchema),
  z.object({ tone: toneSchema.optional(), cells: z.array(cellSchema) }),   // tints the whole row
]);
const tableSchema = z.object({
  columns: z.array(z.string()),
  rows: z.array(rowSchema),
  align: z.array(z.enum(["left", "center", "right"])).optional(),
  density: …, filterable: …                              // unchanged
});
```

- **Renders.** Every cell goes through `InlineMarkdown`, so `**bold**`, `` `code` ``, `*italic*`, `~~struck~~` and links work in a cell for the first time — today they render as literal characters. A row tone sets `background: var(--plan-tone-{tone}-soft)` on its cells; a cell tone does the same for one cell. A badge renders as the same `.plan-badge` span the inline block uses, before the text, `white-space: nowrap` on that cell so the pill and its word stay on one line. `align[i]` sets `text-align` on column *i* (header and cells); omitted columns stay left. Filter and sort use a `cellText(cell)` that joins badge label and markdown source, so `filterable` keeps working with no visible change. Bleed stays `hug`.
- **GFM tables** (`| a | b |` in prose) get two of the same defaults without a prop: `stampBleedingBlocks` treats a top-level `<table>` as `hug`, and the `.plan-mdx table` header row gets the block's muted fill. They do not get tones or badges — reach for the block for those; the doctrine says which is which.
- **Lint.** The ragged-row check reads `cells` from a row object; a cell object with neither `md` nor `badge` warns (it renders empty); an `align` array whose length is not `columns.length` warns (extra entries ignored, missing ones default). The row/cell union needs the `blockSchemaDoc.ts` union rendering from package A to document itself.
- **Vocabulary entry** (replaces the current paragraph). *Cells are inline markdown — bold, code, links work. A cell can be an object `{ "md", "badge", "tone" }` to carry a pill or a tint, and a row can be `{ "tone", "cells": […] }` to tint the whole row — so a status column is a column of pills and the one row that matters is found before the table is read. `align` sets per-column alignment (`"right"` for numbers). A GFM table in prose is fine for a quick grid; use the block for tones, badges, density or a filter.*
- **Doctrine line** (§3, judgement bullet, after the Badge sentence): *in a table, that state is a badge cell and the rows that need finding carry a tone — a reader should locate the lost item by colour before reading a word of the table.*

### 3.7 `Callout` — title and focus

```ts
title: z.string().trim().max(120).optional(),   // replaces the fixed tone label ("Note", "Warning")
focus: z.boolean().optional(),                  // the document's one box of emphasis
```

- **Renders.** `title` replaces the tone's label text in the existing small uppercase line; the icon and frame are unchanged, so an untitled callout looks exactly as it does today. With `focus`: no icon; a 4px left border in the tone colour on a `bg-card` surface instead of the tinted frame; the title at 0.8125rem mono uppercase in the tone colour; the body at 1rem (reading size — today's `text-sm` is one reason the "what it means now" paragraph read as an aside); margin `1.5rem 0`. A paragraph of `Badge`s inside renders as a pill row because badges are inline and wrap.
- **Lint.** None new.
- **Vocabulary entry addition.** *`title` names the box (`What it means now`, `The causal proof`, `The one thing to act on`) in place of the tone's generic label. `focus` is for the one box the reader must not pass — the verdict or the thing to act on — rendered as a bordered panel at reading size; one or two per document, or the emphasis is gone.*
- **Doctrine line** (§2, "what it means for them"): *the consequence paragraph is a `<Callout focus title="What it means now">` directly under the lede or the stats, not a bold run-in inside the lede — a run-in is read as part of the summary, a titled box is read as the section it is.*

### 3.8 `Mermaid` — clean look, node tones, legend

```ts
look: z.enum(["classic", "handDrawn"]).optional(),       // default classic
legend: z.array(z.object({ tone: toneSchema, label: z.string().trim().min(1).max(80) })).max(6).optional(),
```

- **Why `handDrawn` was the default and why it changes.** The July port chose `look: "handDrawn"` as the slimmer stand-in for BuilderIO's Excalidraw sketch conversion — a wireframe aesthetic, not a readability choice (`mermaid.tsx` header comment, commit 2cd3595dd9). `classic` is Mermaid's own default; it renders crisp strokes and text, and nothing in the security posture depends on the look (`securityLevel: "strict"`, `htmlLabels: false` and the SVG sanitiser are unchanged). `handDrawn` stays as an opt-in for a diagram that should read as a sketch.
- **Node tones.** `renderMermaidSvg` passes a `themeCSS` string with six rules of the form `.tone-risk > rect, .tone-risk > polygon, .tone-risk > circle, .tone-risk > path { fill: var(--plan-tone-risk-soft); stroke: var(--plan-tone-risk) }` plus a label colour rule. Authors attach a class with Mermaid's own syntax — `W["writer"]:::tone-warning` or `class W,C tone-neutral` — nothing new to learn and no `classDef` hexes to invent. The SVG is injected inline into the document, so `var(--plan-tone-*)` resolves from the app's `:root`/`.dark` and the diagram flips theme without a re-render; the `--out` render page inlines the same stylesheet. Edges keep Mermaid's `linkStyle n stroke:…`: the vocabulary names the one hex per tone to use (`#e5484d` for risk is already in the recap) so authors stop guessing.
- **Legend.** Renders under the figure, above the caption, as a row of `.plan-badge` swatches with their labels.
- **Lint.** A `:::tone-x` or `class … tone-x` whose `x` is not one of the six tones warns (the class silently styles nothing).
- **Vocabulary entry addition.** *Colour a node by meaning with `:::tone-success` / `:::tone-risk` / … (the shared six-tone palette); `legend` decodes the colours once under the figure. The default look is clean; `look="handDrawn"` for a sketch. Keep an edge's colour to the palette hexes listed in `block-schema.md`'s preamble.*
- **Doctrine line** (§4, the diagram distinction): *tone the two or three nodes the reader should look at first and leave the rest neutral — a graph where every node is the same grey makes the reader search; a graph where every node is coloured does the same.*

### 3.9 `HtmlBlock` — auto-height and app theme

The escape hatch, made cheap to use well. Accepted earlier; two changes, no new props.

- **Auto-height.** `height` becomes optional-as-override: when omitted, the frame measures itself. The frame is same-origin (`allow-same-origin`, no scripts), so the host reads `contentDocument.documentElement.scrollHeight` on `load` and sets the iframe height, then attaches a `ResizeObserver` to the frame's `body` so a panel-width change reflows it. Bounds 48–4000px. The default `240` goes; a `height` given explicitly is honoured as today (for a frame that should scroll). `Prototype` keeps its explicit height — its origin is opaque and cannot be measured.
- **Theme.** `buildSrcDoc` injects, for both surfaces, a `:root` block carrying `color-scheme` and the app's `--background`, `--foreground`, `--card`, `--muted`, `--muted-foreground`, `--border` plus the six `--plan-tone-*` pairs, read from `getComputedStyle(document.documentElement)` at build time, and mirrors the host's `dark` class onto the srcdoc `<html>`; `body` gets `background: var(--background); color: var(--foreground)` and the app's font stack. `srcDoc` is memoised on the resolved theme (`useTheme`), so a theme flip reloads the frame with the new values. The iframe's `bg-white` becomes `bg-background`. A snippet written against `var(--plan-tone-risk)` then matches the document around it in both themes.
- **Lint.** None new.
- **Vocabulary entry addition.** *The frame sizes itself to its content; give `height` only when it should scroll. Write its CSS against the app's variables — `var(--foreground)`, `var(--border)`, `var(--plan-tone-risk)` — and it follows the theme.*

### 3.10 Raw lowercase HTML — the allow-list guard

`remarkUnknownBlockFallback` leaves lowercase tags to MDX, so `<style>` sheets that restyle the app, `position: fixed` overlays and a remote `<iframe>` all lint clean and render today (confirmed by probes in the capability report). No document in `plans/`, `recaps/` or `explainers/` uses a lowercase tag outside a string attribute, so closing the path breaks nothing.

- **Guard** (`mdxCompileOptions.ts`, the same remark pass; the allow-list lives beside the tag set in `planBlockTags.ts` because the worker imports no React): a lowercase `mdxJsxFlowElement`/`mdxJsxTextElement` whose name is not in `{ span, mark, kbd, sub, sup, small, br }` is rewritten to `UnknownPlanBlock` with its `tag` preserved; an allowed tag has every attribute stripped. `UnknownPlanBlock`'s message branches on case: *Raw HTML `<div>` is not rendered — pills are `<Badge>`, grids are `<Columns>`/`<Card>`, a bespoke figure is `<HtmlBlock>`.*
- **Lint** (`planLint.ts`): the same test as an `error` with the same wording; stripped attributes a `warning`.
- **Doctrine.** The contract paragraph in `block-vocabulary.md` adds one sentence: *a handful of unstyled inline HTML tags (`span`, `mark`, `kbd`, `sub`, `sup`, `small`, `br`) pass through; anything else lowercase is rejected — pills come from `<Badge>`.*

### 3.11 Kicker — frontmatter, rendered above the title

- **Pipeline.** A small remark plugin `remarkKicker` in `PLAN_REMARK_PLUGINS` (beside `remarkHeadingAnchors`, not in the guard set the section peek uses) reads the leading `yaml` node, and when it carries a non-empty `kicker` string inserts a `paragraph` node with `data.hProperties.className = "plan-kicker"` immediately after the frontmatter. The reader-brief lint already parses that YAML; the plugin reuses the same decode.
- **Renders.** `.plan-mdx .plan-kicker`: mono 0.6875rem, uppercase, letter-spacing 0.12em, in the `accent` tone colour, `margin-bottom: 0.5rem`; `.plan-kicker + h1 { margin-top: 0 }` so the title keeps its position. The kicker becomes the document's first top-level block, so a document that *adds* a kicker after being annotated shifts its fallback `plan-block-N` anchors by one — the same thing any added paragraph does, and authored block ids are unaffected.
- **Lint.** None (an empty or non-string `kicker` is ignored).
- **Vocabulary entry** (a new "Frontmatter" paragraph under the contract): *`kicker:` is the small line above the title — genre, subject, date, the PR — `Incident recap · #280 · 26 Sep 2026`. It is where the document says what it is, so the title can say what it found.*

## 5. Scope, non-goals, risks

**In scope:** the ten items above, their lint rules, the vocabulary and doctrine text, the recap re-authoring. **Explicitly not:** a horizontal `Steps` (bottom form); a proportion-bar block (one page used it; `HtmlBlock` with theme tokens now covers it cheaply); a sticky in-document nav beyond Phase 1's outline; fonts or the 1240px canvas; `FileTree` author ordering (its own goal task 57400541); promoting the reader-brief lint warning to an error (Phase 2); any change to `Callout`'s tone enum, `Card`'s existing props, or `Table`'s `filterable`/`density`.

**Constraints honoured.** No new required prop anywhere; every new behaviour is a default an author can override (`look`, `height`, `columns`, `focus`) and every doctrine line says *when* and *why*, not *only*. The registry stays closed; attribute values stay literal; the lowercase-HTML guard narrows what renders rather than opening a styled subset. No continuous animation: the one new observer (`HtmlBlock` auto-height) fires on resize events only.

**Risks.**

- *Shared-file collisions in one worktree.* Six files take a line or a region from every package. Mitigated by the append-in-your-region rule and by A landing alone first; the orchestrator sequences the B–E commits and runs the full `mdx-plan` test directory once after each.
- *`InlineMarkdown` on large tables.* A 300-cell table parses 300 short strings on first render (~tens of ms, once, memoised per string). If a filterable master table in a decision batch feels slow, the processor result can be cached module-wide by string; not expected to be needed.
- *Mermaid `themeCSS` and the SVG sanitiser.* `sanitizeSvgMarkup` strips `script`/`foreignObject` and event attributes only, so the `<style>` Mermaid already emits survives with the tone rules in it. Package E confirms in the `--out` page that `var(--plan-tone-*)` resolves inside the inline SVG in both themes; if a browser refuses custom properties inside an SVG `<style>` (none should), the fallback is to resolve the six colours at render time from `getComputedStyle` and emit hexes — same authoring contract.
- *Kicker shifts fallback annotation ids.* Adding a kicker to an already-annotated document moves every un-id'd block's `plan-block-N` by one. Authored ids are unaffected; this is the same cost as inserting any paragraph above the title.
- *Lowercase guard surprises a future author.* The error card and the lint message both say what to use instead; and because the guard lives in the compile path, the `--out` render fails loudly before a human sees it.
