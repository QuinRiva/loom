# Pull 9 strategy — adopt Orchestration V2, re-express Loom on top

Loom is a Pi-first fork of `pingdotgg/t3code` whose product is an orchestration layer: goals, a shared task tree, and a workstream graph of durable threads with roles, briefs, dependencies, review gates, attention flags, a plan position per thread (held or released, and whether the work is accepted as done — separate from whether it is running), liveness detection, isolated worktrees with fan-in, reports, and consult/notify. Upstream has now shipped **Orchestration V2** (commit `de34391427`, 1,914 files) with a native Pi adapter, and deleted the V1 engine Loom's layer is welded to. This document decides, area by area, whether upstream is heading where Loom is heading — and therefore whether Loom adopts upstream's mechanism and re-expresses its guarantees on it, or keeps its own — then rolls that up into one mechanism for pull 9.

**Done** means Carl has recorded a verdict on each of the twelve areas below and answered what remains open, so a follow-on planner can write the implementation plan for the chosen phases. This is revision 3: Carl has chosen the mechanism and settled every question the earlier revisions asked (recorded below); pull 8 has merged and deployed; the per-area verdicts have been re-checked against the pull-8 review reversals and the doctrine rule they produced; and Carl's parallel review of upstream's 41 orchestration tools against Loom's (`docs/upstream-sync/28-pull9-v2-alignment/05-upstream-toolkit-account.md`, `recaps/upstream-toolkit-vs-loom/recap.mdx`) is folded in — its explicit decisions as decisions, its 43 per-tool verdicts as defaults Carl accepted without working every card.

## The recommendation in one paragraph

**Re-platform, staged.** Take `upstream/main` as the base including V2 and the Pi V2 adapter, and re-express Loom's layer as a V2 extension: Loom's thread fields, commands and events as a sidecar contract on V2's store; Loom's decider rules as a delegation arm (redesigned for V2's per-thread locking, not ported) plus a bounded, enumerated set of marked hunks in upstream's decider and dispatch core; Loom's control-plane workers (dispatcher, fan-in, liveness, exhaustion resume) re-seamed onto V2's event stream and shell snapshot; Loom's agent tools moved from bespoke REST routes onto upstream's MCP bridge as a Loom toolkit, with upstream's `delegate_task` family **withheld** from Loom threads so there is one delegation model in every prompt. The evidence says upstream is heading to the same destination as Loom on the *substrate* — durable children as real threads, event-sourced commands with receipts, a durable outbox, restart reconciliation, a shared tool bridge, a separate fork migration ledger — and to a genuinely different (or absent) destination on the *workflow*: no plan axis, no dependencies, no gates, no goals, no human holds, no liveness, no per-child worktree. Adopting the substrate and retaining the workflow is therefore the right split. "Retain" is not a cheap alternative: V2 rewired the web, mobile and client-runtime around V2 contracts and gates `/ws` on protocol version 2, so keeping V1 means freezing the whole client and the store mobile app, i.e. a hard fork. The staging is a feature freeze on Loom's orchestration layer, production staying on pre-pull-9 Loom, a long-lived integration branch, and a cut-over gated by a real Pi workstream smoke test. Pull 8 has landed and is in production, so the integration branch starts from it.

The rule that decides every area is the one pull 8's review wrote into `docs/upstream-sync/05-strategy.md` §4.3: *for each Loom hunk that differs from upstream's approach, ask who decided the difference. Carl decides functionality; an agent often chose the mechanism incidentally. Preserve the intent, not the incidental choice: where upstream now expresses the same functionality, upstream's mechanism is the baseline and Loom's variant is deleted, however much work it represented.* Every "retain Loom" verdict below names the functionality Carl decided and the guarantee upstream's nearest mechanism fails to meet; where it cannot, the Loom mechanism goes.

## What the evidence says, in five facts

The four research reports in `docs/upstream-sync/28-pull9-v2-alignment/` are facts-only; these are the five that carry the decision. Upstream code is cited at the reports' snapshot `a1d9d72aef` except where a fact comes from the toolkit account (report 05), which is pinned to `7812230572` — eight commits later, five touching `orchestration-v2/` or `mcp/`. One of those, `06e627448b` (#15219, "T3 MCP tools take explicit thread and project targets"), changes facts this document relies on: thread reads are environment-wide rather than project-scoped, cross-thread writes are gated by mid-turn and modes rather than project, `t3_thread_configure` targets any writable thread rather than only the caller, and `McpInvocationScope` gained a `requestNamespace` and a not-yet-issued client-caller kind. None of it changes a verdict — it widens what the withheld upstream tools could do, which is a reason for withholding, not against — but it is why the phase sketch re-merges upstream at every phase boundary rather than assuming a frozen target.

1. **V2 is an execution-fidelity model for one conversation, not a workflow engine.** Children share the parent's worktree; there are no dependencies, no staging, no cascade cancellation of app-owned children, no gates, no goals or tasks, no stall detection, no human holds; a role is a one-sentence prefix; the parent is woken with a generic "call `task_status`" pointer (`01-upstream-v2-inventory.md`, §A, §D, §E, §I and the closing *Design centre of gravity*).
2. **Loom is physically separated from V1 files but semantically welded to V1's vocabulary.** 24 commands, 25 events, a `goal` aggregate, about 35 projection columns, 45 migrations, about 20 snapshot-query methods, 8 in-place decider edits and 3 engine-invariant changes (`02-loom-inventory.md`, §0 "One structural fact"). The control-plane workers are portable modules on narrow seams.
3. **The Pi driver decision is downstream of the V2 decision.** Upstream's Pi adapter implements `ProviderAdapterV2`; Loom's implements the deleted V1 shape. If V2 lands, Loom's driver must be rewritten against V2 anyway, and upstream's adapter *is* that rewrite, fixture-tested on pi 1.0.0 (`03-pi-driver-comparison.md`, Headline 1).
4. **The merge is a merge plus a port, whatever the strategy.** 336 conflicted paths: 155 textual (pull-7 shaped, fits the pull-7 tooling) and 181 structural (95 modify/delete, 86 directory-rename relocations) with nothing on the other side to merge into; about 57,000 Loom lines sit on the deleted engine; 92 contract names used by 241 files vanish; about 125 files end up with dangling imports; `config.ts` silently auto-merges to `statev2.sqlite` (`04-trial-merge-surface.md`).
5. **Pull 8 removed only the pre-V2 drift** (348 to 336 conflicts in the dry runs), and the V2 surface is unchanged in size. Pull 8 has since merged (PR #323) and is in production; the merge-base with `upstream/main` is unchanged at `024d49520e`, so the trial-merge counts stand in shape, but they were measured against #323's tip, and `origin/main` has since gained #325 (99 files, the review reversals — notably the workstream web surfaces re-homed onto upstream's theme tokens, which touches the same files the web conflict count covers). Phase 1 re-measures before resolving.

## Area A — Thread graph and delegation

**Same destination? Partly.** Upstream and Loom agree that a delegated child is a *real app thread* with a transcript a human can open and message (V2 `creationSource:"mcp"` children take messages; `02-loom-inventory.md` §A intent), that its parentage is recorded, and that launching into a prepared worktree is a server workflow with progress and retry (`ThreadLaunchService`, `01-upstream-v2-inventory.md` §A "Held / staged creation"). They disagree on everything above that: V2 has no dependency or ordering between children, no held lane, no cascade cancellation of app-owned children, no per-child worktree for delegated tasks, and merge-back is context not code.

**Verdict — hybrid.** Adopt V2's `AppThread` + `lineage` (`parentThreadId`, `relationshipToParent:"subagent"`, `rootThreadId`) as the parentage record, and V2's `message.dispatch` as the kickoff primitive. Retain Loom's graph semantics as an extension: `blockedBy`, the collapsed plan axis (`held`, `outcome`, `kickoffAt` — Area C), `spawnGeneration`, `graphKey`, `isolation`, `fanInState`, `routes`, `anchorTaskId`, `kickoffBriefPath`, `reportPath` in a Loom sidecar record keyed by thread id (not as fields on `AppThread`: V2 threads are full-row upserts and `makeSubagentChildThread` spreads the parent into children, so fields there would leak into upstream's child and fork paths — upstream itself had to stop children inheriting PR links in `7812230572`); `thread.spawn` / `thread.scaffold` / `thread.dependencies.set` / `thread.release` / `thread.outcome.set` / `thread.fanin.set` as Loom commands in the decider arm; the dispatcher's promotion rail and the fan-in reactor as Loom reactors on `streamDomainEvents`.

Two things follow that are easy to miss:

- **Loom children are not V2 "delegated tasks".** `delegated_task.request` requires a blocking parent run owned by the calling provider instance (`parent_not_active`), publishes — once — the child's most recently finished run at the moment the child first goes quiet, and never reopens (`SubagentProjection.ts:243–254`; report 05 §1.10 corrects the earlier "first run" paraphrase). Those invariants — the live-turn requirement, the absence of edges, the pointer result — contradict Loom's control-plane-created, dependency-gated, re-engageable children. (That a delegated child shares its parent's checkout is *not* a contradiction: Carl does not count per-child worktrees as a Loom requirement, below.) So Loom never uses `delegate_task` or `OrchestrationV2Subagent` rows for workstream children; the Loom `thread.spawn` arm nests upstream's `thread.create` with lineage set (the command has no lineage fields today, so the arm sets them the way `dispatchDelegatedTaskRequest` does) and emits Loom events in the same transaction. V2 already uses this nesting pattern internally (`Orchestrator.ts:9884` "nested: dispatchDelegatedTaskRequest already writes child events").
- **V2's `subagent` lineage carries upstream behaviour Loom must accept or hunk, item by item.** Sidebar filtering (`filterSidebarV2VisibleThreads`) matches Loom's "children are invisible in the sidebar" — accept. Thread notifications are suppressed for subagent threads (`ThreadNotificationCoordinator.tsx`) — accept; Loom surfaces children through the attention rollup. Subagent threads are dropped from navigation shells (`client-runtime/src/state/threadShell.ts`) — accept; Loom's thread tabs and board are the navigation. Titles are reformatted for subagents (`models.ts`) — hunk, Loom titles are manual. The awareness relay is silenced for them (`AgentAwarenessRelay.ts`) — accept. Separately, `streamStoredEventsFrom(afterSequence)` offers replay that V1's `streamDomainEvents` lacked; the dispatcher's full idempotent pass stays (it is the right design) but its catch-up machinery shrinks.
- **V2 locks per thread; V1 was one serial fibre.** Loom's arm today writes to many threads in one transaction because V1 processed every command on a single queue. V2 dispatches under `threadDispatch.withLock(threadId)`, reads one thread's projection, and upstream warns the keyed executor is neither reentrant nor deadlock-aware (`Orchestrator.ts:9878–9894`); upstream only ever nests into a thread it has *just created*. So the cancel cascade (writes to descendants), gate traversal (writes to the coder from the reviewer's submit) and gate resolution (both parties `done`) cannot be "one transaction" on V2. The mechanism this document commits to: **the arm writes only to the commanded thread** (and to threads it creates in the same command), recording the *decision* as a Loom event there (`route-taken`, `cascade-requested`); **the dispatcher turns the decision into one idempotent per-thread command per affected thread** under that thread's own lock, with deterministic ids and receipts, re-driven on every pass until the read model shows it applied. Because V2 receipts rejections and a repeated id is `PreviouslyRejected`, a re-drive command that is *not yet applicable* (the target is mid-steer, a merge-back transfer is pending, `/compact` is in flight) must not be rejected: it returns the same deferred error the `start_if_idle` hunk passes through without a receipt, so the next pass tries again. The zero-event hunk covers "already applied"; the deferral covers "not yet". Atomicity becomes eventual consistency with a window of one dispatcher pass; the rails already tolerate exactly that (they are idempotent passes over the full graph). An ordered multi-lock was rejected because upstream's executor gives no deadlock guarantee and Loom would be the only caller holding more than one key.

**What survives, and what does not simplify.** Survives: the dependency gate (every dependency's `outcome` is `done`), the brief gate (an unbriefed scaffold node does not start — this is the hold Loom actually relies on), and the kickoff, which stamps `kickoffAt` on the child's own thread; cancel cascade (the arm records the cascade on the cancelled thread; the dispatcher issues `run.interrupt` + `outcome: cancelled` per live descendant); subtree archive/delete cascade (hunks on V2's `thread.archive|unarchive|delete`, same pattern); honest per-turn diffs (start-of-turn baseline — attaches to V2's `checkpoint.captured` rather than the deleted `CheckpointReactor`; **more** important, not less, once children share a checkout, because sibling edits must fall outside this thread's turn diff). **Worktree isolation becomes an option, not a guarantee.** Carl's preference: a shared checkout is fine, and per-child isolation existed to keep the diff panel coherent. So the default for every role is the parent's checkout — upstream's model — and the guarantee this document previously listed ("dependents start from a tree containing merged output") holds trivially when there is nothing to merge. Pending Carl's confirmation (bottom form), `held`, `workstream_release` and the `staged` spawn parameter go, the collapsed plan axis is `outcome` + `kickoffAt`, and the import maps a V1 `planned` thread as not-started (it starts when its brief and dependencies allow, as any other). **`goal_handoff` is fixed, not re-expressed.** Today it creates a goal plus a root *held* for the human's first send and *without* a worktree; Carl rules both defects. Under V2 the new root is launched through upstream's `ThreadLaunchService.launch` with `workspaceStrategy: {type: "worktree", baseRef}` — the same substrate `t3_thread_launch` uses — so it starts immediately in its own worktree with the setup script run; `goal_continue` keeps sharing the caller's worktree, which is right. A phase-3 item. **Worktree provisioning for isolated children keeps Loom's call site** (when the option is used). V2's `defer_start` only parks a run in `preparing` and records the strategy (`Orchestrator.ts:5158–5171`); the worktree and setup work run in `ThreadLaunchService`'s private `schedulePreparation`, reachable only through `launch` (a new top-level thread) or `retryPreparation`. Pull 8's DL-73 already put the provisioner on upstream's setup-script runner (sentinel completion, idle-shell close) with Loom's breadcrumb and 30-minute breadcrumb timeout as marked hunks, and DL-54 made it honour `worktreeSubmodules`; both carry over unchanged — the functionality Carl decided there is "agents can poll a breadcrumb and a hung script does not hang them forever", which upstream's runner still does not provide. `forkFrom` (acknowledge-then-fork) is decided in Area L.

## Area C — Lifecycle and state model

**Same destination? Partly.** V2's `Run` / `RunAttempt` / `ExecutionNode` / `ProviderSession` states and the shell's `activityRunStatus` are a more honest **runtime axis** than Loom's derived `executing / starting / idle / none` projection over V1 session + latest turn, and V2's settle/snooze/wake model is the one Loom already adopted in the sidebar rehome. V2 has **no plan axis**, **no attention axis**, and **nothing** that detects a running turn making no progress (`01-upstream-v2-inventory.md` §C "Stuck runs, idle and stall detection").

**Verdict — adopt the runtime axis; collapse the plan lane to `held` + `outcome` and move `yielded` into attention (Carl's decision); retain attention, the dispatcher rails, liveness and Loom's restart-recovery rules as an extension; two hunks in V2's dispatch/receipt core are certain, not conditional.**

- **The plan axis, collapsed (Carl's decision).** Loom's six-value *plan lane* (`planned → ready → in_progress → yielded → done | cancelled`) is replaced by three facts that cannot desync. `held` (boolean): the staging hold — `true` means "in the plan, not released to run"; `workstream_release` clears it for a subtree. `outcome` (`done | cancelled | null`): whether the work is accepted-complete (`done` releases dependents and triggers fan-in), abandoned (`cancelled`, terminal, non-releasing), or neither; written by `workstream_submit`'s routing, by `workstream_set_outcome` (the renamed `set_lane`, for a parent or human forcing `done`/`cancelled` or reopening with `none`), and by the gate pass. `kickoffAt` (timestamp or null): when the control plane delivered the first turn — the only stored "has started" fact, so an imported thread or a human-started one reads correctly without consulting V2 runs. The board's columns are **derived**: *held* (`held`), *blocked* (not held, a dependency's `outcome` is not `done`), *ready* (not held, deps done, `kickoffAt` null), *in progress* (`kickoffAt` set, `outcome` null), *done*, *cancelled*. The former `yielded` lane — "parked for the orchestrator's decision" — was an attention flag whose audience is an agent, misfiled as a plan position; it becomes the attention reason **`awaiting_orchestrator`**.
- **Attention.** The stored set is `error | awaiting_acceptance | needs_guidance | awaiting_orchestrator`, plus the derived `awaiting_approval | awaiting_input | brief-needed`. Authority: `error` and `awaiting_orchestrator` are control-plane-only (the `server:` command-id guard works unchanged on V2 command ids); agents raise only `awaiting_acceptance` and `needs_guidance`; derived reasons are recomputed at the read boundary from V2's `pendingRuntimeRequest` and Loom's brief-needed predicate — nothing stored, nothing to erase.
- **What the collapse removes.** The kickoff no longer writes a lane in the same transaction as the first turn (`kickoffAt` is stamped by the dispatcher on its own thread before it dispatches); the "§7 unifying rule" shrinks from "every turn start clears all attention and reverts `ready`/`yielded` to `in_progress`" to "every turn start clears stored attention" (which already clears `awaiting_orchestrator`); the sticky-terminal rule is trivially true because a turn start never touches `outcome`; the gate's reopen is `outcome := null` on the coder (Area D); `workstream_set_lane`'s four-value enum becomes `workstream_set_outcome {done, cancelled, none}` beside the existing `workstream_release`; the historical `thread.status-set` remap is irrelevant because Loom data is not replayed under V2. Dependencies test `outcome == done` (and `fanInState: completed` for isolated dependencies) exactly as they tested the lane. The settlement blockers read `awaiting_orchestrator` where they read `yielded`. Agent-facing text still says "in progress", "ready" and "done" — those are the derived columns' names, and `workstream_list` renders them.
- **Turn-start rules** (clear stored attention on a human- or control-plane-originated turn start or steer; supersede an open question; started-dependents warning on reopen; **the first-turn dependency gate on every dispatch path** — a human message to a scaffolded child whose dependencies are not `done` must not start it, which today lives in a `thread.turn.start` hunk) become **one hunk cluster in V2's `dispatchMessage`** — the function every run start and steer passes through, including PR-watch sync, `runtime-request.respond`, delegated child dispatch and `startNextQueuedRun`, which call it directly rather than going through the `message.dispatch` case — replacing today's spread across `thread.turn.start`. Smaller than before the collapse: no lane revert, no sticky-terminal check.
- **Human stop raises `needs_guidance`, orchestrator stop does not** → hunk in `run.interrupt` keyed on the command-id prefix, as today.
- **Control-plane wakes: steer when steerable, with a tier split (Carl's decision) — mirroring upstream's own delivery path.** Carl sees no reason to prefer Loom's `requireIdle` over upstream's rule (steer into a steerable turn, else queue, never interrupt) and wants a tier split: **FYI digests queued; yields, attention raises and gate verdicts steered.** Both tiers must respect one upstream constraint: a `message.dispatch` carrying a `notification` is accepted **only** as `queue_after_active` (`Orchestrator.ts:4517–4528`), and every other outcome — including a steer that `dispatchSteerIntoRun` rejects because the target is not `running`, has no running provider turn, or is mid-`/compact` — is a receipted rejection that kills the deterministic `server:` id forever (risk 7). So the **steered tier reuses upstream's delegated-completion mechanism verbatim**: a Loom control message is dispatched as `queue_after_active` with its `notification`, and the steer-conversion block upstream already has for delegated completions (`:4570–4605` — steer only into a `running` run with a running provider turn, on a session that supports active steering without interrupting tools, never into a maintenance command) gains a one-clause Loom-origin branch, so the message is steered when it can be, started at once when the target is idle (`shouldQueue` needs a blocking run, `:4696`), and queued otherwise — and **never rejected**. The one cost: a target that is busy but not steerable (`preparing`, `starting`, `waiting`, or compacting) gets a V2 queued run, and V2 holds queued runs after a restart (`ProviderRuntimeRecoveryService.ts:279–291`); Loom's recovery policy module therefore releases or redelivers Loom-origin queued runs at startup, which it must own anyway. The **queued (FYI) tier** keeps the deferral: a Loom `dispatchMode:{type:"start_if_idle"}` whose busy-target outcome is a distinguished *deferred* error that `dispatchWithReceiptEffect` lets through **without writing any receipt**, so the dispatcher recomputes the digest and retries on the next pass — because a V2 queued run is frozen text (three children finishing during one parent turn would queue three digests where the rail delivers one) and is held across a restart. On an idle target `start_if_idle` resolves to `queue_after_active`, which starts at once and may carry the `notification`. One marked hunk at the dispatch/receipt boundary; the same pass-through also catches any residual rejection of a Loom-origin message. **What runs on a steer:** the *target* thread's own turn-start rules — clearing *its* stored attention, the first-turn dependency gate — exactly as they run on a start. Nothing on a steer touches another thread: a yield steered into a running orchestrator does **not** clear the child's `awaiting_orchestrator`; that flag (and the settle blocker it carries) clears only when the child itself gets a turn — a `workstream_prompt`, a gate leg, a human message — or when an outcome is written to it. (No V1 rule ever cleared a child's flag on the parent's wake either: the clear was always on `command.threadId`.)
- **Automated wakes do not erase a hold.** A PR-watch wake (on from pull 9) and, if ever exposed, a schedule fire are `message.dispatch` turn starts carrying a `notification`. Loom's rule clears stored attention on the woken thread's turn start; applied to these it would erase a shipper's `awaiting_acceptance` on the first failing check, or a human's `needs_guidance` on an hourly schedule. Decision: the hunk clears agent-raised attention only for dispatches a human or Loom's control plane originated — keyed on `createdBy: user` or Loom's `origin` field, **not** on the presence of a `notification`, because Loom's own wakes carry one too — and leaves it alone for upstream's notification-source dispatches. Stated precisely: Loom's own control wakes still clear a root's `awaiting_acceptance` when they start its turn (pre-existing V1 behaviour, consistent with "a running thread is not halted awaiting a human"); it is upstream's machine events — PR state, timers — that are exempt. This is also the reason bound schedules stay closed even with the rule in place: they would start turns the dispatcher never authorised.
- **Quiescence as completion (adopted upstream semantic).** Upstream treats a delegated child as complete the moment it first goes quiet. Loom children sometimes finish and forget `workstream_submit`; today the idle "forgot to finish" backstop waits out a grace window and raises `needs_guidance`, pulling a human in for a child that stopped one call short. The adopted shape: when the dispatcher's idle rail finds a child **started** (`kickoffAt` set), idle in V2's terms as projected into the shell — no blocking run and no queued run, which also excludes a thread whose queue is held after a restart; the hook is V2 run completion in the projection, not the adapter's internal `agent_settled` — with no stored attention, `outcome` null, no non-terminal children of its own and no open user-input request, past its grace window, it writes the child's last assistant message to the report file under a synthesised header, records `thread.work.submit` on the child's behalf with the reserved outcome **`quiescent`**, and `routeWorkSubmit` routes it as an unmatched outcome — **yield to the parent**, never `done` ("no outcome can ever silently become `done`" stands). A gate member that goes quiet yields too; its synthesised message is not a verdict. The grace window is keyed on **who started the child's last turn**, read from V2's message `createdBy` (and the shell's `latestUserAuthoredMessageAt`): a turn a human started gets a long window or none — Carl may be reading the answer — while a turn the kickoff, a `workstream_prompt` or a control notice started gets the short one. The timer is not new: it is the existing dispatcher pass (coalescing worker plus periodic tick) comparing activity freshness against the window, exactly as the idle backstop does today; this replaces that backstop's `needs_guidance` raise rather than adding a rail. No upstream hunk; a rail change plus one change in `routeWorkSubmit` (Area D).
- **Zero-event success — the second certain hunk.** V2 rejects any command that produces no domain events (`"Command produced no domain events."`, `:9762`) and receipts the rejection. Loom's unchanged-value guards (a set-style command that changes nothing emits nothing but persists an *accepted* receipt — each redundant echo once cost a 1.5 s dispatcher pass, and one fan-in retry raised the same flag 13,420 times) would all become rejected tool calls. The hunk: for Loom command types, zero events is an accepted outcome with a receipt. Scoped to Loom's types so upstream's invariant is untouched for its own commands.
- **Settlement blockers** (`awaiting_orchestrator` attention, any descendant whose `outcome` is null; a root with a terminal `outcome` settles promptly; human send unsettles) → hunk in V2's `thread.auto-settle` case and `ThreadSettlementService`. Same shape as today.
- **Liveness sweep** (dead / waiting / stalled / spinning, 60 s cadence, one informed nudge then escalate) ports as-is; its heartbeat is written from the V2 adapter event stream (`provider-turn.updated`, `turn-item.updated`) into a Loom table instead of from V1 ingestion.

- **Restart recovery is Loom policy on V2's recovery service, and continuation must be switched on.** V2's `continueThreadsAfterServerUpdate` decodes to `false` by default and its continuation prompt is only "Continue where you left off." (`RestartContinuation.ts:22`). Loom's 28 marked hunks in `serverRuntimeStartup.ts` — a flagged, cancelled or approval-parked thread is not continued; a never-delivered kickoff is re-delivered verbatim rather than "continued"; stale-session reconciliation — become a Loom policy module on `ProviderRuntimeRecoveryService` / `RestartContinuation`, and the setting defaults to `true` for Loom (a settings hunk). Without this the no-silent-halt invariant does not survive a server restart.
- **The pending-steer stash stays.** V2 moved *queued* messages server-side, but a steer pi has already accepted lives in pi's process and dies with it; V2 does not track it. Loom's stash (`pendingSteering.ts`, 42 lines) rides the Loom continuation prompt as today, fed from the V2 adapter's steer path instead of V1 ingestion.

**What is verified before deletion.** Stuck-launch CAS repair (`stuckLaunchRecovery.ts`, 427 lines + decider case) and `thread.turn-start.fail` (40) addressed two V1 failures: a pi that hangs at spawn so the session sits in `starting` with no turn, and a `provider-turn.start` effect that fails before `turn.started` so the pending-turn row holds the idle gate forever. V2 has no watchdog for a run wedged in `starting` (nothing in `orchestration-v2/` detects it; upstream's `6108ef3d3d` fixes session-release record races and retries, not this), and under `start_if_idle` a wedged `starting` run counts as busy — which recreates the 16-hour gate stall the V1 code fixed. So the verification is concrete: kill pi at spawn and fail the start effect on a copied database under V2, and keep both modules unless the effect outbox's attempt retry provably recovers each case. Loom's exhaustion resume stays regardless (V2's `limitRecovery` covers provider usage limits, not Loom's per-account failover targets), re-anchored on V2's run error.

**Users gain** V2's run/attempt detail in the timeline and the settle/wake polish. **Users lose** nothing, provided the two dispatch-core hunks and the recovery policy land; without them the no-silent-halt invariant is not preserved.

## Area D — Review gates and verdict routing

**Same destination? No.** Upstream has nothing structural — no gate, verdict, round, cap or reviewer binding. Its guidance is the opposite design: re-call `delegate_task` per round with the prior findings, a fresh reviewer session each time, and never continue a review on `childThreadId` (`01-upstream-v2-inventory.md` §D). **Verdict — retain Loom, re-expressed on V2.** `routes`, `gateRounds`, `pendingRework`, `reportPath` are Loom sidecar fields and `outcome` is the collapsed plan axis's terminal fact; `thread.work.submit` and gate traversal are Loom commands in the arm; `routeWorkSubmit` (`packages/shared/src/workstreamGraph.ts`, 576 lines, pure) carries **one change**: the reserved `quiescent` outcome returns `yield` *before* the `pendingRework` interception (`workstreamGraph.ts:412–417`, which today loops any non-`needs_human` outcome back to the gate source) and is refused in any route's `on` list — otherwise a coder that went quiet mid-rework would be routed to the reviewer as its hand-back, the one case the semantic must not produce. ## Area E — Goals and task tree

**Verdict — adopt V2's `RuntimeRequest` as the question record and panel; a Loom command creates it and a `runtime-request.respond` hunk routes the answer; retain Loom's holds and shaping; the question tool is for threads a human engages with.** Carl's decision on scope: `ask_user_question` is addressed to a human, and a workstream child has none — its brief is agent-authored and nobody reads its thread unless they write to it. So the `human-input` tool family (`ask_user_question`) is **resident on root threads only** and is refused to children: `enable_toolset human-input` on a thread with a parent returns the reason and points at `consult_thread`. A child with a question its brief does not settle consults its parent; if the parent's answer does not settle it, or the parent is terminal, the child raises `needs_guidance` — that hold stays exactly as it is, because it is the no-silent-halt invariant, not a question. Upstream's `t3_pending_request_*` tools, which would have let a parent answer a child's structured question, are closed for the same reason (Area B). A human who *does* engage a child (sends it a message) can still be asked: the server-side cue in Area G marks the thread human-engaged, and the family may be enabled from then on — the smallest rule that keeps the tool honest without a second question mechanism. This is a redesign, not a port, because the mechanism the obvious reading suggests does not exist and the nearest one would answer twice:

- **No V2 command creates a runtime request.** The command union has only `runtime-request.respond`; requests are born from adapter events (`handleExtensionUiRequest` for pi dialogs). So `ask_user_question` (1–4 validated questions, 2–4 options, one `recommended`, markdown body with file chips — richer than pi's `ctx.ui.select`) needs a Loom command, `runtime-request.create`, in the decider arm that emits `runtime-request.updated` with `kind: user_input` and a Loom marker on the request. That gives the request V2's panel, `pendingRuntimeRequest` on the shell, mobile's card, and `t3_pending_request_respond`.
- **V2's `respond` on a `message`-capability request dispatches the answers as a new user message** with `queue_after_active` (`Orchestrator.ts:6943–6980`). If Loom's tool handler also returned them as the tool result, the agent would receive the answer twice — exactly the double execution the supersede rule exists to prevent. So a hunk in the `runtime-request.respond` case: for a Loom-marked request with a *live* tool waiter, hand the answer to the waiter (Loom's extension long-poll returns it as the tool result) and emit no message; with no live waiter (the pi process died, server restarted) fall through to V2's own message delivery. That fall-through is what Loom's three-layer durable settlement (`userInputSettlement.ts`, 343 lines) was built to approximate on V1, so the settlement module is deleted once the hunk exists — the 22-hour wedge is covered by V2's request lifecycle plus the fall-through.
- `thread.user-input.dismiss` exists in V2 under the same name but **refuses** anything other than a `message`-capability `user_input` request ("This question needs an answer. Answer it or stop the turn.", `:7058`). Loom-created requests are `message`-capability, so dismiss works and Loom's command goes.
- **Supersede** (a plain human message while a question is open resolves it `superseded` and is delivered as the tool result, withholding the turn start) → part of the `message.dispatch` hunk cluster in Area C.
- **Attention holds** (Area C) and the orchestrator doctrine "a child's `awaiting_acceptance` is a human hold" are retained; dependents stay blocked while a raise stands.
- Arrival surfaces: Loom's `pendingUserInputHeader / Since` columns are derived from V2's `pendingRuntimeRequest` on the shell; the columns and migration 1044 go. The panel additions and the MDX `QuestionForm` / `ReviewChoice` answer path are web-only and unchanged.

**Users gain** approvals (V2 permission modes through the bridge's `tool_call` hook, if Loom ever runs below full-access) and upstream's pending-request panels and agent-answered questions for Loom's own questions. **Users lose** nothing.

**Cost class — redesign** (one Loom command, one hunk in `respond`; the settlement module and `pendingUserInput*` columns are the deletions it buys).

## Area K — Persistence

**Same destination? Yes.** Upstream's `legacy-orchestration-migration.md` now states what Loom's `22-migration-lane-split-plan.md` decided a year earlier: a fork's schema belongs in a separate migration table. Loom's `loom_sql_migrations` ledger at `1001+` is exactly that, and the trial merge confirmed the payoff — upstream's `Migrations.ts` conflicts on one trivial hunk, upstream's divergence warning and preview reconciler only scan `effect_sql_migrations`.

**Verdict — adopt V2's store, projections, outbox and `statev2.sqlite`; retain Loom's lane, re-targeted at Loom sidecar tables; Loom writes its own one-shot importer.** Loom's about 35 columns leave `projection_threads` (a V1 table that becomes dead) and land in `loom_thread_workstream` keyed by the V2 thread id, joined into the shell query — no `ALTER TABLE` on upstream's `orchestration_v2_projection_*` tables, so upstream's schema stays byte-identical. `projection_goals / goal_tasks / heartbeats / consults / peer_messages / usage_ledger` and the thread-search index move to `loom_*` names (or stay, if the migrator can rename cheaply). Loom's V1 event types stay in `orchestration_events` at `application_event_version = 1`, unread — Loom data is projection-table-driven under V2, not replayed.

**The dangerous step, in three parts.** `initializeV2Database` copies `state.sqlite` to `statev2.sqlite` once, so every Loom table arrives intact and inert; upstream's `LegacyV1ThreadImporter` reads a fixed column list and none of Loom's. A Loom import step runs after upstream's, reading the copied V1 Loom tables and writing `loom_*` rows for the scope Carl decided: all goals and task trees, plus workstream fields for non-archived threads only — finished workstreams stay as inert rows, queryable by SQL. Because the plan lane is collapsed (Area C), the importer maps each V1 `plan_lane` onto the new facts: `planned` → `held: true`, `outcome: null` (if the staging hold is retired before cut-over, as proposed in the bottom form, `planned` maps to not-started with no hold — the thread starts when its brief and dependencies allow, like any other — and the handful of currently-held threads should be reviewed before cut-over); `ready` → `held: false`, `outcome: null`, `kickoffAt: null`; `in_progress` → `held: false`, `outcome: null`; `yielded` → as `in_progress` plus the attention reason `awaiting_orchestrator`; `done` → `held: false`, `outcome: done`; `cancelled` → `held: false`, `outcome: cancelled`. Independently of lane, **every imported thread that has any turn gets `kickoffAt`** = its first turn time from the copied `projection_turns` (import time if the turn rows are missing); only a never-started thread keeps `kickoffAt: null`. Stored V1 attention (`error`, `awaiting_acceptance`, `needs_guidance`) copies across unchanged. Two things stop the dispatcher re-sending a kickoff to a thread that already has a transcript: the promotion predicate is *not held ∧ every dependency `done` ∧ brief present ∧ `kickoffAt` null ∧ `outcome` null*, and `kickoffAt` is set for started threads whatever their outcome — so a `done` coder whose gate reopens at cut-over (`outcome` back to `null`) is re-prompted by the gate leg, not re-kicked-off by promotion, and a `workstream_set_outcome none` on an imported thread behaves the same way.

1. **Session identity must be imported, or every Loom thread forgets everything.** Upstream's importer deliberately does not translate provider session identity: an imported thread has no provider thread, and its first continuation opens a *fresh* pi session with at most a 32,000-character transcript handoff (`docs/internals/legacy-orchestration-migration.md`, "First continuation"). For Loom that is amnesia on every live orchestrator and child that is continued, notified, woken or re-engaged after cut-over, and `consult_thread`, `forkFrom`, `goal_continue` and relocation lose their target because there is no `nativeThreadRef` to resolve. V2 also requires a strong native ref before restart continuation applies. So the Loom importer, for every imported thread with a pi session on disk, creates the V2 provider-thread binding with `nativeThreadRef` = the existing `*_<threadId>.jsonl` path and `strength: "strong"` — `thread.create.importedNativeThread{ref:{driver, nativeId, strength}}` already exists for exactly this (`orchestrationV2.ts:2493`). The phase-4 gate **continues a pre-existing imported thread and checks that it remembers**.
2. **The receipt ledger is not migrated.** V1's `server:` receipts stay in V1's table; after import, Loom's deterministic ids for already-delivered episodes (terminal-child digests, gate legs, brief-needed rungs) have no V2 receipt. Left alone, the dispatcher's first pass would either re-fire a burst of stale digests at every live parent or never fire. Resolution: Loom data is projection-driven under V2 and imported threads carry **no Loom events**, so the episode-keyed rails (keyed by a Loom event id) have nothing to fire for them by construction; the importer additionally stamps imported terminal children as notified so the delta rail treats them as history. Suppress, not seed.
3. **The copy happens only when `statev2.sqlite` is absent** (`initializeV2Database.ts:26`). If production is rolled back to V1 after a cut-over and later re-cut, V2 resumes from the stale first snapshot and silently loses everything V1 wrote in between. Delete `statev2.sqlite` before any second cut-over; the runbook step says so explicitly.

About 50 tracked files name `state.sqlite` (scripts, the `AGENTS.md` test-data recipe, the `test-t3-app` skill) and must follow.

**Cost class — port plus one data step.**

## Area L — Provider registry and the Pi driver

**Same destination? Yes for the registry and the adapter contract; no for economics and operations.** Upstream's `ProviderDriver` SPI now requires an `orchestrationAdapter: ProviderAdapterV2Shape`, and `PiAdapterV2` + `PiRpc` (about 3,500 lines, 67 tests, 8 recorded live-pi transcripts through a replay harness) is the V2 Pi adapter already written. Loom's `PiDriver.ts` (2,959 lines, 152 tests including six that run the real patched pi) implements the deleted V1 shape and cannot plug into V2 (`03-pi-driver-comparison.md`, Headline 1 and the base-choice assessment).

**Verdict — adopt upstream's adapter; retain Loom's operations as hunks; shrink failover to the functionality Carl decided; resolve session identity in upstream's favour, with no Loom naming.**

Adopted with the adapter: `agent_settled` + idle-probe turn settlement, extension dialogs → approvals and questions, native non-destructive rollback via `fork(entryId)`, native fork and fork-from-turn, `readThreadSnapshot` for handoffs, per-model thinking, live usage, the retry and compaction rows, the unsolicited-activity guard, `set_session_name`, `$skill` expansion.

Retained as Loom hunks or modules: bundled patched pi resolution and manual-only maintenance (`pi update --self` disabled) — functionality: Loom's patches apply, which upstream's unpatched global binary cannot give; Loom open-session fields → argv (Area G); cost and model attribution on usage (`costUsd` has no slot in V2 `tokenUsage` — a contract hunk); the codex → Anthropic tool-id sanitiser (it rewrites history when a thread moves vendor, which the kept reroute does); account quota pollers; `PI_CACHE_RETENTION`; `queue_update` display; the search guard. Stdout backpressure and `rawInput` merging are kept only if a measurement under V2 shows they are still needed.

**Failover shrinks to what Carl decided.** Pull 8's DL-77 held the failover slice untouched precisely because pull 9 rewrites the file it lives in, and its research separated the functionality from the mechanism. CLI Proxy already rotates Claude accounts inside a call and Carl's live config turns Loom's Claude-side failover off; nothing covers OpenAI (one account, bypasses the proxy); and two things cannot live in a proxy at all — parking an exhausted thread and resuming it when the window resets, and moving a thread to a *different vendor's* model (the Codex → Claude reroute, which fired twice in the week before pull 8). So under the doctrine: **keep** `quota_exhausted` classification + `ExhaustionResumeSweep` (park-and-resume) and spawn-time usage headroom (do not spawn onto an exhausted model) — these are Carl's functionality with no upstream or proxy equivalent; **keep the cross-vendor reroute** (Carl's decision): when a thread's model is exhausted and no account of that vendor is available, Loom moves the thread onto another vendor's model mid-conversation rather than parking it — this is the one failover capability that actually fired in the week before pull 8 (twice, an OpenAI Codex limit → Claude Opus) and the one neither CLI Proxy nor upstream V2 can do; it keeps the sanitiser and a single fallback-target setting, not the chain editor; **drop** the fallback-chain editor, the Anthropic ↔ Vertex ladder, manual pause and the T3 slow-retry ladder — pi's own `retry.*` settings and the proxy's rotation stand in, and the ladder was an agent-chosen mechanism. Two defects the DL-77 research found travel with what is kept: the proxy's pool-wide "cooling down" 429 with `Retry-After` does not match `PI_QUOTA_ERROR_RE` and is misclassified transient, and best-remaining aggregation reads one account's full 5-hour window plus another's full weekly window as "healthy". What is kept is re-anchored on `agent_settled`, not ported.

**Session identity — the deepest collision.** Upstream's identity is the session file *path* (`nativeThreadRef`), resumed by RPC `switch_session`, rolled back by `fork(entryId)` which creates a new file; Loom's is a deterministic `*_<threadId>.jsonl`, resumed by patched `--session <file> --cwd`, rolled back by in-place truncation, and about ten Loom modules locate sessions by that name. Two identity schemes is dual-shape, and the deterministic name was a mechanism an agent chose, not functionality Carl decided — the functionality is "an agent and a human can find the thread's session file", which `$PI_SESSION_FILE` (pi-native, always current) gives the agent and `nativeThreadRef` gives everything else. So there is **no `--session-id` hunk**: pi names the file, the work-model addendum's "a file named `*_<threadId>.jsonl`" is rewritten to point at `$PI_SESSION_FILE` alone, **`nativeThreadRef` on the V2 provider thread is the authority**, and the ten consumers (`workstreamAsk`, `threadResolve`, `stallContext`, `workstreamLaunchIdentity`, the dispatcher, the fork and handoff handlers, the drafters) resolve the file through it. Rollback follows upstream (new file, ref updated). Patch 0001 is **extended to RPC `switch_session`** (pi's `switchSession` already accepts `cwdOverride`; the RPC handler just never passes it) so resume after a reaped worktree keeps working through upstream's resume path; the `PiCwdOverride` contract test is ported to that path.

**`forkFrom` (acknowledge-then-fork).** Upstream's `forkThread` forks natively in a throwaway process but does not replay launch identity, so the cache-prefix guarantee needs Loom's identity sidecar on top: retain `workstreamLaunchIdentity.ts` and replay argv in the Loom launch hunk when `forkFromThreadId` is set.

**Pi version (decided).** Upstream recommends pi 1.0 and recorded fixtures on 1.0.0; Loom pins 0.99.2 with two patches. Both patches are still needed against 1.0.2 (`--cwd` absent, `auth.json` still written non-atomically). Carl's decision: bump to 1.0.2, regenerate both patches, and extend the cwd patch to RPC `switch_session`, because the adapter was written and tested against 1.0 behaviour.

**`PiSettings` collisions**: `enabled` default `false` upstream vs `true` in Loom (keep Loom's — Pi-first); `binaryPath:"pi"` resolves the global binary upstream vs the bundled patched copy in Loom (keep Loom's); `customModels` as objects upstream vs strings in Loom (adopt upstream's shape, migrate); the pi-only registry (one hunk, unchanged).

**Session bindings and retention.** Pull 8's DL-74 put Loom's session reaper on upstream's live-only read and kept one marked statement per sweep that deletes stopped bindings of deleted threads, because upstream never deletes one and the table would grow forever. The V1 reaper is deleted upstream under V2 (`ProviderSessionManager` and `orchestration_v2_projection_provider_session_bindings` replace it); phase 2 checks whether V2 ever removes a deleted thread's binding and, if not, the one-statement prune returns as a Loom sweep on the V2 table — the functionality ("deleted threads do not accrete rows forever") is Carl's, the statement is the smallest mechanism.

**Users gain** robustness (settlement, rollback, dialogs, fixtures) and the end of a 2,959-line driver Loom maintained alone. **Users lose** in-place rollback (fine — upstream's is non-destructive), the deterministic session file name, the failover chain editor and retry ladder, and must accept a pi bump.

**Cost class — redesign-sized port.** The adapter is free; the re-anchoring of park-and-resume and the identity re-pointing are the risk, and the latter fails *silently* (amnesia) when wrong, so it gets its own contract test.

    **Is losing cross-thread atomicity a concern?** The multi-thread writes are the cancel cascade (a parent cancelled → every live descendant cancelled and interrupted), the gate pass (a reviewer's `needs_rework` → the coder reopened and re-prompted; a `clean` → both parties done), and dependency release (a child done → its dependents eligible). (Fan-in used to be a fourth; with children sharing the parent's checkout there is nothing to merge.) V1 processed every command on one serial fibre, so Loom wrote all of those in one transaction for free. V2 locks per thread and reads one thread's projection per command, so the arm now records the *decision* as an event on the commanded thread and the dispatcher re-drives one idempotent per-thread command for each affected thread (the "Concurrency model" row above). The residual exposure is a window of one dispatcher pass — about a second — in which the board can show a parent *cancelled* while a child still reads *ready*, or a reviewer *done* while the coder has not yet been reopened; the child's turn is interrupted on the next pass, gate dependents are already held by `isMemberOfUnresolvedGate`, and every rail was already an idempotent pass that tolerates exactly this. It is not a correctness loss: nothing can be released or started in the window that the next pass does not reconcile. It is acceptable here because this is a one-developer tool with a human watching a board, not a multi-tenant system racing on the same graph; and the reviewer's check of upstream's locking confirmed that a Loom-only "workstream root lock" would not restore atomicity anyway, because upstream's own commands (a human message, an adapter run update) never take it. Risk (7) in the phase sketch names the one failure in this area that *would* be silent.

<Callout tone="decision">
**Decision: staged re-platform (recommended in revision 1, chosen by Carl).** It is the only option under which Loom's thesis — a durable, inspectable organisation of threads the *system* keeps coherent, attributable and recoverable — keeps getting the substrate it needs from upstream (adapters, restart reconciliation, settle/wake, a tool bridge every provider shares) while Loom spends its effort on the workflow layer upstream has explicitly chosen not to build. Correctness over convenience says: pay the port once, cleanly, rather than carry two engines or stop syncing.
