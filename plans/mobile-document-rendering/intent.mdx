# Plans, recaps and explainers on the phone, looking as they do on web

**Goal.** "Loom's MDX files (and presumably other artefacts like html) don't render in the mobile app". Today the phone treats an `.mdx` document as plain markdown. The prose and headings come through, and **every block is either dropped without a trace or printed as its raw source**. The work is to draw the document with **the same renderer web uses**, inside the browser view the app already has. It also lets you **tap answers** to its questions and verdicts. The HTML file you saw fail is a **separate matter with its own fix** (§1).

**You'll know it works when.**

- You tap the `plans/sqlite-read-lane-v2/plan.mdx` chip in a chat on the phone. Its six tables, decision boxes, cards and code show as on web, fitted to the phone's width. A table too wide for the screen scrolls sideways.
- The same document opened from the Files browser looks the same.
- A brief with questions shows each question, its options and the recommended one.
- You tap an option, or accept / reject on an item, and it shows as chosen. Back in the chat it is in the message box as a chip, and sending it gives the agent the same answer text web sends. Removing the chip un-answers it.
- It works away from your desk on mobile data, over the tailnet or the tunnel, wherever chat works.
- When a new block type is added to documents, the phone shows it once the server is updated, with no new build of the app.
- A document that cannot be drawn says so and offers its source, instead of showing part of it as if it were whole.
- **Must not:** change how plain `.md` files, HTML files, PDFs or images open. Slow the chat or app start: nothing of the document view loads until a document is opened. Ask you to sign in again inside the document view.

**Approaches in play.**

- **The web renderer, inside the app's built-in browser view.** The Loom server serves a small page holding only the document renderer. The app opens it in the embedded browser view it already uses for HTML files, and hands it the file's text. The page never signs in and fetches nothing private, so it works over every connection the app works over. Wins if it opens quickly over the tunnel and reads well at a phone's width. The picture above is the first evidence for the second. _My pick._
- **The same renderer, packed inside the app instead of served.** Wins if serving it proves slow or unreliable away from home. It costs a new app build every time a block is added.
- Dropped: **rebuilding the blocks as native app components.** About 40 block types and 11,700 lines of web code to mirror, then two renderers to keep in step for every block added. Wireframes, diagrams, prototypes and HTML figures are web content that would need the browser view regardless.
- Dropped: **opening the whole Loom web app inside the phone app.** It needs its own sign-in inside the app, puts a desktop layout on a phone screen, and any answer would land in a second message box rather than the phone's.
- Dropped: **the server flattens the document into a fixed HTML page.** No expanders, tabs or diagrams and no path to tapping answers later. The renderer lives in the web app, so the server would need its own build of it, and the saving over the pick is small.

**Decided.** "Loom's MDX files (and presumably other artefacts like html) don't render in the mobile app".

- How much the phone lets you do: "Read, and tap answers to questions and accept / reject verdicts".
- HTML artefacts: "I have seen an HTML artefact fail on the phone", and "I'm *pretty sure* I've seen html artefacts fail with "preview unavailable"". Your screenshot confirms one. Its link pointed at a path with no file, and the card did not say so. That has its own fix and is not part of this feature.

- _Assumed:_ every `.mdx` file opens in the document view. Its raw source stays one tap away in the file menu, as it is for markdown today. Redirect if wrong.
- _Assumed:_ the phone reads documents up to the same 8 MB as web. Today it cuts a file off at 1 MB. Redirect if wrong.
- _Assumed:_ your phone is Android, running the Loom app installed from a file rather than a store. That is read off your screenshot and an earlier install, not something you said. So each PR is checked on Android, on your phone, and reaches it as a new app file to install. Redirect if wrong.

**Not doing.** Commenting on a block or a highlighted passage. Asking a question on a section (the side conversations web opens from a document). A document panel beside the chat, or a plan opening by itself when an agent writes one. Editing a document on the phone. Any change to web's document view.

**Still unknown.**

- What your phone shows for a document, today and after. Agents have no device, so each PR is tried on your phone before it ships. The plan says what that asks of you.
- Whether a page loads in the embedded browser view on your phone at all. Nobody has watched one. The first try of the reading PR settles it.
- Whether the widest blocks (design boards, annotated code, three cards across) read at a phone's width. The render above reads well apart from wide tables. Opening two or three real documents on the phone settles it.
- How long the first open takes over the tunnel on mobile data. The renderer is roughly 1 MB to download once after each server update, then the phone keeps it. Measured on the first build; if it is too slow, the fallback is packing the renderer inside the app.
