# Open `.mdx` documents on the phone in the web renderer, then let answers be tapped

**Recommendation.** Give the web app a second, small page that holds only the MDX document renderer. The mobile app opens that page from the Loom server in the WebView it already ships, and hands it the file's text over a message bridge. The page never signs in; the app keeps doing all private reads over its existing session. **Two PRs.** The first makes every `.mdx` file readable as on web. The second makes question options and accept / reject verdicts tappable, landing in the phone's composer as the same records web sends. **Roughly two to three days of agent work each.**

It makes two bets. First, that a page served by the server loads in the WebView on Carl's Android phone over the tailnet. Nobody has seen that, and an HTML file failed for him this week for a reason still being diagnosed. The first on-phone check of PR 1 settles it, and the fallback (the same page packed inside the app) changes one URL and nothing else. Second, that the renderer reads at a phone's width. A static render of a real plan at 390 px already does, apart from wide tables.

## 2. The bridge contract

One module, `packages/shared/src/documentViewerBridge.ts`, exported as `@t3tools/shared/documentViewerBridge`, defines the messages, the viewer path and the protocol number. Both sides import it. `@t3tools/shared/htmlRender` is the precedent: a message protocol shared by web and mobile for HTML shown in a WebView.

<Table
  density="compact"

    ["app → page", "`answers-present`", "the `contextId`s of this file's answers now in the thread's draft", "2"],

Rules that hold for both PRs:

- **Transport.** Page to app is `window.ReactNativeWebView.postMessage(JSON)`. App to page is `injectJavaScript` of a `window.postMessage`, the pattern `postTheme` uses in `apps/mobile/src/features/threads/HtmlRenderWebView.tsx`.
- **Token.** The app makes a random token per load and sends it in `init`. Every page message except `ready` must carry it, and the app drops any that does not. Reason: Android exposes `ReactNativeWebView` to every frame, including the scripted sandbox of a document's `<Prototype>`. Without the token an agent-written document could post a forged answer into Carl's composer. The app injects `init` into the top frame only, which a sandboxed frame cannot read.
- **Validation.** The app decodes every message with the module's schema and ignores unknown types. In PR 2 it also decodes `record` with `ReviewCommentContextRecord` from `@t3tools/contracts` and requires `mdxAnchor` present and `filePath` equal to the open file.
- **Skew.** Messages only ever gain optional fields. The page offers tappable answers only when `init` carries `answers`, so a PR 1 app with a PR 2 page stays read-only, and a PR 2 app with a PR 1 page never receives answer messages.
- **Handshake.** The server answers an unknown path with the app shell, so a 200 proves nothing. The app treats the page as loaded only on a valid `ready`.

<Callout tone="decision" title="The composer draft is the truth, as on web">
  An answer exists exactly while its record is in the thread's composer draft. Removing the chip un-answers the question; sending the message clears it. The structured selection (which option ids, which verdict, the note) lives in the page's `localStorage` through web's own `useMdxAnnotationDraftStore`, unchanged, because the comment text cannot be parsed back. That is the same split web makes, with the same edge: if the stored selection is lost while the chip remains, the block shows unanswered and the next tap replaces the chip.

  The record and its composer token are built by web code inside the page, so the text the agent receives is identical to web's by construction. The app stores and shows the record; it does not compose it.
</Callout>

## 5. How a change reaches Carl's phone

The repo does not say, so this comes from the thread that installed the app on 9 Nov. Carl's phone runs an APK built on this server: the preview variant (`com.t3tools.t3code.preview`, "T3 Code Preview"), arm64, signed with the debug key, with the JavaScript bundle embedded and over-the-air updates switched off. Updates are off on purpose: `updates.url` in `apps/mobile/app.config.ts` points at upstream's Expo project, and an update from there would replace Loom's code with upstream's. There is no store build. That the phone is Android, and runs this APK, is read off his screenshot rather than stated by him.

So **both PRs need a new APK, built by the coder and installed by Carl**. Nothing reaches the phone any other way. The build takes about six minutes with warm caches:
