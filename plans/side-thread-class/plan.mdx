# Side threads: one named class that presentation reads, nothing the control plane does

**Recommendation: name the class that query threads and `/handoff` drafters already belong to, `side thread`, as one registry in the loom contracts that every presentation surface reads instead of role names, with four uniform rules: it nests under its anchor's row in the sidebar and is never a top-level inbox item, it hangs as a satellite under its anchor on the graph, it joins its anchor's tab group, and it stays structurally outside `workstream_list` and every rollup.** Nothing on the server's operational graph moves: a side thread keeps `parentThreadId` null and is never anyone's parent, which is what already keeps it out of dispatcher wakes, join barriers, cascades, gate routing and the tree `workstream_list` walks. The class is **derived from the role** (no migration, no stored column), and its one attribute, whether the human reads the thread directly, tells a query thread (shown under its author) from a drafter (hidden until it needs you, as today).

**Your symptom goes away:** a Query no longer "opens a completely new root thread" in the inbox; it appears as a slim indented row under the thread that wrote the document, and the inbox's sort, unread and attention are untouched by it. **Cost:** about a day and a half of coder time, web and client-runtime only, plus a one-line server change (the thread that signed a document) and a sentence in two skills so recaps and explainers get signed like plans do. **Two bets:** that `forkFromThreadId` is the right anchor for every member (it is, for both members today), and that a sub-row rendered inside the anchor's sidebar row is enough nesting for a flat inbox (no tree, no collapse state, nothing persisted).

## 2. What a side thread is

The plan defines four terms; the implementer writes them into `docs/internals/glossary.md` under a `<!-- loom -->` marker (per the domain-modelling rule that the glossary write happens at implementation).

- **Side thread.** A thread that lives on another thread's context, beside the operational graph: a Loom root (`parentThreadId` null), never a parent, with no goal of its own (a query thread has none; a drafter carries its source's goal until it is archived), that exists to serve the human or a tool rather than to do delegated work. Replaces "ghost node" and "pseudo-node". Today: a query thread and a `/handoff` drafter.
- **Anchor.** The thread a side thread hangs from in every presentation: the thread it was forked from, `workstream.forkFromThreadId`. Both members are forks, so the field is the anchor for the whole class; a member with no fork source is not a side thread (it falls back to an ordinary root, so nothing is ever unreachable).
- **Host row.** The sidebar row a side thread nests under: its anchor's row when the anchor is a root, else the anchor's workstream root (sidebar v2 hides children, so the root is the nearest row that exists). Found by the same parent walk the thread tabs already use.
- **Attended.** Whether the human reads the thread directly. A query thread is attended (the human chats in it); a drafter is unattended (it runs once, places a handoff, and the server archives it). Attended side threads are listed and drawn; unattended ones are hidden until they carry attention.

## 3. The registry and its selectors

`packages/contracts/src/orchestrationV2.loom.ts` already hosts `DOCUMENT_QUERY_ROLE`. `HANDOFF_DRAFTER_ROLE` moves there from `apps/server/src/loom/handoff/handoffDraft.ts` (the four server importers switch to the contracts import; the web's three string literals `"handoff-drafter"` become the constant), and the registry sits beside them:

<Code
  language="ts"
  wrap
  code={"/**\n * Side threads (plans/side-thread-class/plan.mdx): threads that live beside the\n * operational graph on another thread's context. A side thread is a Loom ROOT (no lineage\n * parent) and never a parent, so every control-plane reader (dispatcher wakes, join\n * barriers, rollups, cascades, gate routing, workstream_list) excludes it structurally;\n * this registry is read by PRESENTATION only. The three listing predicates and the host walk are client-side selectors in a new `packages/client-runtime/src/state/loom/sideThread.ts`, so web and mobile read one rule (the mobile half is a follow-up, §8):

<Code
  language="ts"
  wrap
  code={"import { sideThreadOf } from \"@t3tools/contracts\";\n\ntype Shell = Pick<OrchestrationV2ThreadShell, \"id\" | \"lineage\" | \"workstream\">;\n\nconst hasAttention = (shell: Pick<Shell, \"workstream\">) =>\n  (shell.workstream?.attention.length ?? 0) > 0;\n\n/** Listed in any flat list of threads (palette, @-mentions): everything but an unattended side thread without attention. */\nexport const isListedThread = (shell: Pick<Shell, \"workstream\">) => {\n  const side = sideThreadOf(shell.workstream);\n  return side === null || side.attended || hasAttention(shell);\n};\n\n/**\n * Takes a top-level sidebar row: an ordinary thread always; a side thread only when it\n * carries attention (the way a broken one reaches you), or when it is attended and its\n * anchor is not in the snapshot (archived or deleted), so a way in is never lost.\n */\nexport const isTopLevelRow = (shell: Pick<Shell, \"workstream\">, present: ReadonlySet<ThreadId>) => {\n  const side = sideThreadOf(shell.workstream);\n  return side === null || hasAttention(shell) || (side.attended && !present.has(side.anchorThreadId));\n};\n\n/** Nests as a sub-row under its host: an attended side thread that takes no top-level row. */\nexport const isSubRow = (shell: Pick<Shell, \"workstream\">, present: ReadonlySet<ThreadId>) =>\n  sideThreadOf(shell.workstream)?.attended === true && !isTopLevelRow(shell, present);\n\n/**\n * The thread a shell hangs from in presentation: its `subagent` parent (the workstream\n * edge), else its side-thread anchor, else null for a root. `hostRowOf` is `resolveThreadGroupKey`'s loop in `apps/web/src/loom/threadTabGroups.ts` lifted out; that file's `parents` map is built with `presentationParentOf` instead of its inline `subagent` test, which is the whole thread-tabs change. **No new persisted client state.** Every value here is derived from the environment's shell snapshot in atoms, the same shape as the rollup index (`rollupsAtom` in `apps/web/src/loom/LoomRollupBadge.tsx`), so it is outside the four tiers in `docs/architecture/loom-ui-state-tiers.md`: nothing is seeded, nothing overrides a user choice, nothing is written to a store.

## 4. The sidebar rule, exactly

**Top level.** `filterSidebarV2VisibleThreads` in `apps/web/src/components/Sidebar.logic.ts` replaces `isVisibleHandoffDrafter(thread)` with `isTopLevelRow(thread.source, present)`, where `present` is the set of ids of the `threads` it was given (one `Set` per call; the function's `Pick` gains `"id"`). `apps/web/src/loom/handoffDrafter.ts` is deleted; its reasoning lives in the registry comment. The same swap, to `isListedThread(thread.source)`, lands in `CommandPalette.logic.ts` (the thread list), `ChatComposer.tsx` line 2654 (the `@` list) and `loom/threadMention.ts` (the `!` list), the three other readers of the deleted helper.

**Sub-row.** A new `apps/web/src/loom/SideThreadRows.tsx` exports `LoomSideThreadRows({ hostThreadKey, onActivate })`, memoised, rendered by **two marked hunks** in `Sidebar.tsx`'s `SidebarThreadRow`: inside the row's `<li>`, directly after the `</Tooltip>` that wraps the row surface, in both the card variant and the slim variant. Inside the `<li>` rather than as a list sibling so that a drag of the host moves the sub-rows with it (dnd-kit transforms the `<li>`), the `[content-visibility:auto]` hint stays on one element, and the list of sortable ids is untouched. It:

- reads `sideThreadRowsAtom(hostThreadKey)` from a new `apps/web/src/loom/sideThreadRows.ts`: a per-environment atom family over `environmentSnapshotAtom(environmentId).threads` builds `Map<hostId, SideThreadRowModel[]>` once per snapshot (`presentationParentOf` for the parents map, `isSubRow` for eligibility, `hostRowOf` for the host, sorted by `createdAt`), and the per-host atom returns the previous array when a JSON key of `[threadId, title, role, running]` has not changed, exactly as `rollupAtom` does, so a host row re-renders only when its own sub-rows change;
- returns null when the host has none, so the ordinary row's markup and height are unchanged for every thread that is not an anchor;
- renders `<ul data-thread-selection-safe onPointerDown={stop}>` (the `stopPropagation` the row's action buttons already use in `handleActionPointerDown`, so a press on a sub-row never starts the host's drag or the selection sweep) of one `<li role="button" tabIndex={0}>` per side thread: indented by the row's content inset plus 1.25rem, height 1.75rem, `text-xs`, a role glyph (`MessageCircleQuestionIcon` for `document-query`, `GitForkIcon` otherwise; a small `Record<SideThreadRole, Icon>` in the component), the title truncated, and a static `size-1.5 rounded-full bg-info` dot at the right while `activityRunStatus` is running (no pulse: no repainting animation);
- marks the sub-row whose thread is the route thread (`useParams({ strict: false }).threadId`, as `HandoffToastCoordinator` reads it) with `aria-current="page"` and `bg-sidebar-row-active`; other sub-rows take `hover:bg-sidebar-row-hover`. Theme tokens only, no `components/ui` restyle;
- calls `onActivate(scopeThreadRef(environmentId, threadId))` on click or Enter; the host row already holds `onThreadActivate` and passes it through.

**Route retention.** The sidebar keeps the route thread visible in a collapsed shelf (`routeThreadOnly`, three call sites in `useSidebarThreads`, plus the settled-tail lookup). When the route thread is a sub-row, its host must be the retained thread: a new `sidebarRouteRowKey(threads, routeThreadKey)` in `apps/web/src/components/Sidebar.logic.loom.ts` returns the host's key for a sub-row thread and the key itself otherwise, and the four lookups use its result. One marked hunk.

**What the sub-row does not do.** It does not take part in the sidebar's sort, multi-select, keyboard arrow navigation, drag, snooze, settle or pin: those are the host's. A side thread's own settled or snoozed state is ignored; it shows while live (not archived), and a superseded query thread (archived on the next Query after a rewrite) leaves the snapshot and the row. Its context menu, archive and delete remain reachable from the thread's own header once open.

**Attention.** A side thread that carries a stored attention reason (today: `error` from the liveness sweep, or `needs_guidance` when a deferred fork is refused) is a top-level row until the reason clears, and not a sub-row: one place, and the sidebar's existing attention override (`loomAttentionOf`) labels it. This is the drafter's current rule applied to the whole class.

## 7. Recap and explainer signing

A Query forks the thread whose pi session signed the document (`manager_sessions` in the frontmatter). `skills/mdx-visual-plan/SKILL.md` tells its author to sign; `skills/mdx-visual-recap/SKILL.md` and `skills/mdx-visual-explainer/SKILL.md` do not, so a Query on a recap fell back to the viewing thread. Two changes:

1. **One sentence in each skill**, in its "Where it goes" section, after the hand-back line, mirroring the plan skill's wording. Recap: "A recap is signed with `sign_document` (role `recap`) when the thread has the tool: a Query on the recap forks the thread that signed it, and an unsigned recap sends the question to whichever thread the reader opened it from." Explainer: the same with "explainer" and role `explainer`. These are model-read instructions: the edit follows `skill-authoring` and `llm-instruction-change` (load both; the diff is quoted in the coder's report), and reaches cockpit sessions at the next release, since `~/.pi/agent/skills/mdx-*` symlink into `loom-releases/current`.
2. **`AUTHOR_ROLES` in `apps/server/src/loom/query/documentAuthor.ts`** gains `"recap"` and `"explainer"`, so a recap signed by its author and later by a `reviewer` still resolves to the author rather than the most recent signer.

`sign_document` accepts any role string, so no change to the signing tool.

## 8. Mobile

The mobile thread list (`apps/mobile/src/features/threads/threadListV2.ts`, two filters at lines 213 and 624; rows in `thread-list-v2-items.tsx`) has no nesting and today lists side threads at top level, drafters included while they draft. The rule is the same as the web's and the predicates are in client-runtime for it. This plan does not change mobile: hiding without a sub-row would be a one-way door (a query thread opened on web would be unreachable on the phone), and the sub-row is a separate list item kind with its own simulator verification. The recommended follow-up applies `isTopLevelRow` in both filters and inserts a `side-thread` item after its host in the section builders. The question form asks whether to fold that into this change.

## 12. Risks

- **A sub-row inside a sortable `<li>`.** dnd-kit measures the `<li>`, so a host with sub-rows is taller while dragging; the drop-position maths uses measured rects, so this is correct, but the first live drag of an anchor row should be looked at. Fallback if it misbehaves: render the sub-row list as a non-sortable sibling `<li>` after the host (one hunk in the items loop instead of two in the row), accepting that sub-rows stay put during a drag.
- **A host that is a child.** When the author is a workstream child (this plan's own author is one), the sub-row sits under the root's row, labelled by the query thread's title, which names the document but not the author. Acceptable for a first cut; the row's tooltip can carry "fork of" plus the author's title if it proves confusing.
- **`contain-intrinsic-size` hints** on the row `<li>` (`auto 78px` / `auto 36px`) are estimates for off-screen rows; a host with sub-rows is taller, so a long scroll may jump by a few pixels once. `auto` remembers the rendered size after first paint.
- **A fourth member later** needs only a registry row, but a member whose anchor is not `forkFromThreadId` would need the registry to name its anchor field; the `SideThread` shape already carries `anchorThreadId`, so only `sideThreadOf` changes.
