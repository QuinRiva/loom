# Child prompt-stack dedup — P1 delta-briefing, P2 single-home protocol + progressive disclosure, P3 per-role tool profiles

**Objective.** A leaf child thread today launches with the orchestrator's full control-plane manual, ~100 tools it will never call, and a completion protocol stated three times — and orchestrators habitually re-transmit standing context in briefs because nothing tells them what a child already receives. This plan designs the loom-side fix: amend the brief contract to state the child's genuinely guaranteed inherited surfaces and the under-specification tail (P1), give the completion protocol one contract of record with every other copy reduced to a reference (P2a), make the graph-authoring surface on-demand rather than resident in every leaf (P2b), and give each role a default tool profile with a one-call escalation path (P3). **Done means:** every prose surface below lands as drafted, a leaf researcher's assembled system prompt drops from ~59 KB to ~45–47 KB, its selected tool count from 101 to ~27, a child that genuinely needs a dormant tool family activates it mid-turn without a restart or human intervention, and the behavioural probes in §7 show briefs and completions improved rather than merely shrank.

**No pi-core patch changes are required.** Every capability this design needs — a launch-time tool allowlist that covers extension tools, per-tool conditional guidelines, and mid-session tool activation — already exists in pi 0.83.0 as shipped. Evidence in §5.6.

The load-bearing facts, each verified in source:

- **Tool selection is already role-conditionable.** `apps/server/src/orchestration/roleOverlay.ts` parses `tools:` frontmatter from `roles/<role>.md` and the reactor passes it to the driver, which hands pi a `--tools` allowlist. pi applies the allowlist to built-in, extension, and custom tools alike (`dist/cli/args.js`: "Applies to built-in, extension, and custom tools"). The `assessor` role already uses this. Every other role has no `tools:` frontmatter, so it gets **every registered tool** — that is where the audited researcher's 101 tools came from.
- **Guidelines are conditional on tool selection.** pi's `agent-session.js` `_rebuildSystemPrompt(toolNames)` collects `promptSnippet` and `promptGuidelines` **only for selected tools**; `system-prompt.js` renders exactly those. Excluding a tool removes its snippet line, its guideline bullets, and its JSON schema from every request. Tool selection is therefore the single lever that delivers both P2b and P3.
- **The inherited surfaces have real conditions.** The skills catalogue is appended **only when the selected tools include `read`** (`system-prompt.js`, skills section) and excludes `disableModelInvocation` skills (`skills.js` `formatSkillsForPrompt`) — so an assessor (whose profile deliberately has `read_full` but no `read`) receives **no skill catalogue**. The goal/task tree is a **launch-time snapshot**, never refreshed (`goal_task_list`'s own description says so). A native fork replays its **source's** captured launch identity, which can be older than the current composition. The P1 contract must be truthful about all three.
- **The lifeline union currently defeats profiling for workstream tools.** `roleOverlay.ts` auto-unions `LIFELINE_TOOLS` — **all 23** provider tool names from `PROVIDER_TOOL_PATHS` — into any role's allowlist, so today no role can shed the graph-authoring tools even with a `tools:` list.
- **Mid-session activation exists and takes effect on the next model round.** Extensions get `pi.getActiveTools()` / `pi.getAllTools()` / `pi.setActiveTools(names)` (`dist/core/extensions/types.d.ts:933–937`). The coding-agent session installs `_installAgentNextTurnRefresh` (`agent-session.js:261`), which refreshes both `tools` and the rebuilt `systemPrompt` from agent state **after every model round within a turn** — so a tool call that activates a family makes the family callable (with its guidelines present) on the very next round, no restart, no new turn.
- **The completion protocol is stated three times**: the guideline bullets of `workstream_submit` / `workstream_set_lane` / `workstream_request_attention` in `providerToolDefs.ts`; the closing bullet(s) of every role overlay; and the last two paragraphs of `workstreamChildPrompt.ts`. Only the tool description is present in every request; the other copies are paraphrases that can drift.
- **Rework-round routing is already delivered just-in-time.** `WorkstreamDispatcher.ts` `buildGateReworkMessage` tells a mid-gate coder, at the exact moment it matters, that its next submit routes to the reviewer and must be a per-finding round report — so the coder overlay's resident copy of that routing is redundant.

## 3. P1 — the brief contract states what a child inherits, truthfully

Root cause: the `workstream_spawn` brief contract demands self-containment but never says what the child reliably receives, so a careful orchestrator over-transmits. One prose surface owns this contract — `workstream_brief`'s `markdown` parameter already defers to it ("It follows the same contract as workstream_spawn's brief"), and `providerToolDefs.test.ts` pins that deference. ## 5. P2b + P3 — one mechanism: role-profiled tool selection with mid-session escalation

P2b (leaf children carry the orchestrator's manual) and P3 (101 tools shipped to a read-only researcher) share a single root cause and a single lever: **which tools are selected**. pi already conditions the snippet list, the guideline bullets, and the per-request schemas on the selection. The design has three parts: (a) name the tool families, (b) give every role a default profile, (c) provide the escalation path.

**Partition invariant.** The three arrays must exactly partition `Object.keys(PROVIDER_TOOL_PATHS)` — complete coverage, no overlap. A type-level assertion strong enough to prove disjointness plus exhaustiveness is not worth its complexity here; instead one focused unit test (in a new `toolPaths.test.ts`) asserts set-equality of the union with the path-table keys and pairwise disjointness, so a future provider tool that lands in no family (or two) fails CI with a named diff. (`enable_toolset` is deliberately outside the partition: it is local, not HTTP-routed — §5.4.)

Judgment calls inside the split: `notify_thread`, `thread_fork`, `goal_handoff`, `goal_continue`, `goal_update` join the delegation family because each is a parent- or root-shaped act (cross-thread tasking, divergence, goal ownership) that a leaf reaches for about as rarely as spawning. `ask_user_question` gets its own family per the settled decision: it is not delegation, and its trigger (a genuinely irreversible/destructive/preference-only fork while a human is reachable) is distinct enough to name.

### 5.4 The escalation path: `enable_toolset`

A new tool in the generated provider extension — **local**: it never POSTs to the server; it calls pi's own extension API. It is auto-unioned into every restricted allowlist, so its snippet line in "Available tools" is the resident, role-agnostic pointer that dormant families exist.

**Registration design (typing).** `ProviderToolDef.name` is typed `ProviderToolName` (`keyof PROVIDER_TOOL_PATHS`) and `withPath` unconditionally attaches `PROVIDER_TOOL_PATHS[def.name]`, so a local tool cannot join the existing table without inventing a fake route. Smallest coherent change: a second, separately-typed table `LOCAL_PROVIDER_TOOL_DEFS` (its own name union, no `errorMode`/`path` — those are HTTP semantics), serialised into the extension beside the routed defs with a `local: true` discriminant the generated shim branches on (local execute = `setActiveTools` union; no `fetch`). `withPath` and the routed table stay untouched; the extension test's "registers all 23 tools" assertion becomes 23 routed + 1 local.

### 5.6 Verdict on the pi-core patch, and the risks

<Callout tone="decision">
**The pi-core patch does not grow.** Launch allowlist (`--tools`, covering extension tools), selection-conditioned snippets/guidelines/schemas (`_rebuildSystemPrompt` + `buildSystemPrompt`), the extension API for mid-session activation (`setActiveTools`), and the per-round tools/system-prompt refresh (`_installAgentNextTurnRefresh`) all exist in pi 0.83.0 unpatched. The design is loom-side only.
</Callout>

<Callout tone="risk">
Known edges, all judged acceptable: **(1) Restart amnesia** — mid-session enablement is not persisted; a resumed session relaunches with the frontmatter profile and the child must re-enable (the tool description says so). **(2) Cache invalidation** — enabling a family rebuilds the system prompt, invalidating the provider prompt-cache prefix once per enablement; small against the per-round savings. **(3) `setActiveToolsByName` ignores the launch allowlist** — it checks registry membership only, which is exactly what lets `enable_toolset` escalate; it also means the allowlist is a default, not a sandbox (fine: this is a token-hygiene mechanism, not a security boundary). **(4) Fork identity** — a fork replays the source's captured argv including `--tools`, so forks inherit the source's profile coherently; the P1 contract names this as a staleness source the brief must cover. **(5) Static tool names in frontmatter** — an unknown name in `tools:` is silently ignored by pi, so a renamed extension tool degrades soft (the role loses it until the frontmatter is fixed); acceptable for a prototype, and the §7 probes catch the common cases.
</Callout>
