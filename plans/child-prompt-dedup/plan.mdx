# Child prompt-stack dedup — P1 delta-briefing, P2 single-home protocol + progressive disclosure, P3 per-role tool profiles

**Objective.** A leaf child thread today launches with the orchestrator's full control-plane manual, ~100 tools it will never call, and a completion protocol stated three times — and orchestrators habitually re-transmit standing context in briefs because nothing tells them what a child already receives. This plan designs the loom-side fix: amend the brief contract to enumerate the child's guaranteed inherited surfaces (P1), make the kickoff wrapper the single home of the submit/attention protocol (P2a), make the graph-authoring surface on-demand rather than resident in every leaf (P2b), and give each role a default tool profile with a one-call escalation path (P3). **Done means:** every prose surface below lands as drafted (after human review), a leaf researcher's assembled system prompt drops from ~59 KB to ~47–49 KB, its selected tool count from 101 to ~28, and a child that genuinely needs a dormant tool family can activate it mid-turn without a restart or any human intervention.

**No pi-core patch changes are required.** Every capability this design needs — a launch-time tool allowlist that covers extension tools, per-tool conditional guidelines, and mid-session tool activation — already exists in pi 0.83.0 as shipped. Evidence in §4.

<Callout tone="decision">
This plan revises the governing doctrine (`.plans/role-scoped-prompting-and-workstream-doctrine.md`, `.plans/role-scoped-prompting-implementation.md`) in one respect: doctrine decision #4 kept `workstreamChildPrompt` as a pure brief-carrier while role doctrine lived in overlays. The human's retro triage (2026-08-10) explicitly re-decided this — the kickoff wrapper becomes the single home of the completion protocol because it is per-child, role-agnostic, and lands last. That fresher human decision supersedes the doctrine on this point; everything else here (permissive spawning, inject-once, overlays carry role doctrine) stays inside the doctrine's frame.
</Callout>

The load-bearing facts, each verified in source:

- **Tool selection is already role-conditionable.** `apps/server/src/orchestration/roleOverlay.ts` parses `tools:` frontmatter from `roles/<role>.md` and the reactor passes it to the driver, which hands pi a `--tools` allowlist. pi applies the allowlist to built-in, extension, and custom tools alike (`dist/cli/args.js`: "Applies to built-in, extension, and custom tools"). The `assessor` role already uses this. Every other role has no `tools:` frontmatter, so it gets **every registered tool** — that is where the audited researcher's 101 tools came from.
- **Guidelines are conditional on tool selection.** pi's `agent-session.js` `_rebuildSystemPrompt(toolNames)` collects `promptSnippet` and `promptGuidelines` **only for selected tools**; `system-prompt.js` renders exactly those. Excluding a tool removes its snippet line, its guideline bullets, and its JSON schema from every request. Tool selection is therefore the single lever that delivers both P2b and P3.
- **The lifeline union currently defeats it for workstream tools.** `roleOverlay.ts` auto-unions `LIFELINE_TOOLS` — **all 23** provider tool names from `PROVIDER_TOOL_PATHS` — into any role's allowlist, so today no role can shed the graph-authoring tools (scaffold, gates, release, forking…) even with a `tools:` list.
- **Mid-session activation exists and takes effect on the next model round.** Extensions get `pi.getActiveTools()` / `pi.getAllTools()` / `pi.setActiveTools(names)` (`dist/core/extensions/types.d.ts:933–937`). The coding-agent session installs `_installAgentNextTurnRefresh` (`agent-session.js:261`), which refreshes both `tools` and the rebuilt `systemPrompt` from agent state **after every model round within a turn** — so a tool call that activates a family makes the family callable (with its guidelines present) on the very next round, no restart, no new turn.
- **The completion protocol is stated three times**: the guideline bullets of `workstream_submit` / `workstream_set_lane` / `workstream_request_attention` in `providerToolDefs.ts`; the closing bullet(s) of every role overlay; and the last two paragraphs of `workstreamChildPrompt.ts`. The kickoff wrapper's copy is the most complete and the only per-child one.

## 5. P2b + P3 — one mechanism: role-profiled tool selection with mid-session escalation

P2b (leaf children carry the orchestrator's manual) and P3 (101 tools shipped to a read-only researcher) share a single root cause and a single lever: **which tools are selected**. pi already conditions the snippet list, the guideline bullets, and the per-request schemas on the selection. The design therefore has three parts: (a) name the tool families, (b) give every role a default profile, (c) provide the escalation path.

### 5.1 Name the families (constants leaf)

A new tool in the generated provider extension (`providerToolExtension.ts`), **local** — it never POSTs to the server; it calls pi's own extension API. ### 5.6 Verdict on the pi-core patch, and the risks

<Callout tone="decision">
**The pi-core patch does not grow.** Launch allowlist (`--tools`, covering extension tools), selection-conditioned snippets/guidelines/schemas (`_rebuildSystemPrompt` + `buildSystemPrompt`), the extension API for mid-session activation (`setActiveTools`), and the per-round tools/system-prompt refresh (`_installAgentNextTurnRefresh`) all exist in pi 0.83.0 unpatched. The design is loom-side only.
</Callout>

<Callout tone="risk">
Known edges, all judged acceptable: **(1) Restart amnesia** — mid-session enablement is not persisted; a resumed session relaunches with the frontmatter profile and the child must re-enable (the digest says so). **(2) Cache invalidation** — enabling a family rebuilds the system prompt, invalidating the provider prompt-cache prefix once per enablement; small against the per-round savings. **(3) `setActiveToolsByName` ignores the launch allowlist** — it checks registry membership only, which is exactly what lets `enable_toolset` escalate; it also means the allowlist is a default, not a sandbox (fine: this is a token-hygiene mechanism, not a security boundary). **(4) Fork identity** — a fork replays the source's captured argv including `--tools`, so forks inherit the source's profile coherently. **(5) Static tool names in frontmatter** — an unknown name in `tools:` is silently ignored by pi, so a renamed extension tool degrades soft (the role loses it until the frontmatter is fixed); acceptable for a prototype, and the dev-verify smoke below catches the common cases.
</Callout>
