# Reword a file where you read its changes, without clicking Edit

**Goal.** "Being able to see what's changed and then edit the file directly in the change view seems to me like the best approach." When an agent's wording in a docstring or a prompt is not quite right, you fix it in the comparison with the original still beside it. Today you click Edit and lose both the comparison and your place.

**You'll know it works when.**

- You open a changed file from Files under "Since your message", "Changes (branch)" or "Uncommitted", click a word on the right-hand side and type. The file on disk has your wording about half a second later, and you never clicked Edit.
- While you type, the left-hand side still shows the original. When you press Escape or click away, the red and green word marks come back and show your wording against the original.
- A comment you left on a line still reaches the agent pointing at that line after you typed new lines in above it.
- Once you stop typing, the "n of m" change counter and the change bar on the right edge agree with the file.
- Reading line 1,570 of a long file, you click Edit and the editor opens at line 1,570. Show changes brings you back to the same place.
- In an "Earlier" comparison, or in a file over about 5,000 lines, a click does not start typing, and Edit works as it does today.
- **Must not:** stutter more than today's editor while you type, or be slower over the tailnet or the relay than Edit is today.
- **Must not:** stop accepting typing when an agent writes the file underneath you, or lose more of your typing than today's editor does.
- **Must not:** change anything about reading: comments, the author card, "Query author", the unified view.

**Approaches in play.**

- Typing starts on a click in the right-hand side and ends on Escape or a click elsewhere. It uses the editing support in the diff library the comparison is already drawn with. _Your pick, and what the spike prototyped._
- Dropped: always typeable. The library hides the green word marks for as long as typing is on, and those marks are how you read a wording change.
- Dropped: changed files open straight in the editor. Typing is immediate, but the comparison, which is why you opened the file, is gone.
- Dropped: the editor shows bars beside the lines the agent changed. Cheaper, but it shows where the text changed and not what it said before.

**Decided.** Your answers to the spike, quoted:

- "Go: build option 3 in the click-to-type form, plus option 1." Option 1 is Edit keeping your place.
- "Click to start, Escape or click away to finish."
- Earlier comparisons: "Stay read-only; use Since your message or Edit to change the file."
- Your condition on that: "Provided it only *past* states - If I'm comparing the current to the most recent (the last turn), or current to origin, then I would expect to be able to edit". So typing is on in every comparison whose right-hand side is the file as it is now. It is off only when both sides are past states.
- Files over about 5,000 lines: "Stay read-only, Edit as today."

- _Assumed:_ where typing is off, the view says so in a few words instead of silently ignoring the click; redirect if you would rather it stayed quiet.
- _Assumed:_ web and desktop only, because the phone app has no whole-file comparison.

**Not doing.** Typing in the rendered view of a Markdown or MDX file. Keeping the green word marks visible while you type (a limit of the library, worked around by click-to-type and not fixed). Any change to how saving works: it stays automatic, as in today's editor.

**Still unknown.**

- Is typing as smooth as today's editor on your machine in the built app? The spike compared two runs per file in a development build, where the noise was as large as the differences. Measuring again on the build settles it, and so does your own typing.
- Does a file between about 3,400 and 5,000 lines stay smooth? Nobody measured that band. The build measures it; if it stutters, where typing switches off comes back to you as one question.
- What happens to your last half-second of typing when an agent writes the file at that moment, and does it all hold over the tailnet? Both were read from the code in the spike and never run. A live check on a real thread with an agent writing settles them.
