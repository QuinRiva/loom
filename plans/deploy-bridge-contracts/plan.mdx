# Deploy safety: keep the Slack bridge matched to the running cockpit

**Objective.** Make the deployed Slack bridge decode WebSocket traffic with the
**same contracts the running cockpit was built from**, and make every cockpit
release flip re-match the bridge to the release that is actually running — so a
deploy can never leave Carl without Slack access to loom.

**Done when** all of the following hold:

- The bridge resolves `@t3tools/contracts` **and** its `effect` instance through
  the cockpit release store's `current` symlink, not through the `~/loom` dev
  checkout.
- `deployctl promote` and `deployctl rollbackTo` restart the bridge as part of
  the sequence, so the bridge's in-memory modules always come from the release
  the cockpit is running.
- Every deploy outcome — success, stage-one failure, soak failure, rollback
  failure, bridge crash-loop, deployd death mid-promotion, host reboot
  mid-promotion — ends with either a healthy bridge or a documented, verified,
  non-Slack recovery path.
- The new sequence is exercised end-to-end on throwaway systemd units and a
  scratch release store **before** it is used on a real deploy.

<Callout tone="decision">
  This is operational tooling whose whole job is protecting the human's access to
  loom, so the invariant above gets a production bar. Everything else stays
  minimal: no new daemons, no new config keys beyond what the invariant needs,
  and no changes at all to the bridge's `src/`.
</Callout>

## What happened, and what is actually load-bearing today

On 2026-09-22 02:44Z a `deployctl deploy cockpit main` promoted loom
`576d1e89e8` (the whole post-pull-7 stack). Build, smoke boot, stage-one and
stage-two all passed; the soak failed ten seconds in with `soak FAILED: bridge
health dropped`, deployctl auto-rolled back to `5c350f7` and restored the DB
snapshot, and the rollback was healthy.

The bridge decodes cockpit WS frames with `@t3tools/contracts`, resolved through
a symlink that `linkContracts()` writes into each bridge release:
`~/loom-bridge-releases/current/node_modules/@t3tools/contracts` →
`/home/Carl/loom/packages/contracts`. `~/loom` is a **dev checkout**, currently
parked on branch `t3code/awaiting-acceptance-hold` at `c06ebec1bf`. Upstream pull
7 removed the project field `defaultStartFromOrigin`; the bridge's strict Effect
Schema decoder rejected the first shell snapshot from the new server
(`SchemaError: Missing key at [0]["snapshot"]["projects"][0]["defaultStartFromOrigin"]`),
dropped its loom connection, and `/healthz` went to `loom: disconnected`.

Two facts make this more than a one-off:

<Callout tone="risk">
  **The production bridge already decodes with contracts that do not match the
  running cockpit.** `~/loom/packages/contracts` resolves `effect@4.0.0-beta.78`;
  the running release `20260920-151345-5c350f7` resolves
  `effect@4.0.0-beta.103`. Today's bridge is green only because the shell-snapshot
  shape happens to be compatible between those two commits. Nothing enforces it,
  and `REFRESH_CHECKOUTS` is unset in `deployd.env`, so `~/loom` is never
  fast-forwarded on promote.
</Callout>

<Callout tone="risk">
  **Even correct contracts only take effect at the bridge's next restart.**
  `promote()` and `rollbackTo()` restart the cockpit unit and never touch the
  bridge, so a running bridge keeps the previous release's modules in memory
  across a flip.
</Callout>

## Fix 1 — the bridge shares the running release's contracts *and* its effect instance

### The decision

The bridge release's `node_modules` gets **two** symlinks, both written by
deployctl after `npm ci`, both pointing through the cockpit store's stable
`current` path:

<Code
  language="text"
  caption="Links written into each bridge release at build time"
  code={
    "<bridge-release>/node_modules/@t3tools/contracts\n  -> /home/Carl/loom-releases/current/packages/contracts\n\n<bridge-release>/node_modules/effect\n  -> /home/Carl/loom-releases/current/packages/contracts/node_modules/effect\n     (itself a relative pnpm link into that release's .pnpm store)\n"
  }
/>

The second link is the finding that changes the shape of the fix. Under
`effect@4.0.0-rc.115`, **two physical copies of effect no longer interoperate**:
the sibling probe showed that a byte-identical `cp -rL` copy of the same effect
build fails Schema decoding where a symlink to the same directory passes. Schema
decoding is module-identity sensitive, so "same version" is not enough — the
bridge must resolve to the **same directory** the contracts package resolves to.
Because Node resolves symlinks by default, both links land on the same realpath
inside the promoted release, and the identity holds.

Two supporting changes ride along:

- `package.json`: `devDependencies.typescript` `~5.7.0` → `7.0.2`. The bridge's
  build gate (`npm run typecheck && npm test`) typechecks **contracts' own
  source** through `export * from "./settings.ts"`; TypeScript 5.7.3 widens
  `Effect.succeed("enter")` to `string` and reports two errors inside the
  contracts package that loom itself never sees (the post-pull-7 release pins
  `typescript: 7.0.2`; the release the bridge is first built against,
  `20260920-151345-5c350f7`, pins `~6.0.3` — the bridge installs its own either
  way, and 7.0.2 is clean against both).
- **Checked precondition, not an assumption:** `typescript@7.0.2` and
  `effect@4.0.0-rc.115` both resolve on `registry.npmjs.org`, so `npm ci` in a
  release dir installs them without reaching into any pnpm store.
- `package.json`: `dependencies.effect` `4.0.0-beta.78` → `4.0.0-rc.115`. The
  relink overwrites whatever `npm ci` installs, but the manifest and lockfile
  should not lie about what the code is compiled against.

<Callout tone="warning">
  `CONTRACTS_DIR` needs **no new env key**. `loadDeployConfig` already computes
  `cockpitRoot` (it uses it for `spoolRoot`), so the bridge's `contractsDir`
  default becomes `join(cockpitRoot, "current", "packages", "contracts")`. That
  keeps the scratch self-test honest for free: a test run with a scratch
  `DEPLOYCTL_RELEASES_ROOT` gets a scratch contracts dir automatically.
</Callout>

### What the rematch does — and the precondition that guards it

The rematch is **a restart and nothing else**, guarded to the cockpit target only
(`cfg.stage2` is already the flag that means "this target's health depends on the
bridge"). It does not re-point any links: a bridge release built with this change
names the stable `current` path, which never changes, so re-asserting its links
would be a no-op.

The interesting case is the release built *before* this change — today's
`20260829-083037-77c4a0c`, whose `node_modules/@t3tools/contracts` points at
`~/loom` and whose `node_modules/effect` is a **real directory** of
`effect@4.0.0-beta.78`. That release is reachable automatically, not just by a
human ignoring a runbook note: a bridge promote that fails its gate auto-rolls
back to it. Restarting it after a cockpit flip changes nothing (it re-resolves
`~/loom`), and *partly* re-pointing it — contracts at the new release, effect
still its own copy — is strictly worse than leaving it alone, because that is the
exact skew the probe measured as two typecheck errors plus a runtime decode
failure on `thread.user-input.respond`, a payload the bridge actually sends.

So the pre-fix release is handled by a **precondition, not a repair**:
`cmdDeploy`'s existing preflight block (free disk, no in-flight marker) gains one
more check, and a **cockpit** promote is **refused before anything is touched**
while the current bridge release cannot follow `current`. The operator's remedy
is one command (`deployctl deploy bridge master`), it costs no downtime, and it
turns what would otherwise be an unenforceable runbook sentence into a mechanical
gate.

The gate carries the **same `cfg.stage2` guard as the rematch**, and for the same
reason stated the other way round: `cmdDeploy` and `promote()` are both
target-generic, so an unguarded check would refuse `deploy bridge` — which is
precisely the remedy, and precisely step 2 of the landing order below. **A bridge
deploy is never refused by this gate.**

<Callout tone="decision">
  This is deliberately **not** a heal. Healing would mean deployctl running
  `rm -rf` inside a release directory on the very path whose job is protecting
  access — and if the replacement target were ever missing, the bridge would be
  left with no `effect` at all. Refusing at preflight is non-destructive, costs
  nothing when the bridge is correctly wired, and fails at the one moment when
  nothing has been stopped, flipped or restarted.
</Callout>

`deployctl restart cockpit` deliberately does not rematch: a plain restart does
not move `current`, so the bridge already resolves the same release. `rollbackTo`
is never guarded — it is the recovery path, and restarting a pre-fix bridge
there is a harmless no-op that leaves it exactly as it was.

### (b) A bridge release built against cockpit N, running against cockpit N+1

**It stays valid**, and the condition is precise. The links are version-agnostic
paths that follow `current`, so the running bridge always decodes with the
running cockpit's schemas: decode mismatch is structurally impossible, whatever
the bridge was built against. The build gate proves something narrower — that the
bridge's *source* typechecks against the contracts that were current at build
time.

That stops being sufficient the day a cockpit release changes the **API surface
the bridge calls**: one of the ten `ORCHESTRATION_WS_METHODS` names, one of the
five command-builder payload shapes (which bypass the type checker via
`as unknown as`), or a field the bridge reads. A type-only break is invisible at
runtime (the bridge runs under `tsx`, which strips types without checking them);
a *runtime* break shows up as failing RPC calls. Detecting that class **before**
the flip is the job of the deferred promote preflight described below — it is not
required by the invariant, because stage-two plus auto-rollback already preserves
access, but it is the difference between a failed deploy and no deploy at all.

### (c) What the deploy path still needs `~/loom` for

Nothing. After this change no production path reads `~/loom`:

- `deployd` and `deployctl` never import contracts.
- Bridge releases resolve contracts and effect through `loom-releases/current`.
- `package.json` keeps the `file:../loom/packages/contracts` specifier only
  because npm has no way to express an absolute one; `npm ci` in a release dir
  produces a dangling link that deployctl immediately overwrites.

`~/loom` remains a **dev-only** dependency: `npm ci` in `~/loom-slack-bridge`
still resolves that relative path. To stop the dev loop from disagreeing with
production, a single `npm run link:contracts` script points a dev checkout at
`loom-releases/current` too — one package.json line, no separate shell script,
and opt-in so `npm ci` still works on a machine with no release store. Leave
`REFRESH_CHECKOUTS` unset — fast-forwarding
`~/loom` on promote would re-introduce the dev checkout as a production input,
and its guard would skip it anyway while the checkout sits on
`t3code/awaiting-acceptance-hold`.

## Landing the fix itself

The order matters, because deployd executes jobs using the deploy code from
`~/loom-bridge-releases/current` — i.e. the **previous** bridge release. A plain
`deployctl deploy bridge master` would therefore build the new release with the
*old* wiring (contracts at `~/loom`, no effect link) while installing the new
`package.json` pins, which is an untested skew that would most likely fail its
own build gate.

<Callout tone="decision">
  Break the circle with the escape hatch that exists for exactly this case:
  `--inline`, run from the **dev checkout** over ssh. `deploy/deployctl` is a
  four-line bash launcher around plain `node deployctl.ts`, so it needs no
  `node_modules` and runs the checkout's own (new) pipeline code.
</Callout>

<Callout tone="risk">
  **Step 2 must not run in a bare foreground ssh session.** It is a ~4-minute
  mutating promote: it writes `~/loom-bridge-releases/deploy-in-progress`, stops
  the unit, snapshots, flips, starts, gates and soaks. A dropped ssh SIGHUPs it;
  if it dies between the stop and the start, the bridge is left **down** and the
  surviving marker trips deployd's `heldBy()` recovery gate, which holds queued
  work for **every** target, including step 4. Run it detached, matching the
  pattern the runbook already uses for disruptive cutovers:
  `systemd-run --user --unit=loom-bridge-inline-deploy --collect ~/loom-slack-bridge/deploy/deployctl deploy bridge master --inline`,

  (`tmux` or `setsid` are equivalent). Recovery if it does die is two commands
  over a fresh ssh: `systemctl --user start loom-slack-bridge`, then
  `deployctl recover bridge --clear`.
</Callout>

<Callout tone="warning">
  Step 3 is easy to forget and silently fatal to the fix: until deployd is
  restarted it keeps executing the *previous* bridge release's `deploy/*.ts`, so
  the cockpit promote in step 4 would run without `rematchBridge`. The unit file
  already documents this caveat; the runbook section should repeat it as a numbered
  step, not a note.
</Callout>

## Verification, before any of it touches production

Three layers, in order. Layers 1 and 2 touch nothing outside `/tmp` and
throwaway systemd units.

**1. Offline compatibility matrix (already run).** In a scratch clone, symlink
contracts and effect at a release dir and run `npm run typecheck && npm test`.
Both corners that matter are green — see the evidence table above. Re-run it on
the actual PR branch before proposing the deploy.

**2. Scratch-store self-test of the new sequence.** Extend
`scripts/phase3-selftest.sh`, which already stands up a throwaway cockpit unit, a
throwaway deployd, a mock Slack API and a scratch release store, and asserts
deployd's PID is unchanged across a cockpit restart. Add a throwaway **bridge**
unit whose `/healthz` reports `loom: connected` only when a version marker it
read **at process start** equals the marker in the release `current` points at
now. That models the in-memory-modules coupling exactly, with no real contracts
involved.

<Callout tone="risk">
  **The harness must be re-scoped before it can be given a bridge release, or it
  will restart the production bridge.** It currently exports only
  `DEPLOYCTL_BRIDGE_RELEASES_ROOT` (script line 196, and the throwaway deployd's
  `Environment=` at line 226). `DEPLOYCTL_BRIDGE_UNIT` and
  `DEPLOYCTL_BRIDGE_HEALTHZ_URL` are unset, so `loadDeployConfig("bridge")`
  yields the **production** `loom-slack-bridge` unit and port 13901. Today that
  is masked by accident: the scratch bridge store has no `current`, so a rematch
  would return early, but adding a throwaway bridge release, which this plan
  requires, is precisely what removes that protection. Both names must be set in
  the client env block **and** in the deployd unit's `Environment=` lines
  (systemd does not inherit the caller's environment, and `rematchBridge` runs
  inside deployd), and the suite must assert the real `loom-slack-bridge`
  MainPID is unchanged across the whole run.
</Callout>

## Deferred hardening (a separate change, after the deploy lands)

Neither item is required by the invariant. Recommend landing them only once the
core fix has survived a real deploy.

**A. Bridge *contract* preflight in the cockpit promote** — distinct from the
bridge-*wiring* preflight above, which is part of the core change and only asks
whether the bridge release can follow `current` at all. This one asks whether the
bridge's code still works against the candidate's contracts. Before the flip, copy
the current bridge release to a scratch dir (`cp -a`, measured at **4.4 s** for
150 MB; a `cp -al` hardlink copy takes 67 ms but is unsafe, because the release
carries a `node_modules/.vite` cache a test run could write through), point the
scratch copy's two links at the **candidate** release, and run
`npm run typecheck` plus a small contract probe that asserts the ten
`ORCHESTRATION_WS_METHODS` still exist in the candidate's `WsRpcGroup` and that
the five command builders still decode against its `ClientOrchestrationCommand`.
Fail the promote before `systemctl stop`, leaving the live system untouched. This
needs two escape-hatch flags so the two build gates cannot deadlock when a bridge
change must accompany a cockpit change: `--skip-bridge-preflight` on
`deploy|promote cockpit`, and `--contracts-from=<cockpit-release-id>` on
`deploy bridge`.

**B. Make `/healthz` tell the truth about decoding.** Today `loom` means "the
WebSocket is open": on 22 Sep stage-two passed at 02:50:13 and the decode failure
dropped the connection at 02:50:23. Worse, `bridgeHealthy()` is a single
point-in-time poll and `stageTwo()` returns on its first success, so a
crash-looping bridge can show a green `/healthz` between restarts. What actually
protects the invariant today is the 300 s soak, which re-polls every 10 s and is
what caught 22 Sep on its first poll. Redefining `loom` as "connected **and** at
least one frame decoded since connect" — the shell snapshot arrives
automatically, so this is roughly ten lines in `src/main.ts` — makes stage-two a
real proof, and makes `ROLLBACK OK` mean the bridge is genuinely usable rather
than merely socketed. Until then, no cell of the matrix above should be read as
"stage two proved the bridge decodes" — it proves the socket opened.

## Scope and non-goals

- **No changes to the bridge's `src/`** in this change. The probe verified the
  bridge's logic is fully compatible with the post-pull-7 contracts (clean
  typecheck, 435/435, all command builders and RPC methods present); every break
  is dependency wiring. Item B above is the only contemplated `src/` change and
  it is deferred.
- **No loom-side changes.** Nothing in this plan goes through `pnpm ship`.
- **The unrelated noise stays out of scope.** The ~34 `OrchestrationGetSnapshotError:
  Thread ... was not found` lines on every bridge reconnect are stale mappings and
  pre-date this incident (they appear identically on every reconnect since at
  least 19 Sep); the Slack `chat.update` rate-limit storm is likewise pre-existing.
- **No new daemons, no new spool semantics, no change to the at-most-once or
  recovery-hold protocols.**
- **The branch `t3code/assistant-delivery-ledger`** (2 commits ahead of master)
  adds no new contract surface and should inherit this fix unchanged. Plan for
  `master`; if the human wants it to ride along, merge it into the same branch
  before step 1 and re-run the offline matrix — no other step changes.
