# Usage visibility: an always-on subscription meter, and real Pi numbers on the Usage page

## Objective

Two things are missing from the deployed loom. There is no surface anywhere that tells you where you stand against your subscription windows without navigating to a page — the sidebar quota pill went with PR #210. And upstream's Usage page reports zero cost and zero tokens for every window, because its scanner reads Codex/Claude/Grok CLI transcripts and this fork drives Pi.

This plan delivers:

- **A subscription meter** in the sidebar footer, mirrored into the chat header when the sidebar is closed, fed from the limits data upstream's Limits page already receives — no new server work, no new wire traffic.
- **A Pi arm for upstream's usage scanner**, so Cost, Tokens, the hourly burn chart and the model breakdown carry real numbers.
- **A correction to what loom polls**, because the quota it currently reports is not the quota your Claude turns actually consume.

Done means: the meter is visible in the chat view in both sidebar states and matches Usage → Limits; the Cost and Tokens tabs show non-zero totals with a per-model breakdown for a real window; and Limits reports the accounts that actually serve your traffic.

## What is actually true today

Three findings from the deployed cockpit's state and the code. They change the shape of the work, so they come before the design.

### The Cost and Tokens tabs are not broken — they have nothing to read

`apps/server/src/usage/UsageService.ts` scans provider CLI transcript directories: `~/.claude/projects`, `~/.codex/sessions`, `~/.grok/sessions`. On the cockpit host, **zero `.jsonl` files under either Claude's or Codex's directory have been modified in the last 40 days**. There is no Pi arm. So every window, on every tab except Limits, is structurally empty — not intermittently, always.

### The numbers that appeared and vanished were the Limits tab

`apps/web/src/components/usage/usagePagePreferences.ts` defaults the page to `metric: "limits"`, `windowDays: 30`, and persists the last choice. Opening `/usage` therefore lands on Limits, which renders real gauges. The screenshot in the report shows Tokens selected and Past 24h — two deliberate moves away from that default. The numbers did not disappear; the tab changed to one that has never had data.

<Callout tone="info">
  There is no client-side defect to fix here. The only code change that makes those tabs honest is the
  Pi arm in part B — and it is worth noting that the same page already contains an hourly burn chart
  and a per-model breakdown table, so feeding it Pi data restores two of the four things the retired
  dashboard lost, at no extra cost.
</Callout>

### Loom is polling the wrong Claude quota

This is the finding that matters most, and it is a configuration gap rather than a bug.

`apps/server/src/provider/Layers/SubscriptionUsagePoller.ts` reads `~/.pi/agent/auth.json` and polls exactly the two tokens it finds there: one `anthropic` and one `openai-codex`. Meanwhile `projection_usage_ledger` records `provider_id = "cliproxy"` for every Claude turn — Claude traffic is routed through the CLIProxyAPI hub at `~/cli-proxy`, which has **five** Claude accounts in its `auths/` directory. The hub's quota is the quota being spent; the `anthropic` token in `auth.json` is a different path to the same vendor and need not be the account that served the turn.

Upstream already ships a reader for exactly this hub — `apps/server/src/usage/UsageLimitSources.ts` plus `apps/server/src/usage/cliproxyApi.ts`, driven by the `usageLimitSources` server setting. That setting is **empty** on the deployed instance. Registering the hub is a settings change with no code behind it, and it is what turns "my usage across my subs" from one opaque number into five real accounts with emails, plans, reset times and reset credits.

<Callout tone="risk">
  Building the meter before registering the hub would ship a confident-looking indicator over the
  wrong account. Slice 0 is therefore a prerequisite, not an optional extra.
</Callout>

## Part B — a Pi arm for the usage scanner

### The options

Upstream's aggregation takes `UsageRecord` values — provider, timestamp, model, session id, four token buckets, an optional provider-reported cost, and a dedupe key — and folds them into `(day, hour, provider, model)` buckets. Anything that can produce `UsageRecord` values slots in. There are two credible producers.

<Callout tone="decision">
  Read pi transcripts. It is the arm upstream's design is shaped for, it needs no new dependency, and
  the measured corpus sits inside upstream's own stated performance envelope.

The performance line is the one that could have gone the other way, so it was measured rather than assumed. Upstream documents a cold 30-day scan of about 1.4 GB landing in two to three seconds. Pi's session corpus is 5.37 GB in total, but the mtime prefilter only opens files inside the window: **0.48 GB for 30 days, 3.34 GB for 90**. The 30-day case is a third of what upstream already considers acceptable, and every subsequent scan re-reads only appended bytes.

Reading the ledger would be defensible, but it buys nothing the transcripts do not already give, misses pi runs outside loom, and pays for it by introducing a database dependency into a module whose every abstraction — the per-file parse cache, the byte-resume position, the device/inode source fingerprint — assumes files. The ledger keeps being written and stays available for the thread-attribution work in part D.

Three details decide whether the numbers come out right.

**The session id comes from the filename, not the line.** Pi writes `<timestamp>_<sessionId>.jsonl`, and the session id is the loom thread id with non-id characters replaced. Only the header line carries the id, so deriving it from the basename keeps the parser stateless — which means the byte-resume path needs no reducer state, unlike Codex.

**The dedupe key is composite.** Pi entry ids are eight hex characters. Across 171,000 records a bare id would collide by birthday alone and silently drop real usage. Keying on id, timestamp and total tokens together makes a false match require all three to agree, while a genuine forked-session copy still matches on all three. If pi forks turn out not to copy entry ids at all, the key simply never fires and nothing is lost.

**Pi is its own provider kind.** `UsageProviderKind` gains `"pi"` and `USAGE_CONTRACT_VERSION` goes to 6; `USAGE_MERGE_COMPATIBLE_SINCE` stays at 4, for the reason the version-5 note already gives — older environments' Claude and Codex buckets remain valid. The alternative, mapping pi's own `provider` field onto the existing kinds, would need no contract change but would report a cliproxy-routed Claude turn as "Claude Code" and risk double-counting against a real Claude transcript. Honest attribution is worth the literal.

### What the tabs will show, and one honest gap

Cost is provider-reported, so `priceUsage` takes it verbatim and marks the bucket `providerReported` — the rate table is not consulted and cannot be wrong. **Cache savings is the exception**: it needs a rate-table hit on the model name, and pi's names are fork aliases that LiteLLM does not carry, so the figure reads `$0.00` until someone adds an override. The page already ships the surface for that, `UsagePriceOverrides` on the Usage page, so this is a setting rather than a defect. It should be stated in the PR body rather than quietly shipped.

## Risks

**Registering the hub may double-report an account.** `collectLimitAccounts` keys native accounts by driver and email; loom's pi instance reports no email, and hub accounts arrive with driver `claudeAgent`. The subscription behind `auth.json` may therefore appear both as a pi window and as a hub account, under different labels. This is visible immediately on the Limits page after slice 0, and is the subject of an open question below.

**The meter re-renders with the presentations atom.** That atom updates on any `serverConfig` change, not just limits. The derive is memoised on the limits slice and the component is wrapped in `memo`, so a provider-status change costs a shallow compare rather than a re-layout. Worth confirming under a profiler while a turn is streaming, since the sidebar is on screen constantly.

**A 90-day cold scan reads 3.34 GB.** One-off, and only if the 90-day window is selected; subsequent scans are incremental. If it proves slow in practice, the retention-window cap is already a constant in `UsageService.ts`.

**Contract version bump.** Environments still on version 5 keep contributing their Claude and Codex buckets through `USAGE_MERGE_COMPATIBLE_SINCE`; they simply report no Pi data. No coordinated upgrade is needed.

Gates first: `vp run typecheck` and `vp check` both pass, per this repo's completion rules, and the `pnpm ship` marker sweep is clean for every hunk added to an upstream-owned file.

Then the end-to-end pass, on a dev instance seeded from a copy of the cockpit database — `VACUUM INTO` a snapshot into the worktree's own `.t3/userdata`, never a server against `~/.t3/cockpit/userdata`:

1. Start the dev instance with the dev-verify recipe in `docs/dev-site-testing.md` and open a thread.
2. **Meter present and correct.** The sidebar footer shows one bar per subscription. Cross-check each percentage against Usage → Limits for the same account: they must agree, because they are the same numbers.
3. **Meter survives the sidebar.** Collapse the sidebar; the chat-header chip appears with the same figure. Re-open it; the chip goes and the footer meter returns.
4. **Near-exhaustion state.** Point the dev instance at a hand-edited settings snapshot that reports a window above 80 and another above 100, and confirm the warning and destructive tones, on both the bar and the popover.
5. **Cost and Tokens carry real numbers.** Open Usage → Tokens, Past 24h. Processed tokens, cached input, uncached input and output are all non-zero; the model breakdown lists the pi models actually used; the hourly chart is populated. Switch to Cost and confirm a plausible total against the ledger for the same window — `select round(sum(cost_usd),2) from projection_usage_ledger where created_at > ...` is an independent second opinion on the same turns.
6. **The scan stays warm.** Refresh the page and confirm the reported scan duration drops sharply on the second read, proving the parse cache is being hit rather than the corpus re-read.
7. **The empty case is still honest.** Select a 90-day window on an environment with no pi sessions and confirm the source row reports missing rather than silently reading zero.
