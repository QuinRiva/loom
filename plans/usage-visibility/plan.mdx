# Usage visibility: an always-on subscription meter, and real Pi numbers on the Usage page

## Objective

Two things are missing from the deployed loom. There is no surface anywhere that tells you where you stand against your subscription windows without navigating to a page — the sidebar quota pill went with PR #210. And upstream's Usage page reports zero cost and zero tokens for every window, because its scanner reads Codex/Claude/Grok CLI transcripts and this fork drives Pi.

This plan delivers:

- **A subscription meter** in the sidebar footer, mirrored into the chat header when the sidebar is closed, fed from the limits data upstream's Limits page already receives — no new server work, no new wire traffic.
- **A Pi arm for upstream's usage scanner**, so Cost, Tokens, the hourly burn chart and the model breakdown carry real numbers.
- **A correction to what loom polls**, because the quota it currently reports is not the quota your Claude turns actually consume.

Done means: the meter is visible in the chat view in both sidebar states and matches Usage → Limits; the Cost and Tokens tabs show non-zero totals with a per-model breakdown for a real window; and Limits reports the accounts that actually serve your traffic.

## What is actually true today

Three findings from the deployed cockpit's state and the code. They change the shape of the work, so they come before the design.

### The Cost and Tokens tabs are not broken — they have nothing to read

`apps/server/src/usage/UsageService.ts` scans provider CLI transcript directories: `~/.claude/projects`, `~/.codex/sessions`, `~/.grok/sessions`. On the cockpit host, **zero `.jsonl` files under either Claude's or Codex's directory have been modified in the last 40 days**. There is no Pi arm. So every window, on every tab except Limits, is structurally empty — not intermittently, always.

### The page opens on a tab that works, next to tabs that never have

`apps/web/src/components/usage/usagePagePreferences.ts` defaults the page to `metric: "limits"`, `windowDays: 30`, and persists the last choice. Opening `/usage` therefore lands on Limits, which renders real gauges, while the screenshot in the report shows Tokens and Past 24h — two deliberate moves away from that default. Whether that is the whole story is taken up in part C.

<Callout tone="info">
  There is no client-side defect to fix here. The only code change that makes those tabs honest is the
  Pi arm in part B — and it is worth noting that the same page already contains an hourly burn chart
  and a per-model breakdown table, so feeding it Pi data restores two of the four things the retired
  dashboard lost, at no extra cost.
</Callout>

### Loom is polling the wrong Claude quota

This is the finding that matters most, and it is a configuration gap rather than a bug.

`apps/server/src/provider/Layers/SubscriptionUsagePoller.ts` reads `~/.pi/agent/auth.json` and polls exactly the two tokens it finds there: one `anthropic` and one `openai-codex`. Meanwhile `projection_usage_ledger` records `provider_id = "cliproxy"` for every Claude turn — Claude traffic is routed through the CLIProxyAPI hub at `~/cli-proxy`, which has **five** Claude accounts in its `auths/` directory. The hub's quota is the quota being spent; the `anthropic` token in `auth.json` is a different path to the same vendor and need not be the account that served the turn.

Upstream already ships a reader for exactly this hub — `apps/server/src/usage/UsageLimitSources.ts` plus `apps/server/src/usage/cliproxyApi.ts`, driven by the `usageLimitSources` server setting. That setting is **empty** on the deployed instance. Registering the hub is a settings change with no code behind it, and it is what turns "my usage across my subs" from one opaque number into five real accounts with emails, plans, reset times and reset credits.

<Callout tone="risk">
  Building the meter before registering the hub would ship a confident-looking indicator over the
  wrong account. Slice 0 is therefore a prerequisite, not an optional extra.
</Callout>

### The one piece of real logic

Loom's own accounts arrive differently from hub accounts, and the meter has to reconcile them. `SubscriptionUsagePoller` folds every account it polls into the **single** `pi` provider instance's `usageLimits.windows`, encoding the account into each window id. `packages/shared/src/usageWindowId.ts` owns that format and already has the decoder.

The new derive module splits the pi instance's flat window list back into one synthetic `LimitAccount` per decoded account, then hands them to upstream's `collectLimitPools`. The split has to do **three** things, and skipping any of them yields a surface that does not match the wireframe above.

**Split after `collectLimitAccounts`, never inside it.** That function merges by driver and email; loom's synthetic accounts have neither, so every one of them would collide on the single pi instance key. The split operates on the array it returns.

**Map the decoded `accountKey` to a real driver.** `collectLimitPools` groups by `account.driver`. Leaving the synthetic accounts as driver `pi` collapses Anthropic and Codex into one pool whose percentage is their mean — one bar labelled *pi*, not the Claude and Codex bars above. The poller writes `providerInstanceId ?? providerName` into `accountKey`, so for the two direct-auth accounts it is literally `claudeAgent` and `codex` (`SubscriptionUsagePoller.ts`, `feed`); map those to the matching driver and leave anything unrecognised as `pi`.

**Rewrite each window id to its account-independent part.** `poolWindows` keys by `` `${kind}:${id}` ``, and loom's ids are already account-unique by construction, so an unmodified split produces one single-member pool per window — exactly the flat run the split exists to remove. Re-keying the id to `kind[:scope]` makes sibling accounts' windows share a key, which is what forms a pooled bar.

<Code
  filename="apps/web/src/loom/subscriptionMeter.ts"

So Codex pools, and **Claude does not**: inside the one `claudeAgent` pool, `session:primary` and `session:five_hour` stay separate, and a subscription reported both directly and through the hub draws two session bars. The duplicate is a configuration artefact rather than a modelling one — after slice 0 the hub reports the Claude accounts properly, with emails, plans and reset credits, which makes the direct-auth Anthropic reading redundant by construction. It is therefore left as an open risk on both surfaces and settled at source by the poller question below, rather than papered over in the client.

The client-side alternative, if the answer there is to keep both readings: re-key loom's windows into the target driver's own vocabulary instead of the decoded kind — `primary → five_hour`, `secondary → seven_day`, scoped → `seven_day_<slug>` under `claudeUsageLimits.ts`'s own rule, leaving Codex as-is. That makes the two pool. It is not the default because it hard-codes a vendor's id strings into a loom module, and if upstream renames a window the pooling stops silently and the duplicate bar returns with nothing failing.

One rendering note: `LimitPoolWindow.label` is inherited from whichever member happened to be first, so the meter labels its rows from the window `kind` rather than trusting that string.

### State tiers

Against `docs/architecture/loom-ui-state-tiers.md`, the meter is **tier 4 throughout** — transient render state. It persists nothing: the pools are derived per render from the presentations atom, and the only mutable state is the 30-second countdown tick, which is component-lifetime `useState`. There is no tier 1 or tier 2 state to migrate, and no `uiStateStore` key to orphan.

The chat-header chip is the one place the doctrine bites. It **reads** the sidebar's open state to decide whether to render, and must never write it — an indicator that nudged the sidebar open or closed would be precisely the automatic override the seed-not-override rule forbids. Rendering is a pure function of `useSidebar().open`; there is no effect, no store write, and no reseeding flag, because the chip has no state of its own to seed.

### Behaviour while limits are unknown

The meter must handle the empty case deliberately, because it is on screen permanently. Provider usage limits are runtime snapshot state, not persisted config: they exist only after `SubscriptionUsagePoller` has published a reading into the instance snapshot, and a server restart or socket reconnect delivers a `serverConfig` with none yet. `collectLimitAccounts` skips a provider whose limits are absent or notice-bearing, so during that gap the derive legitimately returns no pools — and the poller's base cadence is five minutes, backing off to thirty after consecutive failures.

Rendering nothing during that gap makes a permanent surface blink out and return, which is worse on the sidebar than on a page. The meter therefore **holds its last non-empty pools for the lifetime of the mount** and marks them stale — dimmed, with the age in the popover — rather than unmounting. It renders nothing at all only when it has never had a reading. This is still tier 4: the retained value dies with the component, and a reload correctly shows nothing until the first publish.

## Part B — a Pi arm for the usage scanner

### The options

Upstream's aggregation takes `UsageRecord` values — provider, timestamp, model, session id, four token buckets, an optional provider-reported cost, and a dedupe key — and folds them into `(day, hour, provider, model)` buckets. Anything that can produce `UsageRecord` values slots in. There are two credible producers.

  Read pi transcripts. It is the arm upstream's design is shaped for, it needs no new dependency, and
  the measured corpus sits inside upstream's own stated performance envelope.

The performance line is the one that could have gone the other way, so it was measured rather than assumed. Upstream documents a cold 30-day scan of about 1.4 GB landing in two to three seconds. Pi's session corpus is 5.37 GB in total, but the mtime prefilter only opens files inside the window: **0.48 GB for 30 days, 3.34 GB for 90**. The 30-day case is a third of what upstream already considers acceptable, and every subsequent scan re-reads only appended bytes.

That argument rests entirely on the persisted scan cache, which today refuses pi:

<Code
  filename="apps/server/src/usage/usageScanCache.ts"
  language="ts"
  code={"if (entry.p !== \"claude\" && entry.p !== \"codex\" && entry.p !== \"grok\") continue;\n"}

Pi entries serialise correctly and are then dropped on every reload, so each server start would re-parse the whole window rather than reloading the cache. The fix is that one literal. `USAGE_SCAN_CACHE_VERSION` does **not** need bumping — existing version-3 entries stay valid and an unknown provider was already skipped, so there is nothing to migrate and no shim to write. It is easy to miss because nothing fails: the numbers are right and only the timings are wrong, which is why verification below restarts the server rather than only refreshing the page.

Reading the ledger would be defensible, but it buys nothing the transcripts do not already give, misses pi runs outside loom, and pays for it by introducing a database dependency into a module whose every abstraction — the per-file parse cache, the byte-resume position, the device/inode source fingerprint — assumes files. The ledger keeps being written and stays available for the thread-attribution work in part D.

Three details decide whether the numbers come out right.

**The session id comes from the filename, not the line.** Pi writes `<timestamp>_<sessionId>.jsonl`, and the session id is the loom thread id with non-id characters replaced. Only the header line carries the id, so deriving it from the basename keeps the parser stateless — which means the byte-resume path needs no reducer state, unlike Codex.

**The token buckets are copied across, not derived.** Pi's `usage.input` is **exclusive** of the cache buckets — `input + output + cacheRead + cacheWrite` equals its own `totalTokens`, confirmed across sampled records on this host. Both neighbouring arms in the same file do the opposite, computing `uncachedInputTokens` as `inputTokens - cachedInputTokens - cacheCreationTokens`, because Codex and Grok report an inclusive figure. An implementer who copies the adjacent arm clamps pi's uncached input to zero. Because cost is provider-reported, the Cost tab would still look right while the Tokens tab silently under-reported input — and the wrong figure would be baked into the persisted scan cache. There is no subtraction for pi.

**The dedupe key is composite.** Pi entry ids are eight hex characters. Across 171,000 records a bare id collides by birthday with near-certainty and would silently drop real usage. Keying on id, timestamp and total tokens together makes a false match require all three to agree. The key does real work rather than merely guarding a hypothetical: pi's own fork rebuilds the branch as `{ ...entry, parentId }`, preserving `id`, `timestamp` and the message body, so a forked session genuinely duplicates records into a second file.

**Sessions mean threads for pi.** The session id is the loom thread id, so the page's "Sessions" figure — `UsageSource.distinctSessions` — counts threads for pi where it counts CLI sessions for the other providers. Nothing to fix; worth one line in the PR body so nobody reads the two as like for like.

**Pi is its own provider kind.** `UsageProviderKind` gains `"pi"` and `USAGE_CONTRACT_VERSION` goes to 6; `USAGE_MERGE_COMPATIBLE_SINCE` stays at 4, for the reason the version-5 note already gives — older environments' Claude and Codex buckets remain valid. The alternative, mapping pi's own `provider` field onto the existing kinds, would need no contract change but would report a cliproxy-routed Claude turn as "Claude Code" and risk double-counting against a real Claude transcript. Honest attribution is worth the literal.

### What the tabs will show, and one honest gap

Cost is provider-reported, so `priceUsage` takes it verbatim and marks the bucket `providerReported` — the rate table is not consulted and cannot be wrong.

**Cache savings is the exception, and it must be left alone.** That figure needs a rate-table hit on the model name, and pi's names are fork aliases LiteLLM does not carry, so it reads `$0.00`. The tempting remedy — a price override on the Usage page — is actively harmful here, because an override does not merely supply savings rates:

<Code

An override wins outright. The moment one is added for a pi model, every bucket for that model flips from `providerReported` to `modelPriced` and the Cost tab stops showing pi's own per-message cost, showing instead an estimate computed from rates the user invented — for a model LiteLLM has no price for. That trades the authoritative number this whole exercise exists to surface for a guess, and the only hint in the UI is the cost-quality share.

So: leave cache savings at `$0.00`, say why in the PR body, and do **not** recommend an override as a workaround. If the savings figure is later judged worth having, the honest change is to let `cacheSavingsUsd` consult a rate table without letting that table capture `costUsd` — a small, separate change to `priceUsage`, not a setting.

## Part C — the vanished numbers

Two mechanisms can produce what was reported. The query lifecycle rules out a third, and neither survivor is a client defect.

**What the lifecycle rules out.** A fulfilled usage response is not discarded by moving around the page. `usageSummary` is an SWR query with `staleTimeMs: 60_000` (`packages/client-runtime/src/state/server.ts`), keyed per serialised window in `apps/web/src/state/usage.ts`, and `selectMetric` in `UsagePage.tsx` only writes a preference — it triggers no invalidation. So nothing on the Cost or Tokens side can show a number and then take it away; those tabs have never had a number to show on this fork.

**Mechanism 1 — the tab change.** The page opens on Limits, which renders real gauges from the poller. Moving to Tokens replaces them with zeros. From the user's seat that is numbers appearing and then being gone, and it needs no defect; it is also consistent with the screenshot, which is two clicks from the default.

**Mechanism 2 — limits emptying under a reconnect.** Provider usage limits are runtime snapshot state, held in memory by `makeManagedServerProvider` and populated only once `SubscriptionUsagePoller` publishes a reading. A server restart or a socket reconnect delivers a `serverConfig` carrying none, and `collectLimitAccounts` skips any provider whose limits are absent or notice-bearing. Bars drawn from the pre-restart config therefore empty themselves with no user action — and stay empty until the next publish, which is five minutes out at the base cadence and up to thirty after consecutive failures. On a deploy day this is not a hypothetical.

**Which one happened is not determinable from here**, and the plan does not pretend otherwise: the server log line that would date the first publish after restart (`subscription-usage poller: … limits published`) is not readable from this worktree. Both are benign for the Usage page itself.

  Mechanism 2 is not benign for this plan. The meter reads the same atom and would empty the same way

  part A specifies holding the last non-empty reading and marking it stale rather than unmounting.
  The forensic question can stay open; the design requirement it produces cannot.
</Callout>

## Risks

**Registering the hub may double-report a Claude account, on both surfaces.** `collectLimitAccounts` keys native accounts by driver and email; loom's pi instance reports no email, and hub accounts arrive with driver `claudeAgent`. The subscription behind `auth.json` may therefore be counted twice — as a row on the Limits page, and as a second session bar in the meter's Claude pool, since the two sources key their windows differently (`primary` against `five_hour`). Codex is unaffected; its vocabularies already agree. This is visible immediately after slice 0 and is settled by the poller question below, which removes the duplicate at its source rather than reconciling it in the client.

**The meter re-renders with the presentations atom.** That atom updates on any `serverConfig` change, not just limits. The derive is memoised on the limits slice and the component is wrapped in `memo`, so a provider-status change costs a shallow compare rather than a re-layout. Worth confirming under a profiler while a turn is streaming, since the sidebar is on screen constantly.

**A 90-day cold scan reads 3.34 GB.** Only if the 90-day window is selected, and only until the cache is warm. It decays slowly rather than vanishing: `pruneScanCache` evicts by file mtime, and a long-lived loom thread's session file keeps a fresh mtime for months, so its whole history stays cached and re-parsable. Treat the figure as a ceiling. If it proves slow in practice, the retention cap is already a constant in `UsageService.ts`.

**Contract version bump.** Environments still on version 5 keep contributing their Claude and Codex buckets through `USAGE_MERGE_COMPATIBLE_SINCE`; they simply report no Pi data. No coordinated upgrade is needed.
