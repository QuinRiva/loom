# Marking agent-started threads in the sidebar

## Objective

Carl runs a dozen threads at once and does not track titles. When an orchestrator calls the `goal_handoff` tool, the server creates a brand-new **root** thread (own goal, own worktree) and starts it on the agent's brief with nobody pressing Send. That root lands in the sidebar's Active inbox beside the threads Carl opened himself, with nothing to tell them apart, so background agent work gets mistaken for his own or lost. **Done** means: in the left panel, every thread an agent started automatically is recognisable at a glance, on both the card rows (Pinned / Active) and the slim rows (Working / Snoozed / Settled), without reading the title, and from that row Carl can reach the thread that started it. Carl's first idea was a different title colour; he asked what the alternatives are, so this document compares six and recommends one. Nothing is decided until he answers the form at the bottom.

<Callout tone="info">
  Out of scope: duplicate-detection on `goal_handoff` (a separate thread owns it), mobile (the predicate is designed to be shared, but the React Native list is a follow-up), and any regrouping of the sidebar list — goal grouping or drill-ins inside Sidebar v2 were rejected in `docs/upstream-sync/23-sidebar-v2-rehome.md` and this plan does not re-propose them.
</Callout>

## What the server already records

Verified in code; the sidebar is a pure function of the thread **shell** (`OrchestrationV2ThreadShell`, `packages/contracts/src/orchestrationV2.ts`), so the question is what the shell carries.

**The shell already says “an agent created this thread”.** Every shell carries upstream's creation fields `createdBy: "user" | "agent" | "system"` and `creationSource: "web" | "mobile" | "mcp" | "provider" | "server"` (`OrchestrationV2CreationFields`, spread into both `OrchestrationV2AppThread` and `OrchestrationV2ThreadShell`). The `goal_handoff` handler (`apps/server/src/mcp/toolkits/workstream/handlers/goalHandoff.ts`) dispatches `thread.create` with `createdBy: "agent"`, `creationSource: "mcp"`, then `thread.goal.set`, then `ThreadLaunchService.launch` with the brief as the first message (`createdBy: "agent"` again). A thread Carl opens in the web or desktop client is `createdBy: "user"`, `creationSource: "web"`. The web client already receives this on every row — `EnvironmentThreadShell.source` (`packages/client-runtime/src/state/models.ts`) is the full shell — so **the cue itself needs no contract change and no extra bytes on the wire.**

**The shell does not say which thread started it.** The durable trace from commit `c0e646930a` is written on the *caller's* side only:

## Constraints the implementer must respect

- Every hunk inside an upstream-owned file (`Sidebar.tsx`, `Sidebar.logic.ts`, `WorkstreamPanel.tsx`, `orchestrationV2.ts` if touched) carries a `// loom:` marker; the new component and predicate live in `apps/web/src/loom/` and `packages/client-runtime/src/state/loom/` (`pnpm ship`'s unmarked-hunk sweep enforces this).
- No restyling of `components/ui` exports: the glyph is a bare `<button>`/`<span>` with layout classes, as the draft pen and pin are.
- No continuously animating glyph. No per-row subscription: the predicate is a pure function of the row's `source`, and the origin title lookup is a selector over the snapshot that already drives the row.
- The filter option, if Carl adds it, is a tier-2 durable preference per `docs/architecture/loom-ui-state-tiers.md` (client-local `uiStateStore`), never component state.
- Loom migrations are numbered `1001+` in `LoomMigrations.ts`; upstream's `Migrations.ts` is never edited.
- Tests are not the default here; the one piece worth a focused test is the projector stamp rule in `apps/server/src/loom/projection/loomProjection.test.ts` (drafter path credits the source, agent path credits the caller, human never downgraded), because a wrong stamp is silent.

## Risks

- **Origin lag on the destination's shell** (work item 2 step 5): cosmetic and self-healing; the reorder is the fix if it is ever visible.
- **A `goal_handoff` caller that is later archived**: the stamp keeps the id, the snapshot has no title; the row degrades to “origin archived”. Acceptable; the Workstream panel could later read the archive dataset on demand.
- **Agent-created scheduled tasks** carry the cue by the same rule; their hover card has no origin thread (the task is not a thread), so it reads “Started by a scheduled task”. If Carl does not want these marked, the predicate needs `creationSource` and the task's provenance, which the shell does not carry — flagged in the form.
- **Upstream drift in `Sidebar.tsx`**: the two mounts sit at the row's stable data seams (title line, draft-pen slot), the same places the rollup badge attaches; a future upstream rewrite moves the mounts, not the component.
