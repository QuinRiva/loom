# Sidebar workstream badge: what it should say about a thread's sub-threads

**Decision document.** The left sidebar shows one row per top-level thread. When that thread has spawned sub-threads, its row carries a small pill — a graph icon, a count such as `18/19`, sometimes a `· 1!` suffix, in grey, amber or red. Since the V1→V2 transition (upstream pull 9, PR #333) that pill turns amber on workstreams where nothing is wrong: sub-threads are running, or one is queued behind a sibling that has not finished. The reviewer complaint is exact — *"threads whose sub-threads are running read as though something is wrong"* — and nobody ever decided how the pill should behave in the new interface.

This document (1) explains, from the code and the live database, what the pill shows today and why two healthy workstreams carry a warning; (2) records what V1 showed and what the rest of the V2 workstream UI already uses for the same states; (3) proposes a status model; (4) offers three concrete options with the real rows drawn; and (5) ends with the questions only the owner can settle. **Done** means: a human has picked an option in the form at the bottom, and the implementation sketch in this document is enough for a coder to land it without re-deriving anything here. No code changes until then.

## What the badge does today

The pill is `LoomRollupBadge` (`apps/web/src/loom/LoomRollupBadge.tsx`). It is mounted twice in `apps/web/src/components/Sidebar.tsx` (the full row's third line, beside the branch name; and the slim row) and shows only on a **root** thread that has at least one live sub-thread. Its numbers come from `workstreamRollupOf` in `packages/client-runtime/src/state/loom/rollup.ts`, which walks every descendant (children, grandchildren, …) of the root and produces three independent counts that the code deliberately never fuses — the plan, the activity and the attention. The badge composes two of them and ignores the third.

## Why two healthy workstreams carry a warning

Is "blocked by an unfinished dependency" being counted as a problem? **Not directly** — a sub-thread's board column (`blocked`) never reaches the badge. It is counted **through a side door**: a dependency-blocked child that was scaffolded ahead of its brief has neither a brief nor a start, and the client's `brief-needed` derivation does not check dependencies or the held flag. The server's own definition of the same condition does.

So the `1!` on both amber rows is a **client/server disagreement**, which makes it a bug rather than a choice: the server says nobody is owed anything, the sidebar says someone is. The Phase 3 integration notes even recorded the symptom (*"the unbriefed child is deferred … the web still derives brief-needed, the board column stays blocked"*) without anyone deciding whether the badge should care.

Separately, and this is the part that **was never designed**: the V2 badge's composition rule. V1 collapsed the graph into one state with an explicit precedence; V2 re-stated the principle "three rollups, never fused — a surface that wants one glyph composes them itself" and then the badge composed *settled/total + attention* and dropped the activity axis entirely. That is why a workstream with two sub-threads actively working looks identical to one where everything has stopped. No document records that choice.

And the upstream sidebar's own rule — colour for *act now*, *in motion* and *broken* only — is the exact vocabulary the badge needs; "Waiting" in upstream's words is *"the agent stopped with background work that will wake it (subagents, monitors): not the user's turn yet"*, which is precisely an orchestrator with running sub-threads.

### The root row's own label

The text at the top-right of the row ("Waiting", "Working", "Done") describes the **root's own agent**, not its sub-threads: "Working" while the root runs a turn, "Waiting" when it has no run at all (the imported golden-dataset root), and — for a native V2 root whose turn ended after spawning — nothing, or a green "Done" if the turn ended after the user last visited. That last case contradicts a badge saying sub-threads are running; the recommended model below gives the badge the "in motion" colour so the row still reads correctly, and the bottom form asks whether the label itself should say "Waiting" instead of "Done" while sub-threads are unsettled.

## Proposed status model

One summary tone per root, chosen by precedence, from the three rollups the code already computes. Red and amber mean *look at this*; blue means *leave it alone, it is moving*; grey means *nothing is happening*.

<Table
  columns={["State", "Rule (first match wins)", "Colour", "Suffix", "Reads alongside the row label as"]}
  rows={[
    ["Failed / stuck", "any sub-thread has the error reason; or the sub-tree is deadlocked and nothing is running", "error (red)", "· N! (N = flagged sub-threads)", "Waiting + red badge: your orchestrator is parked and a sub-thread is dead."],
    ["Needs you", "any sub-thread carries a reason addressed to the human: approval, input, acceptance, guidance. A yield or missing brief counts only when the root is not itself running (it is the parent's job first).", "warning (amber)", "· N!", "Waiting + amber badge: not the root's turn, but a sub-thread is yours."],
    ["Working", "any sub-thread is preparing, starting, running or waiting on a tool; no human gate", "info (blue)", "none", "Waiting/Done + blue badge: healthy; the root is parked while sub-threads work. A sub-thread queued behind a running sibling lands here, not in a warning."],
    ["All done", "every live sub-thread has an outcome", "muted (grey); success tint is a form question", "none", "Done + grey n/n badge: the workstream is finished; the row's own Done label carries the unread signal."],
    ["Waiting", "nothing running, nothing flagged, work remains (held children, a dependency chain whose head has not been dispatched yet)", "muted (grey)", "none", "Waiting + grey badge: nothing is moving and nothing is asked of you. Usually transient; if it persists the popover says why."],
  ]}
/>

The `!` suffix is reserved for the two states where a human must act, so the character means one thing. Running counts, blocked counts and deadlock stay in the popover and the tooltip (aria-label), where there is room for words. Nothing animates.

<Callout tone="decision">
Needs-you outranks working, reversing V1's "liveness first" rule for the attention case only. V1 hid a human gate behind an unrelated running sibling; a sibling's progress does not answer the question the human was asked. Liveness still outranks *blocked-ness*, which was the rule's real purpose: a child queued behind a running sibling is Working, never a warning.
</Callout>

## Recommendation

<Callout tone="decision">
**Option B.** It is the smallest model in which the correct state is unsurprising: the pill's colour answers "do I need to look?" and the count answers "how far along?", and both use the same tokens as the row label beside it and the graph behind it. Option A fixes the false alarm but leaves the pill unable to say the one thing an orchestrator's row most needs to say — that work is happening. Option C says it, at the cost of two extra chips on a line that is already full. B also restores V1's user-visible meaning (blue on this badge meant *running* for months) without reviving V1's fused state machine: it is one small pure function over the three rollups that already exist, with no server or contract change.
</Callout>
