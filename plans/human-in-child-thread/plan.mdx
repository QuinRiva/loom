## 1. The approval hold

### 1.1 The decision

<Callout tone="decision" title="An approval hold outlives messages">
  Today any human or parent message clears every flag on a child when its turn starts. A held child that is corrected is therefore no longer held, and must raise the flag and submit again. The brief needs the opposite: the child "revises and is still held", and the parent "hears nothing about the round". So `awaiting_acceptance` stops being cleared by messages. The other flags (`needs_guidance`, `awaiting_orchestrator`, `error`) keep today's behaviour.
</Callout>

<Columns>
  <Card heading="Chosen: the hold stands until the thread completes" tone="success" badge="PICKED">
    The control plane keeps the hold through every round, so "still held" does not depend on the model remembering to re-hold. A completing submit over the hold is refused unless a human-authored message started or was steered into the current turn; the parent's explicit accept (`workstream_set_outcome` done) is the other release. A parent's send-back can therefore never end in the child plain-completing and releasing queued work, which is the brief's must-not.
  </Card>
  <Card heading="Rejected: messages keep clearing it; the child re-holds each round" tone="neutral" badge="REJECTED">
    Smaller server change, but "still held" then rests on the model re-submitting after every correction, and a plain submit after a parent's send-back still releases the work behind it. An eval would be the only thing between a model slip and the must-not.
  </Card>
</Columns>

### 1.2 The flow the brief describes, and what carries each step

<Steps>
  <Step title="The child hands back held, in one call.">
    `workstream_submit` with outcome `awaiting_acceptance`. The report is recorded, the flag raised, the outcome stays unset, so siblings that wait on it do not start.

    > **Child receives:** "Work submitted: report recorded and you are held `awaiting_acceptance`: not done, and nothing that waits on you starts. Your parent has been told once and points the human here. …"
  </Step>
  <Step title="The control plane sends the parent one notice.">
    Keyed on the hand-back, not on the flag, so each held hand-back to the parent is one notice and there is no second "matched no route" notice.

    > **Parent receives:** "… has finished its work and handed it back held `awaiting_acceptance` … Read what it handed back against your brief. If something is plainly wrong, send it back … Otherwise tell the human it is waiting for them, with this link: [title](t3-thread://v1/id). …"
  </Step>
  <Step title="The parent reads it against its brief, and may send it back." badge="hold stands">
    `workstream_prompt` no longer clears the hold. The child fixes the defect and hands back held again: one more notice, because the parent asked for this round.
  </Step>
  <Step title="The parent points the human at the child and stops.">
    Its message carries the link from the notice. It neither asks for approval in its own thread nor relays.
  </Step>
  <Step title="The human corrects in the child, any number of times." badge="silent">
    The hold stands through his message. The child revises and replies. If it submits held again out of habit, the report file is refreshed and nothing is dispatched, so the parent hears nothing.
  </Step>
  <Step title="The human approves in the child; it completes." tone="success">
    A plain submit is accepted because a human-authored message is in this turn. The hold clears, the outcome is done, dependents start, and the parent gets the ordinary finished line in its digest.
  </Step>
</Steps>

### 1.3 Server steps, in order

1. **`packages/shared/src/workstreamGraph.ts`.** In `routeWorkSubmit`, `awaiting_acceptance` returns the existing decision `attention`, on the same early line as `needs_human` (so it is not intercepted by a rework round). `holdErasedByCompletion` gains `humanInTurn: boolean`: a standing `awaiting_acceptance` does not block a completing decision when it is true. Add one exported predicate, `isParked(attention)`: true when any reason other than `awaiting_acceptance` stands. `workSubmitRefusal`'s terminal-thread text changes (model-text §4.5).
2. **A new pure predicate, `humanSpokeInTurn(runs, userMessages)`,** beside `turnStartedByHuman` in `apps/server/src/loom/orchestration/quiescence.ts`. True when the latest non-queued run, followed back through continuation runs exactly as `turnStartedByHuman` follows them, has a user message with `loom.humanAuthored === true` and that run's id. A steered human message carries the id of the run it joined, so this covers "started or steered into". `turnStartedByHuman` and the quiet check do not change.
3. **`apps/server/src/orchestration-v2/Orchestrator.loom.ts`.**
   - Turn-start rule 4 in `loomTurnStartRules`, and `loomQueuedTurnAttentionClear`. When `awaiting_acceptance` stands, emit one `thread.attention-cleared` per other standing reason. When it does not, emit today's single clear-all event.
   - `workSubmit`: for decision `attention`, raise `awaiting_acceptance` when the outcome is that word (else `needs_guidance`, as today), only if not already standing. Before refusing a completion over a hold, read the thread's runs and user messages and pass `humanInTurn` to `holdErasedByCompletion`; the read happens only when `awaiting_acceptance` stands and the decision completes.
   - The decider's own refusal of a completion over a hold still ends "Yield with a non-done outcome instead." The handler's mirror normally answers first, but in a race this text would teach the old pattern. For `awaiting_acceptance` it returns `SUBMIT_REFUSED_WHILE_HELD`; for `needs_guidance`, `SUBMIT_REFUSED_WHILE_RAISED`, which the handler already returns.
   - `loomContinuationVetoed`: drop the `awaiting_acceptance` clause. A held thread now runs turns (correction rounds), and one cut by a restart or a usage limit must be continued.
4. **`apps/server/src/loom/economics/RerouteSweep.ts`:** replace `attention.length === 0` with `!isParked(attention)`, so a held thread whose turn hit a usage limit is resumed like any other. The liveness sweep is not changed: it returns early for any flagged thread, so a held child's failed turn gets neither a nudge nor the one automatic resume. In a correction round the human is in the thread and sees the failure. After a parent's send-back, the quiet check of step 5 reports it.
5. **The quiet check keeps covering a held child its parent sent back** (`quiescence.ts`, `quiescenceRail.ts`). Today any flagged thread is excluded, which was safe while a prompt cleared the hold. With the hold standing, a child that its parent sent back and that ends the turn without handing back would be reported to nobody, which the brief's must-not forbids.
   - Exclude a thread when `isParked(attention)`. A thread whose only flag is `awaiting_acceptance` stays a candidate only when its latest turn was started by its parent's prompt and no human-authored message joined it (`humanSpokeInTurn` is false). The first half is a new predicate, `turnStartedByParent`: the twin of `turnStartedByHuman`, reading `loom.origin === "orchestrator"` and following continuation runs the same way.
   - Everything after that line is unchanged. A held child at rest after its own hand-back is still not quiet, by the existing rule that a run the thread submitted from did not go quiet. Turns started by the human, or by a notice, on a held child are never reported.
   - The rail's two cheap pre-checks (`row.attention.length > 0` and `fresh.attention.length > 0`) become `isParked(…)`.
   - The synthesised hand-back yields as today, and the yield notice already carries the clause for a child that also holds the approval flag (model-text §5.3).
6. **`apps/server/src/loom/orchestration/dispatcher/rails.ts`, `attentionRail`.** For `awaiting_acceptance`, the notice's episode is `lastOutcome.eventId` when `lastOutcome.outcome` is `awaiting_acceptance`. Otherwise there is no notice, so a parent that raised the flag on a child itself is not told. A new builder in `wakes.ts` writes the text, which is model-text §5.1. It needs the child's title from `ctx.shells`. The card item omits `documents`; §1.5 says why.
7. **`apps/server/src/mcp/toolkits/workstream/handlers/submit.ts`.** Mirror the completion rule before writing the report (it already mirrors the arm's refusals), returning `SUBMIT_REFUSED_WHILE_HELD` (model-text §3.4). Add the silent branch: outcome `awaiting_acceptance`, the flag already standing, and `humanSpokeInTurn` true: write the report file and return the echo of model-text §4.2 without dispatching. `handlers/attention.ts` refuses a thread raising `awaiting_acceptance` on itself (model-text §4.4); a parent raising it on a child is unchanged.
8. **`render.ts`:** the `attention` echo takes the outcome and returns model-text §4.1 for the new word.
9. **Seed and its doc.** `apps/server/src/dev/seedWorkstream.ts` gains one child handed back held under the seeded root, so the live pass has a fixture; `docs/dev-site-testing.md`'s list of what the seed writes gains it.

### 1.4 Why the notice is keyed on the hand-back

The projection ignores a second raise of a flag that already stands. A notice keyed on the raise would therefore be sent once and never again, and a parent would not hear that a child it sent back has handed back. Keyed on the hand-back, the rule is one notice per held hand-back the parent is owed. The human's rounds owe it none, because they dispatch nothing.

**The ways out are the ones that exist.** The human approves in the child, or the parent accepts it. The Accept and Clear flags actions on the Workstream panel's node menu also release it. They dispatch `thread.outcome.set` and `thread.attention.clear`, and are unchanged.

### 1.5 The parent's part, and the one seam it leaves

**The link.** The notice gives the parent the finished link, so pointing the human at the child is a copy, not a composition.

**The seam.** Review comments on a document land in the composer of the thread the document was opened from. A document opened from the parent's notice card would send the human's corrections to the parent. So the held notice's card carries the report but no document chips, and the link the notice hands the parent is to the child, not the document.

**If the human writes to the parent anyway.** The role has the parent pass a correction on once, or accept the child on an approval. That text is model-text §6.3, and §8 names it as a departure from the brief's letter.

## 2. A child the parent declares human-led

1. **Contract and storage.**
   - `humanLed: boolean` on `LoomThreadWorkstream`, with a decoding default of false. It is optional on the `thread.spawn` command and on the `thread.workstream-created` payload. All three are in `packages/contracts/src/orchestrationV2.loom.ts`.
   - Migration `1070` adds `human_led INTEGER NOT NULL DEFAULT 0`. Register it in `apps/server/src/persistence/LoomMigrations.ts`; `LoomStore.ts` maps the column.
   - The pattern is migration `1058`, which added `kickoff_origin`, without its backfill. `1070` is free on this branch and on `main` today; take the next free number at build time.
2. **Tool.** `workstream_spawn` gains the optional `humanLed` (model-text §2.2); `handlers/spawn.ts` passes it; the spawn arm writes it. It combines with `forkFrom`: it is not inherited launch identity, and forking a thread so the human can talk to the fork is a plausible request. Scaffold nodes do not get it: every observed case was a single spawn made at the human's request.
3. **Quiet check.** `quiescenceCandidate` returns false for a `humanLed` thread, before any grace is read. The brief says "never reported as quiet … however long you take", so the `quiescenceHumanGraceMs` setting does not apply to it, and the rail needs no change for it.
4. **Kickoff.** `workstreamChildPrompt` takes `humanLed` and swaps its three closing lines for the three of model-text §3.3; `kickoffText` and the dispatcher's promotion step pass the row's value.
5. **Fixtures.** The row's type gains a field, so `packages/client-runtime/src/state/loom/loomTestFixtures.ts` and `apps/web/src/preview/loomFixtures.ts` gain `humanLed: false`. No client reads it.

## 3. A finished child the human keeps talking to

1. **The addition.** In `handlers/submit.ts`, before routing, three conditions: the thread's outcome is `done`, it has a report path, and a human-authored user message is newer than `outcomeAt`. Then:
   - append to that report file a section headed `## Added after finishing · ` plus the local timestamp from `formatWakeTimestamp`, then the submitted markdown;
   - re-index the file for thread search with `upsertThreadSearchReport`, as every report write does;
   - dispatch nothing, and return the echo of model-text §4.3.

   `report.ts` gains the append helper. No event is emitted: the path, the outcome and `lastOutcome` are unchanged. So no digest line reaches the parent, and nothing behind the child moves. A done thread in an open rework round, `pendingRework`, is not this case: its submit routes back to its reviewer as today.
2. **Everything else is refused as today, with text that says what to do.** That covers a finished child no human has written to since it finished, a cancelled child, and a finished child with no report on file. The text is model-text §4.5.
3. **The message tool.** `sessionProfile` in `apps/server/src/loom/http/loomAgentRoutes.ts` adds `mcp__t3-code__notify_thread` to `activeTools` for a child a person has written to. That is the condition that already keeps `ask_user_question` for it. The pi extension activates what the profile lists on the next turn, so it needs no change.
4. **The materiality test is the child's.** It reads it in the addition's echo, at the moment it applies, and in the widened parenthesis of `CHILD_READERSHIP_CLAUSE` (model-text §3.1) for a child that never submits.

## 5. Evals

None of the six evals in `evals/README.md` covers this text. `mcp-tool-use` replays upstream's tools under Claude Code and Codex captures, and Loom threads see none of those tools. The other five measure titles, PR text, dictation, test signal and prose density. So the change needs a new eval, in the README's shape, and it lands first.

**`evals/loom-handback`** measures whether a Loom thread hands back, holds and tells its parent the way the control plane expects. Each sample is one model call. Its input is a system prompt and tools assembled from this checkout, and a short authored transcript ending at a decision. Its grade is deterministic: the tool calls and final text of the next assistant message.

- **Assembled from source, never copied.**
  - System prompt: `addendumParts` in `sessionComposerLive.ts`, joined in the composer's order.
  - Tools: `LOOM_TOOL_DEFS`, filtered to the role's resident tools from `loadRoleOverlay`, plus what the session profile adds for a child a person has written to.
  - Kickoffs: `workstreamChildPrompt`. Notices: the builders in `wakes.ts` and `yield.ts`.
  - Tool results already in a transcript: `renderSubmitOutcome` and the refusal texts.
  - Four stub native tools: `read`, `bash`, `edit` and `tool_search`. With `tool_search` present, reaching for a tool that is not declared shows up as a call to it.
- **Runs on both sides of the change.** Four things the control plane produces differ between base and change:
  - the notices a parent gets for a held child;
  - the result of a finished child's submit;
  - the tools added for a child a person has written to;
  - the kickoff of a human-led child.

  One small module, `world.ts`, answers "what this checkout sends" for each. It uses the new export when it exists and today's functions when it does not. Its fallbacks are deleted in commit 3.
- **Flags:** `--out`, `--model`, `--samples` (default 5), `--case`, `--baseline`. A fresh session line per sample defeats the prompt cache, as `explainer-density` does. Route and default model as `explainer-density`; run the coder-role cases on the model coders launch on as well, and name both in the change record.
- **Cases are authored Acme data.** No real thread text; each case's `source` names the real thread it mirrors.

**Protocol.** This is the tier-3 bar of `llm-instruction-change`. The hypothesis is pre-registered in model-text §7.

1. On the commit that adds the eval, run it twice in full. The two runs are the base and the A/A noise floor.
2. After each server commit, run the cases that commit owns against the base with `--baseline`. After commit 3, run all 19.
3. Five samples a case per arm. A case fails when half or more of its samples fail.
4. Read every sample that flipped, in either direction. Read every final text of the orchestrator cases that end in prose: whether a parent asked for approval in its own thread is not something a pattern can grade.
5. The change record states the floor and the fixed and broken counts, and says that five samples a case can only show a large effect.
6. A `bad` case that still fails after its commit, or a control that starts failing, goes back to the planner with the samples. The text is not the coder's to tune.

## 8. Risks, and where the plan departs from the brief's wording

- **A parent's message no longer clears the approval hold.** The brief does not say this, but its must-not on queued work and its "sends the child back … before it points you at the child" need it. `workstream_prompt`'s description says so.
- **"At no point does the parent … pass your words on."** Met for the designed route. If the human writes a correction or approval to the parent anyway, the plan has the parent pass it on once or accept the child rather than drop his word. The planner's report puts this to Carl.
- **A plain submit by mistake in a correction round still completes the child.** In a turn the human wrote in, the control plane cannot tell a correction from an approval; only the model can. A slip there releases the work behind the child, which is the same slip the rejected option exposed after a parent's send-back. The guard is the eval case `held-child-corrections`.
- **A held child's failed turn is not resumed automatically.** The liveness sweep skips flagged threads, and the plan leaves that alone. The human sees the failure in a correction round; after a parent's send-back the quiet check reports it, or the sweep's error flag does once failures repeat.
- **Approval that arrives outside the completing turn.** If the human approves, the child starts a background job, and the job's exit starts the turn that submits, the completion is refused (no human message in that turn). The refusal tells the child to hand back held; the human approves again. Rare, and it fails safe.
- **"A finished child nobody has written to" is read as "since it finished".** A child the human wrote to while it worked, and whose parent later prompts it without reopening it, is refused as today.
- **A finished child with no report on file, or a cancelled child, cannot add.** Both are refused with the new text. Giving them a report would need an event, and neither occurred in the nine refusals behind the brief.
- **`humanLed` is spawn-only and permanent.** There is no way to turn it off; the child ends by submitting, and the parent can still prompt, stop or cancel it.
- **The roles ship with the release.** Built-in `roles/*.md` are read from the running server's checkout, so a dev instance from this worktree uses the new text, and the cockpit uses it after Carl's next deploy.
- **Two existing doors stay open.** A thread can still set its own outcome through `mcp__t3-code__workstream_set_outcome`, which is not on a leaf child's declared tools, and a reviewer's resolving verdict can still complete a held counterpart. `docs/design/workstream-review-gates.md` left both open on purpose and this plan does not touch them.
- **Stored state.** Rows held `awaiting_acceptance` at deploy keep the flag and gain the new rules at once; their `lastOutcome` is an invented word, so no held notice is re-sent for them. No compatibility code is added for the old words.

**Earlier decisions this plan changes.** It supersedes no plan. It changes two decisions recorded elsewhere, and marks neither document:

- `plans/2026-07-31-remove-discuss-mode.md` §1.2 rejects every submit from a finished thread. §3 here accepts one, as an addition, when a human has written since the thread finished.
- `docs/design/workstream-review-gates.md` §3 rests the completion guard on "a turn-start clears stored attention". §1 here makes `awaiting_acceptance` the exception, and moves the guard's release to a human message in the completing turn.
