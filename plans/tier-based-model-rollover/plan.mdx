# Tier-based model rollover

**Objective.** Make the monthly "run the platform update" a one-command run: bump pi, read the new catalogue, work out which tiers moved, write the new slugs into every place a slug lives, prove each changed tier with a real completion, and report before → after per tier and per target. Model identity stays a plain slug everywhere it is today; what changes is that **one skill owns the list of places and the meaning of each** (which tier it holds, through which provider), so no agent ever greps for an old slug again.

**Done means:** a pi bump that ships (say) Opus 6 and GPT-6.5 Sol is rolled out by the skill with exactly two human moments — the ~6 s cli-proxy restart window when a new Claude model is involved, and Carl's own deploy of the loom PR the skill opened — and the report shows every target's before/after and a passing completion per changed tier.

**Required loom runtime changes: none.** Loom, `settings.json`, the pi extensions and cli-proxy never see a tier; the skill resolves tiers to slugs at run time and writes slugs. Nothing moves between runs.

## The tier map and the targets

Both live in the skill: `pi-craft/plugins/pi-craft/skills/platform-update/` — `SKILL.md` (procedure + report template) and `targets.yaml` (the data). The map is Carl's regularity — releases are version bumps within stable families; the map changes only when a new family appears — and it is **vendor-first**, because it is vendors that ship models and models of one tier across vendors are rough equivalents; which provider serves a vendor is a per-target routing detail.

A **pin** is any slug-bearing location listed under `pins`, or a target Carl has removed from `targets`: the skill reports it (and flags it if the id has left the catalogue) but never writes it. To pin a preset to a specific model, delete its entry.

## Resolving a tier to a slug

The current model for `vendor/tier` is **the newest version of `families[vendor][tier]` present in the new pi's catalogue** — `providers/data/anthropic.json` and `openai-codex.json` from the `npm pack`ed `@earendil-works/pi-ai@<same version as pi-coding-agent>` tarball (runbook §1). The parser lives in the skill (a small script beside `targets.yaml`); ids that do not parse are ignored, never guessed.

<Table
  columns={["Vendor", "Grammar (anchored regex)", "Parses", "Ignored (with why)"]}
  rows={[
    ["anthropic", "^claude-([a-z]+)-(\\d+)(?:-(\\d{1,2}))?(?:-(\\d{8}))?$ → family, major, minor=0, date? (minor capped at two digits: with `\\d+`, a major-only dated id such as `claude-opus-6-20270301` would parse as minor 20270301 and outrank every later version)", "claude-opus-5-5 → opus (5,5); claude-opus-5 → opus (5,0); claude-opus-6-20270301 → opus (6,0) dated; claude-haiku-4-5-20251001 → haiku (4,5) dated; claude-fable-5-1 → fable (5,1)", "anthropic.claude-opus-5-5 / au.anthropic.… (bedrock prefixes); claude-opus-4-1@20250805 (vertex suffix); anything with `[1m]`, `-thinking`, `-v1:0` — a trailing segment the grammar does not name"],
    ["openai", "^gpt-(\\d+)(?:\\.(\\d+))?-([a-z]+)$ → major, minor=0, family", "gpt-6-sol → sol (6,0); gpt-5.6-luna → luna (5,6); gpt-6-astra → astra (6,0)", "gpt-5.5 (no family word); gpt-5.3-codex-spark (two words — a variant); gpt-5.6-terra parses as family `terra`, which no tier names → listed under unmapped families; gpt-5-chat-latest, o3, gpt-realtime-2.1"],
  ]}
/>

Ordering: highest `(major, minor)` numerically (4.8 < 5 < 5.5 < 6); on a tie the undated id beats a dated duplicate; if only dated ids tie, the greater date. A family with no parseable id in the catalogue leaves its tier **unchanged** and is reported. A parseable family the map does not name is reported as **unmapped**; mapping it means editing `families` in `targets.yaml` — the map is the skill's, so a new family is a skill edit, not a runtime prompt.

## The run

Trigger: "run the platform update". Everything below is the skill; the runbook keeps the mechanics it links to.

1. **Preflight.** `npm view @earendil-works/pi-coding-agent version time` → candidate (prefer ≥ 24 h old, the pnpm release-age rule). `npm pack` the new `pi-ai` and parse both provider JSONs → *candidate* slug per tier. Read every target's *current* value. A tier whose candidate differs is a **move**. Also note the cloak version in `pi-ai/dist/api/anthropic-messages.js` and cli-proxy's deployed image tag. No move and no new pi ⇒ report "nothing to do" and stop.
2. **cli-proxy, if an anthropic tier moves.** Probe the candidate through `/v1/messages` (unique body). If rejected: AGENTS.md steps 1–7 — fetch tags, pick the lowest tag whose registry has the model *and* whose cloak pin clears the floor in the error, rebase `fix/fable-only-fast-429-*`, absorption test, `go test` in Docker, build, back up and edit `docker-compose.yml`. **Stop — restart window:** "cli-proxy rebuilt as `<tag>-fable-fix`; `docker compose up -d` interrupts live threads for ~6 s — go?" After: `./account status` (5 auths), the completion, the dated §8 record. **If the completion still fails, or the restart is declined, the anthropic tiers are not moved this run** — their `cliproxy` targets keep the old slug and the report says why; everything else proceeds.
3. **pi bump** on a loom feature branch per `infra/pi-patches/README.md` (retirement check on the pristine tarball, pins, regenerate the pnpm patch, contract test), plus the row 7 constant and its test fixtures. `vp check`, `vp run typecheck`, unmarked-hunk sweep, PR via `pnpm ship`.
4. **Global pi** (runbook §5) + the row 14 marker check.
5. **Write the live targets**: rows 5 and 13, atomically. Live in seconds.
6. **Verify each changed tier**: `pi -p --model <via>/<slug> "Reply with exactly: OK"` with the normal extension set (never `--no-extensions` — see risks), plus the negative control `cliproxy/claude-opus-9-9`; read failures per runbook §7 (catalogue miss vs quota vs cloak pin). Then the zero-cost cockpit check: `workstream_list`'s preset block shows the new slugs with no `[INVALID]`. A failed probe on a tier already written is reverted to the old slug and reported.
7. **Report** in the format at the top.

The skill never: guesses a family, writes a pin, restarts cli-proxy, deploys the cockpit, or probes with `--no-extensions`.

## Scope and non-goals

- No tier concept in loom, the settings file, the extensions or cli-proxy. Nothing resolves at runtime.
- No automatic proxy restart, deploy, or family mapping.
- Not attempted: deriving cli-proxy's registry or cloak pin; a servability gate for direct `anthropic-<account>/*` providers (no target uses them; the probe is the check).
- Backward compatibility: none. The hand-copied catalogues and the curated shortlist are deleted, not shimmed.
