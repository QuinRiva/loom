# Tier-based model rollover

**Objective.** Make the monthly "run the platform update" a one-command run: bump pi, let the catalogue say which tiers changed, and have every default, preset and failover target follow — with one stop for a genuinely new model *family* and one for the cli-proxy restart window. Model identity stops being a literal slug copied into ~15 places; it becomes a **tier reference** resolved against pi's live catalogue in exactly one place.

**Done means:** after the loom changes deploy and the live `settings.json` is converted, a pi bump that ships (say) Opus 6 and GPT-6.5 Sol changes what every coder, reviewer, planner, manual thread and failover chain runs on **without any loom source edit and without any settings edit** — the skill's report shows the before → after per tier and per surface, and each tier has passed a real completion.

## Tier map and resolution rule

### The reference grammar

A tier reference sits wherever a pi model slug sits today and keeps the slug's `provider/modelId` shape, with the model id replaced by `@tier`:

<Table
  columns={["Form", "Example", "Meaning"]}
  rows={[
    ["provider/@tier", "cliproxy/@medium", "the newest opus-family model that the `cliproxy` provider lists in pi's live catalogue"],
    ["provider/@tier", "openai-codex/@cheap", "the newest luna-family model on `openai-codex`"],
    ["provider/modelId (unchanged)", "cliproxy/claude-opus-5", "a pin — exactly this slug, never rolled"],
    ["bare provider (unchanged, failover chains only)", "cliproxy", "\"same model on this pool\" — existing chain semantics, untouched"],
  ]}
/>

The provider is explicit because it is the *route* (pooled proxy vs direct account vs Codex), and the route is a deliberate choice that must never be inferred. The vendor is **not** in the reference: it is a property of the model ids the provider lists (`claude-…` is Anthropic, `gpt-…` is OpenAI), so `cliproxy/@medium` and `anthropic-carl/@medium` both mean opus without a provider→vendor table to maintain. Model selection `options` (thinking level, reasoning effort) stay on the selection exactly as today; only `model` carries the ref.

Why `@`: no pi model id starts with `@`, `namespaceOf`/`modelIdOf` in `failoverChains.ts` split on the first `/` and keep working unchanged, and the existing `ModelSelection` schema (`model: TrimmedNonEmptyString`) accepts it with no contract change.

### The tier map

`modelTiers` is a new loom field on `ServerSettings` (`packages/contracts/src/settings.loom.ts`, spread into `LoomServerSettingsFields` and `LoomServerSettingsPatchFields` like `workstreamModelPresets`): `Record<vendor, Record<tier, family>>`. No code default — if the map is absent, no reference resolves, visibly. It lives in loom's `settings.json` rather than a separate file because the server already reads, validates, hot-reloads and broadcasts that file, and the skill already edits it (runbook row 13). Vendors and tiers are free strings; today's map is the one shown above.

### The resolution rule

`resolveTierSlug(ref, catalogueSlugs, modelTiers)` — pure, in `packages/shared/src/modelTiers.ts`:

1. Take every catalogue slug whose provider equals the reference's provider.
2. Parse each model id with the two vendor grammars below; ids that do not parse are **ignored, never guessed**.
3. Keep the ids whose `(vendor, family)` equals `(vendor, modelTiers[vendor][tier])`. If the survivors span more than one vendor, the reference is unresolved (no provider does this today; the rule exists so it can never silently pick).
4. Choose the highest `(major, minor)`; on a tie prefer the **undated** id over a dated duplicate; if only dated ids tie, the greater date; if still tied, the lexicographically greater id.
5. If nothing survives, the reference is **unresolved**: the materialised value keeps the literal `provider/@tier` string. Nothing falls back to another tier, provider or vendor.

Version comparison is numeric on `(major, minor)`: 4.8 < 5 < 5.5 < 6. The parser is deliberately strict: an id that gains a suffix Anthropic has not used before (`claude-opus-6-fast`) is ignored rather than treated as Opus 6 — the safe direction is "the tier stays where it was and the skill's report lists the unparsed id", never "a wrong default appears".

## Where resolution sits

<Mermaid
  caption="One resolution path: refs live in the file, slugs leave the service"
  source={"flowchart LR\n  file[settings.json\\nrefs + pins] --> cache[ServerSettingsService cache\\nraw]\n  cache --> mat[materialise: secrets → tier refs → text-gen provider]\n  cat[PiCatalogue\\nSubscriptionRef of slugs] --> mat\n  disk[(stateDir/pi-catalogue.json)] -. seed at boot .-> cat\n  pi[PiDriver.enrichPiSnapshot\\nevery 2 min] --> cat\n  mat --> server[spawn resolution · failover routing · text-gen · auto-bootstrap]\n  mat --> ws[WS settings snapshot + changes] --> web[web client: new-thread default, project overrides, settings UI]\n  web -. patch .-> guard[preserveModelTierRefs] --> cache\n"}
/>

The seam is `apps/server/src/serverSettings.ts` — upstream-owned, so the three touch points are one-line `// loom:` hunks and everything else lives in `apps/server/src/modelTiers.loom.ts`:

- `getSettings`, `materializeChanges`, and `updateSettings`'s return value gain `Effect.map(resolveModelTierRefs(catalogue))` after `materializeProviderEnvironmentSecrets`.
- `updateSettings` applies `preserveModelTierRefs` before `applyServerSettingsPatch`.
- The `changes` stream is merged with `PiCatalogue.changes` mapped to the current cached settings, so a catalogue change (new model servable) re-emits materialised settings to every subscriber and web client without a file write.

`resolveModelTierRefs` walks every model-slug-bearing field of `ServerSettings` in one pass: `defaultModelSelection`, `projectSettingsOverrides[*].defaultModelSelection`, `textGenerationModelSelection`, `sourceControlWriterModelSelection`, `workstreamModelPresets[*]`, `workstreamModelProfiles[*].selection`, and `providerFailover.chains` (keys **and** targets). It only rewrites `model` strings whose model-id part starts with `@`; everything else is returned by reference.

**Performance.** The pass is pure string work over ≤ ~15 refs × ≤ ~50 slugs per provider; it runs per `getSettings` call (per dispatch/spawn, not per message). It is memoised on the identity pair `(raw settings object, catalogue snapshot)`, so between a settings-file change and a catalogue refresh it costs a `WeakMap` lookup. No new catalogue scan is added anywhere on the turn path — routing already uses the same in-memory slug set.

`PiCatalogue` (`apps/server/src/provider/PiCatalogue.loom.ts`) is a `SubscriptionRef<ReadonlyArray<string>>` provided *below* both `ServerSettingsService` and the provider registry in `apps/server/src/loom/serverLayers.ts`, which is what breaks the settings→providers→settings dependency loop: PiDriver pushes into it from `enrichPiSnapshot` (the same place that fills `modelContextWindows`), and persists the slug list to `<stateDir>/pi-catalogue.json` on every non-empty refresh.

## The `platform-update` skill

Lives in pi-craft (`plugins/pi-craft/skills/platform-update/SKILL.md`) because it touches the machine and three repos; loom's `docs/operations/platform-update.md` shrinks to the mechanics it still owns (pi bump, patches, verification commands) and the skill sequences them. Trigger: "run the platform update". Two stop points, nothing else asks.

1. **Preflight.** `npm view @earendil-works/pi-coding-agent version time` → candidate version (prefer ≥ 24 h old, per the pnpm release-age rule). `npm pack` the old (currently pinned) and new `pi-ai` tarballs; read `providers/data/anthropic.json` and `openai-codex.json`. Read `modelTiers` from the live cockpit settings. Compute both tier tables with `pnpm model-tiers` (loom `scripts/model-tiers.ts`, the same parser as the server): *catalogue* resolution (what pi will list) and *live* resolution (what the running cockpit resolves now, via `pi --list-models` with extensions). Report the pi-ai `anthropic-messages.js` cloak version and cli-proxy's deployed image tag.
2. **Stop 1 — new family.** Any parseable family in the new catalogue absent from the old → ask (question text in the edge-case table). Silence = ignore this run.
3. **cli-proxy, only if an anthropic tier's *catalogue* resolution differs from its *live* resolution.** Probe the new model through the proxy (`/v1/messages`, unique body). If rejected (`Claude Code <old> does not support this model` or missing from the registry): follow `/home/Carl/cli-proxy/AGENTS.md` steps 1–7 — fetch tags, find the lowest tag whose registry has the model *and* whose cloak pin ≥ the floor in the error, rebase `fix/fable-only-fast-429-*` onto it, run the absorption test, `go test` in Docker, build, back up and edit `docker-compose.yml`. **Stop 2 — restart window:** "cli-proxy rebuilt as `<tag>-fable-fix`; `docker compose up -d` interrupts live threads for ~6 s — go?" After the restart: `./account status` (5 auths), the real completion, then append the id to `/home/Carl/cli-proxy/servable-models.json` and the dated record in `docs/cliproxyapi-failover-code-analysis.md` §8. If the probe already passes, append to the allowlist and continue.
4. **pi bump** on a loom feature branch per `infra/pi-patches/README.md` (retirement check against the pristine tarball, pins, regenerate the pnpm patch, contract test). `vp check`, `vp run typecheck`, unmarked-hunk sweep, open the PR via the ship procedure. No model slugs change in loom source.
5. **Global pi** (§5 of the runbook) + patch marker checks (row 14). Write the global pi defaults (row 5) from the tier table.
6. **Verify every tier** with `pi -p --model <resolved slug> "Reply with exactly: OK"` for each `(provider, tier)` in use, plus the negative control (`cliproxy/claude-opus-9-9`), reading failures per the runbook's guide (catalogue miss vs quota vs cloak pin). Then check the live cockpit's view: `workstream_list`'s preset block shows no `[INVALID]` after the next catalogue refresh (≤ 2 min; the skill waits for it rather than restarting anything).
7. **Report** in the format shown at the top: tiers (before/after/surfaces), surfaces (before/after/effect), verification lines, unmapped families, unparsed ids, pins in force, and the pending human acts (deploy; restart if declined).

What the skill must never do: guess a family, write to `settings.json` model fields (they are refs now — the only settings write is `modelTiers` when Carl maps a new family), restart cli-proxy or deploy the cockpit, or run probes with `--no-extensions`.

## Scope and non-goals

- No UI for tiers. The settings UI keeps showing resolved slugs; choosing a model there is a pin. A "via cliproxy/@medium" badge is a later nicety, not part of this.
- No change to `ModelSelection`'s wire shape, to the spawn precedence ladder, to failover chain grammar beyond accepting refs, or to how threads store their selection (threads keep concrete slugs — a running thread never silently changes model mid-life; new spawns pick up the new resolution).
- No automatic proxy restart, no automatic deploy, no automatic family mapping.
- No attempt to derive cli-proxy's registry or cloak pin; no attempt to make direct `anthropic-<account>` providers gate on servability.
- Backward compatibility: none kept. The hand-copied catalogues, the curated shortlist, the `project.create` seed and the per-rollover edits to Codex/Claude adapter constants are deleted, not shimmed.
