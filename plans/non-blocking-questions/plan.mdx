# Agent questions that never block

When an agent asks you something, it will state the assumption it is proceeding on, open a question card, and **keep working**. The card sits in an open-questions rail above the composer, with a header and an age, until you answer it or dismiss it; several can stand at once; it minimises out of your way while you type. Answering sends your pick to the agent as a steer if it is mid-turn or starts a new turn if it is idle, and an answer given an hour after the agent's turn ended still lands. Nothing waits on you unless the agent sets a `blocking` flag, which the tool text reserves for an irreversible step (data leaving a boundary, a destructive change); the audit of October's 128 question sets puts that at about 5. Ship readiness stops being a question: the agent ends its turn saying the work is ready to ship and waits for your "ship it" in chat.

A non-blocking question is the request the server already creates, with one new fact on it, one shared check applied where the server asks "is this thread blocked", and three closing rules removed.

### Steps, in the order a coder would take them

1. **Contract.** `packages/contracts/src/orchestrationV2.ts`: `loom: Schema.optional(Schema.Struct({ blocking: Schema.Boolean }))` on `OrchestrationV2RuntimeRequest` (the Json twin follows through `mapFields`), and `openQuestions` on `OrchestrationV2ThreadShell` and its Json form, optional with a decoding default of `[]`. The `runtime-request.create` command in `packages/contracts/src/orchestrationV2.loom.ts` gains the same optional `loom` field, since that is where the ask stamps it. All `// loom:`. `ThreadPendingUserInput` in `packages/client-runtime/src/state/threadRequests.ts` gains `blocking: boolean`, derived as `request.loom?.blocking !== false`.
2. **One shared predicate.** `hasBlockingPendingRequest(runtimeRequests)` beside `loomAskAnswer` in `apps/server/src/orchestration-v2/Orchestrator.loom.ts`: pending, and not a Loom ask marked `blocking: false`. Its SQL twin is the clause `AND COALESCE(json_extract(request.payload_json, '$.loom.blocking'), 1) = 1`. The table below is every site that changes to use it.
3. **Validation and the ask route.** `validateAskQuestions` in `apps/server/src/loom/userInput/askUserQuestion.ts` accepts `blocking?: boolean`. `openAskUserQuestion` opens a waiter **only when blocking**, stamps `loom: { blocking }` on the `runtime-request.create` command, and returns `{ requestId, blocking, openCount }`; `POST /loom/agent/user-input/ask` in `apps/server/src/loom/http/loomAgentRoutes.ts` passes that through. The pi extension's `execute` in `apps/server/src/provider/Drivers/Pi/loomExtension.ts` returns the open-question text at once when `blocking` is false and long-polls `…/wait` exactly as today when it is true.
4. **The create arm.** `runtimeRequestCreate` carries `loom` onto the request payload and its guard uses the predicate: refuse while a blocking request stands, otherwise allow. The node and turn item it emits are unchanged, so the question still appears in the transcript as a `user_input_request` row and the answer is recorded against it. That row keeps its *waiting* status after the run completes, which today never happens; the coder confirms `MessagesTimeline.tsx` shows it as an open question rather than a live spinner, and adds a `// loom:` presentation hunk if it does not.
5. **The reactor.** In `reactToAskEvent`, the supersede rule and the run-ended rule apply only to requests with `loom.blocking !== false`. The supersede rule also ignores messages whose id starts with `async-answer:`, the message upstream dispatches from an answer; it is stamped human-authored, so without this exclusion answering a non-blocking question while a blocking one stood would close the blocking one as superseded.
6. **The shell.** `apps/server/src/orchestration-v2/ProjectionStore.ts`: the in-memory fold that picks `pendingRuntimeRequest` and the `pending_request_payload_json` and `pending_question_header` subqueries in the shell SQL take the predicate; a new `open_questions_json` subquery aggregates the non-blocking pending requests joined to their `user_input_request` turn item's first header, oldest first. `openQuestions` sits on upstream's shell, not the sidecar join, so threads without a workstream row carry it too.
7. **Answering and dismissing** need no server change. `runtime-request.respond` finds no live waiter (`loomAskTakesAnswer` returns false), builds the message from each question's text and answer, and dispatches it `steer_active` when a run is live or `queue_after_active` when idle, where an idle thread starts a turn. `thread.user-input.dismiss` resolves the request with decision `cancel` and emits nothing. The agent therefore sees your answer as a message that quotes the question it asked, which is what a model needs when the tool call was an hour ago.

Sites that read pending requests and are **correct as they are**: `RestartContinuation.ts` and `ProviderRuntimeRecoveryService.ts` already exclude or keep `message`-capability requests (a non-blocking question survives a restart as data); `ProviderSessionManager.ts` and the delegated-task wait look only at `live` requests; `ThreadDeletion.ts` cancels everything on delete, correctly; the MCP thread tools (`t3_pending_request_list`, `pendingRequestCount`) list open questions, which is right; the runtime-recovery candidate filters include the thread as a candidate, which is harmless. The delegated-task dismiss that fires when a child's result run is cancelled would also dismiss a child's open questions; acceptable, and children rarely hold one.

<Callout tone="decision" title="Why the question stays a runtime request rather than becoming a new Loom table">
A new sidecar entity would need its own web rail, mobile card, Slack post, answer RPC and projection, and would still have to teach the sidebar and inbox about it. As a `user_input` runtime request with `message` capability, the question is already rendered by upstream's composer panel and mobile card, folded by the Slack bridge (which keys on exactly this shape and answers with `runtime-request.respond`), kept across restarts, counted by the sidebar, and answered through a path that already steers. The cost of "non-blocking" is one optional field, two deleted closing rules, and one predicate applied at the dozen sites above. The risk is a missed site, which is why the table is exhaustive and increment 2's verification restarts the server.
</Callout>

**What the agent gets back from a non-blocking ask** (26 words, a new tool-result text; the delivery mechanism is already in the description, so it is not repeated here):

What the rail does, in the order you meet it:

- **Every open Loom question on the thread is a row**, blocking ones first, then oldest first. A row shows the header, the age (the same minute-clock label `pendingUserInputLoom.tsx` already renders), and *proceeding on: the recommended option's label*; a blocking row says *the agent is waiting* instead. Expand, answer and dismiss are on the row.
- **One row is expanded at a time.** The expanded card is upstream's question body and option list (the markdown body with file chips, `ChatMarkdown`, as today), plus the rail's own text field for an answer in your own words, an Answer button and a Dismiss button. Digits select and never submit, as today.
- **The composer is never the answer box.** Upstream's composer-as-answer-form is left as it is for native provider questions, and simply never sees a Loom question: `usePendingThreadRequests.ts` hands Loom asks (`requestId` starting `loom-ask:`) to the rail and the rest to upstream's panel. One `// loom:` hunk. The "Reply in chat instead" control and its host plumbing in `pendingUserInputLoom.tsx` go, because chat is now chat. For a **blocking** question the server still closes it as superseded when you send a chat message, so you keep the way out you have today, without the button.
- **Minimised by default while you type.** When the thread's composer draft is non-empty every row is minimised; when you clear it the rows return to their stored state. An explicit expand while typing holds until the draft is empty again.
- **Minimise state tiers** (per `docs/architecture/loom-ui-state-tiers.md`): the explicit minimise per question is tier 1, a persisted per-thread store keyed by `scopedThreadKey` holding `collapsed: Record<requestId, boolean>`, with the tier doc's versioned `migrate` and a `removeThread` action, and pruned of ids that are no longer pending on each write so it does not grow with resolved questions. A question can stand for hours across navigations and re-expanding on every visit is the state that lies. The typing default is derived, never written. The "expanded despite typing" override is tier 4, component state. Nothing here is an automatic opener, so the seed-not-override rule has nothing to override.
- **Several open questions**: the rail shows up to three rows before a *N more* line; "Dismiss all" appears at two or more.

The rail is a Loom component, `apps/web/src/loom/openQuestions/OpenQuestionsRail.tsx`, mounted by `ChatView.tsx` where the composer panel sits (one `// loom:` hunk); it answers through the existing `threadEnvironment.respondToUserInput` and `dismissUserInput` commands that `usePendingThreadRequests.ts` already wraps. Upstream's `ComposerPendingUserInputCard` is not exported today (`ComposerPendingUserInputPanel.tsx`), so reusing its body and option list for the expanded card needs one `// loom:` export hunk; if its props fight the rail's own answer state, the rail owns a ~100-line option list instead and the plan accepts that. The preview harness gets a fixture in `apps/web/src/preview/loomFixtures.ts` with three open questions, one blocking, for the render loop.

## 6. Plans' own forms

The model says a plan's `QuestionForm` is already a non-blocking question set, and asks whether the rail should list a document's open form as one entry with the document's title. The honest answer is that nothing on the server knows a form exists or whether it was answered: a form's answers arrive as review-comment context records on a later human turn, and the document is a file the agent wrote. Showing it in the rail means a tracker that notices a plan with a `QuestionForm` was handed over in this thread (from the chat chip or the write) and clears when answers arrive. That is a second feature with its own lifecycle questions (what if the human annotates but never submits the form; what if the plan is rewritten), and it is not what unblocks the question tool. **Recommendation: a follow-up**, with the pointer-card pattern retired now by the text in section 3 so the collision the audit found cannot recur in the meantime; until then the agent's chat message with the plan's chip is the signal. Decision 1 at the end lets you pull it in now instead.

## 9. Risks

- **A missed "is this thread blocked" site.** The table in section 2 is the result of reading every pending-request check on the server; a site that was missed would quietly refuse a resume, a snooze or a continuation on a thread with an open question. Mitigation: the predicate has one name, so a grep for the raw `status === "pending"` check is the review; and increment 2's verification restarts the server mid-turn.
- **The agent ignores the answer when it arrives.** The steer lands as a user message quoting the question; mid-turn it reaches a `bg_wait` at once but waits out any other tool call, and a model deep in a task may note it and carry on. Mitigation: the steer text is the question followed by the answer, which reads as an instruction rather than an aside; the measure "answered after the turn ended" shows whether late answers get acted on, and the first twenty real cases are read by hand.
- **Questions pile up.** Nothing closes a non-blocking question except you. The rail's dismiss-all and the three-row cap keep the surface small; the tool result tells the agent how many are open; decision 2 is whether to cap at the server.
- **A chat reply that answers the question in prose leaves the card open.** With supersede retired for non-blocking questions, you may answer in chat and then have to dismiss the card. Decision 4 offers keeping a softer rule.
- **Upstream's composer code stays beside the rail.** Two renderers for a question exist on the web (upstream's for native provider questions, the rail for Loom's). The seam is one filter; the duplication is the option list, which the rail reuses from upstream's card through an export hunk where its props allow.
- **Instruction text is the weakest lever.** Models were told "otherwise state an assumption and proceed" for a month and asked 6.7 times a day. What changes behaviour here is structural: the tool no longer costs the agent its turn, so asking is cheap, and the ship rule names the exact words to write instead.
