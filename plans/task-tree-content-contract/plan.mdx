# Task trees people can actually read: the content contract

The goal task tree exists so a human can glance at a thread and understand what is happening, what is planned, and what has been done — which means every task must be digestible in seconds and communicate the *value* of the work. Real trees fail this completely: tasks run to 2,600 characters of ticket ids, name-hashes, building numbers and ALL-CAPS adjudication verdicts. The structural redesign that just shipped (declarative `goal_tasks_rewrite`, tree echoes, child restrictions — `plans/goal-task-tree-redesign/plan.mdx`) fixed the *shape* problem; this plan fixes the *register* problem: what a task is allowed to say, carried by rewritten guidance with worked before/after examples plus one cheap enforcement lever.

**Done means:** the injected guidance states a concrete content contract (audience, register, where details live) anchored by a real before/after example; the server rejects new or edited task text over a hard length cap with an error that teaches the correct register; tool definitions demand value-register text; and a degraded 88-task tree from the live store, rewritten under the contract, reads as a legible plan.

## The contract: what a task is allowed to say

Derive the rules from the reader. The person glancing at the tree asks exactly three questions: **what is being done, why does it matter, and where does it stand?** The checkbox answers the third. The text must answer the first two — in language a person who has *not* lived the thread understands.

<Callout tone="decision">
**The tree records THAT work exists and whether it is done — never the details of it.** A task is a short plain-language work item naming the outcome and, when it is not obvious, its value. Everything else has a home that is not the tree: coordinates (ids, hashes, SHAs, file paths, line numbers, building/ticket numbers) live in the task's own thread, its report, or a memo file; findings, verdicts and decisions live in reports, memos, or the goal description; draft content lives in the artefact it belongs to. At most **one short pointer** (a ticket id or an artefact name) is tolerated in a task when the reader genuinely needs the key.
</Callout>

Five rules, each one falsifiable at review time:

1. **Imperative, outcome-first, plain language.** Lead with the verb; name the thing the user gets, not the mechanism ("Fix renamed tenants vanishing from the lease tab", not "re-key off names: tenant_id-FIRST with NAME FALLBACK").
2. **About a dozen words; never more than the hard cap** (~40 words / 300 characters, enforced below). If it does not fit, the surplus is detail that belongs elsewhere.
3. **At most one pointer.** One ticket id or artefact name when the reader needs it. Two or more coordinates is coordinate soup.
4. **Results are not tasks.** A finding that creates work becomes a task *phrased as the work*. A finding that settles a question goes in a report or memo. Finishing a task means ticking it — never rewriting it into a result record.
5. **Content is never inlined.** The eleven asks, the rule ledger, the runbook — those are artefacts the task can name, not text the task can carry.

## Mechanism: what carries the contract

Three levers ship; two are rejected. Everything below layers on the shipped mechanics (rewrite tool, tree echoes, child restrictions) — no schema, command, or event changes.

### 1. Injection guidance rewrite (both variants)

`activeGoalContextInstruction` (`apps/server/src/orchestration/Layers/ProviderCommandReactor.ts` ~line 194) currently spends one clause on content. It gains the contract and the micro-example; final wording is the coder's to polish, content is settled. Root-variant draft (the shape/cadence and staleness bullets survive unchanged):

<Code language="text" wrap filename="ProviderCommandReactor.ts — root variant, content bullets (draft)" code={"This tree is the human's at-a-glance view of the plan, so keep it shaped — not merely appended to:\n- Write each task for a reader who has NOT lived this thread: a short imperative item (a dozen words or so) naming the outcome in plain language — the value, not the mechanism. The server rejects task text over 300 characters.\n- The tree records THAT work exists and whether it is done, never the details: ids, hashes, file paths, ticket numbers, findings, verdicts, decisions and draft content live in reports, memo files, or the goal description. At most one short pointer (a ticket id or artefact name) belongs in a task.\n  Not: \"AIT-101 — re-key the Lease Extraction tab off names: tenant_id-FIRST with NAME FALLBACK (002336 bucket keyed by name-hash 13ef806c… ≠ roster id aacbb602…); MUST land before 450112/450117 re-trigger\"\n  But: \"Fix renamed tenants vanishing from the client's lease tab (re-key by tenant id; AIT-101)\"\n- Finishing a task means ticking it, not rewriting it into a result record — outcomes go in your report or a memo, and the goal description is a short objective statement, not a journal.\n- Nest. Top-level items are the goal's phases or themes (aim for 7 or fewer)… [unchanged]\n- Update at the seams… [unchanged]\n- The snapshot above is never refreshed… [unchanged]"} />

The child variant's single content sentence becomes: *"Keep anything you add a short plain-language work item a reader outside your thread understands (the server rejects text over 300 characters) — ids, hashes, paths, findings and verdicts go in your report, not the tree."* Token cost of the whole change: ~120 tokens once per goal-bearing thread spawn (the example is the biggest line item and is deliberately the user's own exemplar). The full four-example set does **not** ship in the injection — it lives here and one pair lives in the cap error, paid only on violation.

### 2. Hard length cap at the HTTP edge, with a teaching error

A server-side cap of **300 characters** on task text, enforced in `apps/server/src/mcp/GoalTaskHttp.ts` for all three mutating tools, with the limit exported as a constant from `goalTaskMarkdown.ts` so tests and tool-def prose reference one number.

Why 300: the healthy register sits at 80–160 chars; 300 (~40 words) is loose enough that no observed *good* task would ever hit it, yet it would have blocked 27% of historic writes — essentially every wall in the taxonomy. The cap is a backstop that makes the pathological register *impossible*; the register itself is the guidance's job.

<Callout tone="decision">
**Grandfathering: the cap applies to new text only.** `goal_task_add` and `goal_task_update` renames always check; `goal_tasks_rewrite` checks only lines that are new tasks or whose text differs from the current task's text. A retained line resubmitted verbatim always passes, whatever its length — otherwise the shipped round-trip identity contract ("`goal_task_list` output resubmitted verbatim is a no-op") breaks on every tree with a historic wall, and degraded trees become impossible to restructure. Contracts/schemas are untouched: historic 2,600-char texts must keep decoding on replay, so the cap can only live at the edge.
</Callout>

The 400 error is the teachable moment — it fires exactly when an agent is mid-wall, so it carries the register, the destinations, and the example (soft error mode returns it as tool-result text the agent reads):

<Code language="text" wrap caption="Cap error copy (add/update; the rewrite variant prefixes the offending line and appends 'Nothing was applied.')" code={"Task text is 1,479 characters; the limit is 300. The tree is the human's at-a-glance view of the plan — a task records THAT work exists, never its details. State the work as a short plain-language item (e.g. \"Fix renamed tenants vanishing from the client's lease tab (re-key by tenant id; AIT-101)\") and put ids, findings, verdicts and draft content in your report, a memo file, or the goal description."} />

The `t3 goal` CLI dispatches commands directly (`apps/server/src/cli/goal.ts` → `runOrchestrationMutation`), bypassing the HTTP edge — deliberately left uncapped as the human escape hatch. Evidence says agents are the only writers anyway (zero CLI task writes ever).

Evasion risks, weighed: **splitting** a ledger across ten 290-char tasks (bounded — each fragment is at least individually readable, the echo shows the accreting mess, and guidance says findings are not tasks at any length); **cramming** via abbreviation (guidance names plain language as the register); **displacement** into the goal description via `goal_update` (the description is injected into every spawn, so a journal there taxes every child — countered by one clause in the injection and in `goal_update`'s tool description; no cap on it yet, see open questions).

### 3. Tool-definition prose (`providerToolDefs.ts`)

Small sharpening, no new tools: `goal_task_add`'s `text` param description becomes *"a short plain-language work item naming the outcome (at most 300 characters) — never a finding, verdict, or status note; details go in reports or memos"*; `goal_task_update`'s `text` param and `goal_tasks_rewrite`'s markdown-param guideline gain the same clause; the existing `goal_tasks_rewrite` shape guideline adds "rewrite journal-entry tasks into short value-register items as you restructure — the cap only binds text you change"; `goal_update`'s description gains "the description is a short objective statement, not a journal". The six `roles/*.md` one-liners fold the register clause into their existing tree sentence.

### Rejected levers

- **Write-time content linting** (reject/warn on hex runs, ticket-id density, CAPS verdict tokens): every heuristic has legitimate hits — the contract itself permits one ticket pointer, and "Fix AIT-101" must not bounce. False positives on a hard reject poison trust in the tool; a warn is a nudge the prior wave already decided against. The cap plus register guidance covers the same mass without an arms race.
- **LLM-based register review of task text**: latency and cost on every mutation for a prototype; unpredictable rejections.
- **Per-turn re-injection of the contract**: ongoing token tax; the spawn injection plus at-violation error hit the two moments that matter.
- **Retroactive migration of existing trees**: no data change ships. Owners of live degraded goals can rewrite them in one `goal_tasks_rewrite` call whenever they next touch them (see open questions for whether to do a one-off pass now).

## Risks

- **Behavioural bet, again.** Whether register guidance changes what agents write is unfalsifiable until live trees accumulate; the cap guarantees only the ceiling, not the register. The before/after example is the strongest known steering device (it anchors the norm, not just the rule), and the at-violation error re-teaches at the exact failure moment. If register stays bad under the cap, the next lever is making `workstream_submit`/report guidance name the tree explicitly as a non-destination — cheap to add later.
- **Splitting.** A determined journaller can shard a ledger into many sub-cap tasks. Accepted: the sharded form is strictly more readable than the wall, the tree echo makes the accretion visible, and shape guidance (~7 top-level themes) caps the blast radius.
- **Displacement into the goal description.** Guarded by guidance only in this wave; a description cap is named in the open questions rather than built speculatively.
- **Cap surprises a legitimate long task.** At 300 chars the observed collision rate with *good* register is zero across 1,232 historic tasks; the error tells the agent exactly how to proceed, and the human CLI path stays uncapped.

## Resolved decisions (2026-08-13, Carl)

All four open questions were answered with the recommended option; these resolutions are binding on implementation:

1. **Cap value: 300 characters** for new/edited task text.
2. **One short pointer per task allowed** (ticket id or artefact name).
3. **No retroactive cleanup** — owners rewrite degraded trees in one call when next touched.
4. **Goal description guarded by guidance only** ("a short objective statement, not a journal"); no description cap this wave.
