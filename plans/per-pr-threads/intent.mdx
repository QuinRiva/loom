# Review one PR while the next is being built

**Goal.** "I want to be able to view what is included in a PR", and now the sharper form: "how do I review PR1 or PR2 whilst PR3 is being worked on?" Your suggestion answers it and the first draft of this brief did not: "have an orchestrator delegate to other orchestrator's, that each create their own worktrees and branches". Each PR of a series gets its own thread, worktree and branch. You open that thread to see exactly that PR, and it can act on your comments while the later PRs carry on.

**You'll know it works when.**

- An orchestrator starts each PR of a series as a child thread in its own worktree, on a branch cut from the PR below it, or on the PR's own branch when that already exists. The threads sit under the orchestrator in the sidebar.
- You open PR 1's thread while PR 3's thread is mid-turn. Its Diff tab on "Changes" with Automatic, and its Files list, show PR 1's files only, pushed or not, with nothing for you to pick and nothing an agent had to set.
- You comment on a line in PR 1's thread. It makes the fix in its own worktree, and nothing in PR 3's worktree moves.
- When PR 1 changes, the PRs above it are told and bring their branches up to date. Each one's diff still shows only its own changes afterwards.
- You tell the top orchestrator something about the whole piece of work and it reaches the right PR's thread. It reports each PR's state back to you in one place.
- You make a ruling about the whole series in one PR's thread, and the orchestrator has it without you repeating it. In the trial that took about ten relayed messages in two hours.
- A PR's thread reads the series' shared plan, budget and evidence without asking the orchestrator for them.
- A PR's thread can still have its own coder and reviewer, working in that PR's worktree.

The three corrections, which hold whichever way you go:

- "Changes" on Automatic compares a branch cut from another PR's branch against that branch, also when an agent cut the branch by hand.
- The base picker appears only beside a comparison it affects. Today it sits beside "Since your message" and "Earlier" and does nothing there, which is what you were looking at when you asked "what should I select here?".
- The thread details card's Changes figure names the branch it is measured against without a hover. In your screenshot it read "Changes vs orig…".

**Must not.**

- Merge a PR's branch back into the orchestrator's branch. The branch is the PR. Loom's earlier per-coder worktrees needed that merge, and it is what left a workstream deadlocked for 43 minutes in September.
- Fill the disk. It is 83% full, so a PR's worktree goes when its thread is settled.
- Change how a single-PR piece of work runs: one shared worktree stays the default.
- Push or open a PR. "I want to review befroe we create the pr".

**Approaches in play.**

- A child thread per PR in its own worktree and branch. Wins if reviewing and fixing one PR while another is built matters more than disk and catch-up work. Loom already creates a worktree on a new branch from a chosen base for a handed-off goal, and records that base, which is why Automatic would be right with nothing picked. What is missing is letting a child start that way. _Chosen, to be built if the trial suits you._
- The same, tried by hand first: the graph-enrichment orchestrator hands its next PR off as its own goal in a fresh worktree. Wins if you want to know it suits you before anything is built. It is rougher than the real thing: the PR's thread is not nested under the orchestrator, and it starts from the project's main checkout and has to move itself onto the PR below. _Chosen as the first step, and done on 25 Nov._
  - What worked: you reviewed the linking PR (PE-2853, #4530), changed the design twice and approved the ticket and the PR in its own thread. Nothing in the orchestrator's worktree moved.
  - What was awkward was mostly the hand route. The thread was not a child, so the orchestrator heard from it only by message. It also had to move itself onto the branch and set its own base.
- A per-PR list in the shared worktree, the first draft. It is viable, since reading a branch that is not checked out is ordinary git. It answers reading only, so it is kept as the fallback if a worktree per PR proves too heavy.
- jj. It would not remove the need for a worktree per PR, because two agents still cannot share one set of files on disk. What it adds is that later PRs catch up by themselves when an earlier one changes. Loom has no jj support, and upstream has merged none: every jj PR there is closed, the latest set on 26 Oct without maintainer approval. _Not recommended for this._
- Dropped: push each PR as a draft and read it on the Pull requests page. You said "I want to review befroe we create the pr".
