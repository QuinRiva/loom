# Thread content search: hybrid lexical + semantic search over root threads

**Objective.** Carl types a few words he remembers about a piece of work — "sidebar v2 rehome", "slash commands in loom", "the model picker with duplicate names" — and the right **top-level thread** is in the first three results, whether it is active or archived, and whether the words came from its title, its goal, a child's brief, a child's report, something the agent said, or a paraphrase of any of those. Done means: the 57-query acceptance set in [Verification](#verification) clears its measured floor on a copy of Carl's real database (with the default local embedder: R@5 ≥ 70 % and MRR ≥ 0.50 on the 43 headline queries; 8/8 exact-identifier queries at #1), results appear within the existing 200 ms debounce on the sidebar, command palette and mobile, search keeps working (lexical-only) when the embedding model is unavailable, and the upstream `LIKE` scan is gone — not sitting beside the new path.

**Evidence base** (read for defect-level detail this plan does not repeat): the search landscape report `/home/Carl/.t3/cockpit/userdata/workstream-reports/c2af4d05-d816-4ff7-8a5d-b9bcb9cf6af1.md`, the pi-session-search assessment `/home/Carl/.t3/cockpit/userdata/workstream-reports/065150b1-ecff-467c-b9bc-eb28381bd07e.md`, and the embedding-model benchmark `/home/Carl/.t3/cockpit/userdata/workstream-reports/01078735-7e35-4e58-9bcf-6620c377f452.md` (five models, two fusion variants, 57 queries). Every number below that is not from those reports was measured for this plan on this machine — the production VM, 16 vCPU Xeon, 62 GB RAM, no GPU — against the `VACUUM INTO` snapshot at `.t3/research/state.sqlite` (5 GB, gitignored, safe to delete).

<Callout tone="decision">
**Recommendation: evolve upstream's `orchestration.searchThreads` in place onto two loom-owned structures in `state.sqlite` — an FTS5 index kept current by SQLite triggers, and one embedding vector per root thread produced by a pluggable embedding provider (default: in-process `bge-small-en-v1.5`) — fused by reciprocal rank fusion in which the lexical side votes only for full-term matches, ranked per root.** The FTS5 table (`loom_thread_search`, porter-stemmed, one row per text unit: title, purpose, brief, goal, task, user message, final assistant message, workstream report) is populated by triggers on the projection tables plus one hook where reports are written, so it cannot drift from the projection. The semantic side is one vector per root over its title, purpose, goal, opening prompt and child titles, produced by whichever of four providers (`none`, `local`, `openai-compatible`, `vertex`) `settings.json` selects, stamped with the provider/model/dimension that made it, and refreshed by a background sweep. The query credits every hit to its root, includes archived roots (marked), returns everything the client needs to draw the row, and runs lexical-only whenever the configured provider is `none` or unavailable.
</Callout>

## Decisions settled in review

Carl reviewed the first draft; these are decided and no longer open:

1. **Embeddings ship in v1, through a pluggable provider, with a local default.** Anthropic has no embeddings API and the OpenAI Codex subscription does not grant `/v1/embeddings`, so the default must run on the box: **in-process `bge-small-en-v1.5` via `@huggingface/transformers`**, confirmed by the five-model benchmark (EmbeddingGemma within noise at 15× the per-root cost; Qwen3-0.6B worse; Vertex `gemini-embedding-2` measurably better but a network and credential dependency). Loom must also run with **no** embedder, or with a different one, the way it supports multiple agent providers — so the embedder is a tiny interface with four implementations (`none`, `local`, `openai-compatible`, `vertex`), selected in `settings.json`. See [Semantic side](#semantic-side-one-vector-per-root-through-a-pluggable-provider).
6. **Fusion is reciprocal rank fusion with a full-coverage lexical list.** The first draft's equal-weight RRF over lexical top-50 and semantic top-50 *reduced* quality for every model (bge-small R@1 51 % → 40 %): lexical's partial-term matches outvote a correct semantic #1. Lexical now votes only for roots whose best document contains every query term. See [Fusion](#fusion).
7. **The acceptance set is the benchmark's 57 queries**, committed beside the harness, with a measured floor per provider instead of "every root top-3" (which only semantic-only meets). See [Verification](#verification).
2. **Workstream reports are indexed from the start** (kind `report`, see [What goes in](#what-goes-in-and-with-what-weight)).
3. **Content hits are root-only on every surface, without exception.** Carl: "I can't imagine that I would *ever* want to find a sub-thread this way … enabling sub-threads to appear in the result is just going to clutter the result with things I'm not looking for." A sub-thread remains reachable by its title through the palette's local term match; its *content* always credits the top-level thread.
4. **The legacy sidebar is out of scope** — Carl uses the default sidebar.
5. **pi-session-search stays rejected even with its sync re-enabled** — the rejection row below says why.

## What exists today, and what is actually wrong with it

Upstream shipped content search on 30 Jul 2026 (`feat(search): find threads by conversation content #4959`) and it is live in loom on the sidebar, the command palette and mobile. The landscape report measured its failure modes on Carl's data; the ones that matter for the design are:

| Symptom | Cause in code | Measured |
|---|---|---|
| The root you want is missing | `searchActiveThreadRows` caps at 50 *threads*, children included; `searchSidebarThreads` then drops any hit whose thread is not a root — children are discarded, not credited to their parent | "sidebar": 145 hits, 54 roots, **5 roots survive** |
| Old work is unfindable | `WHERE threads.archived_at IS NULL` | **217 of 517 roots (42%)** excluded |
| Must remember exact phrasing | one contiguous `LIKE '%q%'` | "thread search" → 3 threads; word-anywhere → 374 |
| Titles, goals, briefs, reports are invisible | only `projection_thread_messages` rows with `role='user'` or a turn's `assistant_message_id` are scanned | 0.7 M chars of purpose, 7.4 M of brief, 1.6 M of goal+task, 28 MB of reports never searched |
| Slow | full-table `LIKE` over 17 k rows | ~200 ms per keystroke settle |

One correction to the landscape report: in loom the scan does **not** run on the writer connection. `ProjectionSnapshotQueryLanes` in `/home/Carl/.t3/cockpit/worktrees/loom/t3code-57998ed5/apps/server/src/persistence/Layers/SqliteLanes.ts` already builds every `ProjectionSnapshotQuery` method (including `searchThreads`) on the worker-thread `SqlReadClient`; only `getThreadRuntimeContext` is pinned in-process. The new query inherits the read lane for free.

The client side is a thin, shared consumer: `useThreadSearch` (`apps/web/src/state/queries.ts`, mirrored in `apps/mobile/src/state/queries.ts`) debounces 200 ms, requires two characters and fans one request per connected environment through `createThreadSearchResultsAtomFamily` in `packages/client-runtime/src/state/threadSearch.ts`. Sidebar, command palette and the three mobile lists each key the returned matches by `[environmentId, threadId]` onto the shells they already hold. That shape is kept: the server decides *which roots* and *in what order*; the clients only decorate.

**Where it plugs in: evolve `orchestration.searchThreads`, do not add a loom RPC.** The request is a live upstream contract consumed by web, mobile and the palette through one shared atom family. **Why per text unit rather than one document per root.** Per-root documents make ranking trivial but maintenance expensive and fuzzy: every turn, title change, task edit or child spawn anywhere in a tree would rebuild a document of up to 1.7 M chars from application code. Per-unit rows are maintained by SQLite triggers in the same transaction as the projection write, cost microseconds each, and give bm25 short, well-normalised documents. Root attribution moves to query time, where a recursive CTE over 3.8 k threads costs ~10 ms.

**Why the derived rowid.** Measured: `DELETE FROM fts WHERE ref = ?` on an UNINDEXED column is a 30 ms content-table scan; by rowid it is a B-tree lookup. All source tables are ordinary rowid tables (TEXT primary keys, not `WITHOUT ROWID`), upserts are `ON CONFLICT DO UPDATE` so rowids are stable, and the server never runs an in-place `VACUUM` (only `VACUUM INTO` copies). The one hazard — a future migration that rebuilds a source table renumbers rowids — is handled by that migration re-running the exported backfill; see [Risks](#risks).

### Tokenizer: porter, not trigram

| | `porter unicode61 remove_diacritics 2` | `trigram` |
|---|---|---|
| Index size (landscape trial, messages only) | 71 MB | 173 MB |
| Query | 1–5 ms | 6–9 ms |
| Buys | stemming (rehome/rehoming/re-home → rehom; lanes → lane), prefix search on the last term as you type | substring-of-word matching anywhere in a token |
| Does not buy | mid-word substrings | stemming; terms under 3 characters; typo tolerance |

Porter matches how Carl searches (words he remembers, roughly inflected) and halves the index; paraphrase is the semantic side's job.

### Kept current by triggers (plus one hook for reports)

Migration `1044_ThreadSearchIndex.ts` (loom lane, `LoomMigrations.ts`) creates both tables, installs the triggers and backfills. The trigger and backfill SQL live once in `threadSearchIndex.loom.ts` so a future rebuild migration reuses them verbatim.

<Code

  language="sql"
  wrap
  code={"-- threads: title (1), purpose (2), brief (3). Fires only when those columns change.\nCREATE TRIGGER loom_ts_threads_au AFTER UPDATE OF title, purpose, brief, deleted_at ON projection_threads BEGIN\n  DELETE FROM loom_thread_search WHERE rowid IN (OLD.rowid*8+1, OLD.rowid*8+2, OLD.rowid*8+3);\n  INSERT INTO loom_thread_search(rowid, thread_id, kind, text)\n    SELECT NEW.rowid*8+1, NEW.thread_id, 'title', NEW.title WHERE NEW.deleted_at IS NULL;\n  INSERT INTO loom_thread_search(rowid, thread_id, kind, text)\n    SELECT NEW.rowid*8+2, NEW.thread_id, 'purpose', NEW.purpose WHERE NEW.deleted_at IS NULL AND NEW.purpose <> '';\n  INSERT INTO loom_thread_search(rowid, thread_id, kind, text)\n    SELECT NEW.rowid*8+3, NEW.thread_id, 'brief', NEW.brief WHERE NEW.deleted_at IS NULL AND NEW.brief <> '';\nEND;\n-- (AFTER INSERT has the same three inserts; AFTER DELETE removes rowids *8+0..3, i.e. the report row too.)\n\n-- messages: user (4), assistant (5). Only finalised text: streaming deltas UPDATE text with is_streaming = 1\n-- (appendStreaming in ProjectionThreadMessages.ts) and must not be indexed per delta.\nCREATE TRIGGER loom_ts_messages_au AFTER UPDATE OF text, is_streaming, origin ON projection_thread_messages\nWHEN NEW.is_streaming = 0 BEGIN\n  DELETE FROM loom_thread_search WHERE rowid IN (NEW.rowid*8+4, NEW.rowid*8+5);\n  INSERT INTO loom_thread_search(rowid, thread_id, kind, text)\n    SELECT NEW.rowid*8+4, NEW.thread_id, 'user', NEW.text\n    WHERE NEW.role = 'user' AND (NEW.origin IS NULL OR NEW.origin NOT IN ('kickoff', 'control_notice'));\n  INSERT INTO loom_thread_search(rowid, thread_id, kind, text)\n    SELECT NEW.rowid*8+5, NEW.thread_id, 'assistant', NEW.text\n    WHERE NEW.role = 'assistant'\n      AND EXISTS (SELECT 1 FROM projection_turns WHERE assistant_message_id = NEW.message_id);\nEND;\n-- (AFTER INSERT ... WHEN NEW.is_streaming = 0 has the same body; AFTER DELETE removes both rowids.)\n\n-- turns: the final assistant message may be recorded before or after the message finalises,\n-- so both sides index it; the derived rowid makes the double write idempotent.\nCREATE TRIGGER loom_ts_turns_au AFTER UPDATE OF assistant_message_id ON projection_turns\nWHEN NEW.assistant_message_id IS NOT NULL BEGIN\n  DELETE FROM loom_thread_search WHERE rowid IN (\n    SELECT m.rowid*8+5 FROM projection_thread_messages m WHERE m.message_id IN (OLD.assistant_message_id, NEW.assistant_message_id));\n  INSERT INTO loom_thread_search(rowid, thread_id, kind, text)\n    SELECT m.rowid*8+5, m.thread_id, 'assistant', m.text FROM projection_thread_messages m\n    WHERE m.message_id = NEW.assistant_message_id AND m.is_streaming = 0;\nEND;\n\n-- goals (6) and tasks (7): keyed by goal_id, thread_id NULL; attributed to roots at query time.\nCREATE TRIGGER loom_ts_goals_au AFTER UPDATE OF title, description, deleted_at ON projection_goals BEGIN\n  DELETE FROM loom_thread_search WHERE rowid = OLD.rowid*8+6;\n  INSERT INTO loom_thread_search(rowid, goal_id, kind, text)\n    SELECT NEW.rowid*8+6, NEW.goal_id, 'goal', NEW.title || char(10) || NEW.description WHERE NEW.deleted_at IS NULL;\nEND;\n-- tasks: same shape on projection_goal_tasks(text, deleted_at) → rowid*8+7.\n\n-- reports (0): no trigger can read a file, so the one place that writes the file also writes the row\n-- (writeWorkstreamReport, see below). Latest report per thread wins: a gate round replaces the previous row.\n-- DELETE FROM loom_thread_search WHERE rowid = (SELECT rowid*8 FROM projection_threads WHERE thread_id = ?);\n-- INSERT INTO loom_thread_search(rowid, thread_id, kind, text) SELECT rowid*8, thread_id, 'report', ? FROM projection_threads WHERE thread_id = ?;\n"}

Why triggers and not a projector hunk: the text arrives through five repository write paths (`ProjectionThreadMessages.upsert` and `.appendStreaming`, `ProjectionTurns.upsert`, `ProjectionThreads` upserts, goals, tasks) plus `DELETE FROM … WHERE thread_id` on thread deletion. Triggers cover all of them from one file, run inside the same transaction, see the source `rowid` without an extra `SELECT`, and cannot be forgotten by a future write path. Reports are the one exception: `writeWorkstreamReport` in `/home/Carl/.t3/cockpit/worktrees/loom/t3code-57998ed5/apps/server/src/orchestration/workstreamReport.ts` already has the thread id and the markdown in hand; it gains a `SqlClient` dependency and runs the two statements above after the file write. Backfill in the migration reads each `projection_threads.report_path` with `node:fs` (3.8 k files, 28 MB, ~1 s; missing files skipped) — the migration already runs on the writer with the DB open, and `report_path` values are absolute.

Backfill of the other seven kinds is the seven `INSERT … SELECT` statements used to build the trial index, then `INSERT INTO loom_thread_search(loom_thread_search) VALUES('optimize')`. On Carl's 5.5 GB database this adds roughly three seconds to one startup. Reads run wherever `ProjectionSnapshotQuery` already runs — the worker read lane.

## Semantic side: one vector per root, through a pluggable provider

### The provider interface

**Why Vertex needs a native adapter.** The benchmark proved Vertex's OpenAI-compatible endpoint (`/endpoints/openapi/embeddings`) returns HTTP 500 for both Gemini embedding models in every location tried, so `openai-compatible` cannot reach it. The native REST calls above worked (`gemini-embedding-001` p50 235 ms per query from `australia-southeast1`; `gemini-embedding-2` p50 632 ms, `global` only). **Data residency:** `gemini-embedding-2` is served only from the `global` endpoint and returns 404 in `australia-southeast1`, so choosing it sends thread text outside Australia; `gemini-embedding-001` stays in-region at a lower MRR (0.60 vs 0.63 fused). The plan's default Vertex config is therefore `gemini-embedding-001` in `australia-southeast1`; the operator opts into `gemini-embedding-2` knowingly.

**Vertex auth.** `google-auth-library` 10.9.1 is already in the server's dependency graph (pi-coding-agent → pi-ai → `@google/genai`), so declaring it directly in `apps/server/package.json` at the same version adds nothing to the install. `new GoogleAuth({ scopes: ["https://www.googleapis.com/auth/cloud-platform"] }).getClient()` resolves Application Default Credentials (the `test-ds-research` service account on this VM) and `getAccessToken()` caches and refreshes the hourly token itself; no hand-rolled refresh timer. <Callout tone="decision">
**Default: `Xenova/bge-small-en-v1.5`, int8 ONNX, run in the server process by `@huggingface/transformers` on `onnxruntime-node`.** It is the fastest option by an order of magnitude on the keystroke path, removes any daemon or network, and the larger local models buy nothing measurable. The server bundle owns its default embedder the same way it owns `node-pty` and `@ff-labs/fff-node`: `@huggingface/transformers` is a declared, externalised dependency, `import()`ed lazily so a missing package degrades rather than crashes.
</Callout>

**What is embedded.** One document per root: `title`, `purpose`, goal title and description, the first non-automated user message (origin `NULL`, capped at 800 chars), and the titles of its direct children (capped at 400 chars), joined by newlines. On Carl's DB that is a median of 242 bge tokens (p90 441); 3 % of roots exceed bge-small's 512-token window, with the lowest-value text (child titles) last so truncation drops the right end. Providers apply their own query/document framing per the table above; the document text itself is provider-independent, which is what lets `source_hash` survive a provider switch.

**How it stays fresh — a hash sweep, not event plumbing.** `ThreadEmbedder.loom.ts` is an Effect service with one job: make `loom_thread_embeddings` agree with the current root documents under the current provider identity. On startup and every 2 minutes it runs one SQL statement that builds the document text for every non-deleted root (528 rows, single-digit ms), hashes each, and queues for embedding every root whose stored row is missing, has a different `source_hash`, or has a different `identity`. The queue is drained sequentially in the background (the local default: 24 ms per root, so a fresh database or a provider switch completes in ~12 s; Vertex: a few minutes at one request at a time, or ~15 s if the provider batches 8-wide as the benchmark did). A sweep after the first finds the handful of roots whose title, purpose, goal or children changed. This replaces per-event wiring with one short query, at the cost of up to two minutes of semantic staleness on a brand-new root — acceptable, because a root under two minutes old is at the top of the sidebar anyway. The in-memory matrix (`Float32Array` of n × dim, identity-matched rows only) is updated on each write.

**Graceful degradation.** `none` and "unavailable" are the same path: `searchThreads` runs lexical-only, which is already a complete answer. Availability is probed lazily on the first search or sweep; a failure logs once at `warn` with the reason (package missing, download failed, ADC unresolved, HTTP 401) and is retried on the next sweep. The search request path never awaits a model load or a network call for availability: a query arriving while the provider is still loading is answered lexically. Vectors whose `identity` does not match the configured provider are never fused — they sit in the table only until the sweep replaces them.

## Ranking and result shape

### Lexical query recipe

The query builder in `ThreadSearch.loom.ts`: lowercase, split on non-alphanumerics, drop a two-dozen-word English stopword list (unless that empties the query), quote each term, and give the **last** term a prefix `*` so results move while Carl is still typing. One `MATCH` per term (typically 2–5, each 4–8 ms) gives per-document **term coverage**, which pure OR-bm25 cannot express and which turned out to be the decisive lexical signal.

<Code
  filename="ThreadSearch.loom.ts — lexical ranking query (one root per row)"
  language="sql"
  wrap
  code={"WITH RECURSIVE roots(thread_id, root_id) AS MATERIALIZED (\n  SELECT thread_id, thread_id FROM projection_threads WHERE parent_thread_id IS NULL\n  UNION ALL\n  -- CROSS JOIN pins the join order: without it the planner scans the recursive queue per row (13 s vs 10 ms).\n  SELECT t.thread_id, r.root_id FROM roots r CROSS JOIN projection_threads t ON t.parent_thread_id = r.thread_id\n),\nhits AS MATERIALIZED (            -- one arm per query term; ?1..?n are the quoted terms, last one with *\n  SELECT 0 AS term, rowid, thread_id, goal_id, kind,\n         bm25(loom_thread_search) * CASE kind WHEN 'title' THEN 4 WHEN 'purpose' THEN 3 WHEN 'goal' THEN 3\n                                              WHEN 'brief' THEN 1.5 WHEN 'task' THEN 1.5 WHEN 'assistant' THEN 0.8 ELSE 1 END AS score\n  FROM loom_thread_search WHERE loom_thread_search MATCH ?1\n  UNION ALL SELECT 1, rowid, thread_id, goal_id, kind, bm25(loom_thread_search) * … FROM loom_thread_search WHERE loom_thread_search MATCH ?2\n  -- …\n),\ndocs AS (SELECT rowid, thread_id, goal_id, kind, COUNT(DISTINCT term) AS coverage, SUM(score) AS score FROM hits GROUP BY rowid),\nattributed AS (\n  SELECT COALESCE(r.root_id, g.thread_id) AS root_id, d.*\n  FROM docs d\n  LEFT JOIN roots r ON r.thread_id = d.thread_id\n  LEFT JOIN projection_threads g ON d.goal_id IS NOT NULL AND g.goal_id = d.goal_id AND g.parent_thread_id IS NULL\n),\nranked AS (\n  SELECT *, ROW_NUMBER() OVER (PARTITION BY root_id ORDER BY coverage DESC, score) AS rn\n  FROM attributed WHERE root_id IS NOT NULL\n)\nSELECT p.root_id, p.rowid, p.kind, p.thread_id AS matched_thread_id, p.coverage\nFROM ranked p JOIN projection_threads t ON t.thread_id = p.root_id\nWHERE p.rn = 1 AND t.deleted_at IS NULL\nORDER BY p.coverage DESC, p.score, t.updated_at DESC\nLIMIT 50; />

**Lexical rule, in words:** a root's score is its single best document; a document is better if it contains more of the query's terms, then by kind-weighted bm25 (bm25 is negative, lower is better); ties by the root's recency. Best-document rather than sum-of-documents is deliberate: sum makes 200-child orchestrator roots win every query ("Cadence pull 7" topped six of eight sums). End-to-end on the snapshot: 40–60 ms for a four-term query including root attribution, before snippets, on the worker lane.

### Fusion

`searchThreads` runs both sides concurrently: the lexical query on the read lane (top-50 roots, each carrying the `coverage` of its best document) and, if the configured provider is available, the query embed (3.5 ms for the default) plus a dot product against the in-memory matrix (top-50 roots, archived included). The two lists are combined by reciprocal rank fusion with k = 60 — `score(root) = Σ 1 / (60 + rank_in_list)` over the lists the root appears in — ordered by that score, ties by recency, first `limit` returned. RRF needs no calibration between bm25 and cosine, which is why pi-session-search uses it too.

<Callout tone="decision">
**Lexical votes only for full-coverage roots.** Before fusion the lexical list is filtered to roots whose best document contains *every* query term (`WHERE coverage = n_terms`); the rest of the lexical top-50 is discarded. Equal-weight RRF over the unfiltered lists — the first draft's recipe — *lowered* quality for every model on the 43 headline queries (bge-small R@1 51 % → 40 %, R@5 70 % → 58 %; gemini-embedding-2 R@1 63 % → 40 %), because lexical's top-50 is mostly partial-term noise that outvotes a correct semantic #1 the lexical side never found. With the filter the fused result keeps semantic-only's R@5 and R@10 while recovering the deep-detail queries semantic-only cannot answer. The filter has no free parameter and never lost to the unfiltered variant on any query group; it was designed on this set, so re-check it when the set grows.
</Callout>

## Risks

- **Heavy native dependency for the default provider.** `onnxruntime-node` is 536 MB on disk (327 MB of it a CUDA provider that is never loaded) in a 3.4 GB release `node_modules`; `sharp` comes along as a transitive dependency of transformers. Mitigation: externalised like `node-pty`, loaded lazily so its absence degrades to lexical-only; trimming the CUDA `.so` is a later nicety. The Windows desktop sidecar derives its runtime roots from the same externals list and would ship it too — loom does not build that artifact today.
- **First-run network for the default provider.** The 34 MB model downloads from huggingface.co once into `<stateDir>/models/`. If the production VM cannot reach it, search runs lexical-only and logs why; the files can be copied in by hand, or the operator switches to `vertex`.
- **Vertex specifics.** `gemini-embedding-2` is served only from `global` (thread text leaves Australia); the OpenAI-compatible Vertex route is broken (HTTP 500), so only the native adapter works; a revoked or expired ADC credential turns search lexical-only until the next sweep succeeds. Per-query latency (235–630 ms) sits on the keystroke path, inside the 200 ms debounce plus request time rather than hidden by it.
- **Fusion rule designed on the acceptance set.** The full-coverage filter has no tunable parameter and beat the unfiltered variant on every group, but the 57 queries are the only evidence; new paraphrase queries that lexical would have rescued with a partial match are the failure mode to watch. The harness and the committed set make it a one-command check.
- **Rowid renumbering.** A future migration that rebuilds a source table by copy-and-rename invalidates the derived rowids. Mitigation: the rebuild migration re-runs the exported backfill (`delete-all` then the eight inserts); `threadSearchIndex.loom.ts` says so at the top.
- **Column drops.** `ALTER TABLE … DROP COLUMN` fails on a column a trigger references (loom's own `1041` dropped columns on `projection_thread_messages`). Mitigation: the exported `dropTriggers`/`createTriggers` pair brackets any such migration.
- **Upstream drift on `searchThreads`.** Upstream may change the contract or ship its own FTS. The `// loom:` hunks are small and the harness is the regression check at the next pull.
- **Staleness window on the semantic side.** A root is embedded within ~2 minutes of changing, not instantly; a brand-new root is lexically searchable immediately (triggers) and semantically after the next sweep. A provider switch re-embeds everything, during which fusion uses only the identity-matched rows embedded so far.
- **bm25 per-term arms cost O(hits).** Five common terms ≈ 40 ms plus attribution; if it grows, cap the arms at the six rarest terms.
