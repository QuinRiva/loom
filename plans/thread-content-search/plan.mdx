# Thread content search: hybrid lexical + semantic search over root threads

**Objective.** Carl types a few words he remembers about a piece of work — "sidebar v2 rehome", "slash commands in loom", "the model picker with duplicate names" — and the right **top-level thread** is in the first three results, whether it is active or archived, and whether the words came from its title, its goal, a child's brief, a child's report, something the agent said, or a paraphrase of any of those. Done means: all eight acceptance queries in [Verification](#verification) rank their root top-3 on a copy of Carl's real database, results appear within the existing 200 ms debounce on the sidebar, command palette and mobile, search keeps working (lexical-only) when the embedding model is unavailable, and the upstream `LIKE` scan is gone — not sitting beside the new path.

**Evidence base** (read for defect-level detail this plan does not repeat): the search landscape report `/home/Carl/.t3/cockpit/userdata/workstream-reports/c2af4d05-d816-4ff7-8a5d-b9bcb9cf6af1.md` and the pi-session-search assessment `/home/Carl/.t3/cockpit/userdata/workstream-reports/065150b1-ecff-467c-b9bc-eb28381bd07e.md`. Every number below that is not from those reports was measured for this plan on this machine — the production VM, 16 vCPU Xeon, 62 GB RAM, no GPU — against the `VACUUM INTO` snapshot at `.t3/research/state.sqlite` (5 GB, gitignored, safe to delete).

<Callout tone="decision">
**Recommendation: evolve upstream's `orchestration.searchThreads` in place onto two loom-owned structures in `state.sqlite` — an FTS5 index kept current by SQLite triggers, and one embedding vector per root thread computed in-process by `bge-small-en-v1.5` — fused by reciprocal rank fusion and ranked per root.** The FTS5 table (`loom_thread_search`, porter-stemmed, one row per text unit: title, purpose, brief, goal, task, user message, final assistant message, workstream report) is populated by triggers on the projection tables plus one hook where reports are written, so it cannot drift from the projection. The semantic side is a 384-dimensional vector per root over its title, purpose, goal, opening prompt and child titles, produced by `@huggingface/transformers` (ONNX, CPU, no daemon) in 105 ms per root and 9 ms per query, refreshed by a background sweep. The query credits every hit to its root, includes archived roots (marked), returns everything the client needs to draw the row, and degrades to lexical-only if the model cannot load.
</Callout>

## Decisions settled in review

Carl reviewed the first draft; these are decided and no longer open:

1. **Embeddings ship in v1, locally.** Anthropic has no embeddings API; the OpenAI Codex subscription does not grant `/v1/embeddings`; Vertex would add a network and credential dependency to a local search feature. The runtime and model were benchmarked on this box (see [Semantic side](#semantic-side-one-vector-per-root-in-process)) — **in-process `bge-small-en-v1.5` via `@huggingface/transformers`**, not the Ollama daemon.
2. **Workstream reports are indexed from the start** (kind `report`, see [What goes in](#what-goes-in-and-with-what-weight)).
3. **Content hits are root-only on every surface, without exception.** Carl: "I can't imagine that I would *ever* want to find a sub-thread this way … enabling sub-threads to appear in the result is just going to clutter the result with things I'm not looking for." A sub-thread remains reachable by its title through the palette's local term match; its *content* always credits the top-level thread.
4. **The legacy sidebar is out of scope** — Carl uses the default sidebar.
5. **pi-session-search stays rejected even with its sync re-enabled** — the rejection row below says why.

## What exists today, and what is actually wrong with it

Upstream shipped content search on 30 Jul 2026 (`feat(search): find threads by conversation content #4959`) and it is live in loom on the sidebar, the command palette and mobile. The landscape report measured its failure modes on Carl's data; the ones that matter for the design are:

| Symptom | Cause in code | Measured |
|---|---|---|
| The root you want is missing | `searchActiveThreadRows` caps at 50 *threads*, children included; `searchSidebarThreads` then drops any hit whose thread is not a root — children are discarded, not credited to their parent | "sidebar": 145 hits, 54 roots, **5 roots survive** |
| Old work is unfindable | `WHERE threads.archived_at IS NULL` | **217 of 517 roots (42%)** excluded |
| Must remember exact phrasing | one contiguous `LIKE '%q%'` | "thread search" → 3 threads; word-anywhere → 374 |
| Titles, goals, briefs, reports are invisible | only `projection_thread_messages` rows with `role='user'` or a turn's `assistant_message_id` are scanned | 0.7 M chars of purpose, 7.4 M of brief, 1.6 M of goal+task, 28 MB of reports never searched |
| Slow | full-table `LIKE` over 17 k rows | ~200 ms per keystroke settle |

One correction to the landscape report: in loom the scan does **not** run on the writer connection. `ProjectionSnapshotQueryLanes` in `/home/Carl/.t3/cockpit/worktrees/loom/t3code-57998ed5/apps/server/src/persistence/Layers/SqliteLanes.ts` already builds every `ProjectionSnapshotQuery` method (including `searchThreads`) on the worker-thread `SqlReadClient`; only `getThreadRuntimeContext` is pinned in-process. The new query inherits the read lane for free.

The client side is a thin, shared consumer: `useThreadSearch` (`apps/web/src/state/queries.ts`, mirrored in `apps/mobile/src/state/queries.ts`) debounces 200 ms, requires two characters and fans one request per connected environment through `createThreadSearchResultsAtomFamily` in `packages/client-runtime/src/state/threadSearch.ts`. Sidebar, command palette and the three mobile lists each key the returned matches by `[environmentId, threadId]` onto the shells they already hold. That shape is kept: the server decides *which roots* and *in what order*; the clients only decorate.

**Why per text unit rather than one document per root.** Per-root documents make ranking trivial but maintenance expensive and fuzzy: every turn, title change, task edit or child spawn anywhere in a tree would rebuild a document of up to 1.7 M chars from application code. Per-unit rows are maintained by SQLite triggers in the same transaction as the projection write, cost microseconds each, and give bm25 short, well-normalised documents. Root attribution moves to query time, where a recursive CTE over 3.8 k threads costs ~10 ms.

**Why the derived rowid.** Measured: `DELETE FROM fts WHERE ref = ?` on an UNINDEXED column is a 30 ms content-table scan; by rowid it is a B-tree lookup. All source tables are ordinary rowid tables (TEXT primary keys, not `WITHOUT ROWID`), upserts are `ON CONFLICT DO UPDATE` so rowids are stable, and the server never runs an in-place `VACUUM` (only `VACUUM INTO` copies). The one hazard — a future migration that rebuilds a source table renumbers rowids — is handled by that migration re-running the exported backfill; see [Risks](#risks).

### Tokenizer: porter, not trigram

| | `porter unicode61 remove_diacritics 2` | `trigram` |
|---|---|---|
| Index size (landscape trial, messages only) | 71 MB | 173 MB |
| Query | 1–5 ms | 6–9 ms |
| Buys | stemming (rehome/rehoming/re-home → rehom; lanes → lane), prefix search on the last term as you type | substring-of-word matching anywhere in a token |
| Does not buy | mid-word substrings | stemming; terms under 3 characters; typo tolerance |

Porter matches how Carl searches (words he remembers, roughly inflected) and halves the index; paraphrase is the semantic side's job.

Why triggers and not a projector hunk: the text arrives through five repository write paths (`ProjectionThreadMessages.upsert` and `.appendStreaming`, `ProjectionTurns.upsert`, `ProjectionThreads` upserts, goals, tasks) plus `DELETE FROM … WHERE thread_id` on thread deletion. Triggers cover all of them from one file, run inside the same transaction, see the source `rowid` without an extra `SELECT`, and cannot be forgotten by a future write path. Reports are the one exception: `writeWorkstreamReport` in `/home/Carl/.t3/cockpit/worktrees/loom/t3code-57998ed5/apps/server/src/orchestration/workstreamReport.ts` already has the thread id and the markdown in hand; it gains a `SqlClient` dependency and runs the two statements above after the file write. Backfill of the other seven kinds is the seven `INSERT … SELECT` statements used to build the trial index, then `INSERT INTO loom_thread_search(loom_thread_search) VALUES('optimize')`. On Carl's 5.5 GB database this adds roughly three seconds to one startup. Reads run wherever `ProjectionSnapshotQuery` already runs — the worker read lane.

<Callout tone="decision">
**`Xenova/bge-small-en-v1.5`, int8 ONNX, run in the server process by `@huggingface/transformers` on `onnxruntime-node`.** It is 5× faster per root and 10× faster per query than the Ollama path with identical quality on the acceptance set, and it removes the daemon: the server bundle owns its embedder the same way it already owns `node-pty` and `@ff-labs/fff-node`. The cost is a heavy native dependency on disk (onnxruntime-node ships every execution provider) and a one-time 34 MB model download from the Hugging Face Hub on first use. Inference runs on onnxruntime's own thread pool, so a 105 ms root embed does not block the event loop; intra-op threads are capped at 4 of the 16 vCPUs.
</Callout>

**What is embedded.** One document per root: `title`, `purpose`, goal title and description, the first non-automated user message (origin `NULL`, capped at 800 chars), and the titles of its direct children (capped at 400 chars), joined by newlines. On Carl's DB that is a median of 1.1 k chars (≈260 tokens; p90 ≈540 tokens) — inside bge-small's 512-token window for almost every root, with the lowest-value text (child titles) last so truncation, when it happens, drops the right end. Queries are prefixed with bge's instruction string (`Represent this sentence for searching relevant passages: `); documents are not. Vectors are L2-normalised so cosine is a dot product.

**Where the model lives.** `env.cacheDir` is `<stateDir>/models/` under the T3 home (sibling of `workstream-reports/`), so the one-time download lands in durable state, not the worktree or `$HOME`. After that the server is fully offline for search.

**How it stays fresh — a hash sweep, not event plumbing.** `ThreadEmbedder.loom.ts` is an Effect service with one job: make `loom_thread_embeddings` agree with the current root documents. On startup and every 2 minutes it runs one SQL statement that builds the document text for every non-deleted root (517 rows, single-digit ms), hashes each, compares with `source_hash`, and queues the differing roots (and roots with no row) for embedding, sequentially, in the background. A fresh database embeds everything in ~54 s; thereafter a sweep typically finds the handful of roots whose title, purpose, goal or children changed since the last pass. This replaces per-event wiring (title regeneration, goal edits, child spawns, first message) with one 10-line query, at the cost of up to two minutes of staleness on a brand-new root — acceptable, because a root under two minutes old is at the top of the sidebar anyway. The in-memory matrix (`Float32Array` of 517 × 384) is updated on each write.

**Graceful degradation.** The embedder loads lazily on the first search (or the first sweep). If loading fails — native binding missing, no network for the first download, model files corrupt — it logs once at `warn`, marks itself unavailable, and `searchThreads` runs lexical-only: the FTS ranking is already a complete answer. Loading is retried on the next sweep. The search request path never awaits a model load: a query arriving while the model is loading is answered lexically.

## Ranking and result shape

### Lexical query recipe

The query builder in `ThreadSearch.loom.ts`: lowercase, split on non-alphanumerics, drop a two-dozen-word English stopword list (unless that empties the query), quote each term, and give the **last** term a prefix `*` so results move while Carl is still typing. One `MATCH` per term (typically 2–5, each 4–8 ms) gives per-document **term coverage**, which pure OR-bm25 cannot express and which turned out to be the decisive lexical signal.

<Code
  filename="ThreadSearch.loom.ts — lexical ranking query (one root per row)"
  language="sql"

**Lexical rule, in words:** a root's score is its single best document; a document is better if it contains more of the query's terms, then by kind-weighted bm25 (bm25 is negative, lower is better); ties by the root's recency. Best-document rather than sum-of-documents is deliberate: sum makes 200-child orchestrator roots win every query ("Cadence pull 7" topped six of eight sums). End-to-end on the snapshot: 40–60 ms for a four-term query including root attribution, before snippets, on the worker lane.

### Fusion

`searchThreads` runs both sides concurrently: the lexical query on the read lane (top-50 roots) and, if the embedder is available, the 9 ms query embed plus a dot product against the in-memory matrix (top-50 roots, archived included). Reciprocal rank fusion with k = 60 — `score(root) = Σ 1 / (60 + rank_in_list)` over the lists it appears in — orders the union; ties by recency; the first `limit` roots are returned. RRF needs no score calibration between bm25 and cosine, which is why pi-session-search uses it too. Measured on the acceptance set with the real FTS and bge-small lists:

## Risks

- **Heavy native dependency.** `onnxruntime-node` is 536 MB on disk (327 MB of it a CUDA provider that is never loaded) in a 3.4 GB release `node_modules`; `sharp` comes along as a transitive dependency of transformers. Mitigation: externalised like `node-pty`; trimming the CUDA `.so` is a later nicety. The Windows desktop sidecar derives its runtime roots from the same externals list and would ship it too — loom does not build that artifact today.
- **First-run network.** The 34 MB model downloads from huggingface.co once into `<stateDir>/models/`. If the production VM cannot reach it, search runs lexical-only and logs why; the files can be copied in by hand. Vendoring the model into the release is the fallback if egress turns out to be blocked.
- **Rowid renumbering.** A future migration that rebuilds a source table by copy-and-rename invalidates the derived rowids. Mitigation: the rebuild migration re-runs the exported backfill (`delete-all` then the eight inserts); `threadSearchIndex.loom.ts` says so at the top.
- **Column drops.** `ALTER TABLE … DROP COLUMN` fails on a column a trigger references (loom's own `1041` dropped columns on `projection_thread_messages`). Mitigation: the exported `dropTriggers`/`createTriggers` pair brackets any such migration.
- **Upstream drift on `searchThreads`.** Upstream may change the contract or ship its own FTS. The `// loom:` hunks are small and the harness is the regression check at the next pull.
- **Staleness window on the semantic side.** A root is embedded within ~2 minutes of changing, not instantly; a brand-new root is lexically searchable immediately (triggers) and semantically after the next sweep.
- **bm25 per-term arms cost O(hits).** Five common terms ≈ 40 ms plus attribution; if it grows, cap the arms at the six rarest terms.
