# Review what the agents changed, from the file tree, since your last message

**Recommendation: snapshot the whole worktree every time a human message lands on a thread, and let that snapshot drive three things you already use.** The Files tree marks every file that differs from the snapshot (folders inherit the mark, and a filter shows only changed files), opening a marked file shows the whole file side by side with the changes highlighted, and the Diff panel's scope menu gains "Since your message" with a list of earlier messages that changed something. The snapshot is taken per source: the worktree's own repo, any git repository nested inside it (fathom's `workbench/`), and declared artefact folders (loom's `.artifacts/`), so the work that today reads "No net changes" is visible, behind a toggle between repo code and everything. The branch comparison you have today stays as the second baseline.

The one bet is to **capture at the message rather than derive from the children's turn checkpoints**: three quarters of child runs overlap a sibling in the same worktree, so no per-thread checkpoint can say what changed after you spoke, while a worktree snapshot is exact whoever edited. The price is about **half a second of background git work per human message** (about 60 a day across every thread on this machine) and one hidden git ref per message per source, about 120 a day across the machine, swept away 14 days after a thread goes quiet (so the steady state is a couple of thousand refs, against the 14,600 this worktree carries today) and capped per thread. The whole-file view needs **no new renderer**: the diff library already installed shows a 10,000-line file side by side with the code visible in 0.2 s.

**Scope.** Web client and server, for the thread you are talking to and its worktree. Done means: a human message on any thread snapshots every source within a second; the Files tree and the Diff panel both show what differs from the chosen baseline; a changed file opens whole, side by side, in under a second for ordinary files; nested-repo and artefact edits appear when "everything" is on; the selector lists only messages after which something changed. Deferred to a fourth, optional PR: changed-file marks and counts on mobile. Not in scope: editing inside the side-by-side view (the Edit toggle returns to today's editor), attribution of a change to a thread (decision 3 may ask for it as a follow-up), and the retention sweep for the 11,000 legacy checkpoint refs this worktree already carries (an earlier, unshipped plan owns that).

## 1. What you will see

**The Files tree.** A baseline chip at the top of the explorer names what the marks are measured from: "Since your message · 14:02" by default when the thread has one, otherwise the branch comparison. A changed file is coloured and lettered (M modified, A added, D deleted, R renamed), its folders take the colour and a count, and "Changed only" collapses the tree to the marked files. The "Everything" chip is the sources toggle: "Repo code" marks only files the worktree's own git tracks or would track; "Everything" adds nested repositories and declared artefact folders, each marked the same way.

**The opened file.** Opening a marked file shows the whole file, old on the left and new on the right, changes highlighted and every unchanged line present, so the enclosing function is on screen. The header carries the same baseline chip, a split or unified toggle, and Edit, which switches back to today's editor on the current contents. A file above about 5,000 lines opens in hunk mode with expand buttons instead, with "Show whole file" one click away.

**"Since your message", in practice.** The span runs from the moment a message you wrote was accepted on this thread to now, whoever edited the worktree in between: the thread's own agent, its coder children in their own turns, or you in an editor. Stepping back shows the span between two earlier messages of yours. A message after which nothing changed is not offered in "Earlier"; "Since your message" itself is offered as soon as the thread has a snapshot, even before anything has changed, because it is the live view and reads "No changes yet" rather than vanishing. The live view refreshes on opening, on an explicit refresh, and whenever **any** thread sharing the worktree finishes a run (the orchestrator or one of its coders), at 0.3 to 0.5 s of git work per enabled source, coalesced on the server so two clients or two quick refreshes share one capture.

## 2. Capturing the baseline at the human message

<Callout tone="decision" title="Decision: a new whole-worktree snapshot per human message, per source">
  The existing start-of-run baseline refs stay as they are. Loom already snapshots the worktree at the start of every workstream turn (the `refs/t3/loom-baseline/…` refs, written in `apps/server/src/orchestration-v2/CheckpointService.ts:177-190` and `:293-306`). Those refs were considered as the baseline and rejected: they are keyed to a run, not a message, and they cover only the outer repo. They keep their current job, making a thread's turn diff honest in a shared checkout, and are not extended.
</Callout>

<Columns>
  <Column label="Why the run-start refs cannot be the baseline">
    A **steered** message (you type while the agent is mid-turn) starts no run, so it gets no baseline at all (`Orchestrator.ts` dispatch modes at `:4864` and `:4977`). A **queued** message gets its baseline when its run eventually starts, after sibling threads have kept editing, so the interval begins late. On the failing workstream, every one of the 16 start-of-run refs holds the identical tree because all the work happened in the gitignored `workbench/` repo. Extending them to nested repos would still leave the message-versus-run mismatch.
  </Column>
  <Column label="Why not the children's turn diffs">
    In the last 30 days, 795 of 1,057 child runs (75%) overlapped a sibling run in the same workstream, so each child's turn diff contains the siblings' edits as well, and nothing can split a run that crosses a message boundary. The failing workstream's 25 child checkpoints all record zero files. A derived view over them would be inexact in exactly the delegated case this work exists for.
  </Column>
</Columns>

**Mechanism.** Loom's dispatch hunk already stamps every message with the one human predicate (`isHumanAuthored`, `apps/server/src/orchestration-v2/Orchestrator.loom.ts:195-200`: created by the user, not a usage-limit continuation, not a scheduled task), computed in `Orchestrator.ts:4731-4738` before the delivery mode is chosen, so it covers new-run, queued and steered messages alike. The event sink then emits `message.updated` with that flag on the payload. A new **review-snapshot reactor** subscribes to the orchestrator's domain-event stream exactly as the emergent-goal reactor does (`apps/server/src/loom/orchestration/EmergentGoalReactor.ts:205-230`), and on the first `message.updated` for a human-authored user message it resolves the thread's worktree (`thread.worktreePath`, else the project's workspace root, as `loom/prompt/sessionComposerLive.ts:215-219` does), enumerates the sources (section 3) and captures each one. The same event is re-emitted for a message later (a queued edit, a promotion to steer), so the reactor ignores a message whose `createdAt` is more than a few seconds old: a capture that was lost is never taken late, because a late one would record the agent's progress as the baseline.

**The race with the first edit.** The reactor runs off the in-process stream published after the event commits, so the capture starts within milliseconds. The thread's own run must first take its start-of-run checkpoint under `CheckpointService`'s lock, start the provider and wait for the model's first tool call, which is seconds; the repo snapshot (0.3 to 0.5 s) wins in practice. Sources are captured repo first, then the others, so a cold first build of an artefact index (up to 9 s) cannot push the repo snapshot past that first edit. An edit by an already-running sibling in that half-second lands in the adjacent interval, which the rejected outbox design would not have prevented either (it orders only against the thread's own run).

<Columns>
  <Column label="Reactor on the event stream (chosen)">
    No change to upstream's effect-outbox schema or worker (`EffectOutbox.ts`, `EffectWorker.ts` stay untouched); the same shape loom already uses for emergent goals. A capture lost to a server restart in the sub-second between the message committing and the snapshot landing simply leaves that message without a boundary, so its interval merges into the previous one; the union of intervals stays exact. Restarts are deploys, so this is rare and bounded.
  </Column>
  <Column label="A new outbox effect kind (rejected)">
    At-least-once after a restart and ordered ahead of the run start on the thread's lane, at the cost of three marked hunks in upstream files that both open upstream PRs on this area would churn, and a late capture after a restart is wrong anyway (it would record the agent's progress as the baseline), so the guarantee buys a row that must then be discarded.
  </Column>

**Capture per source** reuses the isolated checkpoint primitive unchanged (`apps/server/src/vcs/GitVcsDriver.ts:886-1162`: a throwaway index copied from the real one, `add -A`, `write-tree`, `commit-tree -p HEAD`, `update-ref`), so it never touches the real index, `index.lock` or any branch, and `docs/architecture/checkpoint-git-isolation.md` continues to hold. The repo source calls it with the worktree as cwd. A nested repo calls it with the nested root as cwd, which needs nothing extra, so the ref and objects go into the nested repo's own store (150 ms on `workbench/`, 13.9k files; snapshotting the nested content into the outer store was measured at 39.8 s and 249 MB and rejected). An artefact folder is ignored by git, so it gets its own path: `git add -f -A -- <folder>` into a **persistent** per-source index at `git rev-parse --git-path loom-review-<source>.index` (worktree-private), then `write-tree`, `commit-tree`, `update-ref`; on `.artifacts/` (5,249 files, 119 MB) that is 1.8 s the first time and 21 ms after, against 1 to 9 s per capture with a throwaway index. Files over 5 MB in an artefact folder are skipped and recorded.

**Cost, measured.** 261 to 484 ms per capture on this worktree (29k tracked files), 370 to 630 ms on a fathom worktree; production checkpoint spans run at p50 443 ms and p90 918 ms. Human messages ran at 1,770 in the last 30 days machine-wide, about 60 a day, so the total is under a minute of git a day. The reactor forks each capture and serialises captures per worktree with its own keyed lock; a concurrent start-of-run baseline from `CheckpointService` is harmless because every capture uses a private index.

- **A message while a file is half-written** captures the disk as it is; the torn edit shows split across two adjacent intervals and the union is exact.

## 3. Sources and the toggle

**Enumeration asks git, never the disk.** Candidates for nested repositories come from the worktree's own listing of collapsed untracked and ignored directories at the root (`git ls-files --others --exclude-standard --directory` with and without `--ignored`; 40 to 80 ms, 30 to 50 entries on loom and fathom; it finds `workbench/`), plus any gitlinks in the index. Known heavy names (`node_modules`, `.venv`, `__pycache__`, `.t3`, `.git`) are skipped before the stat, then `<dir>/.git` is stat'd once per candidate (a `.git` file counts, which is what `workbench/` uses). Git never descends into an ignored tree, so the walk is bounded by the repo's own ignore rules; nothing walks upward and nothing crosses the worktree boundary. A repo nested inside an ignored directory (`foo/bar/.git` when `foo/` is ignored) is not found this way; the declared list covers it. Artefact folders are **declared only**, because ignored directories also hold `logs/`, `__pycache__` and `.env`.

<Callout tone="info" title="Carl's constraint, honoured">
  "We don't want to be running diff git's across the entire hard drive, or some top-level root folder that consume enormous resources." Every source is the worktree repo, a nested repo found by git's own bounded listing at the root, or a declared path; every source root must resolve (through symlinks) inside the worktree, and the existing foreign-home guard extends to source paths. Per message, the total git work is 0.3 to 0.6 s per source, in the background.
</Callout>

**The declared list** lives beside loom's other per-project configuration, as `.t3code/review.json`, read from the worktree root only (not the nearest-ancestor walk `.t3code/vcs.json` and `.t3code/roles/` use, since nothing in this feature looks above the worktree). Paths are relative to the worktree root. When the file is absent, `.artifacts/` is a built-in default if it exists. ## 5. The Diff panel and the selector

**One selection, two stores.** Upstream's `diffPanelStore` keeps its own kinds (`branch`, `unstaged`, `turn`). ## 9. Verification across the whole

Beyond each PR's checks above: `vp check` and `vp run typecheck` pass before any PR is called done; `unmarkedsweep.sh` at ship time confirms every hunk in an upstream file carries `// loom:`; and one end-to-end pass on the fathom shape, which is the case that started this: a thread whose coder commits into `workbench/` (nested, gitignored) must show that file under "Since your message" with "Everything" on, and show "No net changes" with "Repo code" on, while the sidebar's +/- count stays what it is today.
