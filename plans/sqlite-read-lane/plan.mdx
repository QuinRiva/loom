# SQLite read lane: make the lane a type, and take ingestion's read off it

**Objective.** Loom's server has two SQLite connections: an in-process writer (the default `SqlClient`) and a worker-thread reader (`SqlReadClient`, `PRAGMA query_only`). Two defects share one cause: (1) which repositories actually run on the reader is decided by Effect layer-memoisation order, not by the code — WS reconnect replay has *never* run on the reader, and the usage-ledger write path silently ran on the read-only connection for days; (2) provider-runtime ingestion spends 89% of its processing time waiting for the reader's single permit, almost entirely behind whole-set shell-snapshot transactions fired by background sweeps. **Done means:** every reader-routed service is a distinct layer whose requirement channel names `SqlReadClient`, `SqlReadClientAsSqlClient` and the `Layer.fresh` workaround are deleted, ingestion's per-event read runs on the in-process client, one test pins the lanes, and `vp check` + `vp run typecheck` pass. This is a personal cockpit, not a fleet: the fix is small, verification is one test plus reading a journal line the day after deploy, and everything else is a follow-up with a stated trigger.

<Callout tone="decision">
The worker read lane exists for one thing — keeping *expensive* reads (whole-set snapshots, thread histories, aggregates) off the event loop and off the writer — and it is expressed as a type: reader services are built from the repositories' exported constructors with `SqlClient` substituted *inside* the constructor, never by re-providing the shared tag. Everything else — replay, thread resume, and ingestion's per-event thread lookup — runs on the in-process default `SqlClient`, exactly as upstream does; the measurement says taking that one read off the lane removes 93–98% of ingestion's read wait, with zero new connections. Sweeps, caches, pools and worker changes are not in scope; each is listed at the end with the journal signal that would justify it.
</Callout>

Evidence base: the wiring audit and the workload measurement (two research reports, both read in full; numbers used, not re-derived), plus a design review whose corrections are folded in. Human decisions already taken: ingestion's read goes on the writer's existing connection first; `getThreadShellById` stays on the worker; the snapshot memo is deferred; there is no pre-merge load harness.

The memoisation facts behind the fix (Effect 4.0.0-rc.115, `.repos/effect-smol/packages/effect/src/Layer.ts`): the memo key is the layer *object* (`fromBuildMemo`, 380-388); `Layer.effect` memoises, `provide`/`mergeAll`/`fresh` do not; `Layer.provide(X, dep)` re-runs `X.build` with the same memo map, so it changes the environment *offered*, not the *key*; `Layer.fresh` starts a new root map inside which memoisation still applies and is itself unmemoised (hence the ledger's duplicate instance). The one shape proven collision-proof on a booted server is a **distinct `Layer.effect` whose constructor substitutes `SqlClient` via `Effect.provideServiceEffect(SqlClient.SqlClient, SqlReadClient)`**.

## The rule a maintainer applies when adding a read

<Callout tone="decision">
**Ordinary repositories** — the event store, receipts, projection repositories, auth sessions, the ledger's write side — stay on the default in-process `SqlClient`, exactly as upstream ships them. **Every `ProjectionSnapshotQuery` method runs on the worker read lane by default**, including the ones that look small: they are the reads whose cost grows with the data, and the lane reaches them by being built in `apps/server/src/persistence/Layers/SqliteLanes.ts` from the exported constructor with `SqlClient` substituted *inside* the constructor. A snapshot-query method moves to the in-process instance only by being named in `POINT_READS` in `SqliteLanes.ts`, and only when it is a measured hot-path read whose cost does not grow with a thread's history — an in-process read runs synchronously on the event loop, and one returned row does not bound a query. Never re-provide the shared `SqlClient` tag to a layer, and never `Layer.fresh` a repository: both put the lane at the mercy of build order.
</Callout>

**Lane as a type.** `ProjectionSnapshotQuery` keeps its shared tag (dozens of upstream consumers; one instance in the server) and is built in `SqliteLanes.ts` from `makeProjectionSnapshotQuery` on `SqlReadClient`; its layer object is then distinct from upstream's `OrchestrationProjectionSnapshotQueryLive`, and `server.ts` already substitutes loom's composition with one marked line. The usage ledger gets a distinct tag `ProjectionUsageLedgerReader` for the Usage page's aggregate read; ingestion keeps `Layer.provide(ProjectionUsageLedgerRepositoryLive)` for writes — a different layer object, so no collision and no `Layer.fresh`. **Replay and thread resume are not routed** (supersedes D2 item 2 of the July 6 plan): replay never ran on the reader, the benefit is ~4 ms per 1,000 events, and every extra reader-routed service is another layer to keep collision-proof. The replay wrapper and its engine re-composition are deleted; the engine is composed exactly as upstream's `runtimeLayer.ts` does it.

**Ingestion's point read.** `getThreadRuntimeContext` — one primary-key join, 11 calls/s — runs on the in-process default `SqlClient`, the writer's own connection. Its plain-statement acquirer releases the permit before the synchronous execution, so the read waits only while a write transaction is open (0.9% duty; p95 20 ms, max 274 ms) and can never interleave with one. Zero new connections; upstream's own model. `getThreadShellById` (the WS fan-out, 1.6 calls per event) is *not* moved: it also fetches PR links and aggregates a thread's consult and peer-message history, so its cost grows with thread age and the 0.41 ms benchmark figure came from a cheap thread.

**Rejected, with the reason.** *Worker pool:* scaling plateaus at ~1.5x because the main thread saturates; taking the hot read off the lane beats it at a fraction of the machinery. *Keyed ingestion worker* (`plans/ingestion-backpressure/plan.md` §3.2): the serial fibre was waiting, not computing; after this change the per-event read is ~0.1 ms and the fibre's time is the engine's serial dispatch, which per-thread concurrency cannot overlap. *Writer back on a worker:* p50 2 ms / 0.9% duty; an IPC hop on each of the 10–20 statements per command would roughly double command latency to move under 1% of main-thread time off the loop, and would put the point read back over IPC — the writer stays in-process, as a decision this time rather than the accident of `94a5029ff1`. *Replay on the reader:* above. *Snapshot memo / FIFO semaphore / dedicated read connection:* follow-ups below.

**Prior decisions.** `docs/plans/db-lane-reader-writer-split.md` (July 6): D1, D3 and D2 item 1 are honoured and are what makes the point-read-on-the-writer safe; D2 item 2 (replay on the reader) and the `Layer.fresh` ledger routing are superseded — the change adds one superseding paragraph under D2 of that doc, not a second account. Its author could not be consulted (`consult_manager` fails on an Anthropic OAuth `invalid_grant` on this box). `plans/sqlite-worker-offload/plan.mdx` (July 3): its liveness goal is met by the reader lane for the reads that matter; its mechanism no longer applies to the writer.

**The one test.** `SqliteLanes.test.ts` today names "reader-routed snapshots and replay" and passes regardless of lane; the audit showed replay was on the writer the whole time. Its replacement asserts the lane through the real services: build `OrchestrationLayerOnSqlReadClient` plus `LoomPersistenceLive` on a temp database (as the existing tests do), then assert that a `PRAGMA query_only` run through the connection the **ledger reader** uses returns `1` and through the connection the **ledger writer** (`ProjectionUsageLedgerRepositoryLive`) uses returns `0` — the ledger is the one repository that exists in both variants, so it is where a collision would show. The simplest way to reach each service's connection is a loom-only `laneOf` helper on the two ledger constructors that runs the pragma through their captured `sql` (a few lines in the loom-only ledger file); a write through the writer succeeding and the same write through the reader failing with `SQLITE_READONLY` is an acceptable substitute if the helper is unwelcome. Mutation check while writing it: replace `onReadLane` with a shared-tag re-provide and the test must fail.

**Verification.** `vp check`, `vp run typecheck`, the lane test, and `unmarkedsweep.sh` clean. Then ship. **The day after deploy** (deploy is the human's separate act), read the `provider runtime ingestion interval` journal line: `sqlReadWaitMs` as a share of `processingTotalMs` should have fallen from ~89% to near zero (the point read is no longer charged to it), and `lagP95Ms` should sit in the low seconds in steady state rather than the ~60 s seen in the PR #274 burst. If `attempt to write a readonly database` appears in the journal, the ledger writer is on the wrong lane — the test should have caught it; roll back.

## Follow-ups, and what would trigger them

None of these is in scope. Each is one sentence of design and the journal signal that would justify doing it.

- **Dedicated in-process `query_only` connection for the point read** (~20 loom-only lines): if `lagP95Ms` is still material after deploy and `processingP95Ms` tracks the writer's transaction duration on the `orchestration command queue interval` line — the read is waiting on write transactions.
- **Sweeps on the lean snapshot** (add PR rows to `getLeanShellSnapshot`; switch `ThreadPullRequestReactor`, `ThreadSettlementReactor`, `PullRequestSyncReactor` to it; narrow the `OrchestrationThreadShell` parameter types in `PullRequestSyncReactor.ts` and `ThreadSettlementPolicy.ts` to the fields they read; ~8 hotspot lines plus marked one-liners) and **dropping the redundant whole-snapshot decode** (the transaction closes before it, so this cuts main-thread CPU, not hold time): if read-lane snapshot holds still dominate lane busy in the trace and WS connect / sidebar snapshots feel slow.
- **`getThreadShellById` in-process, or a per-subscriber dedup in `ws.ts`**: if the journal or trace shows the WS fan-out (1.6 calls per engine event) as a material share of ingestion's remaining wait; move it only after measuring old orchestrator threads with hundreds of consults and peer messages.
- **Sequence-validated single-flight memo of the lean snapshot** (serve a cached snapshot only when the projection head equals its `snapshotSequence`; re-apply the in-memory liveness/plan-progress fields; never time-based — a sweep pass clears its trigger flag at start, so a stale snapshot is the wedge class the coalescing workers exist to avoid): after the lean-sweeps change, if snapshot CPU on the main thread is still the dominant lag term. 58% of snapshot reads cluster within 1 s, but the head advances ~11/s, so the hit rate is unknown.
- **Sweeps reading the engine's committed in-memory read model, no SQL**: the true end state for control-plane reads, medium-large (the in-memory `OrchestrationThread` lacks the denormalised shell columns), if snapshots remain the cost after everything above.
- **The residual**: the engine's pre-decision lookups (`getPendingTurnStartThreadIds` on `requireIdle` wakes, `getUserInputActivity` on user-input responses) stay on the worker lane and can hold the serial engine behind a snapshot; if `engineDispatchWaitMs` on the ingestion line or `queueWaitP95Ms` on the engine line grows, move per-row decode outside the held transaction before reaching for a FIFO semaphore.
- **Writer back on a worker**: only if `eventLoopDelayP99Ms` on the `performance interval` line is attributable to writer transactions over 100 ms (bulk deletes, migrations).
- **Read-worker `cache_size`** (2 MB vs the writer's 128 MB): measured effect small; a one-line pragma if ever wanted.
