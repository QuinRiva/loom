# SQLite read lane: make the lane a type, and take the hot path off it

**Objective.** Loom's server has two SQLite connections: an in-process writer (the default `SqlClient`) and a worker-thread reader (`SqlReadClient`, `PRAGMA query_only`). Two defects share one cause and must be fixed as one design: (1) which repositories actually run on the reader is decided by Effect layer-memoisation order, not by the code — WS reconnect replay has *never* run on the reader, and the usage-ledger write path silently ran on the read-only connection for days; (2) provider-runtime ingestion spends 89% of its processing time waiting for the reader's single permit, almost entirely behind whole-set shell-snapshot transactions fired by background sweeps. **Done means:** every reader-routed service is a distinct layer whose requirement channel names `SqlReadClient` (so a build-order change cannot move it), `SqlReadClientAsSqlClient` and the `Layer.fresh` workaround are deleted, ingestion's per-event read no longer queues on the worker lane, the background sweeps stop reading the full UI shell, and the telemetry acceptance in [Verification](#verification) is met on a production-sized copy before merge.

<Callout tone="decision">
**The decision in three sentences.** The worker read lane exists for one thing — keeping *unbounded-size* reads (snapshots, thread detail, activity pages) off the event loop and off the writer — and it is expressed as a type: reader services are built from the repositories' exported constructors with `SqlClient` substituted *inside* the constructor, never by re-providing the shared tag. Everything else — replay, thread resume, and ingestion's per-event thread lookup (plus the WS fan-out shell lookup if it passes a worst-case measurement gate) — runs on the in-process default `SqlClient`, exactly as upstream does; the measurement says taking that read off the lane removes 93–98% of ingestion's read wait, and doing it on the writer's existing connection rather than a new one is the hypothesis the verification tests first. The remaining lane load is the sweeps' snapshot reads; this plan moves the four full-shell sweeps to the lean snapshot and removes a redundant whole-snapshot decode, and records the larger demand-side redesign (sweeps reading the engine's committed in-memory model) as the follow-up with its honest size.
</Callout>

This plan builds on two research reports finished this morning (the wiring audit and the workload measurement); their numbers are used, not re-derived. Where a number below is new it is marked as such. Note for the reader: the measurer's scratch worktree (benchmark sources, replay harness, WAL-mode copy) was removed by worktree cleanup before this plan was finished; only the clustering figure in [What the sweeps actually need](#what-the-sweeps-actually-need) was extracted from it beforehand.

The audit's memoisation findings that shape the fix (Effect 4.0.0-rc.115, `.repos/effect-smol/packages/effect/src/Layer.ts`): the memo key is the layer *object* (`fromBuildMemo`, 380-388); `Layer.effect` memoises, `provide`/`mergeAll`/`fresh` do not (1029-1075, 1251, 1330-1350, 2164); `Layer.provide(X, dep)` re-runs `X.build` with the same memo map, so it changes the environment *offered*, not the *key*; and `Layer.fresh` starts a new root map inside which memoisation still applies (so two copies inside one `fresh` still collide) and is itself unmemoised (so each reference builds another copy — the ledger's duplicate instance). ## The rule a maintainer applies when adding a read

<Callout tone="decision">
**Ordinary repositories** — the event store, receipts, the projection repositories the pipeline writes through, auth sessions, the ledger's write side — stay on the default in-process `SqlClient`, exactly as upstream ships them. **Every `ProjectionSnapshotQuery` method runs on the worker read lane by default**, including the ones that look small: they are the reads whose cost grows with the data (whole-set snapshots, thread histories, window aggregates, searches), and the lane reaches them by being built in `apps/server/src/persistence/Layers/SqliteLanes.ts` from the exported constructor with `SqlClient` substituted *inside* the constructor. A snapshot-query method moves to the in-process instance only by being named in `POINT_READS` in `SqliteLanes.ts`, and only after its cost has been **measured on representative worst-case rows** (a long-lived orchestrator thread with hundreds of consults and peer messages, not a fresh one) and approved for synchronous execution on the event loop. One returned row does not bound query work or payload: a scan, an aggregate, or a growing history needs that scrutiny regardless of how many rows come back. Never re-provide the shared `SqlClient` tag to a layer, and never `Layer.fresh` a repository: both put the lane at the mercy of build order.
</Callout>

## Design

### Lane as a type

Reader-routed services become distinct memoised leaves whose requirement channel names `SqlReadClient`. The audit tested this shape live (replay moved to the reader, appends stayed on the writer, even with the flip probe present). What is routed, and how:

- **`ProjectionSnapshotQuery`** — the only service that must be on the reader. There is exactly one instance in the server, so it keeps its shared tag (dozens of upstream consumers) and is built in `SqliteLanes.ts` as `Layer.effect(ProjectionSnapshotQuery, makeProjectionSnapshotQuery.pipe(Effect.provideServiceEffect(SqlClient.SqlClient, SqlReadClient)))`. Its layer object is then distinct from upstream's `OrchestrationProjectionSnapshotQueryLive`, so no memo collision is possible; `server.ts` already substitutes loom's orchestration composition for upstream's with one marked line. Cost in the upstream hotspot `ProjectionSnapshotQuery.ts`: **one** `// loom:` `export` keyword on `makeProjectionSnapshotQuery`.
- **Usage ledger** — ingestion writes through `ProjectionUsageLedgerRepository` (writer); the Usage page's `topSpendingThreads` aggregate reads through a new distinct tag `ProjectionUsageLedgerReader` built from the exported `makeProjectionUsageLedgerRepository` on `SqlReadClient`. Both ledger files are loom-only; the consumer switch is inside the existing `// loom:` hunk in `ws.ts` plus `loom/wsMethods.ts`. This deletes the `Layer.fresh` workaround and the duplicate read-lane instance it creates.
- **Event replay and thread resume — not routed** (supersedes D2 item 2 of the July 6 plan). Replay never ran on the reader; the measured benefit of routing it is ~4 ms per 1,000 events (the other 34 ms is Schema decode on the main thread on either lane); the writer is busy 0.9% and in-process, so a page of 500 events cannot interleave with a write transaction; and every extra reader-routed service is another layer that must be kept collision-proof. `OrchestrationEngineReaderReplay`, `routeEngineReplayToSqlReadClient` and `OrchestrationEventStoreOnSqlReadClient` are deleted, and `OrchestrationEventStore.ts` needs no export. Consistency is unchanged: a client's shell snapshot is a WAL-consistent view at sequence S from the reader; replay from S+1 on the writer sees every commit — the same pairing the server has always actually run.
- **Deleted:** `SqlReadClientAsSqlClient`, every `.pipe(Layer.provide(SqlReadClientAsSqlClient))`, `ProjectionUsageLedgerOnSqlReadClient` and its `Layer.fresh`, the replay wrapper and its engine re-composition. `SqliteLanes.ts` goes from 102 lines to roughly 45.

**The tests that would have caught the replay no-op.** `SqliteLanes.test.ts` today names "reader-routed snapshots and replay" and passes regardless of lane. It is replaced by lane assertions that need no probe hook, built on one trick: the writer opens one file and `SqlReadClient` opens a **`VACUUM INTO` copy** of it, so the two lanes are *different databases* and any read reveals which one it hit. Two details make this discriminate, both checked in source: `getSnapshotSequence()` reads `projection_state`, not the event-store head, and projection cursors advance only through the projection pipeline inside a *completed dispatch* — a raw `OrchestrationEventStore.append` leaves both databases' projection sequence identical. So the recipe is: seed projected state through the engine (`dispatch` a project-create and a thread-create and await their receipts), take the copy, point the reader at it, then complete **one more writer-side dispatch** and assert that (a) `ProjectionSnapshotQuery.getSnapshotSequence()` returns the copy's sequence, strictly below the writer's (read `projection_state` directly through `SqlClient` for the comparison), and (b) after slice 2, `getThreadRuntimeContext` for the newly created thread returns the row while `getThreadShellById`-class reads still on the worker do not see it. The **collision case** is the ledger, which is the one repository that genuinely exists in both variants: build `ProjectionUsageLedgerRepositoryLive` (default client) and `ProjectionUsageLedgerReaderLive` (reader) in **both dependency orders** — reader-first and writer-first, using `Layer.effectDiscard` consumers to force the order — behind separate consumer handles (`LedgerWriter` and `ProjectionUsageLedgerReader`), and in each order assert that `insert` succeeds *and* that `topSpendingThreads` on the reader does **not** return the row (it is reading the stale copy). The **ordering perturbation** for the snapshot query builds an extra `ProjectionSnapshotQuery` consumer before the engine and after it, and in both orders asserts `dispatch` succeeds and `getSnapshotSequence()` still returns the copy's sequence — the reader result is asserted, not only the successful write. **Mutation check:** with `onReadLane` replaced by a shared-tag re-provide (`Layer.provide(Layer.effect(SqlClient.SqlClient, SqlReadClient))`), at least one dependency order must fail; if both still pass the test is not discriminating. `SqliteRead.ts` exports its `layer(config)` (loom-only file) so a test can point the reader at a chosen file.

**Which in-process connection for point reads.** The writer's own `SqlClient` (the in-process `@t3tools/shared/nodeSqliteClient`), not a third dedicated read connection. Its plain-statement acquirer releases the permit before the synchronous execution, so a point read waits only while a write transaction is open (0.9% duty; p95 20 ms, max 274 ms) and can never interleave with one. **This is a hypothesis, not the measured result**: the −98% figure was measured on a *dedicated* in-process connection that never waits on writes (max 2.0 ms). The shared writer is expected to land close to that at today's write duty, and it is zero new machinery and exactly upstream's model, so it goes first; the harness in [Verification](#verification) measures it directly, and the dedicated `query_only` connection (about 20 loom-only lines, one more file handle and prepare cache) is the measured fallback if point-read wait tracks write-transaction duration.

**The residual on the worker lane.** After the point reads move, the lane still serves the serial engine's own pre-decision lookups — `getPendingTurnStartThreadIds` on every `requireIdle` turn start (which is how dispatcher and fan-in wakes arrive) and `getUserInputActivity` on user-input responses and dismissals — plus WS connect snapshots and the sweeps. A pre-decision lookup that queues behind a 250–900 ms snapshot transaction holds the engine's single worker fibre for that long, and every later command, including ingestion's dispatches, waits behind it. The lane's low utilisation makes this rare, not impossible, and the non-FIFO semaphore means it is not bounded by one snapshot. This plan records it rather than widening the allowlist or adding a fair semaphore without evidence; the verification exercises an automatic idle-gated wake and a user-input response during snapshot pressure and reads `engineDispatchWaitMs` and the engine's own `orchestration command queue interval` line, not only ingestion's SQL wait.

**Telemetry consequence.** `sqlReadWaitMs` on the `provider runtime ingestion interval` line is charged by the worker client's permit wrapper only; the in-process shared client (an upstream package file) has no hook and must not get one. After the point reads move, ingestion's read time lands in `remainderMs` by construction, and `sqlReadWaitMs` will read near zero. `remainderMs` is an interval **total** (processing total minus the two instrumented waits) with no percentile, and it includes uninstrumented waits and scheduling delay, so it is read as `remainderMs / processed` (mean per event) alongside `processingP50/P95Ms`; attribution of what is inside it comes from the harness and trace spans, not from that line. Acceptance uses `lagP95Ms`, `processingP95Ms`, `remainderMs / processed` and `engineDispatchWaitMs` — see [Verification](#verification).

### What the sweeps actually need

Ten call sites in background sweeps read a shell snapshot with no arguments every few seconds. The seven already on `getLeanShellSnapshot` (`WorkstreamDispatcher.runPass`, `WorktreeReaper`, `WorkstreamFanInReactor`, `HandoffDrafterReactor`, `WorkstreamLivenessSweep`, `ExhaustionResumeSweep`, `WorkstreamWorktreeStatus`) document in code why they need the **whole active set, not a subset**: the dispatcher reads the graph (dependencies, gate siblings, parents, fork sources) and a graph read over a filtered map misreads absence as satisfaction; the fan-in reactor's `hasDependentResident` and `isMemberOfUnresolvedGate` scan all threads and interpret absence as "no such thread". Both are documented silent-wedge classes from past incidents. So the targeted-query replacement for those callers is not "fewer rows" — it is either a cheaper full-set read (levers 3 and 4) or an in-memory source (lever 5). Their cost is row width, and the lean snapshot already trimmed that.

The three upstream sweeps still on the full `getShellSnapshot` — `ThreadPullRequestReactor.synchronize`, `ThreadSettlementReactor.sweep` and `settleFinishedRoots`, `PullRequestSyncReactor.sweep` — read only `projects`, `snapshotSequence`, and per thread `branch`, `pullRequests`, `linkedPullRequest`, `branchPullRequest` plus the lean fields (verified by grep of each file). None reads `brief`, `lastActivityPreview`, `consults`, `peerMessages` or `goals`. The lean snapshot's *type* already keeps `pullRequests`/`linkedPullRequest`; its *query* just does not fetch the PR rows. Adding `listActiveThreadPullRequestRows` to the lean transaction (a small, indexed table) and passing `pullRequests` and `repositoryIdentity` into `mapLeanThreadShellRow` (the shell path already does both) makes the lean snapshot sufficient for every sweep. A per-sweep targeted query (e.g. only threads with a PR link for `PullRequestSyncReactor`) would be about 30 lines each in upstream files; it is recorded as a follow-up because after this change these sweeps cost the same as the dispatcher's, and the next real win is lever 5.

**Clustering (new number, from the measurer's trace before its worktree was removed):** of 359 snapshot transactions in the trace, 39% began within 50 ms of the previous one ending and 58% within 1 s. That is the sweeps firing on the same engine events and serialising on the permit. It is why lever 4 is attractive and why its correctness condition matters: a sweep pass clears its pending trigger flag at pass start, so a pass that is served a snapshot older than its trigger is the wedge class the coalescing workers were designed to avoid. Any memo must be validated against the projection head, never by time.

### Keyed ingestion worker

**Not warranted.** `plans/ingestion-backpressure/plan.md` §3.2 staged `makeKeyedDrainableWorker` pending the SQL-wait / dispatch-wait split, and the split says the serial fibre was waiting, not computing. After lever 1 the per-event read is ~0.1 ms in-process; at the measured 11 events/s (and at a plausible 50/s with 50 agents) one serial fibre spends its time in the engine's serial dispatch, which per-thread concurrency cannot overlap. The ordering surface it would open across ~3,000 lines of stateful ingestion code buys nothing. The prior "no" stands; re-open only if `remainderMs` per event (CPU) becomes the dominant term of `processingP95Ms` on the interval line.

### Write lane on a worker

**No — the writer stays in-process on the main thread**, and this plan records that as a deliberate decision rather than the accident of `94a5029ff1`. The July 3 offload plan's target was 10–40 s event-loop stalls from long *queries*; those are the snapshot-sized reads, which the reader lane carries. The writer's measured profile is p50 2 ms / p95 20 ms / max 274 ms per transaction at 0.9% duty. Putting it back on a worker would add a ~0.2 ms IPC round trip to every one of the 10–20 statements in a command transaction — roughly doubling p50 command latency — to move under 1% of main-thread time off the loop, and it would put the point reads this plan just moved in-process back over IPC. The in-process synchronous client also has no async-interleave hazard to guard. Revisit trigger: `performance interval` shows `eventLoopDelayP99Ms` attributable to writer `sql.transaction` spans over 100 ms at a meaningful rate (bulk deletes in `storageCleanup`, migrations, or a future write-heavy reactor).

## Verification

Two constraints, both documented in `docs/dev-site-testing.md` and checked in source, rule out the obvious recipe of "dev server on a production copy, drive 20 agents": the web dev runner opens `<home>/dev-instances/<port>/userdata/state.sqlite` (`scripts/dev-runner.ts`), so a copy at the worktree's `.t3/userdata/` is never read; and a correctly placed cockpit copy trips the foreign-home guard (`apps/server/src/workspace/foreignHomeGuard.loom.ts`), under which `ProviderService.startSession` refuses **every** provider start, so no agent workload exists on such an instance. The guard is not to be disabled, tricked with a local worktree, or sidestepped by sanitising the copy in a way that could point sweeps at live worktrees or sessions. Verification is therefore two parts, and each result section records **the opened database path, the un-archived thread count, and evidence the workload ran** (calls executed per class, events processed).

**Part A — headless workload harness on the production copy (the lane and latency numbers).** A script that builds the real server layers with no server, no reactors and no providers: `Sqlite.makeSqlitePersistenceLive` on a `VACUUM INTO` copy of `~/.t3/cockpit/userdata/state.sqlite` (placed under the worktree's gitignored `.t3/bench/`, a path no runner opens), `SqliteRead.layer` on the same file, and `OrchestrationLayerOnSqlReadClient` on top — so it exercises the actual `ProjectionSnapshotQuery` code over the actual worker and in-process clients, exactly as the measurer's lost harness did. It replays a production-shaped schedule from real thread ids in the copy: `getThreadRuntimeContext` at 11/s and at 50/s (the ~50-agent objective, sustained ≥ 10 min each); `getThreadShellById` at 2/s; `getLeanShellSnapshot` at 0.18/s and `getShellSnapshot` at 0.035/s in the sweeps' clustered pattern (fire the four lean callers on one trigger); and the engine's pre-decision lookups `getPendingTurnStartThreadIds` and `getUserInputActivity` at 1/s so their wait behind snapshots is measured too. It records per class: permit wait, wall, p50/p95/max; whole-method wall and `process.cpuUsage` for both snapshot methods; `monitorEventLoopDelay` percentiles per phase; and, for slice 2, `getThreadRuntimeContext` on the shared writer while a concurrent fibre runs write transactions at 20/s (the WAL benchmark's shape), which is the direct test of the shared-writer hypothesis. Source lives untracked at `apps/server/scratch-readlane/` while running (excluded via `.git/info/exclude`, never committed) with a copy kept under `.artifacts/readlane-bench/` and the result tables in the PR body; slice 2's coder rebuilds it from this description and the measurer's report, and slices 1 and 3 reuse it. Baseline on `main` first; every comparison is between matched phases of the same schedule, never single-run maxima.

**Part B — live-agent smoke on an isolated seeded instance (the end-to-end telemetry line).** The dev-verify recipe with `seedWorkstream.ts` state (its recorded paths are its own, so the guard stays off and providers start). Load matching PR #274's post-deploy recipe: **20 threads on the cheapest pi model, each instructed to read a ~40 KB file 8 times with the `read` tool**, started together in one project, followed by a steady low-rate tail of at least three minutes so the minute-based ingestion logger flushes the post-burst interval. ## Follow-ups

Recorded here so the scope line is explicit; none blocks the slices above.

- **Sequence-validated single-flight memo of the lean snapshot** (lever 4): serve a cached lean snapshot only when `getSnapshotSequence()` on the in-process instance equals the cached `snapshotSequence`; joiners of an in-flight computation record the head at call time and accept the result only if equal; re-apply `ThreadBackgroundLiveness`/`ThreadPlanProgress` fields on serve. Decide after slice 3 telemetry; the 58% clustering figure is the upper bound on hits.
- **Sweeps on the engine's committed in-memory read model** (lever 5): requires the denormalised shell columns in the in-memory `OrchestrationThread` and an accessor on the engine (module-level registration, as `registerEngineEventPubSubSize` does, avoids touching 15 engine fakes). Medium-large; the true end state for control-plane reads.
- **Per-sweep targeted queries** for `PullRequestSyncReactor` (threads with a PR link only) and `ThreadPullRequestReactor` (threads with a branch): ~30 lines each in upstream files.
- **`getThreadShellById` fan-out dedup** in `ws.ts` (same thread and sequence fetched once per subscriber): at 0.4 ms in-process per call this is no longer worth an upstream hunk; revisit only if the subscriber count grows past dozens.
- **Dedicated in-process `query_only` connection for point reads**: trigger is Part A showing `getThreadRuntimeContext` wait p95 tracking the writer's transaction duration under write load, or in production `remainderMs / processed` and `processingP95Ms` rising with writer duty (from the `orchestration command queue interval` line) while trace spans attribute the time to the point read. `remainderMs` has no percentile, so the trigger is never "remainderMs p95".
- **Writer back on a worker**: trigger stated in [Write lane on a worker](#write-lane-on-a-worker).
- **Read-worker `cache_size`** (2 MB default vs the writer's 128 MB): measured effect small (lean 387 → 363 ms) because the OS page cache is warm; a one-line pragma in `SqliteWorker.ts` if ever wanted.
- **FIFO/priority on the lane**: only if WS `subscribeShell` snapshot latency shows starvation behind sweeps.
- **Row decode outside the held transaction** (lever 6): only if the lane's hold time matters again.
