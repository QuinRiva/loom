# SQLite read lane: make the lane a type, and take the hot path off it

**Objective.** Loom's server has two SQLite connections: an in-process writer (the default `SqlClient`) and a worker-thread reader (`SqlReadClient`, `PRAGMA query_only`). Two defects share one cause and must be fixed as one design: (1) which repositories actually run on the reader is decided by Effect layer-memoisation order, not by the code — WS reconnect replay has *never* run on the reader, and the usage-ledger write path silently ran on the read-only connection for days; (2) provider-runtime ingestion spends 89% of its processing time waiting for the reader's single permit, almost entirely behind whole-set shell-snapshot transactions fired by background sweeps. **Done means:** every reader-routed service is a distinct layer whose requirement channel names `SqlReadClient` (so a build-order change cannot move it), `SqlReadClientAsSqlClient` and the `Layer.fresh` workaround are deleted, ingestion's per-event read no longer queues on the worker lane, the background sweeps stop reading the full UI shell, and the telemetry acceptance in [Verification](#verification) is met on a production-sized copy before merge.

<Callout tone="decision">
**The decision in three sentences.** The worker read lane exists for one thing — keeping *unbounded-size* reads (snapshots, thread detail, activity pages) off the event loop and off the writer — and it is expressed as a type: reader services are built from the repositories' exported constructors with `SqlClient` substituted *inside* the constructor, never by re-providing the shared tag. Everything else — replay, thread resume, and the per-event point reads on the ingestion and WS fan-out hot paths — runs on the in-process default `SqlClient`, exactly as upstream does, which removes 93–98% of ingestion's read wait with zero new connections. The remaining lane load is the sweeps' snapshot reads; this plan moves the four full-shell sweeps to the lean snapshot and removes a redundant whole-snapshot decode, and records the larger demand-side redesign (sweeps reading the engine's committed in-memory model) as the follow-up with its honest size.
</Callout>

This plan builds on two research reports finished this morning (the wiring audit and the workload measurement); their numbers are used, not re-derived. Where a number below is new it is marked as such. Note for the reader: the measurer's scratch worktree (benchmark sources, replay harness, WAL-mode copy) was removed by worktree cleanup before this plan was finished; only the clustering figure in [What the sweeps actually need](#what-the-sweeps-actually-need) was extracted from it beforehand.

The audit's memoisation findings that shape the fix (Effect 4.0.0-rc.115, `.repos/effect-smol/packages/effect/src/Layer.ts`): the memo key is the layer *object* (`fromBuildMemo`, 380-388); `Layer.effect` memoises, `provide`/`mergeAll`/`fresh` do not (1029-1075, 1251, 1330-1350, 2164); `Layer.provide(X, dep)` re-runs `X.build` with the same memo map, so it changes the environment *offered*, not the *key*; and `Layer.fresh` starts a new root map inside which memoisation still applies (so two copies inside one `fresh` still collide) and is itself unmemoised (so each reference builds another copy — the ledger's duplicate instance). ## The rule a maintainer applies when adding a read

<Callout tone="decision">
A read runs on the **worker read lane** only when its result size is unbounded — a whole-set snapshot, a thread's detail/activity page, a search, an aggregate over an unbounded table. It gets there by being a method of a service whose layer is built in `apps/server/src/persistence/Layers/SqliteLanes.ts` from the repository's exported constructor with `SqlClient` substituted inside the constructor. Every other read — a bounded few-row lookup, however hot — stays on the default in-process `SqlClient`, exactly as upstream ships it. A `ProjectionSnapshotQuery` method moves to the in-process instance by being named in `POINT_READS` in `SqliteLanes.ts`, and only when it is a bounded read on a measured per-event hot path, because an in-process read runs synchronously on the event loop. Never re-provide the shared `SqlClient` tag to a layer, and never `Layer.fresh` a repository: both put the lane at the mercy of build order.
</Callout>

## Design

### Lane as a type

Reader-routed services become distinct memoised leaves whose requirement channel names `SqlReadClient`. The audit tested this shape live (replay moved to the reader, appends stayed on the writer, even with the flip probe present). What is routed, and how:

- **`ProjectionSnapshotQuery`** — the only service that must be on the reader. There is exactly one instance in the server, so it keeps its shared tag (dozens of upstream consumers) and is built in `SqliteLanes.ts` as `Layer.effect(ProjectionSnapshotQuery, makeProjectionSnapshotQuery.pipe(Effect.provideServiceEffect(SqlClient.SqlClient, SqlReadClient)))`. Its layer object is then distinct from upstream's `OrchestrationProjectionSnapshotQueryLive`, so no memo collision is possible; `server.ts` already substitutes loom's orchestration composition for upstream's with one marked line. Cost in the upstream hotspot `ProjectionSnapshotQuery.ts`: **one** `// loom:` `export` keyword on `makeProjectionSnapshotQuery`.
- **Usage ledger** — ingestion writes through `ProjectionUsageLedgerRepository` (writer); the Usage page's `topSpendingThreads` aggregate reads through a new distinct tag `ProjectionUsageLedgerReader` built from the exported `makeProjectionUsageLedgerRepository` on `SqlReadClient`. Both ledger files are loom-only; the consumer switch is inside the existing `// loom:` hunk in `ws.ts` plus `loom/wsMethods.ts`. This deletes the `Layer.fresh` workaround and the duplicate read-lane instance it creates.
- **Event replay and thread resume — not routed** (supersedes D2 item 2 of the July 6 plan). Replay never ran on the reader; the measured benefit of routing it is ~4 ms per 1,000 events (the other 34 ms is Schema decode on the main thread on either lane); the writer is busy 0.9% and in-process, so a page of 500 events cannot interleave with a write transaction; and every extra reader-routed service is another layer that must be kept collision-proof. `OrchestrationEngineReaderReplay`, `routeEngineReplayToSqlReadClient` and `OrchestrationEventStoreOnSqlReadClient` are deleted, and `OrchestrationEventStore.ts` needs no export. Consistency is unchanged: a client's shell snapshot is a WAL-consistent view at sequence S from the reader; replay from S+1 on the writer sees every commit — the same pairing the server has always actually run.
- **Deleted:** `SqlReadClientAsSqlClient`, every `.pipe(Layer.provide(SqlReadClientAsSqlClient))`, `ProjectionUsageLedgerOnSqlReadClient` and its `Layer.fresh`, the replay wrapper and its engine re-composition. `SqliteLanes.ts` goes from 102 lines to roughly 45.

**The test that would have caught the replay no-op.** `SqliteLanes.test.ts` today names "reader-routed snapshots and replay" and passes regardless of lane. It is replaced by a lane assertion that needs no probe hook: the test builds the writer on one file and `SqlReadClient` on a **`VACUUM INTO` copy** of it taken after N appends (so the reader sees a strictly older database), appends one more event on the writer, and asserts that `ProjectionSnapshotQuery.getSnapshotSequence()` returns the *copy's* sequence (proving the snapshot query is on the reader) while `OrchestrationEventStore.append` and `engine.dispatch` succeed (proving they are on the writer). A second case reproduces the audit's flip probe — an extra consumer of `ProjectionSnapshotQuery` built *before* the engine via `Layer.effectDiscard` — and asserts `dispatch` still succeeds. The ledger case asserts `ProjectionUsageLedgerRepository.insert` succeeds and `ProjectionUsageLedgerReader.topSpendingThreads` reads from the copy. `SqliteRead.ts` exports its `layer(config)` (loom-only file) so a test can point the reader at a chosen file.

**Which in-process connection for point reads.** The writer's own `SqlClient` (the in-process `@t3tools/shared/nodeSqliteClient`), not a third dedicated read connection. Its plain-statement acquirer releases the permit before the synchronous execution, so a point read waits only while a write transaction is open (0.9% duty; p95 20 ms, max 274 ms) and can never interleave with one; expected added wait is well under a millisecond, versus today's p99 239 ms / max 8.8 s. This is zero new machinery and is exactly upstream's model. A dedicated `query_only` in-process connection (about 20 loom-only lines, one more file handle and prepare cache) is the recorded escape hatch, with the trigger in [Follow-ups](#follow-ups).

**Telemetry consequence.** `sqlReadWaitMs` on the `provider runtime ingestion interval` line is charged by the worker client's permit wrapper only; the in-process shared client (an upstream package file) has no hook and must not get one. After the point reads move, ingestion's read time lands in `remainderMs` by construction, and `sqlReadWaitMs` will read near zero. Acceptance therefore uses `lagP95Ms`, `processingP95Ms` and `remainderMs` — see [Verification](#verification).

### What the sweeps actually need

Ten call sites in background sweeps read a shell snapshot with no arguments every few seconds. The seven already on `getLeanShellSnapshot` (`WorkstreamDispatcher.runPass`, `WorktreeReaper`, `WorkstreamFanInReactor`, `HandoffDrafterReactor`, `WorkstreamLivenessSweep`, `ExhaustionResumeSweep`, `WorkstreamWorktreeStatus`) document in code why they need the **whole active set, not a subset**: the dispatcher reads the graph (dependencies, gate siblings, parents, fork sources) and a graph read over a filtered map misreads absence as satisfaction; the fan-in reactor's `hasDependentResident` and `isMemberOfUnresolvedGate` scan all threads and interpret absence as "no such thread". Both are documented silent-wedge classes from past incidents. So the targeted-query replacement for those callers is not "fewer rows" — it is either a cheaper full-set read (levers 3 and 4) or an in-memory source (lever 5). Their cost is row width, and the lean snapshot already trimmed that.

The three upstream sweeps still on the full `getShellSnapshot` — `ThreadPullRequestReactor.synchronize`, `ThreadSettlementReactor.sweep` and `settleFinishedRoots`, `PullRequestSyncReactor.sweep` — read only `projects`, `snapshotSequence`, and per thread `branch`, `pullRequests`, `linkedPullRequest`, `branchPullRequest` plus the lean fields (verified by grep of each file). None reads `brief`, `lastActivityPreview`, `consults`, `peerMessages` or `goals`. The lean snapshot's *type* already keeps `pullRequests`/`linkedPullRequest`; its *query* just does not fetch the PR rows. Adding `listActiveThreadPullRequestRows` to the lean transaction (a small, indexed table) and passing `pullRequests` and `repositoryIdentity` into `mapLeanThreadShellRow` (the shell path already does both) makes the lean snapshot sufficient for every sweep. A per-sweep targeted query (e.g. only threads with a PR link for `PullRequestSyncReactor`) would be about 30 lines each in upstream files; it is recorded as a follow-up because after this change these sweeps cost the same as the dispatcher's, and the next real win is lever 5.

**Clustering (new number, from the measurer's trace before its worktree was removed):** of 359 snapshot transactions in the trace, 39% began within 50 ms of the previous one ending and 58% within 1 s. That is the sweeps firing on the same engine events and serialising on the permit. It is why lever 4 is attractive and why its correctness condition matters: a sweep pass clears its pending trigger flag at pass start, so a pass that is served a snapshot older than its trigger is the wedge class the coalescing workers were designed to avoid. Any memo must be validated against the projection head, never by time.

### Keyed ingestion worker

**Not warranted.** `plans/ingestion-backpressure/plan.md` §3.2 staged `makeKeyedDrainableWorker` pending the SQL-wait / dispatch-wait split, and the split says the serial fibre was waiting, not computing. After lever 1 the per-event read is ~0.1 ms in-process; at the measured 11 events/s (and at a plausible 50/s with 50 agents) one serial fibre spends its time in the engine's serial dispatch, which per-thread concurrency cannot overlap. The ordering surface it would open across ~3,000 lines of stateful ingestion code buys nothing. The prior "no" stands; re-open only if `remainderMs` per event (CPU) becomes the dominant term of `processingP95Ms` on the interval line.

### Write lane on a worker

**No — the writer stays in-process on the main thread**, and this plan records that as a deliberate decision rather than the accident of `94a5029ff1`. The July 3 offload plan's target was 10–40 s event-loop stalls from long *queries*; those are the snapshot-sized reads, which the reader lane carries. The writer's measured profile is p50 2 ms / p95 20 ms / max 274 ms per transaction at 0.9% duty. Putting it back on a worker would add a ~0.2 ms IPC round trip to every one of the 10–20 statements in a command transaction — roughly doubling p50 command latency — to move under 1% of main-thread time off the loop, and it would put the point reads this plan just moved in-process back over IPC. The in-process synchronous client also has no async-interleave hazard to guard. Revisit trigger: `performance interval` shows `eventLoopDelayP99Ms` attributable to writer `sql.transaction` spans over 100 ms at a meaningful rate (bulk deletes in `storageCleanup`, migrations, or a future write-heavy reactor).

## Follow-ups

Recorded here so the scope line is explicit; none blocks the slices above.

- **Sequence-validated single-flight memo of the lean snapshot** (lever 4): serve a cached lean snapshot only when `getSnapshotSequence()` on the in-process instance equals the cached `snapshotSequence`; joiners of an in-flight computation record the head at call time and accept the result only if equal; re-apply `ThreadBackgroundLiveness`/`ThreadPlanProgress` fields on serve. Decide after slice 3 telemetry; the 58% clustering figure is the upper bound on hits.
- **Sweeps on the engine's committed in-memory read model** (lever 5): requires the denormalised shell columns in the in-memory `OrchestrationThread` and an accessor on the engine (module-level registration, as `registerEngineEventPubSubSize` does, avoids touching 15 engine fakes). Medium-large; the true end state for control-plane reads.
- **Per-sweep targeted queries** for `PullRequestSyncReactor` (threads with a PR link only) and `ThreadPullRequestReactor` (threads with a branch): ~30 lines each in upstream files.
- **`getThreadShellById` fan-out dedup** in `ws.ts` (same thread and sequence fetched once per subscriber): at 0.4 ms in-process per call this is no longer worth an upstream hunk; revisit only if the subscriber count grows past dozens.
- **Dedicated in-process `query_only` connection for point reads**: trigger is ingestion `remainderMs` p95 tracking writer transaction duration under load (a sign point reads are waiting on write transactions).
- **Writer back on a worker**: trigger stated in [Write lane on a worker](#write-lane-on-a-worker).
- **Read-worker `cache_size`** (2 MB default vs the writer's 128 MB): measured effect small (lean 387 → 363 ms) because the OS page cache is warm; a one-line pragma in `SqliteWorker.ts` if ever wanted.
- **FIFO/priority on the lane**: only if WS `subscribeShell` snapshot latency shows starvation behind sweeps.
- **Row decode outside the held transaction** (lever 6): only if the lane's hold time matters again.
