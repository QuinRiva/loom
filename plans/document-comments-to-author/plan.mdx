# Open the document where he clicked, then follow it to its author; the hand-over is two sentences of model text behind an eval

**Recommendation.** A click on a link to an `.mdx` document opens it in the right panel at once, exactly as today. In the same instant the app asks the server who wrote it. When the answer is another live thread working on the same file, the app moves the document to that thread's right panel and takes him there. Nothing waits on the lookup, so the document cannot appear later than it does now.

The second half of the brief is one hand-over to the parent on his closing word. It needs no code. It is two sentences added to text a finished child already reads. They ship only if an eval shows the behaviour failing before them and passing after.

**The bets.** That the centre panel changing a moment after the document appears reads as one motion (§1 says how that is measured). That an instruction can make a finished child hold its message until his word, where two real children did not (§4).

**Cost.** Two pull requests. The first is web, one server lookup widened, and the model text with its eval: two coders in parallel, and about $160 and two hours of eval runs. The second is the phone: one coder, after the first has merged.

## 1. The click: open at once, follow when the author answers

Today every way of opening a file writes to the right-panel state of the thread being viewed.<Sidenote>`useRightPanelStore.getState().openFile(threadRef, path)`, called from about 20 places in `apps/web/src`</Sidenote> The document panel then asks the server for the document's author, for the Query card.<Sidenote>`useDocumentQueryAuthor` in `apps/web/src/loom/documentQueryPins.ts`, backed by `loom.documentQueryAuthor`, cached 30 s</Sidenote> The plan keeps both and adds a third step.

<Steps>
  <Step at="1" title="The click opens the document where he is" badge="unchanged">
    `openFile(viewing thread, path, line)`, synchronously, as now. The panel mounts and starts reading the file.
  </Step>
  <Step at="2" title="In the same tick, the author lookup starts" badge="moved earlier">
    The lookup runs through the same cached query the panel uses, keyed by environment, viewing thread and path, so the panel's own request in the viewing thread is served from it. A document that stays costs one call, as today. A document that follows costs a second call once it lands in the author's panel, keyed on the author; the header line and the Query card there fill when it answers.
  </Step>
  <Step at="3" title="When it answers, the document follows to its author" badge={{ "label": "new", "tone": "accent" }} tone="accent">
    Only if another live thread signed the document as its author and works on the same file. One store transition opens the file in the author's right panel and puts the viewing thread's panel back as it was before the click; then the route changes to the author. The author's thread joins the tab strip above the centre panel the way any visited thread does.
  </Step>
</Steps>

<Callout tone="decision" title="Why not decide first, then open once">
  Waiting for the lookup before opening anything is one write instead of two and never shows the document in the wrong thread. It was rejected because the click would do nothing visible until the lookup returns: about 15 to 100 ms locally and a full round trip over the relay. A click that does nothing for a round trip is the regression the brief's must-not is there to prevent, and it would land on every `.mdx` link in every thread, including the common case where the thread he is in wrote the document.
</Callout>

**Why the document should not repaint on the move.** `ChatView` is not keyed by thread for server threads.<Sidenote>`ThreadRouteView.tsx`, `key={nextHandoffKey?.key}`</Sidenote> The file panel is keyed by environment and workspace root.<Sidenote>`RightPanelSurfaceContent.tsx`</Sidenote> So when both threads share a worktree, the same `FilePreviewPanel` instance stays mounted across the route change. The file's contents are cached by environment, workspace root and path, in `useProjectFileQuery`. The live pass in §8 confirms this. If the panel does remount, the cache still prevents a second read.

**How "not slower" is checked.** By construction and by measurement, not by assertion.

- A unit test on the helper with a lookup that never resolves: the file surface is open in the viewing thread's panel state before the lookup settles. This is the property that holds over any connection.
- In the live pass, the time from click to the first rendered block of the document, ten clicks on the base commit and ten on the branch, reported as two medians and two ranges. Also the time from click to the centre panel changing.
- The server's own duration metric for `loom.documentQueryAuthor` (`rpcRequestDuration` in `apps/server/src/observability/Metrics.ts`), before and after §2 widens it.

## 2. What the server says about a document

`resolveDocumentAuthor` in `apps/server/src/loom/query/documentAuthor.ts` already reads the document from the viewing thread's workspace, parses its `manager_sessions` signature, and maps the most recent authoring signer to a live thread. It reuses all of that. Four facts are added to its result, because the client cannot work them out: a finished child's shell is often absent from the client's snapshot, and the client has no tool-call records.

**The copy he sees.** This settles one of the brief's unknowns. He always sees the copy the link pointed at. The server reads the file from the viewing thread's workspace and never from the author's. When the author's workspace holds a different file at that path, `sameFile` is false and he is not moved: the document opens where he is and the header names the author. That is the other-worktree case, 2 of 56 in the brief's figures. Children share their parent's worktree, so the common case is the same file.

**Later editors.** This meets the brief's Decided line on documents several threads changed. It is one new read in `apps/server/src/loom/projection/LoomStore.ts`: the distinct threads under the author's workstream root whose `file_change` turn items name this absolute path and started after the signature's `authored_at`.

- Measured on the live database, it found the right thread for this goal's own brief: the orchestrator that edited the planner's document. It took 1 to 3 ms warm and 50 to 90 ms cold.
- It runs only when the author came from a signature that carries `authored_at`.
- It sees edits made with the write and edit tools, not a file changed from a shell command.

**Deleted, archived, cancelled.**

- Deleted: unchanged. The resolver already skips a deleted signer and falls through to the next signer, then to the viewing thread.
- Archived: reported, not skipped, so the header can name the author and Query still forks it. The client does not move him to an archived author.
- Cancelled (the brief's other "still unknown", settled by reading PR #568): a cancelled author is an ordinary thread, so his message starts a turn and it can edit the document and reply. It cannot add to its report: only a `done` thread's later submit is accepted as an addition (`handlers/submit.ts`, the `row.outcome === "done"` branch), and a cancelled thread's submit is refused with a message that names `notify_thread`. So a cancelled author is treated like a finished one for navigation, and its hand-over is the one message without a report section. Nothing is built for it.

**Query is untouched.** `documentQuery.ts` calls the same resolver and reads none of the new fields.

## 3. Web: one helper, one store action, one header line

**The helper.** A new module `apps/web/src/loom/openDocumentLink.ts` exports `useOpenDocumentLink()`. It returns a function taking the viewing thread and the path (workspace-relative or absolute) with an optional line. It holds the three steps of §1 and nothing else.

- It reuses `useAtomQueryRunner(loomCommands.documentQueryAuthor)` for the lookup, `useNavigate` with `buildThreadRouteParams` for the route change (as `LoomMdxAnnotationLayer.tsx` does), and `isMdxPreviewFile` for the gate.
- The decision is one pure exported function, tested on its own. Given the lookup result, the viewing thread's id and its workstream role, it returns "stay" or the author's thread and path.
- It returns "stay" unless all of these hold:
  - `authorSource` is `"signature"`;
  - `authoringSignature` is true, so a reviewer's signature, reached when every authoring signer is deleted, does not move him;
  - the author is another thread, `authorArchived` is false and `sameFile` is true;
  - the viewing thread is not a query thread (role `document-query`), where a person asking questions is already talking to a fork of the author.
- The follow is dropped, silently, if the lookup fails, if he has since navigated away from the viewing thread, or if he has acted on that thread's panel since the click.

**The store action.** `apps/web/src/rightPanelStore.ts` gains one loom action, a single `set`, taking the two threads, the path and line, the viewing thread's panel state as it was before the click, and the user-action revision read just after the click's `openFile`. It opens the file in the author's panel as a user action. It restores the viewing thread's panel to the before-click state only if that thread's revision is unchanged, the guard `openProactive` already uses. Without the restore, the document would stay open in the thread he left, and commenting on it there on his return would be today's misroute again.

**Who calls the helper.** Opens that start in the conversation: a link he was presented. Every other open stays in place and is covered by the header.

## 4. The hand-over on his closing word

The exact strings, the eval cases and the pre-registered change record are in `plans/document-comments-to-author/model-text.md`. Coders apply the strings verbatim. This section is what a reviewer needs to judge them.

**What is already built.** For a document its author is holding for his approval, PR #568 does what the brief asks: correction rounds send the parent nothing and his approval completes the child. No text aimed at a held child changes.

**The gap, in two real rows.** Of the 15 finished children a person wrote to after they finished (7 Oct to 12 Nov), two received comments on a document. Both messaged the parent at once.

> "tell the parent right away, since it would plan round 3 differently now"

That is a coder on 12 Nov, after PR #568 was live, on receiving five form answers. It is quoting the instruction every child carries: "Tell your parent at once ... only when it would act differently now".<Sidenote>`CHILD_READERSHIP_CLAUSE`, `apps/server/src/loom/prompt/prose.ts`</Sidenote>

**The change.** Two sentences added to that instruction, as its exception, and one sentence added to the result a finished child sees when it adds to its report.<Sidenote>`REPORT_ADDITION_ECHO`, `apps/server/src/mcp/toolkits/workstream/render.ts`</Sidenote> Together they say five things. While the human reviews a document you wrote after you finished, your message to the parent waits until they say the review is finished. A full set of answers is not that word. A review that changed nothing needs no message. Once something has changed, end each reply by telling them the parent has not been told. Then tell it once.

<Callout tone="decision" title="Why the system-prompt clause, when PR #568 found a result sentence worked and a clause edit did not">
  PR #568's lesson was to put a rule where the model is when it decides. Its held child decided after a tool result. A finished child decides on reading his message, before any tool call: the 12 Nov coder made no submit first. The only texts in front of it are his message and this clause, and the clause is what it obeyed.

  Carrying the rule on his message instead would need the server to know that the receiving thread has finished, at both places where it prepares a message for the provider. It would also leave "at once" contradicting it. The report result is amended too, because a child that does record a round is told there to message its parent.
</Callout>

**Each string must earn its place.** Seven new cases in `evals/loom-handback`, run in three arms (cases only; plus the clause; plus the result sentence). A string ships only if its case fails before it and passes after, with every existing guard still passing. The two cases the brief names are among the seven: a finished author that holds through rounds and recognises his closing word, and a parent that receives the hand-over after it has started building on the earlier version. A seventh covers the brief's "then or later": rounds of questions only, then a closing word, and no message.

**Then everything else.** The final commit runs the whole eval once per model, all 27 cases, as `evals/README.md` asks before a merge. Six of the 13 cases outside the arms are children that read the changed clause, among them a planner holding a brief for approval. A case that passed on base and fails here stops the text.

**The per-reply sentence has its own stop rule.** It is read, not pattern-matched. It is kept if at least 7 of 10 samples tell him the parent has not been told in each case where something changed, and it appears in none of the replies in the questions-only, working-child and held-child cases. Otherwise it is dropped and the rest of the text goes ahead. About 500 attempts in all: roughly two hours and $160.

**No text is written for the parent.** Nobody has seen an orchestrator mishandle a late hand-over. The case measures it. If it fails, the failing samples go to a planner.

**The clause is a commonly injected surface** (every child, every turn, 88 words added to 275). `docs/architecture/tool-def-authoring.md` requires a cross-family read before it ships. That read is arranged by the orchestrator, after the eval passes and before the pull request merges.

**Two consequences to show the brief's owner when he tries it.**

- **One more message on a single-round review.** Today, when he answers a finished child's question form and writes nothing else, the parent hears immediately. After this change the child records the answers, replies that the parent has not been told, and waits for his word. That follows from the brief's must-nots ("send the parent anything about a review before you say it is done", "call a review done that you have not"), and it is the 12 Nov row exactly.
- **A line at the end of each reply.** Once he has asked for a change, each of the author's replies ends by saying the parent has not been told. It is the conversational stand-in for the marker he declined, and close to it in kind, so it is his to judge in use.

## 5. The phone (second pull request)

Every way of opening a file on the phone ends at one screen, so the change has one home. `MdxDocumentView` in `apps/mobile/src/features/files/MdxDocumentView.loom.tsx` puts a tapped answer in the draft of the thread on the file screen's route. That target is its `answersTarget`. Its bar reads "N answers ready to send" with a "Back to chat" button.

1. A small hook beside it runs `loom.documentQueryAuthor` for an `.mdx` opened in a thread. It reuses the query family in `packages/client-runtime/src/state/loom/goalCommands.ts`, which the phone does not instantiate yet, and the pure decision function of §3, moved to `packages/client-runtime` so both clients share it.
2. When the decision is to follow, `answersTarget` is the author's thread. The bar reads "N answers ready to send to «author title»" and its button opens the author's chat in place of the file screen, so Back from there returns to the chat he came from.
3. The document draws at once, read-only, and answers become tappable when the lookup has answered. The view already re-sends its `init` message when its inputs change; the answers target becomes one of those inputs. Until then a tap cannot land in the wrong draft. If the lookup fails, answers become tappable into the viewing thread's draft, as today, and the bar names that thread.
4. No server change: the fields come from the first pull request.

On the phone this applies however the document was opened, including from the Files browser. The brief's phone check covers a link; one screen with one rule is fewer parts than telling entry points apart there, and it is the brief's own aim.

## 9. Risks, and where the plan reads the brief rather than meets it literally

**Where the plan reads the brief.**

1. **The first check's end state is met; the path to it has two visible steps.** The brief says the click "takes you to" the author. The document first appears in the thread he clicked in, and the centre panel changes when the lookup answers. This is the price of the speed must-not. If the live pass shows the second step as a distinct jump, the cheap remedy is to start the lookup when the pointer enters an `.mdx` link, so the answer is usually cached by the click.
2. **"Later editors" are the edits Loom recorded.** A file changed from a shell command, or by a thread whose tool records are no longer kept, does not appear.
3. **No instruction is added telling a reviser to sign.** The brief's line describes how the author is determined, and the code already does that. Three of the brief's eight cases were a second planner that did not sign; those now show in the header.
4. **Once he has asked for a change, the author's replies also say the parent has not been told.** The brief assumes the author says it has handed over. The plan adds the mirror statement, because with no marker on the thread it is the only thing that makes an open review visible. The brief's Assumed line now says so.
5. **The phone follows the author however the document was opened.** §5 gives the reason.

**Risks.**

- **The clause change displaces other children.** It is read by every child. The seven guards are in every arm, the full run covers the rest, and a case that flips stops the text. A held child messaging its parent at approval as well as completing is the displacement most likely; `held-child-approval` catches it.
- **The review rule costs him a message on single-round reviews** (§4). It is what the brief asks for. Named so that it is judged in use.
- **A parent building from the earlier version while he reviews.** With no marker, the parent learns at the hand-over. The brief's owner chose this. The orchestrator case measures what the parent then does.
- **The lookup's signature match scans every provider thread** (12 ms at 6,687 rows) and grows with them. It delays only the move, never the document. Not fixed here.
- **A followed open costs a second lookup**, keyed on the author, for the header and the Query card in the author's panel (§1). The document is already showing; only those two wait for it. The coder confirms the count in the live pass: one call for a document that stays, two for one that follows.
- **A cancelled author mid-review is not reached by model-text §2.** Its submit is refused with text that names `notify_thread`, the same nudge §2 qualifies for a finished one. §1 still applies to it. Rare, and not built for.
- **The move, on a thread whose shell the client has not loaded.** A finished child's shell is often absent from the snapshot and loads by id, as thread chips rely on. The coder navigates the way `ThreadMention` does and confirms it in step 1 with an idle child.
