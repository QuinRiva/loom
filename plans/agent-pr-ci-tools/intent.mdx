## 2. The brief

**You'll know it works when.**

- A root, orchestrator or shipper thread started after the next deploy lists the same nine PR tools as today (link, watch, guides) and none of the new nine.
- `pnpm ship` is still how a Loom PR is opened and merged, and the shipper role and ship skill read as they do today.
- Pull 16's decision log carries the ruling and points at this brief, and the note beside the withheld list says why, so the next upstream pull does not redo the question.
- **Must not:** change any text an agent reads; expose any tool that writes to GitHub before the target repository is pinned.

**Approaches in play.**

- **Leave all nine off, as a decision.** Wins if the shell route keeps working as measured. _Chosen._ Worth reopening if agents start answering review threads daily, if `gh` starts hitting rate limits, or if a project moves to a host `gh` cannot reach.
- Not taken: the review-comment pair, `pull_request_read` and `pull_request_respond`. Wins if you want agents answering and resolving Copilot's review threads on fathom-platform PRs to become routine; today they reply and never resolve. It costs about a day of agent work: pin the repository, a sentence of role prose on replying under your name, an eval. It adds roughly 1 KB to each turn that loads them (estimated from the measured 5.0 KB for all nine), and two more Loom choices to re-check at every upstream pull. Any exposure pins the target repository first (the red box above).
- Dropped: the three read tools first, which is what the pull proposed. The reads work by shell and `ci_logs` has no edge.
- Dropped: the create and merge tools, with or without a server check. `pnpm ship` rebases, runs the checks, writes the trailers the deploy notice reads and deletes the branch; there is no point at which it could call the tools instead of `gh`. Outside Loom, `gh` is what the roles prescribe and it works.

**Decided.** "I think you're right that we should be done work like this after the merge lands, I think the issue in the past was that we were failing to do this for up work after the merge lands." This brief is that work.

- On which of the nine his agents get, Carl chose, 24 Nov: "None. Keep all nine withheld as a decision, record why, close the follow-up".
- On whether the server should enforce a project's merge authority, the per-project setting saying whether an agent may merge or must stop at an open PR, he chose: "No. Leave it to role prose, which held".

- _Assumed:_ `pnpm ship` stays the only way an agent opens and merges a Loom PR, because nothing here replaces its checks; redirect if wrong.
- _Assumed:_ upstream's prompt text telling agents to prefer these tools over `gh` stays out of pi's prompt under every option, as the pull left it.
- _Assumed:_ the other tools pull 16 withheld (issue tools, feedback, theme, `send_to_user`) stay out of this goal. They are their own rows in the follow-ups list.

**Not doing.** Any change to `pnpm ship`. Any tool that merges, opens, edits or reviews a PR.

**Settled since.**

- The app's own Create PR button picks the repository the same way as the tools. The watch and link tools agents already have do not: they are given the PR's URL or its repository by name. On a clone of Loom with an `upstream` remote and no `gh repo set-default`, the button would open the PR on `pingdotgg/t3code`. Nothing has tripped it: this VM carries the setting and `pnpm ship` rewrites it on every run. No code change; `docs/operations/shipping.md` now says to run `gh repo set-default` once on a fresh clone, and why the app needs it as much as `gh` does.

**Still unknown.**

- Whether `pull_request_update` can request a review from the Copilot bot, the main reason agents edit reviewers today. Only matters if that tool is ever wanted.
