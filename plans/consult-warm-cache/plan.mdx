# Consult forks should read the target's warm cache

Every `consult_thread` call today pays to re-read the whole target context as a **cache write**, however warm the target is: **about $3.08 for a 213k-token Fable thread and $6.19 at 481k**, where a warm read would be **about $0.25–0.30**. The cause is one thing: the fork is launched without the target's extensions and MCP credential, so it registers **29 tools where the target has 51**; pi 1.1 then declares that difference to the model, the request's `tools` array changes, and Anthropic's cache key (`tools` → `system` → `messages`) misses from the first byte.

**Recommendation.** Launch the consult fork *exactly* as the target was launched — its recorded launch identity (appended prompt, skills, the Loom extension), upstream's bridge extension and an MCP credential — so the fork registers the same tools and pi replays the transcript with no tool delta. Keep it read-only by minting that credential as a **read-only caller**: upstream's `McpToolAccess` already refuses every state-changing upstream tool for a read-only caller, and three small gates do the same for Loom's tools and REST routes. No pi patch, no second cache breakpoint, no change to how targets are launched. About a day of work for one coder, plus the live check.

<Callout focus title="What it means now">
  Consults of a warm root or orchestrator drop to roughly a tenth of today's price, so a retro or a planner can consult the live orchestrator as a matter of course rather than once. Children stay cold (their keep-warm stops at submit), so consults of finished children cost what they cost today. Read-only is preserved by server-side refusal, not by prompt, and the fork keeps bash for inspection exactly as it has today. Three decisions are at the end: approve the launch-like-the-target route over a fork-only stub hook, whether the fork should also block `edit`/`write`, and whether it should run in the target's worktree.
</Callout>

**Scope.** `apps/server/src/loom/workstream/consult.ts` and the four files that make a read-only caller real. Not in scope: keeping children warm after they submit, changing cache retention arms, or pi patches. **Done** means a consult of a warm target shows most of its first request as `cacheRead` in the fork's session usage, and every state-changing tool call from a fork is refused by the server — both checked by the recipe in section 6.

## 1. Why every consult misses

Anthropic hashes the request prefix in the order `tools` → `system` → `messages`; a change at any level invalidates it and everything after. The fork's `system` and `messages` already match the target's — pi 1.1 stores the system prompt in the session and replays it word for word — so only `tools` is in play. The table is the whole diagnosis.

**The mechanism in pi 1.1.** A pi session transcript declares its tools: the leading system message carries `toolsAdded`, and every later change is a system message with `toolsAdded` / `toolsRemoved` deltas. Before each request `declareToolChanges` (pi-agent-core, `agent-loop.js`) compares the transcript's current tools with the tools the process has registered and active; a difference becomes a new delta, and for a model without native mid-conversation tool changes the request's `tools` array becomes the post-delta list. On a `--fork`, pi restores the active loadout from the transcript (`_restoreToolsFromTranscript` in `agent-session.js`) — but only tools that are *registered* can be active. The fork registers none of the `mcp__t3-code__*` tools, so 22 of them are declared removed. Order does not matter: the request's tool order is the transcript's declaration order, not the fork's registration order.

The researcher's dump of a real Loom fork request shows it: 29 tools, and after the question a system message that begins `Updated system prompt section "tools": <tools> - read: …` — the system prompt's tools section regenerated for the smaller set.

<Callout tone="info" title="A finding that departs from the researcher's report">
  The report lists a second cause — "two consults of one target cannot share, because pi's single breakpoint sits after the question" — and proposes a fork-only second breakpoint. That is not needed. The target's own last request wrote a cache entry at the end of its last user / tool-result block. A fork's breakpoint sits after the question; Anthropic's lookback checks up to 20 positions behind a breakpoint for entries prior requests wrote, and the target's entry is two to five positions back (the target's final assistant message, then the question). So fork 1 reads the target's entry, and that read refreshes the entry at no cost, so fork 2 within the lifetime reads it too. The second cause was an observation under the tool mismatch, not an independent cause. (Anthropic: *"The cache is refreshed for no additional cost each time the cached content is used"*; lookback window: 20 blocks, consecutive tool-use or tool-result runs counting as one.)
</Callout>

**The 1-hour arm.** Forks run with `PI_CACHE_RETENTION=short`, so their breakpoints carry no `ttl`. Anthropic's documentation keys cache hits on content — *"cache hits require 100% identical prompt segments"* — and its mixed-TTL billing example shows a 5-minute marker hitting an existing entry, so a short fork should read a 1-hour root's entry. Keeping the fork short is right regardless: its own writes (the question and the answer's tool turns) are throwaway and the 5-minute write is 1.25× base against 2× for 1-hour. The live check in section 6 confirms both arms; if the long arm does not read, the one-line fallback is to launch the fork with the target's retention.

## 2. The fix: launch the fork as the target was launched, under a read-only credential

<Callout tone="decision" title="Decision: reuse the target's launch, not a fork-only hook">
  The consult fork is built with the same inputs `ProviderSessionManager` gives the target — the launch identity record (`workstream-launch-identity/<threadId>.json`: appended prompt, skills, extensions, env, model selection, tool profile), upstream's bridge extension, and an MCP credential — so the bridge registers the identical `mcp__t3-code__*` declarations, the Loom extension's profile part computes the identical active set, and pi's transcript restore finds every declared tool registered. Parity is by construction: whatever changes in how targets are launched flows to forks unchanged. The credential is minted as a read-only caller so nothing it reaches can change state (section 3).
</Callout>

<Columns>
  <Card eyebrow="Recommended" heading="Launch like the target + read-only credential" tone="success" badge="parity by construction" meta={["5 files", "≈ 60 lines", "no pi patch"]}>
    The fork gets the target's recorded composer fields, the bridge, and a credential whose scope says `access: "read-only"`. Tool declarations match because the same code registers them from the same MCP catalogue (`tools/list` is the same for every credential) and the same prose. Read-only rides upstream's existing `McpToolAccess` refusal plus three Loom gates. Drift risk: nil for declarations; the one moving part is the credential's scope.
  </Card>
  <Card eyebrow="Rejected" heading="Fork-only hook that stubs the transcript's declarations" tone="neutral" badge="hackier" meta={["no credential", "≈ 80 lines", "tracks pi internals"]}>
    A fork-only extension reads the transcript's declared tools and registers refusing stubs with the same name, description and parameters, then re-asserts the active set. Read-only is absolute (no credential exists). But declarations must match pi's `toToolDeclaration` byte for byte, including `constrainedSampling`, and the system prompt's `tools` / `rules` sections need each tool's prompt snippet and guidelines, which the transcript does not store — so the server would ship its prose table into the stub extension, a second registration path for the same tools that silently misses the cache the day pi or the bridge changes a detail. The researcher's simpler variant (swap the wire `tools` in `before_provider_request`) is worse again: pi still tells the model the tools were removed, and the swapped-in tools are not callable.
  </Card>
</Columns>

## 3. How read-only is guaranteed after the change

Today's guarantee is "no credential": the fork cannot reach `/mcp` at all. The replacement is a credential whose scope carries `client.access === "read-only"` beside the thread caller, and a refusal at every surface that credential can reach. Declarations are unchanged — the model sees the same 51 tools — and the *effect* of each state-changing one is a server-side refusal the model reads as a tool error.

Why `client.access` rather than a new flag: `McpInvocationScope` already has `client: { sessionId, label, access }` for an outside caller approved as read-only, and upstream's policy for it is exactly the one wanted here — *"A client approved for read-only access changes nothing."* A scope with both `thread` (the target, so profile and reads answer as the target) and a read-only `client` needs no new type, no change to `McpToolAccess`, and reads as a consult in logs through its label. The only upstream edit is two marked lines in `McpSessionRegistry.issue` to accept and copy a `client` into the scope.

**Bounds worth stating.** A fork's reads answer as the target: `workstream_list` and `goal_task_list` show the target's branch, which is what a consult about that thread wants. If the target's provider session is relaunched mid-consult, `prepareMcpSession` revokes every credential on that thread id, the fork's included; its next MCP call fails and the model sees a tool error — rare and harmless. A target with no launch identity record (a thread that never launched through the composer) gets today's cold fork and a warning in the log.

**The test worth writing.** The read-only property is the one thing that must not regress, and it is table-driven: in `registration.test.ts`, for every entry of `LOOM_TOOL_DEFS`, call `callLoomTool` with a scope whose `client.access` is `"read-only"` and handlers that fail the test if invoked; assert the two allowed tools reach their handler and every other returns the refusal text. One more assertion in `loomAgentRoutes.test.ts`: the ask route answers 403 to a read-only caller.
