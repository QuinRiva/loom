# Consult card: show what a running consult is doing

**Objective.** When a thread calls `mcp__t3-code__consult_thread`, its timeline shows a consult card (`apps/web/src/loom/ConsultCardRow.tsx`). While the consult runs the card says only `WAITING`, and expanded it shows the question. A consult is a throwaway fork of the target's pi session (`apps/server/src/loom/workstream/consult.ts`) doing real work with the target's own tools — `rg`, `read`, `bash`, trace fetches — for minutes, and once the current two-minute cap is removed, for five to fifteen minutes or more. The user watching the asker's thread cannot tell a healthy consult from a hung one, and cannot see what the fork is spending or doing. This plan mocks three ways of showing it, in the vocabulary the workstream cards already use (current step and its duration, the model pill, cost and token rows), says exactly which figures exist today and what each one costs to plumb, and recommends one.

**Done means:** Carl has picked an option in the form at the bottom. For the recommended option, done then means: a running consult card shows the consult's elapsed time, the fork's current tool and how long it has run, its tool count and cost on the header, and — expanded — its model, tokens, recent steps, a transcript chip and a Stop button; a finished card freezes those figures above the answer; all of it ticks without per-token WebSocket traffic and without a React commit per second; mobile is unchanged; `vp check` and `vp run typecheck` pass. Nothing is built until the form is answered.

## The card today, and the scenario the mocks use

The card is a `dynamic_tool` turn item of the asker's thread (`toolName: "mcp__t3-code__consult_thread"`), picked out of the grouped tool rows by `isConsultToolItem` and rendered as its own row. It reads the item's `input` (`threadId` or `name`, `question`) and `status`, fetches the full item with `getTurnItem` only when expanded and not waiting (the wire withholds the output), and renders the answer as chat markdown. `STATUS` maps `running` to `waiting` (amber), `completed` to `answered` (info) or `failed` when the output is an error, and `failed`/`interrupted`/`cancelled` to `failed`.

The server side is one Effect: `LoomThreadConsult.ask` spawns `pi --mode rpc --fork <target session>`, asks `get_state` for the fork's session file, sends the question as a prompt, then loops over the fork's RPC events until `agent_settled`, keeping only the last assistant message's provider error. Every `tool_execution_start`, `tool_execution_end`, `message_end` and its usage passes through that loop and is dropped. When the loop ends the transcript is moved under `<stateDir>/workstream-consults/` and the answer returns as the tool result. The MCP handler (`apps/server/src/mcp/toolkits/workstream/handlers/consult.ts`) then dispatches `thread.consult.record`, whose event carries the question, answer, `durationMs` and `forkSessionPath` — of which only a question preview reaches the `loom_thread_consults` table.

Every mock uses one consult. A coder thread working on an empty `tenant_name` asks the thread that triaged the 8 October production batch for file:line evidence and a Langfuse trace id. The fork — a copy of that triage session, on its own model `cliproxy · claude-opus-5-5` — runs `rg` over the tenant-audit package, reads `resolve.py` and `fallbacks.py`, runs the `langfuse_trace.sh` script for the building (38 seconds), filters the trace with `jq`, and re-reads the resolver around the fallback. Seven minutes in it has made 11 tool calls and spent $0.84, mostly cached input. It answers at 9m 40s, 14 calls, $1.12. The failed mocks show a model request that fails with a 529 after retries (Options A and B) and a consult the user stopped from the card at 11m 03s (Option C), because the Stop button is what Option C adds.

One rule is deliberately different from the workstream cards. There, the step and its amber threshold apply to the thread's own tool call, and `mcp__t3-code__consult_thread` was named as a known false cue — a consult legitimately runs past five minutes. On the consult card the **total elapsed is never amber**: a long consult is the expected case. The amber applies only to the **fork's current step** — a single `bash` or `read` or model request that has run five minutes is the stuck signal, exactly as it is on a workstream thread. Option A, which has no step, therefore has no stuck signal at all; that is its real cost, and the reason the recommendation is not Option A.

## The live-consult channel

Options B and C need one piece of plumbing: a path from the fork's events to the card that does not go through the event log or the projection. Three transports were weighed.

- **Partial output on the consult's turn item** (`turn_item.updated` with `status: running`, as streaming `bash` output does). Rejected: `projectTurnItemForWire` withholds a `dynamic_tool`'s output (`outputOmitted: true`), so nothing would reach the card without polling `getTurnItem`.
- **A field on the asker's shell sidecar** (`LoomThreadShellFields`, like `activeStep`). Rejected: the sidecar is DB-backed and a shell re-read is triggered by thread events, so every fork tool boundary would have to be a persisted loom event — forty durable rows per consult for a figure that is worthless once the consult ends.
- **An unsequenced shell-stream item**, exactly as goal writes travel today (`LoomGoalBroadcast`: a PubSub whose items `ws.ts` merges into the shell stream for subscribers that pass `loom: true`, and whose current state rides the authoritative snapshot). **Chosen.** Ephemeral, no DB, no event-log growth, the same fan-out and merge code path as goals, and the snapshot handles reconnects.

**Correlating the item and the live consult.** The MCP request carries no pi `toolCallId` (the bridge in `piT3McpExtensionSource.ts` ignores `execute`'s first argument), so the handler cannot name the asker's turn item directly. It knows the asker thread and the trimmed question, and the card knows the same (the question is whole on the wire — `summarizeDynamicValue` only summarises inputs over 16 KB, and a question is capped at 8,000 characters). So the key is the asker thread plus a hash of the question. The exact alternative — the bridge sending `_meta.toolCallId` on `tools/call`, or an `x-t3-tool-call-id` header, and the MCP HTTP layer threading it into the caller context — is the upgrade if the hash ever collides in practice (two parallel consults from one assistant message, to the same target, with the identical question).

**Stop.** `LoomThreadConsult` gains a registry of running forks: `consultId → { interrupt: Deferred, startedAt }`. `cancel(consultId)` completes the deferred; `ask` races the fork against it and fails with `LoomConsultError("Stopped from the consult card after 11m 03s.")`, the retained transcript still moves under `workstream-consults/`, and the MCP tool returns that sentence as an error result, which the asker's model reads and continues from. The RPC is `loom.consult.cancel` (`rpc.loom.ts`, handler in `loom/wsMethods.ts`, thread-write scope in `auth/RpcAuthorization.ts`). The card shows the button only while `waiting` and only when a live consult is matched, and disables it after one click until the ended item arrives.

## Surfaces

- **Web and desktop.** The card is the same component in both (desktop wraps the web bundle). Everything above applies to both.
- **Mobile.** There is no consult card: a running consult is a generic tool activity row (`apps/mobile/src/lib/threadActivity.ts`, `dynamicToolTitle`) and reads as the tool's name. Option A changes nothing on mobile. Options B and C add shell-stream item kinds that `packages/client-runtime` (shared by both apps) must decode; mobile decodes and ignores them in the first cut. The natural follow-up, out of scope here, is a one-line `consulting «title» · read · 7m` in that activity row.
- **Workstream cards.** During a consult the asker's own Active-now card and graph node already (post PR #347) read `mcp__t3-code__consult_thread · 7m`, amber past five minutes. The consult card is the detail behind that figure. Substituting the fork's step there is a one-line follow-up once the channel exists, not part of this plan.
- **Agents.** The consult's result is unchanged; nothing in the channel is agent-facing. The Stop reason sentence is the one new thing an agent sees.

## Risks

- **Stopping the asker's turn may orphan the fork.** The bridge aborts its `fetch` when pi aborts the tool, but whether the MCP HTTP server interrupts the handler fiber — and so the fork's scope — is unverified. With no cap, an orphan would run to its own completion. The registry makes this deterministic: on the asker's run ending, cancel any live consult keyed to that thread. Verify the abort path during cut 2 and keep the run-ended hook if it does not interrupt.
- **Correlation by question hash.** Two parallel consults from one assistant message, to the same target, with the identical question would share a key and the card would show one fork's progress on both. Pi can run a message's tool calls in parallel, so this is possible but degenerate; the `toolCallId` plumbing is the fix if it is ever seen.
- **Item ordering on first publish.** The adapter projects the asker's `running` item from pi's `tool_execution_start`; the MCP request arrives a few milliseconds later. The card may receive `consult.updated` before its item exists, so the store must hold entries for threads whose card is not mounted yet (it is keyed, so it does), and the card reads the store on mount.
- **Unknown item kinds on older clients.** A client built before cut 2 would fail to decode the new shell-stream kinds. `LoomGoalShellStreamItemMembers` set the precedent (a union member added in a marked block); the mobile and web bundles ship together from this repo, so the window is the deploy itself.
- **Amber on a long model request.** The fork's first request replays the whole target transcript; on a cold cache it can take a few minutes. `thinking · 4m` is still true and still worth a look — the threshold is the same constant as the workstream cards and is one number to raise.
- **Fan-out.** Every loom subscriber receives every consult's items. Bounded by the coalescing and the small payload; the per-thread gate is the escape hatch, not a redesign.
