# A deploy that changes the phone app builds its APK, and the app says so

At the end of every deploy one question is asked: **does an APK the server already holds match the app code of the release now running?** If one does, nothing is built and the phone hears nothing. If none does, a background job builds the APK from that commit. It is published only if it carries the installed app's signing certificate and version code, and it sits beside the one before.

The Loom server streams that state to the app over the connection it already has. The app compares the commit baked into itself with the one on offer. When they differ, the home screen says a new version is ready; a tap downloads it through a short-lived signed link and hands it to Android's installer. Settings → About shows the same state, with the way back.

It is two coder briefs in sequence, about a day of agent work, with two real APK builds as proof. On the machine, each deploy that changes the app costs 10 to 25 minutes of low-priority CPU and about 9 GB of transient disk, on the disk that has room.

## What it means in scope

- **In the cut:** the deploy's background APK build, and the server keeping two APKs and serving them. In the app, the home notice and the "Loom build" rows in Settings → About, with the install and the way back. For agents, `loom-deploy status` shows the phone app's state and `loom-deploy apk` retries a build.
- **Not doing,** as the brief says: served code and anything that prepares for it, iPhone, other users or channels, store builds, changes to pairing. Also not built here: a notice in the web or desktop app, and a setting for any of this. An app too old to connect at all gets no download either (§11).
- **Done means** §9's proof passes on a scratch copy and Carl's three-step check passes on his phone.

## 1. One deploy, end to end

<Steps>
  <Step at="0:00" title="Carl or an agent starts a deploy." aside="As today.">
    `loom-deploy deploy` builds the release, trial-starts it and asks for the switch. Loom is down for about 40 seconds.
  </Step>
  <Step at="about 0:03 to 0:08" title="The five-minute watch." aside="As today.">
    A release that fails here is put back by the launcher. It never reaches the next step, so **a release that is put back builds no APK**.
  </Step>
  <Step at="about 0:08" title="After-accept asks the one question." badge={{ label: "new", tone: "accent" }} aside="Under a second: one git diff and a few file checks.">
    Does a stored APK match the running release (§2)? **Yes:** it is recorded as the matching APK and nothing else happens. **No:** a build is started in its own systemd unit, and the state file says one is building.
  </Step>
  <Step at="about 0:08 to 0:30" title="The build runs apart from Loom." badge={{ label: "new", tone: "accent" }} aside="Survives a Loom restart, another deploy and the end of the deploy command.">
    A fresh checkout of the commit, install, Expo prebuild, Gradle. Then six checks; an APK that fails one is not published and the build is recorded as failed (§4).
  </Step>
  <Step at="about 0:30" title="The APK is published and the phone hears." badge={{ label: "new", tone: "accent" }}>
    The state file names the new matching APK. The server sends the change to every subscribed app within five seconds, and the home notice appears (§7).
  </Step>
</Steps>

<Callout tone="decision" title="The one rule everything else follows from">
  **The server offers the stored APK whose app code equals the running release's. When none does, it builds one.** The same function answers at the end of a deploy, after `loom-deploy back`, and when an agent runs `loom-deploy apk`. A deploy that changes nothing the phone runs leaves the matching APK as it was. Going back to an earlier release makes the earlier APK the matching one again, with no extra mechanism.
</Callout>

## 2. When the app counts as changed

Wrong one way, Carl is asked to install 108 MB for nothing. Wrong the other, the app is behind without saying so, which is the defect this work exists to fix. So the rule is built from what the APK actually contains, with a ring of caution around it, and anything it cannot decide counts as changed.

<Callout tone="decision" title="Chosen: the last APK's own file list, plus a ring of caution">
  Gradle already writes a source map for every release build, at `apps/mobile/android/app/build/generated/sourcemaps/react/release/index.android.bundle.map`. It lists every file in the JavaScript bundle: **1,469 repository files and 3,236 files from 207 dependency folders** in the build of 19 Nov. When an APK is published, those two lists are saved beside it. Later, the app's code at another commit equals that APK's when none of the tests below finds a difference.
</Callout>

Between a stored APK's commit and the running release's commit, **the app has changed when any of these holds**:

1. `git diff --name-only --no-renames` between the two commits names a file in the APK's saved list of repository files.
2. It names anything under `apps/mobile/` that is not a test (`*.test.*`, `__tests__/`) or Markdown. This covers native modules, config plugins, `app.config.ts`, the Metro and Babel configuration and every new file.
3. It names an input outside that folder which the app's configuration and bundler read: anything under `assets/` or `scripts/lib/`, or any `packages/*/package.json`. A file under `packages/` whose name carries `.android.` or `.native.` counts too, since the bundler would pick it over its plain sibling.
4. It names a file under `patches/`, other than a patch of `@earendil-works/pi-coding-agent`. The monthly pi bump rewrites that patch, and pi reaches the mobile workspace only through `packages/provider-pi`, whose two bundled files do not import it.
5. The `apps/mobile:` section of `pnpm-lock.yaml` differs between the two commits. That section holds the resolved version and patch of every direct dependency: Expo, React Native, each native module and config plugin.
6. One of the APK's 207 dependency folders is missing from the running release's `node_modules/.pnpm/`. A folder's name carries the package's version, its peers and its patch, as in `expo-network@58.0.3_patch_hash=b79a…`. So any change to a dependency the bundle reads from renames its folder.
7. Git cannot compare the two commits, or the saved lists are missing or unreadable.

## 3. What identifies a build, and how the app learns the server's

**The commit.** An APK is identified by the full commit it was built from. The app never needs to know which of two builds is newer, only whether its own is the one the server offers. So equality is enough and a content hash buys nothing. The build job sets two environment variables, and `apps/mobile/app.config.ts` writes them into the app's configuration:

<Code
  language="ts"
  filename="apps/mobile/app.config.ts (two marked hunks)"
  code={'// loom: the commit this APK was built from, set by the deploy\'s APK build\nconst loomBuild = repoEnv.LOOM_BUILD_SHA\n  ? { sha: repoEnv.LOOM_BUILD_SHA, committedAt: repoEnv.LOOM_BUILD_COMMITTED_AT }\n  : undefined;\n\n// in `android`: lets the app hand a downloaded APK to Android\'s installer (§5)\n...(loomBuild ? { permissions: ["android.permission.REQUEST_INSTALL_PACKAGES"] } : {}),\n\n// in `extra`: omitted when unset, because a null there is embedded as {}\n...(loomBuild ? { loomBuild } : {}),\n'}
/>

The app reads it as `Constants.expoConfig?.extra?.loomBuild`, the way About already reads `appVariant`, and checks that `sha` is a string before trusting it. Gradle writes the configuration into the APK as `assets/app.config`, so the stamp is checkable on the file itself. An APK built by hand without the variables has no stamp; the app then shows "not recorded" and treats itself as different from whatever the server offers.

**The wire.** Two new members of `LoomWsRpcs` in `packages/contracts/src/rpc.loom.ts`, both needing only the read scope the app's other subscriptions hold:

- `loom.subscribeMobileApp`: a stream whose every value is the whole state below. It is its own subscription, not a new event on `loom.subscribeDeploy`. An older app must keep decoding it after the server has moved on, and a union that gains a member breaks an old decoder.
- `loom.mobileApkUrl`: takes a stored APK's `sha`, returns a signed relative URL and its expiry (§5).

**The contract's one rule:** this shape grows only by optional fields and carries no enumerations. The app that reads it is by definition the one that may be several releases behind the server.

**The state file.** The deploy code writes `mobile-app.json` in the server's state directory, beside `deploy-status.json`, which is written and read the same way. Its schema, `LoomMobileAppFile`, is defined once in contracts: the wire shape plus each APK's absolute `file` path. The server never decides anything; it reads this file, drops the paths and streams the rest.

## 4. The background build

**Machine configuration.** One new optional object in `~/loom-releases/deploy.json`, the file that already holds everything machine-specific. Without it nothing is built and the state file is never written, which is what Jacob's instance and every dev server get.

<Code
  language="json"
  filename="~/loom-releases/deploy.json (addition)"
  code={'"mobile": {\n  "dir": "/mnt/fast/loom-deploy/mobile",\n  "androidHome": "/opt/android-sdk",\n  "javaHome": "/usr/lib/jvm/java-17-openjdk-amd64"\n}\n'}

`unit` is a fourth, optional key, defaulting to `loom-mobile-build`; a scratch store names its own, as `engineUnit` does today. `/mnt/fast/loom-deploy` is the directory `backupDir` already names; it is Carl's, so no `sudo` is needed.

**The decision** is one function, `reconcileMobile(config, releaseDir)` in `mobile.ts`, called from `afterAccept`, from `back()` once Loom answers again, and by the new verb `loom-deploy apk`:

1. Find the newest stored APK that matches the release (§2). If one does: record it as the matching APK, clear any failed build, stop a build in flight, and delete a stored APK newer than it. That last case is an APK built from a release the server has since gone back from.
2. Otherwise, if a build of this same commit is already running, leave it.
3. Otherwise stop any build, write that a build of this commit has started, and start the unit: `node <release>/apps/server/src/loom/deploy/cli.ts <release> apk-build`.

The choice in those three steps is a pure function of four things: the stored APKs, the match, the build on record and whether the unit is active. It is tested as a table.

**The job** (`apk-build`, run inside the unit) makes no decisions:

1. Refuse with under 10 GB free on the mobile directory's disk.
2. Clear `<mobile dir>/build/`, then `git worktree add --detach` the release's commit from the store's mirror into it.
3. `pnpm install --frozen-lockfile`, the command the deploy engine runs for a release.
4. In `apps/mobile`: `npx expo prebuild --clean --platform android`, with `APP_VARIANT=preview`, `T3CODE_MOBILE_UPDATES_ENABLED=0`, `EXPO_NO_GIT_STATUS=1`, `CI=1`, `LOOM_BUILD_SHA`, `LOOM_BUILD_COMMITTED_AT`, and `ANDROID_HOME`, `ANDROID_SDK_ROOT` and `JAVA_HOME` from `deploy.json`. The same variables stay set for the next step, since Gradle writes the configuration into the APK.
5. In `apps/mobile/android`: `NODE_ENV=production ./gradlew assembleRelease --no-daemon -PreactNativeArchitectures=arm64-v8a "-Dorg.gradle.jvmargs=-Xmx8g -XX:MaxMetaspaceSize=2g"`. Steps 4 and 5 are today's hand recipe from `docs/operations/loom-android-apk.md`, with the build stamp's two variables and `--no-daemon` added.
6. Check the APK (below). Any failure ends the job with the build recorded as failed and nothing published.
7. Publish. Copy the APK to `<mobile dir>/apks/loom-<sha7>.apk` through a temporary name. Save the two lists from the source map beside it as `loom-<sha7>.inputs.json`, about 90 KB. Keep the newest other stored APK and delete any older. Write the state file with the new one as the matching APK.
8. Always, including on a stop signal: remove the checkout. The whole output goes to `<mobile dir>/build.log`, replaced by each build.

<Card heading="What a rollback means for the APK on offer" tone="info" badge="follows from the one rule" meta={["no new mechanism", "one call in back()"]}>

**Loom puts a release back by itself.** That happens inside the watch, before after-accept, so no build was started for it and the state file never moved. Nothing to do.

**`loom-deploy back`.** Its last step calls the same decision for the release it returned to. The APK built from the release that was left no longer matches, so the earlier stored APK becomes the matching one. A build still in flight for the left release is stopped, and the left release's APK is deleted.

A phone that never installed the left release's APK is quiet again. A phone that did install it is told "the server went back to an earlier version of the app", with the earlier APK to install (§7). This stays inside Carl's answer that there is "no separate command": nothing is added for a broken app, and the notice only follows what the server runs.

**A fix deployed afterwards** is an ordinary deploy: if the app's code at the fix differs from the matching APK's, it builds.

</Card>

## 5. Where the APKs live and how the phone fetches one

**Kept: two.** The newest and the one before, about 216 MB on `/mnt/fast`, outside every release folder so that release pruning never touches them. The one before is the way back the brief assumes.

**In the app, a tap does three things.**

1. It asks for the link.
2. It turns the relative URL into an absolute one with the connection's `httpBaseUrl`, as `apps/mobile/src/state/assets.ts` does for every other file. The download therefore follows whichever route the app is on.
3. It calls the existing `openAttachmentInViewer` in `apps/mobile/src/lib/attachmentDownload.ts`, with the name `loom-<sha7>.apk` and the APK's MIME type.

That function already downloads to the app's cache with `File.downloadFileAsync` and opens the file through `T3NativeControls.openFile`, an `ACTION_VIEW` intent on a `FileProvider` URI. For an APK, Android answers that intent with its package installer. No new native code.

<Callout tone="warning" title="One thing the app needs that it does not have today">
  Android's installer ignores that intent unless the calling app **declares** `REQUEST_INSTALL_PACKAGES`; the documented symptom is that nothing happens. Today's APK does not declare it, by `aapt2 dump permissions`. The hunk in §3 adds it for Loom's builds only. On the first in-app install Android asks Carl once to allow "T3 Code Preview" to install apps. After that each update is the tap, the download and the confirm the brief describes.
</Callout>

**The hedge.** If the installer returns and the app is still running, the install was cancelled or never opened. The app then offers one more button, "Download in the browser instead", which opens the same signed link with `Linking.openURL`. It is the only alternate path in the plan and it exists because the hand-off is the one step that cannot be run here.

## 6. The way back, and the version code

The brief's third check is an older APK installed over a newer one. Where versions are concerned, Android refuses only an APK whose version code is **lower** than the installed one. Every Loom APK carries version code `1`: `app.config.ts` sets no `android.versionCode`, and the prebuild template's default is `1`. So to Android an older Loom APK and a newer one are the same version. Installing either over the other is the operation Carl has already done with every hand install.

The plan therefore **never lets the code climb**, and enforces it: version code `1` is one of the six checks in §4. An upstream pull that introduced a version code would fail the build loudly instead of breaking the way back quietly.

What that leaves unproven is the app's own data: an older build opening storage a newer build has written to. Android does not guard that and nothing here can. It is step 3 of Carl's check, and the brief's first Still unknown stays open until then.

## 11. Risks, limits and what was left out

- **The app-changed rule has one known gap,** the warning row in §2's drill-down. A build tool that is in no bundle, is no direct dependency and has no patch can change through the lockfile alone. It cannot put different code in the app, and the next real change rebuilds with it.
- **The hand-off to the installer is unproven until step 2.** If it fails, the browser button completes the check and the failure is one more round on the app side, delivered by a hand-installed APK as today.
- **Chrome may warn about an APK fetched over plain HTTP** when the browser button is used. It is a fallback; it was not tested.
- **An app too old to connect is told so, but offered no download.** When a deploy raises the wire protocol, the app's existing screen says "Client not supported … Update your app". The new APK then reaches the phone by a link from an agent, as today. Serving it without the connection needs a download that asks for no sign-in at all, which is a different decision. The protocol number has been raised once in its life.
- **A build that will not open on the phone.** Carl's answer stands: no separate command. The earlier APK is a file under the mobile directory and the rewritten runbook says how an agent hands it over.
- **Two writers of one small file.** The decision and the job both write the state file, through an atomic rename. A deploy landing in the second an APK is published could lose one of the two writes; the next deploy, or `loom-deploy apk`, puts it right.
- **Load.** Gradle with an 8 GB heap on a machine that also runs agents. The unit is low priority and the machine has 62 GB; if it hurts, the heap is one flag.
- **Left out on purpose:** a download progress bar, since the notice says "Downloading"; dismissing the notice; a web or desktop surface; any setting. Also left out is narrowing the rule further by comparing bundle contents. That would cost two to three minutes of bundling on every deploy, to save installs the fortnight has not yet shown to matter.
