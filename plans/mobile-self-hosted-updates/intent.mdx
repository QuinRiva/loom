# The phone app updates itself after each deploy, and tells you when it needs a new install

**Goal.** "Is there a better way to keep the phone app updated rather than having to manually download and install the apk each time?" After a deploy, the Android app brings itself up to the server's version with nothing to install, and it is never behind without saying so.

<Callout tone="decision" title="What you are approving" focus>

- **Day to day.** A deploy publishes the app's code alongside the server. The next time you open the app it downloads that code (about 24 MB) and switches to it when you next leave the app. Nothing to download or install.
- **Still by hand, about once a week.** Some changes live in the APK itself and cannot be swapped this way. You were told that would be the exception. It is not: going by what each one touched, **all 8 upstream pulls since 5 Oct would have needed a new APK**, roughly one a week. After such a deploy the app shows **New install needed** with a download button. You tap it, Android asks you to confirm, and your pairing is kept.
- **A bad update.** One that crashes on opening is meant to be dropped by the updater itself, which reopens the app on the last version that worked. One that opens but is broken is put back from the server, and the phone follows on its next open. Neither needs an APK.
- **Not yet seen on a phone.** No Android device can run on this server, so none of this has run end to end. The first real proof is your phone.
- **Once, on your phone.** One last hand install to switch this on, then a five-minute check, set out under the questions.

</Callout>

**You'll know it works when.**

- A deploy changes the app. You open it, leave it, come back, and Settings → About shows the new build (its commit and time) and **Up to date**. You installed nothing.
- Settings → About always says which Loom build the app is running. Beside it is how that compares with the server: up to date, update downloaded, new install needed, or could not check (with when it last could).
- After a deploy that changes the APK, the app's home screen shows **New install needed**. The download works straight away, and installing over the top keeps your pairing.
- After `loom-deploy back`, or a deploy that Loom puts back by itself, the phone is on the earlier version after its next open.
- An update that crashes on opening does not leave you with a dead app: it reopens on the last version that worked.
- Off the tailnet, the app opens as fast as it does today on the version it has, and checks again when it reconnects.
- **Must not:** ever take an update from upstream's Expo project. Cost you your pairing. Slow the app's start while it waits on a check. Fail or block a server deploy because the app's code failed to build.

**Approaches in play.**

- **The Loom server serves the app's code; each deploy publishes it; the app shows a notice when the APK is too old to take it.** _Your pick. I found nothing against it, and it is unproven on a device._ The app already has the update machinery and it is only switched off. Publishing adds about three minutes of work to a deploy. <Sidenote>Run once in this checkout: 2 min 53 s, and 1 min 54 s on an immediate rerun. Not timed inside a real deploy.</Sidenote>
- Later, if the weekly confirm tap grates: an installer that updates the APK in the background with no prompt. Wins if the weekly tap proves a nuisance. I believe Android 12 and up allows this; I have not verified it.
- Dropped: an in-app APK download for every change. Every deploy would cost a 6 to 22 minute build and an install prompt, against two to three minutes and no prompt.
- Dropped: Obtainium watching a folder of APKs as the whole mechanism. Same cost per change.
- Dropped: an agent pushing the APK over wireless debugging. The link drops on reboot and on a network change.
- Dropped: letting the app take updates from whichever server it is paired with, instead of one address fixed in the APK. It needs the app's protection against an update that bricks it switched off.
- Dropped: trusting the "which APK is this" stamp the build writes by itself. Three builds of the same code gave three different stamps, so the server could never match an update to an APK. Worked out by a separate command instead, the stamp was the same in five checkouts across three deployed versions, and the build accepted it when handed it.

**Decided.** "Yep handoff to a new thread to build out that feature", said of a four-point summary. The server serves updates. A change to the APK-level part still needs a new APK. The app shows a notice with a download link when it does. The server's address is fixed in the APK.

- _Assumed:_ the fixed address is the cockpit's tailnet address, which I take to be the one your phone is paired on (not checked). Off the tailnet there are no updates, and no Loom either; redirect if your phone connects another way.
- _Assumed:_ updates are not cryptographically signed. The address is reachable only inside your tailnet, like the web app's own files, and the update carries app code, no data; redirect if wrong.
- _Assumed:_ new code takes effect when the app next comes back from the background, never mid-session. That is how the existing machinery protects a half-written message; redirect if you want it applied on the spot.
- _Assumed:_ Android only, your one phone, the same "T3 Code Preview" app and signing key as today.

**Not doing.** iPhone. Other users, release channels or staged rollouts. Store builds. Installs with no confirm tap. Changes to pairing or to how the phone connects.

**Your five-minute check, once it is built.**

1. Install the new APK over the top (the last hand install for ordinary changes). Settings → About shows its build and **Up to date**.
2. An agent deploys a small visible change. Open the app, leave it, come back: About shows the new build. That is an update arriving.
3. The agent puts the previous version back. Open, leave, come back: About shows the earlier build. That is a rollback.

**Still unknown.**

- Does the phone take an update from this server at all? Nothing has run end to end. I timed the publish step, measured the stamp, and read the updater's source for the rest. Step 2 above settles it.
- Does the updater accept the tailnet address over plain HTTP, as the app's own connection does? The app's settings allow it. Step 2 settles it.
- Does the updater really fall back after a crash on opening? That is its documented design, read in its source, never seen here. A deliberately broken update on a device settles it, which wants an agent watching (the wireless debugging option) or an emulator.
- How often will **New install needed** fire when nothing in the APK really changed? Counting from git history, over the last eight weeks it would have fired at the 8 upstream pulls and at none of the 246 other changes to main. The count is of what each change touched, not of real stamps. The first month in use settles it.
- Does the no-prompt installer work on your phone? Only worth finding out if the weekly tap grates.
