# A program inside each release, one command and a Deploy control, all around upstream's launcher

Every Loom release carries a small Loom-only program, the **release runner**, which upstream's launcher starts in place of the server. The launcher keeps doing what it ships to do: copy the database, start the new release, and put the old one back if it fails. The runner makes the launcher wait out the **five-minute watch** before it accepts. It keeps the database copy the launcher would delete, and it holds a broken release in place when the deploy was run with `--no-return`. One command, `loom-deploy`, builds a release, trial-starts it on real settings and asks for the switch. Loom's server starts that command from a **Deploy control** and tells every open client what stage the deploy is at. **No upstream updater file is edited.**

Cost: about 1,800 lines of Loom-only code plus tests, a third of it ported from today's tool. About a week of agent work across this repository and the bridge's. One ordinary restart of about 30 seconds at cut-over.

## What it means

- **In the first cut:** the four changes of the brief. A deploy can be started from Loom (web, desktop and the phone app), from the command line, or from Slack. Everyone is warned at the start with a rough time until Loom goes down. A deploy can be run with `--no-return`. Nothing of Loom's deploy is left in the bridge's repository.
- **Not doing,** beyond the brief's own list: a preview of what a deploy would contain before it is pressed; the no-return flag in the Deploy control; going back from the interface.
- **Nothing is deleted** by this plan. The old store's history and database snapshots stay where they are (§8).
- **Done means** §12's end-to-end run passes on a scratch home, and Carl's first deploy on the production machine goes live through the watch.
- **Two open questions** at the end: what a failed pre-switch check does under `--no-return`, and when the bridge's tool loses its Loom target.

## 1. One deploy, start to finish

Three programs take turns. The **engine** is the `loom-deploy` command doing a deploy. It runs in its own short-lived systemd unit, so a restarting Loom, a dropped SSH session or a restarting bridge cannot kill it. The **launcher** is upstream's. The **runner** is Loom's, one per release.

<Steps>
  <Step at="0 s" title="Someone starts it." aside="engine">
    The Deploy control, `loom-deploy deploy` over SSH, or a Slack message the bridge turns into that same command. All three start the same engine unit; a second start while one runs is refused. The status file says `building`, and every open client shows the warning with a rough time until Loom goes down.
  </Step>
  <Step at="~2 min" title="The engine builds a release beside the running one." aside="engine">
    Fetch the store's git mirror, check the commit out into a new release folder, stamp the version, `pnpm install --frozen-lockfile`, `pnpm build`. The estimate is refreshed when the install finishes, which is the step whose length varies most.
  </Step>
  <Step at="+20 s" title="Trial start on real settings and a slice of real data." aside="engine">
    A failure here, including the warning that the settings file could not be read, calls the deploy off. Loom has not been touched.
  </Step>
  <Step at="+2 s" title="The engine asks the running server for the switch." aside="engine, then upstream">
    The server calls upstream's own update request. The launcher either refuses (nothing stops) or accepts, and the server tells every client "Loom is about to restart". Two seconds later the launcher stops the server, copies the database and starts the new release.
  </Step>
  <Step at="down ~40 s" tone="warning" title="The new release's runner starts the server." aside="launcher, then runner">
    Before the server starts, the runner hard-links the launcher's database copy into the kept copies, points the store's `current` link at its own release and writes the "Loom updated" notice. When the server reports it has started, the runner restarts the Slack bridge and writes status `watching`.
  </Step>
  <Step at="5 min" title="The watch." aside="runner">
    The runner probes Loom every 5 seconds. Three failures in a row, or the server exiting, ends the runner. The launcher sees the release fail, restores the database from its own copy and starts the old release, whose runner writes status `put-back` with the reason.
  </Step>
  <Step at="done" tone="success" title="Accepted." aside="runner, then launcher">
    The runner tells the launcher the release has started. The launcher records it as the active version and deletes its database copy; Loom's hard links keep the same files. Status `live`. The runner then starts the after-accept jobs: the manifest Jacob's instance reads, pruning, skill links, the `~/loom` fast-forward.
  </Step>
</Steps>

## 2. The seam with upstream's launcher

The launcher runs whatever executable sits at `<home>/runtime/versions/<version>/t3`, hands it a description of the switch in an environment variable, and talks to it over a pipe. Loom makes `<home>/runtime/versions/<version>` a symlink to a folder inside the release, `deploy/runtime/`, which holds a six-line shell file named `t3` and a marker file naming the version. Upstream prunes old runtime folders but leaves symlinks alone, by its own stated rule. <Sidenote>`prunePinnedRuntimes` in `apps/server/src/cloud/pinnedRuntime.ts`: "leave staging directories, symlinks, and unexpected entries untouched".</Sidenote>

<Callout tone="decision" title="A routine switch asks the running server; the state file is written only when Loom is down">
  Both routes end in the same launcher code. Asking the server means upstream's checks run first, and a refusal leaves Loom running. Those checks refuse a version that is not newer, a release that needs a newer launcher, and a disk too full for the database copy.

  Writing the state file and restarting the service skips them, and a state file the launcher cannot read stops it from starting at all. So the six-a-week path never writes that file. The second route exists because the brief requires that a deploy can be started while Loom is down. It is the same few lines `back` needs.
</Callout>

<Callout tone="decision" title="The store's `current` link names the release that is running, and everything resolves through it">
  Every runner start points `~/loom-releases/current` at its own release. Three things resolve through that link: the service file's start line, the `loom-deploy` on the search path, and the bridge's borrowed message definitions (as today).

  What follows from it. The launcher, the runner it starts first and the command that wrote its state file always come from one release, because `back` hands its last step to the release it returns to (§3.2). Going back therefore takes the launcher and the deploy parts back too. The launcher's own code changes only when the service restarts: a reboot, `back`, or a deploy while Loom is down. The launcher loads all its code when it starts, so pruning the release it was started from does not disturb it; §12 checks that.
</Callout>

**How Loom's parts update themselves, and the way out when one is bad.** They ride in each release. The engine that performs a deploy is the running release's. The runner that watches a release is that release's own, so a bad runner fails its own probation and the launcher puts the old release back. A bad engine shows at the next deploy. The way out is to run the previous release's copy of the command by its full path, which needs no install, or to go back first. <Sidenote>`~/loom-releases/releases/<older id>/deploy/loom-deploy`</Sidenote>

## 3. The parts in this repository

Logic lives in `apps/server/src/loom/deploy/`, a Loom-only folder that is already type-checked, linted and tested with the server. The files that are not TypeScript (two shell files, the service file, the operating notes) live in a new Loom-only top-level folder, `deploy/`. The runner and the command import only Node's built-in modules and upstream's `serviceProtocol.ts` and `serviceLauncher.ts`, and Node runs them from source, as it runs today's tool. They must load when the server's bundle cannot.

### 3.1 The release runner

`deploy/runtime/t3` hands the launcher's `serve` to `apps/server/src/loom/deploy/runner.ts` and every other verb straight to the server's bundle. Two verbs it refuses, with a line naming `loom-deploy`: `update` and `service`, because upstream's `t3 update` would install upstream's T3 Code. The runner, in order:

1. Decodes the launcher's start-up description with upstream's decoder and reads the store's configuration (§7). If the engine deployed this release, it also reads the deploy record the engine left in `deploy/runtime/deploy.json`: who started it, from where, whether `--no-return`, and the change list.
2. **On probation**, which is when the description names a pending update whose target is this version: hard-links the launcher's database copy into the kept copies, beside the launcher's backup folder on the same disk. If the copy is missing it exits, and the launcher puts the old release back. With `--no-return` it now tells the launcher the release has started, so nothing after this can cause a return.
3. Points `current` at its own release if it is not already, and remembers whether it moved.
4. Writes the notice file the server reads once at start. On probation it is "updated" with the change list. When the runner starts as the release that the launcher or `back` returned to, it is "rolled back" with the reason and the time of the switch.
5. Stops leftover agent shells from the previous server, the one step of today's service file that has to run before every start (§9). Then starts the server as its child, from the release's folder, with the configured Node flags.
6. When the server reports it has started: answers "accepted" at once, so the server opens for business. It never passes that report on, because the launcher treats a second one as fatal. It restarts the Slack bridge if `current` moved, and writes status `watching`.
7. **The watch**: `GET /.well-known/t3/environment` every 5 s for the configured 300 s. Three failures in a row, or the server exiting, is a failure. So is a start that takes longer than the configured 240 s to report, which is today's allowance. The bridge is probed on its health address after a 90-second allowance, and three failures in a row are recorded as a bridge fault. A bridge fault fails the watch only when the deploy was started from Slack.
8. On a failure: writes the reason in plain words to the status file and exits. With `--no-return` it instead writes status `held`, stays alive with the server down, and runs the release again when sent `SIGHUP`.
9. When the watch passes: tells the launcher the release has started, writes status `live`, and starts `loom-deploy after-accept` detached. Under `--no-return` the watch still runs and its result is written to the status file; `live` is written only if it passed.
10. On `SIGTERM`: passes it to the server and kills the server 4.5 s later if it is still running.

The engine's steps, each writing its stage and time to the status file:

1. Refuse if a deploy is already building or still being watched (the launcher's state says pending).
2. Fetch the mirror `repo.git`, resolve the commit, `git worktree add --detach releases/<stamp>-<sha7>`.
3. Pick the version: `100.<today in UTC>.<n>` with `n` one above the highest already used today among the staged versions and the active one. Write it into the release's `apps/server/package.json` and into `deploy/runtime/.install-complete`. The web app is not stamped (§7), so `APP_VERSION` is never set for the build.
4. `pnpm install --frozen-lockfile`, then `pnpm build`, in an environment that carries only `HOME` and the configured `PATH`.
5. Trial start. Build a slice of the live database into a scratch home with the new release's `apps/server/scripts/migrate-dev-db.ts`, which reads the live database read-only. Copy in the real `settings.json` and `keybindings.json`, never `secrets` or `environment-id`. Start the built server there on the scratch port, bound to loopback. It passes when three things hold: the server answers within 120 s; its log has no `failed to parse settings.json`; and its log shows the foreign-home guard engaged, which is the device that stops a server on copied data from acting. Stop it by its process id and delete the scratch home.
6. Write the deploy record into the release, list the merged pull requests since the running release for the notice (ported `changes.ts`), and stage the version symlink.
7. Read the live database files once so the launcher's copy is quick (today's tool does the same; it is why its copy takes about 4 s).
8. Switch. If the server answers on loopback, mint a session and `POST /loom/deploy/switch`; a refusal becomes `called-off` with upstream's reason. If nothing accepts a connection on Loom's port across three tries five seconds apart, Loom is down: stop the service, write the pending update through upstream's writer, start the service. A server that accepts connections but does not answer is neither, and the engine stops with that message.

A failure in steps 2 to 6 ends as status `called-off` with the reason. On a routine deploy it also marks the release failed; the newest failed release is kept for inspection until the next deploy, then removed with its manifest record. A refusal at step 8 is not the release's fault, so the release stays and `deploy --release` can retry it.

`after-accept` is started by the runner once the release is accepted, and can never affect that release. In order:

- mark the release `current` in `manifest.json` and the one before it `previous`, with an atomic write, and move the `previous` link;
- keep the current release, the previous one and one more, and the three newest kept copies; remove version symlinks nothing refers to;
- link first-party skills into `~/.pi/agent/skills` and fast-forward the configured checkouts, both ported unchanged;
- append one line to `deploy-history.jsonl` with who started it, from where, how long each stage took and the outcome. The estimate is computed from this file.

### 3.3 The estimate

"About when Loom goes down" is the start time plus the median start-to-stop time of the last ten deploys in `deploy-history.jsonl`, or 150 s until there is history. When the install finishes it is replaced by that moment plus the median of the remaining stages. On the last 30 deploys a fixed estimate missed by a median of 32 s; the refreshed one missed by 18 s and never by more than 42 s. Clients show it as a clock time, "at around 2:32 pm", which needs no ticking display.

### 7.3 Where the database copies go

The live database is on the fast disk. ### 7.4 Numbering, and upstream's update offers

A release's version is `100.<UTC date>.<n>`. The engine stamps it into `apps/server/package.json` in the release folder before the build, so the number committed in the repository stays upstream's. The scheme meets every rule the launcher and upstream's apps apply. It is an exact version in the launcher's sense. Each deploy is newer than the last, and the first move from today's `0.1.7` is accepted. It is above any number upstream will publish, so upstream's apps never see a newer T3 Code to offer.

- **The web app is not stamped.** Its version comes from `apps/web/package.json` unless `APP_VERSION` is set, and the engine never sets it. A page that reported `100.x` would call every `0.1.x` server it connects to (a dev server, Jacob's) out of date. The only skew warning fires when the server is older than the page, which is now never.
- **The setting that makes an unstaged version fail early** is `T3CODE_RELEASE_BASE_URL` in the service file, pointed at a loopback address nothing listens on. One offer survives the numbering: a client that cannot speak the server's protocol asks it to update to the client's own version. That request now fails at its download step with nothing stopped. A release Loom has staged is never downloaded, so Loom's own deploys are unaffected.
- `t3 update` and `t3 service` run through Loom's `t3` are refused by the shell file.

It is a safety net for the settling period. It is not the brief's second approach, today's mechanism moved out of the bridge's repository, which stays Carl's decision if the launcher gives trouble in use.

**The existing store and its history.** The store stays where it is and stays the store: `releases/`, `repo.git`, `manifest.json`, `current` and `previous` keep their roles, which is what lets Jacob's feed and the way back work. `deploy.log`, `spool/`, `state-snapshots/`, `smoke/` and `RUNBOOK.md` are left untouched as history; the bridge's own change moves its worker's queue and log out. New history goes to `deploy-history.jsonl`. Deleting the five old snapshots (33 GB) once the new mechanism has settled is Carl's call and is not scheduled here.

**A launcher protocol change** is the one deploy this procedure does not carry. Upstream has set or raised the protocol number three times, all between 1 August and 15 September. The check in §9 fails at the pull that brings one, and a deploy across it is refused before anything stops. `deploy/README.md` carries the written procedure: stop Loom, copy the database by hand, run the new release's own `loom-deploy adopt`, start Loom. That deploy has no probation and no automatic return, and going back is the same steps with the old release's copy of the command.

## 9. Noticing upstream's changes, and what changes from today

### 9.1 At the weekly pull, not at the next deploy

Three things fail when upstream moves what §2 lists, all before a pull can ship:

1. **Typecheck.** The runner, the command and the server service import upstream's message types, decoders, state writer and update request by name.
2. **The seam test**, `apps/server/src/loom/deploy/launcherSeam.test.ts`. It runs upstream's real `Launcher` class in a temporary home against Loom's real runner and shell file, with a stub in place of the server. Upstream's own `serviceLauncher.test.ts` drives the class the same way, with fixture children. Its cases are in §12. It needs no build and takes well under a minute.
3. **A pinned protocol number.** One assertion that `SERVICE_LAUNCHER_PROTOCOL` is 3, whose failure message names the procedure in `deploy/README.md`.

`docs/upstream-sync/README.md` gains one line under "A pull's runbook": a pull that touches `serviceLauncher.ts`, `cloud/serviceProtocol.ts`, `cloud/selfUpdate.ts` or `cloud/pinnedRuntime.ts` runs that test file by name. The fork's CI workflow is switched off, so the pull's own gates are where this is caught.
