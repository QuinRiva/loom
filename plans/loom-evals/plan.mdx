## 1. Outcome dashboard (Eval 2)

### 1.1 Where it lives and why

<Callout tone="decision">
  Python under `scripts/loom-evals/`, invoked by `bash scripts/loom-evals/run.sh` (and `vp run loom-evals` as a one-line alias in the root `package.json`). Python because the retro scanner and the existing `scripts/prompt-telemetry/` census are Python already, the standard library's `sqlite3` opens a `file:` URI read-only without a dependency, and a fresh worktree can run it with no `vp i`, which a TypeScript script under `scripts/` would need. The directory is measurement scripts, not an eval runner; upstream's `evals/` package arrives at the repository root at the next pull and nothing here collides with it.
</Callout>

**Prior art the brief missed.** `scripts/prompt-telemetry/` (three one-off measurements of October's prompt edits, with baselines) already does read-only census over session files and the database and writes markdown to `.artifacts/`. This plan reuses its conventions and does not fold it in; its skill-read census is a candidate standing metric for a later week once the dashboard exists.

### 1.2 Reading the database

`dashboard.py` opens `${T3CODE_HOME:-~/.t3/cockpit}/userdata/statev2.sqlite` as `sqlite3.connect("file:" + path + "?mode=ro", uri=True)` and runs `PRAGMA query_only = 1` on the connection. Never `immutable=1` (it ignores the WAL and reads stale rows), never a copy, never `.backup`. The queries below each run in about a second on the live 6.6 GB database (measured 2 Nov: the four Loom event types since 7 Oct in 1.1 s, failed tool items in 0.25 s, the usage ledger in 10 ms). The one runaway thread the brief excludes is `9d1afa3a-43e9-4807-9f3a-286313c6d341` (13,582 attention raises in August), held in an `EXCLUDED_THREADS` constant and applied to every query.

**Era.** The orchestration was re-platformed on 7 October 2026. Rows created before carry less: no `loom.humanAuthored` mark on messages, no `ask_user_question` request rows, no `cause` on an outcome, and no `thread.outcome-recorded` event (the sidecar's `last_outcome.eventId` is null on imported rows). The dashboard's default window starts 7 October; a metric that cannot be computed before that prints `n/a before 7 Oct` rather than a number. A thread's model is `json_extract(payload_json, '$.modelSelection.model')` on `orchestration_v2_projection_threads`, shortened past the provider prefix (`cliproxy/claude-opus-5-5` reads `opus-5-5`); its role is `loom_thread_workstream.role`, null for a root, which reads `root`.

Every row is computed for four windows: the ISO week being run, the trailing four weeks, the four before those, and everything since 7 October. The brief's reading rule applies and is printed under the table: a week-to-week move under about 15 points in a rate is noise; read four-week windows.

### 1.4 Where the table goes

`~/loom-evals/` (created on first run), beside `~/loom-retro/`: `dashboard.md` is rewritten each run and `readings/<ISO week>/` keeps the JSON fragments (`metrics.json`, `trace.json`, `escapes.json`) and a copy of that week's `dashboard.md`. `render.py` reads whichever fragments are present and prints one markdown table per metric group with the four windows as columns, then the week's cancel reasons verbatim, then an `Unreviewed` note against any trace check whose first-20 review has not been recorded (§3.4). Nothing is committed: the readings are derived data, recomputable for any week with `run.sh --week 2026-W44`, exactly as `/retro` keeps its runs outside the tree. The two skills that must quote the last two readings read `~/loom-evals/readings/` by path (§8).

## 2. The schema additions

The brief puts three in this change. Grounded in the code, two are built and one is derived.

### 2.1 Cancel reason: built, one optional enum parameter

Thirty-nine cancels since 7 October, 36 of them a parent's `workstream_set_outcome cancelled` (the event's `command_id` reads `command:mcp:<parent>:workstream-set-outcome:…`), one a cascade, none from the UI. Nothing says why. A reason the control plane could fill does not exist: the call carries only `threadId` and `outcome`, and the only candidate inference (the next child under the same parent with the same anchor task) matched 2 of 39.

The chain, each piece named:

- **Contract** (`packages/contracts/src/orchestrationV2.loom.ts`): `LoomCancelReason = Schema.Literals([...])`; `thread.outcome.set` command gains `reason: Schema.optional(LoomCancelReason)`; the `thread.outcome-set` event payload gains the same optional field beside `cause`.
- **Orchestrator** (`apps/server/src/orchestration-v2/Orchestrator.loom.ts`): `setOutcome` passes the command's `reason` through on the `set` cause; the cascade's and the gate's outcome writes carry none.
- **No sidecar column, no migration.** The reason lives on the event in `orchestration_events`, which is where the dashboard reads cancels anyway (§1.3) and where the history rail reads them (below). - **Tool** (`apps/server/src/mcp/toolkits/workstream/defs.ts` `workstream_set_outcome`; `handlers/outcome.ts` passes `input.reason`): the parameter above. A reason on a `done` or `none` is accepted and dropped by the handler, so the description needs no second clause.
- **History rail**, the one place a human sees it, four one-line changes along the existing chain: `apps/server/src/loom/projection/LoomHistoryEvents.ts` (`thread.outcome-set` row gains `reason: Schema.optional(LoomCancelReason)`); `LoomStore.ts` `history` fold (the `thread.outcome-set` case passes `reason: row.payload.reason`); `packages/contracts/src/rpc.loom.ts` (the `outcome-set` member of `LoomThreadHistoryEntry` gains the same optional field); `apps/web/src/lib/workstreamPresentation.ts` (the history `outcome-set` case's `Cancelled` row sets `detail` to the reason when present). The node-based fallback row built from `node.outcome` stays without a reason: `WorkstreamNode` does not change. The web UI's own cancel (`apps/web/src/loom/workstreamState.ts` `setOutcome`) sends no reason; the field is optional so nothing else changes. Mobile renders the same presentation helper.
- **Dashboard**: the cancel row in §1.3 splits by `json_extract(payload_json, '$.reason')` on the event, null before B deploys, so coder A's script runs unchanged before and after.

## 3. Trace checks (Eval 3)

### 3.1 Shape: check functions in the scanner, a corpus driver beside the dashboard

`retro_scan.py` today parses a session once (`parse_session`: every tool call with its arguments and id, every error result, the tool set from `toolsAdded`, human and control turns) and runs five structural checks named in `signals.yaml` (`tool_error`, `repeated_call`, `turn_outlier`, `control_decision`, `missing_tool`). It keeps no successful tool result, no link from a result to its call and no session `cwd`, and checks 1 to 4, 7 and `guard-fired` need all three, so `parse_session` gains the session header's `cwd` and a per-call result record (`toolCallId`, `isError`, the exit code when the text carries `Command exited with code N`, and the first 300 characters) rather than C writing a second parser. The fourteen new checks are functions in the same file, each taking the parsed session (plus the thread's role and report text where the check needs them) and returning its hits (a list of `(timestamp, tool, excerpt)`), declared in `signals.yaml` as `kind: structural`, `scope: session`, `status: seed`, `origin: loom-evals plan (2026-11)`. `scan()` runs them per tree and the digest gains one `## Trace checks` section (one line per check with hits and threads, the same shape as `## Tool-set gaps`); `skills/retro/SKILL.md` §1.1 gains one list item naming it, the only skill-text change, loaded by the retro reviewer alone.

`scripts/loom-evals/trace_corpus.py` is the weekly driver: it builds the thread list from the database instead of a `/retro` manifest and writes `trace.json` plus `hits/<check>.jsonl`.

### 3.4 Reviewing a check before its count is trusted

## 4. Gate escape proxy (Eval 5, tier A, and the census's check 10)

The census's category 10 (gate passed what was later corrected, 2 of 40 threads) and the brief's Eval 5 tier A are one measurement, built once here. The census phrased its signal as a file in a clean gate's diff edited again after a human message to the parent, or a later sibling spawned to fix the same branch; both are candidate kinds in §4.4.

### 4.1 The gates

`gate_escapes.py` selects reviewer rows in `loom_thread_workstream` whose `routes` holds a `loop` route, `json_extract(last_outcome, '$.decision') = 'resolve'`, outcome `clean` or `fixed_inline`, `outcome_at >= 2026-10-07`: **289** on 2 November (loom 183, lease-extraction 80, loom-slack-bridge 11, pi-fathom 7, pi-craft 6, two others). The coder is the loop route's `to`; reviewer and coder models from `orchestration_v2_projection_threads`.

### 4.2 Which files a gate passed

<Callout tone="decision">
  Files are the union of three sources, in this order of trust, with the source recorded per file: **the coder's commits** (every commit in the project's repositories whose message carries `Loom-Thread: <coder id>`), **the coder's checkpoints** (`orchestration_v2_projection_checkpoints.payload_json` `files[].path` for `thread_id = coder`), and **absolute paths in the coder's report** under the project's workspace root. Neither of the first two alone covers lease-extraction.
</Callout>

Grounding, from the repositories on 2 November:

- **Trailers must be read from `%B` with a regex, not `%(trailers:key=Loom-Thread)`.** Lease-extraction's nested `workbench` repository appends a second trailer block (`Fathom-Commit`, `Fathom-Branch`) after a blank line, so git's trailer parser sees only that block: `%(trailers)` found 2 of 610 agent commits since 7 October there, while the trailers are present in every message. In loom, 248 of 250 agent commits on `origin/main` since 20 October carry the trailer.
- **Checkpoints miss the nested repository.** 197 of 262 done loom coders since 7 October have a checkpoint with files; only 50 of 174 lease-extraction coders do, because their edits land in `workbench`, which the checkpoint scope does not cover.
- **Reports carry absolute paths** by the work-model rule, so the third source is extraction of a path shape, not a judgement of prose; a path is kept only if it exists in the repository at the gate's time.

### 4.3 Which repositories to walk

Per project, the git common directories its threads used: `git -C <workspace_root> rev-parse --git-common-dir` plus nested checkouts the project's review snapshots name (`loom_review_snapshots.git_common_dir` by `thread_id`, available from 22 October). Today that resolves to `/home/Carl/loom/.git` for loom; `/home/Carl/fathom-platform/.git` and the bare `/home/Carl/workbench.git` for lease-extraction; `/home/Carl/loom-slack-bridge/.git`, `/home/Carl/pi-fathom/.git`, `/home/Carl/pi-craft/.git`, `/home/Carl/cli-proxy/.git` for the rest. The script fetches nothing and walks `git log --branches --remotes` (never `--all`: `refs/t3/` holds 5,260 checkpoint commits by `T3 Code` since 7 October in fathom-platform alone), reading `%H %aI %an %B` and splitting on a record separator.

### 4.4 What counts as an escape

Two kinds make the **headline rate**, the number that decides whether Carl's hour is spent; a third is reading material only. For each gate resolved at time T with file set F:

- **Kind 1, fix commit** (the brief's): a commit whose author date is in (T, T + 14 days], that touches any file in F (`git show --name-only`), whose subject matches `\b(fix|revert|hotfix|regression)\b` (conventional `fix(...)` included), and whose `Loom-Thread` is neither the coder nor the reviewer.
- **Kind 2, later must-fix** (the brief's): another gate resolved or looped in (T, T + 14 days] whose coder's file set intersects F and whose first verdict was `needs_rework` with `counts.mustFix > 0`.
- **Kind 3, fix child** (the census's form, tightened): a sibling spawned under the gate's parent in (T, T + 14 days] whose title or kickoff brief contains `fix`, `retry`, `regression` or `fresh` and whose own file set (same three sources) intersects F. Written to `hits/escapes.jsonl` with its kind, **not counted in any rate**: a planned later phase matches it too often to be a number.

The census's other form (a commit on F after a human message to the root) is dropped: with 5.4 human messages per goal nearly every later same-tree commit qualifies, and two coders would pick different windows. Every candidate carries its kind and a tag, `same-tree` (the later thread shares `root_thread_id` with the gate) or `other-tree`, because a planned phase 2 in the same workstream touching the same files with a `fix(...)` subject is the obvious false positive. Rates are printed **per kind** (kind 1, kind 2, and their union over gates) and per tag, by reviewer model and by coder model; the dashboard's headline cell is the union of kinds 1 and 2, `other-tree` tag, all models.

`escapes.json`: rows `{by: reviewer_model|coder_model|all, key, window, kind: 1|2|union, tag: same-tree|other-tree|all, gates, escapes}`. `hits/escapes.jsonl`: every candidate with the gate, the commit, the files in common and the subject, oldest first; the first 20 are the reading set the brief asks for, reviewed by the same researcher child as §3.4. The proxy is a lower bound with unknown precision until then, and tier B (Carl's hour) is spent only if the review finds real escapes.

## As built

Built on 2 November 2026 by three coders (commits `fa2131c7ba`, `d61ca2dd81`, `727d30043b`, `36935e7110`) and one integration review (`02cc5a170e`), all gates clean or fixed inline. Where the build departed from this plan, and why:

- **Release labels come from `~/loom-releases/deploy.log`, not `manifest.json`** (§1.3): the manifest holds 16 entries and marks every release before 26 October `failed` after the fact, so it would have labelled most weeks wrongly; the deploy log's successful cockpit promotions and rollbacks give the release actually running.
- **Weeks are local time (AEDT), not UTC** (§1.3, §1.5): the task runs Monday 06:00 local and a UTC week would not have ended; with no `--week` the entrypoint takes the previous complete local week. `trace_corpus.py` imports its window, era and connection helpers from `dashboard.py`, so those names are a contract between A's and C's scripts.
- **The scheduled task takes the model of the thread that creates it** (§1.5): `schedule_task` has no model parameter, so the README's definition is created from a Sonnet thread rather than naming Sonnet.
- **The cancel reason is dropped on `done` and `none` in the orchestrator, not the handler** (§2.1), so every dispatcher behaves alike and the orchestrator-level test holds; the handler passes it through.
- **The stamp is written on the first composed launch, not the first identity write** (§2.2): a fork's first write is a replayed record. `roleOverlay.ts` gained a `roleFiles` helper so the stamp hashes the same role files the overlay reads, and `mcpHttp.testkit.ts` gained a `launchStamps` stub for the typecheck; neither was in the file list. The declared-tools word count moved by 3 (38 to 41 parameter words on `workstream_set_outcome`), confirmed on a dev instance.
- **Seven checks were narrowed to stay structural** (§3.2): `merge-bypass` requires both `.t3code/ship.json` and a `ship` package script (four repositories have the file, one has the script); `forbidden-git` excludes `git add -A <paths>` and requires each segment to start with `git`; `kill-by-pattern` counts `kill $(pgrep|pidof|ps …)` and `pgrep` piped into `xargs kill`, not captured-PID forms; `failed-then-publish` is cleared by any `git status`; `sleep-poll` counts sleeps of 5 s or more; `file-reread` excludes images; `tests-claimed-not-run` excludes "not verified", splits a `verified`-only claim into its own variant (reviewers say it of code they read), and narrows the folded "shipped" claim to a PR or main reference; `moved-text-unwritten` skips sessions with no write call. Hits files carry one line per variant per session with a count, so one noisy session cannot fill a first-20 set.
- **The escape proxy walks `--branches --remotes --not --remotes=upstream`** (§4.3): in loom, 14,877 of 15,831 commits since 6 October are the upstream fork's, and with them every gate "escaped" through someone else's `fix(...)`; rebased copies are deduplicated by author date and subject. Report paths are kept when a walked commit or `ls-tree HEAD` names them, as the stand-in for "exists at the gate's time".
- **The corpus is 2,118 to 2,163 session files, not 2,992** (§3.1): the difference is dev-instance sessions under `/tmp` with no database thread, out of the corpus by construction.
- **First readings.** The first run (week 2026-W44) completed in about 18 s and twice gave identical readings. The escape proxy's headline is 55% of 293 gates (kinds 1 and 2, other-tree), noise-dominated by hot files (`prose.ts` matched 114 times) and other coders' "review round" rework commits; 34.5% with checkpoint-only file matches dropped. It stays `Unreviewed` until the first-20 review, which is expected to narrow it, and tier B is not proposed on this number. `unasked-commit` for roots and `tests-claimed` `verified` for reviewers are expected to be noisy for the same reason.
