# Four PRs: the rule stated once in the plan skill, echoed in one AGENTS.md bullet and two role clauses, enforced by a frontmatter stage in the lint, then applied to the 67 existing plans

**Recommendation.** State the plan lifecycle once, in `skills/mdx-visual-plan/SKILL.md` under a new "The plan's life" heading: a plan carries `status` (`draft | approved | done | dropped | superseded`) and breadcrumb fields (`intent`, `recap`, `supersedes`, `superseded_by`, workspace-relative paths); its body is frozen at approval; the orchestrator appends one `## As built` section at done and sets `status: done`; before drafting, a planner searches the area for the plan it replaces and marks it in the same commit. Paths are workspace-relative (`plans/<slug>/plan.mdx`), the form every brief citation and `consult_manager` anchor already uses, so a breadcrumb is also a path an agent can open. Frontmatter is hidden by the renderer and read raw by agents, which is the audience Carl named ("breadcrumbs are useful for agents that are navigating those files"); an inline body link stays welcome where a human reader needs it, but only the frontmatter pair is checkable. `done` on a plan means the work merged; on a brief it means the owner said it works, which the plan skill already states. ## 2. Where the supersession trigger lives

A lint sees a file; only the planner knows that the plan it is drafting answers a question an older plan already answered. So the trigger is a before-drafting step in the plan skill (search `plans/`, `recaps/`, `explainers/`, `docs/` with `rg`/`fd` on the area's words, and `mcp__t3-code__thread_search` for the discussion; mark what you replace in the same commit), and the review gate on the plan checks that the planner's report says what it searched and found and that a replaced plan carries its mark. The lint then holds the pair honest. This is a check, not a guarantee, and the brief's "Still unknown" carries it: the first plan written in an area that already has one will show whether the habit fires.

The evidence does not support anything stronger. The recap's survey (`recaps/removed-docs-audit/recap.mdx` §3.2) found every discovery channel ends in a file path and that a marker "is cheap only if it is written at the moment of supersession"; the one supersession in loom's history (`plans/2026-07-16-restart-turn-continuation.md`, gutted to a ten-line stub on 21 Sep) was written by the thread that replaced it, at that moment. A scheduled sweep that guesses supersession from code drift would produce false markers, which is worse than none.

## 4. The lint

<Callout tone="decision" title="A pure module with an injected file reader, called from the script">
  `lintPlanSource(source)` in `apps/web/src/components/files/mdx-plan/planLint.ts` takes only the source and is also run in-app by the peek, so link checks that need the filesystem do not go there. They go in a sibling pure module the script calls with Node's `fs`, and that a test calls with a map.
</Callout>

1. **New `apps/web/src/components/files/mdx-plan/planLifecycleLint.ts`** (about 120 lines). Exports `LIFECYCLE_STATUSES = ["draft", "approved", "done", "dropped", "superseded"] as const`, `LINK_FIELDS` as the reciprocity map (`intent` ↔ `plan`, `recap` ↔ `plan`, `supersedes` ↔ `superseded_by`), and `lifecycleFindings(docPath: string, frontmatter: unknown, io: { exists(path: string): boolean; frontmatterOf(path: string): unknown }): PlanLintFinding[]`. Rules, in order: skip entirely unless `docPath` matches `plans/**/plan.mdx`, `plans/**/intent.mdx`, `plans/*.md` or `recaps/**/recap.mdx`; warning "No `status` in frontmatter…" for the three plan shapes when absent; error on a value outside `LIFECYCLE_STATUSES`; error on `status: superseded` without `superseded_by`; for each link field present, error when `io.exists(target)` is false (message names the field and path), else warning when `io.frontmatterOf(target)` lacks the reciprocal field pointing at `docPath` (message gives the exact line to add). Reuse `decodeFrontmatter` by exporting it from `planLint.ts` as `readFrontmatter(source): unknown` (today it is a private `Schema.decodeUnknownOption(fromYaml(Schema.Unknown))`), so both stages decode YAML the same way.
2. **`apps/web/src/components/files/mdx-plan/planLifecycleLint.test.ts`**: a map-backed `io` and six cases: missing status warns; unknown status errors; superseded without target errors; dangling `intent` errors; one-way `recap` warns with the suggested line; a complete plan ↔ intent ↔ recap triangle yields no findings. This is behaviour a bulk pass over 70 files will lean on, which is the "genuinely high risk" the testing rule asks for.
3. **`apps/web/scripts/lint-plan.mjs`** (about +30/−10): accept several positional files (today `file` is the one non-flag argument; `--out`/`--png` stay single-file and error with the usage line otherwise); create the Vite server once; per file, run `lintPlanSource` for `.mdx`, then `lifecycleFindings(relativePath, readFrontmatter(source), { exists: fs.existsSync, frontmatterOf: path => readFrontmatter(fs.readFileSync(path)) })` with paths resolved against the git root (`git rev-parse --show-toplevel`, which `lint-doc.sh` already computes; pass it through as `--root` or recompute); print findings per file and exit 1 if any error. A `.md` file skips the MDX stages.
4. `skills/mdx-doc-core/scripts/lint-doc.sh` needs no change: arguments pass through.
