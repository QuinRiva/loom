# Workstream cards: tidy the tool-call count and show how long the current tool call has run

**Objective.** On the three places Carl watches running agent threads — the *Active now* strip card, the workstream graph node, and the graph's hover card — fold the lifetime tool-call count (`⚒ 75`) into an existing line instead of giving it a row of its own, and add a new at-a-glance figure: what the thread is doing *right now* and for how long (`bash · 17m`). A step that has run past five minutes draws the eye in amber without alarm styling, because a single tool call — or a single model request — running that long is the signature of a stalled or wedged thread, and today nothing on any card distinguishes it from healthy work.

**Decided (Carl's reviews):** the strip card uses the **right-aligned stat column**; the graph node puts the **count in the role strip**; the amber threshold is **5 minutes**; and the model phase between tool calls is timed **exactly like a tool call** (`thinking · 4m`, same format, same threshold). The hover card is drawn once below to Carl's spec — unlabelled rows, title and purpose together, cost and tokens on one line with a separator, the current step in a roomier footer, no interaction hint. The one decision left is the sign-off on that card, in the form at the bottom.

**Done means:** the three surfaces render these layouts; a running thread's card says which tool it is in (or that the model is thinking) and for how long, ticking without a per-card timer or any extra WebSocket traffic beyond one small shell delta per tool completion; the count no longer occupies its own row anywhere; every fact on the hover card appears exactly once; and `vp check`, `vp run typecheck` and the focused `LoomStore` test pass. This document is the approval gate — nothing is built until the form is answered.

The card reads top to bottom as *who → what, since when → what it is doing now → what it costs and how much it has done*. The left column keeps today's sentences (title, `live turn in progress` or the attention label, model); the right column is a stack of figures aligned to those rows — running-for age, the current **step** (tool name and how long it has been in flight, or `thinking · 4m` between tool calls — the same figure in the same format), then cost and count. Under a minute no duration is shown; the step name changing from `read` to `bash` to `thinking` is itself the liveness signal. Past five minutes the duration turns amber; nothing else on the card changes.

## What the three surfaces show today

All three read one object, `WorkstreamNode` (`apps/web/src/lib/workstreamPresentation.ts`), built from the V2 thread shell plus the Loom sidecar fields the shell carries (`OrchestrationV2ThreadShell.workstream`, typed `LoomThreadShellFields` in `packages/contracts/src/orchestrationV2.loom.ts`). The tool-call count is one of those sidecar fields; it was restored to the cards in PR #341 (`e80f227e23`) by appending `⚒ N` to whatever row was nearest.

Two facts about the current data shape matter for everything below. The running-for age on every surface is `formatCompactAge(node.lastActivityAt)`, which for a running thread is the age of `latestRunStartedAt`. And the preview branch on the strip and hover card (`node.preview ? … : getActivity(node)`) is dead on V2: the shell deliberately carries `latestVisibleMessage: null` (`ProjectionStore.ts` line 1457, "thread detail owns message bodies"), so the activity line always shows the generic phrase `live turn in progress`.

**Step title.** The pi adapter (`apps/server/src/orchestration-v2/Adapters/PiAdapterV2.ts`, `emitToolItem`) sets each tool item's `title` to pi's tool name: `bash`, `read`, `edit`, `mcp__pi__rg`, `consult_thread`, `subagent`. The card shows it verbatim, truncated by its slot; MCP prefixes are not stripped in the first cut (the hover card shows the full name).

**Why amber text only.** The card border is the attention channel (`ATTENTION_COLORS`, the ring on the graph node) and must stay reserved for flags a human has to act on. A long tool call is a *look here* cue, not a *stop* cue: `consult_thread` legitimately runs for minutes, and a bash command declared with `# eta: 25m` is healthy at 20 minutes. So the only change past five minutes is the duration's colour — no badge, no border, no pulse (AGENTS.md: no continuously repainting animation). The threshold is a constant `LONG_STEP_MS = 5 * 60_000` in `workstreamPresentation.ts`, not a setting. A `consult_thread` or a declared long bash will cross it; the cost of the false cue is one glance at the hover card, which names the tool and the command.

The drawback this layout carried was the strip's text budget. At 8 px with 0.06 em letter-spacing the 152 px between the paddings holds about 30 characters; today the role is capped at 11 (`truncateLabel(roleLabel, 11)`) and the state word at 20, which already overflows on a gate wait (`getNodeStateWord` → `waiting ⟲2 on Reviewer…`). Adding ` · ⚒ 1204` (9 characters) to the left makes the collision certain. Resolved in two parts:

1. **The gate-wait state word drops its target.** `waiting ⟲2 on Review gate…` becomes `waiting ⟲2` on the node: the target is the loop edge drawn into the node, and the full label stays on the hover card's badge and the timeline drawer. This is a one-line change in `getNodeStateWord`; every other state word (`in progress`, `done`, `held`, `blocked`, `ready`, `cancelled`) is under 12 characters already.
2. **The role yields, not the state word.** The state word is the fact a glance needs (`in progress`, `waiting ⟲2`, `done`); the role is also carried by the hover card and the node's colour. So the strip is laid out right to left: state word first, at most 12 characters (every word after (1) fits); then the count suffix ` · ⚒ N` (omitted when the count is 0); then the role takes what is left — `truncateLabel(role, max(6, 30 − stateWord.length − suffix.length − 2))`, which is the existing 11 in the common case and `ORCHESTR…` beside a four-digit count on a gate wait. The running dot's x-position already derives from the state word's length and needs no change.

## Can the client know the current tool call?

**Not today, and the gap is a single sidecar field.** The workstream surfaces deliberately read only the thread *shell* (`OrchestrationV2ThreadShell`), never a thread's turn items — the sidecar comment in `orchestrationV2.loom.ts` says so: "read with the shell, so a workstream surface never subscribes to a thread's projection". The shell has `activityRunStatus` and `activityRunStartedAt` (the run), but nothing about the item in flight. The thread's turn items are only loaded for the thread that is open in the chat view.

Everything needed is already on the server, indexed, and on the event path that refreshes shells:

- **Tool items have a start time.** Every turn item carries `startedAt`/`completedAt`/`updatedAt` (`OrchestrationV2TurnItemBaseFields`, `packages/contracts/src/orchestrationV2.ts` line 1342). The pi adapter sets `startedAt` on `tool_execution_start` and preserves it across `tool_execution_update`/`tool_execution_end` (`PiAdapterV2.ts` `emitToolItem`, `turn.toolStartedAt`), emitting a `turn_item.updated` with `status: "running"` and `completedAt: null`. Bash becomes `command_execution`, edit/write become `file_change`, everything else (read, rg, MCP tools, web search) becomes `dynamic_tool`.
- **In-flight items are indexed.** The projection table `orchestration_v2_projection_turn_items` has a `status` column and upstream's partial index `orchestration_v2_projection_turn_items_shell_pending_idx` on `(thread_id, run_id) WHERE type IN ('command_execution','dynamic_tool','subagent') AND status NOT IN ('completed','interrupted','failed','cancelled')` — exactly the in-flight tool set. Upstream's own shell read already queries it (`selectShellPendingTurnItemRows`) for the sidebar's background-work pills.
- **The count already rides the sidecar.** `LoomStore.shellFields` → `threadStats` (`apps/server/src/loom/projection/LoomStore.ts` line 545) computes `toolCalls` and `contextUsage` with correlated subqueries and `loomShellJoin.ts` attaches the result as `shell.workstream` to every shell read, snapshot or delta.
- **Tool boundaries already refresh the shell.** `turn-item.updated` is a committed thread event (`ProjectionStore.ts` line 2383). The shell stream (`ws.ts` `projectShellItems`) re-reads the shell of every thread with an event in each 50 ms window, and `skipUnchangedThreadShells` (`ShellStream.ts` line 212) drops the delta when nothing but `updatedAt` changed, resending an unchanged shell at most every 5 s. `workstream` is part of the compared schema, so a sidecar field that changes is sent and one that does not is suppressed.

### The addition: one field on the sidecar

The card and the footer draw from four values (kind, since, title, command), so one field carries all three surfaces. Because the model phase is shown exactly like a tool call, `kind: "model"` is rendered as the step title `thinking` and otherwise follows the same path (same formatter, same threshold).

### How the timer ticks on the client

The decisive case is a tool call that produces no output for ten minutes: there are no thread events, so no shell deltas, so the cards never re-render and any duration would freeze at the value it had when the tool started. The client must own the clock.

- **Cards tick once a minute, on one shared timer.** `useNowMinute()` (`apps/web/src/hooks/useNowMinute.ts`) is a module-level 60 s `useSyncExternalStore` clock the sidebar already uses for its relative ages. The strip and the graph each subscribe once; a minute tick is one React commit for the strip (N cards) and one for the graph, whose layout is memoised on structure (`WorkstreamGraph.tsx` line 126) so only the node text re-renders. No per-card timers, no `requestAnimationFrame`, no CSS animation. Durations are computed from `Date.now()` at render (as `formatCompactAge` does), and under a minute no duration is drawn, so the minute cadence never shows a stale seconds figure. The running-for age gets the same tick for free — today it only updates when a shell delta happens to arrive.
- **The hover card ticks per second, by DOM write.** The card mounts only while hovering. A `StepElapsed` span updates its `textContent` from a 1 s interval exactly as `AgentElapsed` (`apps/web/src/components/chat/AgentElapsed.tsx`) does: zero React commits per tick, torn down on unhover.
- **Boundaries are immediate.** The label flips from `bash` to `thinking` the moment the tool-end delta arrives; the tick only advances durations between deltas.

## Scope and non-goals

In the first cut: the three web surfaces (desktop wraps the same bundle); the pi adapter path, which is the only driver the registry ships. Out of scope, deliberately: a user-facing threshold setting (a constant is enough until a second person asks); stripping MCP prefixes from tool titles; showing the current step on the sidebar row or the agent-facing `workstream_list` render (both read the same shell field and are one-line follow-ups once the card vocabulary is settled); a "no output for N minutes" signal that would track streaming tokens (ruled out above because it would move the shell per token); honouring a bash command's declared `# eta` to suppress the amber (a later refinement if the amber proves noisy). Mobile has no workstream surfaces.

## Risks

- **Stale in-flight item.** If a server crash leaves an item `running` in a run the recovery path later marks finished, scoping to the *active* run hides it; if the run itself is stuck, the step shows as long — which is the truth.
- **Five minutes is a low bar.** `consult_thread`, a declared long bash, a subagent, or a long model answer will all go amber routinely. The amber is text colour only and the hover card names the tool and command, so the cost of a false cue is one glance; the constant is one number to raise if it proves noisy.
- **Minute cadence under a minute.** Durations under 60 s are not drawn, so a card never shows a seconds figure that is up to a minute stale. If Carl wants seconds on the cards, the sidebar's per-row 1 s `WorkingDuration` is the precedent and the cost is one `setState` per running card per second — say so in the form's write-in.
- **Node strip budget is an estimate.** 30 characters at 8 px is derived from the existing 4.4 px/char the running-dot offset already assumes; the preview fixture with `ORCHESTR… · ⚒ 1204` beside `waiting ⟲2` is the check, and the budget constant is one number to tune if it clips.
- **Partial-index reliance.** The in-flight lookup is index-only only while its predicate matches the upstream index's WHERE verbatim; an upstream change to that index would make the query a thread-scoped scan, still bounded by the thread's items, and the `ProjectionSettlement` test pattern already guards upstream's own use of it.
