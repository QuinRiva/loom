# Query author, from the file or diff you are reviewing

**Build Query author in three slices, run one at a time: the model-read text, then contracts and server, then the web.** On the author card, each thread that wrote the selected lines gains Query author beside Open thread. Pressing it and typing a question forks that thread into a read-only copy that answers in the main window, with the file or diff beside it as it was. The asked lines keep a mark, Promote leaves a comment about them in the real coder's composer, and Back to review returns.

It works the same in the **whole-file change view**, where the owner reviews, and in the **Diff panel**. Nothing is built per view: both already draw the card through one slot and the author colours through one stamping hook, and this plan extends those two.

The plan makes **three bets**. A code query is **the existing query-thread role with a second subject record**, so the read-only posture is inherited, not rebuilt. **Both views are served by the two pieces they already share.** And the **model-read text is written and reviewed first**, by its own author, so no coder writes or edits text a model reads.

## 1. What the reviewer does

Three words carry one meaning throughout. The **reviewing thread** is the thread whose file or diff is being reviewed. The **author thread** is the thread a commit names. A **query thread** is the read-only, visible fork of an author that already exists for plans and recaps. <Sidenote>`docs/internals/glossary.md`, Loom side threads.</Sidenote>

<Steps>
  <Step at="select" title="He selects lines in a changed file opened whole.">
    The card opens as it does today, one row per thread that wrote the lines, with earlier authors below. Each row that names a single thread now has two buttons.
  </Step>
  <Step at="ask" title="He presses Query author on a row and types a question.">
    The card shows a question box. Sending calls one RPC, `loom.codeQuery`. The server checks the commit, reads its thread itself, forks that thread into a query thread or reuses the current one, and sends the question as his own message with the lines attached.
  </Step>
  <Step at="answer" title="The main window moves to the query thread.">
    The same file is open beside it, on the same comparison and the same selected lines, because the query thread's panel follows the reviewing thread exactly as the author's does after Open thread. The author thread gains no message and runs no turn.
  </Step>
  <Step at="mark" title="The asked lines carry a mark, in both views.">
    A mark in the line-number gutter, drawn by the hook that draws author colours. Selecting marked lines lists the questions on the card, each with a button that opens the query thread at that question.
  </Step>
  <Step at="promote" title="He presses Promote on an answer.">
    The existing button and tool. The query thread writes one comment; it waits in the real coder's composer as an ordinary line comment on those lines.
  </Step>
  <Step at="back" title="Back to review returns in one click." dashed>
    The button already in the thread header for any thread that follows a review. The reviewing thread's own panel state was never written.
  </Step>
</Steps>

## 4. A query thread about code

<Callout tone="decision" title="One query-thread role; code gets its own subject record, RPC and events beside the document ones">
  A code query is created exactly as a document query is: `launchDraftFork` spawns a goal-less Loom root forked from the author, on the author's project, worktree and model. It takes the **same role**, `DOCUMENT_QUERY_ROLE`. Everything that makes a query thread safe and visible already keys on that role, or on the flag the composer derives from it, so a code query inherits all of it. What differs is the subject. The sidecar gains a second field, `codeQuery`, null on every other thread, and which field is set says what the thread is about.
</Callout>

**The question names its commit.** The fork is shown lines, and has to know which commit of its own they came from. The line-form `review-comment` record carries a file, a range and a hunk, and nothing about commits, and the sidecar's `commitSha` and `ownerShas` are never read by a model. So the message text carries it, between the lines' chip and the question, in one sentence the reviewer also sees in his own bubble:

- always, the named commit's short id and subject;
- when a later commit now owns the lines (a question from an earlier-author row), those commits' short ids and subjects too, with the statement that the hunk shows the lines as they are now, not as the fork wrote them.

That sentence is model-read text, so slice 1 owns it. `codeQueryOverlay.ts` exports a second pure builder, `buildCodeQueryQuestion({ reference, question, commit, owners })`, which returns the message text. Slice 2's dispatch and slice 1's eval cases both import it, so the eval reads the text a real fork will, and nothing is assembled twice. The subjects come from the blame service: `ReviewAuthorship.commitAuthor` takes the named commit and the `ownerShas` together and returns each with its subject.

**Why the reuse key is the author's run.** A document's query thread goes stale when the document is rewritten. A code query goes stale when the author has done more work than the fork knows. For a finished coder, the usual case in a branch review, the key never changes: every question about any of its files lands in one thread, and the prompt cache is warm after the first. The latest run is the one `launchDraftFork` forks from; that selection is lifted into one helper in `handoffDraft.ts` so the key and the fork cannot disagree.

**What a question costs.** The fork is spawned with the author's model selection, so it answers on the model the coder ran on, and its first turn reads the coder's whole context. For a coder that finished a while ago the prompt cache is cold and that read is at the uncached price. The brief records this in the owner's words; the plan adds no cheaper path, because a different model could not read the author's cache at all.

**Promote.** The RPC, `loom.documentQueryPromote`, and the tool, `document_query_promote`, keep their names. Both handlers look for the question in whichever subject field the thread has. For a code query the tool dispatches `thread.code-query.promote` with the text; the lines come from the question.

A promoted code comment is a plain line comment and carries no link back to its query thread. Document promotions have one, but for lines it would mean a new field on the review-comment record stored in every message's context, spliced into upstream's `composerContext.ts`, and hunks in five more upstream files. The brief asks only that the comment be waiting in the coder's composer. The way from the query thread to the author's composer already exists, as the receipt row under a promoted answer, and is derived from the sidecar.

The control is there because this overlay invites overcorrection: told that a shell command which changes a file is refused work, a fork may stop running `git log` or reading its own transcript.

The last case needs a check that reads the whole attempt. In this harness `bash` and `edit` are looking calls: they never decide, and only the deciding message is graded. A fork that committed through bash and then ended its turn politely would be graded on its closing text alone. So that check kind reads the attempt's `prior` calls as well as the deciding message, as the existing notify check does, and fails on any writing call among them. Which shell commands count as writing is decided from the command text, and the grader's own test pins the list.

Each case declares the promote tool as loaded, through the slot the harness already has for tools a thread gains mid-run. The document case runs on the base text and the new, compared with `--baseline`; the three code cases run on the new text only, since their overlay does not exist before it. The cost is proxy quota only.

## 6. The web

**Asking, on the card.** Query author on a row puts the card in ask mode for that row's thread and commit: a text box and Ask. The box is drawn inside the card with the existing `DiffCommentAnnotation` component, which already takes `placeholder`, `submitLabel` and `pending`.

The box is bound to the viewer's draft text, which the slot's actions now pass through with its setter. That is the two marked lines in `AnnotatableCodeView.tsx`, and it buys two things. A card with a question typed into it is not replaced by a stray selection, by the rule the viewer already applies to a typed comment. And the text survives a switch between Comment and Query author.

Ask calls `loomCommands.codeQuery` with what `buildDiffReviewComment` gives for the selection, the row's commit, the view's section, and the reviewing thread. On success it does four things in order, as `LoomMdxAnnotationLayer.tsx` does for a document:

1. clears the text;
2. writes the follow, with the query thread as the destination and the question's `askedAt` as the instant to land on;
3. waits for the query thread's shell;
4. navigates.

In the whole-file view the follow carries the file; in the Diff panel it does not. On failure the server's reason shows on the card and the text stays.

**Marks, through the stamping hook.** A derived atom over the environment's thread shells lists the questions of live code-query threads, as `documentQueryPins.ts` does for documents. `useLoomAuthorship` hands the stamps those with an `ownerShas` entry among the commits of its current answer. The post-render hook sets one more attribute on the gutter cell of each added line from a question's `startLine` to its `endLine`, and static CSS draws the mark.

A line is marked only while the authorship answer still gives that line to one of the question's `ownerShas`, so a mark never sits on lines a later commit has rewritten. The owners are recorded apart from `commitSha` because a question put to an earlier author is about lines a later commit now owns. Both views call the hook, so both get marks with no change at either call site. No row is added or resized.

A mark cannot be clicked: it is plain DOM inside the viewer's shadow root. So the card does the navigation. When the selected lines hold marks, the card lists each question under its author's row ("Asked here ‹when›") with a button that parks a jump at `askedAt`, writes the follow and opens the query thread.

**The query thread itself.** `DocumentQueryHeader.tsx` shows the "read-only fork of" chip and Author thread for either subject, and Open document only for a document. Back to review is already beside it. `DocumentQueryPromoteButton.tsx`, the receipt row in `loomTimelineRows.ts`, and the label and counts in `WorkstreamGraph.tsx` and `WorkstreamQuickFacts.tsx` read whichever subject field is set.

**Promote, on the client.** `useSeedPromotedQueryComments.ts` turns a code promotion into a plain `line` review comment built from its question's stored position and excerpt, seeded once into the author's composer under the promotion's id. Nothing else about review comments changes. Where the author's own panel shows the same view of the same file, the comment also draws under the lines, since a line comment restores by its section and selection.

<Callout tone="info" title="What the query thread's right panel does, and where another goal meets it">
  A query thread is a new thread the main window moves to. Under the follow as built, its panel takes from the reviewing thread: the comparison and base, the Authors toggle and thread filter, the selected file and lines, the panel's width and the Files list's open folders. Its tabs and maximised state are its own, so it shows the one tab the follow opened (the file, or the Diff panel) plus whatever Loom seeds on a new thread. Back to review or the ✕ ends the follow and the thread's own panel is as it was.

  A separate goal, "Right panel carries into child threads", owns how width and the Workstream tab carry from a parent to a child. A query thread is not a child (it is a root forked from the author), but it is entered the same way. This plan adds no carrying mechanism. The one point both touch is `useReviewPanelKey` at `ChatView.tsx`, which chooses whose stored width a thread shows: a review follow should keep precedence there while it exists.
</Callout>

## 8. The live pass, and the summarised coder

Slice 3 ends with one live pass on a dev instance. The free Replay provider cannot run in Loom (issue #579), so every turn here is a real pi turn. The fixture keeps that cheap: a small branch in a scratch worktree, where one coder thread on pi's cheapest model makes two commits, a second rewrites three of its lines, and one line is left uncommitted. A query thread answers on its author's model, so these forks are cheap too.

Run the journey twice, first in the whole-file view, then in the Diff panel:

1. Select lines the first thread wrote. Press Query author on its row, type a question, send. The main window is the query thread, with the lines as a chip and an answer. Beside it is the same file (or diff), comparison and selection.
2. Open the author thread: no new message, no new run.
3. Back to review. The asked lines carry a mark. Select them: the card lists the question, and its button opens the query thread at it.
4. Ask a second question on other lines by the same thread: no new thread. Select the lines the second thread rewrote. From its own row, ask: a second query thread, forked from the second thread. From the earlier-author row, ask: the question lands in the first author's existing query thread, and those lines are marked too.
5. In the query thread, ask it to change a line, then to commit a one-line fix from the shell. It declines both; `git status` and `git log` are unchanged.
6. Promote an answer. The query thread shows the receipt row naming the author. Open the author: one line chip on those lines in its composer. Delete it and reload: it stays gone.
7. Open the other view on the same file: the mark is there too.

Then, once, the first build's timing check on one large changed file with Authors on and off, to show marks cost nothing measurable.

**The summarised coder.** This is the brief's remaining unknown. A cheap model's answer would not settle it, so this one question is asked of a real coder on the model it ran on.

On a copy of the cockpit database, pick a coder thread whose pi session holds a `compaction` entry later than one of its own commits; `apps/server/src/loom/context-viz/piSessionContext.ts` reads that entry. Ask about lines from that commit, and compare the answer with what the thread wrote in the turn that made it. It is one full uncached read of a long context on that coder's model: the dearest single turn in this plan, and the reason it is asked once.

Before asking, confirm two things. Where the fork's session file is written, so the copy never writes beside the live install's sessions. And that `$PI_SESSION_FILE` in the fork holds the author's turns from before the summary.

## 9. Risks, and what goes to the owner

<Callout tone="risk" title="What could go wrong">
  - **A query thread can still write through bash.** The guard refuses pi's `edit` and `write`. A `sed -i` or `git commit` in a shell is stopped only by the overlay's instruction, as for document queries today. It matters more here, because the fork is a coder in the worktree under review. The paragraph under this box says what the plan does about it.
  - **The fork answers on the author's model.** A question to a coder that ran on a dear model costs a full read of its context at that model's price, cold if it finished a while ago. The brief has the owner's words on this; it is restated as an Assumed line because the model is a fact he has not been told.
  - **Marks depend on the query thread's shell being on the client.** Shell snapshots trim older settled roots, and a superseded query thread is archived, so its marks go. A mark is a marker for the review in progress, as document pins are.
  - **Marks are anchored by line number.** A later commit that inserts lines above an asked range, without rewriting it, shifts the mark onto its neighbours inside the same author's block. When the author itself commits again, the next question starts a fresh copy and the old marks go, so the case left is another thread committing above. Accepted for a marker of the review in progress.
  - **A follow from a different checkout.** In the whole-file view such a thread is shown no authors, so no card and no Query. The Diff panel is unaffected. Rare: it needs stacked branches.
  - **Text first means the overlay is written before a fork has run it.** The eval cases and the live pass are its checks; one round back to the text author is planned for (§8).
  - **Upstream churn in `AnnotatableCodeView.tsx`.** Held to two marked lines inside the existing slot call.
</Callout>

**Bash writes.** The overlay says in terms that a shell command which changes a file is refused work by another route. An eval case, graded over every call in the attempt, and the live pass both ask the fork to commit. A commit it did make would carry its own trailer and show as its own block, so it would be seen. A read-only sandbox for the fork is the real fix; it is its own piece of work and would serve document queries equally.

**Added to the brief as Assumed, for the owner to redirect.**

- The marker is a mark in the line-number gutter, and selecting marked lines lists the questions on the card with a way to each answer. The first plan's mockup drew a "1 question" pill at the end of the line.
- A copy answers on the model its coder ran on.
- Asking again after the coder has done more work starts a fresh copy; the older copy is archived and its marks go. The usual way to meet this is his own loop: ask, Promote, send the comment, the coder fixes. The next question to that coder is then a fresh copy, and every mark from the earlier one is gone, in every file.

**Nothing in this plan needs a Goal, check, must-not or Decided line changed.**
