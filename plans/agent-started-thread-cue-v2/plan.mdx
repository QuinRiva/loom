# A rail on the row for threads an agent started

**Recommendation: a 2 px coloured rail down the left edge of the sidebar row** — accent for a thread an agent started on its own, a muted grey one for a thread you asked for with `/handoff`, nothing for the threads you started yourself. It takes no space inside the row, so it reads the same on the tall cards in Active and the slim rows in Working and Settled, and a stripe scans down a long list faster than anything in the title line. A stripe cannot say *why*, so it travels with three companions: the hover card names the thread that started it and opens it, the row's accessible name says "started by an agent", and the thread's Workstream panel gets a "Started by ‹title›" chip. **About a day**: the web cue plus one small server change so the sidebar knows *which* thread did the starting, and whether that was a `/handoff` you typed.

The one bet is a colour-only mark on the row with the words one hover away, over a bot glyph beside the title — the glyph is the strongest alternative, louder and self-explaining, but it spends the slot the unsent-draft pen already uses and shortens every marked title. The six options are compared in sections 1 and 2; the choice is yours in the form at the end.

  A 2 px stripe inside the row's rounded edge, 6 px short of top and bottom. It is the only option that marks every row variant without taking a pixel from the title, the branch or the badge cluster, and the only one whose mark is in the same place on a 78 px card and a 36 px slim row — which is what makes a column of rows scannable. The row's left edge already carries the drag-over ring and the multi-select tint; the rail is placed inside the edge and shorter than it, so the ring still reads as a ring around a stripe. Settled rows dim the rail with the favicon and restore it on hover, so the shelf stays quiet.

The first branch of that function needs a fact the row does not carry today — section 4. Without it the rule still marks every agent-started thread correctly; what it cannot do is tell your `/handoff` from an orchestrator's own handoff, or name the starting thread.

## 4. What the server knows, and the one fact it lacks

Every row the sidebar draws is a pure function of the thread's **shell** — the small per-thread record the server streams to every client — so the question is what the shell carries. It already carries `createdBy: "user" | "agent" | "system"` on every thread, and the `goal_handoff` tool creates its new thread as `createdBy: "agent"`. **"An agent started this" is on the wire today, at no cost.**

What is not on the shell is *which* thread did the starting. The durable trace a handoff leaves (`handoffDestinations`) is written on the **caller's** record — the orchestrator lists where it handed off to — and never on the new thread. The sidebar could walk every live thread's list backwards to find itself, but that fails as soon as the caller is archived, and the hidden helper behind your `/handoff` is archived the moment it has done its job, which is precisely the case the rule needs to recognise.

<Callout tone="decision">
  **Stamp the new thread with its origin.** One nullable field on the thread's existing Loom sidecar record, written by the projector when it folds the handoff event it already handles — no new event, no new command, no extra traffic (it rides the per-thread shell row that already refreshes on the thread's own activity). One migration backfills the threads already in your database from the callers' existing lists.
</Callout>
