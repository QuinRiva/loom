# Pull 10 strategy — a routine cadence pull with one structural prelude

Loom is a Pi-first fork of `pingdotgg/t3code`. Pull 9 re-platformed Loom's orchestration layer onto upstream's Orchestration V2 and landed on `main` with `docs/upstream-sync/UPSTREAM_BASE` = `9bd1d8009a` (2026-10-06). Since then upstream has shipped **554 commits** (`upstream/main` = `58d253231d`, 2026-10-12, v0.0.46-nightly) and Loom has merged ten PRs (#345–#368). This plan decides how to merge those 554 commits into Loom while keeping Loom's own features, following the sync doctrine in `docs/upstream-sync/05-strategy.md`.

**Done** means an orchestrator can write the runbook (`docs/upstream-sync/35-cadence-pull-10-v0.0.46-nightly-20261012.md`) and spawn the workstream in the section "Workstream graph" below without further design work. Carl has ruled on every question the plan raised (section "Carl's rulings"); the one he did not settle up front — how Loom's tools are shown to Pi agents — is settled inside the pull by a measured prototype with stated adopt/reject criteria.

<Callout tone="decision">
**The recommendation.** Pull 10 is a **routine single-pass cadence pull** in the shape of pull 8 (doc 27), not a phased re-platform like pull 9. The trial merge produces 104 conflicted files and 191 conflict markers — pull-8 sized — and upstream has not replaced anything Loom's orchestration layer stands on. What makes it more than a textbook pull is **one structural move upstream made** (every provider, Pi included, now lives in its own `packages/provider-*` package, so Loom's Pi hooks must move with it) and **four places where upstream now expresses functionality Loom built its own way**. Carl took upstream's mechanism for three of them (Pi usage reading, thread links, pull-request listing), and asked for the fourth (upstream's on-demand tool discovery) to be prototyped and adopted only if it performs well. The pull runs overnight on Claude quota that would otherwise expire at the 07:00 and 08:00 weekly resets, and merges itself once every automated gate is green; Carl verifies on the deployed instance, and deploying stays his call.
</Callout>

## What changes for Loom's users, and what is at risk

Carl drives Loom all day through Pi threads, the workstream graph, goals and the task tree, MDX plans, and the sidebar. After pull 10 lands, the visible gains from upstream's 554 commits are:

- **Pi runs better.** Upstream fixed nine Pi-adapter defects Loom currently carries: workspace skills and slash commands are discovered again, selected skills load without dropping prompt text, Pi's native session rewinds are reconciled, extension approvals expire and cancel, thinking defaults are per model, tool images and structured results survive, shell exit codes and native abort outcomes are preserved, and known read-only T3 tools need no approval.
- **Find in thread.** Cmd+F over messages and plans in the open thread (upstream #10439), plus find-in-diffs — complementary to Loom's cross-thread content search, which stays.
- **Usage page.** Loads in under a second, filters by provider, and reads Pi's native sessions — upstream now ships its own Pi usage reader, which replaces the one Loom wrote (Carl's ruling).
- **Pull requests.** Guided reviews, review guides that agents can write and read, quick actions per host, PR actions that confirm in place, and GitHub access through the API instead of the `gh` CLI.
- **Connections and permissions.** Scoped permissions (filesystem read/write, source-control write, preview control, diagnostics, environment administration), hosted agents (ChatGPT, Claude Code) signing in to the T3 MCP server over OAuth, and every MCP tool declaring who may call it.
- **Everyday web polish.** Reopen closed tabs, drag to reorder right-panel tabs, a thread-details shortcut, parent-thread breadcrumbs, grouped keybinding settings, block-level Markdown in the composer, MCP apps rendered inline, the browser preview running on the environment server, perf fixes to the timeline, diff panel and sidebar.
- **Platform.** Effect 4.0.2, typechecking with `tsc-rs`, Claude Haiku 5.5 in the catalogue (Loom already rolled this forward), and roughly eighty mobile commits that Loom takes verbatim because Loom carries nothing in `apps/mobile`.

What is at risk is the same list every pull puts at risk, and it is bounded: the Pi driver's Loom hooks (quota classification, session-id sanitising, steer stash, thread-fork cut, per-turn spend, the bundled patched `pi`), the workstream MCP toolkit's registration on the bridge, Loom's thread-mention chips, the file-chip and artefact viewer in previews, the Pi-first settings defaults, and the sidebar seams. Each is named in the zone tables below with its disposition.

## The structural prelude: Loom's Pi code moves into `packages/provider-pi`

### Adopt or reject

An arm is **adopted** only if it meets all five:

1. **No missed submit.** Every run of the submit journey succeeds, on Opus and on Sonnet.
2. **No forbidden reach.** No run of any journey calls a withheld tool, or calls `ask_user_question` on a thread nobody has written to.
3. **Reliability no worse.** Each other journey succeeds in at least four of five runs, and never below the baseline's count. No failure leaves wrong state behind, such as a side-effecting wrong tool or a child spawned without a brief.
4. **Cost no worse.** Median extra turns per journey is at most one over the baseline. Median total tokens per journey is at most 10% over the baseline; the expected direction is lower.
5. **Prompts barely change.** Role prompts pass unchanged, or need one small text change that a re-run of the failing journeys then passes. Who may author that text is set out below.

**The text-change path.** If an arm meets criteria 1–4 except for failures caused by prompt text, P returns a **conditional verdict** naming the failures and the text at fault. The Fable prose child then writes the change in P's worktree. Next, P, or a fresh researcher child if P has finished, re-runs every failing journey five times on the changed text. Failure modes caused by text that still names `enable_toolset` are the likely case. A re-run that meets all five criteria turns the verdict into an adoption. A failed re-run, or no Fable quota to write the change, means **reject**. Nothing is adopted on text that nobody measured.

If both deferred arms qualify, **all deferred** wins: it leaves less Loom machinery and matches upstream. Otherwise the qualifying arm wins. If neither qualifies, the verdict is **reject** and direct exposure ships. An inconclusive result counts as reject, so the merge is never held for a judgement call. The journey table and failure log go to the runbook's decision log either way, and a rejected result becomes a follow-on task carrying its evidence.

### Heartbeat sub-thread

This follows Carl's standing preference for overnight work. The orchestrator spawns one heartbeat child with S1: Sonnet through an explicit `modelSelection` on instance `pi`, no editing. Every 30 minutes (a `# eta:`-declared `sleep` between checks) it reads `workstream_list`. It reports to the orchestrator, by consult or notify, when:

- a child has had no activity for 45 minutes with no tool in flight;
- a child raised an attention flag;
- a node went quiet with a synthesised report;
- a thread is parked on a quota error.

It reads the router state only when it sees a stall or a phase boundary, never on a timer. It ends when the shipper finishes.

**If a seat hits its 5-hour limit anyway:** its sessions get 429s and the proxy moves them to another seat. Loom's quota classifier parks the affected threads, and `autoResumeLimitedThreads` resumes them. The heartbeat checks that they did resume, and the orchestrator drops to serial for the next phase.
