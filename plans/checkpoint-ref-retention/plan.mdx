# Checkpoint-ref retention policy

**Objective.** Bound the growth of `refs/t3/checkpoints/*` refs in project repos. Today they are created on every turn and deleted only on revert, so they grow without bound — on the live cockpit repo they are 6,831 of ~8,900 refs (77%, `packed-refs` ≈ 940 KB, growing ~2.8k refs/month). This plan establishes what revert and diff viewing actually need retained, compares retention policies, and proposes the smallest mechanism that bounds growth: a checkpoint-ref sweep folded into the existing `WorktreeReaper` 30-minute pass, deleting a thread's whole ref namespace once the thread is terminal (deleted / done / cancelled / archived) and has been quiet past a grace window.

**Done means:** the sweep ships behind the existing reaper cadence, steady-state ref count on the live repo settles at roughly the live-thread share (~1.6k today), the 6.8k backlog is reclaimed on the first pass after an owner-approved rollout, and reopening an old thread degrades gracefully (documented below) rather than erroring loudly or corrupting anything.

<Callout tone="decision">
  **Recommendation: Option A — terminal-state + grace sweep in the existing `WorktreeReaper` pass.** One new pure selector module, one new `for-each-ref` listing op, one small SQL read, ~30 lines of integration. No new periodic machinery, no migration, no event-flow changes, and the first pass after deploy performs the one-off backlog cleanup (owner-gated, dry-run command included).
</Callout>

## How checkpoint refs work today

All refs live under `refs/t3/checkpoints/<base64url(threadId)>/…` in the project repo's **shared** `.git` (worktrees share the common ref store — which is why one repo accumulates every thread's refs, and why refs survive worktree removal and fan-in repointing). Two ref kinds per thread (`apps/server/src/checkpointing/Utils.ts`):

    ["…/baseline/<n>", "turn n starts (start-of-turn tree snapshot)", "adjacent turn-diff view (preferred from anchor), capture of turn n's diff", "revert past it — otherwise never"],
  ]}
/>

So a thread accrues ~2 refs per turn forever. The read model (`projection_threads` + per-thread checkpoint rows in SQLite) stores the ref *names* and the per-turn file summary chips; the full patch text is **not** persisted — `checkpoint_diff_blobs` exists as a table but is written by nothing and is empty on the live DB. Every historical patch view re-derives from the git refs on demand (`CheckpointDiffQuery.getTurnDiff` / `getFullThreadDiff`).

## The invariant: what must exist for what

Established from `CheckpointReactor.handleRevertRequested`, `CheckpointDiffQuery`, and the capture paths:

- **Revert to turn n of thread T** needs: the read-model checkpoint row for turn n (turn 0 excepted — reconstructed by name), the `turn/<n>` ref, an **active provider session** bound to T with a live git cwd, and sole occupancy of the worktree (other live threads sharing it refuse the revert). A missing ref fails gracefully today: an error activity "Filesystem checkpoint is unavailable for turn n", no state change.
- **Turn-diff view (n−1 → n)** needs `turn/<n>` plus `baseline/<n>` (preferred) or `turn/<n−1>`. Missing ref → `CheckpointRefUnavailableError`, rendered as diff-unavailable; the stored file-summary chips still render.
- **Full-thread diff** needs `turn/0` plus the latest `turn/<n>`.
- **Future captures need no old refs.** Each turn's capture anchors to the `baseline/<n>` written at that turn's own start; a thread whose historical refs are gone captures new turns correctly (there is even an existing log-and-continue path for a missing from-anchor).

Therefore a ref is **provably useless** only when its thread is deleted (permanent, no reopen path). For every other state the refs back a *history-viewing and revert UX* whose value decays with time: a done/cancelled thread can be reopened, an archived one unarchived — but revert additionally requires resuming a session in the original cwd and sole worktree occupancy, which for a fanned-in child (worktree removed, meta repointed to the parent's cwd) is effectively never satisfiable again. Retention beyond "thread deleted" is thus a **product decision about how long finished threads keep their browsable diff history**, not a correctness constraint. The read-model cap (`MAX_THREAD_CHECKPOINTS = 500` per thread) already unreferences refs beyond 500 turns, but no real thread approaches it — it is not the binding bound.

Integration in `WorktreeReaper.runPass`, per project (it already iterates projects with a coalescing worker on a 30-minute schedule plus a startup pass): list refs from `project.workspaceRoot` via the new `CheckpointStore.listCheckpointRefs`, fetch `getThreadRetentionStates` once per pass, run the selector, and delete via the existing `CheckpointStore.deleteCheckpointRefs` in chunks of ~500 refs per `update-ref --stdin` transaction (bounds transaction size and isolates a lock failure to one chunk; the call already carries bounded retry — `REF_DELETE_RETRY` — which the sibling fan-in lock-retry work is hardening further). Failures log and leave the refs for the next pass — GC is best-effort by design, matching the reaper's existing posture. Two projects sharing one repo double-enumerate harmlessly: deletion is idempotent and the second pass finds nothing.

**Safety rules (all enforced by the selector or the existing ops):** only refs under `refs/t3/checkpoints/`; whole-namespace-or-nothing per thread; unknown/undecodable thread → keep; terminal + grace only; live threads never touched, so the sweep can never race an in-flight capture (a thread mid-turn is not terminal, and a terminal thread with a just-finished turn has a fresh `updated_at`).

**Degradation when it fires** (reopen/unarchive after the grace window): old turn rows keep their file-summary chips, but opening an old patch view shows the existing diff-unavailable error, and reverting to an old turn produces the existing "Filesystem checkpoint is unavailable" activity. New turns capture and diff normally from their own fresh baselines. No commits, branches, or worktree contents are affected — checkpoint refs only ever back the timeline-diff/revert UX.

## Rollout and the one-off backlog cleanup (owner-gated)

New code only bounds future growth — except that this design's first pass *is* the backlog cleanup: on deploy, the startup reap pass will delete the ~4,500–4,800 currently-eligible refs on the live repo. That deletion on the live repo is **explicitly owner-gated**: approving this plan approves the mechanism, and the owner should run the dry-run below against the live repo before (or instead of immediately) deploying, to eyeball exactly what the first pass will delete. No separate cleanup script is needed — one mechanism, no drift between the one-off and the steady state.

<Code

If the owner wants a rehearsal beyond the count, the same command with `print(*hits, sep=chr(10))` lists the refs; feeding that list to `git update-ref --stdin` is exactly what the sweep will do — but that manual step should not be needed, and this plan does not propose running it by hand.

## Scope and non-goals

- **No read-model changes.** Checkpoint rows, file-summary chips, activities, and events stay; only git refs are reclaimed. No migration (nothing numbered 1037 needed).
- **No changes to capture, revert, or diff flows.** All existing error paths are reused, none added.
- **The dead `checkpoint_diff_blobs` table is left alone** — it is upstream schema; removing it is not this plan's business.
- **Not pursued:** persisting diffs to SQLite before deleting refs (would preserve history-viewing forever, but adds a write path and storage for a UX that decays in value; can be layered on later without conflicting with this design).
- **`git pack-refs` / repo GC** is untouched; deleting ~5k packed refs rewrites `packed-refs` once per chunk and shrinks it by ~three quarters.

## Risks

- **Grace window mis-sized.** Too short and a human reviewing a finished child late loses its patch views; too long and the repo carries weeks of dead refs. 14 days is a judgement call — it is a one-line constant, and the open question below asks the owner to confirm.
- **Archived-as-terminal is the aggressive half of the policy** (55% of refs). Archive is reversible in the UI, so this is where reopen-after-grace degradation will actually be felt if it ever is. The alternative — treating archive as live — leaves 3.7k refs and most future growth unbounded, since archiving is how threads actually end on this host.
- **Ref-transaction contention** with agents' own git subprocesses: bounded by chunking plus the existing/hardened retry; a failed chunk simply waits for the next 30-minute pass.
