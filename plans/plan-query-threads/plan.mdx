# Query threads: ask the author's fork, not the author

**Recommendation: a "Query" button beside "Comment" in the MDX viewer that forks the document's author into a live, read-only query thread and sends your question there, in the main window, with the passage you selected attached.** The fork carries the author's whole reasoning, so it answers the questions the document alone cannot; it cannot edit, commit, spawn or route, so the author stays the document's single writer and its context stays clean. One query thread serves one revision of one document: later questions on the same revision land in it as new turns, each pinned to its passage; after the author rewrites, the next question forks afresh. **Promote** on an exchange makes the query thread write one anchored reviewer's comment that lands as a chip in the author's composer, beside your own annotations, for you to send with the rest of the review. On the graph the query thread hangs off the author on a dashed edge, labelled by document and counts, never a dependency and never a flag.

**About four days, in two slices**: query + read-only posture + pins + graph leaf first (two and a half days), Promote second (a day and a half). The two bets are **where the query thread's identity lives** (a Loom root with a server-owned role and a new sidecar field, not a new upstream lineage kind) and **how the author's warm prompt cache is kept** (the overlay rides the first turn, as a consult's framing does, so the fork re-reads the author's context at cache price rather than rewriting it).

The same document both sides, open in the right panel of the thread that wrote it. Today a selection offers Comment, and the comment becomes a review turn in that thread. After, it also offers Query; a passage already queried carries a hollow accent pin that opens the query thread at that question, beside the solid amber badge a pending comment already draws.

**What this covers.** The Query affordance and pins in the MDX viewer; the query thread (fork, read-only posture, overlay, one per revision); its place on the graph; Promote into the author's composer and the link back from the author's transcript. **Deferred:** a Query affordance on mobile (query threads are ordinary threads, so chatting in one works there already); resolving the author from the document's signature when the viewing thread is not the author; a "close review" that archives every query thread of a document at once. **Done means:** on a seeded dev instance you select a passage of a plan in its author's right panel, press Query, type a question, and the answer streams in the main window with the passage attached; the thread refuses an edit; a second question lands in the same thread with its own pin; the graph shows the leaf under the author with "2 questions"; Promote puts one anchored comment in the author's composer and, once sent, the author's transcript links back to the query thread. **Two questions at the end:** whether the Query button sends the question or only prefills it, and whether promoting ends the query thread.

## 1. One review pass, start to finish

<Steps>
  <Step at="select" title="You select a passage and press Query.">
    The floating affordance that offers Comment now offers Query beside it. Query opens the same card in query mode: the quoted passage, a question box, a Query button. Nothing touches the author's composer.
  </Step>
  <Step at="fork" title="The server forks the author into a query thread.">
    One RPC (`loom.documentQuery`) spawns a Loom root with role `document-query`, prepares the native session fork from the author's latest finished run (the `/handoff` drafter's exact mechanism), writes the overlay as the kickoff, and dispatches your question as your own first message with the passage attached as a review chip. The main window navigates to the new thread. A mid-turn author defers the fork until its turn ends; the thread shows that it is waiting.
  </Step>
  <Step at="answer" title="The fork answers from the author's reasoning and the code.">
    It has read, search and bash; `edit` and `write` are refused by the same hook a consult fork uses; every state-changing workstream tool is refused server-side. It may consult the live author for anything after its fork point. The overlay tells it to flag a mistake rather than defend the text.
  </Step>
  <Step at="again" title="More questions on the same revision land in the same thread.">
    A second Query on the document, while its content is unchanged, reuses the live query thread: a new turn, its own pin. The pin opens the query thread scrolled to that question.
  </Step>
  <Step at="promote" title="Promote turns an exchange into one anchored comment." badge="slice 2">
    An action on the answer sends a promote turn; the fork writes ONE reviewer's comment, anchored to the passage, with `mcp__t3-code__document_query_promote`. The comment appears as a chip in the author's composer, beside your own annotations and form answers. You send the review turn as you do today. The author's transcript shows the chip with a link back to the query thread.
  </Step>
  <Step at="rewrite" title="The author rewrites; the next question forks afresh." dashed>
    When the document's content changes, the query thread for the old revision is superseded: the next Query archives it (outcome done) and forks a new one. The old thread stays on the graph, receded, and reachable.
  </Step>
</Steps>

### 2.1 Identity: a Loom root with a server-owned role, not a new upstream lineage kind

<Callout tone="decision" title="A query thread is a Loom root: role document-query, forkFromThreadId = the author, plus one sidecar field">
  It is created exactly as a `/handoff` drafter is (`buildDraftForkCommands` in `apps/server/src/loom/handoff/handoffDraft.ts`: `thread.spawn` with `parentThreadId: null`, the author's project, worktree, branch, modes and model, `forkFromThreadId` = the author; then `thread.fork.prepare`; then the kickoff). Its `role` is the discriminator every surface reads, as `handoff-drafter` and `retro-reviewer` already are. It has **no goal** and **no parent**, so it is outside every join barrier, dependency rail, rollup and attention cascade by construction. The "lineage kind" the design asked for lives in the sidecar: `role` plus a new `documentQuery` field naming the document, the revision, the questions and the promotions.
</Callout>

<Columns>
  <Card heading="Rejected: a third upstream lineage literal" tone="neutral" badge="REJECTED" meta={["touches upstream contract", "every fork reader misreads it"]}>

Adding `query` there is an unmarked hunk on an upstream file, and every upstream reader of that field (sidebar nesting, the lineage panel, the fork-from-run badge) would have to learn it. The sidecar already carries `forkFromThreadId` for exactly this relation.

Two Loom domain events write it, replay-safe like `thread.handoff-recorded`: `thread.document-query-asked` (appends a question; the first one also sets `filePath` and `revision`) and `thread.document-query-promoted` (appends a promotion). ### 2.2 The author is the viewing thread; a revision is the content hash

The annotation layer already answers "whose thread does this comment reach": `FilePreviewPanel.tsx` passes the viewing thread as `composerDraftTarget`, and `PlanDocumentContext` carries its `threadRef`. Query forks that same thread. In the flow you described, that is the drafter, because you review a plan in the thread that wrote it. When a plan is opened from another thread (a parent reading a child's plan), Query forks the parent, which is the thread a Comment would have reached too; resolving the true author from the document's `manager_sessions` signature (a pi session id the server can map to a thread) is a later refinement, and the sidecar shape does not foreclose it.

The revision is the SHA-256 of the file's bytes as the server reads them (via `WorkspaceFileSystem.readFile`) at the moment of the question, stored as 12 hex characters. The reuse rule, pure and unit-testable:

<Code
  language="ts"
  filename="apps/server/src/loom/query/documentQuery.ts (new)"
  code={"/** The live query thread to reuse for (author, file, revision), else null: fork afresh. */\nexport const reusableQueryThread = (\n  candidates: ReadonlyArray<LoomThreadWorkstream>,\n  input: { authorThreadId: ThreadId; filePath: string; revision: string },\n) =>\n  candidates.find(\n    (row) =>\n      row.role === DOCUMENT_QUERY_ROLE &&\n      row.forkFromThreadId === input.authorThreadId &&\n      row.documentQuery?.filePath === input.filePath &&\n      row.archivedAt === null &&\n      row.deletedAt === null &&\n      row.outcome === null &&\n      row.documentQuery.revision === input.revision,\n  ) ?? null;\n\n/** Live query threads on the same document whose revision is stale: superseded by this ask. */\nexport const supersededQueryThreads = (candidates, input) =>\n  candidates.filter((row) => /* same author, file, live */ row.documentQuery?.revision !== input.revision);\n"}
/>

A superseded thread gets `thread.outcome.set done` and `thread.archive` in the same RPC that forks the new one, so the graph shows it receded (done cards fade) and the sidebar drops it; it is never deleted. A content hash means a one-character edit by the author forks afresh; that is the agreed rule ("one query thread per document revision"), and the fork is cheap because of §2.3.

### 2.3 Read-only posture without breaking the author's prompt cache

<Callout tone="decision" title="Replay the author's identity verbatim; enforce read-only by hook, credential and allow-list; overlay in the kickoff">
  A consult fork is launched exactly as its target was so pi declares the same tools and the request prefix stays byte-identical to the target's: a warm cache is read, not rewritten (`apps/server/src/loom/workstream/consult.ts`, DL-634). The query thread does the same. The composer's fork replay (`launchIdentity` in `apps/server/src/loom/prompt/sessionComposerLive.ts`) already replays the source's record on a fork's first launch; for role `document-query` it replays on every launch and adds one env var, `T3_LOOM_QUERY_FORK=1`, which a new part beside `consultGuard.ts` honours by refusing `edit` and `write` with a query-specific reason. The thread's MCP credential is issued with a read-only client (`ProviderSessionManager.ts`, one marked hunk keyed on the role), so upstream's `McpToolAccess` refuses every environment write; `callLoomTool` in `registration.ts` widens the read-only allow-list for this role to `workstream_list`, `goal_task_list`, `consult_thread`, `set_thread_title` and the new `document_query_promote`. The overlay (§3) is the kickoff turn, as a consult's framing is the question turn: the most recent text wins over the replayed transcript, and the prefix is untouched.
</Callout>

What this buys: a 150k-token author context re-read at cache price (about a tenth of the write price) on the fork's first turn, every time a revision forks afresh. What it costs: the query thread's tool list is the author's, so `document_query_promote` is reached through `tool_search` at promote time (one declared-tool change, one cache miss, at the end of an exchange), which is the retro reviewer's precedent for `goal_handoff`.

### 2.4 The two RPCs and the one tool

  A WebSocket RPC in `packages/contracts/src/rpc.loom.ts` beside `loom.handoffDraft`, handled in `apps/server/src/loom/wsMethods.ts`. The question's message id is deterministic (`message:server:loom:query:<thread>:<n>`), so the sidecar can name it and a retry lands as the same message. When the author is mid-turn the fork defers; a new leg of `HandoffDrafterReactor` (role-keyed, launch only, no settlement) re-sends the fork, kickoff and queued question once the author's run ends, reading them from the thread's `kickoffBriefPath` brief written at spawn.

The event is what the client watches.

### 2.5 Promote lands as a chip in the author's composer, and the chip links back

<Callout tone="decision" title="A promotion is an event on the query thread, seeded once into the author's composer as a chip naming its source">
  The composer draft store is client state (`apps/web/src/composerDraftStore.ts`, persisted per thread), so a server-written comment reaches it the way an auto-opened surface reaches the right panel: a seed, never an override (`docs/architecture/loom-ui-state-tiers.md`). A loom hook mounted by the author's ChatView (`useSeedPromotedQueryComments` in `apps/web/src/loom/`) watches the environment's shells for query threads with `forkFromThreadId` = this thread and, for each promotion id not yet in `workstreamUiStore.seededPromotionIds` (tier 1, durable per thread), calls `addReviewComment(authorRef, chip)` once and records the id. The chip is an ordinary `mdx-anchor` review comment whose `mdxAnchor` carries `queryThreadId` and `promotionId`: deleting it from the composer is the dismissal (the id stays recorded, so it never reseeds), editing it is yours, and sending it rides the review turn as every annotation does. In the author's transcript the chip renders "Promoted from Query: plan.mdx" as a thread link; in the author's prompt the review-comment rendering in `packages/shared/src/composerContextReferences.ts` (loom hunk) adds one line: "promoted from a query thread: the human and a read-only fork of you discussed this passage; this comment distils that exchange".
</Callout>

Why not deliver the promotion straight to the author as a turn (the `notify_thread` shape): the author would start rewriting on the first promotion, changing the revision and superseding the query thread while you are still mid-review. Batching in your composer keeps one review pass as one author turn, and lets you read and edit the fork's wording before the author sees it.

<Columns>
  <Card heading="Known edge: two clients open on the author" tone="warning" badge="ACCEPTED" meta={["same as any composer draft today"]}>
    Each client seeds the chip once. Sending from one leaves a stale chip in the other, which the human sees and deletes. A composer draft is already client-local; this adds no new class of drift.
  </Card>
  <Card heading="Known edge: the author is archived or deleted" tone="neutral" badge="HANDLED" meta={["promote still records"]}>
    The promotion is recorded on the query thread regardless; the chip seeds whenever the author is next opened. If the author is gone for good the promotion stays visible in the query thread's transcript as the tool call's text.
  </Card>
</Columns>

**Every surface, named.** Entry points: the MDX viewer's selection and block affordances only; no command palette or keybinding (a query is always about a passage). Clients: web and desktop get the affordance; mobile opens and chats in a query thread as any thread, with no Query button and no pins. Providers: pi only, as `/handoff` is (the fork relies on pi's native session; the RPC refuses otherwise). Agents: `document_query_promote` is the one tool, refused outside the role. Contracts: all in `packages/contracts`. Reverse states: archive a query thread as any thread (its pins vanish, its leaf recedes); unarchive restores both; delete the composer chip to dismiss a promotion; a superseded thread is archived, never deleted. Connection modes: two RPCs over the existing WS; nothing client-local but the seed flag. Docs: one user-guide section.

## 6. Verification

Unit, on the pure pieces: `reusableQueryThread` / `supersededQueryThreads` (same author and file, revision match vs mismatch, archived and done candidates ignored); `callLoomTool`'s allow-list for the role (promote and consult run, spawn and submit refused with the query-specific message); the reactor's deferred leg (a mid-turn author: nothing dispatched until its run ends, then fork, kickoff and question in order, idempotent on a second pass); `deriveQueryOverlay` placement (satellite under its author, beside a bridge-only root, receded when archived).

End to end, with the dev-verify recipe (`docs/dev-site-testing.md`) on a seeded instance: open a planner thread that wrote a plan, open the plan in its right panel, select a sentence in §2, press Query, ask "why X"; assert the main window is now on `Query: plan.mdx`, the kickoff bubble reads the overlay, your question is your bubble with the passage chip, and the answer streams. Ask it to "change the sentence to Y" and assert the refusal names the author as the writer. Ask "what has the author done since?" and assert a consult card appears and a consult edge draws on the graph from the leaf to the author. Select a second passage, Query again, assert no new thread (sidebar count unchanged), a second pin, and that clicking the first pin lands on the first question. Open the graph: the leaf under the planner reads "2 questions". Slice 2: press Promote on the second answer, assert the tool call in the query transcript, then open the author: one chip in its composer with the query thread link; delete and reload (no reseed); promote again, send with a hand-written annotation; assert the author's transcript shows both chips, the promoted one linking to the query thread, and the agent's prompt capture (`PromptCaptureMenu`) shows the "promoted from a query thread" line. Edit the plan by hand, Query a third time: the old thread is archived, the leaf receded, a new thread forks.

## 7. Risks and what the code contradicted in the brief

<Callout tone="risk" title="Where the design as discussed meets the code">
  - **"The consult-style read-only tool set and no edit tools."** A consult fork does not narrow its tools; it declares the author's and blocks `edit`/`write` by hook, because the declaration is the cache key. The plan keeps that (§2.3). The posture is the one asked for; the mechanism is enforcement, not declaration.
  - **"A new lineage kind beside subagent and fork."** Upstream's `relationshipToParent` literal is left alone; the kind is the sidecar's role plus `documentQuery` (§2.1).
  - **"Composer prefilled with the anchored quote plus the question."** The plan has the Query button send the question (a fork whose first run precedes `thread.fork.prepare` would start as a fresh session, so the server must sequence the first turn; and a prefill is a second send of text already typed). Question 1 at the end.
  - **"Promotion supersedes the query thread."** The plan supersedes on revision change instead, so several exchanges can be promoted from one thread before the author rewrites; promoting does not archive. Question 2 at the end.
  - **The `thread_fork` tool is not the path.** It is agent-called, pins to `latest_stable`, refuses a thread with no completed run and cannot defer behind a mid-turn source; `launchDraftFork` does all of that and is what `/handoff` ships on.
  - **One kickoff-then-question ordering risk.** The question is dispatched right after the kickoff with `queue_after_active`; when the kickoff turn is already running it is steered in and answered in the same turn, otherwise it starts the next turn and the overlay's last line keeps the kickoff turn silent. If a model still answers the brief alone, the fallback is one combined message (overlay then question) and a human-bubble rendering keyed on a new `query-question` origin; neither changes a contract.
  - **The promoted tool is reached through `tool_search`.** One cache miss at promote time per thread. If that proves annoying, the author's identity can declare the tool for every role (one entry in `families.ts`), which keeps the declaration identical between author and fork.
</Callout>
