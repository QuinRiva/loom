# Loom's workstream history becomes its own table

Loom's workstream Timeline tab, `/retro` and the weekly evals dashboard read Loom's past events (outcomes, flags, gate routes, rework rounds) back out of the orchestration event log. Since pull 15 that log is a one-day replay buffer; those rows survive only because of two marked SQL clauses inside upstream's prune passes. **Replace the read with a sidecar table, `loom_thread_history`, written in the commit transaction beside `loom_thread_workstream`, filled once by fork migration 1070 from the rows the guard has kept alive, and delete the guard.** The table stores the **raw event rows** and the existing fold runs over them unchanged: the one hard-to-reverse bet, taken on its reversible side. Nothing visible changes; about a day of coder work.

## 1. Raw rows, folded on read

The fold in `LoomStore.history` turns eight event types into the six-member `LoomThreadHistoryEntry` union the UI renders. <Sidenote>`apps/server/src/loom/projection/LoomStore.ts` l.945.</Sidenote> It carries a `thread.report-set` onto the `thread.outcome-recorded` that follows it, and gives a V1 `thread.route-taken` (which had no kind) the kind `loop`. It turns V1's `thread.plan-lane-set` into synthetic entries: `yielded` is a raise of `awaiting_orchestrator`, `done` and `cancelled` are outcome sets. The table could store either side of that fold.

A ninth type, `thread.gate-warning` (139 rows on the cockpit since 7 Oct: a thread reopened after its dependents had started, and the like), lands in no table today and has no Timeline entry. It is carried as a stored row only: it joins `HISTORY_EVENT_TYPES` and the `HistoryEventRow` union (payload `kind`, `detail`, `threadIds`, per `packages/contracts/src/orchestrationV2.loom.ts`), and the fold returns nothing for it, as it does for an orphan `report-set`. Showing it is a later contract change, not this PR.

<Callout tone="decision" title="Store the raw rows; keep folding on read">
  The table is a filtered copy of the log's Loom rows: `event_type`, `payload_json`, `command_id`, `stream_version`, the event version. The fold moves its `FROM` and nothing else.
</Callout>

**Why `stream_version` and not `sequence`.** `history(threadId)` orders one thread's rows, and `stream_version` is unique and monotone per thread across both event versions. <Sidenote>0 inversions against `sequence` over all 42,203 rows on the cockpit, 10 Nov.</Sidenote> The log's `sequence` is renumbered when `loom-migrate` moves a tree into another database, so a table keyed on it would need the remap the tool already does for `loom_thread_peer_messages.seq`. <Sidenote>`apps/server/src/cli/loomMigrate.loom.ts` l.1221, "Source order, fresh sequence numbers".</Sidenote> `stream_version` is copied as is. Both tools discover tables by their `thread_id` column, so neither needs a change for the new table. <Sidenote>`loomMigrate.loom.ts` `threadIdNullable`; `apps/server/scripts/migrate-dev-db.ts` l.317.</Sidenote> The index is `(thread_id, stream_version)`.

**Why `event_version`.** `dashboard.py` and `gate_escapes.py` filter `application_event_version = 2`, and pull 15's gate proved their output row-for-row identical before and after a prune. <Sidenote>Pull 15 decision log, DL-1898.</Sidenote> Keeping the column keeps that proof: the scripts change two table names and two column names and produce the same JSON. Dropping it would fold 4,324 V1 outcome rows into `first_verdict` and `finished` for imported threads, moving numbers nobody asked to move.

/>

The type list is a literal, not an import of `HISTORY_EVENT_TYPES`: a migration is frozen at the schema it created. The migration is registered as `[1070, "LoomThreadHistory", Migration1070]` in `apps/server/src/persistence/LoomMigrations.ts` (fork lane, never `Migrations.ts`), and `LoomMigrations.v1copy.test.ts`'s ten-row ledger-tail window shifts to end at 1070. On the cockpit the backfill is one scan of the log: 1.2 s warm, bounded by a cold read of the 7.3 GB file (pull 15's `VACUUM INTO` read it in 32 s), so boot is a minute slower once.

**The ordering constraint.** The backfill is only correct on a database where the guard has protected the rows until the moment it runs. That is every Loom database that exists: the guard shipped in the same pull as the prune. It stops being true the day after any deploy without the guard, so this PR carries the guard's removal and the migration together, and lands before pull 16. The live cockpit has no prune mark yet, so at 10 Nov nothing has been pruned there at all. <Sidenote>`orchestration_v2_projection_metadata` holds only `thread-projections`.</Sidenote> A restore from the kept pre-promotion snapshot re-runs 1070 on boot and backfills again from the full log.

## 3. Writing at commit time

`applyLoomProjectionEvent` in `apps/server/src/loom/projection/loomProjection.ts` runs inside V2's commit transaction, after `EventSink` has appended the events to the log and before upstream's projection applies. <Sidenote>`apps/server/src/orchestration-v2/EventSink.ts` l.475–479: `eventStore.append`, then `applyStoredEvents`.</Sidenote> The domain event it receives has no `stream_version` or `command_id`, but the log row it was just written as does, under a UNIQUE index on `event_id`. So the write is one `INSERT … SELECT` from that row:

## 4. The readers move

The fold under it does not change. Its interface comment says the sidecar table instead of "Read from the event log". <Sidenote>`LoomStore.ts` l.375–380.</Sidenote> `loom.threadHistory` and `/retro`'s attention count call `history` and need nothing. <Sidenote>`apps/server/src/loom/wsMethods.ts` l.261; `apps/server/src/loom/handoff/retroDraft.ts` l.285.</Sidenote>

**The two evals scripts.** Each has one SQL string that names the log; each changes table, id column and version column and nothing else. `order by sequence` becomes `order by thread_id, stream_version`. Both scripts only ever take the first row per thread, through `setdefault`, so per-thread order is all they relied on.

## 8. Risks

- **A path that applies a Loom event without a log row in the same transaction** would insert nothing (the `SELECT` finds no row), and the Timeline would silently miss that entry. Every V2 write goes through `EventSink` (`eventStore.append` then `applyStoredEvents`), and `ProjectionReplay.rebuild` reads the log it replays. No such path exists today; the `loomProjection.test.ts` case in §7 is the tripwire if one appears.
- **Pull 16 rewrites the prune SQL.** With the guard gone that is upstream's file verbatim and conflicts nowhere; this is the point.
- **The backfill runs on a database that was pruned without the guard.** Not possible for any database Loom has booted, and the ordering constraint in §2 keeps it so. The one gap: `t3 doctor compact` (`DatabaseMaintenance.ts`) opens the database without running migrations, so running the new build's `doctor compact` before its first boot would delete the V1 rows unguarded; the deploy notes say not to; the kept pre-promotion snapshot is the recovery if a cockpit database ever loses rows before 1070 runs on it.
- **Boot time.** One cold scan of the 7.3 GB file, under a minute, once.

## Decided

<Callout tone="decision" title="History table only; no archive of upstream's events">
  Carl, 10 Nov, asked what the prune would delete and whether it mattered for his intermittent self-analytics. Of the 1.49 M log rows, 1.36 M are streaming deltas (`turn-item.updated`, `node.updated`, `message.updated`, `provider-turn.updated`, `run.updated`) whose final state the projections keep with timestamps; his trace checks read the pi session files, which the prune never touches; and the kept pre-promotion snapshot archives everything to deploy day. The only Loom signal that fell through was `thread.gate-warning`, so it is carried. His words: "Yes proceed on that basis."
</Callout>
