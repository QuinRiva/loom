# Stale-worktrees visibility surface

## Objective

Give the human one cheap place to see every workstream worktree on disk — who owns it, how old it is, how much disk it costs, and **why the conservative auto-reaper did not delete it** — plus a guarded, human-confirmed Remove action. Done means: a `Worktrees` settings page lists all worktrees across projects with owner/age/size/merge/dirty state and a per-row removal reason, removal of a stale worktree works from the page with server-enforced guardrails, and nothing on the page can delete work that is merely stale without an explicit acknowledgement.

This is a maintenance panel, not a dashboard product. It follows the design principle settled for Phase 3: **auto-reap only provably-dead worktrees; everything else is surfaced, not deleted.** The Wave-1 reaper handles the provably-dead class; this surface exists for everything the reaper deliberately refuses to touch.

The page lists **all** worktrees the classifier finds (grouped/sortable by project when more than one project has any), so the disk total is honest. `Active` rows and `Auto-reap soon` rows carry no action — the former are alive, the latter are the reaper's job. Every other row gets `Remove…`.

## Scope and non-goals

**In:** one read-only scan query, one guarded removal command, one settings page, a nav entry. **Out (deliberately):** auto-refresh/polling or live push events (manual Refresh matches the Diagnostics idiom and this is a maintenance surface); bulk/multi-select removal; any "open in editor / browse diff" affordances; changing reaper policy from the UI; cross-environment aggregation (the page reads the primary environment, like every other settings page); mobile.

## Where it lives: a `Worktrees` settings page

New route `apps/web/src/routes/settings.worktrees.tsx` + `WorktreesSettings.tsx` panel, with a nav entry in `SettingsSidebarNav.tsx` (between Source Control and Connections). It reuses the Diagnostics page idiom wholesale — `SettingsPageContainer`/`SettingsSection`, the `StatsGrid`/`StatBlock` header, `DiagnosticsLastChecked`-style "Checked Ns ago" + refresh button, and the same table styling — so the new UI is mostly composition of existing pieces in `apps/web/src/components/settings/`.

<Callout tone="decision">
  A dedicated settings page, not a section on the Diagnostics page and not a per-thread surface. Diagnostics is process/trace-oriented and already long; worktrees are a per-repo maintenance concern with their own actions. Per-thread surfaces (DiffPanel, workstream cards) are the wrong scope — the whole point is the aggregate view across threads, including orphans that have no thread at all.
</Callout>

## Data flow: on-demand server scan, not projection state

The truth about worktrees lives on disk and in git; the projection only knows threads. So the page issues an on-demand query RPC (exactly like `server.getProcessDiagnostics`): the handler runs the Wave-1 **classification module** (built by the reaper coder: `git worktree list` + projection join → per-worktree classification), layers disk sizing on top, and returns a snapshot with a `readAt` timestamp. Nothing is materialised or kept in sync; Refresh re-scans.

Disk sizing is the only expensive part of the scan (`du` per worktree, bounded concurrency, per-worktree timeout). ~20 worktrees × ~128 MB is a few seconds cold — acceptable for an explicit maintenance query; `sizeBytes` is nullable so a timed-out `du` degrades one cell, not the scan.

Classification meanings, aligned with the reaper brief: `active` = owning thread non-terminal or fan-in unsettled; `reapable` = provably dead, the reaper will take it at its next tick (shown as "Auto-reap soon"); `conflicted` = fan-in conflict escalated and abandoned; `cancelled` = carries a `wip: cancelled` snapshot; `orphaned` = no projection thread claims the path (crash leftover); `deferred-removal` = a cancel-time removal was deferred and lost to a restart; `stale` = none of the above but past the reaper's age threshold with an unmerged/dirty reason.

## The removal action

The server handler **re-classifies the single worktree before acting** — the guardrails are server-enforced, never trusted from a possibly-stale client snapshot:

1. `active` → always refused (message: thread is live / fan-in pending).
2. `dirty` without `acknowledgeDirty`, or unmerged without `acknowledgeUnmerged` → refused; the client re-renders the confirm with the live facts.
3. Otherwise: remove the worktree via `GitWorkflowService.removeWorktree` (force when dirty), **under `WorktreeMutationLock` on the parent repo cwd** — the same serialisation the provisioner and fan-in use, so a removal can never race a concurrent merge.
4. Delete the `ws/…` branch **only when fully merged**; an unmerged branch always survives worktree removal, so acknowledged-unmerged removal loses no commits, only checkout disk.
5. If an owning thread exists, dispatch `thread.meta.update` with `worktreePath: null` (the schema already permits it), and refresh vcs status.

This intentionally does **not** reuse the existing raw `vcs.removeWorktree` RPC that thread-deletion uses (`useThreadActions.ts`): that path has no classification guard, no lock on the parent repo, no branch handling, and no thread-meta cleanup. Server-side, though, the removal tail (steps 3–5) should be the **same routine the Wave-1 reaper calls**, with the acknowledgement flags as the only difference — one removal implementation, two callers.
