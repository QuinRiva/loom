# A gate over several siblings is several loop edges, one verdict, one barrier

A review gate over N siblings is **N loop routes on the reviewer, one per sibling**, which is the shape `routes` already stores; nothing about a stored gate changes. A `needs_rework` names the siblings to reopen (`rework` on `workstream_submit`) and emits **one `thread.route-taken` per named sibling**, so the event schema does not change either. The re-drive planner sends one rework leg per reopened sibling, and sends the **one re-verify leg only when every reopened sibling has routed back** (a cancelled one drops out of the wait). `clean` or `fixed_inline` completes the reviewer and every sibling still open. **One verdict is one round**, counted on the reviewer as today.

Two bets make it small. First, multiplicity by repetition of the records that exist (routes, traversal events, legs) rather than widening any record to a list; the one record that must hold a set is the reviewer's current-round traversal, which becomes `lastRoutes` behind a one-line migration. Second, per-sibling leg ids stay receipt-deduped exactly as today, with the one migration re-keying the historical receipts to the new ids (deterministic: each receipt's `aggregate_id` is the leg's target), so no finished gate in the live database can re-fire; the only state the planner reads is the barrier's. Roughly two coder-days across shared routing, the arm, the planner, the projection, the tool surface, the texts models read, and three small web fixes; no new verdict token, no new table.

<Callout tone="decision" title="What is being approved" focus>
  The model in §1, the six decisions in §2 (each with the alternative it rejects), and the ordered steps in §3. The brief's two questions are decided by the owner, in its Decided line: **the reviewer names the reopened set, and a gate over several siblings refuses a `needs_rework` that names none**; **re-verification waits for the whole set**. §2.2 and §2.3 implement those decisions.
</Callout>

**Scope.** Spawn and scaffold accept one sibling or a list in `gate.rework`; submit gains `rework`; the arm, planner, projection, wakes and web graph handle the set; the texts models read say so. **Not in scope:** several reviewers over one sibling (a coder's `pendingRework` stays one flag, as today), the mobile app (it does not draw the graph; its shell type gains nothing it renders), shipping or human-policy changes. **Done means** the brief's five checks pass on the dev-verify instance with the seeded two-sibling gate, the tests in §5 pass, and `vp check` and `vp run typecheck` are clean. One open question at the end: whether `gate.rework` keeps accepting a bare string. **Base:** this plan is written against `origin/main` at `fe75bb6` (29 Oct); the branch is 2,480 commits behind it with no local commits and is fast-forwarded before any coder starts (a tree task under Build). File and symbol names below are main's.

## 1. The model

A gate is still derived, never stored: the reviewer is the thread whose `routes` carry loop edges, and the gate's siblings are those edges' targets. Today there is one such edge; after this change there may be several, and every pure predicate that already iterates `routes` (`gateSourceFor`, `unresolvedGateSourcesOf`, `isMemberOfUnresolvedGate`, `validateNewNodes`, the graph layout's loop arrows) needs no change at all.

## 2. Decisions

### 2.1 Multiplicity by repetition, not by widening

<Callout tone="decision" title="N loop routes, N traversal events, N legs; one list on the reviewer">
  `WorkstreamRoute` keeps its single `to`. A gate over N siblings is N loop routes with the same `on` and `maxRounds`. A fan-out verdict emits N `thread.route-taken` events in one commit. The planner emits N rework legs and N resolve legs. The only record that must hold a set is the reviewer's **current round's traversals**, `LoomThreadWorkstream.lastRoute` (one record) becoming `lastRoutes` (a list, replaced when the round or kind changes, appended within a round).
</Callout>

<Columns>
  <Column label="Chosen: repeat the record">
    The live cockpit database holds **766 reviewer rows with a loop route** and **267 `thread.workstream-created` events** carrying one; both stay valid as written, because a one-sibling gate is the one-route case of the new shape. `forkJoinLayout.ts` already iterates `m.routes` and draws one return arrow per loop route, so the graph draws the set with no change. `gateSourceFor`, `unresolvedGateSourcesOf`, `isMemberOfUnresolvedGate` and `validateNewNodes` already iterate every route. The `thread.route-taken` payload is unchanged, so the 1,008 stored traversal events replay and the timeline's history fold decodes them as before.
  </Column>
  <Column label="Rejected: `to` becomes a list">
    Widening `WorkstreamRoute.to` and `LoomRouteRecord.to` to arrays would mean rewriting 769 stored `routes` values, versioning or transforming three event payloads on replay (`workstream-created`, `route-taken`, and the history fold in `LoomStore.history`), and touching every reader of `.to`. The brief's "decode that reads both" is the shim the repo rules forbid; the migration route is far more work for the same end state. The one cost of repetition is `maxRounds` written on every loop route of a gate; `gateRoutes` writes the same value on each and the cap is read from the first loop route, as `getGateLoopCap` does today.
  </Column>
</Columns>

### 2.2 The reviewer names the reopened set; a multi-sibling gate refuses a verdict that names none

`workstream_submit` gains `rework?: string[]`: thread ids (or `thread:<id>`) of the gate's loop targets to reopen. Rules, applied by the arm and mirrored by the submit handler so the refusal lands before the report file is written:

- `rework` on an outcome that matches no loop route of the caller is refused: it only accompanies a verdict the gate loops on.
- A name that is not a loop target of the caller's routes is refused, with the targets listed.
- A loop verdict with no `rework` on a gate with **one** loop target reopens that one (today's behaviour, unchanged). On a gate with **several**, it is refused with the targets listed: the owner's decision in the brief ("a gate over several siblings refuses a needs_rework that names none").
- Named targets that are cancelled or missing drop out; if none remain the verdict degrades to `yield`, which generalises today's dead-target rule (R4) from one target to the set.

The pure decision widens: `WorkSubmitRouting.routeTo` becomes `ReadonlyArray<ThreadId>` (empty unless `loop`) and `resolveWith` becomes the list of non-terminal loop targets. `routeWorkSubmit(thread, threads, outcome, rework?)` takes the resolved ids and does the set arithmetic; the three refusals above join the shared `workSubmitRefusal` (`packages/shared/src/workstreamGraph.ts`), which the arm and `handlers/submit.ts` already both call, so neither side can drift.

### 2.3 Re-verification waits for the whole reopened set

The planner derives the barrier from projection state alone. For a non-terminal reviewer whose `lastRoutes` are loop traversals of round r, with members M = the traversals' targets that exist and are not cancelled:

- a member has **routed back** when its own `lastRoutes` holds a `loop-back` of round r to this reviewer;
- the re-verify leg is owed when every member has routed back and at least one exists; its `sources` are the members with their loop-back event ids; its id is unchanged, `server:workstream-gate:<reviewer>:<r>:reverify`, one per round.

The suppression predicate follows the same scoping. `isWaitingInGate`'s source-waiting test counts a loop target only while it holds `pendingRework` or its last outcome is a loop-back of the reviewer's **current** round (`target.lastOutcome.round === thread.gateRounds`); a sibling parked from an earlier round that this round did not rename does not keep the reviewer suppressed. Without that clause, round 2 naming only A, then A cancelled, would leave the reviewer suppressed by B's old loop-back and the dead gate would never surface. `lastOutcome.round` is in the client shell, so the web keeps one predicate.

What the wait does with the ways a member can stop short, none of which is new machinery:

Rejected, and settled by the owner's decision in the brief ("once, when every reopened sibling has resubmitted"): re-verify per resubmission. It needs no barrier, but the reviewer then judges a partial set, and a second `needs_rework` while another member is still reworking would open round r+1 on top of an unfinished round r.

### 2.4 One verdict is one round

`gateRounds` is already assigned from the traversal's `round` on the reviewer, so N events of the same round are one increment and the fold is replay-safe. A reopened sibling's loop-back carries `round = reviewer.gateRounds` as today. The cap check in `routeWorkSubmit` and the cap-breach yield are untouched except that the yield's "gate counterpart" becomes a list of every sibling's latest report.

### 2.5 Per-sibling leg ids, made safe by re-keying the historical receipts

Rework and resolve legs are per sibling, so their command ids gain the target: `server:workstream-gate:<reviewer>:<round>:rework:<sibling>` and `…:resolve:<sibling>`. That is a hazard the brief did not anticipate: the pass input (`listPassInput`, read by `readPassInput` in `redrive.ts`) includes done rows for seven days after their outcome and for as long as any sibling is live, so the planner **re-plans the legs of finished gates** and relies on the receipt under the old id to swallow them. In the live cockpit database 62 done coders hold a `loop-back` and 64 done reviewers hold a `resolve`; a changed id with no receipt would re-deliver a rework resume to a finished coder, reopening it, or a resolve to a reopened sibling.

<Callout tone="decision" title="The migration re-keys the historical receipts; dedupe stays receipt-based, as today">
  Every gate receipt in `orchestration_command_receipts` has `aggregate_id` equal to the leg's target thread (verified over all 158 rework and resolve receipts in the live database: none names the reviewer), so the new id is a pure function of the old row: `UPDATE … SET command_id = command_id || ':' || aggregate_id WHERE command_id GLOB 'server:workstream-gate:*:rework' OR … ':resolve'`. It cannot miss a row. Re-verify receipts keep their id. The planner then plans rework and resolve legs for every traversal exactly as today and lets `dispatchServerCommand`'s receipt check swallow the delivered ones; the only state it reads is the barrier's (§2.3).
</Callout>

Rejected: deciding a leg is owed from the parties' state instead (`pendingRework`, routed back, outcome null). It fails one real shape: a done reviewer holding a `resolve` whose sibling is **reopened later**, by `workstream_set_outcome` none or by a newer gate's rework leg. The sibling's outcome is null again, the reviewer's traversal still matches, the new id has no receipt, and the stale resolve leg would mark the reopened thread done mid-work and clear its attention. The live database has done that reopen 16 times after 8 resolves. A state guard would also inherit a stale `pendingRework` on a sibling whose gate was dissolved mid-round (one live row), which would starve a later gate's rework leg. Rejected too: keeping the old id for a one-sibling gate and adding the suffix only for several, which leaves two id shapes forever.

### 2.6 Stored shape: one column, one migration, no shim

One loom migration, numbered at the **next free loom id when the coder starts** (1067 as of `origin/main` `fe75bb6`: 1060 to 1066 exist and are applied in the live database), `apps/server/src/persistence/Migrations/<n>_LoomMultiSiblingGate.ts`, registered in `LoomMigrations.ts` and never in `Migrations.ts`. Two statements: add `last_routes TEXT NOT NULL DEFAULT '[]'`, fill it with `json_array(json(last_route))` where `last_route` is not null, and drop `last_route` (the column is `NOT NULL` like `routes`, `blocked_by` and `attention`, so no null-to-list decode exists anywhere); then the receipt re-key of §2.5. The cockpit database at `/home/Carl/.t3/cockpit/userdata/statev2.sqlite` (the brief's `~/.t3/userdata/statev2.sqlite` holds only the V1 `state.sqlite`) has 153 rows with a traversal and 158 receipts to re-key. `routes` is untouched. The contract field becomes `lastRoutes: Schema.Array(LoomRouteRecord)`; the V1 importer writes `[]`; it stays omitted from `LoomThreadShellFields`, so no client sees it.

### 2.7 The web graph gets fixes, not drawing

The layout already draws one loop arrow per loop route. Three edits, all in files the brief named:

- `WorkstreamGraph.tsx` loop-edge badge: the open-round dot (`●`, and the wider pill) reads `target?.pendingRework` where `target` is looked up through `gateLoopTargetOf(source)`, i.e. always the first route's sibling. It must read the **edge's own** target, `byId.get(edge.toKey)`. The rounds-of-cap text stays the reviewer's and is the same on every arrow of one gate.
- `WorkstreamTimeline.tsx` gate list: the `<li>` key is `kind:on`, which collides across N loop routes; key by `kind:on:to`. Each route renders its own "loops to X on needs rework (≤2 rounds)" line via `describeRoute`, unchanged.
- `loomFixtures.ts`: a fixture with a three-sibling gate mid-round (two reopened, one holding `pendingRework`), so the preview harness shows the arrows and settles the brief's one unknown.

The history fold renders one "Rework round n → X" row per reopened sibling on the reviewer's timeline; that is the least new drawing and reads correctly.

## 5. Verification

## 6. Risks

- **The receipt re-key and the planner's id drift apart.** Cost: a finished or reopened thread messaged or completed by a stale leg. Guarded by the migration test's equality check (§5): the re-keyed receipt id is asserted equal to `gateLegCommand`'s id for the same row, so the two cannot diverge unnoticed.
- **A barrier that never completes.** A member parked by `needs_human` or quiescence holds the reviewer at "waiting on rework" indefinitely; the orchestrator hears through that member's own notice, as for a single coder today, and the recovery rule (set the reviewer done) is unchanged. No new rail.
- **Arrows overlap in the graph.** Three loops leaving one card share a port; `routeUnderChannel` already pulls overlapping lanes apart, and the preview fixture is the check. If it reads badly the fix is a per-route port offset in `forkJoinLayout.ts`, not a redesign.
- **Two reviewers over one sibling** keep today's ambiguity (`pendingRework` is one flag; `gateSourceFor` takes the first). Out of scope and unchanged.

## As built

Built on `t3/multi-sibling-gate-rework` as steps 1 to 4 and 9 (one coder, one gate, clean first round) then steps 5 to 8 (one coder on the planner tier for the model-read text, one gate with the text veto, one rework round that cut seven derivable clauses). Two coders in sequence rather than the suggested parallel split, because they share one worktree and the contract change breaks every reader until updated. Departures:

- **`isWaitingInGate` keeps the old predicate for a one-sibling gate** and uses the round-scoped test only for several (§2.3 asked for the scoped test everywhere). The coder kept the single-sibling path byte-for-byte per the brief's must-not; the reviewer accepted the reasoning.
- **The round cap is checked before the "name `rework`" refusal** (§2.2 order), so a capped multi-sibling `needs_rework` naming nobody yields to the orchestrator as a cap-breach instead of being refused. Found by the core reviewer, fixed in the surface step.
- **Toolkit `prose.ts` gate sentences were not changed**: the `gate: { rework: coderId }` example the plan names no longer exists on this base, so the tool-description changes live in `defs.ts` alone.
- **The step 7 fixture needed a harness entry** in `apps/web/src/preview/workstreamFixtures.tsx` to be visible; added.
- **`gate.rework` accepts a bare string or a list** (the plan's open question, decided by the orchestrator for the recommended "both"): a `Schema.Union` normalised to one deduped list at the handler boundary, so `x` and `thread:x` make one loop edge.
- **No `forkJoinLayout.ts` port offset.** The brief's one unknown is settled in the preview harness and the seeded dev instance: three arrows from one reviewer read as three loops, dots only on the reopened siblings; the two open badges sit close at narrow widths but overlap nothing.
- **Projection appends within a round**, so a resolved reviewer reopened and resolving again in the same round gains duplicate `resolve` traversals; they plan the same receipted ids, so harmless, noted by the core reviewer.

Migration 1067 was run on a `VACUUM INTO` copy of the live database (173 traversal rows, 178 rework/resolve receipts re-keyed, 89 reverify receipts untouched); the re-drive planner then planned only legs that already held receipts, including after reopening the siblings of every finished reviewer by hand.
