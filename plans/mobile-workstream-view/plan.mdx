## 3. The lane layout

The graph is a list of rows. Each row draws its own slice of the lanes in a narrow SVG at its left edge, the way `git log --graph` does. Rows can therefore be windowed, and can grow with the system font size without the lines coming apart.

```text
lane 0  1  2   slots    row text
     ■                  23:35 · 1 thread
     │  ●               Two rulings: fitout cap           coder · bash · 4m
     ■                  23:05 · 1 thread
     │  ■               Phase 5: updates from new docs    orchestrator · 2 running   Needs you
     │  │  ◎ ─╮ ⟲2/3    Phase 5 plan review               reviewer · gate · round 2 of 3
     │  │  ● ◀╯         Phase 5 updates plan for Jacob    planner · rework round 2 · edit · 1m
     │  │  ∶            ▸ 2 settled
     ■                  21:32 · 10 threads
     │  ◎ ◀┄╮           Held-out tenants: no tuning test  coder · waits on Live page read…
     │  ● ┄┄╯           Live page read as the client      reviewer · awaiting acceptance   Accept?
     │  ●               Republish the seeds               coder · done · report
     ■                  ▸ 13:46 · 12 settled
     ■                  ▸ 08:47 · 6 settled · 1 cancelled
```

Read it top down. Each `■` on lane 0 is a wave on the root's spine, newest first. Phase 5 is a sub-orchestrator, so its children sit one lane in, and its two settled children are one folded row. The solid arrow with `⟲2/3` is a review gate on its second round of three. The dashed arrow is a live wait. The last two rows are whole settled waves, one row each.

### The rules

A **wave** is the children one parent spawned in one turn: same parent, same `spawnGeneration`; a child spawned outside a turn is a wave of one. That is web's rule (`layoutOrchestrator` in `apps/web/src/lib/forkJoinLayout.ts`), restated here in ten lines because web's copy is tangled into its 2D geometry.

1. **Waves newest first**, by their earliest child's creation time. The root's waves each get a caption row with a square on lane 0, the spine.
2. **Inside a wave, a thread sits above what it waits on.** Take each thread nothing else in the wave waits on, newest first, and follow it with the threads it waits on (its `blockedBy` and its gate's rework target), depth first. A reviewer therefore sits directly above the coder it gates, and their arrow is one row long.
3. **A settled wave is one row.** Settled means every member and every descendant has an outcome. The row expands in place when tapped and collapses from its caption. Cancelled threads count as settled and recede like done ones.
4. **A sub-orchestrator indents its children one lane**, without caption rows; its settled waves fold the same way. A settled sub-orchestrator with only settled descendants shows no nested rows until its chevron is tapped. Lanes cap at four; deeper nesting shares the last lane.
5. **A gate arrow** (solid, primary colour, with the round badge) runs from the reviewer to its rework target while the gate is unresolved or once it has looped at least once. A gate that passed clean first time reads `gate · clean` in its row and draws no arrow.
6. **A waits-on arrow** (dashed) is one trunk per waiting thread, joining it to each dependency that is not yet done, with the arrowhead at the waiter. A thread that waits on four others takes one slot, not four. The gate arrow stands in for the dependency between a reviewer and its coder.
7. **An arrow to a folded thread ends at the folded row**, so the lanes continue through collapsed history.
8. **Slots:** shortest arrow first, each takes the first slot free across its rows. Arrows that would need a fifth slot are not drawn; the waiting row still names what it waits on.

The population is every workstream in the live database with 20 or more non-archived sub-threads, read in place and read-only. Most are finished, so the two "forced live" rows re-open the newest waves to approximate mid-flight. Under the rejected rule that draws every recorded dependency, the same data needs 5 slots on Mirvac folded, 6 expanded, and 95 on the largest.

**Gutter width.** Lane `n` is at `20 + 24n` dp. Slot `s` is at the last lane's x plus `22 + 9s`. The gutter ends 12 dp past the last slot, or 18 dp past the last lane when there are no arrows. Two lanes and no arrows is 62 dp; Mirvac is 111 dp; the cap (four lanes, four slots) is 153 dp. The layout takes a slot limit so the gutter never exceeds 40% of the list's width, which matters in the 280 dp unfolded pane.

**How a row draws its slice.**

- Vertical runs are lines from the row's top, or from its dot, to the row's bottom. They are given in percentages, so they stretch with the row.
- Bends and arrowheads are paths in the fixed band around the dot, which sits a fixed distance from the row's top.
- Glyphs follow web's shapes with the phone list's colours. A filled dot is running or done, a ring not started, a ring around a dot waiting. A rounded square is an orchestrator and two small dots a fold.
- Settled rows draw at reduced opacity. Nothing animates.

### The contract

```ts
// apps/mobile/src/features/workstream/laneLayout.loom.ts
type LaneNode = Pick<WorkstreamNode,
  "id" | "parentThreadId" | "spawnGeneration" | "createdAt" | "outcome" | "blockedBy" | "routes" | "gateRounds">;

type LaneRow =
  | { kind: "wave"; key: string; at: string; count: number; gutter: RowGutter }           // caption, square on the spine
  | { kind: "thread"; key: ThreadId; lane: number; orchestrator: boolean; gutter: RowGutter }
  | { kind: "fold"; key: string; lane: number; threadIds: ReadonlyArray<ThreadId>;        // a settled wave or sub-tree
      at: string; settled: number; cancelled: number; gutter: RowGutter };

interface RowGutter {
  lanes: ReadonlyArray<{ lane: number; above: boolean; below: boolean }>;  // which halves carry the lane's line
  forkTo: number | null;                                                   // a branch from this glyph to the next lane
  arcs: ReadonlyArray<{ slot: number; kind: "waits" | "gate"; above: boolean; below: boolean;
                        joins: "none" | "source" | "target"; sourceId: ThreadId }>;
}

interface LaneLayout {
  rows: ReadonlyArray<LaneRow>;
  laneCount: number;
  slotCount: number;
  undrawn: ReadonlySet<ThreadId>;   // waiters whose arrow found no slot
}

function layoutLanes(nodes: ReadonlyArray<LaneNode>, rootId: ThreadId,
  expanded: ReadonlySet<string>, maxSlots: number): LaneLayout
```

The layout reads structure and outcomes only. Activity, steps, flags and round counts are read at render from the node, so a running thread's step ticking over never re-runs it. The round badge resolves `gateRounds` and the cap from `sourceId` at render, as web's graph does.

<Details summary="The measurement script: the rules above as 90 lines of Python, for the coder to check the TypeScript against">

Save it as `lanes.py` and run it from anywhere on the cockpit VM. It opens the live database read-only and prints the totals, then the Mirvac and audit workstreams on their own lines. `python3 lanes.py` is the first table row; `python3 lanes.py 2` forces the newest two waves live; `--expand` unfolds everything.

```python
import collections, json, os, sqlite3, sys

con = sqlite3.connect(f"file:{os.path.expanduser('~')}/.t3/cockpit/userdata/statev2.sqlite?mode=ro", uri=True)
con.row_factory = sqlite3.Row
LIVE_WAVES = int(sys.argv[1]) if len(sys.argv) > 1 and sys.argv[1].isdigit() else 0
EXPAND = "--expand" in sys.argv

def load(root):
    out = {}
    for r in con.execute("""select thread_id id, parent_thread_id parent, spawn_generation gen, created_at created, outcome,
            blocked_by, routes, gate_rounds from loom_thread_workstream
            where root_thread_id = ? and deleted_at is null and archived_at is null""", (root,)):
        n = dict(r)
        n["blocked_by"] = json.loads(n["blocked_by"])
        n["loop_to"] = [x["to"] for x in json.loads(n["routes"]) if x.get("kind") == "loop" and x.get("to")]
        out[n["id"]] = n
    return out

def layout(nodes, root):
    kids = collections.defaultdict(list)
    for n in nodes.values():
        kids[n["parent"]].append(n)
    def waves(parent):  # newest wave first
        groups = collections.defaultdict(list)
        for c in kids[parent]:
            groups[c["gen"] or f"solo:{c['id']}"].append(c)
        return sorted(groups.values(), key=lambda g: min(m["created"] for m in g), reverse=True)
    if LIVE_WAVES:
        def unsettle(n):
            n["outcome"] = None
            for c in kids[n["id"]]: unsettle(c)
        for g in waves(root)[:LIVE_WAVES]:
            for m in g: unsettle(m)
    def settled(n):
        return n["outcome"] is not None and all(settled(c) for c in kids[n["id"]])
    def chain(members):  # each thread nothing waits on, newest first, followed by what it waits on
        ids = {m["id"]: m for m in members}
        deps = lambda m: [ids[d] for d in {*m["blocked_by"], *m["loop_to"]} if d in ids and d != m["id"]]
        waited_on = {d["id"] for m in members for d in deps(m)}
        out, seen = [], set()
        def visit(m):
            if m["id"] in seen: return
            seen.add(m["id"]); out.append(m)
            for d in sorted(deps(m), key=lambda x: x["created"], reverse=True): visit(d)
        newest = sorted(members, key=lambda x: x["created"], reverse=True)
        for m in [m for m in newest if m["id"] not in waited_on] + newest: visit(m)
        return out
    rows, row_of = [], {}
    def fold(n, idx):
        row_of[n["id"]] = idx
        for c in kids[n["id"]]: fold(c, idx)
    def emit(parent, lane):
        for members in waves(parent):
            if not EXPAND and all(settled(m) for m in members):
                rows.append(lane)
                for m in members: fold(m, len(rows) - 1)
                continue
            if lane == 1: rows.append(0)  # the wave's square on the spine
            for m in chain(members):
                rows.append(lane); row_of[m["id"]] = len(rows) - 1
                if kids[m["id"]]:
                    if not EXPAND and settled(m):
                        for c in kids[m["id"]]: fold(c, len(rows) - 1)
                    else: emit(m["id"], lane + 1)
    emit(root, 1)
    spans = []
    for n in nodes.values():
        if n["id"] not in row_of: continue
        here = row_of[n["id"]]
        for target in n["loop_to"]:  # a gate arrow: unresolved, or it has looped
            if target in row_of and row_of[target] != here and (n["outcome"] is None or n["gate_rounds"] > 0):
                spans.append(sorted((here, row_of[target])))
        if n["outcome"] is None:  # one waits-on trunk per waiting thread, to its unfinished dependencies
            held_by = {row_of[d] for d in n["blocked_by"]
                       if d in row_of and row_of[d] != here and d not in n["loop_to"] and nodes[d]["outcome"] != "done"}
            if held_by: spans.append([min(held_by | {here}), max(held_by | {here})])
    slots = []
    for lo, hi in sorted(spans, key=lambda s: s[1] - s[0]):  # shortest first, first free slot
        for used in slots:
            if all(hi < a or lo > b for a, b in used): used.append((lo, hi)); break
        else: slots.append([(lo, hi)])
    return dict(rows=len(rows), lanes=max(rows, default=0) + 1, arcs=len(spans), slots=len(slots))

roots = [r[0] for r in con.execute("""select root_thread_id from loom_thread_workstream
    where deleted_at is null and archived_at is null and parent_thread_id is not null
    group by root_thread_id having count(*) >= 20""")]
results = {root: layout(load(root), root) for root in roots}
print(f"{len(roots)} workstreams of 20+ live sub-threads; live_waves={LIVE_WAVES} expand={EXPAND}")
for key in ("slots", "lanes"):
    print(f"  {key}:", dict(sorted(collections.Counter(r[key] for r in results.values()).items())))
rows = sorted(r["rows"] for r in results.values())
print(f"  rows: median={rows[len(rows)//2]} p90={rows[int(len(rows)*0.9)]} max={rows[-1]}")
for title in ("Mirvac audit via graphtus: execution", "Loom Codebase Audit and Cleanup"):
    root = con.execute("select thread_id from orchestration_v2_projection_threads where title = ?", (title,)).fetchone()[0]
    if root in results: print(f"  {title}: {results[root]}")
```

## 6. Navigation: one route, the same stack folded or unfolded

The workstream is a route, `Workstream`, with the environment and the root thread's id. It stays on the navigation stack in both postures; posture decides only **where it is drawn**. That is what makes "folding and unfolding keeps both" true without any state to synchronise.

- **Cover screen:** the route is a full screen. A child opens on top of it; Back returns to it.
- **Unfolded:** whenever a `Workstream` route is anywhere on the stack, the left pane shows its cards and lanes in place of the thread list, which stays mounted underneath. The route's own screen shows the "Select a thread" placeholder when nothing is open over it. The pane's header has a close button that takes the route off the stack and gives the thread list back.

At most one `Workstream` route is on the stack; opening another replaces it. Picking a thread from the Home list, a notification or a deep link goes through upstream's `selectWorkspaceDetail`. The same module owns the one-shot **dispatch-jump request**: `requestDispatchJump(threadKey, at)` to park it, and a read, finish and subscribe trio shaped like `threadMessageJump.ts`. The sheet writes it and the parent's thread screen consumes it, and those are built by different pieces, so the store sits in the piece both depend on.

<Callout tone="risk" title="The trap: on Android, Back from a thread goes Home unless told otherwise">
  `ThreadRouteScreen` installs `useAndroidWorkspaceBack`, which sends both the system Back and the header arrow to `returnToAndroidWorkspaceList`. </Callout>

**View state.** Which folds are expanded and the scroll offset live in an in-memory map keyed by environment and root, in `workstreamView.loom.ts`. That is the same class as the chat timeline's remembered scroll in `docs/architecture/loom-ui-state-tiers.md`. It survives remounts and the swap between the full screen and the left pane, and resets on reload.

**Sheet.** A routed form sheet, the pattern `ThreadAgentsSheet` uses. **Show where it was dispatched.** The sheet calls `requestDispatchJump` from `workstreamNavigation.loom.ts` with the parent thread and the child's creation time, and opens the parent. It then hands the message id to the phone's existing `requestThreadMessageJump`. If nothing is found the thread simply opens at its end.

**Open report.** `navigate("ThreadFile", …)` with the sub-thread's own id and `fileRoutePathSegments(reportPath)`. Markdown opens rendered, which is already Loom's default on the phone.

## 10. Risks

- **The first run is on Carl's phone.** A defect a five-second look would catch reaches him as an installed APK. Three things reduce that. The two intricate parts are pure and tested. The lanes are rendered from real data where an agent can see them. Each surface added to Home, the thread screen and the workspace layout sits behind its own error boundary, so a crash in new code shows a failure view instead of taking the screen down. The route itself is already behind upstream's per-screen boundary. Nothing makes the layout, the touch targets or the sheet visible before he sees them.
- **The unfolded pane is one element in a 1,080-line upstream layout file** with hinge alignment and pane animations around it. It draws only when the layout is split and a workstream is on the stack, so the cover-screen path cannot be affected by it.
- **Seven upstream mobile files gain or change a marked hunk** (`Stack.tsx`, `AdaptiveWorkspaceLayout.tsx`, `android-workspace-navigation.ts`, `ThreadHeader.tsx`, `ThreadRouteScreen.tsx`, `ThreadDetailScreen.tsx`, `thread-list-v2-items.tsx`). Each is a call or a prop; the code is in Loom files.
- **Shell changes arrive several times a second while agents run.** The view recomputes on each. It is a walk of one sub-tree and a field comparison per node. If it shows on the phone, the remedy is to compare the sub-tree's shells by identity before rebuilding.
- **The dispatch jump is approximate** and bounded. A spawn far back in a long orchestrator thread may not be reached in 20 pages; the thread then opens at its end.
- **The move in web is behaviour-neutral by intent, not by proof.** The moved tests, the typecheck and the fixture comparison are the evidence.
