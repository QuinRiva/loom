# Agent context grows only when someone decides it should

**Goal.** "We don't want to just be constantly incrementing up a test arbitrarily or else some other agents could run into the same issue again soon." Make growth in what Loom agents read every turn a deliberate decision, and stop ordinary Loom work tripping a number nobody is deciding on.

<Callout focus title="What we found">
**The 77,240 vs 77,369 mystery is a rebase, not the machine.** 77,240 was measured before the branch was rebased. The rebase brought in an optional `reason` field on `workstream_set_outcome`, which is exactly 129 bytes and was never re-measured. Both figures reproduce on demand, and the measurement does not depend on the machine or worktree.

**Nothing in Loom's flow is actually guarding the number:**
- `pnpm ship` never runs the test.
- Upstream's GitHub label check only compares the budget file with main's, and `pnpm ship` merges within seconds, so the check usually compares main with itself.
- The one time the check failed (#521), an agent added the label under your login 12 seconds later.

**The test also measures the wrong thing for Loom:**
- Two of its three figures cover Claude and Codex, which Loom does not run.
- The third counts every registered tool, but a root actually carries about 40 KB of the 77 KB and a coder about 10 KB. The rest are deferred behind tool search.
- What a pi agent actually reads goes unmeasured: the work-model addendum, role text, Loom's resident tools and Loom's skills.
</Callout>

**You'll know it works when.**

- An agent changing Loom code, roles or tools never has to touch a budget number unless its change pushes Loom's per-turn context past the limit.
- When a change does push past it, `pnpm ship` stops. The message names which part grew and by how much (for example "orchestrator role +1.2 KB"), and the agent comes to you rather than raising the limit itself.
- An upstream pull re-measures upstream's figure as part of the pull, without a separate Loom bump.
- A figure recorded on a branch is always the figure for the tree that merges.
- **Must not:** add a check that agents learn to satisfy by editing a number. Must not add an upstream-file change that conflicts at every pull. Must not slow `pnpm ship` by more than about a minute.

**Approaches in play.**

- **Recommended.** Keep upstream's test, but measure only upstream's own tools, so its figure moves only when upstream text changes. Add a Loom limit on what Loom puts in front of a root orchestrator and a coder each turn, set at today's size plus a small headroom. `pnpm ship` runs both after its rebase. Under the limit, nobody touches anything. Over it, ship refuses until you approve the increase. Wins if a limit you set once a month or so is enough to make creep a decision.
- An exact-match Loom snapshot like upstream's: every growth shows up as a number change in the PR that caused it. Wins if you want to see every byte, but bumping it becomes routine, which is the pattern you want gone.
- No gate, and a monthly size report from real session files instead (they already record exactly what each agent received). Wins if you would rather keep trimming by periodic audit, as with the three cuts since 5 Oct. Creep is found late.
- Dropped: deleting or skipping upstream's test. It conflicts at every pull and loses the check on Loom edits to upstream tool text.
- Dropped: relying on upstream's GitHub label check. It never runs the test, and agents merge before it matters.

**Decided.** Your answers, 3 Nov:
- Upstream's test: "Measure only upstream's tools, so it moves only on upstream pulls".
- Loom's guard: "A limit you own: ship stops when Loom's per-turn context goes over it".
- Headroom: "2 KB per role (about 750 tokens)".
- Loom's `AGENTS.md`: "Yes, as its own line with its own headroom".

_Assumed:_
- The ship-gate step is in scope whatever you answer, because it fixes the wrong-number problem on its own.
- The Loom limit counts text Loom writes (preamble, work-model addendum, role text, ship policy, roles catalogue, Loom's skills, `bg_*`) plus every MCP tool a Loom role keeps resident, upstream's included, because choosing what is resident is Loom's lever.
- The limit leaves out per-thread data (thread identity, goal tasks), your global `AGENTS.md`, pi-craft and pi-web-access.
- Trims never require touching the limit; whoever trims may lower it.

Redirect any of these if wrong.

**Not doing.** Cutting any text now. Guarding your global `AGENTS.md` or pi-craft, which live outside this repo. Measuring Claude or Codex beyond what upstream's test already does.
