# Built-in roles for every cockpit project

## Objective

Every thread the cockpit launches — in any of its ten projects, and in any project added later — runs with the current role definition for its role (orchestrator, planner, coder, reviewer, researcher, assessor, shipper). Loom ships those seven roles inside the server release as **built-ins**. A project adds only what is genuinely specific to it, as a short file that is **appended** to the built-in — never a copy of it — so a change to loom's roles reaches every project on the next deploy without anyone enumerating projects or hand-merging. And a thread finds its project's additions from anywhere under the repo, because lookup walks up the directory tree to the repository's top level.

Done means, observably: a thread in `cli-proxy` (no `roles/`, not even a git repo) launches with the built-in role text and a seven-role catalogue; a **local** lease-extraction thread (project root three directories below the fathom repo root) launches with the built-in text plus fathom's data-science additions; a loom thread launches with the built-in text plus loom's `pnpm ship` / reliability-boundary additions; and `roleOverlay.test.ts` covers the walk-up and the merge. The evidence for each is the prompt-debug sidecar the server already writes per thread (see Verification).

<Callout tone="decision">
  Mechanism: built-in defaults shipped as `roles/*.md` in the loom release, plus an **additive** per-project overlay at `.t3code/roles/<role>.md`, found by walking up from the thread's working directory to the git top level. No compatibility path for today's "a project file replaces the whole role" behaviour: the loader reads one location for built-ins and one for overlays, and nothing else.

  Settled with Carl: the overlay path, the built-ins as markdown files located from the server module, the git-top-level bound, and that the role-pruning commits land on `main` first. The one open call — how much of fathom's coder/reviewer posture stays in its overlay — is the form at the bottom.
</Callout>

## What is true today

- **Lookup reads exactly one path and never walks up.** `apps/server/src/orchestration/roleOverlay.ts:165-166` reads `<projectRoot>/roles/<slug>.md`; a miss returns `undefined` (line 188) and `listRoleOverlays` returns `[]` when the directory is absent (line 131). The thread then runs with no role text, no tool profile and no catalogue. `.t3code/ship.json`, by contrast, is found by walking to the filesystem root (`packages/shared/src/shipPolicy.ts:19-38`).

For lease-extraction that root is `/home/Carl/.t3/project-roots/fathom-platform/data-pipeline-jobs/lease-extraction`, three levels below the repo root where fathom's `roles` symlink lives — so every local (non-worktree) lease-extraction thread launches roleless.

- **The server already records what each thread was launched with.** `apps/server/src/provider/Drivers/PiDriver.ts:2436` sets `T3_PROMPT_DEBUG_PATH` for every workstream thread, and the pi extension writes the fully assembled prompt — including the appended role overlay — to `<userdata>/prompt-debug/<threadId>.md` on each agent start (`apps/server/src/provider/Drivers/Pi/providerToolExtension.ts:123-135, 264-275`). ## Where the built-ins live at runtime

The built-ins stay where they are: `roles/*.md` at the loom repo root. The server locates that directory from its own module path, the way `apps/server/src/config.ts:286-294` finds the bundled client and `apps/server/src/persistence/NodeSqliteWorkerClient.ts:51-53` distinguishes source from bundle:

- **Deployed release:** the unit runs `apps/server/dist/bin.mjs` with `WorkingDirectory=/home/Carl/loom-releases/current` (the systemd unit; `deployctl.ts` builds each release in place from a git checkout, so `<release>/roles/` is always present — `ls ~/loom-releases/current/roles` shows it today). From `dist/`, the repo root is three levels up.
- **Dev (`vp run dev`) and tests:** plain `node src/bin.ts` / vitest run the `.ts` source, where `roleOverlay.ts` sits at `apps/server/src/orchestration/` — four levels up.

So the constant is a two-branch path, selected by whether `import.meta.url` ends in `.ts` (the `NodeSqliteWorkerClient` test), and the module **asserts the directory exists at load time**. A release without `roles/` is a broken install, and the whole point of this change is that a missing role is never silent again.

The alternative — embedding the seven texts as string constants in a server module, as `retroDraft.ts` does for one role — is rejected on authoring grounds, not mechanism: 270 lines of model-facing prose with a few hundred backticks would live inside template literals, every wording change would be a TypeScript diff, and the cross-family wording review would be reviewing escaped strings. Markdown files are the format every author of this text (Carl, the GPT reviewer, the platform-update skill) already works with.

One consequence worth stating plainly: **the built-ins are the server's copy, not the thread's worktree's.** A loom thread that edits `roles/coder.md` in its worktree no longer changes what threads in that worktree receive; the edit takes effect in a dev instance started from that worktree (`vp run dev`, the `t3code-dev-instance` skill) or after deploy. Today's behaviour — the project root's `roles/` being live — was an accident of loom being the project whose roles they were.

Built-in `skills:` frontmatter keeps working: paths resolve against the built-in directory's parent (the release or repo root), so `skills/mdx-visual-plan` and `skills/workstream-review-gate` resolve to the release's own copies. In production those same skills are also installed globally by deploy (`~/.pi/agent/skills/*` → `~/loom-releases/current/skills/*`); pi resolves symlinks and skips a file it has already loaded (`pi-coding-agent/dist/core/skills.js:323-325`), so the double reference is harmless — and it is what loom threads already do today.

## The project overlay

### Overlay path

The overlay directory is `.t3code/roles/`, beside `.t3code/ship.json`, not a bare `roles/` at the repo root. Three reasons, in order of weight:

1. **Walking up makes an unqualified `roles/` dangerous.** Once lookup climbs from the working directory to `/`, any ancestor directory named `roles/` — an Ansible tree, a docs folder, a `~/roles` someone once made — would be read as agent role overlays. `.t3code/` is namespaced to this tool.
2. **It keeps loom's own `roles/` unambiguous.** With built-ins at `<loom>/roles/`, loom's *project delta* cannot also live at `<loom>/roles/`; it goes to `<loom>/.t3code/roles/`. Every project then has the same shape: built-ins are loom's, `.t3code/` is mine.
3. **`.t3code/` is already "what loom reads from a project"** — the ship policy lives there and is found by a walk of the same shape.

Costs: loom-slack-bridge moves `roles/slack-inbox.md` to `.t3code/roles/slack-inbox.md`; fathom-platform's `.gitignore` gains `/.t3code` next to its existing `/roles` and `/skills` lines (`.gitignore:582-583`), and pi-fathom's `sync_agent_overlay.sh` links `.t3code/roles` instead of `roles`. All three are one-line changes; the sequencing is in the work breakdown.

### Walk-up bound

Lookup starts at `roleProjectRoot` (`ProviderCommandReactor.ts:954` — worktree path or project workspace root, unchanged) and takes the **nearest** `.t3code/roles/` directory at or above it, stopping at the filesystem root. That is the `resolveMergeAuthority` loop (`shipPolicy.ts:19-38`), so the ship policy and the roles are always found in the same place. It does not consult git: cli-proxy is not a repository, and the loader is synchronous. The nearest *directory* wins, not the nearest file — one project directory is the unit, so a role absent from it is "no addition", not "keep looking".

The one non-obvious consequence: a `~/.t3code/roles/` would act as a user-level addition for every project under home. Nothing in this plan creates one; it is noted so nobody creates one by accident.

## Risks and unknowns

- **Built-ins are the server's copy.** Editing `roles/*.md` in a loom worktree no longer affects threads in that worktree (see "Where the built-ins live"). Anyone iterating on role prose needs a dev instance or a deploy. This is the one behaviour a loom author will notice.
- **Every project's delegation-capable threads gain the seven-line catalogue block** and every role gains its overlay text. That is the intended outcome, but it is a prompt-cache invalidation for every thread that restarts after the deploy — the same cost any role edit has today, paid once across all projects.
- **The wording changes are behavioural bets.** The generic reviewer boundary list and the generic shipper procedure are new sentences that thousands of turns will read. The cross-family review exists for this; the planner (this thread's author) adjudicates its findings.
- **How much of fathom's posture lives in its overlay** is the one open decision; both variants are drafted, so Carl's answer changes which files the fathom PR carries, not the loader.

- **cli-proxy is not a git repository**, so its walk reads only `/home/Carl/cli-proxy` itself — correct, and no change for it today (it has no overlay). Making it a repository is Carl's call and needs no loader change.
- **The bundle path assumption** (`dist/` is three levels below the release root) is checked by the load-time assert: a future bundling change that moves the chunk fails the server at boot, not a thread at launch.
