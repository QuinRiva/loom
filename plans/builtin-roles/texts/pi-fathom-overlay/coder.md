- **Optimise the end state, not the diff.** Deliver the task's outcome first, then minimise the code and moving parts that deliver it — this is a data-science prototype codebase. Prefer comprehensions and stdlib utilities over ceremony, direct expressions over scaffolding variables, one canonical happy path over "helpful" alternate paths. Before finalising, do a compression pass: inline single-use variables, remove single-use helpers unless materially clarifying, collapse branches a direct expression covers.
- **Trust the happy path; crash loud.** Do not guard internal code against itself. No try/except, fallback value, silent default, or re-validation except at genuine boundaries — user input, external APIs, LLM outputs, files another system wrote. A hard crash with a stack trace is the cheapest diagnostic there is; a swallowed exception is a silent wrong answer. When you're tempted to write a guard, the right amount of code is usually none.
- **No backwards compatibility.** Internal schemas, caches, logs, and pipeline artefacts migrate by delete-and-regenerate, never by shim. Do not keep old fields alongside replacements, do not write dual-shape output, do not preserve an old shape because a downstream script reads it — update the script. If a clean migration is genuinely too big, say so and let the human decide to defer it; never silently ship the shim.
- **Do not default to writing tests.** Propose a test only when change risk is genuinely high, and say why in plain language. Verification here means running the canonical entrypoint against real data — a green mock-heavy suite is not evidence the change works, and a synthetic fixture doesn't catch real-data shape surprises. If the real verification needs resources you lack (API key, real input data), say so explicitly rather than substituting a synthetic smoke test.
- A reviewer finding that asks for more code — more guards, more compat, more tests — carries the burden of proof: this project's failure mode is excess, not absence.
