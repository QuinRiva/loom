# Cockpit performance remediation

**Objective.** Restore and protect cockpit responsiveness at real workstream load (85+ worktrees, 1,168 nominally-active threads, a PTY per agent), after the production instance (`loom-cockpit.service`) degraded to the point of timing out websocket-ticket mints. **Done means:** total subprocess spawns under 10/s at today's worktree/PTY counts, HTTP p50 under 20 ms after 24 h of uptime, zero orchestration slow-command entries in steady state, and the fan-in retry-loop class structurally impossible — all verified with the same measurement harness that produced the baseline numbers.

This plan synthesises two completed investigations: a live measurement of the production instance (report `e7ee63dc`) and a code audit at HEAD `84d49ab48` (report `c6957453`). Both supersede the earlier write-up in `loom-slack-bridge/docs/cockpit-sluggishness-investigation.md`, which is partly falsified. Every remediation below is a **patch or targeted re-architecture — nothing is removed**: both investigations found that every expensive feature is cheap once gated or cached, and this plan adopts that conclusion.

## What made it slow — the reconciled story

The two investigations agree on the load composition and disagree on the acute trigger. The reconciled picture has three layers.

**Layer 1 — a proven steady-state floor: 53.2 subprocess spawns/s.** Measured composition: `VcsStatusBroadcaster` remote-status polling 27.3/s (51%), repository-identity/detection probes 15.0/s (28%), terminal subprocess poll 10.1/s (19%). Children consume 55% of total CPU; ~43% of the server's own CPU is fork/exec system time. Critically, this floor is **identical in the starved and healthy states** — it is a scaling ceiling (~2× aggregate headroom; terminals are the steepest per-unit driver, starving the main thread at ~50 PTYs), not the acute cause.

**Layer 2 — the acute starvation: two compounding mechanisms, neither yet proven.**

- **Heap-sawtooth hypothesis (measurement, moderate confidence).** The live process runs a ~1.4 GB V8 heap sawtooth (~39 min period, 19.3 MB/min growth, dropping to ~721 MB on major GC). Latency stalls (p95 143 ms, worst 1,184 ms) correlate with concurrent-GC CPU and are uncorrelated with child CPU. Node spawns via `fork()`, so per-spawn cost scales with RSS — measured 0.26 ms at 46 MB vs 0.85 ms at 1,454 MB. A restart (which resets only the heap) restored responsiveness.
- **Projection-stall hypothesis (audit, mechanism proven, load not reproduced).** `refreshThreadShellSummary` runs five unbounded `listByThreadId` scans **inside the command transaction on the single serialised command queue** (`OrchestrationEngine.ts:252-259` → `ProjectionPipeline.ts:771-822`). On the retry-storm thread (13,609 activity rows) one refresh took 9.2 s — and everything behind it on the queue, including the user's next message, waits. At current load the measurement could not reproduce it: queueWait p50 is 1 ms and the only two slow commands since boot were on a thread with just 299 events.

These theories **compound rather than conflict**: a big heap makes all 53 spawns/s costlier, and a multi-second projection stall makes everything queued behind it invisible to the user. Both can be true, and the same amplifier feeds both.

**Layer 3 — the amplifier that connects them: unguarded feedback loops over a 55× inflated thread set.** The fork-only fan-in reactor has no terminal failure state; one incident looped 13,410 times over 6 days, each failure appending an activity row (growing exactly the table `refreshThreadShellSummary` rescans) and raising attention with no unchanged-value guard — and each raise bought a full dispatcher pass (~1.5 s decoding shell snapshots for all 1,168 "active" threads, of which ~21 are genuinely working). Those full-set decode passes at ~1.5/s are also the leading suspect for the heap sawtooth's allocation churn. **A live instance of the same class is running right now**: "worktree removal skipped, workspace is occupied" logged 28× in 43 min for `ws-ws-t3code-84f4cc4c-coder-7b8c915b-coder-ef0c4003`.

### Reconciliation 1 — sidebar VCS load is remote-status polling, not local-status polling

The audit predicted ~21/s of `git status --porcelain` from per-sidebar-row subscriptions; the measurement observed **zero** `status --porcelain` spawns. Reading `VcsStatusBroadcaster.ts` resolves this mechanistically: the audit got the **subscription cardinality** right and the **poll content** wrong. Every rendered sidebar row does open a live per-cwd subscription (`SidebarV2.tsx:515-521` → `streamStatus`), but the subscription loads local status **once** at subscribe time and thereafter serves it from cache, refreshing only on explicit invalidation (event-driven, after git operations). The steady-state poller each subscription retains (`makeRemoteRefreshLoop`, 30 s + 20% jitter) refreshes **remote status only**. So the fix target for the 51% bucket is the **remote batch composition and the subscription cardinality** — the audit's F4-C (a cheap local-status variant for the poller) targets a call that is not being polled, and is dropped from this plan.

What one remote refresh actually spawns (median 9 git processes per cwd per cycle, measured):

- `VcsDriverRegistry.detect` re-probes the repo on **every** status call because its cache TTL is 2 s (`VcsDriverRegistry.ts:15`) — never survives a 30 s cycle: 3 spawns (`rev-parse --is-inside-work-tree`, `--show-toplevel`, `--git-common-dir`). This, not `RepositoryIdentityResolver` alone, explains most of the measured 28% "identity probe" bucket (`--is-inside-work-tree` and `--git-common-dir` at 3.35/s each).
- `readStatusDetailsRemote` (`GitVcsDriverCore.ts:1229-1305`): branch lookup, upstream resolution, divergence `rev-list`, and — duplicated within a single refresh via both `resolveDefaultBranchName` and the `computeAheadCountAgainstBase`/`resolveBaseBranchForNoUpstream` path — `symbolic-ref refs/remotes/origin/HEAD` and `rev-parse --abbrev-ref @{upstream}` (each measured ~2× per cwd per cycle). The no-upstream path additionally runs `readBranchRecency`'s `git for-each-ref refs/heads refs/remotes` — at 56–106 ms the single most expensive command in the system — **per worktree**, even though all ~85 worktrees share one repo's refs.

### Reconciliation 2 — the terminal poll

No tension in substance: exactly 3 spawns/PTY/s confirmed (`pgrep -P`, `ps -p comm=`, and an unconditional full `ps -eo pid=,ppid=` table scan per PTY per second — `Manager.ts:697-843`), no subscriber gate anywhere (`terminalEventListeners` is a bare global Set, `Manager.ts:1220`). This is upstream code whose cost model assumed a handful of human-opened terminals; loom opens a PTY per agent and they persist after every client disconnects. It is the steepest per-unit scaling driver (starvation at ~50 PTYs). The fix is gating and sharing, not interval tuning — a 5 s interval only moves the constant.

### Reconciliation 3 — five corrections carried forward

From the audit, so the plan does not reintroduce falsified claims: (1) `PR_LOOKUP_CACHE_TTL` is keyed by cwd+branch+upstreamRef+epoch, not cwd alone; (2) `useThreadRunningTerminalIds` has three callers (all cosmetic), not zero; (3) `refreshThreadShellSummary` derives eight scalars from five queries, not four; (4) the POSIX terminal inspector costs 3–4 spawns per poll, not one; (5) the fan-in infinite loop lives in the **deferred-removal** branch (`WorkstreamFanInReactor.ts:659`) where `fanInState` is already `completed` — advancing the fan-in state is not by itself a fix; only clearing `worktreePath` (via `repointMeta`) or a terminal failure state stops the guard rematching.

## Scope and non-goals

**In scope:** the seven Wave-0 quick wins, the Wave-1 diagnostic restart, and the four Wave-2 structural items below. All are patches or targeted re-architectures of existing mechanisms.

**Explicitly not doing, adopting both reports' recommendations:**

- **No feature removals.** The terminal-activity label (F5-E), the VCS sidebar chips, and the fork-added cost/token/diff metrics (F2-D) all stay: each is cheap once gated, cached, or computed incrementally, and each carries real UX value.
- **No moving projection off the command transaction (F2-C).** It is architecturally the right end-state but breaks the engine's read-your-writes guarantee (`getPendingTurnStartThreadIds` reads inside the same serial boundary). High risk, separate piece of work — not bundled with a remediation effort whose goal is fast, verifiable relief.
- **Nothing about checkpointing — and the `git add -A` churn in user worktrees is `commitAll`, not `CheckpointReactor`.** The follow-up investigation (report `89f0712d`) falsified that attribution: the measured triple (`git add -A`; `git diff --cached --quiet`; `git rev-parse HEAD`) matches only `commitAll` (`GitVcsDriverCore.ts:2917-2933`), i.e. fan-in reconciliation and worktree provisioning — a real-index path that is already `WorktreeMutationLock`-serialised, child-quiescence-gated and retry-hardened, and whose call rate the fan-in items below reduce at source. `CheckpointReactor` is not a poller at all (no timer; purely turn-start/turn-end events, ~2 captures per turn) and cannot race an agent's git operations: every checkpoint command runs against a throwaway index via `GIT_INDEX_FILE` (`GitVcsDriver.ts:744-754`), so it never touches `.git/index` and never takes `index.lock` — verified empirically. See `docs/architecture/checkpoint-git-isolation.md`.
- **No production deploy as part of this work.** Shipping ends at merge per repo policy; the Wave-1 restart is the one deliberately human-authorised production action in this plan.

The second mechanism: `VcsDriverRegistry`'s `DETECTION_CACHE_TTL` is **2 seconds** (`VcsDriverRegistry.ts:15`), so every 30 s status refresh re-runs the 3-spawn `detectRepository` probe per cwd. A repo's kind at a fixed cwd is stable; raise the TTL to 10 minutes (keep zero TTL on failure, as now).

- **Breaks:** a directory deleted and recreated as a different repo kind serves a stale answer for up to the TTL; a moved worktree keeps a stale toplevel entry until restart. Both acceptable for a prototype — worktree paths are create-once.
- **Acceptance:** `rev-parse --show-toplevel` + `--is-inside-work-tree` + `--git-common-dir` combined under 0.5/s in a 45 s spawn sample (baseline 11.4/s).

### W0-2 · Fan-in: stop the loop, then make the class impossible

Two changes, shipped together (the audit's F1-B + F1-A):

1. **Skip-if-missing guard (stops the live loop today).** In `finaliseRemoval` (`WorkstreamFanInReactor.ts:337-355`), when the child cwd no longer exists on disk, skip the unguarded `commitAll` and go straight to `repointMeta` — the only step that clears `worktreePath` and stops the deferred-removal guard (`:659`) rematching.
2. **Terminal `failed` fan-in state (makes the class impossible).** `ThreadFanInState` is `["none","completed","conflicted"]` (`packages/contracts/src/orchestration.loom.ts:114`) — there is nothing for the error handler (`:698-706`) to write, so it appends an activity, raises attention, and loops forever. Add `"failed"`, write it on unexpected per-child failure, and surface a stuck-fan-in badge in the UI. A `failed` fan-in must **not** release dependents (same semantics as `conflicted`). If the stored shape needs it, the migration is a loom migration numbered ≥1001 in `LoomMigrations.ts` — never in upstream's `Migrations.ts`.

- **Breaks:** nothing; a previously-infinite retry becomes a visible terminal state a human can act on.
- **Acceptance:** the live loop (`ws-ws-t3code-84f4cc4c-…`, 28 skips in 43 min) stops within one pass of deploy; an artificially induced `commitAll` failure lands the child in `failed` exactly once, with exactly one attention raise and no repeats over 24 h.

### W0-3 · Unchanged-value guard on `thread.attention.raise`

`decider.loom.ts:643-681` emits `thread.attention-raised` even when the flag is already set with the same reason, and that event is a `WorkstreamDispatcher` trigger (`WorkstreamDispatcher.ts:3300`) — each redundant raise bought a ~1.5 s full-set pass. Make the command a no-op when reason and payload are unchanged. The fan-in reactor already hand-rolls exactly this guard for `fanin.set` (`WorkstreamFanInReactor.ts:466`), with a comment explaining the self-feeding edge — this moves the same idea to the decider where it belongs.

- **Breaks:** anything relying on a re-raise re-notifying (e.g. an external notification hook firing again for an already-raised thread). Verify no consumer of `thread.attention-raised` depends on repeat delivery before landing; none is known.
- **Acceptance:** raising the same attention reason twice emits one event (assert via event log); dispatcher pass rate stays flat during an induced repeated-raise burst.

### W0-4 · Terminal poll: gate on listeners, share one snapshot per tick

Two orthogonal patches to `Manager.ts` (audit F5-A + F5-C, extended by the measurement's per-command costs):

1. **Listener gate:** skip the poll cycle entirely when `terminalEventListeners.size === 0` — no client is connected, nobody can see the tab label. This zeroes the cost whenever the cockpit is unattended, which is most of the time.
2. **One process snapshot per tick:** replace the per-PTY `pgrep -P` + `ps -p comm=` + full `ps -eo pid=,ppid=` scan (3–4 spawns/PTY/s, `Manager.ts:697-843`) with a single shared `ps -eo pid=,ppid=,comm=` snapshot per tick (or an in-process `/proc` read), answered for all PTYs from the one table. Cost becomes ≤1 spawn/s **total**, independent of PTY count.

`PortDiscovery.registerTerminalProcesses` (`PortScanner.ts:350`) consumes the descendant PID set and must keep receiving it for polled PTYs — the shared snapshot produces the same set. If finer gating is ever wanted, `PortScanner`'s retain-count pattern (`PortScanner.ts:313-330`) is the in-repo model for per-terminal attachment tracking (audit F5-B) — deferred; the two patches above already remove the scaling term.

- **Breaks:** the tab label and the three cosmetic running-terminal indicators freeze while no client is connected (nobody is looking) and update from a snapshot up to 1 s stale (as today).
- **Acceptance:** terminal bucket ≤1 spawn/s with a client attached regardless of PTY count (baseline 3/PTY/s); 0 spawns/s with no clients connected. The projected ~50-PTY starvation ceiling disappears from the scaling table.

### W0-5 · Coalescing workers + `threadsById` index

`WorkstreamDispatcher` already diagnosed this class and fixed itself: it uses `makeCoalescingWorker` with a comment explaining that a pass costs ~1.5 s while triggers arrive at ~1.5/s (`WorkstreamDispatcher.ts:3290-3291`). Three reactors armed by the same high-frequency events still queue every trigger via `makeDrainableWorker` on a payload-free, idempotent full recompute — the precise precondition for coalescing: `WorkstreamFanInReactor.ts:720`, `HandoffDrafterReactor.ts:270`, `WorktreeReaper.ts:242`. Swap all three. In the same change, build a `threadsById` Map once per fan-in pass, replacing the per-child `threads.find` (`:594`) and `hasDependentResident`'s `threads.some` (`:317-329`) — ~1.4 M comparisons per pass at 1,168 threads today.

- **Breaks:** nothing — coalescing is semantics-preserving for idempotent full recomputes (the dispatcher's comment is the proof this codebase already accepts).
- **Acceptance:** during an event burst, each reactor runs at most one pass plus one queued pass (log-assertable); fan-in pass CPU no longer quadratic in thread count.

### W0-6 · Prompt-debug fs off the hot paths

`workstreamPromptDebug.ts:42` runs a blocking `readdirSync` on the event loop per shell snapshot, and `:58` an `existsSync` per shell-stream `thread-upserted` event per subscriber — both serving a **debugging-only** surface. Gate the whole prompt-debug surface behind a dev flag (default off in production). Async+cached is the fallback if the surface turns out to be wanted always-on (question at the bottom).

- **Acceptance:** production config performs zero sync fs calls in `getShellSnapshot` and the shell-stream event path (assert by code inspection + a grep-level lint in review).

### W0-7 · `WHERE state='running'` for the session-set turn scans

`ProjectionPipeline.ts:1802` and `:1827` each run a full `projectionTurnRepository.listByThreadId` (turn rows carry `checkpointFiles` JSON) on every `thread.session-set` — the highest-frequency lifecycle event — purely to find turns with `state === "running"`. Add a filtered repository query and use it at both sites.

- **Acceptance:** `thread.session-set` on a thread with thousands of turns decodes only its running turns (typically 0–1 rows).

## Wave 1 — the acute-cause diagnostic

One authorised production restart, carrying Wave 0 plus instrumentation, discriminates the two acute theories for the cost of seconds of downtime. This is deliberately **before** committing to heap-hunting work that may be unnecessary: Waves 0+2 already shrink both suspected drivers (the attention guard cuts pass frequency; settledness cuts per-pass allocation ~55×; aggregate SQL removes the O(history) scans), so the diagnostic's real job is telling us **what remains**.

**Instrumentation to land with Wave 0 (S, one PR):**

- Start flags for the restart: `--trace-gc` (GC type, pause, heap before/after per collection, to the journal) and an explicit `--max-old-space-size` so the sawtooth ceiling is a chosen number rather than a machine-derived heuristic.
- In-process, permanent (cheap enough to keep): a periodic log line with `v8.getHeapStatistics()` + `monitorEventLoopDelay` percentiles (60 s cadence), and command-queue wait percentiles alongside the existing `orchestration command slow` log so queue stalls are visible below the current 3 s threshold.
- Keep the inspector port available (bind loopback) so a heap snapshot can be taken on demand at sawtooth peak without another restart.

## Wave 2 — structural

Justified independently of the Wave-1 outcome (each removes a mechanism that is real at today's scale), but sequenced after it so the diagnostic's before/after is clean.

### W2-1 · Shell summary: aggregate SQL, then incremental if needed

Replace `refreshThreadShellSummary`'s five list-and-fold scans (`ProjectionPipeline.ts:771-822`) with aggregate queries — `MAX(created_at) WHERE role='user'`, `COUNT(*) WHERE status='pending'`, `SUM` for cost/diff totals, `ORDER BY … LIMIT 1` for the latest token snapshot (audit F2-B). This keeps the recompute-on-every-event shape (replay-exact by construction, low risk) while removing the O(history) row decode — ~90% of the win. Only if the Wave-1 diagnostic or re-measurement shows the aggregate version still hot, follow with incremental-on-write (F2-A: fold the incoming event into the prior row; keep the full recompute for `thread.reverted`, which genuinely rewinds history) — medium risk, so it must earn its way in with evidence.

- **Effort:** S/M (aggregates), M (incremental, conditional). **Risk:** low / medium respectively. **Breaks:** nothing on the wire — same eight scalars.
- **Acceptance:** shell-summary refresh on the 13,609-activity thread drops from 9.2 s to under 50 ms; command queueWait p99 under 100 ms during a synthetic activity burst.

### W2-2 · Settledness-aware server sweeps

The server's "active" predicate is archive-era (`deleted_at IS NULL AND archived_at IS NULL`, `ProjectionSnapshotQuery.ts:899-937`): 1,168 rows vs ~21 genuinely working — a 55× multiplier on every sweep and the client snapshot. Upstream's sidebar settledness (#4026) got no server counterpart — a rebase artefact. Fix: lift the settledness predicate from `packages/client-runtime/src/state/threadSettled.ts` into `@t3tools/shared` (both sides import one definition), add `listWorkingThreadRows`, and migrate consumers **sweep-by-sweep with an explicit per-sweep audit** — a settled-but-not-terminal thread that a sweep stops visiting is a sweep that stops doing its job:

### W2-3 · VCS remote batch slimming + subscription scoping

Three cuts to the 51% bucket, in cost order (per Reconciliation 1, the fix target is the remote batch and cardinality — not local status):

1. **Per-repo topology memo.** Key the default-branch lookup (`symbolic-ref refs/remotes/origin/HEAD`) and `readBranchRecency`'s `for-each-ref` (56–106 ms) by **git common dir**, TTL ≈ one poll cycle — all ~85 worktrees of one repo share the answer, so the most expensive command runs once per repo per cycle instead of per worktree. (S)
2. **Intra-refresh dedupe.** One `readStatusDetailsRemote` invocation currently resolves the upstream ref and default branch twice via its two call paths; thread the resolved values through instead. Removes ~40% of the batch per the measured duplication. (S)
3. **Subscription scoping.** Every rendered sidebar row opens a live per-cwd subscription (`SidebarV2.tsx:515-521`); mount the VCS query only for rows actually on screen (virtualised list or section-visibility gate). Combines multiplicatively with W2-2 shrinking the unsettled row count. The audit's coarser alternative (one poll per project, F4-A) is held in reserve — visible-rows keeps today's UX. (S/M)

- **Breaks:** off-screen rows' PR/branch chips update on scroll-into-view instead of continuously — acceptable.
- **Acceptance:** VCS bucket under 5 spawns/s at 85 worktrees (baseline 27.3/s); `for-each-ref` at most once per repo per cycle in the spawn sample.

### W2-4 · Decider-level unchanged-value guards for all set-style commands

Generalise W0-3: every set-style command in `decider.loom.ts` (attention, fan-in state, plan lane, and siblings) should emit no event when the write is a no-op, in the decider once — not re-derived per call site (the fan-in reactor's hand-rolled guard at `WorkstreamFanInReactor.ts:466` gets deleted in favour of it). This removes the whole class of "redundant write → global sweep" amplification, including future instances.

- **Effort:** S. **Risk:** low; per-command review that no consumer depends on echo events.
- **Acceptance:** replaying any set command with identical payload appends zero events (event-log assertion across the command inventory).
