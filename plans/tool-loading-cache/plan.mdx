# Loading a tool mid-session should cost a few hundred tokens, not a full cache rewrite

**Updating the out-of-date packages does not fix this; a ~20-line hoist in loom's pi extension does, so do both.** The rewrite happens because pi 1.3.0 only uses its cache-safe inline tool loading when the request **starts with pi's system message**, and every loom session starts with notes that two global pi packages inject at `session_start` instead. We are indeed behind — `pi-total-recall` 1.8.1 against 1.9.1, with `@samfp/pi-memory` 1.3.5 vs 1.6.1 and `pi-session-search` 1.4.3 vs 1.6.0 — and I installed the current versions in an isolated pi setup and re-ran the experiment: the newer `pi-memory` no longer writes its note at `session_start`, but `pi-session-search` 1.6.0 still does, **and** `pi-memory`'s new default (per-turn memory through pi's `context` hook) trips a second pi behaviour that defeats inline tool loading outright. Current packages, no fix, Fable 5.1: **0 / 9,655** cacheRead / cacheWrite on the turn after a load. Current packages + `perTurnInjection: false` + the hoist: **9,158 / 1,060**. Since 13 Oct, 99 of 104 post-load turns rewrote the cache ($141 in 6.5 days, about **$650 a month** notional); with the fix the same loads cost about $15 a month. The resident browser toolset, the per-spawn toolset switch and the MDX-skill rewrite no longer earn their keep and are dropped.

Two things the runs show. **Updating alone (K) leaves the rewrite where it is**, because the primer still sits ahead of pi's system message. **Updating with the new memory default also disables the hoist (L):** pi-memory's `context` hook edits the message list on every request, and pi's runner then *collapses every system message into one head carrying all current tools* (`restoreSystemMessages` in `core/extensions/runner.js`) before the hoist ever runs — so the request's `tools` array grows on each load and nothing can anchor an inline addition. That is a pi behaviour, not a pi-memory bug, and it is triggered by any extension that edits messages in `context` (in Carl's set: pi-memory ≥ 1.5 by default; pi-btw and plannotator only when they have one of their own messages to filter out). Hence the recommendation: **take the update for its own fixes, pin `perTurnInjection: false`, and keep the hoist** (M). The hoist is not a stop-gap for old packages; the injecting pattern is what these authors consider correct, and the durable fix belongs in pi (§8 files it). Prefix sizes differ between rows because the isolated pi carries only the recall tools; the shapes are what matter.

Memory quality is the trade. The new hook retrieves memory relevant to each prompt; `perTurnInjection: false` keeps today's one-shot dump (8 KB cap, which the audit already flagged as truncating). Beyond defeating inline tools, the hook also moves its ephemeral block to sit before each *new* user message, so by construction every new human or parent turn re-writes the previous turn's suffix from that point — an inferred cost I did not measure because the first problem already rules the mode out for loom. If pi fixes the collapse upstream, the setting can be revisited.

## 3. The fix: keep pi's system message at the head of every request

<Callout tone="decision" title="Decision: a request-local hoist in loom's pi extension, not a pi patch and not forks of the injecting packages">
  A `context_with_system` handler — the hook pi documents for exactly this ("use `context_with_system` only when a request-local transformation must own the complete transcript, and keep a system message at index zero") — moves the first system message to index 0 when only user-side context precedes it. The saved transcript is unchanged, so relaunch, fork, consult and the session-log scans all see what they see today.
</Callout>

Register it in `LOOM_EXTENSION_PARTS` in `apps/server/src/provider/Drivers/Pi/loomExtension.ts` and name it in that file's header comment. Nothing else in loom changes shape: the composer still materialises one extension file; `promptDebug` still captures the same prompt; the cache warmer's "context still current" check compares pi's *state* messages, not the transformed request, so idle keep-alive pings are unaffected (and the warm ping re-sends the hoisted request it was given, so its prefix matches).

**What changes for agents, and how it is watched.** The system prompt moves from a mid-conversation "Updated system prompt section …" message delivered *after* the memory note, the recent-sessions note and the brief, to the API's `system` field (Codex: `instructions`) ahead of all three — where every model is trained to find it. One literal instance of today's delivery confusing a model: in run A (Haiku 5.5, no fix), the first assistant turn opened with *"I won't reproduce or rewrite my system prompt; that's not something I'll share"* — it read the harness's own prompt-update message as a user request. A scan of the 564 loom sessions since 13 Oct finds **0** first turns mentioning a system prompt that way, so in production the expected visible change is none; the fix is a correction of where the prompt sits, not a behaviour experiment. Watch (§7): that first-turn scan stays at zero after the deploy, and the audit's refusal and hard-failure rates for the first post-deploy week sit inside the 13–19 Oct band.

### 3a. The companion one-liner: stop reshuffling searched-in tools

Loom's extension re-asserts the role's tool profile at every turn (`apply()` in `toolProfilePart`). It rebuilds the active list as *profile → `tool_search` → discovered tools in pi's registration order → `ask_user_question` last*. After a `tool_search`, pi's active order is *previous active → the matches in rank order*, so the first wake after a load almost always changes the order — which rewrites pi's `<tools>` prompt section (its text follows the active order) with no tool added or removed. Today that is a full rewrite ($15 across three forks of planner `01a13979` on 14 Oct). After the hoist it is a ~3k-token appended section patch per loading session (runs G and I show the size: 2,893–2,906 tokens) — about $1–2 a week. Small, but it is three lines in the function being touched and it keeps a spurious prompt patch out of every loading session's transcript, so it rides along.

## 4. The package update and the proxy header

**`pi-total-recall` 1.8.1 → 1.9.1, with `memory.perTurnInjection: false`.** Take the update for its own fixes (indexing on a worker thread so startup no longer freezes pi; atomic index writes; the duplicate-row cleanup) and pin the memory mode so the injection shape stays what the hoist handles (run M). Both are global pi settings, so they touch terminal pi as well as loom: the `~/.pi/agent/settings.json` `memory` block gains `"perTurnInjection": false` beside the existing `consolidationModel`, and the update is `pi update npm:pi-total-recall` (or the equivalent) on the global install — **done by Carl or the parent, not by a child thread**, since it is a live-environment change; the plan's job is to say it is safe and what to set first. Order matters: set the flag *before* updating, so no session ever starts under the context-hook default. 1.6.1 still honours the `memory.consolidationModel` key and the same `~/.pi/memory/memory.db`, so nothing else moves. If Carl prefers the per-turn semantic memory, that is a conscious choice to keep the rewrite until pi fixes the collapse (question 2 at the end).

**cliproxy: request the inline-tools beta.** pi adds `inline-tools-2026-09-15` to its beta list when it uses native tool changes, but cliproxy's configured `anthropic-beta` header replaces pi's list (`/home/Carl/pi-craft/plugins/pi-craft/extensions/cliproxy.ts`, lines 49–61), so the beta is never requested. The `tool_addition` requests worked unflagged in every run through the proxy on Haiku 5.5, Opus 5.5 and Fable 5.1, but that is Anthropic (or the proxy's rebuilt baseline) being lenient. Add the beta to the list with a comment naming why; it is one line in pi-craft, takes effect for every new pi process without a loom deploy, and the proxy's header comment already documents that five betas are forwarded only when the caller asks. Verification in §7 step 3.
