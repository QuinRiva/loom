# Pin every read to its SQLite connection, and move ingestion's one hot read off the worker

**Recommendation.** Make the choice of SQLite connection a property of the code rather than of Effect's layer build order, and move one read — the per-event thread lookup that provider ingestion does about eleven times a second — off the worker-thread reader onto the writer's in-process connection. **About a day, one PR, net about a hundred lines removed, no new connections or machinery.** The measurements say this one move removes **93–98% of ingestion's read wait**, which is **89% of its processing time** today.

It makes two bets. First, that the lane bug is a *typing* bug: reader services reach the read-only connection today by re-providing a shared service tag, and Effect memoises layers by object identity, so which connection a service gets depends on build order — WS replay has never run on the reader, and the usage ledger's writes silently ran on the read-only connection for days. Substituting the read client *inside* each reader service's constructor gives a distinct layer object that cannot collide. Second, that ingestion's lag is head-of-line blocking, not read cost: its lookup is one primary-key join, 0.09 ms in-process, that queues behind whole-set snapshot transactions holding the reader's single permit for up to 8.7 s.

**What you are approving.** The small fix: lane-as-a-type plus that one read in-process, one test that pins the lanes, and a journal line to read the day after deploy. **Not in scope**, each a follow-up with the signal that would justify it (§7): a worker pool, a snapshot cache, moving sweeps to a leaner read, moving the writer back to a worker. **Done means:** every reader-routed service is a distinct layer whose requirement channel names the read client; the shared-tag adapter and the `Layer.fresh` workaround are deleted; ingestion's per-event read runs in-process; the lane test passes; `vp check` and `vp run typecheck` pass. No open questions: four calls you already made in the research discussion are built in — the hot read goes on the writer's existing connection first, `getThreadShellById` stays on the worker, a snapshot cache waits, and there is no pre-merge load harness — and the rest is settled below; annotate any you want reopened.

Vocabulary used throughout, in plain words. The **worker read lane** is loom's second SQLite connection: it lives on a worker thread, is opened `PRAGMA query_only`, and exists so expensive reads do not sit on the event loop or block the writer. The **in-process writer** is the default `SqlClient`, the connection every upstream repository uses. **Ingestion** is the serial fibre that takes each provider event and applies it to the engine. A **shell snapshot** is the whole-set read of every un-archived thread's summary row (2,641 threads, 17–25 MB) that WS connects and background **sweeps** (the PR-tracking, PR-sync and settlement reactors) perform.

The memoisation facts behind the fix (Effect 4.0.0-rc.115, `.repos/effect-smol/packages/effect/src/Layer.ts`): the memo key is the layer *object* (`fromBuildMemo`, lines 380–388); `Layer.effect` memoises, `provide` / `mergeAll` / `fresh` do not; `Layer.provide(X, dep)` re-runs `X.build` with the same memo map, so it changes the environment *offered*, not the *key*; `Layer.fresh` starts a new root map inside which memoisation still applies and is itself unmemoised (hence the ledger's duplicate instance). The one shape proven collision-proof on a booted server is a distinct `Layer.effect` whose constructor substitutes `SqlClient` via `Effect.provideServiceEffect(SqlClient.SqlClient, SqlReadClient)`.

## 2. The lane becomes a type

<Callout tone="decision">
Reader services are built from the repositories' exported constructors with `SqlClient` substituted *inside* the constructor, never by re-providing the shared tag to a layer. The resulting layer object is distinct from upstream's, and its requirement channel names `SqlReadClient`, so no build order can hand it the writer. The shared-tag adapter (`SqlReadClientAsSqlClient`), the `Layer.fresh` copy of the usage ledger, the replay wrapper and the engine re-composition that carried it are deleted; the engine is composed exactly as upstream's `runtimeLayer.ts` composes it.
</Callout>

Two services keep a foot on the reader. `ProjectionSnapshotQuery` keeps its shared tag — dozens of upstream consumers, one instance in the server — and is built in `SqliteLanes.ts` from `makeProjectionSnapshotQuery` on `SqlReadClient`; `server.ts` already substitutes loom's composition for upstream's with one marked line. The usage ledger — one row per terminal provider turn, the Usage page's spend figures — gets a distinct tag `ProjectionUsageLedgerReader` for its aggregate read, while ingestion keeps upstream's `ProjectionUsageLedgerRepositoryLive` for writes: a different layer object, so no collision and no `Layer.fresh`.

**Replay is not routed to the reader.** The earlier reader/writer-split plan intended WS reconnect replay to run on the reader; it never did, the benefit is about 4 ms per 1,000 replayed events, and every extra reader-routed service is another layer to keep collision-proof. That intention is superseded here (§5).

## 3. Ingestion's one hot read runs in-process

<Callout tone="decision">
`getThreadRuntimeContext` — one primary-key join, about eleven calls a second — runs on the in-process default `SqlClient`, the writer's own connection. Zero new connections; this is upstream's own model for every repository. `getThreadShellById`, the other read ingestion triggers, stays on the worker.
</Callout>

Why sharing the writer's connection is safe: the in-process client's plain-statement acquirer releases its permit *before* the synchronous execution, so the read waits only while a write transaction is open — 0.9% of the time, p95 20 ms, max 274 ms — and can never interleave with one. The 274 ms worst case is a bulk delete; the typical wait is nothing.

Why `getThreadShellById` is **not** moved, although its benchmark looked similar: it is the WS fan-out's read (1.6 calls per engine event), and besides the thread row it fetches PR links and aggregates the thread's consult and peer-message history, so its cost grows with thread age — the 0.41 ms benchmark figure came from a cheap thread. An in-process read runs synchronously on the event loop; one returned row does not bound a query.

## 4. The rule a maintainer applies when adding a read

<Callout tone="decision">
**Ordinary repositories** — the event store, receipts, projection repositories, auth sessions, the ledger's write side — stay on the default in-process `SqlClient`, exactly as upstream ships them. **Every `ProjectionSnapshotQuery` method runs on the worker read lane by default**, including the ones that look small: they are the reads whose cost grows with the data. A snapshot-query method moves to the in-process instance only by being named in `POINT_READS` in `SqliteLanes.ts`, and only when it is a measured hot-path read whose cost does not grow with a thread's history. Never re-provide the shared `SqlClient` tag to a layer, and never `Layer.fresh` a repository: both put the lane at the mercy of build order.
</Callout>

This rule is the doc comment on `ProjectionSnapshotQueryLanes`, so it is read where the decision is made.

## 5. What was considered and rejected

<Card heading="A pool of reader workers" tone="neutral" badge="REJECTED" meta={["plateaus at ~1.5x", "new machinery"]}>
  Scaling the reader plateaus at about 1.5x because snapshots are main-thread bound (331 of 388 ms of a lean snapshot is main-thread CPU); the worker only offloads the SQLite part. Taking the one hot read off the lane beats a pool on the metric that matters, at a fraction of the machinery.
</Card>

<Card heading="A keyed ingestion worker (per-thread concurrency)" tone="neutral" badge="REJECTED" meta={["from plans/ingestion-backpressure", "wrong diagnosis"]}>
  Proposed in the earlier ingestion-backpressure plan on the assumption that the serial fibre was computing. It was waiting. After this change the per-event read is about 0.1 ms and the fibre's remaining time is the engine's serial dispatch, which per-thread concurrency cannot overlap.
</Card>

<Card heading="Move the writer back onto a worker thread" tone="neutral" badge="REJECTED" meta={["writer 0.9% busy", "would double command latency"]}>
  The writer moved in-process on 2026-09-21 by accident of a refactor; it stays there now as a decision. At p50 2 ms per transaction and 0.9% duty, an IPC hop on each of the 10–20 statements per command would roughly double command latency to move under 1% of main-thread time off the loop — and would put the point read back over IPC.
</Card>

<Card heading="Route WS reconnect replay to the reader" tone="neutral" badge="REJECTED" meta={["never actually delivered", "~4 ms per 1,000 events"]}>
  Intended by the earlier reader/writer-split plan (`docs/plans/db-lane-reader-writer-split.md`, decision D2's second item) but never delivered because of the memo collision; 1,000 replayed events cost 38 ms, 34 ms of it main-thread decode the reader cannot help with. Every reader-routed service is another layer to keep collision-proof. This plan adds one superseding paragraph under that decision in the earlier doc rather than a second account.
</Card>

<Card heading="A snapshot cache, a FIFO semaphore, a dedicated read connection" tone="neutral" badge="DEFERRED" meta={["each has a journal trigger in §7"]}>
  Real options, none needed to fix the two defects. Each is listed in §7 with the journal signal that would justify it.
</Card>

Of the earlier reader/writer-split plan's decisions, three are honoured and are what makes the point-read-on-the-writer safe: fsync-free commits (`synchronous = NORMAL`), zero cross-process writers, and routing the snapshot queries to the read-only connection. The earlier worker-offload plan's liveness goal is met by the reader lane for the reads that matter; its mechanism no longer applies to the writer.

**The one test.** Today's `SqliteLanes.test.ts` is titled "reader-routed snapshots and replay" and passes whichever lane the services land on — the audit showed replay was on the writer the whole time it was green. Its replacement asserts the lane through the real services. Build `OrchestrationLayerOnSqlReadClient` plus `LoomPersistenceLive` on a temp database (as the existing tests do), then insert a ledger row through the **ledger writer** (`ProjectionUsageLedgerRepositoryLive`) and expect it to succeed, and insert through the **ledger reader** (`ProjectionUsageLedgerReader`) and expect `attempt to write a readonly database`. The ledger is the one repository that exists in both variants, so it is where a collision would show — and it is the collision that actually happened. Mutation check while writing it: replace `onReadLane` with a shared-tag re-provide and the test must fail.
